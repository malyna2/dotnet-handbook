# Частина 1 · Зверніть увагу

> **Призначення цієї сторінки.** Тут зібрано найпоширеніші пастки, що призводять до хибних відповідей у частині 1, по одному рядку на кожну: як виглядає пастка, який механізм робить її небезпечною та як її уникнути. Перечитайте перед співбесідою чи перевіркою коду; повне пояснення є в розділі з першої колонки.

| Розділ | Пастка | Чому це небезпечно | Як виправити |
|---|---|---|---|
| [4](#chapter-4-async-essentials) | `async void` для запуску без очікування | Немає `Task`, який міг би передати exception (виняток): побудовник методу повторно викидає його в захопленому контексті або потоці пулу, `catch` викликача не спрацьовує, і процес завершується. | Повертайте `Task`. Справжні фонові завдання запускайте через queue (чергу) або `BackgroundService`, що відстежує збої; `async void` використовуйте лише для handlers (обробників) events (подій), огорнувши весь код у `try/catch`. |
| [4](#chapter-4-async-essentials) | `await Task.WhenAll(...)` журналює лише одну помилку | `await` повторно викидає лише перший збережений exception; інші залишаються в задачі. | Збережіть задачу `WhenAll` у змінній і журналюйте `task.Exception?.InnerExceptions` (значення null, якщо задачу скасовано). |
| [4](#chapter-4-async-essentials) | `.Result`, `.Wait()`, `.GetAwaiter().GetResult()` під час обробки запиту | Кожен виклик закріплює потік пулу на весь час очікування; продовження, які могли б його звільнити, стають у queue за новими запитами, а пул повільно додає потоки. Усі endpoints (кінцеві точки) сповільнюються, хоча процесор майже не завантажений. | Асинхронність на всіх рівнях; стежте за довжиною queue thread pool (пулу потоків) і кількістю потоків. |
| [4](#chapter-4-async-essentials) | `new HttpClient()` для кожного виклику | Кожен клієнт створює власний connection pool (пул з'єднань); кожне закрите з'єднання утримує порт у стані `TIME_WAIT` (60 с у Linux), а App Service має 128 портів SNAT на екземпляр і призначення. | `IHttpClientFactory` або один довготривалий клієнт із `PooledConnectionLifetime`. |
| [7](#chapter-7-data-access) | Ліниве завантаження або читання навігаційної властивості в циклі | Кожен доступ до навігаційної властивості виконує окремий запит: 1 + N обмінів із базою; плани кожного запиту дешеві, тому жоден із них не показує загальну вартість. | `Include` або проєкція; рахуйте запити на кожен запит до застосунку; вимкніть ліниве завантаження. |
| [7](#chapter-7-data-access) | Запити з відстеженням на endpoints лише для читання | Механізм відстеження зберігає знімок і запис у карті ідентичності для кожного повернутого рядка, хоча їх ніхто не зберігатиме. | `AsNoTracking()` або проєкція. |
| [7](#chapter-7-data-access) | Неправильний порядок колонок у складеному індексі | Індекс упорядковано зліва направо. Без першої колонки немає суцільного діапазону для пошуку, тож відбувається сканування; якщо першою йде колонка діапазону, колонка рівності стає фільтром для кожного рядка. | Спершу колонки рівності, потім діапазону або сортування; перевірте наявність обох у предикаті пошуку. |
| [7](#chapter-7-data-access) | Функція чи перетворення над колонкою | `LOWER(Email)` або порівняння колонки `varchar` із параметром `nvarchar` запитує значення, яких немає в індексі, тому відбувається сканування (у досліді — 888 читань проти 3). | Порівнюйте початкову колонку з параметром правильного типу (`IsUnicode(false)`, `DbString { IsAnsi = true }`); замість `LOWER` використовуйте зіставлення без урахування регістру. |
| [11](#chapter-11-messaging-and-background-work) | Handler працює довше, ніж діє блокування | Блокування — це оренда (типово 1 хвилина, щонайбільше 5); після її завершення інший consumer (споживач) отримує повідомлення, поки ви ще працюєте. | `ServiceBusProcessor` з поновленням блокування, без надмірних пакетів і попереднього завантаження; handler має бути ідемпотентним. |
| [11](#chapter-11-messaging-and-background-work) | Дедуплікація з перевіркою перед дією | Дві паралельні копії проходять перевірку, перш ніж будь-яка запише ідентифікатор; збій між побічним ефектом і записом повторює цей ефект. | Спершу закріпіть ідентифікатор: додайте його під унікальним ключем у транзакції з побічним ефектом; передавайте ключ зовнішнім API. |
| [11](#chapter-11-messaging-and-background-work) | «Виявлення дублікатів робить нас ідемпотентними» | Воно відкидає повторні *надсилання* в межах вікна, але повторно доставлене повідомлення — це те саме повідомлення, якого механізм не бачить. | Залиште його для відправників, але все одно зробіть кожен handler ідемпотентним. |
| [11](#chapter-11-messaging-and-background-work) | Голий `202` без `Location` | Клієнт не може знайти результат, а повторний `POST` запускає другу роботу. | `202` із `Location` і `Retry-After`; ресурс стану відповідає кодом 200, потім 303; для `POST` використовуйте idempotency key (ключ ідемпотентності). |
| [16](#chapter-16-working-like-a-middle-developer) | Коментар до перевірки без умови | «Тут може бути проблема» неможливо перевірити, тож сперечатися чи ігнорувати його дешевше, ніж щось робити. | Умова → механізм → вартість → виправлення з позначкою `blocking:`, `suggestion:`, `nit:` або `question:`. |
| [16](#chapter-16-working-like-a-middle-developer) | Завищена точкова оцінка | Кроки, яких ви не можете уявити, не потрапляють до суми, тому похибка завжди зростає в один бік, а запас приховує припущення, що визначає результат. | Діапазон на основі фактичних даних для схожої роботи, із зазначенням ключового припущення; переоцініть, щойно воно порушиться. |
| [16](#chapter-16-working-like-a-middle-developer) | Виконання нечіткого завдання без уточнень | Неправильне тлумачення виявиться після написання коду, коли виправляти його найдорожче. | Перш ніж писати код, коротко опишіть проблему й свої запитання. |
| [9](#chapter-9-exceptions-logging-and-first-diagnosis) | `throw ex;` | Stack trace (трасування стека) починається заново з повторного викидання, тож кадр, у якому виник exception, зникає, а журнал указує на блок `catch`. | `throw;` або обгорніть exception, зберігши початковий у `InnerException`. |
| [9](#chapter-9-exceptions-logging-and-first-diagnosis) | Запис у журнал і повторне викидання на кожному рівні | Один збій створює N записів `Error`, кожен із неповною історією. | Журналюйте один раз — на межі, що обробляє збій. |
| [9](#chapter-9-exceptions-logging-and-first-diagnosis) | `LogInformation($"…")` | Провайдер отримує готовий рядок: немає властивостей для запитів, а кожне значення створює новий шаблон повідомлення. | Використовуйте шаблони повідомлень; для hot paths (гарячих шляхів) — `[LoggerMessage]`. |
| [1](#chapter-1-c-essentials) | `==` для `object` або в узагальненні `where T : class` | Оператори зв'язуються на етапі компіляції, тож порівнюються посилання без попередження. | Порівнюйте через фактичний тип або використовуйте `Equals`. |
| [1](#chapter-1-c-essentials) | Запит EF оголошено як `IEnumerable<T>` | Викликається `Enumerable.Where`: подальші фільтри виконуються в C#, а кожне перебирання знову запускає SQL. | Зберігайте `IQueryable<T>` до фільтрації; матеріалізуйте лише раз. |
| [1](#chapter-1-c-essentials) | Довіра до анотацій nullable у десеріалізованих даних | Вони діють лише під час компіляції; серіалізатор записує `null` у властивість, що не допускає null. | `required`, `RespectNullableAnnotations`, `ArgumentNullException.ThrowIfNull`. |
| [5](#chapter-5-http-and-web-apis) | Singleton приймає scoped `DbContext` | Його отримують із кореневої області й ніколи не звільняють: один контекст використовують усі запити й потоки. Перевірка виконується лише в Development. | Scoped-залежність або `IServiceScopeFactory` / `IDbContextFactory`; у Development увімкніть `ValidateOnBuild`. |
| [5](#chapter-5-http-and-web-apis) | `UseAuthorization` перед `UseAuthentication` або `UseRouting` | Авторизація читає `User` і метадані endpoint, яких ще немає: повертається 401 для дійсних токенів або 500. | Спершу routing (маршрутизація), потім автентифікація, а за нею авторизація. |
| [8](#chapter-8-testing) | Тести на EF-провайдері in-memory | SQL не виконується: унікальні індекси, зіставлення й транзакції не застосовуються, тож проходять тести коду, який реальний рушій відхиляє. | Для всього, що взаємодіє із SQL, використовуйте продакшенний рушій у Testcontainers. |
| [8](#chapter-8-testing) | Окремо проходить, а в наборі — ні | Класи тестів виконуються паралельно й мають спільні статичні дані, фікстури та рядки бази. | Кожен тест має власні дані; спільні ресурси між класами захищайте через `[Collection]`. |
| [10](#chapter-10-design-basics) | Шаблон «заради гнучкості» | Кожен читач платить за опосередкування, а зміна, до якої готувалися, зазвичай так і не настає. | Напишіть простий варіант; переходьте до шаблону, коли проблема повториться. |
| [13](#chapter-13-git-and-cicd) | Rebase гілки, яку хтось уже отримав | Rebase замінює коміти новими ідентифікаторами; наступне надсилання потребує примусової команди й перезапише чужі зміни. | У спільних гілках зливайте зміни; rebase робіть лише для власної роботи, яку ще не надсилали. |
| [13](#chapter-13-git-and-cicd) | Додавання вже зафіксованого файла до `.gitignore` | Правило ігнорування стосується лише невідстежуваних файлів; файл лишається в кожному коміті, зокрема й секрети. | Виконайте `git rm --cached` і замініть кожен секрет, який колись потрапив до коміту. |
| [12](#chapter-12-security-essentials) | Авторизація endpoint, а не запису | Політика бачить користувача, але не власника замовлення з `id` 42, тож будь-який авторизований користувач може прочитати будь-яке замовлення. | Кожного разу перевіряйте власника в запиті (`WHERE OwnerId = @user`). |
| [12](#chapter-12-security-essentials) | Довіра до CORS як захисту endpoint | Браузер усе одно надсилає простий міждоменний запит; CORS лише приховує відповідь від скрипту-викликувача. | На сервері використовуйте авторизацію й захист від підроблення запитів; CORS визначає, що браузерам дозволено читати. |
| [15](#chapter-15-dates-money-and-strings) | `double` для грошей | Більшість сум у центах не має точного двійкового представлення, тож суми й порівняння відхиляються, а округлення не відновить значення, уже нижче середини інтервалу. | `decimal`, найменші одиниці з валютою й одне явне правило округлення. |
| [15](#chapter-15-dates-money-and-strings) | `DateTime.Now` або `Kind = Unspecified` у сховищі | На кожному сервері й під час кожної зміни переходу на літній час це значення позначає іншу мить. | Зберігайте UTC або `DateTimeOffset`; часовий пояс користувача зберігайте окремо; для «зараз» використовуйте `TimeProvider`. |
