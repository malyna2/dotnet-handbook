# Розділ 34: Поглиблений розгляд фронтенду й повного стека

[Розділ 6: Основи фронтенду](#chapter-6-frontend-essentials) пояснив механізми браузера: pipeline (конвеєр) рендерингу, цикл events (подій), модель React «рендеринг і ефект», CORS і файли cookie з боку браузера. У цьому розділі йдеться про рішення, які на цій основі ухвалює старший розробник повного стека, зазвичай для команди: де створювати HTML; де зберігати стан і як його кешувати; що сповільнює фронтенд і як довести, що він працює швидко; як тестувати інтерфейс без нестабільного набору тестів; як не допустити запуску впровадженого сценарію; як SPA має автентифікуватися у вашому API.

Перша половина охоплює архітектуру фронтенду: стратегії рендерингу, керування станом у масштабі, продуктивність, тестування й політику безпеки вмісту. Друга — межу повного стека з боку .NET: автентифікацію SPA та Backend-for-Frontend, REST і GraphQL, завантаження файлів, SignalR у браузері, Blazor і нативні клієнти на C#, а також докладну доступність. Як і в розділі 6, приклади JavaScript і TypeScript працюють у репозиторії (`verify/frontend/ch34`), крім кількох, яким потрібні справжній браузер або запущений сервер; для них це зазначено окремо.

## Стратегії рендерингу: CSR, SSR, SSG, потокова передача й гідратація

Місце створення HTML визначає, що користувач побачить першим, скільки JavaScript треба завантажити перед початком роботи сторінки та що робитимуть ваші сервери для кожного запиту. На кожній архітектурній зустрічі згадують п’ять понять.

- **CSR (рендеринг на боці клієнта).** Сервер надсилає майже порожню HTML-оболонку й пакет JavaScript. Браузер завантажує й виконує пакет, отримує дані з API та будує DOM. Хостинг статичний і дешевий. Користувач бачить порожній екран або каркас, доки все це не завершиться, а пошуковий робот, який не запускає JavaScript, нічого не побачить.
- **SSR (рендеринг на боці сервера).** Сервер для кожного запиту виконує компоненти й надсилає справжній HTML, тож вміст з’являється під час першого кадру. Потім у браузері завантажується той самий JavaScript, що робить сторінку інтерактивною. Кожен запит витрачає процесор сервера, а перед надсиланням сторінки серверу потрібні дані.
- **SSG (генерація статичного сайту).** Компоненти запускаються один раз, *під час збирання*, а HTML розгортається як статичні файли в CDN. Перший байт надходить якнайшвидше, але вміст не новіший за останнє збирання. Інкрементальні різновиди повторно генерують сторінки за розкладом або на запит.
- **Потоковий SSR.** Замість очікування найповільніших даних сервер надсилає HTML частинами, коли вони готові: заголовок і макет одразу, повільний список товарів — після завершення запиту, а до того — заповнювач. React робить це на сервері за допомогою меж `<Suspense>`; у статичному SSR Blazor для цього є *потоковий рендеринг*.
- **Гідратація** перетворює HTML, відрендерений на сервері, на робочий застосунок: JavaScript на боці клієнта повторно запускає ті самі компоненти, проходить наявний DOM і додає до нього handlers (обробники) events і стан замість створення нових вузлів.

```text
           first byte   content visible           interactive
 CSR       fast ──────► after JS download+run+fetch ─► same moment
 SSR       after data ─► on first paint ────────────► after JS download + hydration
 SSG       fastest ────► on first paint ────────────► after JS download + hydration
 Streaming fast ──────► shell first, parts as ready ─► per part, as each hydrates
```

> **Зверніть увагу.** **Чому SSR може виглядати готовим, але не реагувати на натискання.** Після першого кадру сторінка SSR *виглядає* готовою, але нічого не працює, доки не буде завантажено, розібрано й гідратовано JavaScript. На телефоні середнього класу це може тривати кілька секунд. У цей проміжок натискання нічого не робить або відтворюється пізніше. Отже, SSR покращує LCP, але сам собою не покращує INP і не зменшує обсяг JavaScript — він лише переносить витрати. Менше JavaScript постачають інші механізми: *острови* (гідратуються лише інтерактивні частини, решта залишається статичним HTML), серверні компоненти React (виконуються лише на сервері й не передають JavaScript) і статичний SSR Blazor з інтерактивністю окремих компонентів.

Для гідратації також діє правило правильності: перший рендер клієнта має створити точно такий самий HTML, як сервер. Усе, що відрізняється між середовищами, порушує це правило:

```tsx
function LastUpdated() {
  return <p>Updated at {new Date().toISOString()}</p>;   // a different value on server and client
}
```

Якщо HTML створено на сервері о 10:00:00, а гідратація відбувається через дві секунди, текст уже не збігається. React повідомляє про *невідповідність гідратації* як про помилку, з якої можна відновитися: відкидає серверний HTML цієї частини й рендерить її ще раз на клієнті. Тож ви оплачуєте рендеринг і на сервері, і на клієнті, а вміст блимає (тест репозиторію показує помилку й заміну серверного значення клієнтським). Зазвичай винні час і дати (зокрема часові пояси), випадкові ідентифікатори, перевірки `window` чи `localStorage` під час рендерингу та форматування за локаллю. Виправлення: передайте серверне значення клієнту як дані, щоб обидві сторони відрендерили те саме, або рендерте залежну від середовища частину лише після гідратації в ефекті. `suppressHydrationWarning` приховує одне невиправне розходження, наприклад часову мітку; у такому випадку React не виправляє текст.

| Вміст | Стратегія |
|---|---|
| Маркетингові сторінки, документація, блог: публічні, рідко змінюються | SSG (з інкрементальною регенерацією, якщо змінюються щодня) |
| Публічні дані для SEO, залежні від запиту (сторінки товарів, результати пошуку) | SSR; потокова передача, якщо частина даних повільна |
| Панель після входу або внутрішній бізнес-застосунок | CSR підходить: пошукові роботи його не індексують, а інтерактивність важливіша |
| Переважно статична сторінка з кількома інтерактивними віджетами | Острови або статичний SSR Blazor з інтерактивними компонентами |

> **Рекомендація.** Обирайте стратегію для кожного маршруту, а не компанії загалом. Метафреймворк (Next.js, Nuxt, SSR Angular, Blazor Web Apps) дає змогу розмістити маркетингові сторінки статично, сторінки товарів відрендерити на сервері, а розділ облікового запису — на клієнті в одній кодовій базі. Вимірюйте до й після: витрати сервера та гідратації у SSR реальні, тож рішення має спиратися на LCP та INP реальних користувачів, а не на моду.

## Керування станом у масштабі

Більшість суперечок про «керування станом» змішує два різновиди стану, для яких потрібні різні інструменти.

- **Стан сервера** — копія на боці клієнта даних, власником яких є сервер: список замовлень, профіль користувача, сьогоднішні ціни. Щойно отримані дані можуть застаріти, їх можуть змінювати інші користувачі, а для них потрібні отримання, кешування, усунення дублікатів, оновлення й інвалідація кешу. Це проблема кешування, така сама, як описана для сервера в [розділі 18](#chapter-18-data-in-depth).
- **Стан клієнта** існує лише в браузері: відкрите модальне вікно, текст незаповненої форми, вибрана вкладка, тема. Він належить інтерфейсу, не застаріває й зазвичай локальний для компонента.

Більшість помилок SPA міститься у стані сервера, написаному вручну: `useEffect`, що завантажує дані в `useState`. Це переганяння, про яке йшлося у вправі розділу 6, відсутній стан завантаження чи помилки, два компоненти, що завантажують той самий список, список, який не оновлюється після редагування. **Бібліотеки отримання даних** трактують стан сервера як кеш із ключем *запиту*. TanStack Query (React, Vue та інші), SWR, RTK Query й API ресурсів Angular працюють за цим принципом:

```tsx
import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";

type Order = { id: number; status: string };

function useOrders() {
  return useQuery({
    queryKey: ["orders"],                       // the cache key: same key, same cache entry
    queryFn: async (): Promise<Order[]> => {
      const res = await fetch("/api/orders");
      if (!res.ok) throw new Error(`Orders failed: ${res.status}`);
      return res.json();
    },
    staleTime: 30_000,                          // fresh for 30 s: no refetch on mount or focus
  });
}

function OrderCount() {
  const { data, isPending, error } = useOrders();
  if (isPending) return <p>Loading…</p>;
  if (error) return <p role="alert">{error.message}</p>;
  return <p>{data.length} orders</p>;
}

function CancelButton({ id }: { id: number }) {
  const queryClient = useQueryClient();
  const cancel = useMutation({
    mutationFn: () => fetch(`/api/orders/${id}/cancel`, { method: "POST" }),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ["orders"] }),  // refetch the list
  });
  return <button onClick={() => cancel.mutate()} disabled={cancel.isPending}>Cancel</button>;
}
```

Механізм, як демонструють тести репозиторію: два одночасно змонтовані компоненти `OrderCount` надсилають **один** запит, бо підписані на запис `["orders"]`; третій компонент, змонтований до завершення `staleTime`, отримує дані з кешу без запиту; мутація скасування позначає запис застарілим і завантажує його повторно для кожного підписника. Бібліотека також бере на себе те, про що часто забуває самописний код: скасування вже непотрібного запиту, retries (повторні спроби), стани завантаження й помилки.

Стандартні значення навмисно агресивні й пояснюють запитання від бекенд-команди «чому мій API викликають так часто?». Кешовані дані **одразу застарілі** (`staleTime` 0); застарілі запити повторюються у фоновому режимі, коли монтується компонент, фокус повертається у вікно або відновлюється мережеве з’єднання. Неактивні записи видаляються через п’ять хвилин, невдалі запити повторюються тричі зі збільшенням затримки. Кожне повторне завантаження — це запит до API. Найефективніший спосіб скоротити трафік — призначити запитам `staleTime` відповідно до справжньої частоти змін даних; API, який надсилає `ETag`, дає змогу решту запитів дешево завершувати кодом `304`.

Для стану клієнта спершу використовуйте найпростіше місце й переходьте до складнішого лише за наявності реальної проблеми:

| Стан клієнта спільний для | Зберігайте його в |
|---|---|
| Одного компонента | `useState` (Angular: сигнал компонента) |
| Батьківського компонента й кількох дочірніх | Батьківському компоненті; передавайте властивості вниз |
| Усього піддерева, змінюється рідко (тема, поточний користувач, локаль) | Контексті React (Angular: служба) |
| Багатьох віддалених компонентів, часто змінюється | Сховищі: Redux Toolkit, Zustand; в Angular — службі на основі сигналів або NgRx |
| Дані, які мають переживати перезавантаження або передаватися як посилання | URL: параметри маршруту й рядок запиту |

Четвертий рядок пояснюється вартістю контексту: кожен компонент, що читає контекст, ререндериться після зміни його значення, тож часто змінюване значення в контексті біля кореня перерендерює значну частину застосунку. Сховища дають компонентам змогу підписуватися лише на потрібний фрагмент. А URL — недовикористане сховище стану: фільтри, порядок сортування, вибрана вкладка й розбиття на сторінки мають бути в рядку запиту. Тоді працюють кнопки «Назад» і «Оновити», а посиланням можна поділитися.

> **Пастка.** Копіювати серверні дані до глобального сховища, «щоб кожен компонент їх бачив», — означає відтворити проблему кешу вручну, але без інвалідації. Сховище міститиме лише те, що завантажили першим, а кожна мутація має пам’ятати про його оновлення. Зберігайте стан сервера в кеші отримання даних, а стан клієнта — у сховищі, і останнє зазвичай виявиться невеликим.

## Детальна продуктивність фронтенду

[Розділ 6: Основні Web Vitals](#core-web-vitals) визначив три метрики. Тут ідеться про те, що на них впливає й як довести, що зміна дала результат.

### Розмір пакета визначає час головного потоку

JavaScript — найдорожчий байт у мережі. Зображення завантажують і декодують переважно поза головним потоком. Скрипт завантажують, а потім **розбирають, компілюють і виконують у головному потоці** — там само, де обробляють введення й рендеринг. Тому великий пакет має подвійні витрати: затримує перший рендер CSR-застосунку (LCP) і займає головний потік, поки користувачі взаємодіють (INP). Стиснення пришвидшує завантаження, але не розбір і виконання, що залежать від нестисненого розміру.

Щоб контролювати розмір пакетів, дотримуйтеся трьох правил:

- **Переглядайте вміст пакета.** Візуалізатор для вашого пакувальника (для Vite працює `rollup-plugin-visualizer`, бо API його плагінів наслідує Rollup) показує, які пакети займають місце. Зазвичай знаходять цілі імпорти бібліотеки дат або утиліт, дві версії однієї залежності, бібліотеку графіків чи редактора, додану на кожну сторінку.
- **Допомагайте струшуванню дерева.** Пакувальник видаляє невикористані експорти лише з ES-модулів, імпорт яких не має побічних ефектів. Пакети CommonJS і пакети без `"sideEffects": false` у `package.json` часто додаються цілком. Імпортуйте конкретну функцію (`import debounce from "lodash-es/debounce"`), а не простір імен.
- **Встановіть бюджет і перевіряйте його в CI.** Обмеження розміру кожного початкового пакета, яке перевіряють у кожному PR, допоможе знайти залежність на 300 КБ під час рецензування, а не в продакшені.

### Розділення коду на частини

Більшість користувачів не відвідує більшість маршрутів, тож основне завантаження не має містити код для всіх маршрутів. Динамічний `import()` указує пакувальнику: «цей модуль і залежності лише для нього винеси в окрему частину, яку треба завантажити під час виконання цього рядка». `lazy` у React пов’язує це з рендерингом, а `<Suspense>` показує заповнювач, доки завантажується частина:

```tsx
import { lazy, Suspense } from "react";

const ReportsPage = lazy(() => import("./ReportsPage"));   // its own chunk, fetched on first render

function App({ route }: { route: string }) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      {route === "/reports" ? <ReportsPage /> : <p>Home</p>}
    </Suspense>
  );
}
```

Тести репозиторію показують обидві частини: рендеринг домашнього маршруту не завантажує модуль `ReportsPage`; перший рендер `/reports` показує заповнювач, завантажує модуль, а потім сторінку. Крім того, збирання цього застосунку командою `vite build` створює для `ReportsPage` окрему частину з хешем вмісту в назві файла. В Angular працює аналогічний `loadComponent: () => import(...)` у визначенні маршруту. Спершу розділяйте код за маршрутами: це природна межа, яку routers (маршрутизатори) підтримують напряму. Компроміс — запит під час першого переходу на маршрут; попереднє завантаження ймовірної наступної частини під час наведення вказівника або простою браузера приховує затримку.

### Зображення, шрифти й кешування

Зображення зазвичай є елементом LCP і спричиняють більшість зміщень макета.

- **Задавайте розміри кожного зображення** (`width` і `height` або CSS `aspect-ratio`), щоб браузер зарезервував місце ще до отримання файла. Це саме собою усуває більшість CLS.
- **Віддавайте відповідний розмір і формат.** `srcset` і `sizes` дають браузеру змогу вибрати файл відповідно до розміру області перегляду й щільності пікселів; AVIF і WebP для фотографій значно менші за JPEG і PNG.
- **Відкладайте завантаження зображень нижче видимої області, але не зображення LCP.** `loading="lazy"` відкладає завантаження зображень за межами екрана. Це правильно для сітки товарів, але неправильно для головного зображення, для якого слід задати `fetchpriority="high"`, щоб його запитали раніше за менш важливі ресурси.
- **Шрифти.** Якщо вебшрифт надходить із запізненням, текст або приховано, або замінено шрифтом іншого розміру. `font-display` визначає, який сценарій обрати; попереднє завантаження єдиного шрифту першого екрана скорочує затримку.

```html
<img src="/img/hero-1200.avif" srcset="/img/hero-800.avif 800w, /img/hero-1200.avif 1200w"
     sizes="100vw" width="1200" height="600" fetchpriority="high" alt="Spring collection">
<img src="/img/p-42.webp" width="300" height="300" loading="lazy" alt="Linen shirt, blue">
```

Кешування — ділянка, де бекенд пришвидшує фронтенд. Назви файлів із хешем вмісту, які створює Vite, змінюють URL ресурсу після зміни вмісту. Тому самі ресурси можна кешувати рік із директивою `immutable`; натомість `index.html`, де перелічено поточні хеші, треба перевіряти під час кожного завантаження. Якщо зробити навпаки, користувачі отримуватимуть учорашню версію застосунку, доки кеш не спливе. В ASP.NET Core налаштуйте це в параметрах статичних файлів (`OnPrepareResponse` задає `Cache-Control` окремо для файлів) або на CDN.

### Виправлення INP

INP — затримка між взаємодією й наступним кадром. Майже завжди причина — **довге завдання**: JavaScript займає головний потік більш як приблизно на 50 мс, і браузер не може намалювати реакцію на натискання. Перевіряйте інструменти в такому порядку:

- **Виконуйте менше роботи під час взаємодії.** У React зміна стану високо в дереві повторно рендерить усі дочірні компоненти. Якщо опустити стан нижче або розділити компонент так, щоб дорога частина не залежала від змінного стану, часто усувається більшість роботи. `memo`, `useMemo` і `useCallback` пропускають повторний рендеринг, коли входи не змінилися, але це скальпель, а не налаштування за замовчуванням.
- **Рендерте менше.** Таблиця з 5000 рядків створює 5000 вузлів DOM. *Віртуалізація* (react-window, TanStack Virtual, віртуальне прокручування Angular CDK) рендерить лише видимі рядки; серверне розбиття на сторінки, тобто ваша частина API, часто усуває саму потребу.
- **Передавайте керування.** Розбивайте неминучу тривалу роботу на частини, щоб браузер міг промалювати кадр між ними (цикл events із розділу 6), або позначайте не термінове оновлення як перехід (`startTransition` у React), щоб введення лишалося чутливим, поки повторно рендериться великий список.
- **Перенесіть роботу з потоку.** Розбір, сортування чи криптографічні операції над великими даними можна виконувати у Web Worker.

### Вимірювання

Лабораторні інструменти й польові дані відповідають на різні запитання; у старшій інженерній роботі використовують і ті, й інші.

- **Lighthouse** (у Chrome DevTools або Lighthouse CI для кожного PR) один раз завантажує сторінку з імітацією обмеженої пропускної здатності, показує LCP, CLS, Total Blocking Time і можливості для покращення. Результат можна повторювати — він добре виявляє регресії, але є синтетичним і не відображає досвід ваших користувачів. Крім того, він не вимірює INP, бо ніхто не натискає на сторінку. Total Blocking Time — його замінник метрики чутливості до взаємодії.
- **Панель Performance в DevTools** записує tracing (трасування): кожне завдання головного потоку, позначені тривалі завдання, events компонування й малювання та повільна взаємодія. Тут ви знайдете *причину*.
- **Польові дані** надходять із браузерів реальних користувачів. Бібліотека `web-vitals` передає метрики разом з елементом або взаємодією, що їх спричинила. Надсилайте дані до власної endpoint (кінцевої точки) й обчислюйте 75-й перцентиль для кожної сторінки й класу пристроїв:

```typescript
import { onCLS, onINP, onLCP, type Metric } from "web-vitals";

function report(metric: Metric) {
  const body = JSON.stringify({ name: metric.name, value: metric.value, rating: metric.rating,
                                id: metric.id, page: location.pathname });
  navigator.sendBeacon("/api/vitals", body);   // survives the page being closed
}

onCLS(report);
onINP(report);
onLCP(report);
```

(Для цього потрібні API продуктивності справжнього браузера, тому репозиторій цього не запускає.) Кінцева точка-приймач — кілька рядків ASP.NET Core, які записують дані до pipeline метрик ([розділ 25](#chapter-25-observability-and-testing-at-scale)). Публічний звіт Chrome про користувацький досвід надає ті самі три показники для популярних сайтів без написання коду.

> **Рекомендація.** Виконайте одну зміну, виміряйте її на реальних користувачах, а тоді переходьте до наступної. У роботі над продуктивністю фронтенду багато правдоподібних змін, які нічого не поліпшують (або переносять витрати в інше місце, як SSR до гідратації). Саме польове значення 75-го перцентиля бачать користувачі й пошукові системи.

## Тестування фронтенду

Ідеї тестування з [розділу 8: Тестування](#chapter-8-testing) і структура набору тестів із [розділу 25](#chapter-25-observability-and-testing-at-scale) тут працюють без змін. Іншими є інструментарій і один принцип, на якому його побудовано.

**Модульні тести** перевіряють логіку без інтерфейсу: форматування, правила валідації, редюсери, перетворення ProblemDetails на помилки полів. Це звичайні функції, які запускає Vitest або Jest; вони швидкі й стабільні. Більшість логіки фронтенду варто винести з компонентів у такі функції, щоб її можна було перевірити цим способом.

**Тести компонентів** рендерять один компонент (або невелике дерево) у симульованому DOM — jsdom чи happy-dom, взаємодіють із ним і перевіряють побачене користувачем. Стандартом є **Testing Library** (для React, Angular, Vue та інших), принцип якої — тестувати так, як сторінкою користується людина: знаходити елементи за **роллю й доступним ім’ям**, текстом мітки чи видимим текстом, але ніколи за CSS-класом або внутрішнім устроєм компонента:

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { OrderList } from "./OrderList";

test("cancelling an order reports that order's id", async () => {
  const onCancel = vi.fn();
  render(<OrderList orders={[{ id: 7, customer: "Ada", total: 12 }]} onCancel={onCancel} />);

  await userEvent.click(screen.getByRole("button", { name: "Cancel" }));   // as a user would

  expect(onCancel).toHaveBeenCalledWith(7);
});
```

Це справжній тест `OrderList` із розділу 6, який запускається в репозиторії. `getByRole("button", { name: "Cancel" })` не пройде, якщо кнопка стане елементом `<div>` або втратить мітку, тож тест заодно перевіряє доступність — саме як селектори за ролями в Playwright із розділу 25. `user-event` імітує всю послідовність справжнього натискання (events вказівника, фокус, клік), тоді як низькорівневий `fireEvent` надсилає лише один event. Мережеві виклики підміняйте на рівні мережі, а не власних модулів: підміняйте `fetch` або використовуйте Mock Service Worker, який перехоплює запити й повертає заздалегідь задані відповіді. Так виконується справжній код компонента для отримання даних.

> **Нюанс.** jsdom — не браузер. У ньому є DOM і events, але немає механізму компонування, тому розміри дорівнюють нулю, геометрично ніщо не є «видимим», а CSS-медіазапити не працюють. Тести компонентів доводять поведінку й правильність розмітки; компонування, справжній рендеринг і міжбраузерну поведінку перевіряють наскрізними тестами.

**Наскрізні тести** керують справжнім браузером проти запущених застосунку й API. Для нової роботи стандартом є **Playwright**: TypeScript на боці фронтенду або C# ([розділ 25: Playwright для .NET](#playwright-for-net) розглядає автоматичне очікування, селектори за ролями, tracing й інтеграцію axe-core; обидві мови мають той самий API):

```typescript
import { expect, test } from "@playwright/test";

test("a customer can place an order", async ({ page }) => {
  await page.goto("/products/42");
  await page.getByRole("button", { name: "Add to basket" }).click();
  await page.getByRole("link", { name: "Basket" }).click();
  await page.getByRole("button", { name: "Place order" }).click();
  await expect(page.getByRole("heading", { name: "Thank you" })).toBeVisible();
});
```

(У репозиторії цей тест не запускається: потрібні браузери й розгорнутий застосунок.) Залиште кілька наскрізних тестів для основних сценаріїв, що приносять дохід або викликали б гучні новини в разі збою. Решту перевіряйте швидшими модульними тестами й тестами компонентів, які падають з однієї причини.

Ще два типи тестів допомагають виявити те, що пропускають попередні. **Розбіжність контракту** між SPA й API найкраще виявляти під час компіляції за допомогою клієнта, згенерованого з документа OpenAPI у CI (розділ 6), і кроку порівняння схем, що виявляє несумісні зміни документа ([розділ 22](#api-versioning-backward-compatibility)). Тести **візуальної регресії** (порівняння знімків Playwright, служби на основі Storybook) знаходять зміни CSS, що порушили макет, але на які не перевіряє жодне твердження. Для цього потрібні стабільні шрифти й дані, інакше вони самі стають нестабільним набором тестів, який усі ігнорують.

## Політика безпеки вмісту

[Розділ 12: Заголовки безпеки](#security-headers) познайомив із CSP — заголовком, який обмежує дії впровадженого сценарію, — а [розділ 6: XSS із фронтенду](#xss-from-the-front-end) пояснив, як відбувається впровадження. Тут пояснено, як насправді працює CSP і як увімкнути її в SPA, нічого не зламавши.

**Механізм.** Заголовок відповіді `Content-Security-Policy` визначає, які ресурси сторінка може завантажувати й виконувати: `script-src` для сценаріїв, `style-src` для стилів, `connect-src` для цілей `fetch` і WebSocket, `img-src`, `frame-ancestors` для дозволених вбудовувань сторінки тощо. Все, що не дозволено, блокується, а в консолі з’являється повідомлення. Щойно політика має `script-src` без `'unsafe-inline'`, **вбудований сценарій перестає виконуватися**: блоки `<script>` без nonce чи хешу, атрибути `onclick="…"` і URL `javascript:`. Більшість XSS-вставок мають саме такий вигляд, тож вони не спрацьовують, навіть якщо саме впровадження вдалося.

**Списки дозволених адрес не працюють; nonce й хеші — працюють.** Очевидна політика перелічує домени, з яких завантажуються сценарії (`script-src 'self' https://cdn.example.com …`). Дослідження й практика показують, що такі політики зазвичай можна обійти, бо на дозволеному домені є вразливий ресурс (стара бібліотека, endpoint JSONP), а підтримувати такі переліки неможливо. Рекомендована **строга CSP** довіряє сценаріям через секрет, який змінюється для кожної відповіді:

```text
Content-Security-Policy:
  script-src 'nonce-R4nd0mPerResponse' 'strict-dynamic';
  object-src 'none';
  base-uri 'none'
```

Сценарій запускається, лише якщо його тег містить `nonce="R4nd0mPerResponse"` — випадкове значення, яке сервер генерує **для кожної відповіді**. Тому нападник, що впровадив тег `<script>`, не знатиме його. `'strict-dynamic'` поширює цю довіру на сценарії, *завантажені* довіреним сценарієм. Так працюють динамічні частини пакувальника й більшість завантажувачів третіх сторін; водночас браузер ігнорує списки дозволених хостів. Замість nonce політика може містити **хеш** кожного дозволеного сценарію (`'sha256-…'`); це підходить для статичних сторінок, сценарії яких не змінюються.

**SPA й проблема nonce.** Nonce має бути новим для кожної відповіді, тому `index.html` не може залишатися статичним файлом у CDN. Є два робочі варіанти:

- **Обробляйте `index.html` в ASP.NET Core** і додавайте nonce. Сервер генерує його, надсилає в заголовку й додає в теги сценаріїв поверненого HTML. Це безпечно, оскільки `index.html` — результат вашого збирання, а не дані користувачів; додавання nonce до HTML із введенням користувача дозволило б і впроваджені теги.
- **Статичний хостинг із хешами.** Вихід збирання Vite завантажує застосунок зовнішніми модульними сценаріями й за типової конфігурації не має вбудованих сценаріїв. Тому CDN може використовувати політику на основі хешів або `'self'`. Вона слабша за `'strict-dynamic'` із nonce, але значно краща за відсутність політики.

```csharp
app.Use(async (context, next) =>
{
    var nonce = Convert.ToBase64String(RandomNumberGenerator.GetBytes(16));   // new for every response
    context.Items["csp-nonce"] = nonce;
    context.Response.Headers.ContentSecurityPolicy =
        $"script-src 'nonce-{nonce}' 'strict-dynamic'; object-src 'none'; base-uri 'none'";
    await next();
});

app.MapFallback(async context =>            // index.html for every client-side route, nonce stamped in
{
    var html = await File.ReadAllTextAsync(Path.Combine(app.Environment.WebRootPath, "app.html"));
    var nonce = (string)context.Items["csp-nonce"]!;
    context.Response.ContentType = "text/html; charset=utf-8";
    await context.Response.WriteAsync(html.Replace("<script ", $"<script nonce=\"{nonce}\" "));
});
```

(Перевірено для ASP.NET Core 10: кожна відповідь отримує новий nonce і в заголовку, і в тегу сценарію. Шаблон називається `app.html`, щоб middleware (проміжне програмне забезпечення) статичних файлів ніколи не віддавало його без доданого nonce.)

**Спершу ввімкніть режим звітування.** `Content-Security-Policy-Report-Only` застосовує політику, але не примушує її виконувати; кожне порушення надсилається до консолі й endpoint, указаного директивою `report-to`. Кілька тижнів перевіряйте й виправляйте справжні проблеми (сценарій аналітики, віджет чату, вбудовані стилі бібліотеки компонентів), а тоді увімкніть режим примусового виконання для тієї самої політики. Обидва заголовки можна надсилати одночасно; так випробовують суворішу політику, продовжуючи застосовувати чинну.

**Trusted Types** закривають решту дірки — DOM XSS у вашому коді. Якщо політика містить `require-trusted-types-for 'script'`, браузер відхиляє звичайні рядки в небезпечних місцях (`innerHTML`, `eval`, `src` сценарію) й приймає лише значення, створені визначеною вами функцією політики, зазвичай із санітайзером. Підтримка в різних браузерах неоднакова (перевірте MDN перед застосуванням); там, де вона є, правило «не передавати введений користувачем текст у `innerHTML`» стає помилкою виконання, а не рекомендацією для рецензента.

> **Пастка.** `'unsafe-inline'` у `script-src` вимикає більшість захисту CSP від XSS, а `'unsafe-eval'` знову дозволяє `eval`. Обидві директиви додають «тимчасово», щоб виправити сторінку, і ніколи не прибирають. Якщо за політики сторінка зламалася, знайдіть вбудований сценарій або `eval` і перенесіть його у файл чи додайте nonce. У кожній політиці залишайте `object-src 'none'` і `base-uri 'none'`: класичний спосіб обходу — плагіни й підмінений тег `<base>`.

## Поглиблена інтеграція API .NET із JavaScript SPA

### Автентифікація SPA

Це найчастіша помилка. Є два основні підходи; [розділ 6](#cookies-localstorage-and-sessionstorage-where-browser-state-lives) пояснює компроміс між варіантами зберігання.

**На основі токенів (токени Bearer у JavaScript).** SPA отримує токен доступу (зазвичай JWT) і надсилає його в заголовку `Authorization: Bearer`. Логіку легко зрозуміти, але токен треба десь зберігати в браузері. Усе, що може прочитати JavaScript, доступне й XSS-помилці чи скомпрометованій залежності. У цьому головна слабкість.

**На основі файлів cookie.** Сеанс зберігається в cookie з атрибутами `HttpOnly`, `Secure`, `SameSite`, яке JavaScript не може читати, а браузер додає автоматично. XSS не може викрасти токен, але треба захищатися від CSRF.

Для отримання токена стандартом є **OIDC із потоком коду авторизації та PKCE** ([розділ 12: Потік коду авторизації з PKCE](#authorization-code-flow-with-pkce)); неявний потік застарів. Рекомендована нині схема для SPA поєднує обидва підходи:

> **Рекомендація — шаблон BFF.** Розмістіть між SPA й API легкий серверний компонент (часто ваш застосунок ASP.NET Core). BFF виконує вхід OIDC як конфіденційний клієнт, зберігає токени *на сервері*, а браузеру видає лише сеансову cookie `HttpOnly`. SPA взагалі не торкається токена, тож усувається цілий клас атак із викрадення токенів через XSS. Проєкт рекомендацій IETF *OAuth 2.0 for Browser-Based Applications* наполегливо радить таку архітектуру для бізнес-застосунків, чутливих застосунків і систем із персональними даними.

Конкретно: SPA викликає `/bff/api/orders`, cookie автентифікує запит, а BFF пересилає його до API з токеном доступу, який зберігає. Для .NET це готове рішення надає `Duende.BFF`, а пересилати запити може YARP. SPA й BFF мають використовувати одне джерело, щоб cookie були основними й не потрібен був CORS; тоді endpoints BFF потрібен захист від CSRF. У згаданому проєкті рекомендацій IETF пропонують вимагати власний заголовок запиту: міжсайтова сторінка може надіслати такий заголовок лише після попереднього запиту CORS, який BFF відхилить. [Розділ 21: Шлюз API й Backend for Frontend](#api-gateway-and-backend-for-frontend) розглядає BFF як архітектурний шаблон, а не лише засіб автентифікації.

### Форма API: REST чи GraphQL

**REST** через JSON — стандартний і правильний вибір для більшості систем: URL ресурсів, дієслова HTTP, коди стану й кешування HTTP. **GraphQL** дає змогу клієнтам за один запит отримувати саме потрібні поля. Він добре підходить, якщо багато клієнтів мають різні потреби в даних або потрібні глибоко вкладені графи. Вартість — відсутність кешування HTTP (більшість запитів — `POST` на один URL) і складніший сервер: обмеження вартості запиту, обробка N+1 завантажувачами даних і авторизація для кожного поля (`HotChocolate` — провідний сервер .NET). Типово обирайте REST. Переходьте на GraphQL, якщо доведено, що надмірне завантаження даних для багатьох екранів є проблемою, або розмістіть BFF перед службами REST, щоб форматувати відповіді для кожного екрана.

### Завантаження файлів

Завантажуйте файли через `multipart/form-data`, а не JSON; браузер надсилає тіло `FormData` без вручну заданого `Content-Type` (див. розділ 6). На сервері:

```csharp
app.MapPost("/api/upload", async (IFormFile file) =>
{
    var name = $"{Guid.NewGuid()}{Path.GetExtension(file.FileName)}";   // never trust the client's name
    await using var stream = File.Create(Path.Combine("uploads", name));
    await file.CopyToAsync(stream);
    return Results.Ok(new { name, file.Length });
}).DisableAntiforgery(); // or supply the token from the SPA
```

Ім’я файла від клієнта контролює нападник (`../../appsettings.json` також є назвою файла), тож створюйте своє й зберігайте вихідне лише як метадані для показу.

> **Пастка:** Kestrel і IIS обмежують розмір тіла запиту (за замовчуванням близько 28–30 МБ). Для великих файлів збільште `RequestSizeLimit`, а краще скористайтеся поновлюваним завантаженням частинами або підписаним завантаженням безпосередньо в сховище великих об’єктів, щоб файл узагалі не проходив через API.

### Обмін даними наживо через SignalR

Для поточних оновлень (сповіщення, панелі, чат) SignalR надсилає дані із сервера до браузера через WebSocket, а за потреби переходить до Server-Sent Events або довгого опитування. Хаб, групи, `IHubContext` і масштабування через ретранслятор описані в [розділі 22: SignalR](#signalr). На боці браузера використовується пакет npm `@microsoft/signalr`; у SPA потрібно правильно керувати життєвим циклом з’єднання — це ефект із [розділу 6](#effects-and-their-dependency-arrays): відкрити під час монтування, закрити під час очищення.

```tsx
import { HubConnectionBuilder } from "@microsoft/signalr";
import { useEffect, useState } from "react";

function Notifications() {
  const [messages, setMessages] = useState<string[]>([]);

  useEffect(() => {
    const conn = new HubConnectionBuilder()
      .withUrl("/hubs/notifications")              // same origin: the auth cookie goes along
      .withAutomaticReconnect()
      .build();
    conn.on("notify", (msg: string) => setMessages((m) => [...m, msg]));
    conn.start().catch((err) => console.error("SignalR connection failed", err));
    return () => { conn.stop(); };                 // unmount, or StrictMode's dev re-run
  }, []);

  return <ul>{messages.map((m, i) => <li key={i}>{m}</li>)}</ul>;
}
```

(У репозиторії цей код не запускається: потрібен запущений хаб.) Без очищення кожне повторне монтування залишає з’єднання, а повторний запуск StrictMode у режимі розробки відкриває два. `withAutomaticReconnect` повторює спроби за розкладом, але повідомлення, надіслані під час розриву, губляться. Тому панель має повторно завантажити дані після відновлення з’єднання (callback (зворотний виклик) `onreconnected`). API із токеном Bearer не може надіслати заголовки WebSocket із браузера, тож клієнт передає токен через `accessTokenFactory`, SignalR додає його до рядка запиту, а сервер має прочитати його саме звідти. Якщо використовується BFF і cookie з тим самим джерелом, усе це не потрібно. (Індекси в цій таблиці можна використовувати, бо повідомлення лише додаються до списку.)

## Blazor: C# у браузері (і на сервері)

Blazor дає змогу створювати інтерактивні вебінтерфейси на C# і Razor замість JavaScript. Для команди .NET це привабливо: одна мова, спільні моделі й перевірки. Але «Blazor» — це сімейство моделей розміщення та рендерингу; неправильний вибір часто викликає жаль. Режими рендерингу безпосередньо відповідають стратегіям на початку розділу.

### Дві класичні моделі

**Blazor Server** виконує компоненти на сервері. У браузері працює тонке середовище JavaScript, під’єднане через WebSocket SignalR; events інтерфейсу надходять на сервер, виконується C#, а назад надсилається *різниця DOM*. Завантаження невелике, доступна повна потужність сервера й секрети, запуск миттєвий. Але кожна взаємодія потребує мережевого обміну й залежить від затримки; кожен користувач має відкрите з’єднання, що використовує пам’ять сервера. Ця модель масштабується за кількістю одночасних з’єднань, а не за дешевим режимом без стану.

**Blazor WebAssembly (WASM)** запускає середовище .NET у WebAssembly і компоненти *повністю в браузері*, як звичайна SPA. Він працює без мережі, розвантажує сервер і потребує лише статичного хостингу. Вартість — більший початковий пакет (runtime (середовище виконання)) і відсутність прямого доступу до серверних ресурсів: він викликає ваше API так само, як React.

### Уніфіковані режими рендерингу .NET 8+

.NET 8 об’єднав ці моделі в одну систему компонентів із **режимами рендерингу** для кожного компонента. Саме так нині слід розглядати Blazor:

- **Статичний SSR** — компоненти рендерять HTML на сервері *без інтерактивності*: серверний рендеринг без гідратації, за потреби — потоковий рендеринг повільних даних. Швидко, зручно для SEO й сторінок із вмістом. Завдяки цьому Blazor став повноцінним вибором для традиційних сайтів із серверним рендерингом.
- **Interactive Server** — класична модель Blazor Server (канал SignalR), застосована окремо до кожного компонента.
- **Interactive WebAssembly** — класична модель WASM, також окремо до компонента.
- **Auto** — спершу швидко завантажується Interactive Server, а у фоновому режимі — середовище WASM; під час наступних відвідувань система переходить на клієнтський режим. Найкраще з обох моделей, але компоненти мають працювати в обох: інтерактивний код не може безпосередньо викликати методи лише для сервера.

> **Рекомендація:** для нових вебзастосунків Blazor за замовчуванням використовуйте **статичний SSR**, а окремі компоненти робіть інтерактивними, лише якщо це потрібно. Більшість застосунку лише показує дані; інтерактивність додається тільки до потрібних «островів». Це описана вище архітектура островів, реалізована на C#.

### Модель компонентів

Компонент Blazor — це файл `.razor`, який поєднує розмітку й C#. Стан зберігається у звичайних полях; після їх зміни виклик `StateHasChanged` (часто неявний, після handler events) запускає повторний рендеринг.

```razor
@* Counter.razor *@
<button class="btn" @onclick="Increment">Clicked @count times</button>

@code {
    [Parameter] public int Step { get; set; } = 1;
    private int count;
    private void Increment() => count += Step;
}
```

Властивості `[Parameter]` — це входи (властивості React). Компоненти поєднуються, передають батькам `EventCallback`, а станом діляться через каскадні значення або впроваджені служби. Ментальна модель та сама, що вивчалася на React у розділі 6: рендерити зі стану, обчислити різницю й оновити DOM, — тільки тепер усе на C#. `@key` виконує ту саму роль, що `key` у списках React.

### Взаємодія з JavaScript

Blazor не може повністю відмовитися від JavaScript: API браузера (геолокація, деякі бібліотеки графіків, `localStorage`) належать JavaScript. `IJSRuntime` забезпечує зв’язок:

```razor
@inject IJSRuntime JS

@code {
    async Task SaveDraft(string text) =>
        await JS.InvokeVoidAsync("localStorage.setItem", "draft", text);
}
```

Взаємодія перетинає межу серіалізації й виконується асинхронно (в Interactive Server це мережевий обмін). Використовуйте її свідомо, а не за звичкою: надмірна взаємодія нівелює перевагу Blazor як єдиної мови.

### Коли обрати Blazor, а коли краще SPA на JavaScript

**Обирайте Blazor, якщо:** команда переважно працює на C# і має мало досвіду JavaScript; потрібно ділити DTO й перевірки між клієнтом і сервером; це внутрішній бізнес-застосунок (панелі адміністрування, внутрішні інструменти, інформаційні панелі), де велика екосистема npm-компонентів не є вирішальною; важливо не перемикатися між мовами.

**Обирайте SPA на JavaScript (React/Angular/Vue), якщо:** потрібна велика екосистема сторонніх компонентів (розширені сітки даних, карти, системи дизайну); ви наймаєте фахівців на ринку з великою кількістю JavaScript-розробників; потрібен повний контроль над розміром пакета й першим рендером публічного критичного до продуктивності сайту; або вже є фронтенд на JavaScript і важлива відповідність мобільній вебверсії.

> **Чесне застереження:** завантаження середовища Blazor WASM і затримки / з’єднання Blazor Server — реальні обмеження, а не примітки в рекламі. Перш ніж вибрати модель для цілого продукту, створіть прототип *найгіршої* взаємодії в *реалістичній* мережі.

## Нативні клієнти на C#: MAUI, Uno, Avalonia

Нативний інтерфейс для комп’ютерів і мобільних пристроїв — окрема дисципліна; книжці про бекенд не потрібен її повний огляд. Достатньо розпізнавати три фреймворки, до яких звертаються команди .NET, бо рано чи пізно один із них викликатиме ваше API:

- **.NET MAUI** — наступник Xamarin.Forms: застосунки для iOS, Android, Windows і macOS з однієї кодової бази C#/XAML, що рендериться справжніми нативними елементами керування. Типовий приклад — внутрішній мобільний застосунок, який підтримує команда .NET, відповідальна за бекенд. Варіант **Blazor Hybrid** розміщує наявні вебкомпоненти Blazor у нативній оболонці через `BlazorWebView`, обмінюючи вигляд платформи на повторне використання вебінтерфейсу.
- **Uno Platform** підтримує мобільні пристрої, комп’ютери *й* браузер (через WASM) на основі WinUI/XAML; охоплення ширше за MAUI.
- **Avalonia** — зрілий міжплатформний фреймворк для комп’ютерів на основі XAML, популярний там, де важлива підтримка Linux. MAUI цю платформу не підтримує.

Важливий для старшого розробника висновок: усі три — *клієнти API*. Вони залежать від вашої частини межі: чіткого документованого контракту OpenAPI, потоків автентифікації на основі токенів, що працюють без файлів cookie браузера, стійкості до нестабільної мобільної мережі й насамперед дисципліни версіонування. Встановлений застосунок не можна примусово оновити, як SPA, тож старі версії клієнта викликатимуть ваше API місяцями. Добре спроєктуйте цю межу — і вибір клієнтського фреймворку стане їхньою справою, а не вашою.

## Доступність: тепер це вимога закону — докладно

[Розділ 6](#accessibility-the-part-that-is-now-law) розглядав законодавство, принципи WCAG, семантичний HTML перед ARIA, роботу з клавіатурою й доступні форми. Тут ідеться про зміни в SPA, тестування й специфічні для Blazor пастки.

У WCAG 2.2 додано кілька критеріїв, важливих для сучасних інтерфейсів: фокус не можна повністю приховувати за фіксованим заголовком; для перетягування потрібна альтернатива одним вказівником; цілі натискання мають бути достатнього розміру; не можна змушувати користувачів повторно вводити інформацію, яку вони вже надали в тому самому процесі.

### Зміна маршрутів у SPA

У застосунку із серверним рендерингом перехід на іншу сторінку повертає фокус угору, а програма зчитування з екрана оголошує нову назву документа. У SPA навігація на боці клієнта замінює частину DOM, фокус залишається на старому посиланні, якого вже немає, а зміна ніде не оголошується. Користувачі клавіатури й програм зчитування опиняються на сторінці, яка змінилася без попередження. В усіх фреймворках виправлення однакове: після навігації перемістіть фокус на головний заголовок нової сторінки (задайте `tabindex="-1"`, щоб він отримував фокус, але не входив у порядок Tab), оновіть `document.title` і, за потреби, оголосіть зміну через область `aria-live`. Деякі фреймворки частково роблять це автоматично (шаблон router Blazor містить `FocusOnNavigate`, що переводить фокус на новий `<h1>`). Перевірте клавіатурою, що саме робить ваш, а не покладайтеся на припущення.

### Тестування доступності

Автоматизовані перевірки справді корисні й водночас обмежені; важливо розуміти співвідношення. Інструменти на основі правил, як **axe-core**, надійно виявляють відсутній альтернативний текст, недостатню контрастність, непідписані поля вводу, дубльовані ідентифікатори й некоректну ARIA. Це реальна частина проблеми, що непомітно виникає знову після змін. Опубліковані дослідження послідовно оцінюють автоматичне покриття приблизно у **30–40 % проблем WCAG**. Решту — чи *змістовний* альтернативний текст, чи *логічний* порядок фокуса, чи допомагає повідомлення про помилку, чи можна користуватися власним віджетом із програмою зчитування — має перевіряти людина.

Тож використовуйте обидва методи:

- **У CI** запускайте axe-core для ключових сторінок і зупиняйте збирання через нові порушення. Налаштування описано в [розділі 25: Перевірки доступності в тому самому запуску](#accessibility-checks-in-the-same-run); тести компонентів із пошуком за роллю (див. розділ про тестування) безкоштовно додають перевірки.
- **Час від часу вручну:** перевірте лише клавіатурою за процедурою з розділу 6, збільште масштаб до 200 % і скористайтеся програмою зчитування (NVDA для Windows безкоштовна, VoiceOver постачається з macOS). Пів години роботи з програмою зчитування на власному продукті — найефективніше доступне навчання доступності; воно змінює підхід до розмітки надовго.

### Пастки доступності у Blazor

Blazor створює HTML, тож усе описане вище стосується й його. Але модель компонентів спричиняє дві проблеми, які часто застають команди зненацька.

**Зміна маршруту не оголошується**, як і в будь-якій SPA. `<FocusOnNavigate RouteData="routeData" Selector="h1" />` у шаблоні router обробляє типовий випадок. Якщо його прибрали або компонент має сам перемістити фокус, зробіть це після рендерингу:

```razor
@inject NavigationManager Nav

<h1 @ref="_heading" tabindex="-1">@Title</h1>

@code {
    private ElementReference _heading;

    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (firstRender)
            await _heading.FocusAsync();   // tabindex="-1" makes this possible
    }
}
```

Поєднайте це з областю `aria-live`, яка оголошує назву нової сторінки, щоб користувачі, чий фокус не переміщується, також знали, де вони опинилися.

**Режими рендерингу змінюють час запуску JavaScript.** За `InteractiveServer` або `InteractiveWebAssembly` сторінку спершу надсилають як статичний HTML, а згодом роблять інтерактивною — це проміжок гідратації, описаний на початку розділу. Будь-яка поведінка доступності, реалізована в `OnAfterRenderAsync` або через взаємодію з JavaScript, у цей час недоступна. За повільного з’єднання це триває кілька секунд. Перевагу мають рішення, що працюють у початковій розмітці (справжня кнопка `<button>`, справжня мітка `<label>`), а не ті, що чекають на інтерактивність.

Також `NavLink` створює `<a>`, і це правильно; але `NavLink`, стилізований під кнопку, або `<a>` без `href`, використаний як ціль натискання, знову створює проблему `div` замість кнопки в синтаксисі Razor. Якість доступності бібліотек компонентів дуже відрізняється; перш ніж покладатися на обрану бібліотеку в сорока екранах, перевірте її клавіатурою.

## Запитання для співбесіди

**SSR чи CSR для цієї сторінки і скільки коштує гідратація?**
Вибирайте за вмістом і аудиторією: публічним сторінкам, важливим для SEO, потрібні SSR або SSG задля швидкого LCP; авторизований застосунок може використовувати CSR. Для гідратації клієнт завантажує й повторно запускає компоненти, щоб додати handlers, тому SSR пришвидшує перший кадр, але не зменшує вартість JavaScript чи INP. Розбіжність між сервером і клієнтом змушує React повторно рендерити цю частину на клієнті.

**Тривожна відповідь:** «SSR пришвидшує застосунок». Він пришвидшує *відображення* вмісту, але не інтерактивність, і додає витрати сервера.

**Чому SPA так часто викликає наше API й що ви змінили б?**
За замовчуванням кеш отримання даних на кшталт TanStack Query одразу позначає дані застарілими й повторно завантажує їх під час монтування, повернення фокуса у вікно й відновлення з’єднання. Задайте `staleTime` відповідно до справжньої частоти змін даних, інвалідуйте кеш після мутацій замість опитування й додайте до API `ETag`, щоб повторне завантаження коштувало дешево.

**У чому різниця між станом сервера й клієнта?**
Стан сервера — кешована копія даних, власником яких є сервер. Його треба отримувати, дедуплікувати, інвалідувати й оновлювати, тому йому місце в кеші отримання даних. Стан клієнта належить інтерфейсу (відкриті модальні вікна, чернетки форм), тому його зберігають якнайближче до місця використання; усе, що має пережити перезавантаження, зберігають у URL.

**Як пришвидшити повільну SPA?**
Спочатку виміряти: польові дані для 75-го перцентиля, панель Performance — для виявлення причин. Потім: розділити код за маршрутами, скоротити пакет і застосувати струшування дерева, задати розміри зображень і відповідний формат, нескінченно кешувати ресурси з хешем, але ніколи — `index.html`. Виправити INP, скоротивши роботу для кожної взаємодії (розміщення стану, віртуалізація, передавання керування).

**Який вигляд має строга CSP і як розгорнути її для SPA?**
`script-src 'nonce-…' 'strict-dynamic'; object-src 'none'; base-uri 'none'` із новим nonce для кожної відповіді, щоб вбудований впроваджений сценарій не запускався. SPA може віддавати `index.html` через сервер для додавання nonce або використовувати хеші зі статичного хостингу. Спершу ввімкніть режим звітування.

**Де зберігати токени браузерної SPA?**
На сервері, за BFF, який виконує потік коду OIDC із PKCE як конфіденційний клієнт і передає браузеру лише cookie `HttpOnly`, `Secure`, `SameSite`. Тоді BFF потребує захисту від CSRF.

**Тривожна відповідь:** «Токен лежить у `localStorage`, але в нас є CSP, тож XSS не буває». CSP зменшує ризик XSS, але не робить зберігання токена Bearer там, де його читає будь-який сценарій, гарною ідеєю.

**Як тестувати фронтенд без нестабільного набору тестів?**
Логіку перевіряти модульними тестами; компоненти — Testing Library із пошуком за роллю й міткою та підміною мережі на рівні `fetch`; кілька наскрізних сценаріїв — Playwright. Розбіжність контракту API виявляти під час компіляції за допомогою згенерованого клієнта.
