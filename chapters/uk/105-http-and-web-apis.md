# Розділ 5: HTTP і веб-API

Більшість помилок, що потрапляють у продакшен вебслужб, насправді не є помилками *коду*. Це мережеві помилки в маскуванні: виклик працює на вашому ноутбуці, але під навантаженням завершується тайм-аутом; служба, що обробляла тисячу запитів за секунду, починає викидати `SocketException`; endpoint (кінцева точка) відповідає `200`, а клієнт бачить помилку. Цей розділ пояснить, що відбувається між `await httpClient.GetAsync(url)` і поверненням байтів, а потім допоможе побудувати поверх цього коректний API ASP.NET Core: з правильним порядком middleware, перевіркою введених даних на межі, повторним використанням з’єднань для вихідних викликів і повторами лише безпечних запитів, а також методами, кодами стану й заголовками, з якими можуть працювати клієнти та проксі.

Ось увесь шлях одним поглядом:

```
await httpClient.GetAsync(url)
  |
  |  DNS lookup      name -> IP (cached per TTL)       \
  |  TCP handshake   SYN / SYN-ACK / ACK      1 RTT     | skipped when a pooled
  |  TLS 1.3         ClientHello/ServerHello  1 RTT     | connection is reused
  |                                                     /  (SocketsHttpHandler)
  v
  HTTP request over the connection
  |    (HTTP/2: one of many multiplexed streams on one TCP connection)
  v
  load balancer (L4/L7, often terminates TLS)
  |
  v
  origin server --> response back down the same path --> your await resumes
```

Розділ іде за цим запитом. Почнемо з основ HTTP, рівнів мережі, TCP і UDP та DNS; потім розглянемо сам HTTP: методи й можливість безпечного повтору, коди стану та заголовки, три версії протоколу й connection pool (пул з’єднань), через який нешкідливий на вигляд `using` може призвести до вичерпання сокетів. З цією моделлю правильно викликатимемо зовнішні служби з .NET через `IHttpClientFactory` і pipeline (конвеєр) стійкості. Друга половина присвячена серверу: pipeline middleware та routing (маршрутизація), двом способам оголошувати endpoints, фільтрам, JSON, прив’язуванню й перевірці моделі, скасуванню, наскрізним аспектам, REST і OpenAPI та health checks (перевірок працездатності). TLS розглянуто в [Розділі 12: Основи безпеки](#chapter-12-security-essentials); балансувальники навантаження, зворотні проксі й CDN — у [Розділі 26: Доставка й платформа](#chapter-26-delivery-and-platform); версіонування, gRPC і SignalR — у [Розділі 22: еволюція API, обмін даними в реальному часі й серіалізація](#chapter-22-api-evolution-real-time-and-serialization).

Упродовж усього розділу пам’ятайте одну ідею: **мережа — спільне, ненадійне й потенційно ворожe середовище, яке часом удає, ніби є надійним викликом функції.** Усі абстракції цього розділу потрібні, щоб керувати цією ілюзією.

## Багаторівнева модель: OSI і TCP/IP

Мережі вивчають як стек рівнів, бо саме так їх побудовано. Кожен рівень розв’язує одну задачу й передає чітко визначену абстракцію рівню вище, як матрьошки одна в одній.

Класична **модель OSI** має сім рівнів, але на практиці достатньо зрозуміти спрощену **модель TCP/IP** із чотирьох:

| Рівень | Призначення | Приклади |
|-------|-----|----------|
| Прикладний | Що *означають* байти | HTTP, DNS, gRPC, WebSocket |
| Транспортний | Доставлення байтів потрібній *програмі* на вузлі, надійно або ні | TCP, UDP, QUIC |
| Мережевий | Доставлення пакетів потрібному *вузлу* між мережами | IP, ICMP |
| Канальний | Передавання бітів одним фізичним сегментом | Ethernet, Wi-Fi |

Запам’ятайте аналогію з листом. **Канальний** рівень — поштовий автомобіль між поштовими відділеннями. **Мережевий** рівень (IP) — адресна система, яка маршрутизує конверт між містами без гарантії доставлення. **Транспортний** рівень — внутрішня пошта, яка доставляє лист *Бобу з бухгалтерії* (за номером порту) і, у випадку TCP, повторно надсилає загублені сторінки. **Прикладний** рівень — власне текст листа зрозумілою Бобу мовою.

> **Рекомендація.** Під час налагодження запитуйте себе: *який рівень дає збій?* «У з’єднанні відмовлено» — транспортний рівень або вузол (на цьому порту нічого не слухає). «Відомий вузол не знайдено» — DNS або прикладний рівень. `500` — прикладний рівень. Плутанина між рівнями марнує години.

## TCP і UDP

TCP і UDP працюють поверх IP, обидва використовують **номери портів** для доставлення даних конкретному процесу. На цьому їхня схожість закінчується.

**TCP (Transmission Control Protocol)** — *надійний, упорядкований потік із встановленням з’єднання*. Перед передаванням даних TCP виконує **тристороннє рукостискання** (`SYN` → `SYN-ACK` → `ACK`), щоб установити з’єднання. Потім він гарантує:

- **Надійність** — виявлення втрачених пакетів (за підтвердженнями) і повторне надсилання.
- **Порядок** — байти надходять у надісланій послідовності, навіть якщо базові пакети проходять різними маршрутами.
- **Керування потоком і перевантаженням** — TCP обмежує швидкість, щоб не перевантажувати ні отримувача, ні мережу.

Ціна за це — *затримка* й *стан*. Рукостискання додає повне коло обміну до першого байта. Блокування на початку queue (черга) (докладніше далі) означає, що втрата одного пакета затримує всі наступні.

**UDP (User Datagram Protocol)** — це *дейтаграми без гарантій*. Немає рукостискання, упорядкування, повторного надсилання чи керування перевантаженням. Ви надсилаєте пакет — він може надійти, не надійти, надійти двічі або не в порядку. Натомість отримуєте мінімальні накладні витрати й відсутність блокування на початку queue.

Уявіть TCP як телефонний дзвінок: спершу встановлюєте з’єднання, говорите по queue й підтверджуєте, що почули співрозмовника. UDP — це крик через людний зал: швидко, але невідомо, чи вас хтось почув.

**Що й коли використовувати:**

- **TCP:** HTTP, підключення до баз даних, передавання файлів — усе, де правильність важливіша за затримку. Так працює 95% вашого коду.
- **UDP:** DNS-запити, відео- й голосовий зв’язок реального часу (втрачений кадр кращий за зупинку), ігри й, що особливо важливо, **QUIC** — основа HTTP/3, яка знову додає надійність *поверх* UDP, обходячи обмеження TCP.

## Розв’язання DNS

Люди використовують імена (`api.example.com`), а IP-маршрутизація — числа (`93.184.216.34`). **DNS (Domain Name System)** — розподілена телефонна книга, яка перетворює одне на інше. Це ієрархія, яку обходять справа наліво.

Коли застосунок шукає `api.example.com`:

1. ОС перевіряє локальний кеш і файл `hosts`.
2. Якщо запису немає в кеші, надсилає запит **рекурсивному резолверу** (часто це сервер провайдера або `8.8.8.8`).
3. Резолвер запитує **кореневий** сервер: «хто відповідає за `.com`?»
4. Сервер **TLD** для `.com` відповідає: «запитайте авторитетний сервер імен для `example.com`».
5. **Авторитетний** сервер повертає справжню IP-адресу (запис `A` для IPv4, `AAAA` для IPv6).
6. Кожен рівень кешує відповідь згідно з **TTL** (часом життя).

Це може вимагати кількох кіл обміну, тому кешування всюди й перший запит до нового вузла повільніший.

> **Нюанс.** `HttpClient` і його connection pool можуть кешувати DNS-відповіді протягом *усього часу життя з’єднання*. Якщо DNS-запис зміниться (перемикання після збою чи deployment (розгортання) blue-green), довготривалі з’єднання з пулу можуть і далі звертатися до старої IP-адреси. Виправлення — періодично виводити з’єднання з експлуатації; далі в [I`HttpClient`Factory і стійкість за допомогою Polly](#ihttpclientfactory-resilience-with-polly) описано два способи. Через цю проблему не раз виникало запитання: «чому трафік досі йде на недоступний сервер?»

## Як працює HTTP

**HTTP (HyperText Transfer Protocol)** — *протокол прикладного рівня без збереження стану, семантично текстовий, із моделлю «запит — відповідь»*. Клієнт надсилає запит, сервер надсилає одну відповідь. У цьому весь контракт.

Ось необроблений запит HTTP/1.1:

```
GET /users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGci...

```

А ось відповідь:

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27
Cache-Control: max-age=60

{"id":42,"name":"Ada"}
```

Кожен запит має **метод** (дієслово), **шлях**, **заголовки** (метадані у формі пар ключ — значення) й необов’язкове **тіло**. Відповідь має **код стану**, заголовки й тіло.

Ключова властивість — **відсутність стану**: кожен запит містить усе потрібне серверу; cookie, токени й сеанси лише *імітують* стан поверх цього. Завдяки цьому можна горизонтально масштабувати службу: будь-який сервер обробить будь-який запит, якщо дані сеансу зберігаються в спільному сховищі, а не в пам’яті процесу.

### Методи HTTP та ідемпотентність

Кеші, проксі й політики повторів враховують дві властивості методу (RFC 9110):

- **Безпечний** — клієнт не просить змінювати стан: `GET`, `HEAD`, `OPTIONS`, `TRACE`. Безпечні відповіді можна кешувати й завчасно отримувати.
- **Ідемпотентний** — N однакових запитів мають той самий ефект на сервері, що й один: усі безпечні методи, а також `PUT` і `DELETE`. Йдеться про ефект, а не відповідь: другий `DELETE` може повернути `404`, залишаючись ідемпотентним.
- **Не належить до жодної категорії** — `POST` («оброби це») і `PATCH`, якщо ви спеціально не зробили його ідемпотентним.

> **Зверніть увагу.** **Ідемпотентність визначає, хто може повторити запит без погодження.** Після тайм-ауту клієнт не знає, чи запит уже виконано. Тому HTTP дозволяє клієнтам і проксі автоматично повторювати ідемпотентні запити й забороняє повторювати решту. Повторити `PUT` безпечно; повторний `POST` може двічі стягнути кошти з картки. Зробіть кожну операцію, яку можна повторити, ідемпотентною, а для `POST`, який не має виконуватися двічі, додайте idempotency key (ключ ідемпотентності) ([Idempotency keys: безпечні повтори `POST`](#idempotency-keys-making-post-retry-safe) у Розділ 20).

## Важливі коди стану й заголовки

Коди стану поділяються на п’ять родин. Клієнти, проксі й панелі спостереження реагують на код, не читаючи тіла відповіді:

- **1xx** Інформаційні (рідкісні; `101 Switching Protocols` — оновлення до WebSocket).
- **2xx** Успіх — `200 OK`, `201 Created` (із заголовком `Location`), `204 No Content`.
- **3xx** Переспрямування — постійне `301`, тимчасові `302`/`307`, `304 Not Modified` (кешування).
- **4xx** Помилка клієнта — некоректний запит `400`, неавтентифікований `401`, автентифікований, але без прав `403`, не знайдено `404`, конфлікт `409`, не можна обробити `422`, забагато запитів `429`.
- **`5xx`** Помилка сервера — необроблений exception (виняток) `500`, помилка шлюзу `502` (проксі отримав неправильну відповідь), недоступний `503` (перевантаження або deployment), тайм-аут шлюзу `504`.

В API: повертайте `201` із `Location` після створення, `204` після успішного `DELETE`, `409` для конфлікту з поточним станом, `429` за rate limiting (обмеження частоти) й `500` лише для власних помилок. Різниця між `400` і `422` залежить від домовленостей: `400` для некоректного запиту, `422` — для коректного за формою, але такого, що порушує правило. Автоматична перевірка в ASP.NET Core повертає `400`; якщо оберете `422`, використовуйте його всюди, щоб клієнти бачили єдину домовленість.

> **Пастка.** Повернення `200` із помилкою в тілі. Політики повторів, кеші й панелі помилок читають код стану, а не тіло; отже, усі вони вважатимуть збій успіхом.

> **Рекомендація.** Люди часто плутають `401` і `403`. `401` означає: «ми не знаємо, хто ви; автентифікуйтеся», і відповідь має містити заголовок `WWW-Authenticate` із потрібним способом. Клієнт оновить токен або попросить користувача ввійти. `403` означає: «ми знаємо, хто ви, але цю дію виконувати не можна»; повторна автентифікація не допоможе, тож клієнт не має її повторювати.

Добре знати напам’ять такі заголовки: `Content-Type` і `Accept` (узгодження формату вмісту), `Authorization`, `Cache-Control` та `ETag` (кешування: [CDN і заголовки кешування](#cdns-and-caching-headers) у Розділ 26), `Content-Encoding` (стискання gzip/brotli), `Retry-After` (разом із `429`/`503`) і `X-Forwarded-For`/`X-Forwarded-Proto` (справжня IP-адреса клієнта й схема, додані проксі; довіряйте їм лише від контрольованих вами проксі).

## HTTP/1.1, HTTP/2 і HTTP/3: як усували блокування на початку queue

Кожна версія HTTP виправляє проблеми продуктивності попередньої. Розуміння розвитку протоколу пояснює, *чому* працює сучасний веб.

**HTTP/1.1** надсилає відкритий текст через TCP-з’єднання, обробляючи один запит і одну відповідь на з’єднання за раз. Головним нововведенням були **постійні з’єднання** (keep-alive), що уникали TCP-рукостискання перед кожним запитом. Але був серйозний недолік: **блокування на початку queue прикладного рівня**. Одне з’єднання працює лише з одним запитом водночас. Браузери обходили це, відкриваючи близько шести паралельних з’єднань на вузол — марнуючи ресурси й усе одно обмежуючи паралельність.

**HTTP/2** (2015) усунув блокування прикладного рівня за допомогою **мультиплексування**. З’явився **рівень двійкового кадрування**: одне TCP-з’єднання переносить багато незалежних **потоків** одночасно, а запити й відповіді діляться на кадри, що чергуються. Також додано **стискання заголовків (HPACK)**, оскільки заголовки HTTP часто повторюються, і **push із сервера** (який здебільшого вже застарів). Одне з’єднання, багато паралельних запитів — більше не потрібно відкривати шість сокетів.

Але HTTP/2 і далі використовує TCP, а TCP має власне блокування на початку queue рівнем нижче. Якщо загубиться один пакет TCP, протокол затримає *всі* потоки до його повторного надсилання — навіть ті, чиї дані вже надійшли. У мережі з втратами (мобільному зв’язку чи Wi-Fi) HTTP/2 насправді може працювати гірше за кілька з’єднань HTTP/1.1.

**HTTP/3** (2022) усуває проблему в корені, повністю відмовившись від TCP. Він працює поверх **QUIC** — нового транспортного протоколу на основі **UDP**. QUIC повторно реалізує надійність, порядок і керування перевантаженням *для кожного потоку окремо*, тому втрата пакета блокує лише *його* потік. Транспортне й TLS-рукостискання також **об’єднані**, тож установлення з’єднання часто потребує лише одного обміну (або жодного за повторного підключення). Крім того, працює **міграція з’єднання**: телефон, що переходить із Wi-Fi на стільникову мережу, зберігає те саме QUIC-з’єднання за ідентифікатором з’єднання замість пари IP-адреса:порт.

| Версія | Транспорт | Паралельність | Основне виправлення |
|---------|-----------|-------------|---------|
| HTTP/1.1 | TCP | 1 запит/з’єднання | Постійні з’єднання |
| HTTP/2 | TCP | Мультиплексовані потоки | Блокування прикладного рівня, стискання заголовків |
| HTTP/3 | QUIC/UDP | Незалежні потоки | Блокування транспортного рівня, швидше рукостискання, міграція |

У .NET HTTP/2 добре підтримується, а HTTP/3 доступний; його можна ввімкнути для окремого запиту:

```csharp
using var client = new HttpClient();
var request = new HttpRequestMessage(HttpMethod.Get, "https://example.com")
{
    Version = HttpVersion.Version30,
    VersionPolicy = HttpVersionPolicy.RequestVersionOrLower
};
var response = await client.SendAsync(request);
```

`RequestVersionOrLower` означає «спробувати HTTP/3, а за потреби перейти на нижчу версію». Це важливо, оскільки HTTP/3 залежить від того, чи оголосив сервер підтримку (через заголовок `Alt-Svc`) і чи не блокує UDP міжмережевий екран.

## Keep-Alive, connection pool і вичерпання сокетів

Рукостискання TCP, а потім TLS потребують кількох обмінів, тому клієнти HTTP підтримують з’єднання відкритими й зберігають у пулі для спільного використання запитами. Обійшовши пул, ви отримаєте одну з найвідоміших помилок .NET — **вичерпання сокетів**:

```csharp
// DO NOT DO THIS in a loop / per request
using (var client = new HttpClient())
{
    return await client.GetStringAsync(url);
}
```

Кожен `new HttpClient()` отримує власний handler (обробник) і connection pool, тому кожен виклик відкриває з’єднання, а `Dispose` його закриває. Сторона, що першою закрила з’єднання, утримує його в `TIME_WAIT`, щоб запізнілі пакети не дійшли до нового з’єднання, і разом із ним — локальний порт: 60 секунд у Linux (значення ядра) і типово 4 хвилини у Windows. Якщо відкривати з’єднання швидше, ніж звільняються порти, діапазон тимчасових портів вичерпається: у Linux з’явиться `HttpRequestException: Cannot assign requested address` (`SocketError.AddressNotAvailable`), а у Windows — повідомлення *Only one usage of each socket address…*. Причина — начебто правильний `using`.

> **Зверніть увагу.** **Чому проходять усі тести, але проблема виникає за пікового навантаження.**
>
> `TIME_WAIT` перетворює звичку створювати клієнт для кожного виклику на обмеження *нових з’єднань за секунду*:
>
> - **Linux:** 28 232 тимчасові порти (32768–60999) ÷ 60 с ≈ 470 з’єднань за секунду до кожного адресата.
> - **Windows:** 16 384 (49152–65535) ÷ 240 с ≈ 68 з’єднань за секунду.
> - **Azure App Service:** 128 попередньо виділених портів SNAT на екземпляр і адресата, звільнюються через чотири хвилини після закриття. Понад одне нове з’єднання приблизно за дві секунди екземпляр чекає на додаткові порти Azure ([Сценарій 3](#case-3-intermittent-timeouts-under-load-with-every-dashboard-green) у Розділ 30).
>
> Тести й робочі станції не досягають такої швидкості, а пік трафіку — досягає. Проблему виявляє лише навантажувальне тестування зі справжніми вихідними викликами; виправляє її тільки повторне використання з’єднань, як у наступному розділі.

## `IHttpClientFactory` і стійкість із Polly

Повторне використання з’єднань розв’язує проблему сокетів і повертає проблему DNS з розділу [Розв’язання DNS](#dns-resolution). `HttpClient` визначає IP-адресу лише під час відкриття з’єднання, а з’єднання з пулу закривається лише після хвилини бездіяльності. Тому довготривалий клієнт ніколи не виводить активне з’єднання з експлуатації й після перемикання через збій продовжує звертатися до старої IP-адреси.

`HttpClient` — легка обгортка; connection pool міститься у внутрішньому `HttpMessageHandler`. `IHttpClientFactory` розв’язує обидві проблеми: щоразу видає новий `HttpClient` поверх спільного handler, тому з’єднання повторно використовуються (звільняти клієнт фабрики безпечно, бо він не володіє handler), і через дві хвилини виводить кожен handler з експлуатації (`SetHandlerLifetime`). Нові з’єднання повторно шукають DNS, і після перемикання служба перестає звертатися до недоступної IP-адреси.

```
CatalogClient ──> HttpClient          (new each time — cheap wrapper)
                      │
                      ▼
              HttpMessageHandler      (pooled & shared — owns the sockets;
                                       recycled every ~2 min → fresh DNS)
```

**Іменовані клієнти** налаштовуються за рядковим ключем:

```csharp
// Registration
builder.Services.AddHttpClient("github", client =>
{
    client.BaseAddress = new Uri("https://api.github.com/");
    client.DefaultRequestHeaders.Add("User-Agent", "MyApp");
});

// Usage
public class GitHubService(IHttpClientFactory factory)
{
    public async Task<string> GetUserAsync(string login)
    {
        var client = factory.CreateClient("github");
        return await client.GetStringAsync($"users/{login}");
    }
}
```

**Типізовані клієнти** обгортають `HttpClient` у строго типізований сервіс. Це зручніше й мій типовий вибір:

```csharp
public class CatalogClient
{
    private readonly HttpClient _http;
    public CatalogClient(HttpClient http) => _http = http;

    public async Task<Product?> GetProductAsync(int id, CancellationToken ct) =>
        await _http.GetFromJsonAsync<Product>($"products/{id}", ct);
}

builder.Services.AddHttpClient<CatalogClient>(c =>
{
    c.BaseAddress = new Uri("https://catalog.internal/");
    c.Timeout = TimeSpan.FromSeconds(10);
});
```

> **Пастка: типізовані клієнти мають transient-час життя.** Singleton, що приймає типізований клієнт, назавжди захоплює один `HttpClient` і його handler, повертаючи проблему застарілого DNS. Залиште consumer (споживач) scoped або transient, впровадьте `IHttpClientFactory` і створюйте клієнти для кожного використання або (починаючи з .NET 8) установіть `PooledConnectionLifetime` через `.UseSocketsHttpHandler(...)`, щоб повертати до пулу нові з’єднання, не змінюючи handler.

Без фабрики коректно використовувати й один довготривалий `HttpClient`, якщо з’єднання періодично змінюються:

```csharp
var handler = new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),
    MaxConnectionsPerServer = 20
};
var client = new HttpClient(handler);
```

> **Рекомендація.** Ніколи не створюйте `HttpClient` через `new` для кожного запиту. Використовуйте `IHttpClientFactory` (типізовані клієнти й стійкість через `Microsoft.Extensions.Http.Resilience`) або один довготривалий екземпляр із налаштованим `PooledConnectionLifetime`.

### Стійкість із Polly

Мережеві збої часто тимчасові. **Polly** (інтегрований через `Microsoft.Extensions.Http.Resilience`) додає стратегії стійкості в pipeline handlers:

```csharp
builder.Services.AddHttpClient<CatalogClient>(...)
    .AddResilienceHandler("catalog", pipeline =>
    {
        pipeline.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true            // Avoid synchronized retry storms.
        });
        pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            SamplingDuration = TimeSpan.FromSeconds(30),
            BreakDuration = TimeSpan.FromSeconds(15)
        });
        pipeline.AddTimeout(TimeSpan.FromSeconds(3)); // Per-attempt timeout.
    });
```

Три основні шаблони й призначення кожного:

- **Повтор** із експоненційним очікуванням і випадковим збуренням обробляє короткочасні збої. Типові `HttpRetryStrategyOptions` повторюють запити після тимчасових помилок: 5xx, 408, 429 і `HttpRequestException`, але не після клієнтських помилок 4xx. Повторюйте лише *ідемпотентні* операції ([Методи HTTP та ідемпотентність](#http-methods-and-idempotency)), інакше побічний ефект може відбутися двічі.
- **Circuit breaker (автоматичний вимикач)** припиняє надсилати запити службі, яка явно не працює. Після досягнення порогу помилок він «розмикає коло» й швидко відхиляє виклики протягом періоду охолодження, щоб залежна служба встигла відновитися. Без нього повтори перетворять збій на каскадний.
- **Тайм-аут** обмежує тривалість однієї спроби, щоб повільна залежність не займала потоки.

Ізоляцію ресурсів і дію цих шаблонів між багатьма службами розглянуто в [Розділі 20: distributed systems (розподілені системи)](#chapter-20-distributed-systems).

> **Тут також важливий порядок.** Стратегії, додані *раніше*, розміщуються *зовні* тих, що додані пізніше. У прикладі вище повтор — зовнішній, тому тайм-аут у 3 секунди є бюджетом *на одну спробу*: кожен повтор отримує нові 3 секунди, а `Timeout` типізованого клієнта в 10 секунд обмежує всю операцію разом із повторами. Тайм-аут однієї спроби розміщуйте всередині повтору, а загальний — зовні.

> **Рекомендація.** Якщо не маєте конкретних значень для налаштування, почніть із `.AddStandardResilienceHandler()` — одного рядка, що додає рекомендований Microsoft pipeline (обмежувач частоти, загальний тайм-аут, повтор, автоматичний вимикач і тайм-аут окремої спроби) з адекватними значеннями за замовчуванням. Змінюйте їх, лише якщо є докази, що типові значення не підходять.

Це був клієнтський бік HTTP. Решта розділу — інший кінець з’єднання: що робить ASP.NET Core із запитом після надходження.

## Pipeline middleware і життєвий цикл запиту

**Запит проходить ланцюжок компонентів, кожен із яких може виконати роботу до й після наступного компонента.** Цей ланцюжок — *pipeline middleware*. Компонент може й перервати його: відповісти самостійно, не викликаючи решту. На зворотному шляху відповідь проходить ті самі компоненти у зворотному порядку, тож зовнішній middleware обгортає все всередині.

Компонент middleware — функція, що приймає поточний `HttpContext` і делегат для «решти pipeline» (`RequestDelegate`, який зазвичай називають `next`).

```csharp
public class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _logger;

    public RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var start = Stopwatch.GetTimestamp();

        // Work BEFORE the rest of the pipeline runs.
        await _next(context); // Hand off to the next middleware.
        // Work AFTER control unwinds back to us.

        var elapsed = Stopwatch.GetElapsedTime(start);
        _logger.LogInformation("{Method} {Path} took {Ms} ms",
            context.Request.Method, context.Request.Path, elapsed.TotalMilliseconds);
    }
}
```

Сигнатура `InvokeAsync` — це *домовленість*, а не інтерфейс (хоча `IMiddleware` існує для варіанта, який створює фабрика). Платформа знаходить цей метод за назвою. Сам middleware створюється **один раз** як singleton під час запуску. Тому `RequestDelegate` і `ILogger` (singleton-сервіси) передають у конструктор, а scoped-сервіси — **ні**. Щоб використовувати scoped-сервіс, передайте його параметром у `InvokeAsync`, де вже доступна область запиту.

Зареєструйте middleware у pipeline через `UseMiddleware` або обгорніть його в метод розширення:

```csharp
var app = builder.Build();

app.UseMiddleware<RequestTimingMiddleware>();
```

Для одноразової логіки можна використати вбудовані лямбди:

```csharp
// Passes control onward.
app.Use(async (context, next) =>
{
    context.Response.Headers["X-Request-Id"] = Guid.NewGuid().ToString("N");
    await next(context);
});

// Terminal middleware — never calls next, ends the pipeline.
app.Run(async context =>
{
    await context.Response.WriteAsync("Nothing matched.");
});
```

Також є `Map` і `MapWhen` для розгалуження pipeline за шляхом або умовою.

### Порядок має вирішальне значення

Порядок додавання middleware — це *порядок*, у якому проходить запит.

> **Рекомендація — типовий порядок.** Спершу exception handling (обробка винятків) (вона обгортає решту), потім HSTS і переспрямування на HTTPS, статичні файли, routing, CORS, автентифікація, авторизація й насамкінець endpoints. Автентифікація має передувати авторизації: не можна перевірити, *що дозволено робити людині*, доки невідомо, *хто вона*.

```csharp
app.UseExceptionHandler();      // Outermost: catches everything below.
app.UseHsts();
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();               // Decides which endpoint matches.
app.UseCors();
app.UseRateLimiter();
app.UseAuthentication();        // Who are you?
app.UseAuthorization();         // Are you allowed?
app.MapControllers();           // Terminal: executes the endpoint.
```

Цей порядок реєстрації створює таку вкладену послідовність:

```
       request                                    response
          |                                           ^
          v                                           |
+-- UseExceptionHandler ------------------------------|------+
|         |                                           |      |
|  +-- UseRouting / UseCors / UseRateLimiter ---------|---+  |
|  |      |                                           |   |  |
|  |  +-- UseAuthentication -> UseAuthorization ------|-+ |  |
|  |  |   |                                           | | |  |
|  |  |   +-----> MapControllers (endpoint) ----------+ | |  |
|  |  +-------------------------------------------------+ |  |
|  +------------------------------------------------------+  |
+------------------------------------------------------------+
```

Кожен middleware бачить лише те, що встановили попередні компоненти, тож неправильний порядок дає передбачувані помилки:

- **`UseAuthorization` перед `UseAuthentication`:** авторизація читає `HttpContext.User`, який автентифікація ще не заповнила. Користувач виглядає анонімним, тому кожна endpoint з `[Authorize]` повертає `401`, навіть за правильного токена.
- **`UseAuthorization` перед `UseRouting`:** endpoint ще не вибрано, тож немає метаданих `[Authorize]` для перевірки. Middleware endpoint виявить, що авторизація пропустила її, і викине помилку *"Endpoint … contains authorization metadata, but a middleware was not found that supports authorization"*: на кожній захищеній endpoint буде `500`, а не тихе обходження авторизації. Так само перевіряються метадані CORS.
- **`UseExceptionHandler` зареєстровано не першим:** він обгортає `await next(context)` у `try`, тож не може перехопити exception middleware, зареєстрованого перед ним.

**Якщо щось «не застосовується», спершу перевірте порядок.**

> **Зверніть увагу.** **`WebApplication` сам упорядковує стандартні компоненти, доки ви не викликаєте їх вручну.** Якщо явних викликів немає, `WebApplicationBuilder` додає навколо вашого middleware такі компоненти: `UseDeveloperExceptionPage` (лише в Development), `UseRouting`, потім `UseAuthentication` і `UseAuthorization`, якщо зареєстровано потрібні служби, далі все з `Program.cs`, а тоді — endpoints. Саме тому мінімальний застосунок із `AddAuthentication()` працює без викликів `Use…`. Щойно ви самі викликаєте `app.UseRouting()`, `UseAuthentication()` чи `UseAuthorization()`, автоматичне додавання пропускається: порядок тепер задаєте ви й можете спричинити помилки вище. Або не викликайте жоден із трьох, або викликайте всі й у правильному порядку.

## Routing та routing endpoints

У сучасному ASP.NET Core routing має **два етапи**, і завдяки цьому middleware між ними бачить, *яка* endpoint виконається. `UseRouting` зіставляє вхідну URL-адресу з endpoint й зберігає результат у `HttpContext`. Наступний middleware (автентифікація, CORS) може прочитати метадані endpoint. Насамкінець middleware endpoint (неявно доданий через `MapControllers`/`MapGet`) виконує її.

Шаблони маршрутів підтримують **обмеження**, що відсіюють відповідності за типом або шаблоном:

```csharp
app.MapGet("/orders/{id:guid}", ...);          // Only matches valid GUIDs.
app.MapGet("/reports/{year:int:min(2000)}", ...); // int >= 2000.
app.MapGet("/files/{*path}", ...);             // Catch-all segment.
app.MapGet("/users/{name:alpha:length(3,20)}", ...);
```

Обмеження призначені для *усунення неоднозначності маршрутів*, а не для перевірки введених даних. Якщо `{id:int}` не відповідає запиту, повернеться `404` (маршрут просто не підходить), а не зрозумілий `400` про некоректний ідентифікатор. Використовуйте обмеження для правильної routing, а перевірку моделі — для зрозумілих повідомлень про помилки.

## Мінімальні API та контролери (MVC)

ASP.NET Core надає дві моделі програмування, які компілюються в ту саму інфраструктуру routing endpoints. Жодна не є «кращою» — їх оптимізовано для різних завдань.

**Контролери (MVC)** об’єднують endpoints в класи, спираються на домовленості (routing атрибутами, фільтри, прив’язування моделі за атрибутами) й корисні для багатьох endpoints зі спільною наскрізною поведінкою.

```csharp
[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private readonly IProductService _service;
    public ProductsController(IProductService service) => _service = service;

    [HttpGet("{id:int}")]
    public async Task<ActionResult<ProductDto>> GetById(int id)
    {
        var product = await _service.FindAsync(id);
        return product is null ? NotFound() : Ok(product);
    }

    [HttpPost]
    public async Task<ActionResult<ProductDto>> Create(CreateProductRequest request)
    {
        var created = await _service.CreateAsync(request);
        return CreatedAtAction(nameof(GetById), new { id = created.Id }, created);
    }
}
```

Атрибут `[ApiController]` непомітно робить багато роботи: автоматично перевіряє стан моделі (за помилки прив’язування повертає `400` із деталями проблеми), визначає джерело прив’язування (тіло, маршрут чи рядок запиту) й формує відповіді `ProblemDetails`. `ControllerBase` надає допоміжні методи `Ok`, `NotFound`, `CreatedAtAction` тощо.

**Мінімальні API** оголошують endpoints безпосередньо в застосунку або групі маршрутів як лямбда-вирази. Тут менше шаблонного коду, call stack (стек викликів) коротший (швидший запуск і трохи швидша обробка запитів), а оголошення читаються згори донизу.

```csharp
var products = app.MapGroup("/api/products").WithTags("Products");

products.MapGet("/{id:int}", async (int id, IProductService service) =>
    await service.FindAsync(id) is { } p ? Results.Ok(p) : Results.NotFound());

products.MapPost("/", async (CreateProductRequest request, IProductService service) =>
{
    var created = await service.CreateAsync(request);
    return Results.CreatedAtRoute("GetProduct", new { id = created.Id }, created);
})
.WithName("CreateProduct");
```

Зауважте, що залежності (`IProductService`) просто задаються параметрами: платформа знаходить їх у DI за типом. `Results` — відповідник допоміжних методів `ControllerBase` для мінімальних API, а `TypedResults` — строго типізований варіант, зручніший для тестування й виведення схеми OpenAPI.

> **Що й коли використовувати.** Обирайте **мінімальні API** для мікросервісів, невеликих спеціалізованих служб і рівнів BFF/шлюзів, де важливі стислість і швидкий запуск. Обирайте **контролери** для великих API зі спільними домовленостями, активним використанням фільтрів або потребою швидко знаходити endpoints за принципом «клас на ресурс». Їх можна поєднувати в одному застосунку.

## Фільтри

Фільтри виконуються *всередині* MVC або endpoint після вибору маршруту. Вони дають доступ до контексту прив’язування моделі (далі) й результату дії, яких не бачить звичайний middleware. Вони утворюють власний мініконвеєр із визначеним порядком: **авторизація → ресурс → дія → (endpoint) → результат**, а фільтри **exceptions** перехоплюють викинуті exceptions.

```csharp
public class AuditActionFilter : IAsyncActionFilter
{
    private readonly ILogger<AuditActionFilter> _logger;
    public AuditActionFilter(ILogger<AuditActionFilter> logger) => _logger = logger;

    public async Task OnActionExecutionAsync(
        ActionExecutingContext context, ActionExecutionDelegate next)
    {
        _logger.LogInformation("Executing {Action}", context.ActionDescriptor.DisplayName);
        var executed = await next(); // Runs the action.
        if (executed.Exception is null)
            _logger.LogInformation("Completed {Action}", context.ActionDescriptor.DisplayName);
    }
}
```

- **Фільтри авторизації** виконуються першими й визначають, чи можна продовжити запит (саме до них під’єднується `[Authorize]`).
- **Фільтри ресурсів** обгортають прив’язування моделі — зручно для кешування або раннього припинення дорогої роботи.
- **Фільтри дій** виконуються до й після методу дії та мають доступ до прив’язаних аргументів і результату.
- **Фільтри результату** обгортають виконання результату (наприклад, формування відповіді).
- **Фільтри exceptions** перехоплюють необроблені exceptions з дій і дають змогу перетворити їх на відповідь.

Аналог мінімальних API — **фільтр endpoint** (`IEndpointFilter`/`AddEndpointFilter`), легший ланцюжок навколо однієї endpoint або групи.

> **Фільтр чи middleware — що обрати?** Якщо логіці потрібні відомості про *дію, її аргументи чи результат*, використовуйте фільтр. Для наскрізної логіки, що не залежить від типу вмісту (вимірювання часу, ідентифікатори кореляції, стискання), використовуйте middleware. Middleware ширший і дешевший, фільтр має конкретніший контекст.

## Серіалізація: `System.Text.Json` чи Newtonsoft.Json

Між байтами в мережі й об’єктами, які endpoint приймає та повертає, працює серіалізатор. Роками типовим стандартом був **Newtonsoft.Json** (Json.NET). Починаючи з .NET Core 3.0, Microsoft постачає **`System.Text.Json` (STJ)** разом із платформою. Його створено для **високої продуктивності й малої кількості виділень пам’яті**: він працює безпосередньо з `Span<byte>`/UTF-8, оминаючи проміжне перетворення на рядки, яке виконує Newtonsoft, і значно швидший та економніший.

Основні відмінності:

- **Продуктивність:** STJ значно швидший і виділяє менше пам’яті. У ASP.NET Core він використовується за замовчуванням.
- **Типові параметри:** STJ типово **суворіший** — чутливий до регістру під час зіставлення властивостей (це можна налаштувати), не приймає коментарів і завершальних ком без окремого ввімкнення, а деякі дані, які Newtonsoft приймає поблажливо (наприклад, числа в лапках), обробляє лише після спеціального налаштування.
- **Ширина можливостей:** Newtonsoft досі краще підтримує окремі складні сценарії (`TypeNameHandling` для вбудовування типу поліморфного об’єкта, гнучкий `[JsonConstructor]`, особливості `DefaultValueHandling`, зручність LINQ-to-JSON із `JObject`/`JToken`), хоча STJ наздогнав його в більшості можливостей і додав поліморфізм (`[JsonDerivedType]`) та `JsonNode`.

```csharp
var options = new JsonSerializerOptions
{
    PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
    PropertyNameCaseInsensitive = true,
    DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull,
    WriteIndented = false
};

string json = JsonSerializer.Serialize(order, options);
Order? back = JsonSerializer.Deserialize<Order>(json, options);
```

### Власні конвертери

Коли типове зіставлення не підходить (власний формат дати, перелік як рядок, доменний примітив), створіть **`JsonConverter<T>`**:

```csharp
public sealed class DateOnlyConverter : JsonConverter<DateOnly>
{
    private const string Format = "yyyy-MM-dd";
    public override DateOnly Read(ref Utf8JsonReader reader, Type t, JsonSerializerOptions o)
        => DateOnly.ParseExact(reader.GetString()!, Format);
    public override void Write(Utf8JsonWriter writer, DateOnly value, JsonSerializerOptions o)
        => writer.WriteStringValue(value.ToString(Format));
}
```

ASP.NET Core читає тіла запитів і записує відповіді через STJ із вебпараметрами за замовчуванням: назви в camelCase та пошук без урахування регістру під час читання. Змініть їх через `ConfigureHttpJsonOptions` для мінімальних API або `AddControllers().AddJsonOptions(...)` для контролерів. Генератор джерела STJ створює код серіалізації під час компіляції, усуває рефлексію під час запуску й забезпечує сумісність із trimming та Native AOT. У [Генератори вихідного коду: JSON без рефлексії](#source-generators-json-without-reflection) у Розділ 22 розглянуто цей підхід та інші типові налаштування STJ, які створюють проблеми під час переходу з Newtonsoft.

> **Рекомендація.** Для нових проєктів типово обирайте `System.Text.Json`; для AOT або обрізаних застосунків і hot paths (гарячі шляхи) серіалізації додайте генерацію коду. Залишайте Newtonsoft лише тоді, коли потрібна відсутня у STJ функція або бібліотека, що вимагає його; під час міграції враховуйте відмінності в суворості.

## Прив’язування й перевірка моделі

Прив’язування моделі перетворює необроблений HTTP — значення маршруту, рядок запиту, заголовки, поля форми й тіло JSON — на параметри методу C# та об’єкти. З `[ApiController]` джерело прив’язування *визначається автоматично*: складні типи надходять із тіла, прості — з маршруту чи рядка запиту. Джерело можна вказати явно через `[FromBody]`, `[FromRoute]`, `[FromQuery]`, `[FromHeader]`, `[FromServices]`.

### DataAnnotations

Вбудований спосіб перевірки — позначити властивості атрибутами, наприклад `[Required]` і `[StringLength]`:

```csharp
public class CreateProductRequest
{
    [Required, StringLength(120, MinimumLength = 3)]
    public string Name { get; set; } = string.Empty;

    [Range(0.01, 100_000)]
    public decimal Price { get; set; }

    [EmailAddress]
    public string? ContactEmail { get; set; }
}
```

З `[ApiController]` невідповідна модель автоматично формує `400 Bad Request` із даними `ProblemDetails` про помилку перевірки — ASP.NET Core спершу заповнює `ModelState`, тож вам не потрібно писати `if (!ModelState.IsValid)`. Мінімальні API за замовчуванням не перевіряють модель. Починаючи з .NET 10, `builder.Services.AddValidation()` застосовує ті самі DataAnnotations (і `IValidatableObject`) до параметрів із рядка запиту, заголовків і тіла та повертає `400` з описом помилок. У попередніх версіях перевіряйте дані вручну або використовуйте фільтр.

> **Зверніть увагу.** **Автоматичний `400` створює фільтр дій, тому сама дія не виконується.** `[ApiController]` додає фільтр, який перевіряє `ModelState` після прив’язування й до запуску дії: точка зупину в дії не спрацює, а рядок журналу не буде записано. Помилки прив’язування потрапляють туди ж: нерозбірне тіло або неправильний тип JSON дає `400` від цього фільтра, а не exception. Щоб змінити формат відповіді, налаштуйте `ApiBehaviorOptions.InvalidModelStateResponseFactory`, а не додавайте недосяжні перевірки `if (!ModelState.IsValid)`.

### FluentValidation

Коли правила стають умовними або залежать від кількох полів («знижка діє, лише коли товар розпродають»), DataAnnotations стають незручними. **FluentValidation** переносить правила до окремого класу з виразним API, зручним для тестування:

```csharp
public class CreateProductValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductValidator()
    {
        RuleFor(x => x.Name).NotEmpty().Length(3, 120);
        RuleFor(x => x.Price).GreaterThan(0);
        RuleFor(x => x.ContactEmail)
            .EmailAddress()
            .When(x => x.ContactEmail is not null);
    }
}
```

**Для чого насправді потрібен валідатор.** Перш ніж обговорювати API, визначмо межу між рівнями — саме тут команди часто помиляються. Валідатор запиту відповідає на запитання *«чи правильно сформовано цей запит?»* — питання транспортного рівня: чи правильно структуровано JSON, чи не задовгі рядки, чи можна розібрати дату, чи входить значення переліку до допустимого набору. Інваріант домену відповідає на інше запитання: *«чи дозволений такий стан?»* Замовлення не можна відправити до оплати, баланс не може бути від’ємним, знижка не може перевищувати суму позиції. Перше стосується повідомлення, друге — моделі.

Причина розділяти їх практична, а не естетична. Валідатор запускається лише там, де ви згадали його викликати, а HTTP-кінцева точка — не єдиний шлях змінити стан. Фонова задача, consumer повідомлень, скрипт адміністратора й майбутня endpoint gRPC змінюють ту саму сутність, але жоден із них не проходить через `CreateProductValidator`. Якщо єдиний захист системи від недозволеного стану — валідатор, під’єднаний до одного контролера, достатньо додати один шлях коду, щоб цей стан став можливим.

Тому перевіряйте дані на межі *й* встановлюйте обмеження в домені. Завдання валідатора на межі — повернути клієнту належний `400` зі списком помилок для полів замість `500` через exception у конструкторі. Завдання домену — зробити недозволений стан неможливим незалежно від викликувача: за допомогою охоронних перевірок, об’єктів-значень ([Розділ 10: Основи проєктування](#chapter-10-design-basics)) та інваріантів у кореневому агрегаті ([Розділ 21: архітектура](#chapter-21-architecture)). Перевірка «ім’я має містити 3–120 символів» в обох місцях — не дублювання, яке треба прибрати рефакторингом; це дві перевірки з різними завданнями й наслідками помилки. **Перевірка на межі не виправдовує анемічну доменну модель.**

**Під’єднання.** Валідатори реєструються пошуком у збірці:

```csharp
builder.Services.AddValidatorsFromAssemblyContaining<CreateProductValidator>();
```

Цей виклик реєструє кожен `AbstractValidator<T>` у збірці як `IValidator<T>` — за замовчуванням зі scoped-часом життя, тож валідатори можуть мати залежності DI. Він навмисно **не** під’єднує їх до pipeline прив’язування моделі MVC. Стара інтеграція `AddFluentValidationAutoValidation()` застаріла, і причина повчальна: вона працювала під час синхронного прив’язування моделі, тому асинхронні правила доводилося блокувати; спрацьовувала для *кожного* складного прив’язаного типу незалежно від потреби; повідомляла про помилки через `ModelState`, внутрішній механізм якого доводилося відтворювати. Сучасний підхід явний: отримайте `IValidator<T>` і викликайте його там, де вирішили:

```csharp
products.MapPost("/", async (CreateProductRequest request,
    IValidator<CreateProductRequest> validator, IProductService service, CancellationToken ct) =>
{
    var result = await validator.ValidateAsync(request, ct);
    if (!result.IsValid)
        return Results.ValidationProblem(result.ToDictionary());

    return Results.Ok(await service.CreateAsync(request, ct));
});
```

`ToDictionary()` створює словник `field → messages` (поле → повідомлення), який `Results.ValidationProblem` перетворює на `ValidationProblemDetails` — ту саму форму RFC 7807, що й `[ApiController]`. Тому в застосунку зі змішаними підходами єдиний формат помилок, а не два.
Щоразу писати ці чотири рядки в кожній endpoint швидко набридає, тож винесіть їх у фільтр endpoint (фільтр мінімальних API з розділу [Фільтри](#filters) вище):

```csharp
public class ValidationFilter<T> : IEndpointFilter where T : class
{
    public async ValueTask<object?> InvokeAsync(
        EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        var model = ctx.Arguments.OfType<T>().FirstOrDefault();
        var validator = ctx.HttpContext.RequestServices.GetService<IValidator<T>>();
        if (model is null || validator is null) return await next(ctx);

        var result = await validator.ValidateAsync(model, ctx.HttpContext.RequestAborted);
        return result.IsValid
            ? await next(ctx)
            : TypedResults.ValidationProblem(result.ToDictionary());
    }
}

products.MapPost("/", ...).AddEndpointFilter<ValidationFilter<CreateProductRequest>>();
```

Еквівалент для контролера — `IAsyncActionFilter`, що отримує модель із `context.ActionArguments`. Або, якщо вам зручні валідатори, які викидають exception, дозвольте `ValidationException` поширитися й перетворіть його через `IExceptionHandler` ([Що показувати: ProblemDetails](#what-to-surface-problemdetails) у Розділ 9).

> **Нюанс.** Цей фільтр **пропускає запит за відсутності валідатора**: без зареєстрованого валідатора запит пройде далі. Це правильне типове значення для загального фільтра (не потрібно повертати `500` для endpoints без параметрів), але помилка в назві класу валідатора непомітно вимкне перевірку без жодного збою. Якщо застосовуєте фільтр за домовленістю до всієї групи, додайте тест запуску, який перевіряє, що для кожного DTO запиту, доступного з endpoints, зареєстровано `IValidator<T>`.

**Композиція.** Виразний API справді корисний для правил, яких не можна описати через DataAnnotations:

```csharp
public class CreateOrderValidator : AbstractValidator<CreateOrderRequest>
{
    public CreateOrderValidator(IValidator<OrderLineDto> lineValidator)
    {
        ClassLevelCascadeMode = CascadeMode.Continue;   // report every bad property...
        RuleLevelCascadeMode  = CascadeMode.Stop;       // ...but one message per property

        RuleFor(x => x.CustomerId).NotEmpty().WithErrorCode("order.customer_required");
        RuleFor(x => x.Lines).NotEmpty().WithErrorCode("order.lines_empty");

        RuleForEach(x => x.Lines).SetValidator(lineValidator);   // one child validator per element

        When(x => x.Coupon is not null, () =>
        {
            RuleFor(x => x.Coupon!.Code)
                .Matches("^[A-Z0-9]{4,12}$").WithErrorCode("coupon.malformed");
            RuleFor(x => x.Coupon!.Amount)
                .LessThanOrEqualTo(x => x.Lines.Sum(l => l.UnitPrice * l.Quantity))
                .WithErrorCode("coupon.exceeds_total");
        });

        RuleSet("Admin", () =>
            RuleFor(x => x.BackdatedAt).NotNull().WithErrorCode("order.backdate_required"));
    }
}
```

- **`RuleForEach(...).SetValidator(...)`** передає кожен елемент колекції окремому валідатору й додає індекс до `PropertyName` помилки — `Lines[2].Quantity`. Так клієнт підсвітить неправильний рядок, а не весь масив. `SetValidator` для однієї властивості так само перевіряє вкладений об’єкт.
- **`When` / `Unless`** активують правила за умовою. Віддавайте перевагу блочному варіанту вище замість `.When(...)` наприкінці кожного правила: умову вказано один раз, вона читається як гілка й не загубиться, коли хтось додасть до неї правило.
- **`RuleSet`** називає групу правил, яку запускають лише за запитом: `validator.ValidateAsync(order, o => o.IncludeRuleSets("Admin"), ct)`. Це зручно, коли той самий DTO надходить від двох викликувачів із різними правами, хоча часто простіше завести два DTO.
- **Режими каскаду** визначають, що відбувається *після* помилки. `RuleLevelCascadeMode = Stop` припиняє ланцюжок перевірок однієї властивості після першої помилки: для відсутнього `Name` буде повідомлення «обов’язкове поле», а не воно *і* «має містити 3–120 символів». `ClassLevelCascadeMode = Stop` завершує весь валідатор після першої неправильної властивості — майже ніколи не те, що потрібно API: клієнт радше виправить усе за один запит, а не гратиме в «удари крота».

> **Рекомендація — стабільні коди помилок.** `WithErrorCode` додає ідентифікатор для машинної обробки поруч із повідомленням для людини. Завдяки йому клієнт розрізняє правило за кодом, а не шукає текст `"Coupon exceeds order total"`. Повідомлення локалізують, переписують за вимогами продукту й змінюють під час редагування файла; коди — це контракт. Повертайте їх, наприклад, у масиві `errors` з об’єктами `{ code, field, message }`, який містить більше від словника «поле → повідомлення», і вважайте перейменування коду несумісною зміною ([Розділ 22](#chapter-22-api-evolution-real-time-and-serialization) пояснює, що ще ламає клієнта).

**Асинхронні правила й пастка в них.** Валідатори можуть звертатися до бази даних, адже вони є службами DI:

```csharp
RuleFor(x => x.Sku)
    .MustAsync(async (sku, ct) => !await db.Products.AnyAsync(p => p.Sku == sku, ct))
    .WithErrorCode("product.sku_taken")
    .WithMessage("SKU '{PropertyValue}' is already in use.");
```

Це корисно: замість `500` через `DbUpdateException` порушення обмеження перетворюється на зрозумілий `400` з указанням поля. Але це *не* гарантія унікальності. Між `AnyAsync`, що відповідає «вільно», і `SaveChangesAsync`, що вставляє запис, інший запит може зробити те саме. Це класична помилка «перевір, а потім виконай», а вікно гонки охоплює решту обробки запиту. Два паралельні запити з тим самим SKU обидва пройдуть перевірку й обидва виконають вставлення.

Унікальність насправді забезпечує лише **унікальний індекс у базі даних** ([Розділ 7: Доступ до даних](#chapter-7-data-access)), оскільки тільки ця перевірка відбувається в межах тієї самої атомарної операції, що й запис. Тому потрібні обидва механізми: валідатор формує зрозуміле повідомлення для найпоширенішого випадку, індекс забезпечує коректність решти, а ви перехоплюєте `DbUpdateException` і повертаєте те саме тіло, яке сформував би валідатор. Якщо можете реалізувати лише один із них, створіть індекс.

> **Пастка — один `DbContext`, одна операція за раз.** Валідатор, якому впровадили `AppDbContext`, використовує той самий *scoped*-екземпляр запиту, що й handler та інші валідатори цього запиту. Один `ValidateAsync` безпечний, бо FluentValidation очікує правила послідовно. Але якщо розпаралелити роботу (`Task.WhenAll` для кількох валідаторів або паралельну перевірку елементів пакетного запиту), два правила `MustAsync` можуть одночасно звернутися до контексту. Тоді виникне *"A second operation was started on this context instance."* Виконуйте перевірки послідовно або впровадьте `IDbContextFactory<AppDbContext>` і створюйте короткочасний контекст для кожної перевірки ([Час життя `DbContext` і пул підключень](#dbcontext-lifetime-and-connection-pooling) у Розділ 7). Також зауважте: одного `MustAsync` достатньо, щоб увесь валідатор став асинхронним; виклик синхронного `Validate()` викине exception.
**Тестування.** Валідатори — звичайні об’єкти, які не залежать від HTTP, тому це одні з найдешевших модульних тестів у кодовій базі. `FluentValidation.TestHelper` надає перевірки через вирази над моделлю:

```csharp
[Fact]
public void Rejects_blank_name()
{
    var validator = new CreateProductValidator();

    var result = validator.TestValidate(new CreateProductRequest { Name = "", Price = 10m });

    result.ShouldHaveValidationErrorFor(x => x.Name)
          .WithErrorCode("product.name_required");
    result.ShouldNotHaveValidationErrorFor(x => x.Price);
}
```

Назва властивості задається лямбда-виразом, а не рядком, тому перейменування `Name` спричинить помилку компіляції, а не залишить тест, який непомітно перевіряє застарілий літерал `"Name"`. Перевіряйте `WithErrorCode`, а не `WithErrorMessage`, з тієї самої причини, з якої ми надали клієнтам коди: текст зміниться. Обов’язково перевіряйте й *негативні* випадки — порожній рядок, граничне значення, відсутню знижку та умовну гілку, яка працює лише за наявності `Coupon`; інакше їх знайде за вас продакшен.

**Який механізм обрати?**

| Підхід | Переваги | Обмеження |
|---|---|---|
| **DataAnnotations** | Декларативна перевірка форми поруч із DTO; без додаткового налаштування з `[ApiController]`; атрибути потрапляють у схему OpenAPI й відображаються у створених SDK клієнта | Правила між полями та умовні правила (`IValidatableObject` або власний атрибут) незручні; немає DI, асинхронних правил чи звернення до даних; фіксований набір правил для типу не залежить від викликувача чи сценарію |
| **FluentValidation** | Умовні правила, перевірки кількох полів і елементів колекції; DI та асинхронність; кілька валідаторів для однієї форми; стабільні коди помилок; просте модульне тестування | Непомітний для OpenAPI без фільтра схеми; потребує явного виклику й захищає лише налаштовані шляхи; усе ще має гонку «перевір, а потім виконай» із базою даних |
| **Доменне обмеження / об’єкт-значення** | Діє для *всіх* викликувачів — HTTP, consumer повідомлень, задачі, тесту; робить недозволений стан неможливим; правило розміщене поруч із поняттям, якого стосується | Викидає exception за першого порушення замість накопичення помилок, тому формує погане тіло відповіді; спрацьовує запізно, щоб надати клієнту список помилок для полів |

Це рівні, а не альтернативи. Для простих DTO достатньо DataAnnotations або нічого; FluentValidation на межі формує зрозумілу відповідь про помилки, а доменні обмеження забезпечують коректність, на яку можна покластися.

## Поширення `CancellationToken`

У [Розділ 4](#cancellationtoken-cooperative-cancellation) пояснено роботу `CancellationToken`; у веб-API його переваги особливо помітні. Після розриву з’єднання, тайм-ауту чи переходу користувача на іншу сторінку робота для нього марнується. `HttpContext.RequestAborted` — це `CancellationToken`, який спрацьовує після розриву з’єднання; мінімальні API й MVC передають його будь-якому параметру `CancellationToken` endpoint чи дії. Він допомагає, лише якщо ви *передаєте його далі*: запити EF Core, виклики `HttpClient` і читання потоків його приймають.

```csharp
app.MapGet("/reports/{id:int}", async (int id, AppDbContext db,
    ReportRenderer renderer, CancellationToken ct) =>
{
    var data = await db.ReportRows
        .Where(r => r.ReportId == id)
        .ToListAsync(ct);                    // Stops the query if the client is gone.

    return Results.Ok(await renderer.RenderAsync(data, ct));
});
```

Якщо клієнт від’єднається посеред запиту, EF Core скасує команду бази даних, а підключення повернеться до пулу. Без токена запит виконуватиметься до кінця, хоча викликувач уже не прочитає відповідь.

Найбільше це важливо під навантаженням. Клієнти отримують тайм-аут, кидають запити й *повторюють* їх. Якщо сервер ігнорує скасування, покинуті запити продовжують виконуватися, а повторні запускають дублікати. Навантаження подвоюється саме тоді, коли система вже має труднощі, і сповільнення переходить у збій. Передавання токена дає змогу зупинити покинуту роботу.

Токен зупиняє лише виклики, до яких його передано: один метод у ланцюжку, який не передав його далі, залишає решту роботи активною ([Розділ 4](#cancellationtoken-cooperative-cancellation) пояснює механізм і аналізатор, який знаходить забутий токен).

> **Нюанс.** Не все слід скасовувати. Якщо платіж уже списано й ви збираєтеся записати event (подія) до outbox, скасування *посеред запису* через від’єднання клієнта гірше за завершення марної роботи: гроші списані, а event втрачено. Після точки неповернення передавайте `CancellationToken.None` (або токен, не пов’язаний із запитом). Важливо знати, які операції можна безпечно покинути, а які вже створили зобов’язання.## Наскрізні аспекти HTTP

## Наскрізні аспекти HTTP

**CORS** (Cross-Origin Resource Sharing — обмін ресурсами між джерелами) визначає, з яких джерел браузера можна викликати API. **Джерело** — трійка схема + вузол + порт (`https://app.example.com`), а **Same-Origin Policy** забороняє JavaScript із одного джерела читати відповіді іншого. CORS дає серверу змогу *дозволити* конкретних зовнішніх викликувачів. Для всього, що виходить за межі «простого» запиту, браузер спершу надсилає **попередню перевірку** через `OPTIONS`: «чи може `https://app.example.com` надіслати сюди `POST` із заголовком `Authorization`?». Сервер відповідає заголовками `Access-Control-Allow-*` і лише тоді надсилається справжній запит. Тому `UseCors` має виконуватися до endpoint (див. порядок вище): `OPTIONS` не має власної endpoint, тож на нього відповідає middleware CORS.

```csharp
builder.Services.AddCors(o => o.AddPolicy("spa", p => p
    .WithOrigins("https://app.example.com")        // Explicit — never "*" on a real API.
    .WithMethods("GET", "POST")
    .WithHeaders("Authorization", "Content-Type")));
// ...
app.UseCors("spa");
```

CORS — механізм, який застосовує *браузер*: він не захищає сервер, а лише повідомляє браузеру, що дозволено. Це працює в обидва боки. Повідомлення консолі *«заблоковано політикою CORS»* означає, що **браузер не передав відповідь вашому JavaScript**. Сам запит зазвичай уже дійшов до сервера й був виконаний; перш ніж вирішити, що нічого не сталося, перевірте журнали сервера. І навпаки, CORS нічого не робить для `curl` чи іншої серверної програми — це не авторизація. У [CORS не є контролем доступу](#cors-is-not-access-control) в Розділ 12 розглянуто безпеку, а в [Розділі 6: Основи фронтенду](#chapter-6-frontend-essentials) — бік браузера.

> **Пастка.** `AllowAnyOrigin()` разом із `AllowCredentials()` заборонено специфікацією, і така комбінація не працюватиме. Не дозволяйте всі джерела в продакшені без окремої причини.

> **Нюанс — CORS не захищає від CSRF.** Якщо браузер автентифікує користувачів за *cookie*, потрібен захист **antiforgery**, який постачає ASP.NET Core: автоматичний для допоміжних тегів форм Razor Pages/MVC і доступний у мінімальних API через служби antiforgery, додані в .NET 8. API з автентифікацією за токеном, де клієнт надсилає заголовок `Authorization`, не вразливі до CSRF, бо браузер не додає цей заголовок автоматично до міжсайтових запитів. У [Захист від підроблення запитів / CSRF](#anti-forgery-csrf) у Розділ 12 тему розглянуто повністю.

**Rate limiting запитів** (вбудоване від .NET 7) захищає від зловживань і раптових сплесків навантаження. Коли відхиляти запит — на межі чи в застосунку — і що повертати, розглянуто в [Rate limiting й тайм-аути на межі](#rate-limiting-and-timeouts-at-the-edge) у Розділ 26. Алгоритми: фіксоване вікно, ковзне вікно, кошик токенів і обмеження паралельності:

```csharp
builder.Services.AddRateLimiter(o =>
    o.AddFixedWindowLimiter("api", opt =>
    {
        opt.PermitLimit = 100;
        opt.Window = TimeSpan.FromMinutes(1);
        opt.QueueLimit = 0;
    }));
app.UseRateLimiter();
```

**Кешування виводу** зберігає на сервері *сформовану відповідь* і повертає її для відповідних запитів — чудово підходить для дорогих `GET`-запитів, дані яких рідко змінюються. Це не те саме, що *кешування відповідей*, яке задає HTTP-заголовки кешу й покладається на клієнтів і проксі ([CDN і заголовки кешування](#cdns-and-caching-headers) у Розділ 26).

**Стискання відповіді** (Brotli/Gzip) зменшує розмір даних. Якщо зворотний проксі (nginx, YARP) уже стискає їх, повторне стискання в застосунку марнує процесорний час — враховуйте топологію.

## REST і OpenAPI

**REST** — набір обмежень, а не закон, але кілька принципів приносять користь: моделюйте API навколо **ресурсів** (іменників), а не дій; використовуйте **методи** HTTP за призначенням (GET — читання, POST — створення, `PUT` — заміна, PATCH — часткове оновлення, `DELETE` — видалення) із гарантованими властивостями безпеки й ідемпотентності ([Методи HTTP та ідемпотентність](#http-methods-and-idempotency)); результат повідомляйте **кодом стану** ([Важливі коди стану й заголовки](#status-codes-and-headers-that-matter)).

**OpenAPI/Swagger** описує API у машиночитаному контракті. Сучасний .NET має вбудоване створення документів OpenAPI (`AddOpenApi` / `MapOpenApi`); Swagger UI або Scalar відображає їх людям. Детальні метадані (`WithName`, `Produces`, коментарі XML, `TypedResults`) роблять специфікацію й створені на її основі SDK клієнтів точними. У [Розділ 6](#chapter-6-frontend-essentials) з неї генерується клієнт TypeScript.

Коли клієнти залежать від цього контракту, безпечне його змінення стає окремою дисципліною: що вважати несумісною зміною, як версіонувати API й уникати потреби в новій версії — у розділі [Версіонування API й зворотна сумісність](#api-versioning-backward-compatibility) у Розділ 22.

## Health check

Оркестраторам (Kubernetes, балансувальникам навантаження) треба знати, чи застосунок працює й чи готовий приймати трафік. ASP.NET Core розрізняє два запитання:

- **Живучість** — «процес справний чи його треба перезапустити?». Перевірка не має залежати від зовнішніх систем: збій бази даних не повинен створювати цикл перезапусків.
- **Готовність** — «чи може цей екземпляр обробляти трафік саме зараз?». Тут перевіряються залежності (БД, message broker (брокер повідомлень)), щоб неготовий екземпляр прибрати з обслуговування, але не завершувати.

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddNpgSql(connString, tags: ["ready"]);

app.MapHealthChecks("/health/live",
    new() { Predicate = c => c.Tags.Contains("live") });
app.MapHealthChecks("/health/ready",
    new() { Predicate = c => c.Tags.Contains("ready") });
```

Позначення перевірок тегами й відбір за тегом чітко розділяють живучість і готовність.

Під капотом працюють три компоненти, без жодної магії. Кожна перевірка — це `IHealthCheck`, один метод якого повертає результат; `AddCheck`/`AddNpgSql` лише реєструють реалізації в DI (пакети спільноти `AspNetCore.HealthChecks.*` постачають готові перевірки майже для будь-якої залежності). Коли надійшов запит перевірки, `HealthCheckService` паралельно запускає кожну зареєстровану перевірку, теги якої відповідають `Predicate`; кожній передається CancellationToken. Потім endpoint об’єднує результати: **перемагає найгірший окремий стан**, який відображається в HTTP — `Healthy` і `Degraded` повертають `200`, `Unhealthy` — `503`.

Третій стан часто забувають. **`Degraded`** означає «працює, але не дуже добре»: затримка репліки, повільна залежність, зростання queue. Оскільки повертається `200`, оркестратор не завершує й не вилучає екземпляр; це сигнал для панелей і сповіщень, жовте світло між зеленим і червоним. Власна перевірка — це проста реалізація інтерфейсу:

```csharp
public class QueueBacklogHealthCheck(IQueueClient queue) : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext ctx, CancellationToken ct)
    {
        var depth = await queue.GetDepthAsync(ct);
        return depth switch
        {
            < 1_000  => HealthCheckResult.Healthy(),
            < 10_000 => HealthCheckResult.Degraded($"Backlog: {depth}"),
            _        => HealthCheckResult.Unhealthy($"Backlog: {depth}")
        };
    }
}
// builder.Services.AddHealthChecks()
//     .AddCheck<QueueBacklogHealthCheck>("queue-backlog", tags: ["ready"]);
```

Типово тіло endpoint — звичайний текст із загальним станом (`Healthy`). Щоб отримати JSON для кожної перевірки — яка саме не пройшла, чому й скільки тривала — додайте `ResponseWriter` (пакет `HealthChecks.UI.Client` містить готовий варіант). Для моніторингу через публікацію `IHealthCheckPublisher` змінює напрямок: застосунок запускає перевірки за таймером і надсилає результати до телеметрії, а не чекає на запити перевірки.

> **Пастка.** Ці endpoints опитуються кожні кілька секунд на кожному екземплярі. Дорога перевірка готовності — повне сканування таблиці чи некешований зовнішній виклик — тепер виконується з частотою «опитування × кількість серверів» і сама може перевантажити нестабільну залежність. Залишайте перевірки дешевими, обмежуйте їх тайм-аутом і кешуйте результат дорогих. Не включайте зовнішні залежності до перевірки живучості: у [Проби працездатності: живучість, готовність, запуск](#health-probes-liveness-readiness-startup) у Розділ 26 пояснено, як інакше збій бази даних спричинить перезапуски всього кластера.

## Підсумок

Мережа під HTTP складається з рівнів, кожен із яких може зламатися незалежно; перш ніж налагоджувати, визначте потрібний. HTTP поверх неї — це протокол без стану із запитами й відповідями, а методи та коди стану є інструкціями для механізмів: політики повторів, кеші, проксі й браузери реагують на них без читання тіла. Відкривати з’єднання дорого, тому їх зберігають у пулі; новий `HttpClient` на кожен виклик руйнує повторне використання, а IHttpClientFactory або єдиний клієнт із ротацією з’єднань зберігає його.

ASP.NET Core — це **pipeline компонентів**, складений під час запуску, через який запит проходить у порядку реєстрації. Кожен middleware бачить лише результат попередніх, а endpoint з фільтрами, прив’язуванням і перевіркою моделі — найглибший рівень. Перевіряйте дані на межі, щоб повертати доречний `400`, а коректність забезпечуйте в домені й базі даних; передавайте токен скасування далі, повторюйте лише ідемпотентне й повертайте код стану, що відповідає результату.

## Перевірте на практиці

Дві програми — по одній для кожного кінця з’єднання. Перш ніж запускати їх, передбачте виведення.

**1. Новий HttpClient для кожного запиту щоразу залишає сокет.**

`verify/path/HttpClientPerRequest/Program.cs` · запустіть із `verify/path` командою `dotnet run --project HttpClientPerRequest`:

```csharp
using System.Net.NetworkInformation;

// Prove it: a new HttpClient per request opens (and closes) one TCP connection per request, and
// every closed connection then sits in TIME_WAIT. A shared client reuses its pooled connections.
int port = Random.Shared.Next(20_000, 30_000);     // a fresh port, so earlier runs don't count
var builder = WebApplication.CreateSlimBuilder();
builder.Logging.ClearProviders();
builder.WebHost.UseUrls($"http://127.0.0.1:{port}");
var server = builder.Build();
server.MapGet("/", () => "ok");
await server.StartAsync();

var shared = new HttpClient();
await Measure("one shared HttpClient", () => shared.GetStringAsync($"http://127.0.0.1:{port}/"));
await Measure("new HttpClient per request", async () =>
{
    using var perRequest = new HttpClient();
    return await perRequest.GetStringAsync($"http://127.0.0.1:{port}/");
});

async Task Measure(string label, Func<Task<string>> call)
{
    int before = SocketsInTimeWait();
    for (int i = 0; i < 500; i++) await call();
    Console.WriteLine($"{label,-27} 500 requests, new sockets in TIME_WAIT: {SocketsInTimeWait() - before}");
}

int SocketsInTimeWait() => IPGlobalProperties.GetIPGlobalProperties().GetActiveTcpConnections()
    .Count(c => c.State == TcpState.TimeWait && c.RemoteEndPoint.Port == port);
```

```text
one shared HttpClient       500 requests, new sockets in TIME_WAIT: 0
new HttpClient per request  500 requests, new sockets in TIME_WAIT: 500
```

Зверніть увагу:

- **Спільний клієнт: жодного нового сокета.** Усі 500 запитів використовували те саме з’єднання з пулу.
- **Клієнт на кожен запит: 500 сокетів у `TIME_WAIT`.** Кожен клієнт відкрив з’єднання й закрив його під час `Dispose`. Сторона, що закрила з’єднання, утримує сокет і локальний порт у `TIME_WAIT` протягом 60 секунд у Linux.
- **За швидкості продакшену порти закінчуються.** Нові порти доступні лише після завершення `TIME_WAIT`, що обмежує кількість нових з’єднань на секунду до одного адресата. В App Service обмеження набагато нижче: 128 портів SNAT на екземпляр і адресата, кожен звільняється через чотири хвилини після закриття з’єднання. Набір тестів ніколи не досягає цього рівня; піковий трафік — досягає.
**2. Singleton, що залежить від scoped-сервісу, зберігає один його екземпляр.** Час життя служб і залежність-полонений описані в розділі [Dependency injection (впровадження залежностей)](#dependency-injection) у Розділ 3; ось як помилка виглядає в API. Програма реєструє scoped `AppDb` і singleton `PriceCache`, який його отримує, а потім розв’язує їх у двох областях запиту й повторює операцію з перевіркою області. Перед запуском передбачте три рядки.

`verify/path/CaptiveDependency/Program.cs` · запустіть із `verify/path` командою `dotnet run --project CaptiveDependency`:

```csharp
// Prove it: a singleton that takes a scoped service keeps ONE instance of it for every scope; ValidateScopes refuses it.
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection()
    .AddScoped<AppDb>()                    // one per request, like a DbContext
    .AddSingleton<PriceCache>();           // one per process, and it asks for an AppDb

using (var root = services.BuildServiceProvider())     // ValidateScopes = false: the default outside Development
{
    for (int request = 1; request <= 2; request++)
    {
        using var scope = root.CreateScope();          // ASP.NET Core opens one scope per request
        AppDb own = scope.ServiceProvider.GetRequiredService<AppDb>();
        AppDb captured = scope.ServiceProvider.GetRequiredService<PriceCache>().Db;
        Console.WriteLine($"request {request}: its own AppDb #{own.Id}, the singleton's AppDb #{captured.Id}");
    }
}

using (var root = services.BuildServiceProvider(new ServiceProviderOptions { ValidateScopes = true }))
using (var scope = root.CreateScope())
{
    try { scope.ServiceProvider.GetRequiredService<PriceCache>(); }
    catch (InvalidOperationException e) { Console.WriteLine($"ValidateScopes = true: {e.GetType().Name}: {e.Message}"); }
}

sealed class AppDb { private static int s_created; public int Id { get; } = ++s_created; }
sealed class PriceCache(AppDb db) { public AppDb Db { get; } = db; }
```

```text
request 1: its own AppDb #1, the singleton's AppDb #2
request 2: its own AppDb #3, the singleton's AppDb #2
ValidateScopes = true: InvalidOperationException: Cannot consume scoped service 'AppDb' from singleton 'PriceCache'.
```

Зверніть увагу:

- **В обох запитах — №2.** Кожна область отримала власний `AppDb` (спершу №1, потім №3), а singleton використовує №2 в обох. Для справжнього `DbContext` це був би один контекст на всі запити й потоки.
- **№2 не належить жодному запиту.** Він створений разом із singleton у кореневій області (у вихідному коді runtime (середовище виконання) називає scoped-службу «підвищеною до singleton»), тому жодна область запиту його не звільнила.
- **Ті самі реєстрації, лише одна відмінність у параметрах.** З увімкненим `ValidateScopes` отримання singleton викидає exception. `WebApplicationBuilder` вмикає його разом із `ValidateOnBuild` лише в Development, де `builder.Build()` завершується помилкою, обгорнутою в `AggregateException`, ще до першого запиту. У Production перевірки немає, і помилка потрапляє в реліз.

## Перевірте на роботі

**Перевірте код.** Знайдіть у службі `new HttpClient(`: кожне використання на шляху запиту чи повідомлення створює витік сокетів, який проявиться під час пікового навантаження. Перегляньте singleton-и: реєстрації `AddSingleton`, розміщені служби й middleware, створювані за домовленістю. Перевірте конструктори на scoped-залежності: `DbContext`, репозиторій та все, що зареєстровано через `AddScoped` або `AddDbContext`. Запустіть службу з `ASPNETCORE_ENVIRONMENT=Development`: з `ValidateOnBuild` залежність-полонений зірве `Build()` до deployment. У `Program.cs` перевірте, що handler exceptions зареєстровано першим, автентифікація передує авторизації, а кожен клас options викликає `ValidateOnStart()`.

**Виміряйте.** Розбийте метрику `http.server.request.duration` (вбудовану в ASP.NET Core від .NET 8) за `http.route` і `http.response.status_code`. 5xx у endpoint, яка лише відхиляє неправильне введення, має бути 400. Якщо endpoint повертає тільки `200`, перевірте, чи не приховані помилки в тілі.

## Запитання для співбесіди

**Поясніть pipeline middleware.**
Компоненти middleware утворюють ланцюжок. Кожен отримує `HttpContext`, може обробити запит, викликати `next()` для передавання керування далі й обробити відповідь на зворотному шляху — як вкладені рівні. Порядок має значення: спершу exception handling, потім routing, автентифікація (до авторизації), а далі endpoints. Компонент може перервати pipeline, не викликаючи `next()`.

**Singleton отримав scoped `DbContext`. Що станеться в ASP.NET Core і чому помилку виявляють лише в Development?**
ASP.NET Core створює одну область DI на запит, тож scoped-сервіс має окремий екземпляр для кожного запиту. Singleton розв’язується один раз у кореневій області, отже захоплений ним DbContext не належить жодному запиту: усі запити й потоки спільно використовують його, і EF Core викидає *"A second operation was started on this context instance"* для двох одночасних запитів. `WebApplicationBuilder` вмикає `ValidateScopes` і `ValidateOnBuild` лише в Development, де `Build()` відмовляється від такої реєстрації. У Production перевірок немає, і помилка потрапляє в реліз. Часи життя розглянуто в [Розділі 3](#captive-dependencies-the-classic-di-bug).

**Тривожний сигнал:** «Зробімо все singleton, так швидше» — захоплений DbContext тоді перетікає між запитами; це помилка коректності, а не оптимізація.

**Як працює прив’язування моделі?**
ASP.NET Core зіставляє вхідні дані запиту — значення маршруту, рядок запиту, поля форми, тіло JSON і заголовки — з параметрами дій і властивостями моделі за назвою, а потім виконує перевірку атрибутами. Джерело можна вказати через `[FromBody]`, `[FromQuery]`, `[FromRoute]` тощо. Помилки прив’язування й перевірки заповнюють `ModelState`; із `[ApiController]` неправильний `ModelState` повертає 400 до виконання дії, а без нього перевірку виконуєте самі.

**Що таке фільтри й коли обрати їх замість middleware?**
Фільтри виконуються в pipeline MVC (авторизації, ресурсів, дій, exceptions і результату) й мають доступ до контексту MVC, зокрема дії та стану моделі. Використовуйте фільтр для наскрізної логіки, якій потрібен цей контекст: перевірка моделі, авторизація дії, формування результату. Middleware використовуйте для логіки всіх запитів незалежно від MVC: logging (журналювання), стискання, глобальна exception handling.

**Мінімальні API чи контролери?**
Мінімальні API — легкі оголошення endpoints із меншим обсягом шаблонного коду, вони добре підходять невеликим службам і мікросервісам. Контролери додають структуру: домовленості атрибутів, фільтри, можливості прив’язування й знайому організацію для великих застосунків. Вони мають спільні routing й DI; вибирайте за розміром команди та складністю застосунку, а не за швидкодією.

**JWT чи автентифікація за cookie?**
Cookie мають стан, ними керує браузер, і їх надсилають автоматично; їх легко відкликати на сервері. Це зручно для класичних вебзастосунків (але потрібен захист від CSRF). JWT — автономні токени пред’явника в заголовку `Authorization`: вони не зберігають стан і підходять API та автентифікації між службами, але їх важко відкликати до завершення строку дії. Тому задавайте короткий строк і використовуйте токени оновлення. Обидва варіанти розглянуто в [Розділі 12](#chapter-12-security-essentials).

**Тривожний сигнал:** «JWT безпечні, бо їхній вміст зашифровано» — це лише Base64-кодування й *підпис*; прочитати твердження може будь-хто.

**REST: які коди стану й ідемпотентність?**
200 OK, 201 Created (із `Location`), 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 500 Server Error. GET, PUT, DELETE ідемпотентні (повторення дає той самий стан), POST — ні. Це важливо для повторів: клієнти повторюють запит після мережевого збою, тому небезпечним неідемпотентним операціям потрібен idempotency key ([Розділ 20](#idempotency-keys-making-post-retry-safe)).

**Що таке CORS і чому він блокує запити?**
CORS — браузерний механізм безпеки: сторінка з джерела A не може викликати API з джерела B, якщо API явно не повертає заголовки з дозволом для джерела A. Його застосовує браузер, а не сервер: він захищає користувачів і тому JavaScript отримує помилку CORS, хоча `curl` працює. Налаштуйте дозволені джерела, методи й заголовки на сервері; не поєднуйте `AllowAnyOrigin` з credentials (облікові дані).

**Тривожний сигнал:** «CORS — це серверний захист, який не дає зловмисникам викликати API» — це захист браузера для користувачів; клієнт поза браузером повністю його обходить.
