# Розділ 6: Основи фронтенду

Щойно ваш API починає взаємодіяти з браузером, на вас чекають проблеми, які не можна перекласти на когось іншого: чому SPA працює локально, але ламається в продакшені; чому запит, «заблокований CORS», усе ж змінив базу даних; чому сторінка зависає, хоча endpoint (кінцева точка) відповідає за 40 мс; де зберігати токен входу. Більшість команд .NET постачають фронтенд на React або Angular разом зі своїм API, а на співбесідах кандидатам на бекенд ставлять запитання про фронтенд. Цей розділ дасть вам базу рівня junior+: достатню, щоб читати й змінювати SPA, налагоджувати її в DevTools браузера, відповідати на типові запитання, розуміючи механізм роботи, і спроєктувати межу API так, щоб команда фронтенду могла швидко працювати.

Розділ простежує шлях сторінки: як браузер перетворює HTML, CSS і JavaScript на пікселі; кожна мова окремо, з JavaScript саме в тому аспекті, який перевіряють на співбесідах; DOM і events (події); TypeScript очима розробника на C#. Далі розглянуто те, за що відповідаєте ви: `fetch`, CORS, cookie, типізовані клієнти; механізм React і відмінності Angular; routing (маршрутизацію) та форми; доступність; інструментарій npm і Vite; XSS і показники Core Web Vitals, що вимірюють результат.

Усі приклади JavaScript і TypeScript тут виконуються: тести репозиторію запускають їх у `verify/frontend/` (із зафіксованими версіями TypeScript, React і Angular, Vitest та jsdom). Стратегії рендерингу, поглиблений розгляд продуктивності й тестування, Content Security Policy та автентифікацію SPA описано в [Розділі 34: Фронтенд і повний стек поглиблено](#chapter-34-frontend-and-full-stack-in-depth).

## Веб, який бачить браузер

У кожному браузері працюють три мови, і кожна має своє призначення.

**HTML** задає структуру документа: дерево вкладених елементів (`<header>`, `<article>`, `<button>`). **CSS** відповідає за вигляд: селектори знаходять елементи й застосовують правила стилів (`color`, `display: flex`, `grid-template-columns`). **JavaScript** задає поведінку: виконує код, реагує на введення користувача й змінює сторінку.

Коли браузер розбирає HTML, він будує **DOM** (Document Object Model) — дерево об’єктів у пам’яті, що представляє документ. JavaScript не редагує текст HTML, а змінює це живе дерево:

```javascript
const btn = document.querySelector("#save");
btn.addEventListener("click", () => {
  document.querySelector("#status").textContent = "Saving...";
});
```

Зрештою кожна видима зміна вебсторінки є зміною DOM; React, Angular і Blazor — це механізми, які визначають, *які саме* зміни потрібно внести.

### Від байтів до пікселів: pipeline рендерингу

Браузер перетворює відповідь на пікселі в чіткій послідовності, і більшість проблем «сторінка повільна» виникають через те, що один етап чекає на інший.

```text
 HTML ──► DOM ───┐
                 ├──► render tree ──► layout ──► paint ──► composite
 CSS ───► CSSOM ─┘
 <script>: may pause the HTML parser; runs on the same main thread as all of it
```

1. **HTML → DOM** — поступово, у міру надходження байтів. *Сканер попереднього завантаження* читає документ наперед і починає завантажувати знайдені таблиці стилів, скрипти й зображення.
2. **CSS → CSSOM** — не поступово: пізніше правило може перевизначити попереднє, тому стилізувати елементи можна лише після отримання всього CSS. **CSS блокує рендеринг.**
3. **Дерево рендерингу**: DOM разом із CSSOM, але лише видимі елементи (`display: none` не потрапляє до дерева, а `visibility: hidden` усе ще займає місце).
4. **Розкладка** (*reflow*) обчислює розмір і положення кожного блока; зміна розміру одного елемента може зсунути всі наступні.
5. **Малювання** заповнює пікселями кожен шар, а **компонування** накладає шари на екрані. Зміни `transform` і `opacity` часто можна одразу передати на етап компонування, тому в плавних анімаціях використовують саме їх.

**Що що блокує.** Звичайний `<script src>` **блокує парсер**: браузер припиняє будувати DOM, завантажує й виконує скрипт, а потім продовжує, адже скрипт може читати або змінювати вже побудовану частину DOM. Скрипт також може запитувати обчислені стилі, тож перед його виконанням браузер дочекається CSS. CSS блокує скрипти, а скрипти блокують розбір HTML:

```html
<script src="/legacy-widget.js"></script>          <!-- blocks parsing until run -->
<script defer src="/app.js"></script>               <!-- runs after parsing, in order -->
<script async src="/analytics.js"></script>         <!-- runs on arrival, any order -->
<script type="module" src="/assets/index-4f9a1c.js"></script>  <!-- deferred by default -->
```

Скрипти з `defer` запускаються після розбору HTML у порядку документа й до events `DOMContentLoaded`; скрипти з `async` — щойно завантажаться. Для коду застосунку використовуйте `defer` (або модульний скрипт, який генерує Vite), для незалежних скриптів на кшталт аналітики — `async`, а звичайний `<script>` у `<head>` майже ніколи не потрібен.

**Після першого малювання pipeline (конвеєр) запускається знову після кожної зміни**, але зміни групуються: десять послідовних записів у DOM потребують лише однієї розкладки перед наступним кадром. Дорогий шаблон — чергувати записи з читанням значень розкладки:

```javascript
for (const row of rows) {
  row.style.width = container.offsetWidth + "px";   // read forces layout, write invalidates it
}
```

Кожне читання `offsetWidth` після запису примусово запускає *синхронну* розкладку, тож для 500 рядків виконається 500 розкладок — це **надмірне перерахування розкладки**. Прочитайте значення один раз перед циклом, а потім виконуйте записи.

> **Зверніть увагу.** **Чому сторінка може бути «завантажена», але залишатися порожньою або завислою.** Усе це, як і весь JavaScript, працює в **одному головному потоці**: поки виконується скрипт, нічого не розбирається, не розкладається, не малюється й не реагує на натискання. Таблиця стилів, що блокує рендеринг і повільно завантажується з CDN, залишить екран порожнім, якою б швидкою не була ваша API; цикл тривалістю 300 мс змусить кожне натискання в цей проміжок чекати 300 мс. Вихід — прибрати роботу з критичного шляху (`defer`, менше CSS, поділ пакетів) і розбивати тривалі завдання на частини.

### SPA порівняно з класичною моделлю запит/відповідь

**Традиційний вебзастосунок** (Razor Pages, MVC) генерує повний HTML на сервері після кожного переходу, а браузер запускає весь pipeline для кожної нової сторінки. **Односторінковий застосунок (SPA)** завантажується один раз, а потім сам керує навігацією: JavaScript перехоплює натискання, отримує JSON від API й повторно рендерить частини DOM. Найпоширеніші рішення — React, Angular і Vue. Перевага — плавність, як у застосунку; ціна — складність, великий обсяг JavaScript, який має виконатися, перш ніж користувач щось побачить, і складніша SEO-оптимізація. Проміжними підходами є серверний рендеринг, статична генерація й гідрація ([Розділ 34](#chapter-34-frontend-and-full-stack-in-depth)).

## HTML: структура, семантика й форми

Вибраний вами елемент визначає, що браузер зробить автоматично: керування фокусом із клавіатури, надсилання форми, оголошення для програм читання з екрана, індексацію пошуковими системами.

### Семантичні елементи визначають поведінку

**Семантичний** елемент описує, *чим є* його вміст, а не те, який він має вигляд:

- **Орієнтири** (`<header>`, `<nav>`, `<main>`, `<aside>`, `<footer>`): користувачі програм читання з екрана переходять між ними так само, як ви переглядаєте сторінку.
- **Заголовки** `<h1>`–`<h6>` формують структуру; вибирайте рівень за нею, а не за розміром шрифту.
- **`<button>` і `<a>`**: посилання *кудись веде* (має `href`, відкриває нову вкладку чи змінює URL), кнопка *виконує дію*. `<div>` з handler (обробником) натискання не є ні тим, ні іншим: він не отримує фокус, не реагує на Enter і оголошується як звичайний текст.
- **`<ul>`/`<ol>`** для списків, **`<table>`** із `<th>` лише для табличних даних, **`<label>`/`<fieldset>`/`<legend>`** для пов’язування тексту з елементами форми.

Якщо все зроблено через `<div>`, структуру втрачено.

### Як працює форма без JavaScript

`<form>` уже є повноцінним клієнтом для вашої API. Його поведінка пояснює і помилки, успадковані SPA, і прив’язування моделі на сервері ([Розділ 5: Прив’язування та перевірка моделі](#model-binding-validation)).

```html
<form id="signup" action="/api/signup" method="post">
  <label for="email">Email</label>
  <input id="email" name="email" type="email" required autocomplete="email">

  <button>Sign up</button>
  <output></output>
</form>
```

Коли користувач надсилає форму, браузер:

1. **Перевіряє** обмеження розмітки (`required`, `type="email"`, `min`/`max`, `pattern`). Якщо якесь не виконано, показує повідомлення, переводить фокус на поле, і event `submit` не спрацьовує.
2. **Збирає** всі активні елементи керування з атрибутом **`name`**. Поле без `name` непомітно пропускається під час надсилання — зазвичай саме тому «поле завжди має значення null» у дії з прив’язаною моделлю.
3. **Кодує** їх: у рядок запиту для `get`, як `application/x-www-form-urlencoded` для `post` або як `multipart/form-data` (потрібно для файлів).
4. **Переходить**: надсилає запит і замінює сторінку відповіддю.

> **Нюанс.** **`<button>` усередині форми надсилає її, якщо не вказано інше.** Типове значення `type` — `submit`, тож кнопка «Додати рядок», записана як `<button>Add line</button>`, надсилає форму; у SPA це означає повне перезавантаження сторінки й втрату стану. Для кожної кнопки, яка не має надсилати форму, задавайте `type="button"`.

SPA залишає кроки 1–3, але замінює крок 4: скасовує навігацію через `preventDefault()`, формує тіло запиту за допомогою `FormData` і надсилає його через `fetch`:

```javascript
const form = document.querySelector("#signup");

form.addEventListener("submit", async (event) => {
  event.preventDefault();                  // stop the browser's own full-page POST
  const body = new FormData(form);         // every field with a name attribute
  const res = await fetch(form.action, { method: "POST", body });
  form.querySelector("output").textContent = res.ok ? "Saved" : `Failed: ${res.status}`;
});
```

Не встановлюйте `Content-Type` самостійно для тіла `FormData`: браузер задає `multipart/form-data` *із межею* між частинами, а без неї сервер не зможе розібрати заголовок. Вбудована перевірка — це зручність, а не захист; сервер усе одно перевіряє дані повторно.

## CSS: блокова модель, каскад і компонування

На співбесіді можуть запитати, чому елемент ширший за заданий `width`, чому стиль «не застосовується» і як розмістити два елементи поруч. Відповідь дають блокова модель, каскад і режими компонування.

### Блокова модель

Кожен елемент відображається як прямокутний блок із чотирьох шарів, від центру назовні: **вміст**, **внутрішній відступ** (усередині рамки, має той самий фон), **рамка** та **зовнішній відступ** (прозорий простір за рамкою).

Типово (`box-sizing: content-box`) `width` задає лише ширину *вмісту*: за значень `width: 200px; padding: 16px; border: 1px solid` елемент на екрані матиме ширину 234 пікселі. Тому на початку майже кожної таблиці стилів є скидання, після якого `width` включає внутрішній відступ і рамку:

```css
*, *::before, *::after { box-sizing: border-box; }
```

**Вертикальні зовнішні відступи схлопуються**: між двома блоками проміжок дорівнює більшому відступу, а не їх сумі. **`display`** визначає участь блока в компонуванні: `block` займає всю ширину й розташовується в окремому рядку, `inline` вписується в рядок тексту й ігнорує `width`/`height`, а `flex` і `grid` перетворюють елемент на контейнер компонування.

### Каскад і специфічність

Часто кілька правил задають ту саму властивість для одного елемента. **Каскад** — це алгоритм вибору правила-переможця; він порівнює правила в такому порядку:

1. **Походження та важливість.** Стилі браузера поступаються вашим таблицям стилів; оголошення з `!important` перемагає звичайні (і змінює порядок пріоритету походження).
2. **Шари каскаду.** Правила в блоках `@layer` поступаються правилам поза шарами, а пізніші шари перемагають раніші незалежно від селекторів. Завдяки цьому базові стилі дизайн-системи легко перевизначати.
3. **Специфічність** селектора, описана нижче.
4. **Порядок появи.** Якщо все інше однакове, перемагає правило, розташоване останнім.

**Специфічність** — це оцінка з трьох чисел, яку порівнюють зліва направо, як номер версії: кількість **ідентифікаторів**, кількість **класів, атрибутних селекторів і псевдокласів**, кількість **типів елементів і псевдоелементів**.

| Селектор | Оцінка | Примітки |
|---|---|---|
| `p` | (0, 0, 1) | один тип |
| `.price` | (0, 1, 0) | один клас переважає будь-яку кількість типів |
| `ul li.price:hover` | (0, 2, 2) | клас і псевдоклас, два типи |
| `#cart .price` | (1, 1, 0) | один ідентифікатор переважає будь-яку кількість класів |
| `style="color: red"` | переважає всі селектори | вбудований стиль не є селектором |

Причина «мій CSS не застосовується» майже завжди в тому, що десь є конкретніше правило; на панелі Styles у DevTools перелічено всі відповідні правила, а ті, що програли, перекреслено. Успадкування працює окремо: `color` і `font-*` передаються дочірнім елементам, `margin` і `width` — ні, а будь-яке правило, що безпосередньо збігається з елементом, має перевагу над успадкованим значенням.

> **Пастка.** Спроба перебити специфічність за допомогою `!important` або довших селекторів лише загострює боротьбу. Саме ця проблема разом із єдиним глобальним простором імен CSS спонукає команди використовувати **ізольовані стилі**: CSS Modules і стилі компонентів Angular переписують назви класів, щоб правила не виходили за межі компонента; Tailwind використовує селектори лише з одним класом; у Blazor є ізоляція CSS. Перш ніж писати правило, з’ясуйте, який підхід використовує проєкт.

### Flexbox і Grid

**Flexbox** розміщує дочірні елементи вздовж **однієї осі**: `justify-content` вирівнює їх уздовж цієї осі, `align-items` — поперек, `gap` задає проміжки, а `flex: 1` для дочірнього елемента означає «зайняти решту простору». **Grid** розміщує елементи у **двох вимірах**: контейнер задає стовпці й рядки, одиниці `fr` позначають частки вільного простору, а `repeat(auto-fill, minmax(…))` створює стільки стовпців, скільки вміщується, без медіазапиту.

```css
.toolbar {                      /* flexbox: one row, items centred vertically */
  display: flex;
  align-items: center;
  gap: 8px;
}
.toolbar .search { flex: 1; }   /* the search box takes the leftover width */

.products {                     /* grid: as many 220px+ columns as fit */
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
  gap: 16px;
}
```

| Потрібно | Використовуйте |
|---|---|
| Елементи в рядку (панель інструментів, група кнопок, навігація) та їх вирівнювання | Flexbox |
| Каркас сторінки: заголовок, бічна панель, основна область, нижній колонтитул | Grid |
| Адаптивна сітка однакових карток | Grid із `auto-fill` / `minmax` |
| Відцентрувати один елемент у блоці | Будь-який: `display: grid; place-items: center` — найкоротший варіант |

**Адаптивний дизайн** спирається на тег `<meta name="viewport" content="width=device-width, initial-scale=1">` (без нього телефони зменшують сторінку для комп’ютера), одиниці `rem` і медіазапити з підходом mobile-first (`@media (min-width: 768px)` додає правила до макета для малих екранів).

## JavaScript у форматі запитань на співбесіді

Синтаксис JavaScript здається знайомим розробнику на C#, але під ним працює зовсім інший механізм: динамічна типізація, прототипи й один потік. Запитання на співбесідах якраз і перевіряють випадки, у яких інтуїція з C# підводить.

### Типи, перетворення та рівність

Є сім примітивних типів (`number`, `string`, `boolean`, `undefined`, `null`, `bigint`, `symbol`), а також об’єкти, до яких належать масиви й функції. `number` — це 64-бітне число з рухомою комою, як `double`, тому для грошей воно не підходить ([Розділ 15](#chapter-15-dates-money-and-strings)).

Типи мають значення, а не змінні; оператори **перетворюють** операнди до потрібного їм типу:

```javascript
console.log(1 + "2");            // "12": + with a string concatenates
console.log("3" * "4");          // 12: * converts both to numbers
console.log(0 == "");            // true: "" becomes 0
console.log(0 == "0");           // true: "0" becomes 0
console.log("" == "0");          // false: two strings
console.log(null == undefined);  // true: a special rule
console.log(null == 0);          // false
console.log(NaN === NaN);        // false: use Number.isNaN
console.log(typeof null);        // "object": a historic bug
```

`==` спочатку перетворює операнди до спільного типу за настільки заплутаними правилами, що рівність навіть не є транзитивною (`0 == ""` і `0 == "0"`, але `"" != "0"`). `===` нічого не перетворює. **Завжди використовуйте `===`**, за exception (винятком) поширеного випадку `x == null`, який повертає true лише для `null` і `undefined`. За обох операторів об’єкти порівнюються за посиланням, а перевизначити `Equals` не можна.

### Істинність значень і оператори для null

В умові будь-яке значення перетворюється на логічне; рівно вісім значень є **хибними**: `false`, `0`, `-0`, `0n`, `""`, `null`, `undefined`, `NaN`. Усе інше істинне, зокрема `"0"`, `[]` і `{}`. Тому `if (count)` стане помилкою, щойно `count` законно дорівнюватиме нулю, а `||` — пастка для значень за замовчуванням:

```javascript
const settings = { pageSize: 0, title: "" };

console.log(settings.pageSize || 20);  // 20: 0 is falsy, so || throws it away
console.log(settings.pageSize ?? 20);  // 0: ?? replaces only null and undefined
console.log(settings.title || "Untitled");  // "Untitled"
console.log(settings.owner?.name);     // undefined: ?. stops at the missing owner
```

`??` і `?.` працюють так само, як однойменні оператори в C#. Використовуйте `??`, якщо нуль або порожній рядок є допустимим значенням.

### Область видимості та замикання

Є два покоління оголошень змінних:

- **`var`** має **функціональну область видимості**: одна змінна на всю функцію, *піднята* на її початок, тому вона існує (зі значенням `undefined`) ще до рядка оголошення.
- **`let`** і **`const`** мають **блокову область видимості**, як локальні змінні C#, і спричиняють помилку, якщо звернутися до них до оголошення. `const` фіксує *прив’язування*, а не значення: до масиву `const` усе ще можна додавати елементи.

**Замикання** — це функція разом зі змінними, захопленими з області видимості, де її створили. Замикання захоплюють *змінні*, а не значення, через що `var` і `let` поводяться в циклі по-різному:

```javascript
const withVar = [];
for (var i = 0; i < 3; i++) withVar.push(() => i);
console.log(withVar.map((f) => f()));  // [3, 3, 3]: one i for the whole loop

const withLet = [];
for (let j = 0; j < 3; j++) withLet.push(() => j);
console.log(withLet.map((f) => f()));  // [0, 1, 2]: a fresh j per iteration
```

З `var` усі три функції використовують одну змінну `i`, значення якої під час виклику дорівнює 3; `let` створює окреме прив’язування для кожної ітерації. Така сама пастка була в C# із `foreach` до C# 5 ([Розділ 1: Замикання та пастка захоплення змінної](#closures-and-the-capture-trap)). Замикання дають змогу зберігати приватний стан і без класу: локальна змінна живе, доки її використовує функція, повернута з відповідної області видимості. Типово пишіть `const`, `let` — коли перевизначаєте значення, а `var` не використовуйте.

### Значення `this` визначає спосіб виклику

У JavaScript `this` — це неявний параметр, значення якого визначає **спосіб виклику функції**, а не місце її оголошення:

- **`obj.method()`**: `this` — це `obj`, об’єкт перед крапкою.
- **Звичайний виклик `fn()`**: у строгому режимі `undefined`; класи й модулі завжди працюють у цьому режимі.
- **`new Fn()`**: `this` — щойно створений об’єкт.
- **`fn.call(x)`, `fn.apply(x)`, `fn.bind(x)`**: `this` явно дорівнює `x`; `bind` повертає нову функцію, назавжди прив’язану до цього значення `this`.
- **Стрілкові функції** не мають власного `this`, а захоплюють його з зовнішньої області видимості.

```javascript
const cart = {
  items: 0,
  add() { this.items++; return this.items; },
  addLater() { return [1, 2].map(() => this.add()); },
};

console.log(cart.add());               // 1: called as cart.add(), so this is cart

const add = cart.add;                  // the function, detached from its object
try { add(); } catch (e) { console.log(e.constructor.name); }  // TypeError: this is undefined

console.log(cart.add.bind(cart)());    // 2: bind fixes this for good
console.log(cart.addLater());          // [3, 4]: arrow functions use the this of the code around them
```

Від’єднаний виклик — це типова помилка в реальному коді: передавання `this.handleClick` або `service.load` як callback (зворотного виклику) від’єднує метод від об’єкта, тож пізніше виникає помилка «cannot read properties of undefined». Обгорніть виклик у стрілкову функцію (`() => this.handleClick()`) або застосуйте `bind`.

### Прототипи та класи

Кожен об’єкт має приховане посилання на інший об’єкт — **прототип**; якщо властивість не знайдено в самому об’єкті, пошук триває в **ланцюжку прототипів**, аж доки її не буде знайдено або доки не досягнемо `null`. Саме таку структуру створює синтаксис `class`:

```javascript
class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} makes a sound`; }
}

const rex = new Animal("Rex");
console.log(typeof Animal);                                // "function": a class is a function
console.log(Object.getPrototypeOf(rex) === Animal.prototype);  // true
console.log(Object.hasOwn(rex, "name"), Object.hasOwn(rex, "speak"));  // true false

Animal.prototype.speak = function () { return `${this.name} was patched`; };
console.log(rex.speak());   // "Rex was patched": the lookup happens at call time, on the chain
```

`name` належить екземпляру, а `speak` зберігається один раз у `Animal.prototype` і є спільним для всіх екземплярів; `extends` з’єднує один прототип із наступним. Оскільки пошук динамічний, заміна методу в прототипі змінює поведінку всіх уже створених об’єктів; контракту `virtual`/`override` на етапі компіляції немає, а значення `this` у методі, як і раніше, визначає спосіб виклику. Приватність на рівні мови забезпечують поля `#private`.

### Promise та async/await

**Promise** — це аналог `Task` у JavaScript: спочатку стан *pending*, а потім він змінюється лише раз — на *fulfilled* зі значенням або *rejected* з помилкою. Функція `async` повертає promise, а `await` продовжує виконання зі значенням або викидає причину відхилення. Загальна модель така сама, як у [Розділі 4: Основи асинхронності](#chapter-4-async-essentials), але є відмінності:

- **Thread pool (пулу потоків) немає.** Кожне продовження виконується в одному головному потоці, коли до нього доходить queue (черга) циклу events (див. наступний розділ). Під час очікування `await` звільняє потік, але ніколи не переносить роботу процесора в інше місце.
- **Promise починає виконуватися одразу й не підтримує скасування.** Виклик функції `async` запускає роботу, як гарячий `Task`. Аналог `CancellationToken` — це `AbortController`; його `signal` передають у `fetch`.
- **`Promise.all` швидко завершується помилкою**: повертає відхилення за першої помилки, поки решта операцій продовжує непомітно виконуватися; натомість `Task.WhenAll` очікує на всі завдання. `Promise.allSettled` очікує на всі й повідомляє результат кожного.
- **Відхилення без handler** стає *необробленим відхиленням*: у браузері з’являється помилка в консолі, а Node типово аварійно завершує процес. Зазвичай причина в тому, що ніхто не очікував на promise.

Тут так само, як у C#, постає запитання про `await` у циклі:

```javascript
const delay = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

let start = Date.now();
await delay(100);
await delay(100);
console.log(Date.now() - start >= 200);   // true: the second wait starts after the first ends

start = Date.now();
await Promise.all([delay(100), delay(100)]);
console.log(Date.now() - start < 200);    // true: both waits run at the same time
```

Очікуйте послідовно лише тоді, коли виклик залежить від результату попереднього.

### Цикл events: завдання та мікрозавдання

Один потік, один call stack (стек викликів): усі events, що мають статися пізніше (таймер, відповідь, натискання), потрапляють у queue, а **цикл events** вибирає, що виконувати далі, із двох типів queues:

- **Завдання** (макрозавдання): виконання скрипту, callback `setTimeout`, натискання, повідомлення від worker.
- **Мікрозавдання**: callbacks promise (зокрема код після `await`), `queueMicrotask`.

Правило таке: **виконати одне завдання до кінця; потім виконати всі мікрозавдання, зокрема додані за цей час, доки queue не спорожніє; тоді, якщо настав час кадру, відрендерити його; після цього перейти до наступного завдання.**

```text
   ┌─► take ONE task ──► run to completion ──► drain ALL microtasks ──► render? ──┐
   └──────────────────────────────────────────────────────────────────────────────┘
```

Тому в цій програмі порядок виконання незмінний:

```javascript
console.log("1: sync");
setTimeout(() => console.log("6: timer (a task)"), 0);
Promise.resolve().then(() => console.log("4: then (a microtask)"));

async function save() {
  console.log("2: save() up to its first await");
  await null;
  console.log("5: rest of save() (a microtask)");
}
save();
console.log("3: sync, after save() returned");
```

Скрипт є одним завданням, тому спочатку виконуються 1, 2 і 3; рядок 2 показує, що функція `async` виконується синхронно до першого `await`, як і в C# ([Розділ 4: Що насправді робить `await`](#what-await-actually-does)). Потім виконуються мікрозавдання в порядку queue: 4, 5. Таймер — це завдання, тож він виконається останнім, навіть із затримкою 0.

> **Зверніть увагу.** **Чому «асинхронний» код усе одно заморожує сторінку.** `await` допомагає лише під час *очікування*. Поки JavaScript обчислює (сортує 50 000 рядків, розбирає величезну відповідь), натискання, введення й рендеринг чекають завершення поточного завдання та всіх його мікрозавдань; а оскільки цикл спорожнює всю queue мікрозавдань перед рендерингом, ланцюжок promise, який безперервно додає мікрозавдання, блокує рендеринг так само, як цикл `while`. Що робити: зменшити обсяг роботи на клієнті (зазвичай це ваше завдання — робити пагінацію на сервері); розбити тривалу роботу на частини, які передають керування через справжнє завдання (`await new Promise(r => setTimeout(r, 0))`); або перенести її у **Web Worker** — окремий потік без доступу до DOM.

Тут гонки мають інший вигляд: дві ділянки JavaScript не виконуються одночасно, тому немає часткових записів чи блокувань, але між двома `await` може виконатися будь-що. Гонка стосується *порядку виконання*, як у вправі наприкінці.

### Модулі

Сучасні файли JavaScript — це **модулі ES**: кожен має власну область видимості, працює в строгому режимі й обмінюється кодом через `export` і `import`. Статичні імпорти дають інструментам змогу побачити весь граф залежностей, тож пакувальник може вилучити невикористаний код (*tree-shaking*); виклик `import()` завантажує модуль за потреби й дає змогу розділяти код ([Розділ 34](#chapter-34-frontend-and-full-stack-in-depth)). `require()` у старішому коді Node належить до CommonJS — початкової системи модулів.

## DOM і events

API DOM дає JavaScript змогу читати сторінку й змінювати її. Фреймворки роблять це за вас, але для налагодження потрібно розуміти механізм, а на співбесідах особливо часто запитують про events.

### Читання та зміна дерева

`querySelector`/`querySelectorAll` знаходять елементи за CSS-селектором. `textContent` задає звичайний текст; `innerHTML` *розбирає* HTML — саме так може проникнути XSS ([XSS на фронтенді](#xss-from-the-front-end)). `classList` перемикає класи, залишаючи стилі в CSS, а `dataset.orderId` читає атрибут `data-order-id`.

### Спливання, перехоплення та делегування

Event проходить деревом у три фази: **перехоплення** — від window до цільового елемента; **ціль**; потім **спливання** — назад угору через усіх предків. `addEventListener` за замовчуванням слухає event під час спливання, а з параметром `{ capture: true }` — під час перехоплення. Отже, натискання кнопки в `<div>` запускає handlers перехоплення `<div>`, потім кнопки, а потім handlers спливання `<div>`. Два методи часто плутають: **`stopPropagation()`** зупиняє подальше проходження events, тоді як **`preventDefault()`** скасовує **типову дію** браузера (перехід за посиланням, надсилання форми), але не зупиняє спливання.

Спливання уможливлює **делегування events**: достатньо одного handler на контейнері, а `event.target` покаже, у якому рядку натиснули:

```javascript
// One listener on the list handles clicks on every row, including rows added later.
const list = document.querySelector("#orders");

list.addEventListener("click", (event) => {
  const button = event.target.closest("button[data-order-id]");
  if (!button || !list.contains(button)) return;   // a click elsewhere in the list
  cancelOrder(Number(button.dataset.orderId));
});
```

`event.target` може вказувати на піктограму *всередині* кнопки, тому `closest()` піднімається деревом до неї (`currentTarget` — це елемент, на якому зареєстровано handler). Один handler замінює тисячі, а нові рядки одразу працюють. React використовує той самий механізм: один раз слухає events на кореневому елементі застосунку й передає їх вашим handlers.

## TypeScript для розробників на C#

**TypeScript** — це JavaScript зі статичною системою типів, яка додається під час компіляції. Компілятор перевіряє типи, а потім **стирає** їх: у браузері виконується звичайний JavaScript. Багато що здаватиметься знайомим, але є відмінності, через які легко припуститися помилки.

### Структурна типізація

C# використовує **номінальну типізацію**: тип відповідає інтерфейсу, лише якщо явно його реалізує. TypeScript використовує **структурну типізацію**: значення відповідає типу, якщо має потрібну *структуру*.

```typescript
interface Point { x: number; y: number }

function distanceFromOrigin(p: Point): number {
  return Math.hypot(p.x, p.y);
}

const pin = { x: 3, y: 4, label: "Warehouse" };
console.log(distanceFromOrigin(pin));   // 5: pin has x and y, so it is a Point; no "implements"

class Pixel { constructor(public x: number, public y: number) {} }
console.log(distanceFromOrigin(new Pixel(6, 8)));   // 10: a class that never heard of Point
```

Додаткові властивості допустимі в уже створеному об’єкті, але для **літерала** об’єкта, записаного там, де очікується тип, виконується *перевірка зайвих властивостей*: `const p: Point = { x: 1, y: 2, label: "A" }` спричинить помилку, адже невикористана властивість, імовірно, є опискою. Водночас `OrderId` і `CustomerId`, якщо обидва мають тип `string`, взаємозамінні.

### Об’єднання типів і звуження

**Об’єднаний тип** `A | B` означає одне або інше значення; перш ніж використовувати специфічні властивості, потрібно довести компілятору, який саме тип маємо: виконати **звуження** через `typeof`, `in`, `instanceof` або спільне поле з літеральним значенням. Поширений шаблон — **дискриміноване об’єднання**:

```typescript
type Order = { id: number; total: number };

type LoadResult =
  | { kind: "ok"; order: Order }
  | { kind: "not-found" }
  | { kind: "error"; status: number };

function describe(result: LoadResult): string {
  switch (result.kind) {
    case "ok":
      return `Order ${result.order.id}: ${result.order.total}`;  // narrowed: order exists here
    case "not-found":
      return "No such order";
    case "error":
      return `Failed with ${result.status}`;
    default: {
      const unreachable: never = result;   // a new case that is not handled stops the build here
      return unreachable;
    }
  }
}

console.log(describe({ kind: "ok", order: { id: 7, total: 30 } }));  // "Order 7: 30"
console.log(describe({ kind: "error", status: 503 }));               // "Failed with 503"
```

Це зіставлення зі зразком у C# для закритого набору записів, доповнене рядком із `never`, завдяки якому забутий четвертий варіант `kind` спричинить помилку компіляції. У режимі `strict` тип включає `null` лише тоді, коли це зазначено в об’єднанні (`string | null`); це аналог типів посилань, що допускають null, у C#, але тут порушення завершується помилкою.

### Узагальнення

Узагальнення подібні до C# і працюють схоже, а обмеження задають через `extends`. Разом із `keyof` (об’єднанням назв властивостей типу) вони дають змогу виражати зв’язки, яких у C# немає:

```typescript
function firstBy<T, K extends keyof T>(items: T[], key: K, value: T[K]): T | undefined {
  return items.find((item) => item[key] === value);
}

const users = [{ id: 1, email: "a@example.com" }, { id: 2, email: "b@example.com" }];
console.log(firstBy(users, "email", "b@example.com")?.id);   // 2
// firstBy(users, "emial", "x")  -> compile error: "emial" is not a key of the user type
// firstBy(users, "id", "2")     -> compile error: id is a number
```

`T[K]` означає «тип властивості `K` типу `T`». На цьому побудовано **допоміжні типи**: `Partial<T>` (тіло PATCH-запиту), `Pick`, `Omit`, `Record<string, number>`. Узагальнення стираються: під час виконання `typeof(T)` не існує.

### Межі TypeScript: типи стираються

Оскільки типи зникають, ніщо не перевіряє, чи відповідають їм дані, що надходять під час виконання (тіло `fetch`, `JSON.parse`, `localStorage`):

```typescript
type Order = { id: number; total: number };

const fromServer = JSON.parse('{"id": "42", "total": "19.90"}');   // type: any
const order = fromServer as Order;   // a promise to the compiler, checked by nobody

console.log(typeof order.id);        // "string": the type said number
console.log(order.total + 1);        // "19.901": string concatenation, no error anywhere

function isOrder(value: unknown): value is Order {   // a runtime check the compiler trusts
  return typeof value === "object" && value !== null
    && typeof (value as Order).id === "number"
    && typeof (value as Order).total === "number";
}
console.log(isOrder(fromServer));    // false
```

`as` — це не приведення типу в C#: воно нічого не перетворює й не перевіряє. `any` вимикає перевірку типів; `unknown` — безпечний відповідник, який потрібно звузити. Функція, що повертає `value is Order`, є *захисником типу*: це перевірка під час виконання, якій довіряє компілятор. Перевіряйте дані на межі за допомогою бібліотеки схем (часто використовують Zod) або застосовуйте клієнт, згенерований із документа OpenAPI, щоб принаймні типи відповідали контракту.

| | C# | TypeScript |
|---|---|---|
| Сумісність | Номінальна: оголошене успадкування | Структурна: відповідність структури |
| Під час виконання | Типи існують (рефлексія, `is`, `typeof(T)`) | Типи стерто; виконується звичайний JavaScript |
| Приведення типу | Перевірене перетворення, помилка за невідповідності | `as`: неперевірене твердження |
| Закритий набір варіантів | Записи та зіставлення зі зразком | Дискриміновані об’єднання та `never` |
| Безпека щодо null | Типи посилань, що допускають null (попередження) | `strictNullChecks` (помилки) |
| Обхід перевірок | `dynamic` | `any` (краще `unknown`) |

## Взаємодія з API з браузера

Це межа, за яку відповідаєте ви: виклик `fetch`, правила браузера щодо походження, cookie та контракт, який гарантує consistency (узгодженість) обох сторін.

### fetch і один неочікуваний нюанс

Розгляньмо мінімальний endpoint API:

```csharp
app.MapGet("/api/orders/{id:int}", async (int id, IOrderService svc) =>
{
    var order = await svc.GetAsync(id);
    return order is null ? Results.NotFound() : Results.Ok(order);
});
```

та виклик SPA, який її використовує:

```typescript
type Order = { id: number; total: number };

async function loadOrder(id: number, signal?: AbortSignal): Promise<Order> {
  const res = await fetch(`/api/orders/${id}`, { credentials: "include", signal });
  if (!res.ok) throw new Error(`Order ${id} failed: ${res.status}`);  // fetch does not throw on 404 or 500
  return (await res.json()) as Order;
}
```

Найважливіші тут чотири моменти:

- **`fetch` повертає відхилення лише тоді, коли відповідь не надійшла** (мережа недоступна, запит скасовано або його відхилив CORS). `404` чи `500` означає *успішний* виклик fetch із `res.ok === false`; якщо пропустити перевірку, тіло ProblemDetails потрапить у застосунок як дані, як показано у вправі.
- **`credentials`**: `"same-origin"` (типове значення) надсилає cookie лише на власне походження сторінки, `"include"` — також між джерелами (якщо сервер дозволив це в CORS), `"omit"` — ніколи. Відносна URL-адреса визначається відносно походження сторінки, тому SPA, яку обслуговує хост API, узагалі не потребує CORS.
- **`signal`** приймає сигнал від `AbortController` — аналога `CancellationToken`; `AbortSignal.timeout(5000)` автоматично скасовує запит, оскільки у `fetch` немає тайм-ауту.
- **`res.json()` повертає `any`**, тому `as Order` — це неперевірене твердження, описане в розділі про TypeScript.

### Політика однакового походження та CORS очима браузера

**Походження** — це *(схема, хост, порт)*: `https://app.example.com` і `https://api.example.com` мають різні походження, як і `localhost:5173` та `localhost:5000`. **Політика однакового походження** не дозволяє скриптам одного походження *читати* відповіді іншого; інакше будь-яка сторінка могла б звертатися до вашого банку з вашими cookie й читати відповіді. Але вона не блокує *надсилання*: форми й зображення завжди могли це робити.

**CORS** дає серверу змогу повідомити браузеру, яким іншим джерелам дозволено читати його відповіді; налаштування ASP.NET Core розглянуто в [Розділі 5: HTTP і веб-API](#chapter-5-http-and-web-apis). Міждоменний `fetch` містить заголовок `Origin` і проходить одним із двох шляхів:

- **Простий запит** (`GET`, `HEAD` або `POST`, лише дозволені заголовки й тіло типу `text/plain`, `application/x-www-form-urlencoded` або `multipart/form-data`) **надсилається одразу**, адже такий запит можна було б надіслати звичайною формою. Якщо `Access-Control-Allow-Origin` не збігається, скрипт отримає помилку, але сервер уже виконав запит.
- **Будь-який інший запит** (`PUT`, `PATCH`, `DELETE`, заголовок `Authorization`, тіло JSON — більшість викликів SPA) проходить **попередню перевірку**: спершу надсилається запит `OPTIONS` із проханням дозволити операцію.

```text
OPTIONS /api/orders/42 HTTP/1.1                    ← preflight
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 600                        ← cache this answer for 600 s

PUT /api/orders/42 HTTP/1.1                         ← now the real request
Origin: https://app.example.com
```

Без `Access-Control-Max-Age` відповідь на попередню перевірку кешується на 5 секунд, а браузери обмежують максимальне значення. Запит із credentials (обліковими даними) також потребує `Access-Control-Allow-Credentials: true` і точної адреси походження — ніколи не `*`.

**У DevTools** консоль показує причину повідомлення «blocked by CORS policy», а на вкладці Network попередня перевірка відображається окремим рядком `OPTIONS`. Якщо попередня перевірка не пройшла (зазвичай middleware автентифікації повертає `401` на `OPTIONS` без credentials), справжній запит не надсилається; невдалий *простий* запит уже надіслано й виконано, приховано лише його відповідь. Тому CORS не є засобом безпеки: [Розділ 12: CORS не контролює доступ](#cors-is-not-access-control).

### Cookie та сеанси

**Cookie** дають серверу змогу зберегти дані в браузері, які автоматично надсилатимуться з кожним наступним запитом до цього домену. Сервер задає їх заголовком `Set-Cookie`:

```text
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

Ці атрибути критично важливі для безпеки:

- **HttpOnly**: JavaScript не може читати cookie (`document.cookie`), тож XSS-помилка не дасть змоги її викрасти.
- **Secure**: cookie надсилається лише через HTTPS.
- **SameSite** регулює запити з *іншого сайту*: `Strict` ніколи не надсилає cookie, `Lax` — лише під час переходу на верхньому рівні з безпечним методом (наприклад, за посиланням), що блокує типовий **CSRF** через надсилання форми; `None` (потребує `Secure`) надсилає її завжди. У деяких браузерах типове значення — `Lax`; задавайте його явно.

**Сайт — це не походження.** `SameSite` порівнює схему та реєстрований домен, тож `app.example.com` і `api.example.com` належать до одного сайту, але мають різні походження: cookie `Lax` *надсилається* з застосунку до API, тоді як читання відповіді й далі регулює CORS. Спільний реєстрований домен для SPA та API уможливлює автентифікацію через cookie.

**Сеанс** зберігає непрозорий ідентифікатор у cookie, а стан — у *спільному* сховищі на сервері (Redis, SQL), щоб запит користувача міг обробити будь-який екземпляр застосунку.

### Де зберігається стан браузера: cookie, localStorage і sessionStorage

| | Cookie | `localStorage` | `sessionStorage` |
|---|---|---|---|
| Надсилається серверу | Автоматично | Ні | Ні |
| Доступне будь-якому скрипту цього походження | Ні, якщо є `HttpOnly` | Так | Так |
| Тривалість зберігання | `Max-Age`/`Expires` або сеанс | До очищення | До закриття вкладки |
| Розмір | Кілька КБ на cookie | Приблизно 5 МіБ на походження | Приблизно 5 МіБ на походження |

Вебсховище — це синхронне сховище пар ключ-значення, де значеннями є **рядки**; тому об’єкти потрібно перетворювати на JSON перед збереженням і після читання:

```javascript
localStorage.setItem("cart", { items: 2 });
console.log(localStorage.getItem("cart"));   // "[object Object]": values are always strings

localStorage.setItem("cart", JSON.stringify({ items: 2 }));
console.log(JSON.parse(localStorage.getItem("cart")).items);   // 2
```

Для налаштувань і чернеток це цілком придатне сховище; для токена доступу — поганий вибір, бо одна XSS-помилка або скомпрометований пакет npm може прочитати його й надіслати будь-куди. Скрипт не може прочитати cookie з `HttpOnly`, але тоді потрібен захист від CSRF. Сучасні рекомендації радять узагалі не зберігати токени в браузері: для цього використовують шаблон **Backend-for-Frontend**, описаний у [Розділі 34](#chapter-34-frontend-and-full-stack-in-depth); потоки розглянуто в [Розділі 12: Потік коду авторизації з PKCE](#authorization-code-flow-with-pkce).

### Контракт під вашим контролем: OpenAPI і типізовані клієнти

Для швидкої роботи фронтенду ніщо не зрівняється з точним **документом OpenAPI** ([Розділ 5: REST і OpenAPI](#rest-and-openapi)) та клієнтом, *згенерованим* на його основі: написані вручну типи непомітно розходяться з контрактом, тоді як згенеровані спричиняють помилку *під час компіляції*:

```bash
# NSwag example: OpenAPI -> typed TS client
nswag openapi2tsclient /input:swagger.json /output:src/api-client.ts
```

Перейменуйте властивість, згенеруйте клієнт заново — і TypeScript позначить кожне місце, яке зламалося. Генеруйте його в CI, щоб клієнт ніколи не відставав від контракту (версіонування розглянуто в [Розділі 22](#api-versioning-backward-compatibility)).

## React: механізм роботи

Модель React достатньо проста, щоб зрозуміти її за механізмом: **інтерфейс — це функція стану**. Компонент отримує props і стан та *повертає опис* екрана. Коли стан змінюється, React викликає його знову, порівнює новий опис із попереднім (*узгодження*) і вносить лише необхідні зміни в DOM.

### Компоненти та props

Компонент — це функція, яка повертає **JSX** — синтаксичний цукор, що компілює `<OrderRow order={o} />` у виклик функції, яка створює звичайний об’єкт. **Props** — це вхідні параметри, доступні лише для читання. Дані передаються вниз через props, а зміни — вгору через callbacks:

```tsx
type Order = { id: number; customer: string; total: number };

type OrderRowProps = { order: Order; onCancel: (id: number) => void };

function OrderRow({ order, onCancel }: OrderRowProps) {
  return (
    <li>
      {order.customer}: {order.total.toFixed(2)}
      <button onClick={() => onCancel(order.id)}>Cancel</button>
    </li>
  );
}

function OrderList({ orders, onCancel }: { orders: Order[]; onCancel: (id: number) => void }) {
  if (orders.length === 0) return <p>No orders yet.</p>;
  return <ul>{orders.map((o) => <OrderRow key={o.id} order={o} onCancel={onCancel} />)}</ul>;
}
```

Умови задають звичайним `if`, списки — через `map`, а `{expression}` вставляє довільне значення. У термінах Blazor властивості `[Parameter]` — це props, а `EventCallback` — callback.

### Стан і повторний рендеринг

`useState` дає компоненту **стан**, який зберігається між викликами: значення та функцію-сетер. Сетер не змінює змінну в поточному коді, а просить React **виконати повторний рендеринг** — викликати компонент і його дочірні компоненти знову. Це недорого, бо DOM змінюється лише там, де відрізняється результат.

Кожен рендеринг бачить стан як **знімок**, незмінний упродовж цього рендерингу; це пояснює найпоширенішу помилку зі станом:

```tsx
import { useState } from "react";

function Quantity() {
  const [count, setCount] = useState(0);

  function addThreeWrong() {
    setCount(count + 1);   // count is 0 in this render: "set to 1"
    setCount(count + 1);   // "set to 1" again
    setCount(count + 1);   // the next render shows 1
  }

  function addThree() {
    setCount((c) => c + 1);   // updaters are queued and run in order
    setCount((c) => c + 1);
    setCount((c) => c + 1);   // the next render shows 3
  }

  return (
    <>
      <output>{count}</output>
      <button onClick={addThreeWrong}>+3 (wrong)</button>
      <button onClick={addThree}>+3</button>
    </>
  );
}
```

React **об’єднує** оновлення в handler events в один повторний рендеринг; якщо нове значення залежить від попереднього, передавайте функцію оновлення. Із цього механізму випливають ще два правила. **Рендеринг має бути чистим** (не можна отримувати дані, оформлювати підписки чи змінювати DOM у тілі компонента), адже React може викликати його будь-коли. А **стан замінюють, а не змінюють**: React порівнює старе й нове значення через `Object.is`, тож `items.push(x); setItems(items)` передає *той самий* масив, і оновлення пропускається. Пишіть `setItems([...items, x])`.

> **Зверніть увагу.** **Чому «я змінив стан, а змінна все ще має старе значення».** Сетер планує новий рендеринг, у якому `useState` поверне нове значення; `count` поточного рендерингу — стала, захоплена кожним замиканням, створеним під час нього. Виведіть її одразу після `setCount(5)` — побачите старе значення. Потрібне нове значення просто зараз? Це те, яке ви передали сетеру.

### Правила хуків

Функції, назви яких починаються з `use`, — це **хуки**. React зберігає список комірок хуків для кожного екземпляра компонента й зіставляє виклики з комірками **за порядком виклику**, а не за назвою. Звідси правила: викликайте хуки **лише на верхньому рівні** компонента або користувацького хука (ніколи в умовах, циклах чи після раннього повернення) і **лише з функцій React**. Порушите перше правило — комірки змістяться:

```tsx
import { useState } from "react";

type User = { name: string };

function Profile({ user }: { user: User | null }) {
  const [theme] = useState("light");           // hook 1 on every render
  if (!user) return <p className={theme}>Signed out</p>;   // an early return...
  const [tab, setTab] = useState("orders");     // ...so hook 2 runs on some renders only
  return <button onClick={() => setTab("settings")}>{user.name}: {tab}</button>;
}
```

Коли `user` зміниться з `null` на значення, React викине помилку «Rendered more hooks than during the previous render»; у зворотному випадку — «Rendered fewer hooks than expected». Перемістіть усі хуки перед раннім поверненням. Правило лінтера `eslint-plugin-react-hooks` виявляє цю проблему й відсутні залежності ефекту під час збирання.

### Ефекти та масиви залежностей

Код, що взаємодіє із зовнішнім світом (підписка, таймер, віджет поза React), належить до **ефекту**. `useEffect(setup, dependencies)` запускає `setup` **після того**, як результат рендерингу потрапив у DOM; повернена функція `setup` — це **очищення**, яке викликається перед повторним запуском ефекту та під час демонтування компонента.

**Масив залежностей** визначає, коли ефект запускається повторно:

| Залежності | Коли виконується ефект |
|---|---|
| не вказано | після кожного рендерингу |
| `[]` | лише після першого рендерингу (очищення виконується під час демонтування) |
| `[roomId]` | після першого рендерингу, а потім щоразу, коли змінюється `roomId` (порівняння через `Object.is`) |

```tsx
import { useEffect } from "react";

function ChatRoom({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = createConnection(roomId);   // the effect reads roomId...
    connection.connect();
    return () => connection.disconnect();          // ...cleanup undoes it before the next run
  }, [roomId]);                                    // ...so roomId is a dependency

  return <h2>Room {roomId}</h2>;
}
```

Якщо перейти з `"general"` на `"travel"`, а потім демонтувати компонент, послідовність викликів буде така: підключитися до general, від’єднатися від general, підключитися до travel, від’єднатися від travel. **У списку потрібно вказати кожне значення, яке читає ефект**; якщо пропустити якесь, ефект зберігатиме значення рендерингу, під час якого його створили, — це *застаріле замикання* (чат залишиться в попередній кімнаті).

У режимі розробки `<StrictMode>` навмисно запускає кожен ефект у послідовності **налаштування, очищення, налаштування** під час монтування, щоб виявити помилки очищення. Якщо API викликається двічі під час розробки, причина саме в цьому; виправлення — належне очищення. Багатьох ефектів можна уникнути: обчислюйте похідні значення під час рендерингу, а натискання обробляйте в handler натискання. Отримання даних в ефектах має чимало пасток (див. вправу); більшість команд використовує бібліотеку для отримання даних ([Розділ 34](#chapter-34-frontend-and-full-stack-in-depth)).

### Ключі в списках

Під час повторного рендерингу списку React зіставляє старі й нові елементи за **`key`**. Стан належить *позиції в дереві*, а для елементів списку ключ і є цією ідентичністю:

```tsx
import { useState } from "react";

type Item = { id: number; name: string };

function Line({ item }: { item: Item }) {
  const [note, setNote] = useState("");   // state belongs to the position React matched
  return (
    <li>
      {item.name} <input aria-label={`Note for ${item.name}`} value={note}
                         onChange={(e) => setNote(e.target.value)} />
    </li>
  );
}

function Basket({ items, keyByIndex }: { items: Item[]; keyByIndex: boolean }) {
  return (
    <ul>
      {items.map((item, index) =>
        <Line key={keyByIndex ? index : item.id} item={item} />)}
    </ul>
  );
}
```

Введіть примітку для «Чаю», а потім видаліть цей рядок. Із `key={index}` «Молоко» опиниться на індексі 0; React вирішить, що елемент 0 залишився, і «Молоко» успадкує примітку «Чаю». Із `key={item.id}` рядок «Чаю» буде знищено, а «Молоко» збереже власний стан. Використовуйте стабільний ідентифікатор із даних. Індексні ключі безпечні лише для списків, які ніколи не змінюють порядок, не отримують і не видаляють елементів; ключі `Math.random()` створюють усі рядки заново під час кожного рендерингу.

### Чим відрізняється Angular

Багато команд .NET обрали **Angular**, і його архітектура здасться знайомою. React — це бібліотека рендерингу, навколо якої ви збираєте стек; Angular — повний, цілісний фреймворк із router (маршрутизатором), формами, HTTP-клієнтом, dependency injection (впровадженням залежностей), тестуванням і CLI. Його вирізняють три механізми.

**Dependency injection** вбудований й подібний до ASP.NET Core: `providedIn: "root"` задає singleton, провайдери компонента надають його піддереву окремий екземпляр (аналог обмеженого часу життя в Angular), а `inject()` запитує залежність:

```typescript
import { Component, Injectable, inject, signal } from "@angular/core";
import { HttpClient } from "@angular/common/http";

type Order = { id: number; total: number };

@Injectable({ providedIn: "root" })            // one instance for the app: a singleton
export class OrderService {
  private http = inject(HttpClient);
  getOrders() { return this.http.get<Order[]>("/api/orders"); }   // an Observable
}

@Component({
  selector: "app-orders",
  template: `@for (o of orders(); track o.id) { <li>{{ o.id }}: {{ o.total }}</li> }`,
})
export class OrdersComponent {
  orders = signal<Order[]>([]);
  constructor() { inject(OrderService).getOrders().subscribe((o) => this.orders.set(o)); }
}
```

У шаблонах використовується власний синтаксис Angular (`track` — це аналог `key`), а компілюються вони заздалегідь.

**Спостережувані об’єкти RxJS** — це основний механізм асинхронності в Angular. На відміну від promise, **Observable** є *відкладеним* (запит не почнеться, доки не з’явиться підписник), може видавати *багато* значень у часі й підтримує *скасування* (відписка перериває запит). Оператори об’єднують потоки, як у типовому полі пошуку:

```typescript
import { Subject, debounceTime, distinctUntilChanged, from, switchMap } from "rxjs";

const searchTerms = new Subject<string>();     // the input's (input) handler calls searchTerms.next(text)

searchTerms.pipe(
  debounceTime(300),                            // wait for a 300 ms pause in typing
  distinctUntilChanged(),                       // skip a term equal to the previous one
  switchMap((term) => from(searchApi(term))),   // a new term drops the previous request
).subscribe((results) => render(results));
```

Коли надходить новий пошуковий запит, `switchMap` відписується від попереднього, тому повільна відповідь за старим запитом не зможе перезаписати новішу: цю гонку з вправи наприкінці розділу розв’язує один оператор. Недоліки — крута крива навчання та новий тип витоку: підписка, яка переживає свій компонент (для цього існують канал `async` і `takeUntilDestroyed()`).

**Виявлення змін** дає Angular змогу визначити, коли оновити DOM. Протягом більшої частини історії Angular **zone.js** перехоплював асинхронні API браузера (таймери, events, promise, XHR), щоб Angular отримував сповіщення про кожен callback і повторно перевіряв шаблони. Не потрібно було вказувати, що саме змінилося, але перевірки відбувалися набагато частіше, ніж необхідно. Сучасний Angular використовує **сигнали** — реактивні значення, які знають, хто їх читає:

```typescript
import { computed, signal } from "@angular/core";

const quantity = signal(2);
const price = signal(9.5);
const total = computed(() => quantity() * price());   // remembers which signals it read

console.log(total());   // 19
quantity.set(3);        // marks total stale; nothing recomputes yet
console.log(total());   // 28.5: recomputed on the next read
```

Шаблон, що читає сигнал, оновлюється, коли цей сигнал змінюється. Починаючи з Angular 21, нові застосунки типово працюють **без зон**: виявлення змін запускають оновлення сигналів, handlers events шаблону, канал `async` і `markForCheck`, а не zone.js. Старіші кодові бази досі використовують зони, часто разом із `OnPush`, щоб зменшити кількість перевірок.

## Routing та форми в SPA

### Клієнтська routing

Router SPA зіставляє URL-адреси з компонентами без звернення до сервера: після натискання посилання викликає `preventDefault()`, змінює адресу в рядку браузера через **History API** (`history.pushState`, без запиту) й рендерить компонент маршруту; натискання «Назад» генерує event `popstate`, який обробляє router.

Звідси типова помилка deployment (розгортання): навігація працює, але після **оновлення** `/orders/42` або відкриття спільного посилання сервер повертає **404**, бо тепер браузер справді запитує в нього `/orders/42`. Сервер має відповідати `index.html` на невідомі шляхи, які не вказують на файли, а далі керування перейме router. В ASP.NET Core:

```csharp
app.UseStaticFiles();                                  // the built SPA: index.html, assets/*
app.MapControllers();                                  // /api/...
app.Map("/api/{**rest}", () => Results.NotFound());    // unknown API paths stay 404s
app.MapFallbackToFile("index.html");                   // everything else: let the SPA route it
```

Без третього рядка помилково введена URL-адреса API також отримає `index.html` зі статусом `200 OK`, а SPA згодом видасть незрозумілу помилку розбору JSON замість коректного 404 (перевірено в ASP.NET Core 10). **Захист маршрутів покращує UX, але не забезпечує безпеку**: приховування `/admin` у router не завадить нікому викликати `/api/admin`. Крім того, SPA під час навігації не переводить фокус і не оголошує нову сторінку, як це відбувається під час повного завантаження ([Розділ 34](#chapter-34-frontend-and-full-stack-in-depth) описує рішення).

### Форми в SPA

**Керований** елемент введення React зберігає значення у стані (`value={email}` разом з `onChange`), тому його можна перевіряти після кожного натискання клавіші; **некерований** зберігає значення в DOM, звідки його читають під час надсилання через `FormData`. В Angular є *форми на основі шаблонів* і *реактивні форми* (типізована модель форми в компоненті); у більших кодових базах зазвичай застосовують реактивні. Надійність форми визначають три моменти, важливі для бекенду:

- **Перевіряйте двічі з різних причин**: на клієнті — для миттєвого зворотного зв’язку, на сервері — бо значення має лише ця перевірка.
- **Пов’язуйте помилки сервера з полями.** `ValidationProblemDetails` містить об’єкт `errors` із ключами-назвами полів; якщо показати його біля полів введення, `400` стане помилкою, яку можна виправити. Заздалегідь узгодьте регістр назв полів.
- **Передбачте повторне надсилання.** Вимикайте кнопку, поки запит очікує на відповідь, і зробіть endpoint безпечним для повторного виклику (idempotency key (ключ ідемпотентності), [Розділ 20](#chapter-20-distributed-systems)).

## Доступність: тепер це вимога закону

Доступність перестала бути «гарною практикою, до якої колись дійдуть руки» й стала «юридичною вимогою з конкретною датою». **Європейський акт про доступність**, чинний із червня 2025 року, зобов’язує широкий спектр споживчих продуктів і послуг, що продаються в ЄС (електронну торгівлю, банківські послуги, продаж транспортних квитків, електронні книжки, телекомунікації), відповідати вимогам доступності. Гармонізований стандарт EN 301 549 посилається на **WCAG 2.1/2.2 рівня AA**; на державний сектор уже поширювалася Директива про доступність вебсайтів. У США розділ 508 охоплює державні закупівлі, а позови щодо недоступних сайтів на підставі ADA стабільно надходять уже десять років. Отже, **недоступна розмітка — це порушення вимог, а не косметичний недолік**, і відповідь «дизайнер цього не вказав» більше не приймається.

### WCAG і практичне мислення про доступність

WCAG спирається на чотири принципи, які утворюють абревіатуру **POUR**. Їх корисно знати як інструмент міркування, а не як контрольний список:

- **Сприйнятність.** Чи може користувач отримати інформацію? Потрібні текстові альтернативи для зображень, субтитри для відео, достатній колірний контраст; не можна передавати зміст лише кольором.
- **Керованість.** Чи може користувач взаємодіяти з інтерфейсом? Усе має бути доступним і придатним до використання з клавіатури, без пасток фокуса, із достатнім часом; не повинно бути блимання, що провокує судоми, а посилання пропуску мають обходити повторювану навігацію.
- **Зрозумілість.** Чи поводиться інтерфейс передбачувано? Навігація послідовна, поля мають мітки, помилки визначені й пояснені текстом, а зміна фокуса не спричиняє несподіваних змін контексту.
- **Надійність.** Чи зможуть допоміжні технології розібрати інтерфейс? Потрібна коректна розмітка та правильні назва, роль і значення кожного елемента керування.

Відповідність має рівні A, AA і AAA. **Цільовий рівень — AA**: саме на нього посилаються нормативні вимоги, а AAA містить вимоги (наприклад, контрастність 7:1), недосяжні для більшості дизайнів.

### Спершу семантичний HTML, потім ARIA

Майже кожна помилка доступності в інтерфейсах команд .NET має ту саму першопричину, про яку йшлося в розділі HTML: `<div>` з handler натискання використовується замість `<button>`.

```html
<!-- Not focusable, not keyboard-operable, no role, no state.
     A screen reader announces nothing useful. -->
<div class="btn" onclick="submit()">Save</div>

<!-- Focusable, Enter/Space activated, announced as a button,
     disabled state understood — all of it for free. -->
<button type="button" onclick="submit()">Save</button>
```

Вбудований елемент має *назву*, *роль* і *стан*, які браузери й допоміжні технології вже розуміють однаково. Щоб відтворити це за допомогою ARIA, довелося б правильно реалізувати керування фокусом, активацію з клавіатури, стан `aria-pressed`/`aria-expanded` і семантику вимкненого елемента — для кожної комбінації браузера й програми читання з екрана.

Саме тому **перше правило ARIA** звучить так: не використовуйте ARIA. Якщо існує вбудований елемент або атрибут із потрібною семантикою, скористайтеся ним. ARIA додає розмітці *семантику*, але ніколи не додає *поведінку*. `role="button"` на `<div>` не змусить Enter активувати елемент, не зробить його доступним для фокуса й не перетворить на кнопку. Натомість програма читання з екрана оголосить «кнопка», але натискання Enter нічого не зробить — це гірше, ніж не оголошувати нічого.

> **Пастка.** Найпоширеніша шкідлива практика — застосовувати ARIA, щоб приховати структурну проблему: додавати `aria-label` до `<div>`, який використовується як заголовок; задавати `role="navigation"` елементу, який мав би бути `<nav>`; або повсюдно додавати `aria-live`, щоб примусово оголошувати зміни. Погано застосована ARIA помітно гірша за її відсутність: щорічне опитування WebAIM стабільно виявляє в середньому *більше* помилок на сторінках з ARIA, ніж без неї.

Звертайтеся до ARIA, лише коли немає вбудованого відповідника: для набору вкладок, комбінованого поля зі списком автозаповнення, деревоподібного подання чи живої області для асинхронного статусу. Якщо використовуєте ARIA, точно дотримуйтеся шаблонів **ARIA Authoring Practices Guide**, зокрема таблиць взаємодії з клавіатурою: саме цю частину розробники часто пропускають, але користувачі одразу помічають.

### Керування з клавіатури та фокус

Перевірте це сьогодні у застосунку, над яким працюєте: відкладіть мишу й спробуйте пройти основний шлях користувача. Ця проста вправа виявить більшість серйозних проблем.

На що звертати увагу:

- **До всіх інтерактивних елементів можна дістатися** клавішею Tab, у порядку, що відповідає візуальному розташуванню. Якщо для виправлення порядку ви хочете використати `tabindex="3"`, проблема в порядку DOM — виправте саме його. Зазвичай використовуйте лише `tabindex` зі значеннями `0` (додати до природного порядку) і `-1` (доступний для фокуса скриптом, але не через Tab).
- **Фокус видно.** `outline: none` без заміни — найшкідливіший для користувачів клавіатури рядок CSS. Якщо стандартне кільце фокуса негарне, стилізуйте `:focus-visible`, а не прибирайте його.
- **Модальні вікна утримують фокус, поки відкриті, і повертають його після закриття.** Відкрийте діалогове вікно й переходьте ним клавішею Tab: фокус не має виходити на сторінку позаду. Після закриття він має повернутися до елемента, який відкрив вікно; інакше користувач опиниться на початку документа й не зрозуміє, де перебуває. Вбудований елемент `<dialog>` із `showModal()` автоматично виконує більшу частину цієї роботи.
- **Посилання для пропуску.** Посилання «перейти до основного вмісту» як перший елемент у порядку фокуса позбавляє користувачів клавіатури потреби проходити сорок пунктів навігації на кожній сторінці.
- **Не створюйте ненавмисних пасток фокуса** — типовий приклад: вбудований сторонній віджет, у який можна перейти клавішею Tab, але з якого не можна вийти.

### Форми: найважливіша ділянка

Саме через недоступні форми незручність інтерфейсу починає коштувати людям грошей.

```html
<!-- The label is programmatically associated: clicking it focuses the
     input, and a screen reader announces the label with the field. -->
<label for="email">Email address</label>
<input id="email" name="email" type="email"
       autocomplete="email"
       aria-describedby="email-hint email-error"
       aria-invalid="true" />
<p id="email-hint">We'll only use this for order updates.</p>
<p id="email-error" class="error">Enter an email address in the format name@example.com.</p>
```

Найважливіші правила такі: кожне поле введення має справжній `<label>` (текст-заповнювач — не мітка: він зникає, коли користувач починає вводити текст, і часто має недостатню контрастність); помилки пов’язують із полем через `aria-describedby` і `aria-invalid`, а не позначають лише червоним кольором; текст помилки пояснює, що робити, а не просто повідомляє «некоректне введення»; атрибути `autocomplete` дають браузерам і менеджерам паролів змогу заповнити поля; обов’язкові поля позначають текстом, а не лише зірочкою, значення якої пояснено в легенді, яку ніхто не читає.

Для асинхронної перевірки й повідомлень про стан область `aria-live="polite"` оголошує зміни, не забираючи фокус. Використовуйте її помірно й лише для справді важливих повідомлень; жива область у журналі чату, що спрацьовує після кожного натискання клавіші, перетворюється на знаряддя тортур.

Про автоматичне тестування всього цього в CI та ручну перевірку клавіатурою й програмою читання з екрана йдеться в [Розділі 34](#chapter-34-frontend-and-full-stack-in-depth).

> **Рекомендація.** Виправляйте проблеми доступності у спільних компонентах, а не на сторінках. Якщо компоненти `Button`, `Modal`, `Field` і `Table` у дизайн-системі один раз зробити правильно, сотні екранів стануть доступними автоматично. Так доступність перестає бути додатковими витратами для кожної функції й перетворюється на розв’язану інфраструктурну проблему. Такий самий аргумент стосується будь-якого наскрізного питання в цій книжці.

## Інструменти: npm, package.json, lock-файли та Vite

Браузери не можуть виконувати TypeScript чи JSX, тому між вихідним кодом і браузером потрібен набір інструментів. Якщо «у мене на комп’ютері збирається» не працює в CI, шукайте причину тут.

### npm, package.json і lock-файл

**npm** — це аналог NuGet. У файлі **`package.json`** зберігаються `scripts` (`npm run dev`, `npm test`), `dependencies` (потрапляють у пакет) і `devDependencies` (інструменти збирання й тестування). Версії задаються діапазонами semver; типово перед номером стоїть каретка: `"^19.2.0"` означає будь-яку версію 19.x починаючи з 19.2.0, а `"~19.2.0"` — лише версії 19.2.x. Діапазон — це політика, а не конкретна версія: два встановлення з інтервалом у тиждень можуть відрізнятися.

**Lock-файл** `package-lock.json` фіксує точну версію й контрольну суму кожного пакета в дереві залежностей. Додавайте його до репозиторію. `npm install` може змінити його; **`npm ci`**, призначений для CI й Docker, видаляє `node_modules`, встановлює саме зафіксовані версії та завершується помилкою, якщо lock-файл не узгоджується з `package.json` (порівняння з NuGet — у [Розділі 27: Lock-файли](#lockfiles)).

> **Пастка.** Невеликий застосунок може підтягнути сотні транзитивних пакетів, а їхні сценарії встановлення виконують довільний код на комп’ютері, де вони встановлюються, зокрема на CI-агенті із секретами. Додавайте lock-файл до репозиторію, збирайте через `npm ci`, серйозно ставтеся до `npm audit` і перевіряйте, що саме додає нова залежність ([Розділ 27](#chapter-27-security-in-depth-and-the-supply-chain)).

### Vite: сервер розробки та збирання

**Пакувальник** обходить граф імпортів, компілює TypeScript і JSX, вилучає невикористані експорти та створює кілька оптимізованих файлів. **Vite** — сучасний типовий інструмент для нових проєктів React і Vue (CLI Angular використовує всередині Vite та esbuild); він має два режими:

- **`vite` (сервер розробки)** не пакує файли: він обслуговує вихідний код як нативні модулі ES і компілює кожен файл за запитом; **гаряча заміна модулів** підміняє у відкритій сторінці лише змінений модуль.
- **`vite build`** пакує код за допомогою Rolldown (Vite 8; у попередніх версіях використовувався Rollup): виконує tree-shaking і мінімізацію, створює фрагменти й **назви файлів із хешем вмісту** (`index-4f9a1c.js`), тож ресурси можна кешувати безстроково, а `index.html` — ніколи.

На межі з вашою API важливі дві можливості:

```javascript
// vite.config.js
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    proxy: { "/api": "http://localhost:5080" },   // dev server forwards /api to Kestrel
  },
});
```

**Проксі сервера розробки** дає браузеру єдине походження: виклики `/api` надходять на `localhost:5173`, а Vite передає їх до Kestrel. CORS не потрібен, а в коді використовуються відносні URL-адреси, як у продакшені.

**Environment variables (змінні середовища)** компілюються в код: до клієнтської частини потрапляють лише змінні з префіксом `VITE_` (`import.meta.env.VITE_API_URL`), причому вони записуються в пакет **під час збирання**. Отже, це відкриті дані (ніколи не секрети), а пакет прив’язаний до одного середовища. Щоб просувати той самий артефакт між середовищами ([Розділ 13](#chapter-13-git-and-cicd)), натомість завантажуйте `config.json` під час запуску.

## XSS на фронтенді

Сторону сервера розглянуто в [Розділі 12: Міжсайтовий скриптинг (XSS)](#cross-site-scripting-xss). З боку браузера: **XSS виникає, коли контрольований зловмисником текст потрапляє в місце, де браузер інтерпретує його як код**, — *точку виконання*:

- Розбір HTML: `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`.
- URL-адреси, які виконують код: `href` або `src` зі значенням `javascript:…`.
- Код із рядків: `eval`, `new Function`, `setTimeout("string")`.
- Вбудовані атрибути handlers events: `onerror="…"`, `onclick="…"`.

Фреймворки **типово безпечні**, бо за звичайного використання уникають точок виконання: `{text}` у JSX стає **текстовим вузлом**, який не розбирається як розмітка, а Angular *санітизує* значення, прив’язані до HTML чи URL-контекстів. Небезпека криється в обходах цього захисту:

```tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>;   // text becomes a text node: markup in it is shown, never parsed
}

function CommentUnsafe({ html }: { html: string }) {
  return <p dangerouslySetInnerHTML={{ __html: html }} />;   // parsed as HTML: an XSS sink
}
```

Для `<img src="x" onerror="alert(1)">` перший приклад покаже символи, а другий створить справжній `<img>`, у якого виконається `onerror`. В Angular обхідним шляхом є `DomSanitizer.bypassSecurityTrustHtml`. React 19 замінює URL `javascript:` в `href` на такий, що спричиняє помилку (старіші версії лише видавали попередження); усе одно перевіряйте створені користувачем URL-адреси на `http:`/`https:`. Якщо потрібно показувати користувацький HTML (Markdown, форматований текст), санітизуйте його підтримуваною бібліотекою, як-от DOMPurify, а не регулярним виразом. Зберігання токенів поза досяжністю JavaScript і **політика безпеки вмісту** ([Розділ 34](#chapter-34-frontend-and-full-stack-in-depth)) обмежують шкоду від успішної ін’єкції.

## Основні показники вебпродуктивності

**Core Web Vitals** від Google — це три числові показники того, що відчувають користувачі; кожен пов’язаний із механізмом, описаним у цьому розділі:

| Показник | Що вимірює | Добре | Погано | Типові причини |
|---|---|---|---|---|
| **LCP**, найбільше відображення вмісту | Завантаження: коли відображається найбільше зображення або текстовий блок у межах екрана | ≤ 2.5 с | > 4 с | повільна відповідь сервера (ваш TTFB), CSS і JS, що блокують рендеринг, велике головне зображення, застосунок із клієнтським рендерингом, який нічого не показує до виконання пакета |
| **INP**, затримка до наступного відображення | Відгук: затримка від натискання, дотику чи клавіші до малювання наступного кадру протягом усього сеансу | ≤ 200 мс | > 500 мс | довгі завдання в головному потоці: важкі handlers events, масштабний повторний рендеринг, обробка JSON |
| **CLS**, сукупний зсув макета | Візуальна стабільність: наскільки несподівано переміщується видимий вміст | ≤ 0.1 | > 0.25 | зображення й вставлені елементи без заданих розмірів, банери й реклама, додані над вмістом, вебшрифти, які змінюють розмір тексту |

У 2024 році INP замінив First Input Delay: FID вимірював затримку введення лише під час першої взаємодії, а INP — кожну взаємодію до наступного малювання. Сторінка проходить перевірку, якщо **75-й перцентиль** реальних відвідувань має «добрий» результат за всіма трьома показниками. **Польові дані** реальних користувачів (бібліотека `web-vitals`, публічний звіт Chrome) є джерелом істини; **лабораторні дані** одного завантаження Lighthouse відтворювані, але синтетичні, і не вимірюють INP, адже ніхто не натискає елементи. Внесок бекенду більший, ніж здається: LCP починається з часу до першого байта вашого сервера, а LCP сторінки з клієнтським рендерингом очікує на API-виклик, який заповнить її. [Розділ 34](#chapter-34-frontend-and-full-stack-in-depth) описує вимірювання та виправлення кожного показника.

## Скільки фронтенду насправді потрібно вивчити?

Прагніть *ефективно працювати на межі*, а не ставати розробником фронтенду:

- **Вільно орієнтуватися:** знати достатньо HTML, CSS, JavaScript і TypeScript, щоб читати SPA, вносити невеликі зміни, писати виклики `fetch` і налагоджувати їх у DevTools. Коли «фронтенд зламався», спершу відкривайте вкладки Network і Console.
- **Глибоко знати:** контракт API — OpenAPI, згенеровані клієнти, версіонування, потоки автентифікації (OIDC, PKCE, BFF), CORS і взаємодію в реальному часі. Це *ваша* сфера.
- **Розуміти:** як React і Angular структурують застосунок — достатньо, щоб переглядати PR і проєктувати сумісні API; також концептуально розуміти стратегії рендерингу й pipeline збирання.

> **Найцінніша інвестиція:** контролювати межу контракту. Документований, версійований і типізований API з чіткою автентифікацією перетворює інтеграцію фронтенду з переговорів на формальність.

### Вибір стека інтерфейсу

Короткий посібник для вибору:

1. **Багато вмісту, публічний сайт, критична SEO-оптимізація?** Серверний рендеринг: Razor Pages/MVC, Blazor Static SSR або метафреймворк JS із SSR.
2. **Внутрішній бізнес-застосунок у команді .NET?** Blazor (Static SSR з інтерактивними островами або Auto) — надійний вибір із низьким порогом входження.
3. **Насичена публічна SPA з широкою екосистемою та доступними фахівцями з JS?** React/Angular/Vue із REST API, бажано за BFF.
4. **Кросплатформний настільний або мобільний застосунок на одній кодовій базі C#?** MAUI або Blazor Hybrid для повторного використання вебінтерфейсу; Avalonia, якщо важлива підтримка Linux на настільних системах; нативний стек, якщо ключова перевага продукту — якісна інтеграція з платформою.

[Розділ 34](#chapter-34-frontend-and-full-stack-in-depth) порівнює Blazor, стратегії рендерингу й нативні клієнти. Універсальної відповіді немає: потрібно свідомо вибрати варіант, який пасує *саме цій* команді, аудиторії та бюджету продуктивності.

## Вправи

### Знайдіть помилку

Цей компонент пошуку працює в демонстрації. У продакшені користувачі повідомляють, що результати іноді не відповідають введеному тексту, а сторінка часом стає порожньою.

```tsx
import { useEffect, useState } from "react";

type Product = { id: number; name: string };

export function ProductSearch({ query }: { query: string }) {
  const [results, setResults] = useState<Product[]>([]);

  useEffect(() => {
    fetch(`/api/products?q=${encodeURIComponent(query)}`)
      .then((res) => res.json())
      .then((data: Product[]) => setResults(data));
  }, [query]);

  return (
    <ul>
      {results.map((p) => <li key={p.id}>{p.name}</li>)}
    </ul>
  );
}
```

Поясніть механізм обох симптомів, а потім виправте їх.

<details>
<summary>Відповідь</summary>

**Хибні результати: гонка між відповідями.** Кожна зміна `query` запускає новий запит, але старий ніхто не зупиняє. Користувач вводить «lap», а потім «laptop»; повільніша відповідь для «lap» надходить *останньою*, її `setResults` також виконується останньою, і під запитом «laptop» показуються результати для «lap». Це не гонка даних, а лише *порядок* callbacks і ефект, який запускає асинхронну роботу без очищення.

**Порожня сторінка: неперевірена відповідь.** `fetch` не повертає відхилення за статусу `500`. Тіло ProblemDetails успішно розбирається, `setResults` зберігає *об’єкт*, і під час наступного рендерингу `results.map` спричиняє помилку. Без межі обробки помилок React демонтує все дерево. Анотація `data: Product[]` нічого не змінила: типи стираються.

Виправлення скасовує попередній запит під час очищення (воно запускається перед наступним ефектом і під час демонтування компонента) та перевіряє статус:

```tsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/products?q=${encodeURIComponent(query)}`, { signal: controller.signal })
    .then((res) => {
      if (!res.ok) throw new Error(`Search failed: ${res.status}`);
      return res.json();
    })
    .then((data: Product[]) => { setResults(data); setError(null); })
    .catch((err) => { if (err.name !== "AbortError") setError(err.message); });
  return () => controller.abort();   // a newer query cancels this one, and so does unmounting
}, [query]);
```

(із станом `error`, який відображається як `<p role="alert">`). Прапорець `ignore`, установлений під час очищення, теж працює, але скасування заощаджує роботу сервера; затримка введення зменшує кількість запитів, проте не усуває гонку. Перевірено в `verify/frontend/ch06`: якщо відповіді надходять не в тому порядку, початковий компонент показує результати за старим запитом, а виправлений — за новим; за статусу `500` початковий компонент викидає `results.map is not a function` і React очищує сторінку, тоді як виправлений показує помилку.
</details>

Друга вправа — звичайний JavaScript. Сповіщення стверджує, що все збережено, але в базі бракує деяких рядків, а помилки ніхто не бачить.

```javascript
export async function saveAll(lines, api) {
  lines.forEach(async (line) => {
    await api.save(line);
  });
  return lines.length;
}

export async function onSaveClicked(lines, api, toast) {
  try {
    const count = await saveAll(lines, api);
    toast(`Saved ${count} lines`);
  } catch (e) {
    toast(`Save failed: ${e.message}`);
  }
}
```

<details>
<summary>Відповідь</summary>

`forEach` викликає callback `async` для кожного рядка й **ігнорує повернений ним promise**, тому `saveAll` запускає всі операції збереження, не очікуючи на жодну, а сповіщення про успіх з’являється раніше, ніж щось буде збережено. Пізніша помилка відхиляє promise, на який ніхто не посилається: блок `try`/`catch` давно завершився, а браузер записує необроблене відхилення в журнал, який ніхто не читає. Це аналог `async void` у C# ([Розділ 4](#chapter-4-async-essentials)).

Зберігайте посилання на promise: `await Promise.all(lines.map((line) => api.save(line)))` виконує збереження паралельно й повертає відхилення, якщо будь-яке завершилося помилкою; `for (const line of lines) await api.save(line);` зберігає рядки послідовно, один за одним. Перевірка в репозиторії показує: початковий код надсилає сповіщення «Saved 2 lines», хоча нічого не збережено, а невдале збереження дає сповіщення про успіх і необроблене відхилення; виправлений код сповіщає після обох операцій і повідомляє про помилку.
</details>

### Що б ви зробили?

Команда SPA створює новий застосунок React для вашого API. Вони просять увімкнути CORS через `AllowAnyOrigin()`, «бо сервер розробки працює на localhost:5173 і запити блокуються», а також повертати JWT у тілі відповіді на вхід, щоб зберігати його в `localStorage`. Демонстрацію потрібно провести в п’ятницю.

<details>
<summary>Як міркує старший інженер</summary>

Відокремте проблему від запропонованого розв’язання. Перша проблема — локальна розробка з двома джерелами; проксі сервера розробки Vite розв’язує її краще за CORS. У продакшені одному хосту CORS не потрібен; в іншому разі налаштуйте справжні джерела окремо для кожного середовища й ніколи не використовуйте підстановку для API з автентифікацією.

Друге прохання — це рішення з безпеки, замасковане під зручність, тож воно потребує короткого обговорення, а не мовчазного «так» чи «ні». Будь-який скрипт цього джерела, зокрема скомпрометована залежність, може прочитати токен у `localStorage`; запропонуйте BFF із cookie `HttpOnly`, пояснивши реальну вартість такого рішення. Якщо до п’ятниці чекати справді не можна, узгодьте, що саме є тимчасовим, і зафіксуйте це разом із датою.

Ознака досвідченого підходу — команда не залишається заблокованою, уже сьогодні має робоче налаштування, а рішення щодо токенів явно ухвалюють ті, хто відповідає за ризики, а не залишають його на розсуд випадку.

### Перевірте самостійно

У SPA, яку обслуговує ваш API, перевірте браузер і код, а не покладайтеся на пам’ять:

- Відфільтруйте вкладку Network у DevTools за `OPTIONS`: скільки попередніх перевірок припадає на одне завантаження сторінки і чи є в них `Access-Control-Max-Age`? Чи можуть SPA та API мати спільне походження?
- Запустіть Lighthouse для найповільнішої важливої сторінки. Який елемент визначає LCP і яку частину LCP становить час до першого байта вашого сервера?
- Знайдіть у фронтенді `dangerouslySetInnerHTML`, `innerHTML`, `bypassSecurityTrust` і `eval(`. Звідки надходять дані для кожного з них?
- Чи додано `package-lock.json` до репозиторію, чи використовує CI `npm ci` і чи не є секретом якась змінна `VITE_`?
- Оновіть сторінку з глибокої URL-адреси на кшталт `/orders/42` і запитайте неіснуючу URL-адресу `/api/...`: чи отримуєте ви сторінку й відповідь 404?

## Запитання на співбесіді

**Що відбувається між введенням URL-адреси й появою сторінки?**
DNS, TCP, TLS і HTTP ([Розділ 5](#chapter-5-http-and-web-apis)); потім DOM (будується поступово), CSSOM (блокує рендеринг), скрипти (звичайні блокують парсер), розкладка, малювання й компонування. Пізніші зміни DOM повторно запускають частину pipeline.

**`==` і `===`: у чому різниця?**
`===` ніколи не перетворює типи; `==` спершу виконує неявне перетворення за правилами, які навіть не є транзитивними. Використовуйте `===`; поширений exception — `x == null`.

**Тривожний сигнал:** «`===` порівнює посилання, а `==` — значення». Обидва оператори порівнюють об’єкти за посиланням; різниця в неявному перетворенні типів.

**Як визначається `this`?**
Способом виклику: `obj.f()` задає `obj`, звичайний виклик у строгому режимі — `undefined`, `new` — новий об’єкт, `bind` — зафіксоване значення; стрілкові функції використовують `this` із зовнішньої області. Метод, переданий як callback, втрачає це прив’язування.

**Поясніть цикл events. Що запуститься раніше: callback `setTimeout(…, 0)` чи `then` для виконаного promise?**
Одне завдання виконується до кінця, потім запускаються всі мікрозавдання, далі відбувається рендеринг і запускається наступне завдання. Callbacks promise — це мікрозавдання, а таймери — завдання, тож спершу виконається `then`.

**Тривожний сигнал:** «`await` переносить роботу у фоновий потік». Потік лише один; `await` лише не дає функції блокувати його під час очікування, а обчислення процесора все одно заморожують сторінку.

**`Promise.all` і `Task.WhenAll`: у чому різниця?**
`Promise.all` повертає відхилення після першої помилки, а решта операцій продовжує виконуватися без спостереження; `Task.WhenAll` очікує на всі. `Promise.allSettled` теж очікує на всі, але повідомляє про кожен результат.

**Чим система типів TypeScript відрізняється від системи типів C#?**
Вона структурна, а не номінальна; типи стираються під час виконання, тож `as` нічого не перевіряє, а дані API потрібно перевіряти або використовувати згенерований клієнт.

**Коли браузер надсилає попередній запит CORS і що означає помилка CORS?**
Для міждоменних запитів, які не можна надіслати звичайною формою (інші методи, `Authorization`, JSON). Помилка CORS означає, що браузер приховав відповідь; простий запит сервер уже виконав.

**Де SPA має зберігати токен доступу?**
Не в `localStorage`, який доступний усім скриптам цього походження; краще використовувати BFF із cookie `HttpOnly`.

**Чому зміна стану на місці не запускає повторний рендеринг у React і чому не можна викликати хуки за умовою?**
React порівнює новий стан зі старим через `Object.is`, тож переданий назад змінений масив вважається «незміненим». Хуки зіставляються з комірками за порядком виклику, тому умовний виклик зсуває всі наступні комірки.

**Чим виявлення змін і спостережувані об’єкти Angular відрізняються від React?**
React повторно рендерить компонент після виклику сетера. Angular використовував zone.js для повторної перевірки після кожного асинхронного callback; починаючи з версії 21, типово використовується режим без зон, де зміни запускають сигнали. Спостережувані об’єкти відкладені, можуть видавати багато значень і підтримують скасування.

**Чому фреймворки типово захищають від XSS і як уразливість повертається?**
`{text}` стає текстовим вузлом, який не розбирається як HTML. XSS повертається через `dangerouslySetInnerHTML`, `innerHTML`, `bypassSecurityTrustHtml`, URL-адреси `javascript:` і `eval`.

**Що таке Core Web Vitals?**
LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1 на 75-му перцентилі реальних відвідувань. Lighthouse надає лабораторні дані й не вимірює INP.

**Тривожний сигнал:** «Lighthouse показує 98, отже з продуктивністю все добре». Одне синтетичне завантаження не відображає досвід ваших користувачів.
