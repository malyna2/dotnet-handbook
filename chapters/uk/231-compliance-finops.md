# Розділ 31: Відповідність вимогам, приватність даних і вартість хмари (FinOps)

На початку кар’єри «вимоги» зазвичай надходять від власника продукту як історії користувачів. На шляху до старшого інженера з’являються друга й третя групи вимог, яких ніхто не записує на стікері, але всі очікують їх дотримання: закон і рахунок. Функція, що розкриває персональні дані або непомітно втричі збільшує рахунок за хмару, не завершена, хай би якими зеленими були тести. Цей розділ присвячений невидимим зацікавленим сторонам — регулятору, фінансовому директору й дедалі частіше звітності зі сталого розвитку — та інженерним рішенням, які задовольняють їх усіх. Як з’ясується, третя сторона здебільшого хоче того самого, що й друга; це найкорисніший факт у розділі. Частина A перетворює закони про приватність на інженерні рішення (класифікація, мінімізація, видалення, резидентність, аудит); частина B робить те саме з рахунком — від моделі вартості до важелів, доступних розробнику; частина C показує, що екологічне ПЗ здебільшого спирається на ті самі важелі. Матеріал розвиває карту хмари з [розділу 28](#chapter-28-cloud-fundamentals-aws-azure).

> **Цей розділ містить загальні інженерні поради, а не юридичну консультацію.** Норми відрізняються за юрисдикціями, змінюються з часом і залежать від обставин організації. Коли постає реальне питання відповідності, залучайте юридичну команду, фахівців із приватності й безпеки. Завдання інженера — будувати системи, які *можуть* відповідати вимогам, і знати відповідну лексику для співпраці.

## Частина A — Відповідність вимогам і приватність даних для інженерів

### Коротко про нормативні режими

Диплом юриста не потрібен, але потрібна робоча ментальна модель основних режимів, бо кожен накладає інші *технічні* обов’язки.

- **GDPR (Загальний регламент про захист даних)** — закон ЄС про захист даних. Він стосується будь-якої організації, що обробляє персональні дані людей у ЄС, незалежно від місця реєстрації компанії. Це найвпливовіший у світі закон про приватність; він запровадив поняття (права суб’єктів даних, правова підстава, повідомлення про витік протягом 72 годин), які наслідують інші закони.
- **CCPA / CPRA (Каліфорнія)** — надають жителям Каліфорнії право знати, які дані збирають, вимагати їх видалення й відмовлятися від їх «продажу». За суттю схожі на GDPR, але більше зосереджені на споживачах і праві відмовитися, тоді як GDPR насамперед спирається на згоду.
- **HIPAA (охорона здоров’я США)** — регулює «захищену медичну інформацію» (PHI). Якщо система працює з медичними записами, потрібні суворий контроль доступу, журнали аудиту й шифрування, а також підписана *угода про ділове партнерство* з постачальниками, зокрема хмарним провайдером.
- **PCI-DSS** — не державний закон, а договірний стандарт індустрії платіжних карток. Він визначає, як зберігати, обробляти й передавати дані власників карток. Найдешевший спосіб відповідати вимогам зазвичай — *не зберігати номери карток*, а передати обробку провайдеру токенізації (Stripe, Adyen, Braintree).
- **Закон ЄС про ШІ** — набув чинності в серпні 2024 року; вимоги вводяться поетапно до 2026–2027 років. Він стосується систем із функціями ШІ й установлює обов’язки за категорією ризику (заборонений, високий, обмежений, мінімальний); категорія визначає ваші зобов’язання.

Спільна тема така: **усі ці норми стосуються персональних даних — хто має доступ, де вони зберігаються, як довго їх утримують і чи можна довести, що з ними відбувалося.** Таке формулювання перетворює закон на архітектуру.

### Виявлення та класифікація персональних даних

Усе подальше залежить від того, *які* дані ви зберігаєте та *наскільки вони чутливі*.

- **PII (персональні дані, що дають змогу ідентифікувати особу)** — усе, що ідентифікує людину: ім’я, електронна адреса, телефон, IP-адреса, ідентифікатори пристроїв, точне місце перебування та поєднання даних, які разом ідентифікують особу (дата народження, поштовий індекс і стать можуть вказати на несподівано велику частку людей).
- **PHI (захищена медична інформація)** — PII в контексті охорони здоров’я, а також діагнози, лікування й страхові дані.
- **Дані спеціальних категорій / чутливі дані** — за GDPR, наприклад, медичні, расові, релігійні, біометричні, політичні дані й дані про сексуальну орієнтацію; вони мають додатковий захист.

Звичка досвідченого інженера — **класифікувати дані на рівні схеми, а не лише подумки.** Зробіть чутливість повноцінним атрибутом моделі, щоб інструменти могли на неї реагувати:

```csharp
[AttributeUsage(AttributeTargets.Property)]
public sealed class PersonalDataAttribute : Attribute
{
    public DataSensitivity Sensitivity { get; }
    public PersonalDataAttribute(DataSensitivity sensitivity) => Sensitivity = sensitivity;
}

public enum DataSensitivity { Low, Pii, Sensitive }

public class Customer
{
    public Guid Id { get; set; }                       // pseudonymous key — not itself PII

    [PersonalData(DataSensitivity.Pii)]
    public string Email { get; set; } = default!;

    [PersonalData(DataSensitivity.Pii)]
    public string FullName { get; set; } = default!;

    [PersonalData(DataSensitivity.Sensitive)]
    public string? HealthNotes { get; set; }

    public DateTimeOffset CreatedOn { get; set; }      // not personal
}
```

Атрибути дають змогу керувати автоматизованою поведінкою через метадані: створювати карту даних для аудиторів, формувати експорт за правом доступу за допомогою reflection, приховувати класифіковані поля з журналів і тестами перевіряти, що жодна властивість `Sensitive` не серіалізується в аналітичну тему. **Відповідність вимогам на основі метаданих масштабується; ручна пильність — ні.** ASP.NET Core Identity використовує цей самий шаблон `[PersonalData]` для вбудованих функцій завантаження й видалення — його варто вивчити як приклад реалізації.

Microsoft Purview (і подібні засоби) сканує сховища й автоматично класифікує стовпці, але класифікація *під час створення* дешевша й точніша за пошук постфактум.

> **Рекомендація: мінімізація даних.** Найбезпечніші персональні дані — ті, яких ви ніколи не збирали. Перш ніж додати поле, запитайте: «Чи маємо ми для нього конкретну актуальну мету?» Збір даних «про всяк випадок» збільшує наслідки кожного майбутнього витоку й додає роботи з кожним запитом на видалення.

### Практичне застосування прав суб’єктів даних

Закони на кшталт GDPR надають людям права, що безпосередньо перетворюються на кінцеві точки API та фонові завдання.

**Право на доступ (перенесення даних).** Користувач може запросити копію всіх даних про себе, зазвичай у машинозчитуваному форматі. Якщо персональні дані розкидані між монолітною базою, трьома мікросервісами, сховищем даних і SaaS для email-маркетингу, виконати запит складно. Проєктуйте систему з урахуванням цього: ведіть інвентар *місць*, де зберігаються персональні дані, і створіть процедуру агрегації для кожної підсистеми.

**Право на видалення («право бути забутим»).** Саме тут архітектура найсильніше стикається з реальністю: системи проєктують так, щоб *ніколи* не втрачати дані.

Розгляньмо рівні, яких має досягти один запит «видаліть мене»:

1. **М’яке видалення** — поширений шаблон, де встановлюють `IsDeleted = true`. Це *не* видалення: дані все ще є. М’яке видалення добре працює для скасування й посилальної цілісності, але стає пасткою відповідності вимогам, якщо на цьому зупинитися.
2. **Фізичне видалення** — справжнє вилучення рядка або його незворотне знеособлення.
3. **Резервні копії та знімки.** Щоночі створені резервні копії все ще містять дані людини. Зазвичай не можна й не слід вибірково редагувати резервні копії. Прийнятний підхід — задокументована політика: копії вилучаються після визначеного строку (наприклад, 35 днів), а після відновлення видалення застосовується повторно. Зафіксуйте це: аудитори приймають визначений процес, а не бездоганність.
4. **Похідні дані** — пошукові індекси, кеші, моделі читання, аналітичні сховища та журнали. Кожна копія також потребує обробки.

Практичний шаблон — **криптографічне знищення ключа**: шифруйте персональні дані кожного користувача окремим ключем, а для «видалення» знищуйте ключ. Шифротекст залишиться в резервних копіях, але його не можна прочитати. Так можна обійти неможливе редагування незмінних резервних копій.

```csharp
public async Task ForgetCustomerAsync(Guid customerId, CancellationToken ct)
{
    // 1. Hard-delete or anonymize primary records
    await _db.Customers
        .Where(c => c.Id == customerId)
        .ExecuteUpdateAsync(s => s
            .SetProperty(c => c.Email, _ => $"deleted+{customerId}@example.invalid")
            .SetProperty(c => c.FullName, _ => "[erased]")
            .SetProperty(c => c.HealthNotes, _ => (string?)null), ct);

    // 2. Destroy the per-user encryption key (crypto-shredding of anything encrypted with it)
    await _keyVault.PurgeUserKeyAsync(customerId, ct);

    // 3. Fan out to owning services / indexes / warehouse via an event
    await _bus.PublishAsync(new CustomerErased(customerId), ct);

    // 4. Record that erasure happened — the audit trail must survive the person
    await _audit.WriteAsync(AuditEvent.Erasure(customerId, actor: "dsr-pipeline"), ct);
}
```

Зверніть увагу на суперечність у кроці 4: людину видаляють, але *зберігають доказ* цього рішення. Доказ посилається на псевдонімний ID, а не на видалені персональні поля.

> **Пастка: м’яке видалення видають за відповідність вимогам.** Фільтр `WHERE IsDeleted = 0` задовольняє інтерфейс, але дані залишаються відновлюваними. Якщо процедура видалення закінчується на м’якому видаленні, ви не відповідаєте вимогам — лише приховали проблему від себе.

**Згода.** Якщо згода є правовою підставою, її потрібно надавати вільно й усвідомлено, для конкретної мети та *так само легко відкликати, як надати*. Технічно зберігайте згоду як версійований запис із часовою позначкою (мета, версія політики, час і спосіб), а не як один логічний прапорець. Після відкликання обробка має справді зупинитися, тож під час обробки треба вміти перевірити стан згоди.

**Строк зберігання та завдання очищення.** Дані не повинні зберігатися вічно «просто так». Визначте строк для кожної категорії даних і забезпечте його дотримання запланованими завданнями.

```csharp
// A hosted service that purges expired records on a schedule
public class RetentionPurgeService(IServiceProvider sp, ILogger<RetentionPurgeService> log)
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromHours(24));
        do
        {
            using var scope = sp.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var cutoff = DateTimeOffset.UtcNow.AddYears(-2); // policy: 24-month retention

            var purged = await db.SupportTickets
                .Where(t => t.ClosedOn < cutoff)
                .ExecuteDeleteAsync(stoppingToken);

            log.LogInformation("Retention purge removed {Count} tickets older than {Cutoff}",
                purged, cutoff);
        }
        while (await timer.WaitForNextTickAsync(stoppingToken));
    }
}
```

### Резидентність і суверенітет даних

Деякі закони вимагають зберігати дані про жителів країни в межах її кордонів. Це не проблема коду, яку можна виправити пізніше, а рішення про *топологію*. Воно визначає регіони хмари для розгортання, місця баз даних і резервних копій, а також де CDN кешує вміст. Якщо плануєте обслуговувати клієнтів з ЄС за вимог резидентності, обирайте регіони ЄС і переконайтеся, що журнали, копії та репліки аварійного відновлення теж залишаються в регіоні. Перенесення резидентності в систему з одним регіоном — це міграція, а не перемикач конфігурації.

Для передавання даних саме з ЄС до США **Рамкова угода ЄС–США про захист даних** (рішення про адекватність від липня 2023 року, наступник скасованої Privacy Shield) є чинним правовим механізмом; альтернативою залишаються стандартні договірні положення.

### Шифрування об’єднує ці вимоги

Шифрування — резервний захист для більшості перелічених вимог (інші розділи докладніше розглядають безпеку). Є два напрями:

- **Під час передавання** — TLS скрізь, зокрема між *внутрішніми* службами. «Воно за брандмауером» — не модель загроз.
- **У сховищі** — TDE бази даних, зашифровані диски й blob-сховища. Керовані хмарні бази дають змогу ввімкнути це прапорцем — користуйтеся ним. Для найчутливіших полів додайте шифрування на рівні застосунку, щоб навіть адміністратор бази з прямим доступом бачив шифротекст; це також дає змогу криптографічно знищити ключ.

Зберігайте ключі в керованому сховищі (Azure Key Vault, AWS KMS), а не в конфігурації чи коді. Ротуйте їх. **Ключ, закомічений у git, — це витік, який уже стався.**

### Журнал аудиту: хто, що і коли зробив

Від журналу аудиту залежать нормативні перевірки й реагування на інциденти. Він відповідає на запитання: *хто* виконав *яку дію* над *яким ресурсом*, *коли* і, бажано, *звідки*.

Що має містити подія аудиту:

- Ідентичність виконавця (користувач або суб’єкт-служба), а не просто «система».
- Дію та ідентифікатор цільового ресурсу.
- Часову позначку (UTC, за надійним годинником).
- Результат (успіх або помилка) та ID кореляції чи траси.
- Достатній контекст для відтворення подій, але **ніколи не самі чутливі дані.**

> **Пастка: журнали аудиту розкривають дані.** Журнал аудиту приваблює саме ті дані, які потрібно захищати. Записуйте *факт*, що медичну картку переглянули, і хто це зробив, — але не її вміст. Дотримуйтеся рекомендацій OWASP: не записуйте паролі, токени, повні номери карток чи ID сеансів; за замовчуванням приховуйте PII.

**Захист від змін і незмінність.** Журнал, який може редагувати зловмисник (або працівник у паніці), не допоможе розслідуванню. Техніки від простіших до надійніших:

- Сховище лише для додавання, без дозволів `UPDATE` чи `DELETE` для ролі застосунку.
- Рівні зберігання лише для запису (наприклад, blob-сховище з політикою незмінності чи юридичного утримання або bucket із режимом WORM).
- **Ланцюжок хешів** — кожен запис містить хеш попереднього; будь-яка зміна минулого розриває ланцюжок. Це недорогий доказ втручання без екзотичної інфраструктури.

```csharp
public record AuditEntry(long Seq, string Actor, string Action, string TargetId,
                         DateTimeOffset At, string PrevHash)
{
    public string Hash() => Convert.ToHexString(
        SHA256.HashData(Encoding.UTF8.GetBytes(
            $"{Seq}|{Actor}|{Action}|{TargetId}|{At:O}|{PrevHash}")));
}
```

Перевірити ланцюжок згодом просто: переобчислити хеші й порівняти. Розбіжність покаже, де саме сталося втручання.

### Псевдонімізація та анонімізація

Ці поняття часто плутають, хоча юридично різниця важлива.

- **Псевдонімізація** замінює ідентифікаційні поля токеном або ключем (наприклад, ім’я та email замінюють випадковим ID, а таблицю відповідності зберігають окремо). Якщо ви маєте таблицю, дані *можна* пов’язати знову. GDPR і далі вважає псевдонімізовані дані **персональними**: ризик знижується, але обов’язки залишаються.
- **Анонімізація** перетворює дані так, щоб ніхто, навіть ви, не міг розумними засобами знову ідентифікувати людей. Справді анонімізовані дані *не підпадають* під законодавство про приватність, але досягти цього складно. Видалення імені рідко достатньо: поєднання непрямих ідентифікаторів може розкрити особу. До такого рівня прагнуть за допомогою агрегації, узагальнення та *k*-анонімності.

> **Рекомендація:** використовуйте псевдонімізацію для зменшення масштабу наслідків у внутрішній аналітиці й інструментах підтримки, але не вважайте її звільненням від вимог. Це забезпечує лише справжня незворотна анонімізація — доведіть її, перш ніж так стверджувати.

### Секрети та перевірки доступу

Аудитори регулярно запитують: *хто має доступ до продакшен-даних* і *як контролюються секрети*?

- **Найменші привілеї** — інженери й служби отримують мінімально потрібні права. Широкі постійні права адміністратора — зауваження аудитора, яке лише чекає нагоди. Віддавайте перевагу тимчасовому підвищенню прав замість постійного доступу.
- **Перевірка доступу** — періодично (часто щокварталу) підтверджуйте, хто до чого має доступ, і відкликайте застарілі дозволи. Це нудно — і саме це аудитори SOC 2 перевіряють вибірково.
- **Керування секретами** — жодних секретів у коді, конфігураційних файлах чи змінних середовища, закомічених у репозиторій. Використовуйте сховище секретів, ротуйтe облікові дані й за можливості застосовуйте керовані ідентичності, щоб довготривалих секретів узагалі не було.

### Сертифікації: SOC 2 та ISO 27001

Зрештою вас залучать до сертифікації. Найчастіше трапляться дві:

- **SOC 2** — підтвердження аудитора, що засоби контролю безпеки, доступності, конфіденційності, цілісності обробки та приватності спроєктовані й *діють* протягом визначеного періоду. Тип II особливо зосереджений на *доказах за часом*.
- **ISO 27001** — міжнародний стандарт системи управління інформаційною безпекою (ISMS); сертифікація засвідчує систематичний, перевірений аудитом підхід до керування інформаційними ризиками.

**Що роблять інженери?** Сертифікат належить керівництву, але *докази* — ваша справа: обов’язкові перевірки коду й захист гілок, CI із перевірками безпеки, заявки на зміни з посиланнями на розгортання, експорти перевірок доступу, записи тестів відновлення резервних копій, параметри шифрування та приклади журналу аудиту. Урок для старшого інженера: **вбудуйте слід доказів у звичайний робочий процес** (шаблони PR, обов’язкові рецензенти, автоматичне журналювання), щоб «сезон аудиту» був запитом, а не авралом.

### Приватність у проєктуванні та DPIA

GDPR закріплює **приватність у проєктуванні та типових налаштуваннях**: про приватність дбають від першого рядка, а типові параметри мають забезпечувати найбільший захист. На практиці це означає мінімізувати збір, типово вимикати функції, рано застосовувати псевдонімізацію та визначати строки зберігання відразу, а не «прикручувати» приватність пізніше.

**DPIA (оцінка впливу на захист даних)** — структурований аналіз ризиків, який проводять *до* створення системи, що обробляє персональні дані у великому обсязі чи ризикованим способом. Навіть коли закон цього не вимагає, *підхід DPIA* — корисна звичка старшого інженера: перш ніж будувати функцію, з’ясуйте, які персональні дані проходять через неї, навіщо, хто їх бачить, як довго вони зберігаються та що найгірше станеться в разі витоку. Десять хвилин такого міркування під час проєктування запобігають дорогому переробленню.

## Частина B — Вартість хмари / FinOps

### Чому вартість — інженерна відповідальність

В епоху власних серверів потужності були проблемою капітальних витрат іншого відділу, яку вирішували за кілька місяців наперед. У хмарі *код кожного інженера витрачає гроші в реальному часі.* Необережний `SELECT *` у гарячому циклі, забутий `n2-highmem-16` або необмежений каскад викликів мікросервісів з’явиться в рахунку наступного місяця. Вартість стала нефункціональною вимогою, як затримка чи доступність; і, як їх, її дешевше врахувати одразу, ніж додавати пізніше.

**FinOps** — дисципліна фінансової відповідальності за хмарні витрати. Її культурна основа — три повторювані етапи:

1. **Інформування (видимість)** — кожен бачить вартість ресурсів і розуміє, хто витрачає кошти.
2. **Оптимізація** — скорочення марних витрат і добір ресурсів під реальний попит.
3. **Управління (відповідальність)** — команди сприймають витрати як звичайну інженерну метрику.

Зміна мислення, яку підтримують старші інженери: **вартість — спільна відповідальність інженерів, а не те, що фінанси зводять постфактум.**

### Куди насправді йдуть гроші

Неможливо оптимізувати те, чого не розумієш. Основні чинники вартості:

- **Обчислення** — віртуальні машини, контейнери, функції. Зазвичай найбільша й найпомітніша стаття; її найлегше надмірно збільшити «про всяк випадок».
- **Передавання даних / вихідний трафік — підступна стаття.** Передавання даних *з* регіону чи провайдера або між зонами доступності коштує грошей, тоді як вхідний трафік зазвичай безкоштовний. Міжзонна взаємодія служб, повернення великих наборів даних у власний дата-центр або неправильна конфігурація CDN, що оминає кеш, можуть непомітно стати основною частиною рахунку. **Вихідний трафік прихований у стрілках архітектурної схеми, а не в її блоках.**
- **Рівні сховищ** — ціна зберігання відрізняється. Гарячі/стандартні рівні дорожчі за гігабайт, але читання дешевше; холодні/архівні дешевші для зберігання, проте стягують плату за отримання даних і додають затримку. Зберігати холодні журнали в гарячому сховищі — марна витрата.
- **Надбавка за керовані служби** — керована база, черга чи пошукова служба заощаджує операційну роботу, але коштує дорожче за необроблені обчислювальні ресурси. Часто це виправдано — але рішення має бути свідомим, а не автоматичним.
- **Невикористані й покинуті ресурси** — найбільше джерело марних витрат: середовища розробки, що працюють уночі, непідключені диски, покинуті балансувальники, кластери з надмірною потужністю та 10% використання. Нічого не *зламалося* — гроші просто витікають.

### Тегування й розподіл вартості

Якщо не можна віднести витрати до команди, служби чи середовища, відповідальності немає: витрати залишаються спільною купою, якою ніхто не опікується. **Тегування** (мітки на кожному ресурсі) — основа видимості FinOps. Дотримуйтеся єдиної таксономії: `team`, `service`, `environment`, `cost-center`. Зробіть теги обов’язковими політикою хмари (Azure Policy, AWS SCP чи Config), щоб ресурси без тегів позначалися або блокувалися під час створення.

> **Рекомендація:** вважайте тегування *вимогою платформи з першого дня*, забезпеченою інфраструктурою як код, а не проєктом очищення. Ретроспективно позначати тисячі ресурсів нестерпно; політика, що відхиляє ресурси без тегів, автоматично підтримує чисті дані.

### Узгодження пропозиції з попитом

Коли витрати стали видимими, скористайтеся важелями для їх зниження:

- **Добір розміру** — обирайте розміри екземплярів за *виміряним* використанням, а не здогадками. Якщо CPU віртуальної машини тримається на 8%, а пам’ять — на 20%, вона завелика на кілька розмірів. Перевіряйте періодично: навантаження змінюються.
- **Автомасштабування** — масштабуйтеся горизонтально за попитом, щоб платити за пікову потужність лише під час піку. Поєднуйте його з масштабуванням до нуля для нерівномірного навантаження чи розробки та вимикайте непродакшен-середовища на ніч і вихідні (приблизно 65% економії на цих ресурсах).
- **Моделі купівлі** — оплата за фактичне використання найгнучкіша й найдорожча. Для стабільного базового навантаження **зарезервовані екземпляри / плани заощаджень** фіксують зобов’язання на 1–3 роки в обмін на велику знижку. Для переривних і відмовостійких завдань (пакетна обробка, CI, робочі процеси без стану) **spot/preemptible** дають найбільші знижки, але екземпляр можуть вилучити. Досвідчений підхід — *портфель*: резервувати передбачувану основу, оплачувати за фактом змінну середину, а для витривалих пікових завдань використовувати spot.

### Модель вартості безсерверних служб

Безсерверні служби (Azure Functions, AWS Lambda) змінюють модель: оплата нараховується за запит і час виконання, а простій нічого не коштує. Це добре для нерівномірних навантажень із низьким середнім трафіком і засобів розробки — не потрібно платити за віртуальну машину, яка просто чекає.

Однак досвідчений інженер зважає на межі моделі:

- **Холодні запуски** — після простою перший запит чекає, поки запускається середовище виконання. Для .NET затримка може бути помітною; trimming, ReadyToRun/AOT і підготовлена паралельність її зменшують, але *підготовлена паралельність знову створює постійні витрати*, частково нівелюючи заощадження.
- **Точка перетину** — оплата за запит дешева лише до певного обсягу. Стабільне навантаження з високою пропускною здатністю може коштувати *дорожче* на безсерверній службі, ніж на постійно ввімкненому контейнері правильного розміру. Розрахуйте точку перетину для *свого* трафіку, а не припускайте, що безсерверне рішення завжди дешевше.

### Архітектура як чинник вартості: балакучі служби та N+1

Саме тут проєктування застосунку впливає на рахунок і де досвідчені інженери додають найбільшу цінність.

- **Балакучі мікросервіси** — поділ системи на багато служб множить мережеві виклики. Кожен перехід додає затримку й, якщо перетинає зону чи регіон, *вартість вихідного трафіку*. Запит до дванадцяти служб, кожна з яких окремо звертається до бази й кешу, може коштувати на порядок більше за добре розміщений монолітний потік. Розміщуйте служби, що часто спілкуються, поруч, групуйте виклики й переглядайте межі, які змушують служби часто обмінюватися даними.
- **N+1 у масштабі** — класична проблема ORM N+1 (один запит для списку, потім по одному для кожного елемента) не є проблемою коректності, але стає катастрофою *вартості* у масштабі. Сторінка з тисячею елементів виконує 1001 запит, збільшує навантаження на базу та змушує перейти на дорожчий тариф. Проєкція й завчасне завантаження виправляють і затримку, і витрати: **оптимізація продуктивності й вартості зазвичай та сама.**

```csharp
// N+1: one query for orders, then one per order for its customer — 1 + N round-trips
var orders = await db.Orders.ToListAsync(ct);
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);   // lazy load fires a query each iteration

// Fixed: a single projected query returns exactly the columns needed
var rows = await db.Orders
    .Select(o => new { o.Id, CustomerName = o.Customer.Name })
    .ToListAsync(ct);
```

### Кешування для контролю витрат

Кешування зазвичай вважають засобом зниження затримки, але воно так само знижує вартість. Кожен запит із локального чи розподіленого кешу — це невиконаний запит до бази, невикликаний сервіс, а для відповіді CDN — байти, які не передано з джерела. Добре налаштований CDN для статичного й напівстатичного вмісту знижує і витрати на обчислення джерела, і плату за вихідний трафік. Компроміс — складність і застарівання; кешуйте там, де читань багато відносно записів і коротке застарівання прийнятне.

### Спостережуваність вартості: бюджети й сповіщення

Вимірюйте *вартість* так само, як затримку й помилки. Провайдери хмари пропонують **бюджети** зі сповіщеннями на порогах: створюйте їх для команд і служб за тегами та спрямовуйте сповіщення команді-власнику, а не у фінансову поштову скриньку, яку команда не читає. Додайте **виявлення аномалій**, щоб раптовий стрибок (завдання без обмежень, неправильно налаштоване автомасштабування, витік даних) викликав сповіщення протягом годин, а не з’явився в місячному рахунку. **Скоротіть зворотний зв’язок за витратами з місяця до дня — і марні витрати не встигатимуть накопичуватися.**

Для чіткої відповідальності показуйте вартість кожної служби на тих самих панелях, що й затримку та частоту помилок: команда бачитиме «ця функція коштує $X на тисячу запитів» поруч із SLO.

### Контрольний список FinOps для інженера

Застосовуйте під час кожної суттєвої зміни:

- [ ] Кожен створений ресурс **має теги** (команда, служба, середовище).
- [ ] Розмір екземплярів **підібрано** за реальним використанням, а не завищено навмання.
- [ ] Непродакшен-середовища **вимикаються** поза робочим часом або масштабуються до нуля.
- [ ] Стабільна базова потужність оплачується **зарезервованими планами / планами заощаджень**; витривалі завдання працюють на **spot**.
- [ ] Я знаю шляхи **вихідного трафіку** й уникаю непотрібного передавання між зонами, регіонами та провайдерами.
- [ ] Дані зберігаються на **правильному рівні**; холодні дані не лежать у гарячому сховищі.
- [ ] На гарячих шляхах немає **N+1** чи безпідставних **частих міжслужбових викликів**.
- [ ] **Кешування** застосовано там, де читань багато й допускається коротке застарівання.
- [ ] Для ресурсів, за які я відповідаю, є **бюджет і сповіщення**.
- [ ] Я знаходжу й видаляю створені мною **простійні та покинуті ресурси**.

> **Рекомендація.** Витрати — найпростіший початок консультативної розмови. Рахунок зрозумілий кожному; висновок «ваші непродакшен-середовища коштують [X] на місяць, хоча простоюють» керівник може використати без лекції з архітектури. Перевірка підписки клієнта за цим списком і звіт у грошах — невелике обмежене завдання, яке відкриває розмову про ширші проєктні питання. [Розділ 40](#chapter-40-lab-the-net-health-check) перетворює це на повну оцінку.

## Частина C — Екологічне ПЗ: ті самі важелі, ще один привід

Поруч із регулятором і фінансовим директором з’являється третя зацікавлена сторона. Добра новина: здебільшого їй потрібно те саме, що й фінансовому директорові.

**Зв’язок прямий.** Рахунок за хмару приблизно відображає оплату електроенергії, амортизації обладнання та дата-центру. Простійний екземпляр споживає електрику. Завелика віртуальна машина споживає її пропорційно розміру. Балакуча служба передає байти через комутатори, які теж споживають струм. Майже кожен важіль FinOps із частини B також зменшує викиди, тож внутрішню дискусію легко виграти: не треба обмінювати гроші на моральну користь.

Це формулювання важливе, бо навколо теми багато нечітких розмов. Ось інженерний погляд.

**Специфікація SCI (Software Carbon Intensity) Green Software Foundation** дає практичну модель:

```
  SCI  =  ( E × I  +  M )  per unit of work
           │   │      │
           │   │      └── embodied carbon: the emissions from manufacturing
           │   │          the hardware, amortized over its useful life
           │   └───────── carbon intensity of the grid supplying the region,
           │              in gCO₂e/kWh — varies by location and by hour
           └───────────── energy your software consumed, in kWh
```

Із формули випливають три наслідки, і вони не такі, як багато хто очікує.

**1. Ефективність допомагає, але завантаження — більше.** Зменшити час CPU вдвічі на сервері, який працює весь день, означає менше заощадження, ніж здається: навіть у простої сервер споживає значну частку пікової потужності. Значення `E` справді зменшується, коли працює *менше машин із вищим завантаженням*: щільніше розміщення, автомасштабування, яке справді зменшує ресурси, масштабування до нуля для нерівномірних навантажень і вимкнення непродакшен-середовищ на ніч. Наведений вище контрольний список добору розміру — вже готова програма зниження викидів.

**2. Де й коли працює система важливіше за те, як написано код.** Вуглецева інтенсивність `I` у різних регіонах хмари може відрізнятися в кілька разів і змінюватися щогодини в межах регіону, коли слабшає вітер і навантаження беруть на себе газові електростанції. Перенесення нічного пакетного завдання в регіон із низькою інтенсивністю викидів або на час, коли мережа найчистіша, може за місяць скоротити їх більше, ніж будь-яка зміна коду. Це **планування з урахуванням викидів**; для нечутливих до затримки завдань (пакетна звітність, навчання моделей, резервне копіювання, великі передавання даних) воно майже безкоштовне. Провайдери публікують регіональні показники, а Carbon Aware SDK Green Software Foundation надає прогнози для планування.

> **Нюанс.** Регіон із найнижчою вуглецевою інтенсивністю часто не збігається з місцем перебування користувачів, а інколи закон забороняє там зберігати дані (див. *Резидентність і суверенітет даних* вище). Розміщення з урахуванням викидів застосовуйте до *переносних* навантажень. Не переміщуйте чутливу до затримки службу чи регульований набір даних заради енергетичної структури регіону.

**3. Втілений вуглець заохочує ефективно завантажувати обладнання й довше ним користуватися.** Значення `M` фіксується під час виробництва обладнання і для сучасних серверів становить значну частину викидів за весь строк служби. Це суперечить поширеній інтуїції: найекологічніше — *довго й інтенсивно використовувати сервер*, а не замінювати його трохи ефективнішою моделлю. На рівні застосунку це означає віддавати перевагу вищій щільності — більшій кількості роботи на вузол — замість збільшення кількості вузлів.

**Які рішення .NET справді мають значення.** Важливо чесно оцінювати масштаб впливу, інакше можна витратити спринт без результату:

- **Native AOT і trimming** ([розділ 17](#chapter-17-runtime-internals-and-performance)) скорочують час запуску та використання пам’яті. Для довготривалої служби ефект невеликий. Для безсерверної функції з мільйонами викликів або навантаження, що часто масштабується до нуля й назад, коротший холодний запуск зменшує оплачуваний час обчислень і споживання енергії — ось де це окупається.
- **Зменшення виділень пам’яті** має значення тоді, коли змінює кількість екземплярів або поріг масштабування. Зменшення виділень у службі, де CPU не був вузьким місцем, — хороша інженерна робота без аргументу про енергію; протилежне твердження дискредитує тему.
- Справжні цілі — **запит N+1 і балакуча служба** з розділу про вартість. Вони множать роботу, а саме множники змінюють `E`.
- **Кешування** з розділу про вартість — найочевидніша перемога: невиконана робота не споживає енергії.

**Велике питання про ШІ.** Інференс уже становить значну частку обчислень багатьох організацій і споживає особливо багато енергії: один запит до великої моделі може потребувати на порядки більше енергії, ніж показ вебсторінки. Тож усе про механіку вартості в [розділі 33](#chapter-33-building-ai-powered-systems) є й енергетичним рішенням. Пріоритети ті самі: найменша модель, яка проходить оцінювання; агресивне кешування (влучання в кеш — запит, якого не було); пакетне виконання некритичних до часу завдань; бюджет міркування лише там, де воно корисне; обмеження циклів агентів. Вибрати малу модель для звичайної класифікації замість гранично великої — імовірно, найважливіше енергетичне рішення більшості команд застосунків цього року.

**Наближається звітність.** У ЄС поступово вводяться вимоги CSRD щодо звітності зі сталого розвитку для великих компаній. Як і з правилами приватності в частині A, інженери відчувають це опосередковано: хтось із фінансів або юридичного відділу просить цифри про системи. Відповісти можуть команди, які вже позначили ресурси за службою й командою (частина B), адже викиди розподіляються так само, як витрати. Виконали тегування для FinOps — виконали більшість роботи з даними сталого розвитку.

> **Рекомендація.** Вважайте викиди *похідною* метрикою, а не приводом будувати окрему панель. Розраховуйте їх з даних тегування й завантаження, які вже збираєте, та показуйте поруч із витратами. Команда, яка в одному поданні бачить «ця служба коштує €4 200 на місяць і створює 1,1 т CO₂e», ухвалюватиме однакові рішення з обох причин. Окрема панель сталого розвитку без власника стане слайдом у річному звіті.

> **Пастка — метрики без змісту.** Скептично ставтеся до заяв «вуглецево нейтральний», що цілком ґрунтуються на придбаних компенсаціях; до панелей провайдерів, які показують викиди *за ринковим методом* (сертифікати відновлюваної енергії, а не фактичну електрику, спожиту вашим навантаженням) без *показників за місцем споживання*; і до метрик, які поліпшуються, якщо нічого не робити. Надійні показники нудні: завантаження, години роботи екземплярів, кВт·год, якщо доступні, та вартість як наближення решти.

## Об’єднання трьох тем

Відповідність вимогам, вартість і викиди здаються проблемами різних відділів — юристів, бухгалтерів і звітності зі сталого розвитку. Але основа спільна: **усі три винагороджують точне знання про наявні дані й ресурси, причину їх існування та можливість це довести.** Добре класифіковану, позначену тегами й описану в інвентарі систему легше перевіряти на приватність, дешевше експлуатувати й, як показує частина C, екологічніше обслуговувати: на всі три питання відповідає один інвентар. Перевага старшого інженера — вважати регулятора й фінансового директора повноцінними зацікавленими сторонами від етапу проєктування, адже додавати їхні вимоги пізніше завжди болючіше й дорожче.
