# Розділ 7: Доступ до даних

Майже кожен нетривіальний застосунок під своїми функціями є механізмом безпечного й швидкого переміщення даних до бази й назад. Безпомилкова бізнес-логіка не врятує рівень даних, який виконує тисячу запитів замість одного, сканує індекс, у якому мав би шукати, або втрачає оновлення одного користувача через зміну іншого. Цей розділ навчить вас писати й переглядати доступ до даних так, щоб надсилати очікуваний SQL: ви читатимете фактичний план запиту й пояснюватимете, чому кожен оператор індексу шукає чи сканує; писатимете запити EF Core, для яких кількість звернень до бази можна порахувати до запуску; і захищатимете рядки від втрати оновлень.

Розгляд починається з бази даних і рухається вгору. Спочатку — схема й SQL (нормалізація, об’єднання, індекси, execution plans (плани виконання), транзакції), адже EF Core генерує SQL, і оцінити його результат можна лише навчившись читати його. Потім — сам EF Core: відстеження змін, завантаження пов’язаних даних і проблема N+1, проєкції, масові записи й каскадні операції, час життя `DbContext`. Паралельність спирається на обидві теми: маркер паралельності — це стовпець у частині `WHERE` команди `UPDATE`. Сирий SQL і Dapper допоможуть із запитами, які ORM не має писати; кешування — із запитами, які взагалі не слід виконувати; міграції покажуть, як змінювати схему в pipeline (конвеєрі). У частині 2 тему розглянуто глибше в [Розділі 18: Дані поглиблено](#chapter-18-data-in-depth): скомпільовані запити, масові вставлення, планувальник PostgreSQL, Redis, NoSQL і масштабування.

## Проєктування бази даних і нормалізація

Якісне проєктування схеми запобігає цілим класам помилок. **Нормалізація** — це принцип структурування таблиць, за якого кожен факт зберігається лише один раз.

- **Перша нормальна форма (1NF):** кожен стовпець містить одне атомарне значення — без списків через кому й повторюваних груп. Один номер телефону на стовпець або окрема пов’язана таблиця для кількох номерів.
- **Друга нормальна форма (2NF):** 1NF і залежність кожного неключового стовпця від *усього* первинного ключа (це важливо для складених ключів). Жоден стовпець не повинен залежати лише від частини ключа.
- **Третя нормальна форма (3NF):** 2NF і відсутність залежності неключового стовпця від іншого неключового стовпця (тобто *транзитивної* залежності). Якщо зберігати `CustomerId` і `CustomerCity`, місто залежить від клієнта, а не від замовлення — винесіть його.

Інтуїція проста: **один факт — одне місце.** Коли клієнт змінює місто, ви маєте оновити один рядок, а не шукати кожне замовлення, де місто продубльовано. Через дублювання бази даних втрачають consistency (узгодженість).

**Зовнішні ключі й обмеження** змушують базу даних дотримуватися ваших правил, тож некоректні дані не зможуть з’явитися навіть через помилки застосунку:

```sql
CREATE TABLE Orders (
    Id INT PRIMARY KEY,
    CustomerId INT NOT NULL,
    Total DECIMAL(10,2) NOT NULL CHECK (Total >= 0),
    Status VARCHAR(20) NOT NULL DEFAULT 'Open',
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(Id)
);
```

Зовнішній ключ гарантує, що замовлення не посилатиметься на неіснуючого клієнта. `CHECK` гарантує відсутність від’ємних сум. Це ваш останній рубіж захисту, і в ньому не буває помилок, властивих коду застосунку.

### Коли денормалізувати

Нормалізація оптимізує коректність запису, але може сповільнити читання через потребу в багатьох об’єднаннях. **Денормалізація** навмисно дублює дані, щоб пришвидшити читання — наприклад, зберігає заздалегідь обчислений `OrderCount` у `Customer` замість підрахунку замовлень щоразу.

> **Рекомендація:** спершу нормалізуйте, а денормалізуйте лише тоді, коли цього вимагає виміряна проблема читання. Після цього ви відповідатимете за підтримання consistency дубльованих даних (тригерами, кодом застосунку або запланованими завданнями). Денормалізація — це позика продуктивності, яку повертають складністю.

## Основи SQL

Кожен виклик ORM зрештою перетворюється на SQL, тож починати слід саме з нього: що повертає об’єднання, як індекс знаходить рядки, як план показує спосіб пошуку і що гарантує транзакція. Досвідчений розробник читає згенерований SQL і execution plan, а не лише код C#.

### Об’єднання

Об’єднання поєднує рядки двох таблиць за пов’язаним стовпцем.

- **INNER JOIN** повертає лише рядки, що мають відповідник в обох таблицях.
- **LEFT (OUTER) JOIN** повертає всі рядки лівої таблиці, а там, де відповідника праворуч немає, підставляє NULL.
- **RIGHT JOIN** працює навпаки; **FULL OUTER JOIN** повертає рядки без відповідників з обох таблиць.

```sql
SELECT o.Id, c.Name
FROM Orders o
INNER JOIN Customers c ON c.Id = o.CustomerId
WHERE o.Status = 'Open';
```

`o.Customer.Name` у проєкції EF Core (див. нижче [Проєкції](#projections-select-only-what-you-need)) перетворюється саме на такий INNER JOIN або на LEFT JOIN, якщо зв’язок необов’язковий.

### Індекси: кластерні, некластерні, покривні

Індекс — це копія деяких стовпців таблиці, відсортована за ключем у B-дереві; завдяки йому рушій знаходить рядки, не читаючи всі сторінки. Без індексу умова `WHERE` у таблиці з мільйоном рядків прочитає їх усі: це **сканування таблиці**.

**Кластерний індекс** і *є* таблицею: на його сторінках-листках зберігаються самі рядки в порядку ключа. У таблиці може бути лише один такий індекс, зазвичай за первинним ключем (SQL Server робить первинний ключ кластерним, якщо кластерного індексу ще немає), а пошук за кластерним ключем — найдешевший із можливих.

**Некластерний індекс** — це окреме B-дерево, рядки-листки якого містять проіндексовані стовпці та ідентифікатор рядка: кластерний ключ або ID рядка для таблиці без кластерного індексу. Кожен стовпець, потрібний запиту додатково, спричиняє **пошук за ключем**: для кожного відповідного рядка доводиться ще раз спускатися кластерним індексом.

**Покривний індекс** усуває цей крок, *додаючи* зайві стовпці до своїх рядків-листків:

```sql
-- Query: SELECT Email, Name FROM Customers WHERE City = 'Berlin'
CREATE NONCLUSTERED INDEX IX_Customers_City
    ON Customers (City)
    INCLUDE (Email, Name);   -- now the index alone answers the query
```

Запит *покритий*: усе потрібне міститься в індексі, тож пошуків за ключем не буде. Оскільки кластерний ключ входить до кожного некластерного індексу, запит `SELECT Id FROM Customers WHERE Email = @e` покриває вже сам індекс за `Email`, а широкий кластерний ключ збільшує кожен інший індекс.

> **Зверніть увагу.** **Чому складений індекс працює лише для свого лівого префікса.** Індекс за `(City, CreatedAt)` відсортовано за `City`, а за `CreatedAt` — лише всередині кожного міста, як телефонний довідник, спершу впорядкований за прізвищем, а потім за ім’ям. Для пошуку потрібен один неперервний діапазон у цьому порядку:
>
> - `City = @c` — один неперервний блок: пошук.
> - `City = @c AND CreatedAt >= @d` — один діапазон усередині цього блока: пошук за обома стовпцями; рядки повертаються в порядку дат, тож для `ORDER BY CreatedAt` сортування не потрібне.
> - Самої умови `CreatedAt >= @d` недостатньо для діапазону: рядки розміщені в блоках усіх міст, тому рушій сканує весь індекс і фільтрує результат.
> - У `(CreatedAt, City)` діапазон за *першим* стовпцем робить другий непридатним для пошуку: у межах діапазону дат міста не впорядковані. SQL Server переходить до початку діапазону й перевіряє `City` в кожному рядку як залишкову умову `WHERE:` оператора пошуку, читаючи всі рядки періоду, щоб залишити одне місто.
>
> Отже: спершу стовпці рівності, потім один стовпець діапазону або сортування. Переконайтеся, що кожен стовпець, за яким ви очікуєте пошук, є в умові пошуку плану. У SQL Server 2022 CU27 (200 000 рядків, 4 vCPU, кеш прогрітий) умова `CreatedAt >= @p` просканувала `(City, CreatedAt)` із 712 логічними читаннями, тоді як `City = @p AND CreatedAt >= …` знайшла потрібне за 3 ([`seek-vs-scan.txt`](https://github.com/malyna2/dotnet-handbook/blob/main/verify/path/reference-runs/seek-vs-scan.txt)). Крок 6 у [Розділі 19: Лабораторна робота з повільними запитами](#chapter-19-the-slow-query-lab-reading-execution-plans) вимірює неправильний порядок стовпців у PostgreSQL.

> **Пастка:** індекси пришвидшують читання, але сповільнюють запис, бо кожен `INSERT`/`UPDATE`/`DELETE` має їх оновити. Не індексуйте всі стовпці. Індексуйте ті, за якими фільтруєте, об’єднуєте й сортуєте, та вимірюйте результат.

### Execution plans

Execution plan — це стратегія рушія для запиту: які індекси читати, у якому порядку об’єднувати таблиці, виконувати пошук чи сканування. **Пошук в індексі** переходить до одного неперервного діапазону індексу; **сканування індексу** читає його весь (сканування кластерного індексу є скануванням таблиці). Сканування великої таблиці з вибірковим фільтром зазвичай указує на відсутній індекс або умову, яку індекс не може використати.

Читайте *фактичний* план. У SSMS увімкніть *Include Actual Execution Plan* (Ctrl+M); у скрипті — `SET STATISTICS XML ON` або `SET STATISTICS PROFILE ON`. `SET SHOWPLAN_ALL ON` і розрахунковий план не виконують запит, тож у них немає фактичної кількості рядків. Додайте `SET STATISTICS IO ON`, щоб отримати **логічні читання** для кожної таблиці: кількість сторінок по 8 КБ, до яких запит звернувся в пам’яті. Вони вимірюють обсяг роботи й, на відміну від мілісекунд, однакові на ноутбуці та сервері. Потім шукайте сканування під вибірковим фільтром, пошуки за ключем для багатьох рядків, оцінки, далекі від фактичної кількості рядків, і попередження.

Пошук за умовою можливий лише тоді, коли вона **SARG-сумісна**: порівнює саме збережений стовпець зі значенням. Якщо обгорнути стовпець у функцію (`LOWER(Email)`, `YEAR(CreatedAt) = 2026`), обчислювати з ним або починати `LIKE` зі знака `%`, рушію доведеться обчислити вираз для кожного рядка й виконати сканування. Перепишіть умову, залишивши стовпець без змін (`CreatedAt >= '2026-01-01' AND CreatedAt < '2027-01-01'`), або проіндексуйте вираз (обчислюваний стовпець у SQL Server, індекс за виразом у PostgreSQL).

> **Зверніть увагу.** **`string` у .NET у порівнянні зі стовпцем `varchar` може перетворити пошук на сканування.** SqlClient і Dapper надсилають `string` із C# як `nvarchar`; так само EF Core поводиться з властивістю, зіставленою з Unicode (типове налаштування). `nvarchar` має вищий пріоритет типу даних, тож SQL Server перетворює *стовпець* через `CONVERT_IMPLICIT(nvarchar(100),[Email],0)`, а не параметр. Чи вдасться після цього пошук, залежить від сортування стовпця:
>
> - **За SQL-сортування**, `varchar` порівнюється за власними правилами сортування, а `nvarchar` — за правилами Unicode; порядки відрізняються: `'a-c' < 'ab'`, але `N'a-c' > N'ab'`. Порядок `varchar` в індексі не може відповісти на перетворене порівняння, тому план сканує індекс, а в XML-плані з’являється `<PlanAffectingConvert ConvertIssue="Seek Plan" …>`. Приклад — `SQL_Latin1_General_CP1_CI_AS`: типове налаштування для інсталяцій зі стандартною англійською США та сортування нової бази Azure SQL.
> - **За сортуванням Windows** (`Latin1_General_CI_AS`) обидва типи дотримуються однакових правил, тому оптимізатор обчислює діапазон пошуку за параметром (`GetRangeThroughConvert` у плані) і виконує пошук. Саме тому той самий код швидкий в одній базі та повільний в іншій.
>
> У SQL Server 2022 CU27 (16.0.4295.3, 200 000 рядків, 4 vCPU, прогрітий кеш) параметр `nvarchar` спричинив сканування індексу й 888 логічних читань, а `varchar` — пошук в індексі й 3 читання; за сортуванням Windows параметр `nvarchar` також прочитав 3 ([`seek-vs-scan.txt`](https://github.com/malyna2/dotnet-handbook/blob/main/verify/path/reference-runs/seek-vs-scan.txt), [`collation.txt`](https://github.com/malyna2/dotnet-handbook/blob/main/verify/path/reference-runs/collation.txt)). Виправлення — задати параметр того самого типу, що й стовпець: у EF Core — `.IsUnicode(false).HasMaxLength(100)` для властивості (тоді `ToQueryString()` показує `DECLARE @email varchar(100)` замість `nvarchar(4000)`); у Dapper — `new DbString { Value = email, IsAnsi = true, Length = 100 }`; в ADO.NET — `SqlDbType.VarChar`. Або зробіть стовпець типу `nvarchar`, щоб обидві сторони збігалися.

Плани варто навчитися читати системно, а не лише розпізнавати знайомі шаблони. Найпростіше вчитися на PostgreSQL: результат `EXPLAIN` — звичайний текст, який показує і те, чого рушій *очікував*, і те, що справді *відбулося*. У [Розділі 18: Дані поглиблено](#chapter-18-data-in-depth) план розглядається рядок за рядком, а [Розділ 19](#chapter-19-the-slow-query-lab-reading-execution-plans) — це практична лабораторна робота.

### Транзакції та ACID

Транзакція об’єднує команди, які успішно виконуються або скасовуються як одне ціле. Абревіатура ACID позначає чотири гарантії:

- **Атомарність** — фіксуються всі команди або жодна. Платіж не може бути переказаний лише частково.
- **Consistency** — база даних переходить з одного допустимого стану в інший, дотримуючись обмежень.
- **Ізоляція** — паралельні транзакції не псують одна одну (рівень можна налаштувати, див. нижче).
- **Довговічність** — після фіксації зміна переживає аварійне завершення.

```sql
BEGIN TRANSACTION;
    UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
    UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
COMMIT;   -- both or neither; ROLLBACK undoes everything
```

EF Core обгортає команди одного виклику `SaveChanges` в одну транзакцію, тож за замовчуванням одиниця роботи виконується повністю або не виконується зовсім. Два виклики `SaveChanges` — це дві транзакції: якщо друга зазнає невдачі, перша залишається зафіксованою.

### Рівні ізоляції

Ізоляція — це регулятор компромісу між коректністю та паралельністю. Послаблення дає змогу одночасно виконувати більше транзакцій, але допускає аномалії:

- **Брудне читання** — ви читаєте незавершену зміну іншої транзакції, яку згодом можуть скасувати.
- **Неповторюване читання** — ви читаєте рядок двічі й отримуєте різні значення, бо між читаннями інша транзакція його оновила.
- **Фантомне читання** — ви двічі виконуєте той самий запит за діапазоном і бачите нові рядки, вставлені іншою транзакцією.

Чотири стандартні рівні від найслабшого до найсуворішого:

| Рівень | Брудне | Неповторюване | Фантомне |
|---|---|---|---|
| Read Uncommitted | можливе | можливе | можливе |
| Read Committed (типовий) | унеможливлено | можливе | можливе |
| Repeatable Read | унеможливлено | унеможливлено | можливе |
| Serializable | унеможливлено | унеможливлено | унеможливлено |

Serializable — найбезпечніший рівень, але він створює найбільше блокувань і найбільше зменшує паралельність. Більшість систем працює з Read Committed і посилює ізоляцію окремих транзакцій, коли цього вимагає коректність. (У SQL Server також є ізоляція `SNAPSHOT`, яка використовує версії рядків, щоб забезпечити узгоджене читання без блокування записувачів.)

### Deadlock

Deadlock (взаємне блокування) виникає, коли транзакція A утримує блокування, потрібне B, а B утримує блокування, потрібне A: утворюється циклічне очікування, у якому обидві чекають безкінечно. База даних виявляє цикл і перериває одну транзакцію («жертву»), яка завершується помилкою. Типова причина — два шляхи коду, які блокують ті самі рядки **в різному порядку**.

> **Рекомендація:** у всьому застосунку звертайтеся до таблиць і рядків **у сталому порядку**, тримайте транзакції короткими й будьте готові перехопити помилку deadlock (помилка SQL Server 1205) та повторити операцію.

## Entity Framework Core: об’єктно-реляційний відображувач

Тепер, коли ми розглянули SQL, можна перейти до ORM над ним. Завдання ORM — з’єднати два світи, що мислять по-різному. Код C# оперує об’єктами, посиланнями й колекціями. Реляційна база даних — таблицями, рядками й зовнішніми ключами. EF Core перекладає між ними. Небезпека в тому, що цей переклад настільки *непомітний*, що легко забути про нього; усі проблеми продуктивності EF виникають через те, що доступ до властивості або `foreach` може непомітно стати окремим зверненням до бази даних.

### DbContext і відстеження змін

`DbContext` — серце EF Core. Думайте про нього як про поєднання **одиниці роботи** й **сеансу**: він представляє одну логічну розмову з базою даних. Він зберігає `DbSet<T>` для кожного типу сутності, перетворює LINQ на SQL і, що найважливіше, відстежує зміни.

```csharp
public class ShopContext : DbContext
{
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();

    protected override void OnConfiguring(DbContextOptionsBuilder options)
        => options.UseSqlServer("Server=.;Database=Shop;Trusted_Connection=True;");

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Order>()
            .HasOne(o => o.Customer)
            .WithMany(c => c.Orders)
            .HasForeignKey(o => o.CustomerId);
    }
}
```

Коли ви завантажуєте сутність, контекст зберігає **знімок** її початкових значень у внутрішній структурі, яка називається засобом відстеження змін. Під час виклику `SaveChanges()` EF порівнює поточний стан кожної відстежуваної сутності зі знімком, визначає змінені властивості й генерує мінімально необхідні команди `INSERT`, `UPDATE` або `DELETE`.

```csharp
using var ctx = new ShopContext();
var customer = ctx.Customers.Single(c => c.Id == 42);
customer.Email = "new@example.com";   // no SQL yet — just a change in memory
ctx.SaveChanges();                     // now EF emits: UPDATE Customers SET Email=... WHERE Id=42
```

Зверніть увагу: ви не вказували EF зберегти клієнта. Він зрозумів це сам, бо відстежував його. Це зручно, але має ціну: зберігання знімків кожної завантаженої сутності потребує пам’яті й ресурсів процесора. Кожна сутність проходить через п’ять станів — `Added`, `Unchanged`, `Modified`, `Deleted`, `Detached`; їх можна переглянути через `ctx.Entry(customer).State`.

> **Рекомендація:** створюйте `DbContext` на короткий час. Це одиниця роботи для *однієї* операції (зазвичай одного вебзапиту), а не довготривалий кеш. Контекст, який живе годинами, накопичує відстежувані сутності й стає джерелом витоку пам’яті та помилок коректності.

### Час життя DbContext і connection pool

Відкриття фізичного з’єднання з базою даних дороге: потрібні TCP-рукостискання й автентифікація. **Connection pool (пул з’єднань)**, типово ввімкнений в ADO.NET, зберігає набір відкритих з’єднань і видає їх на вимогу, тому «відкрити» з’єднання зазвичай означає позичити вільне. Тому відкривайте з’єднання якомога пізніше й закривайте якомога раніше: ви берете його зі спільного обмеженого пулу.

`DbContext` **не є потокобезпечним** і має мати **обмежений час життя** — один екземпляр на запит. `AddDbContext` реєструє його з таким часом життя, як і потрібно:

```csharp
builder.Services.AddDbContext<ShopContext>(o =>
    o.UseSqlServer(connectionString));   // scoped: one per HTTP request
```

> **Критична пастка:** ніколи не впроваджуйте `DbContext` у сервіс **singleton**. Singleton переживає область запиту й спільно використовуватиме один контекст для всіх паралельних запитів — це катастрофа для потокобезпечності й джерело дивних періодичних помилок. Це захоплена залежність із [Розділу 3](#captive-dependencies-the-classic-di-bug). Якщо singleton потрібні дані, впровадьте `IDbContextFactory<T>` і створюйте контекст для кожної операції.

Для дуже високої пропускної здатності `AddDbContextPool` повторно використовує *екземпляри* контексту (а не лише з’єднання), скидаючи їхній стан між запитами й уникаючи повторних витрат на налаштування:

```csharp
builder.Services.AddDbContextPool<ShopContext>(o =>
    o.UseSqlServer(connectionString), poolSize: 128);
```

Але контексти з пулу повторно використовуються, тому ніколи не зберігайте стан конкретного запиту в полі `DbContext`: він просочиться до наступного запиту, якому дістанеться цей екземпляр. Про поведінку connection pool, коли запитів більше, ніж з’єднань, ідеться в [Розділі 18](#connection-management-under-load).

### AsNoTracking: швидкість читання

Якщо ви лише читаєте дані, щоб надіслати їх далі (поширений сценарій у веб-API), відстеження змін узагалі не потрібне. `AsNoTracking()` наказує EF не створювати знімки. Для endpoints (кінцевих точок) із переважно читанням це помітно зменшує виділення пам’яті й підвищує швидкість.

```csharp
// Read-only query: no snapshots, faster, less memory.
var products = ctx.Products
    .AsNoTracking()
    .Where(p => p.IsActive)
    .ToList();
```

> **Практичне правило:** якщо не збираєтеся змінювати й зберігати сутності в тому самому контексті, додавайте `AsNoTracking()`. Його навіть можна зробити типовим режимом: `ctx.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;`.

### Завантаження пов’язаних даних: жадібне, відкладене, явне

У `Order` є `Customer` і колекція `OrderLines`. Як EF заповнює ці зв’язки? Є три стратегії, і неправильний вибір — найпоширеніша помилка продуктивності EF.

**Жадібне завантаження** отримує пов’язані дані в тому самому запиті за допомогою `Include`:

```csharp
var orders = ctx.Orders
    .Include(o => o.Customer)
    .Include(o => o.Lines)
        .ThenInclude(l => l.Product)
    .Where(o => o.Status == OrderStatus.Open)
    .ToList();
```

**Явне завантаження** навмисно завантажує зв’язок за потреби за допомогою видимого виклику методу:

```csharp
var order = ctx.Orders.Single(o => o.Id == id);
ctx.Entry(order).Collection(o => o.Lines).Load();   // explicit, one extra query on purpose
```

**Lazy loading (відкладене завантаження)** автоматично завантажує зв’язок у момент звернення до навігаційної властивості. Для цього потрібні пакет `Microsoft.EntityFrameworkCore.Proxies`, віртуальні навігаційні властивості й `UseLazyLoadingProxies()`. Воно здається зручним, але є пасткою, як показано в наступному розділі.

### Проблема N+1: виявлення та усунення

Це характерна помилка продуктивності ORM. Розгляньмо виведення кожного замовлення разом з іменем його клієнта:

```csharp
var orders = ctx.Orders.ToList();          // 1 query: SELECT * FROM Orders
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);    // each access = 1 more query (lazy loading)
```

Якщо замовлень 500, виконається **1 + 500 = 501 запит**. Це проблема N+1: один запит для батьківських записів, а потім N запитів для дочірніх. За будь-якої мережевої затримки 501 обмін із базою може перетворити операцію тривалістю 5 мс на п’ятисекундну. Підступність у тому, що під час розробки з локальною базою й трьома рядками все здається справним.

Виправлення — заздалегідь повідомити EF, що саме вам потрібно:

```csharp
var orders = ctx.Orders
    .Include(o => o.Customer)   // one JOIN, one round trip
    .ToList();
foreach (var o in orders)
    Console.WriteLine(o.Customer.Name);   // already in memory, no query
```

> **Пастка: вимкніть lazy loading типово.** Саме воно найчастіше спричиняє випадкову проблему N+1. Багато досвідчених команд вимикають його повністю й вимагають від розробників явно визначати потреби в даних через `Include` або проєкції. Непомітна зручність, яка коштує 500 звернень до бази, — це не зручність.

### Проєкції: вибирайте лише потрібне

Часто вам узагалі не потрібні цілі сутності — достатньо кількох стовпців, сформованих у DTO. Проєкція через `Select` генерує коротший SQL, не завантажує невикористовувані стовпці й не потребує відстеження змін:

```csharp
var summaries = ctx.Orders
    .Where(o => o.Status == OrderStatus.Open)
    .Select(o => new OrderSummary(
        o.Id,
        o.Customer.Name,          // EF generates the JOIN automatically
        o.Lines.Sum(l => l.Price) // aggregated in SQL, not in C#
    ))
    .ToList();
```

EF перетворює `o.Customer.Name` на об’єднання, а `o.Lines.Sum(...)` — на агрегатну функцію SQL. Ви отримуєте рівно три запитані значення, обчислені базою даних. **Проєкція часто є найкращим розв’язанням проблеми N+1**, бо водночас обходить потребу і в жадібному завантаженні, і у відстеженні.

### Include та проєкція: Include непомітно ігнорується

`Include` і `Select` відповідають на те саме запитання — «які дані потрібні цьому запиту?» — але перемогти може лише один, і це завжди проєкція. `Include` — це інструкція щодо *створення сутностей*: «під час створення цих сутностей `Order` також створити їхні сутності `Customer` і налаштувати навігацію». Щойно запит завершується `.Select(...)` із типом, що не є сутністю, EF перестає створювати сутності `Order` і створює DTO, тож `Include` більше не має до чого приєднати дані. EF відкидає його без попередження, exception (винятку) чи сліду у згенерованому SQL.

Це не означає, що пов’язані дані зникнуть. У проєкції SQL JOIN формуються через *звернення до навігацій усередині `Select`*, а не через наведені вище Includes:

```csharp
var rows = ctx.Orders
    .Include(o => o.Customer)      // dead code: ignored, produces no SQL
    .Include(o => o.Approver)      // dead code: ignored, produces no SQL
    .Where(o => o.Status == OrderStatus.Open)
    .Select(o => new OrderRow(
        o.Id,
        o.Customer.Name,           // THIS generates the JOIN to Customers
        o.Approver.LastName))      // THIS generates the JOIN to Approvers
    .ToList();
```

Видаліть обидва рядки `Include` — і SQL залишиться побайтно ідентичним. Запит працює в обох випадках, саме тому цей шаблон проходить перевірку коду: Includes *здаються* важливими, рецензенти думають, що вони виконують жадібне завантаження, і ніхто не помічає, що вони не діють.

Чому це важливо не лише з погляду охайності:

- **Вводить в оману.** Спільний базовий запит на кшталт `AccessibleOrders()` із кількома Includes натякає: «викликачі отримають замовлення разом із клієнтами». Якщо кожен виклик завершується проєкцією, ця обіцянка ніколи не виконується. А коли хтось створить сутності безпосередньо (`.ToList()` без `Select`), Includes раптом *спрацюють*, і форма та вартість запиту несподівано зміняться.
- **Приховує справжню залежність.** Потрібні проєкції стовпці зазначено всередині `Select`. Розкидані над ним Includes — це шум; щоб зрозуміти, що насправді отримує запит, їх потрібно подумки порівнювати з проєкцією.

Практичне правило таке: запит або *створює сутності* (тоді зв’язки завантажуються через `Include`), або *формує проєкцію* (тоді тіло `Select` — єдине джерело істини, а Includes не діють). Оберіть один підхід для запиту й видаляйте Includes із будь-якого запиту, що завершується проєкцією.

> **Нюанс.** Є один exception: `Include` ігнорується лише тоді, коли проєкція не залишає типів сутностей. Якщо `Select` повертає сутність *усередині* оболонки — `.Select(o => new { Order = o, LineCount = o.Lines.Count })`, — сутність `Order` усе ще створюється, тому до неї застосовуються Includes. Важливо не те, «чи є Select», а те, «чи містить результат сутність, для якої задано Include».

### Розділені запити

Жадібне завантаження кількох колекцій через `Include` спричиняє проблему, що називається **декартовим вибухом**. Якщо замовлення має 10 рядків і 5 відправлень, один JOIN поверне 10 × 5 = 50 рядків, дублюючи дані замовлення для кожної комбінації. `AsSplitQuery()` наказує EF натомість виконати окремий запит для кожної колекції:

```csharp
var orders = ctx.Orders
    .Include(o => o.Lines)
    .Include(o => o.Shipments)
    .AsSplitQuery()   // 3 queries total, no row multiplication
    .ToList();
```

Компроміс такий: кілька мережевих обмінів проти одного роздутого набору результатів. Використовуйте розділені запити, коли включаєте кілька колекцій; залишайте один запит, коли включаєте посилання (зв’язки багато-до-одного) або одну невелику колекцію.

### Оновлення й видалення на основі наборів: ExecuteUpdate та ExecuteDelete

Відстеження змін — не той інструмент для масових записів. Оновлення 100 000 рядків через завантаження, зміну й `SaveChanges` означає створити 100 000 сутностей, зробити знімок кожної й виконати 100 000 окремих `UPDATE`. Починаючи з EF Core 7, `ExecuteUpdate` і `ExecuteDelete` перетворюють предикат LINQ безпосередньо на одну SQL-команду `UPDATE`/`DELETE` для набору рядків — нічого не завантажується й не відстежується:

```csharp
await ctx.Orders
    .Where(o => o.Status == OrderStatus.Abandoned && o.Created < cutoff)
    .ExecuteDeleteAsync();

await ctx.Products
    .Where(p => p.CategoryId == categoryId)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Price, p => p.Price * 0.9m));
```

> **Нюанс:** ці методи повністю обходять засіб відстеження змін. Сутності, які контекст уже відстежує, *не* оновлюються й непомітно застарівають; перехоплювачі `SaveChanges` та все, що на них підписано, як-от аудит чи надсилання доменних events (подій), не запускаються. Використовуйте ці методи для масового обслуговування й очищення, а не для записів, які мають бачити перехоплювачі.

Сучасне зіставлення EF також зменшує потребу звертатися до сирого SQL для роботи з формою даних: у EF Core 7 з’явилися **стовпці JSON** (агрегат, що належить сутності, зіставляється з одним стовпцем JSON, який усе ще можна запитувати через LINQ), а в EF Core 8 — **складені типи** (об’єкти-значення без ключа) і **колекції примітивів** (значення `List<int>`/`string[]` зберігаються вбудованими в JSON, а не в окремій таблиці).

### Каскадна поведінка: що відбувається з дочірніми рядками

Якщо видалити клієнта із замовленнями, із цими замовленнями щось має статися. У EF Core це визначає `DeleteBehavior`; плутанина виникає через те, що одне значення enum налаштовує **два різні механізми на двох різних рівнях**: зовнішній ключ, записаний EF у міграцію, і дії самого EF у пам’яті над дочірніми рядками, які він відстежує.

```
      ctx.Customers.Remove(customer)
                 │
                 ├─── EF, in memory ────►  what happens to LOADED children
                 │                          (the "Client..." half of the behaviour)
                 │
                 └─── SQL sent to DB ───►  what the FOREIGN KEY does
                                            (ON DELETE CASCADE / SET NULL / NO ACTION)
```

| `DeleteBehavior` | Зовнішній ключ у базі даних | Дії EF над *відстежуваними* дочірніми рядками |
|---|---|---|
| `Cascade` | `ON DELETE CASCADE` | Видаляє їх |
| `ClientCascade` | `ON DELETE NO ACTION` | Видаляє їх |
| `SetNull` | `ON DELETE SET NULL` | Задає FK значення null |
| `ClientSetNull` | `ON DELETE NO ACTION` | Задає FK значення null |
| `Restrict` | `ON DELETE RESTRICT` | Нічого не робить |
| `NoAction` | `ON DELETE NO ACTION` | Нічого не робить |
| `ClientNoAction` | `ON DELETE NO ACTION` | Нічого не робить, а EF пропускає власну перевірку consistency |

Правила EF за замовчуванням залежать від обов’язковості зв’язку: для **обов’язкового** зв’язку типовим є `Cascade` (рядок замовлення не може існувати без самого замовлення, тож його видалення прибирає й рядки), а для **необов’язкового** — `ClientSetNull` (дочірній рядок може залишитися з FK, що дорівнює null, але лише якщо EF його завантажив).

Останнє уточнення і є пасткою. `ClientSetNull` задає null для FK дочірніх рядків **у засобі відстеження змін**. Рядки, які залишилися в базі й не були завантажені, не змінюються; зовнішній ключ має значення `NO ACTION`, тому база даних відхилить видалення:

```csharp
// Children not loaded -> nothing for EF to fix up -> the FK stops the DELETE.
var customer = await ctx.Customers.SingleAsync(c => c.Id == id);
ctx.Customers.Remove(customer);
await ctx.SaveChangesAsync();   // DbUpdateException: FK violation

// Children loaded -> EF nulls their FK in the same SaveChanges.
var customer = await ctx.Customers
    .Include(c => c.Orders)
    .SingleAsync(c => c.Id == id);
ctx.Customers.Remove(customer);
await ctx.SaveChangesAsync();   // works
```

Те саме видалення успішне або невдале залежно від того, чи є трьома рядками вище `Include`. Це справді неочікуваний зв’язок і найпоширеніша причина ситуацій «у тесті працює, а в продакшені — ні» під час видалення: тести часто завантажують весь агрегат, а робочий код — ні.

`Restrict` і `NoAction` здаються взаємозамінними, але це не так. `Restrict` створює FK, який відхиляє видалення *негайно*, щойно змінюється рядок. `NoAction` відкладає перевірку до кінця команди, тому команда, яка одночасно видаляє батьківські й дочірні рядки, може пройти з `NoAction` і завершитися невдачею з `RESTRICT`. PostgreSQL точно дотримується цієї відмінності; вона важлива й для відкладених обмежень, де `NO ACTION` можна перенести на момент фіксації, а `RESTRICT` — ні.

Ще дві особливості, які варто знати заздалегідь:

**Розрив обов’язкового зв’язку видаляє дочірній рядок.** Видалення елемента з `order.Lines` не лише очищує FK: за обов’язкового зв’язку дочірня сутність стає сиротою, і EF видаляє її. Усередині агрегату це зазвичай очікувана поведінка, але тривожна, якщо зв’язок помилково зробили обов’язковим.

**`ExecuteDelete` узагалі не запускає каскад в EF.** Він видає одну команду `DELETE` і залишає рішення базі даних, тож працює лише за наявності в схемі справжнього `ON DELETE CASCADE`. Якщо модель використовує `ClientCascade` (який створює `NO ACTION`), додане заради продуктивності масове видалення завершиться порушенням FK саме для рядків, які раніше оброблялися шляхом із відстеженням:

```csharp
// Fine with DeleteBehavior.Cascade. FK violation with ClientCascade.
await ctx.Customers.Where(c => c.LastSeen < cutoff).ExecuteDeleteAsync(ct);
```

> **Нюанс:** SQL Server відмовляється створювати **кілька каскадних шляхів** до тієї самої таблиці (помилка 1785): якщо два зв’язки можуть каскадно вести до `OrderLines`, міграція завершиться невдачею. Виправлення — задати для одного шляху `NoAction` і видаляти ці рядки явно. У PostgreSQL такого обмеження немає; це одна з непомітних відмінностей, що проявляються під час перенесення кодової бази між цими системами.

М’яке видалення теж має свою пастку: глобальний фільтр запиту, що приховує рядки з `IsDeleted`, **не** виконує каскад. М’яке видалення батьківського рядка залишає дочірні видимими й пов’язаними з батьківським записом, якого решта застосунку не бачить. Якщо м’яко видаляєте корінь агрегату, видаляйте так само весь агрегат — окремою командою `ExecuteUpdate` для кожної дочірньої таблиці або доменним методом, що керує всією операцією.

> **Рекомендація:** дозволяйте каскадне видалення лише *всередині* агрегату, ніколи — через межі агрегатів (визначення агрегатів наведено в [Розділі 21: Архітектура](#chapter-21-architecture)). Видалення замовлення має видаляти його рядки, але ніколи не повинно непомітно видаляти рахунки клієнта. Явно задавайте межу через `Restrict`, а не покладайтеся на домовленість за замовчуванням, щоб випадковий каскад спричинив явну помилку, а не втрату даних, виявлену за місяць.

## Паралельність: оптимістичне чи песимістичне керування

Рівні ізоляції визначають, що бачать паралельні транзакції, але не зупиняють найпоширенішу помилку вебзастосунків. Коли двоє користувачів одночасно редагують той самий запис, один може непомітно перезаписати зміни іншого — це проблема **втраченого оновлення**, адже читання й запис кожного користувача відбуваються в окремих запитах і не охоплюються однією транзакцією. Є два підходи до її розв’язання.

**Песимістичне блокування** виходить із того, що конфлікти ймовірні: заблокуйте рядок під час читання, щоб ніхто інший не зміг змінити його до завершення операції (`SELECT ... FOR UPDATE`). Це безпечно, але блокування знижують паралельність і можуть спричинити deadlock. Підходить для коротких операцій із високою конкуренцією, наприклад зменшення кількості товару.

**Оптимістичне керування паралельністю** припускає, що конфлікти трапляються рідко: усі можуть читати дані без обмежень, а конфлікт виявляється під час збереження. EF Core підтримує цей підхід за допомогою **версії рядка** (маркера паралельності). Кожен `UPDATE` додає версію до умови `WHERE`; якщо інша транзакція вже змінила рядок, версії не збігаються, жодного рядка не буде змінено, а EF викине `DbUpdateConcurrencyException`.

```csharp
public class Product
{
    public int Id { get; set; }
    public int Stock { get; set; }

    [Timestamp]                       // maps to SQL Server rowversion
    public byte[] RowVersion { get; set; } = default!;
}

try
{
    var product = ctx.Products.Single(p => p.Id == id);
    product.Stock -= 1;
    ctx.SaveChanges();
    // EF emits: UPDATE Products SET Stock=@s WHERE Id=@id AND RowVersion=@original
}
catch (DbUpdateConcurrencyException)
{
    // Someone else updated it first. Reload, re-apply, and retry — or tell the user.
}
```

> **Рекомендація:** у звичайних вебзастосунках віддавайте перевагу оптимістичному керуванню паралельністю — воно масштабується, бо не утримує блокувань. Песимістичне блокування залиште для справді «гарячих» ділянок із високою конкуренцією.

> **Зверніть увагу.** **Проміжок часу, який охоплює маркер паралельності.** EF Core додає до `WHERE` *початкове* значення маркера, яке прочитав цей контекст. Тому наведений вище приклад захищає лише кілька мілісекунд між власними викликами `Single` і `SaveChanges`. Під час вебредагування проміжок набагато довший. Форму користувача створено з версії 1, інша людина зберегла версію 2; handler (обробник) збереження повторно завантажує продукт, отримує версію 2, копіює в нього дані форми, і його `UPDATE … WHERE RowVersion = <version 2>` знаходить один рядок. Помилки не буде, але зміни іншого користувача втрачено. Виправлення — використовувати початкове значення, яке бачив користувач: надсилати версію рядка разом із формою (або як `ETag`) і задавати її перед збереженням.

```csharp
var product = await ctx.Products.SingleAsync(p => p.Id == id, ct);
ctx.Entry(product).Property(p => p.RowVersion).OriginalValue = form.RowVersion; // the version the user edited
product.Stock = form.Stock;
try
{
    await ctx.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException)
{
    return Results.Conflict();   // or 412 Precondition Failed when the version came as If-Match
}
```

## Збережені процедури, подання та сирий SQL

**Подання** — це збережений запит, із якого можна читати як із таблиці; воно корисне для інкапсуляції складного об’єднання або представлення спрощеної форми даних. **Збережена процедура** — це попередньо скомпільована SQL-логіка в базі даних, яку викликають за назвою.

Сирий SQL — через збережені процедури, `FromSqlRaw` або Dapper — виправданий, якщо запит надто складний чи критичний для продуктивності, щоб добре виразити його в LINQ; потрібні специфічні для бази даних можливості, яких EF не надає; або ви виконуєте масові операції над наборами (оновлюєте мільйон рядків однією командою замість завантаження й відстеження).

> **Примітка:** для *масового запису* сирий SQL зазвичай уже не потрібен: `ExecuteUpdate`/`ExecuteDelete` ([Оновлення й видалення на основі наборів](#set-based-updates-and-deletes-executeupdate-and-executedelete)) виконують одну команду для набору даних без завантаження чи відстеження. Залиште сирий SQL для справді складних запитів або специфічних можливостей постачальника.

```csharp
// EF calling raw SQL while staying in the entity model
var open = ctx.Orders
    .FromSqlInterpolated($"SELECT * FROM Orders WHERE Status = {status}")
    .ToList();   // interpolated form is parameterized — not string concatenation
```

> **Пастка:** ніколи не складайте SQL конкатенацією з введених користувачем даних — так відкривається шлях до SQL-ін’єкції ([Розділ 12](#a03-injection)). Завжди використовуйте параметри. Ураховуйте компроміс зі збереженими процедурами: логіка в базі не відстежується системою version control (контролю версій) і CI застосунку, якщо навмисно не керувати нею як версійованими скриптами міграцій.

## Dapper: коли ORM — зайвий

Коли SQL і так пишете ви, варто запитати, чи потрібен у цьому ланцюжку EF Core. EF підвищує продуктивність розробки, але додає накладні витрати: перетворення виразів, відстеження змін, створення об’єктів. Іноді потрібен сирий SQL із тонким і швидким зіставленням з об’єктами. **Dapper** — це мікро-ORM, фактично набір методів розширення для `IDbConnection`, який виконує ваш SQL і зіставляє результат із типами C#, не роблячи нічого зайвого.

```csharp
using var conn = new SqlConnection(connectionString);
var orders = conn.Query<OrderSummary>(
    @"SELECT o.Id, c.Name AS CustomerName, SUM(l.Price) AS Total
      FROM Orders o
      JOIN Customers c ON c.Id = o.CustomerId
      JOIN OrderLines l ON l.OrderId = o.Id
      WHERE o.Status = @status
      GROUP BY o.Id, c.Name",
    new { status = "Open" });   // parameterized — safe from SQL injection
```

Dapper чудово підходить для звітних запитів із переважно читанням, складного SQL із ручною оптимізацією та hot paths (гарячих шляхів), де важливі накладні витрати EF. Багато зрілих систем використовують **обидва** інструменти: EF — для доменної моделі запису, де корисне відстеження змін, Dapper — для інтенсивного читання. Ви втрачаєте відстеження змін, міграції та LINQ і самі відповідаєте за SQL — саме це потрібно, коли важливий контроль.

### Що варто знати про Dapper

Поверхня Dapper невелика, але чотири можливості охоплюють більшість того, що інакше довелося б писати вручну.

**Багаторазове зіставлення** розділяє один рядок на кілька об’єктів, даючи змогу матеріалізувати результат об’єднання без плаского DTO:

```csharp
var sql = @"SELECT o.id, o.total, c.id, c.name
            FROM orders o JOIN customers c ON c.id = o.customer_id
            WHERE o.status = @status";

var orders = await conn.QueryAsync<Order, Customer, Order>(
    sql,
    (order, customer) => { order.Customer = customer; return order; },
    new { status = "open" },
    splitOn: "id");   // where one object ends and the next begins
```

Найчастіше помиляються з `splitOn`: він задає стовпець, із якого Dapper починає заповнювати *наступний* тип, а типове значення — `Id`. Якщо неправильно впорядкувати стовпці, отримаєте null замість помилки.

**`QueryMultiple`** повертає кілька наборів результатів за одне звернення до бази — це дешевий спосіб сформувати дані панелі моніторингу без N запитів:

```csharp
using var multi = await conn.QueryMultipleAsync(
    "SELECT * FROM orders WHERE id = @id; SELECT * FROM order_lines WHERE order_id = @id;",
    new { id });

var order = await multi.ReadSingleAsync<Order>();
var lines = (await multi.ReadAsync<OrderLine>()).ToList();
```

`DynamicParameters` обробляє вихідні параметри й збережені процедури, а **параметри-списки працюють одразу**: Dapper розгортає `WHERE id = ANY(@ids)` (або `IN @ids` у SQL Server) на основі масиву, тож вам не потрібно створювати заповнювачі.

**Небуферизовані запити** передають дані потоком замість матеріалізації. Типово `QueryAsync` буферизує весь результат у список; передавання `buffered: false` видає рядки в міру надходження. Це потрібно для експорту мільйона рядків, але так робити *не можна*, якщо плануєте закрити з’єднання посеред ітерації.

Для скасування потрібен `CommandDefinition`: зручні перевантаження не мають параметра `CancellationToken`, через що токен часто непомітно губиться дорогою до бази даних:

```csharp
var orders = await conn.QueryAsync<Order>(
    new CommandDefinition(sql, new { status }, cancellationToken: ct));
```

### Dapper та EF Core в одній транзакції

Ці інструменти співіснують краще, ніж можна очікувати: EF надає своє з’єднання й поточну транзакцію. Отже, запит Dapper може брати участь у тій самій одиниці роботи, що й відстежувані зміни:

```csharp
await using var tx = await ctx.Database.BeginTransactionAsync(ct);

// Dapper, on EF's connection and inside EF's transaction
var affected = await ctx.Database.GetDbConnection().ExecuteAsync(
    new CommandDefinition(
        "UPDATE inventory SET reserved = reserved + @qty WHERE sku = @sku",
        new { qty, sku },
        transaction: ctx.Database.GetDbTransaction(),
        cancellationToken: ct));

ctx.Orders.Add(order);
await ctx.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

> **Нюанс:** передати транзакцію обов’язково. Команда Dapper на з’єднанні EF *без* `transaction:` завершиться помилкою в SQL Server (з’єднання має активну локальну транзакцію) або виконається поза вашою транзакцією в PostgreSQL. Другий варіант небезпечніший, адже він фіксується окремо й переживає ваш відкат.

Також пам’ятайте, що засіб відстеження змін не бачить записів Dapper, як і `ExecuteUpdate`. Уже завантажені сутності зберігають застарілі значення.

| Ситуація | Використовуйте |
|---|---|
| Доменна логіка запису, агрегати, інваріанти | EF Core — для цього й потрібні відстеження та одиниця роботи |
| Модель читання з налаштованим вручну об’єднанням або віконною функцією | Dapper |
| Hot path, де профіль показує вартість матеріалізації | Dapper — після вимірювання |
| Масове обслуговування багатьох рядків | `ExecuteUpdate`/`ExecuteDelete` або сирий SQL |
| Розвиток схеми | Міграції EF незалежно від способу читання даних |

> **Рекомендація:** не перетворюйте фразу «Dapper швидший» на архітектурний принцип. Різниця продуктивності важлива лише тоді, коли матеріалізація займає вимірювану частину часу запиту; до того моменту ви вже знатимете, яким саме трьом запитам потрібен Dapper. Додати його для конкретного шляху читання — правильне рішення; переписувати навколо нього доменну модель зазвичай не варто.

## Кешування

Найшвидший запит — той, якого ви не виконуєте. Кешування зберігає результати дорогих операцій, щоб повторні запити обслуговувалися зі швидкого сховища.

### IMemoryCache і IDistributedCache

`IMemoryCache` зберігає об’єкти в оперативній пам’яті локального процесу — це дуже швидко, але кожен екземпляр сервера має власну копію, яка зникає після перезапуску. `IDistributedCache` зберігає серіалізовані байти у зовнішньому сховищі (зазвичай Redis), спільному для всіх екземплярів. Це трохи повільніше, зате узгоджено в масштабованому кластері.

```csharp
// In-memory, single instance
public async Task<Product> GetProductAsync(int id)
{
    return await _cache.GetOrCreateAsync($"product:{id}", async entry =>
    {
        entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);
        return await _db.Products.AsNoTracking().SingleAsync(p => p.Id == id);
    });
}
```

### Шаблон Cache-Aside

Найпоширеніша стратегія кешування. Логікою керує застосунок, а не кеш:

1. Перевірити кеш. Якщо значення є (**влучання**), повернути його.
2. Якщо стався **промах**, завантажити дані з бази, зберегти їх у кеші й повернути результат.

Наведений вище `GetOrCreateAsync` виконує Cache-Aside одним викликом. Це просто й надійно, адже кеш ніколи не є джерелом істини: порожній кеш означає лише повільніший перший запит, а не збій.

### Інвалідація та лавина запитів

> «У комп’ютерних науках є лише дві складні речі: інвалідація кешу та вибір назв». — Філ Карлтон

**Інвалідація** визначає, коли кешовані дані застаріли. Є дві загальні стратегії: **строк дії** (обмеження за часом — просто, але застарілі дані видаються до завершення TTL) і **явне видалення** (видалити ключ під час зміни вихідних даних — точно, але потрібно пам’ятати про кожне місце запису). Більшість систем поєднує обидві: видаляє значення під час запису й задає TTL як страховку для пропущених місць.

**Лавина кеш-запитів** (або «догпайл») виникає, коли спливає строк популярного ключа й сотні паралельних запитів одночасно промахуються, разом навантажуючи базу даних під час відновлення значення. Це може перевантажити її саме в момент найбільшого трафіку. Захист: **блокування**, за якого лише один запит відновлює значення, а решта чекає; **випереджальне/імовірнісне оновлення** (оновити трохи раніше завершення строку); видавання трохи застарілих даних під час оновлення.

.NET 9 **HybridCache** (`Microsoft.Extensions.Caching.Hybrid`) об’єднує ці підходи: поєднує локальний кеш L1 із розподіленим L2 за єдиним API `GetOrCreateAsync` і відразу має захист від лавини запитів — паралельні промахи за тим самим ключем згортаються в одне відновлення. Якщо ви вручну створюєте дворівневий кеш і блокування відновлення, краще скористайтеся ним.

Про Redis (проєктування ключів, типи даних, витіснення) і розподілене кешування між екземплярами йдеться в [Розділі 18: Дані поглиблено](#chapter-18-data-in-depth).

## Міграції в CI/CD

Схема змінюється разом із кодом, і ці зміни потрібно надійно та повторювано застосовувати в кожному середовищі. **Міграції** EF фіксують кожну зміну схеми в окремому версійованому файлі C#, згенерованому на основі різниці моделей:

```bash
dotnet ef migrations add AddCustomerCity
dotnet ef database update            # apply to the target database
```

Кожна міграція описує, що змінилося і як скасувати зміни; EF зберігає список застосованих міграцій у таблиці `__EFMigrationsHistory`, щоб ніколи не запускати їх удруге.

Стратегічне запитання — *коли* запускати міграції в pipeline. Можливі варіанти:

- **`context.Database.Migrate()` під час запуску застосунку** — найпростіше, але ризиковано в масштабі. Починаючи з EF Core 9, `Migrate()` і `MigrateAsync()` перед застосуванням змін блокують усю базу даних (`sp_getapplock` у SQL Server; рядок у таблиці `__EFMigrationsLock` у SQLite, який може залишитися після примусово завершеного процесу). Завдяки цьому екземпляри, що запускаються одночасно, чекатимуть у queue (черзі), а не пошкодять схему. Але блокування не усуває інших витрат: кожному екземпляру потрібні права DDL під час виконання, усі чекають, поки один виконує міграцію (на великій таблиці достатньо довго, щоб перевірки запуску перезапустили їх), невдала міграція зриває все deployment (розгортання), а починаючи з EF Core 9 `Migrate()` викидає exception, якщо зміни моделі не охоплено міграціями. У EF Core 8 і раніших версіях блокування немає, і паралельні запуски справді змагаються.
- **Окремий етап deployment** — згенерувати ідемпотентний скрипт SQL (`dotnet ef migrations script --idempotent`) і виконати його на окремому контрольованому етапі CI/CD до запуску нової версії застосунку. Це найбезпечніший і найпрозоріший підхід для продакшену.
- **Автономні засоби міграції — DbUp або Flyway** — застосовують звичайні впорядковані скрипти SQL, написані вручну. Команди, яким потрібен повний контроль над точним SQL (і перевірка DBA), часто віддають їм перевагу перед згенерованими міграціями EF. **DbUp** — бібліотека .NET, **Flyway** — мовонезалежний інструмент. Обидва, як і EF, записують застосовані скрипти в таблицю метаданих.
- **Окремий етап deployment** — згенеруйте ідемпотентний SQL-скрипт (`dotnet ef migrations script --idempotent`) і виконайте його як окремий контрольований етап CI/CD до запуску нової версії застосунку. Це найбезпечніший і найпрозоріший для аудиту підхід для продакшену.
- **Окремі інструменти міграцій — DbUp або Flyway** — застосовуйте звичайні впорядковані SQL-скрипти, написані вручну. Команди, яким потрібен повний контроль над конкретним SQL і перевірка адміністраторів баз даних, часто обирають їх замість згенерованих EF міграцій. **DbUp** — бібліотека для .NET, а **Flyway** — інструмент, не прив’язаний до мови. Обидва, як і EF, записують застосовані скрипти в таблицю метаданих.

> **Рекомендація:** робіть зміни схеми **зворотно сумісними**, щоб під час поетапного deployment стара й нова версії застосунку одночасно працювали з новою схемою. Спершу додайте стовпець, що допускає null; зробіть його обов’язковим в *одній із наступних* міграцій, коли весь код уже записуватиме в нього дані. Підхід «розширити, потім звузити» дає змогу розгортати схему й код незалежно, без простою; у [Розділі 18](#migrations-at-scale-zero-downtime) він застосовується до таблиць, надто великих для блокування.

## Підсумок

База даних — не чорна скринька. Нормалізація зберігає кожен факт в одному місці, а обмеження відсікають некоректні дані незалежно від поведінки застосунку. Індекс — це відсортована копія деяких стовпців, тому запит виконує пошук лише тоді, коли його умова задає лівий префікс значеннями, наявними в індексі; фактичний план і логічні читання покажуть, чи сталося це. Транзакція робить групу команд неподільною, а її рівень ізоляції визначає, що бачать паралельні транзакції.

EF Core підвищує продуктивність лише тоді, коли ви розумієте SQL, який він надсилає: відстежуйте лише те, що зберігаєте; отримуйте пов’язані рядки за одне звернення через `Include` або проєкцію; використовуйте один короткоживучий `DbContext` на запит, команди для наборів під час масових записів і маркер паралельності з початковим значенням, яке бачив користувач. Сирий SQL і Dapper підходять для запитів, які LINQ виражає невдало; кешування прибирає зрозуміле вам навантаження; міграції «розширити, потім звузити» дають змогу змінювати схему в працюючій системі. Постійно запитуйте себе: *що насправді відбувається в базі даних і чи достатньо цього, щоб забезпечити коректність?*

### Пошук чи сканування

П’ять запитів до таблиці з 200 000 рядків; для кожного буде виведено оператор індексу та логічні читання. Перш ніж запускати, передбачте для кожного, чи буде ПОШУК або СКАНУВАННЯ.

Потрібен SQL Server: запустіть його з каталогу `verify/path` командою `ACCEPT_EULA=Y docker compose up -d mssql` (образ має ліцензійну угоду; у PowerShell спершу задайте `$env:ACCEPT_EULA="Y"`), а після завершення зупиніть через `docker compose down`.

`verify/path/SeekVsScan/Program.cs` · запустіть із каталогу `verify/path` командою `dotnet run --project SeekVsScan`:

```csharp
using System.Data;
using Microsoft.Data.SqlClient;

// Prove it: which predicates can SEEK an index and which must SCAN it. Needs a SQL Server:
// `docker compose up -d` in this folder. Prints each query's index operator and logical reads.
using var db = new SqlConnection("Server=localhost,14330;Database=tempdb;User Id=sa;Password=Emulator-Only-Passw0rd!;TrustServerCertificate=true");
db.Open();
new SqlCommand("""
    DROP TABLE IF EXISTS dbo.Customers;
    CREATE TABLE dbo.Customers (Id int IDENTITY PRIMARY KEY, Email varchar(100) NOT NULL, City varchar(50) NOT NULL, CreatedAt datetime2 NOT NULL);
    INSERT dbo.Customers (Email, City, CreatedAt) SELECT CONCAT('user', value, '@example.com'), CONCAT('City', value % 200), DATEADD(minute, -value, '2026-01-01') FROM GENERATE_SERIES(1, 200000);
    CREATE INDEX IX_Email ON dbo.Customers (Email); CREATE INDEX IX_City_CreatedAt ON dbo.Customers (City, CreatedAt);
    SET STATISTICS PROFILE ON; SET STATISTICS IO ON;
    """, db).ExecuteNonQuery();
string reads = "?";
db.InfoMessage += (_, e) => { if (e.Message.Contains("logical reads")) reads = e.Message.Split("logical reads ")[1].Split(',')[0]; };
Plan("Email = @p", SqlDbType.NVarChar, "user42@example.com");     // a C# string is sent as nvarchar
Plan("Email = @p", SqlDbType.VarChar, "user42@example.com");
Plan("LOWER(Email) = @p", SqlDbType.VarChar, "user42@example.com");
Plan("City = @p AND CreatedAt >= '2025-12-31'", SqlDbType.VarChar, "City7");
Plan("CreatedAt >= @p", SqlDbType.DateTime2, new DateTime(2025, 12, 31));
void Plan(string where, SqlDbType type, object value)
{
    using var command = new SqlCommand($"SELECT Id FROM dbo.Customers WHERE {where}", db);
    command.Parameters.Add(new SqlParameter("@p", type) { Value = value });
    var ops = new List<string>();
    using (var reader = command.ExecuteReader())
        do while (reader.Read()) if (reader.FieldCount > 2 && reader.GetString(2).Contains("Index")) ops.Add(reader.GetString(2).Trim()); while (reader.NextResult());
    Console.WriteLine($"WHERE {where} (@p {type}): {reads} logical reads\n    {string.Join(" ", ops).Replace("[tempdb].[dbo].[Customers].", "")}");
}
```

```text
WHERE Email = @p (@p NVarChar): 888 logical reads
    |--Index Scan(OBJECT:([IX_Email]),  WHERE:(CONVERT_IMPLICIT(nvarchar(100),[Email],0)=[@p]))
WHERE Email = @p (@p VarChar): 3 logical reads
    |--Index Seek(OBJECT:([IX_Email]), SEEK:([Email]=[@p]) ORDERED FORWARD)
WHERE LOWER(Email) = @p (@p VarChar): 888 logical reads
    |--Index Scan(OBJECT:([IX_Email]),  WHERE:(lower([Email])=[@p]))
WHERE City = @p AND CreatedAt >= '2025-12-31' (@p VarChar): 3 logical reads
    |--Index Seek(OBJECT:([IX_City_CreatedAt]), SEEK:([City]=[@p] AND [CreatedAt] >= '2025-12-31 00:00:00.0000000') ORDERED FORWARD)
WHERE CreatedAt >= @p (@p DateTime2): 712 logical reads
    |--Index Scan(OBJECT:([IX_City_CreatedAt]),  WHERE:([CreatedAt]>=[@p]))
```

Запуск виконано на SQL Server 2022 CU27 (16.0.4295.3) із сортуванням `SQL_Latin1_General_CP1_CI_AS` у Docker на Xeon із 4 vCPU та 16 ГБ RAM. Зверніть увагу на три сканування, кожне з іншої причини:

- **Перетворення застосовується до стовпця.** `nvarchar` має вищий пріоритет типу даних, ніж `varchar`, тож SQL Server перетворює *стовпець*: `CONVERT_IMPLICIT(…,[Email],0)`. За SQL-сортування `varchar` і `nvarchar` впорядковуються по-різному, тому індекс не може відповісти на запит: 888 читань замість 3. За сортуванням Windows той самий параметр усе ж виконує пошук через обчислений діапазон: у пов’язаному запуску [`collation.txt`](https://github.com/malyna2/dotnet-handbook/blob/main/verify/path/reference-runs/collation.txt) — 3 читання й `GetRangeThroughConvert`. Тому ця помилка трапляється в одній базі, але не в іншій.
- **Функція застосовується до стовпця.** `lower([Email])` — це значення, якого немає в індексі: 888 читань.
- **Індекс використовується, але сканується.** Сам по собі `CreatedAt` не є лівим префіксом `(City, CreatedAt)`, тож SQL Server читає весь індекс: 712 читань. Якщо спершу зафіксувати `City`, обидва стовпці з’являються в `SEEK:`: 3 читання.
- **Усі запити покриті індексом.** Кожен вибирає лише `Id` — кластерний ключ, який міститься в кожному рядку некластерного індексу. Виберіть `City` з `IX_Email` — і для кожного відповідного рядка додасться пошук за ключем.

**Виправлення в .NET:** надсилайте параметр типу `varchar`. У EF Core зіставте властивість через `.IsUnicode(false).HasMaxLength(100)`: тоді `ToQueryString()` покаже `DECLARE @email varchar(100)`, тоді як типове зіставлення показує `nvarchar(4000)`. У Dapper задайте `new DbString { Value = email, IsAnsi = true, Length = 100 }`, у сирому ADO.NET — `SqlDbType.VarChar`.

**Потім виконайте лабораторну роботу** ([набір матеріалів](https://github.com/malyna2/dotnet-handbook/tree/main/labs/37-execution-plans), PostgreSQL у Docker, приблизно 3 години): прочитайте розділи *Мета* й *Налаштування* [Розділу 19](#chapter-19-the-slow-query-lab-reading-execution-plans), виконайте рівень 1 (сходинки 1–4: N+1, декартів вибух через два `Include`, функція над стовпцем, перетворення стовпця) і сходинку 6 (порядок стовпців). Переглядайте *Підказки й відповіді* для сходинки лише після того, як ваше виправлення пройшло перевірку. Результати додайте до власного публічного портфоліо, а не до цього репозиторію.

Також виконайте вправу *Що б ви зробили?* (звіт на 40 секунд) нижче.

### Підрахунок команд

Ті самі 50 замовлень і 100 рядків завантажуються чотирма способами, підраховується кожна SQL-команда EF Core. Перш ніж запускати програму, передбачте чотири результати; останній буде несподіванкою.

`verify/path/NPlusOne/Program.cs` · запустіть із каталогу `verify/path` командою `dotnet run --project NPlusOne` (потрібен лише .NET 10 SDK):

```csharp
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Diagnostics;

// Prove it: loading related rows one parent at a time sends 1 + N SQL statements; Include or a projection sends 1.
int statements = 0;
var options = new DbContextOptionsBuilder<Shop>().UseSqlite("Data Source=shop;Mode=Memory;Cache=Shared")
    .LogTo(_ => statements++, [RelationalEventId.CommandExecuted]).Options;       // counts every SQL command sent
using var seed = new Shop(options);
seed.Database.OpenConnection();                    // an in-memory database lives while a connection to it is open
seed.Database.EnsureCreated();
seed.Orders.AddRange(Enumerable.Range(1, 50).Select(i => new Order { Lines = [new() { Sku = $"A-{i}" }, new() { Sku = $"B-{i}" }] }));
seed.SaveChanges();
Count("Load() each order's lines in a loop", db =>
{
    var orders = db.Orders.ToList();
    foreach (var order in orders) db.Entry(order).Collection(o => o.Lines).Load();   // what lazy loading runs per order
    return orders.Sum(o => o.Lines.Count);
});
Count("Include(o => o.Lines)", db => db.Orders.Include(o => o.Lines).ToList().Sum(o => o.Lines.Count));
Count("Select(o => new { o.Id, Skus = ... })", db => db.Orders.Select(o => new { o.Id, Skus = o.Lines.Select(l => l.Sku).ToList() }).ToList().Sum(o => o.Skus.Count));
Count("neither, and no lazy loading", db => db.Orders.ToList().Sum(o => o.Lines.Count));
void Count(string label, Func<Shop, int> load)
{
    using var db = new Shop(options);              // a fresh context, as each request gets from DI
    statements = 0;
    Console.WriteLine($"{label,-38} {load(db),3} order lines, {statements,2} SQL statement(s)");
}
class Shop(DbContextOptions<Shop> options) : DbContext(options) { public DbSet<Order> Orders => Set<Order>(); }
class Order { public int Id { get; set; } public List<OrderLine> Lines { get; set; } = []; }
class OrderLine { public int Id { get; set; } public int OrderId { get; set; } public string Sku { get; set; } = ""; }
```

```text
Load() each order's lines in a loop    100 order lines, 51 SQL statement(s)
Include(o => o.Lines)                  100 order lines,  1 SQL statement(s)
Select(o => new { o.Id, Skus = ... })  100 order lines,  1 SQL statement(s)
neither, and no lazy loading             0 order lines,  1 SQL statement(s)
```

На що звернути увагу:

- **1 + N — це кількість, а не повільний запит.** 51 команда: одна для замовлень і по одній для кожного замовлення. Lazy loading дає саме такий результат, бо геттер навігаційної властивості запускає той самий `Load` під час першого звернення; у циклі просто не видно явного виклику. Для SQLite в пам’яті кожна команда коштує мікросекунди. На сервері бази кожна стає мережевим зверненням і позикою з’єднання з пулу, а їхня кількість зростає разом із кількістю рядків на сторінці.
- **`Include` і проєкція надсилають по одній команді.** Обидва перетворюються на один `LEFT JOIN`. Проєкція читає лише стовпці зі свого `Select` і нічого не відстежує; `Include` створює й відстежує всі 150 сутностей.
- **Не завантажити нічого — це не повільно, це неправильно.** Коли lazy loading вимкнено, `o.Lines` залишається порожнім списком, створеним разом із сутністю: 0 рядків і жодного exception. Вимкнути lazy loading, не додавши `Include` чи проєкцію, означає перетворити N+1 на відсутні дані. Якщо колекцію не ініціалізовано в самій сутності, замість цього залишиться `null`, і цикл викине exception.
- **Для кожного вимірювання потрібен новий контекст.** Контекст початкового заповнення досі відстежує кожне замовлення й кожен рядок, тому запит через нього повернув би вже наявні екземпляри з приєднаними рядками, нічого не завантажуючи. Тест, який заповнює й читає дані через один контекст, може пройти, хоча в продакшені код не повертає нічого.

Потім виконайте вправу *Знайдіть помилку* нижче: порахуйте запити, які надсилає endpoint, перш ніж відкрити відповідь.

### Пошук, сканування та покриття

**1.** Є індекс за `(City, CreatedAt)`. Чому `WHERE CreatedAt >= @d` сканує, тоді як `WHERE City = @c AND CreatedAt >= @d` виконує пошук? І чому `(CreatedAt, City)` буде гіршим для другого запиту?

<details>
<summary>Відповідь</summary>

- **Чому один запит виконує пошук, а інший — сканування.** Індекс відсортований за `City`, а потім за `CreatedAt` у межах кожного міста. Одне місто утворює неперервний блок із датами в потрібному порядку, тож рушій переходить до `(City, start date)` і читає далі. Сам діапазон дат розкиданий між блоками всіх міст: немає єдиного діапазону для пошуку, тому рушій сканує (712 читань проти 3 в експерименті).
- **Чому `(CreatedAt, City)` гірший.** Діапазон дат у першому стовпці *неперервний*, але містить рядки всіх міст за цей період, а міста в його межах не впорядковані. `City` можна перевірити лише рядок за рядком, тож рушій читає весь період, щоб залишити рядки одного міста. Сходинка 6 [Розділу 19](#chapter-19-the-slow-query-lab-reading-execution-plans) вимірює саме це.
- **Правило:** спершу стовпці рівності, потім стовпець діапазону чи сортування. Skip scan у PostgreSQL 18 послаблює це обмеження лише тоді, коли перший стовпець має мало різних значень.
</details>

**2.** Той самий запит виконує пошук, якщо запустити його в SSMS із літералом, але сканує індекс, коли запит надсилає застосунок. Стовпець має тип `varchar`. Чому так і як це виправити в EF Core та Dapper?

<details>
<summary>Відповідь</summary>

- **Застосунок надсилає `nvarchar`.** SqlClient і Dapper передають `string` із C# як `nvarchar`, якщо вказати інше; EF Core робить так само для властивості, не зіставленої як не-Unicode.
- **Перетворення застосовується до стовпця.** `nvarchar` має вищий пріоритет типу даних, тому SQL Server перетворює стовпець `varchar`, а не параметр.
- **Сортування визначає, чи буде сканування.** За SQL-сортування, наприклад `SQL_Latin1_General_CP1_CI_AS`, `varchar` і `nvarchar` впорядковуються по-різному, тому індекс не може відповісти на перетворене порівняння: сканування з 888 читаннями замість 3. За сортуванням Windows оптимізатор усе ще може обчислити діапазон пошуку — тому «в іншій базі працює». Літерал SSMS `'user42@example.com'` має тип `varchar`, тож пошук виконується всюди.
- **Виправлення:** надсилайте `varchar`. EF Core: задайте властивості `.IsUnicode(false).HasMaxLength(100)`. Dapper: використайте `DbString { IsAnsi = true, Length = 100 }`. ADO.NET: `SqlDbType.VarChar`. Або змініть тип стовпця на `nvarchar`.
</details>

**3.** Є індекс за `Email`, а `Id` — кластерний первинний ключ. Запит `SELECT Id FROM Customers WHERE Email = @e` виконує один пошук в індексі. Додайте `City` до `SELECT` — і план доповниться пошуком за ключем. Чому так, що станеться, якщо знайдеться 10 000 рядків, і як це виправити?

<details>
<summary>Відповідь</summary>

- **`Id` додається безкоштовно.** Рядок некластерного індексу містить свій ключ і кластерний ключ — ідентифікатор рядка. `Id` уже є в індексі, тому одного пошуку достатньо для відповіді.
- **`City` потребує читання рядка.** Для кожного відповідного рядка індексу SQL Server переходить кластерним ключем до кластерного індексу — це *пошук за ключем*: ще один спуск індексом і кілька сторінок для кожного рядка. Для 10 000 рядків буде 10 000 спусків, і після певної кількості оптимізатор натомість просканує всю таблицю.
- **Виправлення:** `CREATE INDEX … ON Customers (Email) INCLUDE (City)`. Тепер індекс покриває запит, і додаткові пошуки зникають. Стовпці `INCLUDE` зберігаються лише в листках індексу: вони збільшують розмір і час запису, але не впливають на порядок ключів.
</details>

### Що надсилає EF Core

**4.** Endpoint надсилає 1 + N запитів, і в кожному плані є пошук в індексі тривалістю менш як мілісекунда. Чому endpoint повільний, чому жоден окремий план не покаже проблему і як її знайти?

<details>
<summary>Відповідь</summary>

- **Витрати визначає кількість.** Кожна команда потребує мережевого обміну, з’єднання з пулу й матеріалізації. N команд повторюють ці витрати N разів, а N зростає разом із даними, а не з кодом.
- **У жодному плані проблеми немає.** Кожна команда справді дешева, тому кожен план має ідеальний вигляд. Проблема — в кількості команд, які надсилає один запит, а жоден план цієї кількості не містить.
- **Порахуйте команди на запит.** Під час розробки — у журналі команд EF Core (`LogTo` або категорія `Microsoft.EntityFrameworkCore.Database.Command` на рівні `Information`). У продакшені — у tracing (трасуванні) одного запиту, де видно проміжки бази ([Розділ 9](#observability-wiring)), або в підрахунках викликів на сервері: `pg_stat_statements` ([Розділ 19, рівень 3](#level-3-beyond-the-harness)) чи Query Store. Ознака — кількість викликів однієї команди є кратною кількості іншої.
- **Виправлення:** використайте `Include`, проєкцію або розділений запит і вимкніть lazy loading, щоб шаблон не повернувся непомітно.
</details>

**5.** Запит починається з `.Include(o => o.Customer)`, посередині має `.AsNoTracking()`, а завершується `.Select(o => new OrderRow(o.Id, o.Customer.Name))`. Який із трьох викликів змінює SQL чи обсяг роботи і чому?

<details>
<summary>Відповідь</summary>

- **Усе визначає `Select`.** Навігація `o.Customer.Name` усередині нього створює об’єднання, і читаються лише два вибрані стовпці.
- **`Include` нічого не робить.** Це інструкція зі створення сутностей `Order`, а запит створює `OrderRow`. EF Core відкидає її без попередження; без неї SQL ідентичний.
- **`AsNoTracking` також нічого не робить.** Відстежуються екземпляри сутностей, а результат без сутностей не відстежується.

Видаліть обидва виклики. Вони впливають на результат лише тоді, коли він знову містить сутність, наприклад `.Select(o => new { Order = o, o.Customer.Name })`.
</details>

**6.** `Product` має версію рядка `[Timestamp]`. Користувач відкриває форму редагування, хтось інший зберігає той самий продукт, а через п’ять хвилин перший користувач зберігає свою форму й непомітно перезаписує ту зміну. `DbUpdateConcurrencyException` не виникає. Чому і як це виправити?

<details>
<summary>Відповідь</summary>

- **Маркер захищає проміжок між читанням і записом одного контексту.** EF Core додає до `WHERE` команди `UPDATE` *початкове* значення маркера, прочитане цим контекстом.
- **Handler збереження прочитав поточну версію.** Форму користувача створено з версії 1. Інше збереження зробило версію 2. Handler завантажує продукт (версія 2), копіює на нього дані форми й надсилає `UPDATE … WHERE RowVersion = <version 2>`: знаходиться один рядок, помилки немає, а зміну іншого користувача втрачено.
- **Виправлення: використати початкове значення, яке бачив користувач.** Надсилайте версію рядка разом із формою (або як `ETag`) і перед `SaveChanges` задавайте `db.Entry(product).Property(p => p.RowVersion).OriginalValue = form.RowVersion`. Тепер не буде відповідних рядків, `SaveChanges` викине exception, а handler поверне `409 Conflict` (`412 Precondition Failed` для заголовка `If-Match`), щоб користувач оновив дані.
</details>

### Ваш найповільніший запит

**Перевірте.** Візьміть найдорожчий запит вашого сервісу з Query Store (або найповільнішу залежність у APM) і відкрийте його *фактичний* план. Визначте, який оператор індексу виконує пошук, а який — сканування. Для кожного сканування з’ясуйте, яка з трьох причин з експерименту його викликає, або чи сканування виправдане, бо запиту потрібна більшість таблиці. Для кожного стовпця `varchar`, за яким фільтрує код, перевірте тип параметра (`ToQueryString()` показує `DECLARE` EF Core).

**Виміряйте.** Порівняйте логічні читання запиту до й після виправлення (`SET STATISTICS IO ON`), а з Query Store візьміть кількість виконань за годину. Заощаджені читання, помножені на кількість виконань, і є прибраним навантаженням.

### Ваш найзавантаженіший endpoint

**Перевірте.** Увімкніть журнал команд EF Core під час розробки, один раз викличте найзавантаженіший endpoint на реалістичних даних і порахуйте рядки `Executed DbCommand`. Добре, якщо кількість невелика й не змінюється зі зростанням даних. Погано, якщо вона зростає разом із кількістю рядків на сторінці. Потім знайдіть у коді `.Include(` у запитах, що завершуються `.Select(`, `UseLazyLoadingProxies` і `DbContext`, який утримує будь-який singleton, зокрема розміщені служби.

**Виміряйте.** За день порахуйте кількість проміжків бази даних на запит до цього endpoint в трасуваннях APM чи OpenTelemetry. Дивіться на максимум, а не на середнє: N+1 проявляється в запитах із найбільшою кількістю рядків.

## Вправи

### Знайдіть помилку

Цей endpoint працює правильно, проходить інтеграційний тест на базі, заповненій 20 замовленнями, і водночас ставить продакшен на коліна.

```csharp
app.MapGet("/api/customers/{id:int}/summary", async (int id, AppDbContext db) =>
{
    var customer = await db.Customers.FindAsync(id);
    if (customer is null) return Results.NotFound();

    var orders = await db.Orders
        .Where(o => o.CustomerId == id)
        .ToListAsync();

    var lines = new List<OrderLineDto>();
    foreach (var order in orders)
    {
        foreach (var line in order.Lines)          // navigation property
            lines.Add(new OrderLineDto(line.Sku, line.Quantity, line.Product.Name));
    }

    return Results.Ok(new SummaryDto(customer.Name, orders.Count, lines));
});
```

Скільки запитів буде виконано для клієнта з 200 замовленнями, кожне з яких у середньому має 5 рядків?

<details>
<summary>Відповідь</summary>

Приблизно **1 + 1 + 200 + 1000 = 1 202 запити**, якщо ввімкнено lazy loading.

- 1 — для клієнта, 1 — для замовлень.
- `order.Lines` не завантажувалася, тож кожна ітерація запускає окремий запит — таких буде 200.
- `line.Product.Name` запускає ще по одному запиту для кожного рядка — приблизно 1 000 додаткових.

Це проблема **N+1**, причому двічі й вкладено. Тест проходить, бо 20 замовлень означають приблизно 120 запитів до локальної бази — достатньо швидко, щоб ніхто не помітив.

Є дві причини, чому ситуація гірша, ніж здається. По-перше, якщо lazy loading *вимкнене*, `order.Lines` буде порожньою колекцією, і endpoint непомітно поверне неправильні дані замість того, щоб просто працювати повільно, — це гірша помилка. По-друге, кожен із запитів бере з’єднання з пулу, тож за паралельного навантаження цей endpoint вичерпує пул і сповільнює не пов’язані з нею endpoints.

Виправлення — отримати рядки однією проєкцією, а замовлення порахувати окремо:

```csharp
var lines = await db.Orders
    .Where(o => o.CustomerId == id)
    .SelectMany(o => o.Lines)
    .Select(l => new OrderLineDto(l.Sku, l.Quantity, l.Product.Name))
    .ToListAsync();
var orderCount = await db.Orders.CountAsync(o => o.CustomerId == id);
```

Усього три команди незалежно від кількості замовлень клієнта. Проєкція читає лише названі в ній стовпці, тож EF не створює об’єктів `Order`, `OrderLine` чи `Product` і нічого не відстежує: результат без сутностей не відстежується, тому `AsNoTracking()` тут нічого не змінить. Продукт, спільний для кількох рядків, завантажується відкладено лише раз на контекст, тому 1 000 — це верхня межа для запитів продуктів.
</details>

### Що б ви зробили?

Запит для звіту виконується 40 секунд. Колега пропонує поставити перед ним кеш Redis із TTL у 5 хвилин. Execution plan показує сканування кластерного індексу на 12 мільйонах рядків і операцію hash match, яка скидає дані в tempdb. Що ви відповісте?

<details>
<summary>Як міркує досвідчений інженер</summary>

Сам кеш не є помилкою, але його пропонують замість того, щоб розібратися в проблемі, а це має витрати, яких ініціатор пропозиції не оцінив:

- **Проблема ховається, але її масштаб не обмежується.** Сканування все одно відбувається — раз на п’ять хвилин, після кожного холодного старту й кожного витіснення з кешу. За достатньої конкуренції кілька запитів одночасно промахнуться повз кеш і спричинять лавину: п’ять копій 40-секундного запиту виконуватимуться паралельно, що гірше за роботу без кешу.
- **Виникає питання коректності,** яке ще ніхто не поставив: чи прийнятні для цього звіту дані, застарілі на п’ять хвилин? Можливо, так. Це має бути усвідомлене рішення, а не побічний ефект оптимізації продуктивності.
- **План точно показує проблему.** Сканування разом зі скиданням у тимчасове сховище означає або відсутній індекс, або предикат, який не можна використати для пошуку за індексом (функція над стовпцем, неявне перетворення типу, шаблон із початковим символом `%`), або запит повертає набагато більше рядків, ніж потрібно.

Тож відповідь: «імовірно, потрібні обидва рішення, саме в такому порядку». Спершу прочитайте план і усуньте сканування — зазвичай допомагає покривний індекс або переписаний предикат, — а *потім* вирішуйте, чи потрібен кеш. Запит, який замість 40 секунд виконується за 200 мс, може взагалі не потребувати кешування; так ви усунете компонент, режим відмови й питання застарілих даних замість того, щоб додати їх.

Загальний висновок: кешування — доречний інструмент для навантаження, яке ви розумієте й вирішили не оплачувати щоразу. Це поганий спосіб приховати з панелі моніторингу запит, який ви ще не дослідили.
</details>

### Перевірте самостійно

У власному сервісі:

- Увімкніть logging (журналювання) запитів EF Core із чутливими даними під час розробки й завантажте одну сторінку з високим навантаженням. Порахуйте запити. Майже кожен бодай раз дивується результату.
- Знайдіть шлях запиту лише для читання, де не використовується `AsNoTracking()`. Виміряйте різницю на реалістичному наборі результатів.
- Візьміть найповільніший відомий запит і перегляньте його фактичний execution plan, а не розрахунковий. Чи є сканування там, де ви очікували пошук? Який індекс вибрав оптимізатор і чому не той, на який ви розраховували?
- Перевірте фактичний рівень ізоляції транзакцій. Більшість відповість «read committed» і матиме рацію; деякі системи непомітно використовують snapshot або serializable, що й пояснює deadlocks.

## Запитання для співбесіди

**Що таке відстеження змін?**
`DbContext` у EF Core створює знімки завантажених сутностей і відстежує їхній стан (Added/Modified/Deleted/Unchanged). Під час `SaveChanges` він формує SQL лише для фактичних змін. Це зручно, але витрати пам’яті й процесора зростають пропорційно до кількості відстежуваних сутностей — одна з причин вимикати відстеження для запитів лише на читання.

**Коли й навіщо використовувати `AsNoTracking`?**
Для запитів лише на читання, результати яких ви не оновлюватимете. Метод пропускає створення знімка для відстеження змін, тому працює швидше й потребує менше ресурсів. Використовуйте його для endpoints списків, звітів і GET; залишайте відстеження для сценарію «прочитати — змінити — зберегти».

**Що таке проблема N+1 в EF?**
Один запит завантажує N батьківських записів, а звернення до навігаційної властивості запускає окремий запит для кожного з них — разом N+1 мережевих обмінів. Причина — lazy loading в циклі або проєкція навігацій без їх включення. Виправте це жадібним завантаженням (`Include`), проєкцією (`Select`), яка створює об’єднання, або розділеним запитом — так кількість запитів зменшиться до 1 чи 2.

**Тривожний сигнал:** «Зробімо цикл паралельним або асинхронним, щоб запити виконувалися швидше» — паралельний N+1 усе одно означає N+1 мережевих обмінів; виправлення полягає в меншій кількості запитів, а не швидших циклах.

**Відкладене, жадібне чи явне завантаження?**
**Жадібне** (`Include`) завантажує пов’язані дані одразу в межах запиту. **Відкладене** завантажує їх під час першого звернення до навігаційної властивості (зручно, але легко випадково отримати N+1). **Явне** (`Load()`) завантажує пов’язані дані за потреби окремим явним викликом. Для передбачуваної кількості запитів віддавайте перевагу жадібному завантаженню або проєкціям; остерігайтеся lazy loading на hot paths.

**Назвіть транзакції та рівні ізоляції.**
Від найслабшого до найсильнішого: **Read Uncommitted** (брудні читання), **Read Committed** (типовий у багатьох БД; брудних читань немає), **Repeatable Read** (немає неповторюваних читань), **Serializable** (повна ізоляція, немає фантомів). Вищий рівень ізоляції означає більше блокувань і конкуренції. Обирайте найнижчий рівень, який зберігає коректність операції; ізоляція знімків (MVCC) зменшує блокування між читачами й записувачами.

**Кластерний чи некластерний індекс?**
**Кластерний** індекс визначає фізичний порядок рядків таблиці — такий індекс може бути один, зазвичай це первинний ключ. **Некластерний** індекс є окремою структурою з покажчиками на рядки; таких індексів може бути багато. Кластерний добре підходить для сканування діапазону за ключем, а некластерний покриває пошук за іншими стовпцями. «Покривний» індекс містить усі стовпці, потрібні запиту, тож звертатися до таблиці не доводиться.

**Коли індекс шкодить?**
Кожен індекс потрібно оновлювати під час вставлення, оновлення й видалення, і він займає місце, тож надмірна кількість індексів сповільнює запис. Стовпці з дуже малою кількістю різних значень (наприклад, булеві) рідко дають користь. Індексуйте стовпці, за якими фільтруєте, об’єднуєте чи сортуєте; спирайтеся на плани запитів, а не індексуйте все підряд.

**Тривожний сигнал:** «Індекси лише допомагають, тож проіндексуймо кожен стовпець» — кожен індекс оновлюється під час кожного запису й обтяжує вставлення та оновлення.

**Що спричиняє deadlock в базі даних і як його уникнути?**
Дві транзакції утримують блокування, потрібні одна одній, і захоплюють їх у протилежному порядку. Уникайте цього, скрізь отримуючи блокування в однаковій послідовності, тримаючи транзакції короткими, використовуючи найнижчий придатний рівень ізоляції й додаючи retries (повторні спроби) для помилки про жертву deadlock. Deadlocks — це проблема проєктування та порядку дій, а не просто невдача.

**Оптимістичне чи песимістичне керування паралельністю?**
**Оптимістичне:** вважаємо конфлікти рідкісними й не блокуємо рядки; виявляємо конфлікт під час збереження за допомогою стовпця версії/rowversion і повторюємо операцію, якщо рядок змінив хтось інший. **Песимістичне:** блокуємо рядок під час читання, щоб ніхто не міг змінити його до завершення операції. Оптимістичний підхід краще масштабується й типовий для вебзастосунків; песимістичний доречний для коротких критичних секцій із високою конкуренцією.

**Коли варто відмовитися від EF Core на користь Dapper?**
Коли потрібен точний контроль над SQL і максимальна швидкість читання — на hot paths запитів, у складних вручну оптимізованих запитах чи під час масового читання, — а відстеження змін і міграції не потрібні. Багато команд використовують обидва інструменти: EF для моделі запису й CRUD, Dapper для читань, критичних до продуктивності. Це рішення для кожного запиту окремо, а не питання віри.

**Що означає ACID?**
**Atomicity** (атомарність: усе або нічого), **Consistency** (consistency: перехід від одного коректного стану до іншого, обмеження виконуються), **Isolation** (ізоляція: паралельні транзакції не псують одна одну), **Durability** (довговічність: зафіксовані дані переживають аварійне завершення). Реляційні БД забезпечують ці властивості; distributed systems (розподілені системи) часто поступаються деякими з них.

**Що таке нормалізація і коли варто денормалізувати?**
Нормалізація впорядковує дані, усуваючи надлишковість (кожен факт зберігається один раз), і зменшує аномалії оновлення. Денормалізуйте свідомо заради швидкості читання: дублюйте дані або зберігайте результат об’єднання наперед, щоб уникнути дорогих об’єднань на hot paths читання, приймаючи витрати на синхронізацію копій. Типово нормалізуйте, а денормалізуйте лише за наявності доказів потреби.
