# Розділ 3: Як .NET виконує ваш код

У цьому розділі розглянуто механізми .NET, спільні для кожної служби: де runtime (середовище виконання) розміщує виділену пам’ять і як garbage collector (збирач сміття) її звільняє, як налаштування потрапляють до класів, як контейнер dependency injection (впровадження залежностей) створює й звільняє об’єкти та як Generic Host запускає й зупиняє програму. Ви зможете пояснити, чому пам’ять зростає, а потім зменшується, чому помилка в назві параметра налаштувань проходить непоміченою та чому служба `Scoped` усередині singleton обслуговує кожен запит застарілими даними.

Розділи йдуть від основ до вищих рівнів. Спочатку розглянемо **пам’ять і збір сміття**, адже на них ґрунтуються витрати на виділення пам’яті, її звільнення й тривалість життя об’єктів. **Конфігурація** та **dependency injection** — це дві системи, які поєднують частини програми; шаблон options об’єднує їх, а тривалість життя служб визначає, як довго живуть об’єкти. **Generic Host** керує обома системами й життєвим циклом фонової роботи. Наприкінці розглянемо **періодичність випусків**, яка визначає, на якій версії runtime варто працювати.

[Розділ 1](#chapter-1-c-essentials) пояснює типи значень і посилань та пакування на рівні мови, а цей розділ розвиває цю тему. Поглиблений розгляд (Large Object Heap, Server і Workstation GC, фоновий GC, JIT і Native AOT) є в [Розділі 17: Внутрішня будова runtime й продуктивність](#chapter-17-runtime-internals-and-performance); logging (журналювання) — у [Розділі 9](#chapter-9-exceptions-logging-and-first-diagnosis), а серіалізація JSON — у [Розділі 5](#serialization-systemtextjson-vs-newtonsoftjson).

## Модель пам’яті: стек і керована купа

Runtime .NET надає кожній керованій програмі дві принципово різні області пам’яті: **стек** і **керовану купу**. Розуміння того, де зберігаються значення, — найкорисніша модель для міркувань про виділення пам’яті, збір сміття й продуктивність.

**Стек** — це локальна для потоку область із порядком «останнім надійшов — першим вийшов». Кожен потік має власний стек (у Windows типово 1 МБ). Під час виклику методу runtime додає в стек *кадр стека*, що містить параметри методу, локальні змінні та службові дані, наприклад адресу повернення. Після завершення методу кадр видаляється миттєво й без витрат на очищення. Garbage collector не працює зі стеком: пам’ять звільняється простим переміщенням вказівника назад.

**Керована купа** — це спільна для всіх потоків область процесу, у якій живуть об’єкти типів посилань. Коли ви пишете `new Customer()`, runtime виділяє місце в купі й повертає *посилання* (фактично вказівник) на нього. Посилання може бути у стеку (як локальна змінна) або в іншому об’єкті в купі (як поле), але сам екземпляр `Customer` завжди перебуває в купі.

Місце зберігання даних залежить від оголошення змінної, а не лише від її типу: локальний `int` міститься в кадрі стека, поле `int` класу — всередині об’єкта в купі, а посилання у стеку вказує на об’єкт у купі. Правила наведено в [Розділі 1](#stack-vs-heap-where-the-bytes-actually-live).

```csharp
public void Example()
{
    int localValue = 42;              // the int 42 lives on the stack
    Point p = new Point(1, 2);        // Point is a struct: its two ints live on the stack
    Customer c = new Customer();      // 'c' (a reference) is on the stack;
                                      // the Customer object is on the heap
    int[] numbers = new int[100];     // 'numbers' reference on stack;
                                      // the 100 ints live in a heap array
}

public struct Point { public int X, Y; public Point(int x, int y) => (X, Y) = (x, y); }
public class Customer { public int Id; public string Name = ""; }
```

Коли `Example` завершується, кадр стека (з `localValue`, `p` і посиланнями `c` та `numbers`) безкоштовно зникає. Але `Customer` і `int[]` залишаються в купі, доки garbage collector не доведе, що до них більше немає доступу. Саме для цього GC знаходить недосяжні об’єкти й звільняє їх.

> **Чому це важливо:** кожне виділення пам’яті в купі має свою ціну: не лише саме виділення, а й подальша робота GC зі звільнення пам’яті. Високопродуктивний код .NET зменшує кількість таких виділень: використовує структури (`structs`) для малих короткоживучих даних, `Span<T>` для зрізів без копіювання й уникає прихованих виділень (пакування, замикання, LINQ у hot paths (гарячі шляхи)). У [Розділ 17](#chapter-17-runtime-internals-and-performance) показано, як їх вимірювати.

**Пакування** — місце, де ці два типи пам’яті взаємодіють: тип значення, присвоєний `object` або інтерфейсу, копіюється в новий об’єкт у купі — виділення пам’яті, якого не видно в коді ([Розділ 1](#boxing-and-unboxing-the-hidden-tax)).

## Збір сміття

Garbage collector .NET — це **трасувальний, поколіннєвий і компактуючий** збирач. Розгляньмо кожну характеристику, адже за кожною стоїть проєктне рішення, що впливає на роботу програм.

**Tracing (трасування)** означає, що GC визначає, які об’єкти живі, починаючи з набору *коренів* (статичних полів, локальних змінних і регістрів процесора в стеках усіх потоків, а також дескрипторів GC) і рекурсивно переходячи за посиланнями. Об’єкт, досяжний від кореня, *живий*; решта — сміття. Програма не має вказувати GC, що звільняти: він сам це знаходить.

**Компактування** означає, що після виявлення сміття GC пересуває живі об’єкти один до одного й усуває проміжки, щоб уникнути фрагментації. Саме тому виділення пам’яті в купі .NET надзвичайно швидке: коли купа компактна, для виділення зазвичай достатньо пересунути вказівник («вказівник виділення»), а не шукати вільний блок як у `malloc`. Компроміс у тому, що живі об’єкти *переміщуються*. Тому runtime має призупинити потоки в безпечних точках і виправити посилання під час збирання.

### Покоління 0, 1 і 2

**Гіпотеза поколінь** ґрунтується на спостереженні, що більшість об’єктів швидко зникають. JSON-відповідь, десеріалізована для обробки вебзапиту, проміжні рядки під час форматування, тимчасовий список у методі — усе це живе мікросекунди. Деякі об’єкти (кеші, singleton, довготривалі буфери) живуть увесь час роботи процесу. Об’єкти із «середньою» тривалістю життя трапляються рідко.

GC використовує цю властивість, поділяючи купу на три **покоління**:

- **Gen 0** — молоде покоління. Тут виділяються всі нові невеликі об’єкти. Gen 0 мале (налаштоване так, щоб уміщатися в кеш процесора), тому його швидко збирати.
- **Gen 1** — проміжне покоління між короткоживучими й довгоживучими об’єктами. Об’єкти, що пережили збирання Gen 0, *підвищуються* до Gen 1.
- **Gen 2** — довгоживучі об’єкти. Ті, що пережили збирання Gen 1, підвищуються сюди. Об’єкти розміром від 85 000 байтів оминають молоде покоління й потрапляють у Large Object Heap, яку збирають разом із Gen 2 ([Розділ 17](#chapter-17-runtime-internals-and-performance) пояснює, чому це важливо).

```
   new small objects
        |
        v
   +--------+               +--------+               +-----------------+
   | Gen 0  | --survivors-> | Gen 1  | --survivors-> |      Gen 2      |
   +--------+   promoted    +--------+   promoted    +-----------------+
    most objects                                      collected only by
    die here (cheap,                                  full GCs (expensive)
    frequent GCs)                                    +-----------------+
   new objects >= 85,000 bytes --------------------> |       LOH       |
                                                     +-----------------+
                                                      collected with Gen 2
```

Диво в тому, що **для більшості цілей збирання нижчого покоління не потребує сканування вищих**. Під час збирання Gen 0 переглядаються лише об’єкти Gen 0 (і спеціальний механізм, описаний нижче, що знаходить посилання *зі* старих об’єктів *на* Gen 0). Оскільки Gen 0 мале і більшість його об’єктів уже мертві, його збирання надзвичайно дешеве й часте. Збирання Gen 2 (його також називають *повним*) дороге, бо сканує всю купу; такі збирання мають бути рідкісними.

> **Бар’єр запису й таблиці карток.** Як збирання Gen 0 може бути коректним, якщо воно не сканує Gen 2? Старий об’єкт може містити посилання на молодий (наприклад, ви додаєте новий об’єкт у довготривалий кеш). Runtime розв’язує цю проблему за допомогою **бар’єра запису**: щоразу, коли посилання записується в поле об’єкта, невеликий фрагмент коду, згенерований JIT, позначає «картку» (малу область пам’яті) як змінену в **таблиці карток**. Під час збирання Gen 0 GC переглядає лише змінені картки старших поколінь, щоб знайти міжпоколіннєві посилання. Через невидимий бар’єр присвоєння посилань трохи дорожче за присвоєння значень.

### Як GC вирішує, коли збирати

Збирання починається, коли стається одна з events (події):

1. **Gen 0 заповнюється.** Вичерпано бюджет виділення пам’яті Gen 0 — це найпоширеніша причина. Runtime динамічно коригує бюджет на основі темпу виділення пам’яті й виживання об’єктів.
2. **Брак пам’яті з погляду ОС.** Система повідомляє, що фізичної пам’яті залишилося мало.
3. **Явний виклик `GC.Collect()`.** Ви самі його запитали (зазвичай дарма — див. нижче).

GC також *динамічно налаштовує себе*. Якщо помічає, що об’єкти, підвищені до Gen 2, продовжують виживати, він змінює бюджет, щоб рідше збирати Gen 2. Це адаптивна система, а не фіксований розклад.

### Фіналізація та зв’язок з `IDisposable`

GC автоматично звільняє *керовану* пам’ять. Але деякі об’єкти обгортають *некеровані* ресурси (файлові дескриптори, дескриптори сокетів, підключення до баз даних, нативну пам’ять), про які GC нічого не знає. Для цього є два механізми: **фіналізатори** й **IDisposable**.

**Фіналізатор** (`~ClassName()`) — метод, який GC викликає перед звільненням об’єкта, даючи змогу звільнити некеровані ресурси. Але фіналізація — повільний і недетермінований запасний механізм:

1. Коли GC знаходить недосяжний об’єкт *із фіналізатором*, він не може звільнити його одразу. Натомість поміщає об’єкт у **queue (черга) фіналізації**, яка утримує його в пам’яті.
2. Окремий **потік фіналізації** згодом запускає фіналізатор.
3. Об’єкт буде зібрано лише під час *наступного* циклу GC.

Отже, фіналізований об’єкт переживає принаймні ще одне покоління, а для його звільнення потрібні два цикли збирання. Надмірне використання фіналізаторів справді шкодить продуктивності.

**`IDisposable`** забезпечує *детерміноване* очищення: ви або блок `using` викликаєте `Dispose()` у точно відомий момент, а не чекаєте на GC. Це основний механізм; його використання розглянуто в [Розділі 1](#idisposable-iasyncdisposable-and-the-dispose-pattern).

Канонічний шаблон поєднує обидва механізми: `Dispose()` виконує детерміноване очищення, фіналізатор служить запасним варіантом, якщо викликач забув звільнити об’єкт, а `GC.SuppressFinalize` дає змогу пропустити дорогий фіналізатор, коли `Dispose` уже виконав роботу:

```csharp
public sealed class NativeBufferOwner : IDisposable
{
    private IntPtr _handle;              // unmanaged resource
    private bool _disposed;

    public NativeBufferOwner(int size) => _handle = Marshal.AllocHGlobal(size);

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);       // no need to run the finalizer now
    }

    private void Dispose(bool disposing)
    {
        if (_disposed) return;
        if (disposing)
        {
            // release *managed* IDisposable fields here
        }
        if (_handle != IntPtr.Zero)      // release *unmanaged* resources always
        {
            Marshal.FreeHGlobal(_handle);
            _handle = IntPtr.Zero;
        }
        _disposed = true;
    }

    ~NativeBufferOwner() => Dispose(false); // backstop if Dispose was never called
}
```

> **Рекомендація:** якщо тип містить лише *керовані* поля `IDisposable` (типовий випадок — `HttpClient` або `DbConnection`), реалізуйте `IDisposable`, але **не** пишіть фіналізатор. Довірте некерований рівень типам на основі `SafeHandle`. Фіналізатор потрібен лише тоді, коли ви безпосередньо володієте необробленим некерованим ресурсом на кшталт `IntPtr`. Навіть тоді краще використати `SafeHandle`: він надійніший у крайових випадках.

### `GC.Collect` і чому його не варто викликати

`GC.Collect()` примусово запускає збирання. У продакшен-коді майже завжди цього робити не слід, адже:

- Евристики самоналаштування GC кращі за вашу інтуїцію. Ручне повне збирання скидає ретельно підібрані бюджети й часто *погіршує* ситуацію.
- Воно примусово підвищує об’єкти: ті, що померли б у Gen 0, скануються та можуть перейти до Gen 1/2, якщо випадково ще живі саме в цей момент, і житимуть довше.
- Воно створює синхронну паузу саме тоді, коли вона вам не потрібна.

Законних причин мало: бенчмаркінг (щоб отримати чисту базову лінію), одноразове очищення після завантаження великого набору даних, який створив багато довготривалого сміття, або безпосередньо перед створенням знімка пам’яті для діагностики. Якщо ви хочете викликати `GC.Collect()`, щоб «виправити» проблему з пам’яттю, справжнє рішення майже завжди — менше виділяти або належно звільняти ресурси.

Це все про GC, що потрібно знати розробнику рівня Middle: покоління, причини збирання й роль фіналізаторів як запасного механізму. Про різновиди GC на сервері, фрагментацію Large Object Heap і читання лічильників GC під навантаженням — у [Розділі 17](#chapter-17-runtime-internals-and-performance).

## Система конфігурації

Кожній службі потрібні налаштування, які змінюються між середовищами без повторного збирання: connection strings (рядки підключення), endpoints (кінцеві точки) й перемикачі функцій. `IConfiguration` — це набір **пар «ключ — значення»**, сформований із кількох **провайдерів**; пізніший провайдер перевизначає попередній. `WebApplication.CreateBuilder` об’єднує їх у такому порядку:

1. `appsettings.json` (базові налаштування)
2. `appsettings.{Environment}.json` (наприклад, `appsettings.Production.json`)
3. **Секрети користувача** (лише для розробки — секрети не потрапляють у систему керування версіями)
4. **Environment variables (змінні середовища)**
5. **Аргументи командного рядка** (найвищий пріоритет)

Кожен наступний рівень перевизначає попередній: у продакшені environment variable може замінити параметр JSON без зміни файлів, а аргумент командного рядка — будь-яке налаштування для одноразового запуску. Ключі мають ієрархічну структуру; роздільник `:` утворює шлях на кшталт `Logging:LogLevel:Default`. У environment variables замість нього використовується `__` (подвійне підкреслення), оскільки `:` не підтримується в усіх командних оболонках.

```json
// appsettings.json
{
  "ConnectionStrings": { "Default": "Server=.;Database=App;" },
  "Email": { "SmtpHost": "smtp.local", "Port": 25, "UseSsl": false }
}
```

```csharp
var builder = WebApplication.CreateBuilder(args);
// CreateBuilder already wires up JSON, env vars, user secrets, and CLI args.

string? conn = builder.Configuration.GetConnectionString("Default");
int port = builder.Configuration.GetValue<int>("Email:Port");
```

### Шаблон Options і прив’язування конфігурації

**Шаблон Options** прив’язує розділ конфігурації до типізованого класу, щоб решта коду не читала рядкові ключі, а значення можна було перевірити.

```csharp
public sealed class EmailOptions
{
    public const string SectionName = "Email";
    public string SmtpHost { get; set; } = "";
    public int Port { get; set; }
    public bool UseSsl { get; set; }
}

// Registration:
builder.Services
    .AddOptions<EmailOptions>()
    .Bind(builder.Configuration.GetSection(EmailOptions.SectionName))
    .ValidateDataAnnotations()          // enforce [Required], [Range], etc.
    .ValidateOnStart();                 // fail fast at startup, not first use
```

Потім ви впроваджуєте один із трьох інтерфейсів options. Їхній час життя визначає, який із них побачить змінене значення (`CreateBuilder` типово перезавантажує `appsettings*.json` після змінення):

- **`IOptions<T>`** — singleton, значення якого обчислюється під час першого використання й більше не змінюється. Відредагований файл на нього вже не вплине. Його безпечно впроваджувати будь-де.
- **`IOptionsSnapshot<T>`** — **scoped**-сервіс, значення якого обчислюється один раз на запит, тож він бачить перезавантажені значення; підтримує іменовані options. Його не можна впровадити в singleton (див. далі про залежності-полонені).
- **`IOptionsMonitor<T>`** — singleton, який перераховує значення після перезавантаження конфігурації, надає `CurrentValue` і викликає `OnChange`. Використовуйте його, коли singleton потрібна актуальна конфігурація.

> **Зверніть увагу.** **Прив’язування не завершується помилкою, якщо ключ відсутній або написаний неправильно; натомість залишається значення за замовчуванням.** Прив’язувач копіює знайдені ключі у властивості з відповідними назвами й ігнорує решту. Тому ключ `"SmtpHots"` у JSON або забута environment variable дадуть `SmtpHost = ""` без жодної помилки. Саме перевірка перетворює це на помилку, і вона відбувається під час першого обчислення options: під час першого запиту, якому вони потрібні, — можливо, через кілька годин після успішного на вигляд deployment (розгортання). `ValidateOnStart()` переносить цю перевірку на запуск хоста (`Host.StartAsync` виконує її до запуску будь-якої розміщеної служби), тож неправильне налаштування зірве deployment, а не запит клієнта. `BinderOptions.ErrorOnUnknownConfiguration = true` додатково відхиляє ключі, яким не відповідає жодна властивість.

```csharp
public class Mailer(IOptions<EmailOptions> options)
{
    private readonly EmailOptions _cfg = options.Value;
}
```

## Dependency injection

У наведеному шаблоні Options уже використовувалося dependency injection: `AddOptions<T>()` реєструє сервіс, а `Mailer` отримав `IOptions<EmailOptions>`, не створюючи його самостійно. Клас *оголошує* свої залежності (зазвичай параметрами конструктора), а вбудований контейнер (`Microsoft.Extensions.DependencyInjection`) їх надає. Ви реєструєте сервіси в `IServiceCollection`; контейнер створює `IServiceProvider`, який рекурсивно їх *розв’язує*: щоб створити `OrderService`, він спочатку створить потрібний йому `IRepository`, потім потрібний репозиторію `DbContext` і так далі за графом залежностей.

### Часи життя сервісів

- **Transient** — щоразу під час запиту створюється **новий екземпляр**. Якщо `A` і `B` залежать від transient-сервісу `C`, кожен отримає власний екземпляр `C`.
- **Scoped** — **один екземпляр на область видимості**. ASP.NET Core створює область на кожен HTTP-запит, тож scoped-сервіс спільний у межах запиту, але відрізняється між запитами. Типовий приклад — `DbContext`: одна одиниця роботи на запит.
- **Singleton** — **один екземпляр на весь час роботи застосунку**, спільний для всіх одночасних запитів, тож він має бути потокобезпечним. Підходить для сервісів без стану, кешів і об’єктів, які дорого створювати.

```csharp
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddTransient<IEmailValidator, EmailValidator>();
```

### Залежності-полонені — класична помилка DI

Оскільки контейнер рекурсивно розв’язує залежності, сервіс із довшим часом життя, який захоплює сервіс із коротшим часом життя, **утримує** цей короткоживучий сервіс протягом усього свого життя. Це **залежність-полонений**, і вона часто спричиняє помилки в продакшені.

Розгляньмо **singleton, залежний від scoped `DbContext`**. Singleton створюється один раз, отже один раз отримує `DbContext`, а потім *утримує той самий `DbContext` назавжди* — між усіма запитами й потоками. `DbContext` не є потокобезпечним, тому два паралельні запити отримають помилку EF Core *"A second operation was started on this context instance"*. Запити з відстеженням також повертатимуть сутності, завантажені давно, зі старими значеннями.

> **Правило:** сервіс може залежати лише від сервісів із **таким самим або довшим** часом життя. Singleton → Singleton — безпечно. Scoped → Singleton — безпечно. Singleton → Scoped — помилка. Transient, захоплений singleton-сервісом, фактично стає singleton.

> **Зверніть увагу.** **Захоплений екземпляр не належить жодному запиту, тому його ніхто не звільнить.** Контейнер створює singleton у *кореневій* області й там само розв’язує його залежності; scoped-сервіс, отриманий у кореневій області, за формулюванням самого runtime «підвищується до singleton». Це окремий екземпляр, не пов’язаний з екземплярами запитів; він живе до зупинки застосунку й спільний для всіх запитів. Саме тому симптоми — паралельний доступ і застарілі дані, а не `ObjectDisposedException`. Цей exception (виняток) виникає за протилежного захоплення: наприклад, коли `Task.Run` продовжує використовувати `DbContext` запиту після відповіді й закриття області. Обидва випадки виправляє один підхід: той, хто працює довше за запит, створює та контролює власну область.

Вбудований контейнер може виявити перше захоплення. **`ValidateScopes`** змушує його кинути exception, якщо singleton отримує scoped-сервіс (*"Cannot consume scoped service 'X' from singleton 'Y'"*) або scoped-сервіс розв’язується з кореневого провайдера. **`ValidateOnBuild`** перевіряє кожну реєстрацію під час створення провайдера, тож `builder.Build()` завершується помилкою на старті, а не під час першого розв’язання. `WebApplicationBuilder` вмикає обидві перевірки **лише в середовищі Development**. У Production перевірки не виконуються, і помилка потрапляє в реліз.

```csharp
// If a singleton genuinely needs a scoped service, inject the FACTORY,
// not the service, and create a scope explicitly for each unit of work:
public class BackgroundProcessor(IServiceScopeFactory scopeFactory)
{
    public async Task DoWorkAsync()
    {
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        // ... use db within this scope, then it's disposed
    }
}
```

Контейнер також **звільняє** створені ним об’єкти: сервіс `IDisposable` звільняється після завершення своєї області (scoped — після запиту, singleton — під час завершення застосунку). Об’єкт, який ви створили через `new`, цього не отримає.

## Generic Host і фонові служби

**Generic Host** (`IHost`) — корінь композиції сучасного застосунку .NET. Він об’єднує dependency injection, конфігурацію, logging й керування часом життя в одному об’єкті, який можна створити, запустити й коректно зупинити. На ньому побудовані і `WebApplication` (ASP.NET Core), і консольний `Host`.

Хост керує набором екземплярів **`IHostedService`** — компонентів із методами `StartAsync` і `StopAsync`, час життя яких пов’язаний із застосунком. Під час запуску хост запускає всі розміщені служби; отримавши сигнал завершення (Ctrl+C або SIGTERM від Kubernetes), коректно їх зупиняє й дає поточній роботі завершитися.

Для тривалої фонової роботи успадкуйтеся від **`BackgroundService`** — базового класу, який реалізує `IHostedService` і надає єдиний метод `ExecuteAsync`. У прикладі показано потрібний тут шаблон — окрема область для кожної одиниці роботи; повний опис створення воркерів наведено в [Розділі 11](#chapter-11-messaging-and-background-work):

```csharp
public sealed class QueueProcessor(
    IServiceScopeFactory scopeFactory,
    ILogger<QueueProcessor> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        logger.LogInformation("Queue processor started");
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                using var scope = scopeFactory.CreateScope();     // scope per iteration
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
                await ProcessBatchAsync(db, stoppingToken);
                await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
            }
            catch (OperationCanceledException) { break; }         // graceful shutdown
            catch (Exception ex)
            {
                logger.LogError(ex, "Batch failed; retrying");
                await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
            }
        }
    }
}

// builder.Services.AddHostedService<QueueProcessor>();
```

> **Пастка:** `stoppingToken` — сигнал завершення; обробляйте його, інакше застосунок не зупиниться коректно, а оркестратори після завершення пільгового періоду надішлють `SIGKILL`. Також зверніть увагу на шаблон **окрема область на кожну ітерацію**: `BackgroundService` фактично є singleton, тож він не має безпосередньо захоплювати scoped-сервіси. Натомість він створює область для кожної одиниці роботи — саме цього вимагає правило про залежності-полонені.

## Цикл випуску .NET: LTS і STS

Microsoft випускає **нову основну версію .NET кожного листопада** за передбачуваним графіком, чергуючи два види підтримки:

- Релізи **LTS (Long-Term Support, довгострокова підтримка)** підтримуються **3 роки**. Це версії з **парними номерами**: .NET 6, **.NET 8**, **.NET 10**.
- Релізи **STS (Standard-Term Support, стандартна підтримка)** підтримуються **2 роки** — до .NET 7 підтримка тривала 18 місяців, а від .NET 9 — два роки. Це версії з **непарними номерами**: .NET 7, **.NET 9**, **.NET 11**.

Обидва типи проходять однаковий інженерний процес і графік випуску; відрізняється лише **період підтримки**. Останні шість місяців цього періоду — етап супроводу: виходять лише виправлення безпеки. Патчі публікуються щомісяця, у вівторок оновлень.

Версії та дати станом на жовтень 2026 року (`releases-index.json` у репозиторії `dotnet/core`; у [додатку](#appendix-net-version-comparison-cheat-sheet) наведено нововведення кожної версії):

- **.NET 8** (LTS, листопад 2023 року) і **.NET 9** (STS, листопад 2024 року) — обидві у фазі супроводу; підтримка завершиться **10 листопада 2026 року**. Саме довший період STS пояснює, чому вони завершуються одночасно.
- **.NET 10** (LTS, листопад 2025 року) — поточний реліз із довгостроковою підтримкою, яка триватиме до **14 листопада 2028 року**; це цільова версія для нових проєктів.
- **.NET 11** (STS) — кандидат на випуск (RC1, вересень 2026 року, його вже дозволено використовувати в продакшені); загальний випуск заплановано на листопад 2026 року.

> **Рекомендація для команд:** використовуйте релізи **LTS** для продуктів із тривалим періодом супроводу — вони дають три роки до обов’язкового оновлення й рідший цикл міграції. Обирайте **STS**, лише якщо потрібна конкретна функція, яка з’явилася саме там. Незалежно від вибору, плануйте оновлення *до* завершення підтримки: runtime без підтримки більше не отримує виправлень безпеки, що створює проблему для аудиту й відповідності вимогам.

## Підсумок

- Пам’ять поділяється на **стек** потоку, який безкоштовно звільняється після повернення з методу, і спільну **керовану купу**, яку звільняє GC. Кожне виділення пам’яті в купі означає майбутню роботу для GC.
- **GC** трасує об’єкти, використовує покоління й ущільнює купу: збирання Gen 0 дешеві й часті, а Gen 2 дорогі, тому вони мають бути рідкісними. Фіналізатор змушує об’єкт пережити ще одне збирання, тож віддавайте перевагу `IDisposable` і не викликайте `GC.Collect()`.
- **Конфігурація** об’єднує провайдери, причому пізніший перекриває попередній; **шаблон Options** прив’язує розділ до класу, а відсутній ключ стає помилкою лише після перевірки, зокрема через `ValidateOnStart`.
- **Контейнер DI** будує граф об’єктів із трьома видами часу життя. Сервіс може залежати лише від сервісів із таким самим або довшим часом життя, а `ValidateScopes` виявляє залежність-полоненого лише в Development.
- **Generic Host** об’єднує конфігурацію, DI та logging, запускає й зупиняє розміщені служби та передає `BackgroundService` токен завершення, який потрібно враховувати.
- **Листопадовий цикл випуску** з релізами **LTS (парні номери) / STS (непарні номери)** дає змогу спланувати оновлення до завершення підтримки.
