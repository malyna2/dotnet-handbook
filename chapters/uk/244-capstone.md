# Розділ 44: Випускний проєкт — один проєкт дорослішає

Читання про архітектуру дає термінологію. Еволюція однієї реальної системи навчає ухвалювати рішення. У цьому розділі один проєкт проходить усі етапи свого життєвого циклу, тож ви відчуєте проблему, яка мотивує кожну техніку, перш ніж застосувати її. Ви створите **ShopCore** — невелику серверну частину електронної комерції з товарами, кошиками, замовленнями й платежами. Предметна область навмисно знайома, щоб зосередити увагу на інженерії.

Вісім кроків відповідають порядку книжки. У кроках 1–5 застосовується матеріал частини 1: веб-API на EF Core, тести, контейнер, конвеєр, а потім кешування, автентифікація й спостережуваність. У результаті ви матимете систему, якою може самостійно володіти розробник середнього рівня. У кроках 6–8 застосовується частина 2: рефакторинг до чітких меж, поділ на служби, що взаємодіють через outbox, і розгортання результату в хмарі засобами коду. Виконуйте кроки послідовно. У кожному вказано розділи, які він охоплює, і критерії приймання — конкретні перевірювані твердження, що підтверджують справжнє завершення кроку, а не просто «в мене компілюється».

> **Правило портфоліо.** ShopCore, його показники й описи роботи мають бути у *вашому власному* публічному репозиторії, а не в цьому. Це природна центральна робота для портфоліо доказів із [розділу 37](#chapter-37-the-story-bank-evidence-portfolio): докази — це критерії приймання кожного кроку.

## Крок 1 — Чесний моноліт

Почніть з одного проєкту веб-API ASP.NET Core, EF Core із провайдером Npgsql і бази PostgreSQL у локальному контейнері. Змоделюйте товари, кошики й замовлення. Створіть кінцеві точки CRUD і оформлення замовлення. Зберігайте модульну структуру моноліту: окремі теки чи проєкти для кожної функції, без передчасного розділення на служби.

*Практика:* ASP.NET Core ([розділ 5](#chapter-5-http-and-web-apis)), EF Core і моделювання даних ([розділ 7](#chapter-7-data-access)), гроші як тип ([розділ 15](#chapter-15-dates-money-and-strings)), основи шаблонів проєктування — лише якщо шаблон себе виправдовує ([розділ 10](#chapter-10-design-basics)).

*Критерії приймання:*
- Клієнт може від початку до кінця створити товар, додати його до кошика й оформити замовлення.
- Міграції EF Core створюють схему з нуля в порожній базі даних.
- Гроші змодельовано правильно (decimal із урахуванням валюти), а в замовленнях збережено ціну на момент купівлі, а не посилання на поточні ціни товарів.
- Рішення збирається й запускається однією командою `dotnet run`, щойно піднято контейнер бази даних.

## Крок 2 — Доведіть працездатність: тести

Тепер зробіть систему надійною. Додайте модульні тести доменної логіки (ціноутворення, суми в кошику, переходи станів замовлення) за допомогою xUnit. Додайте інтеграційні тести, що запускають справжній PostgreSQL у Testcontainers і перевіряють API через `WebApplicationFactory`, звертаючись до реальної бази даних, а не до макетів.

*Практика:* модульне й інтеграційне тестування з Testcontainers ([розділ 8](#chapter-8-testing)), асинхронність від початку до кінця ([розділ 4](#chapter-4-async-essentials)), проєктування з урахуванням тестування ([розділ 10](#chapter-10-design-basics)).

*Критерії приймання:*
- Для доменних правил є модульні тести; навмисне порушення правила змушує тест завершитися помилкою.
- Принаймні один інтеграційний тест оформлює замовлення через HTTP до PostgreSQL, запущеного в Testcontainers.
- Увесь набір виконується командою `dotnet test` і завершується менш ніж за хвилину.
- Дані тестів ізольовані для кожного тесту; порядок запуску не має значення, а результати можна повторити.

## Крок 3 — Створіть Docker-образ

Запакуйте API в контейнер за допомогою багатостадійного Dockerfile (образ SDK для збирання, образ середовища виконання для запуску). Додайте `docker-compose.yml`, що разом запускає API й PostgreSQL. Саме тут «працює на моїй машині» перетворюється на «працює будь-де».

*Практика:* образи, багатостадійні збірки, Compose і контейнери без прав root ([розділ 14](#chapter-14-containers-and-linux)).

*Критерії приймання:*
- `docker compose up` запускає API й базу даних без ручних кроків.
- Образ середовища виконання побудовано на полегшеному образі slim/aspnet; SDK до нього не входить.
- Образ працює від користувача без прав root і читає конфігурацію (рядки підключення, секрети) зі змінних середовища, а не з вбудованих файлів.

## Крок 4 — CI/CD із GitHub Actions

Автоматизуйте шлях від коміту до артефакту. Створіть процес GitHub Actions, який відновлює залежності, збирає проєкт, запускає повний набір тестів (Testcontainers працює на виконавці), збирає й надсилає образ Docker до реєстру (GitHub Container Registry) після злиття змін у main.

*Практика:* CI/CD і GitHub Actions ([розділ 13](#chapter-13-git-and-cicd)), реєстри контейнерів ([розділ 14](#chapter-14-containers-and-linux)).

*Критерії приймання:*
- Кожен запит на злиття запускає збірку й тести; невдалий тест блокує злиття.
- Після злиття в main до реєстру публікується образ із тегом.
- Конвеєр визначено у YAML під контролем версій, його виконання триває приблизно до десяти хвилин.

## Крок 5 — Кешування, автентифікація та спостережуваність

Зміцніть запущену систему. Додайте Redis як розподілений кеш для часто читаних даних (каталогу товарів) із розумною інвалідацією. Додайте автентифікацію на основі JWT і авторизацію за ролями: оформляти замовлення можуть лише автентифіковані користувачі, а змінювати каталог — лише адміністратори. Замініть несистемне журналювання структурованим (Serilog) і додайте інструментування застосунку через OpenTelemetry для розподіленого трасування й метрик із передаванням до локального збирача (Jaeger або OTEL Collector разом із Prometheus).

*Практика:* кешування й інвалідація ([розділ 7](#chapter-7-data-access); Redis поглиблено — у [розділі 18](#chapter-18-data-in-depth)), автентифікація, авторизація й робота з токенами ([розділ 12](#chapter-12-security-essentials)), структуроване журналювання ([розділ 9](#chapter-9-exceptions-logging-and-first-diagnosis)), трасування й метрики ([розділ 25](#chapter-25-observability-and-testing-at-scale)).

*Критерії приймання:*
- За кешованих запитів до каталогу гарантовано не відбуваються повторні звернення до бази, а запис інвалідує відповідний елемент кешу.
- Захищені кінцеві точки відхиляють запити без токена або з недійсним токеном кодом 401; для заборонених ролей повертається 403.
- Журнали структуровані (можна виконувати запити за полями на кшталт ідентифікатора замовлення); одне оформлення замовлення створює єдине пов'язане трасування через API, базу даних і кеш.

## Крок 6 — Рефакторинг до чистої архітектури й DDD

Моноліт працює, і за ним ведеться спостереження — саме час поліпшити внутрішню структуру без зміни поведінки. Запровадьте чіткі рівні: проєкт Domain із сутностями, об'єктами-значеннями (Money, Address) та агрегатами (Order як корінь агрегату, що забезпечує виконання власних інваріантів); рівень Application із обробниками сценаріїв використання (розгляньте MediatR або власні обробники команд і запитів); рівень Infrastructure для EF Core і зовнішніх залежностей. Залежності мають указувати всередину. Використовуйте тести з кроку 2 як захисну сітку — саме тут вони окупляться.

*Практика:* чиста архітектура й інверсія залежностей ([розділ 10](#chapter-10-design-basics)), тактичні шаблони DDD ([розділ 21](#chapter-21-architecture)).

*Критерії приймання:*
- Проєкт Domain не залежить від інфраструктури й не має залежностей від EF Core чи ASP.NET.
- Бізнес-інваріанти (замовлення не можна оплатити двічі; не можна оформити порожній кошик) належать домену й забезпечуються там, а не в контролерах.
- Усі тести з кроку 2 проходять без змін — рефакторинг зберіг поведінку.

## Крок 7 — Розділіть систему на мікросервіси

Лише тепер, коли межі вже чітко проведено, безпечно розділяти систему. Виділіть дві або три служби за межами, виявленими під час роботи з DDD, наприклад **Catalog**, **Ordering** і **Payments**. Налаштуйте їхню асинхронну взаємодію через RabbitMQ за допомогою MassTransit. Критично важливо застосувати **шаблон Outbox**: служба записує доменні зміни й вихідні повідомлення в одній транзакції бази даних, а потім ретранслятор їх публікує, тож події не губляться й не надсилаються двічі мережею.

*Практика:* обмін повідомленнями й outbox ([розділ 11](#chapter-11-messaging-and-background-work)), ідемпотентність і гарантії доставки між службами ([розділ 20](#chapter-20-distributed-systems)), визначення меж служб ([розділ 21](#chapter-21-architecture)).

*Критерії приймання:*
- Оформлення замовлення в Ordering публікує подію, яку споживають Catalog (товарні запаси) і Payments; для цього процесу між ними немає синхронних викликів HTTP.
- Публікацію повідомлень виконує outbox у транзакційному режимі: аварійне завершення служби посеред оформлення не залишає замовлення без відповідної події чи події без замовлення.
- Споживачі ідемпотентні: повторна доставка того самого повідомлення не створює дубльований платіж і не зменшує запаси двічі.
- Кожна служба володіє власною базою даних; жодна служба не звертається до таблиць іншої.

## Крок 8 — Розгортання за допомогою інфраструктури як коду

Перенесіть систему в реальне середовище. Напишіть Terraform для створення інфраструктури: керованого кластера Kubernetes або хмарної служби контейнерів (Azure Container Apps, AWS ECS), а також керованих PostgreSQL, брокера повідомлень і Redis. Розгорніть три служби, налаштуйте параметри й секрети та відкрийте вхідну кінцеву точку. Тепер конвеєр CI/CD із кроку 4 просуває образи до цього середовища.

*Практика:* хмарні служби й інфраструктура як код ([розділ 28](#chapter-28-cloud-fundamentals-aws-azure); для Azure — [розділ 29](#chapter-29-azure-in-depth-for-net-developers)), Kubernetes і стратегії розгортання ([розділ 26](#chapter-26-delivery-and-platform)), спостережуваність у продакшені ([розділ 25](#chapter-25-observability-and-testing-at-scale)).

*Критерії приймання:*
- Усе середовище можна створити й знищити командами `terraform apply` / `terraform destroy`; нічого критичного не налаштовано вручну через інтерфейс.
- Усі три служби працюють на цільовій платформі й доступні через одну вхідну кінцеву точку або шлюз.
- Секрети надходять із керованого сховища секретів і ніколи не зберігаються у файлах під контролем версій.
- Трасування й метрики з кроку 5 надходять до розміщеної служби моніторингу, тож ви можете спостерігати, як реальний запит проходить між службами.

Після кроку 8 ви не просто прочитали про розподілені системи — ви створили, зламали й експлуатували одну з них. Саме такий досвід інтерв'юери й колеги розпізнають як досвід старшого фахівця.
