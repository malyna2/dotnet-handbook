# Розділ 14: Контейнери й Linux

Типова ціль хмарного deployment (розгортання) — контейнер Linux, а проблема «у мене на машині працює» там проявляється у конкретний і зрозумілий спосіб: застосунок не може записати файл, під час завершення губляться запити, порт недоступний.

Увесь розділ об’єднує одна ідея: **контейнер — це звичайний процес Linux** з обмеженим оглядом системи (простори імен, namespaces) і виділеною часткою її ресурсів (групи керування, cgroups), який запускається з багатошарового образу лише для читання. Усе, що в ньому йде не так, пояснюється поведінкою Linux: дозволи на файли визначають, що можна записувати; сигнали — чи завершиться процес коректно; environment variables (змінні середовища) передають конфігурацію; stdout — журнали.

Масштабний запуск контейнерів (Kubernetes, Helm, service mesh, .NET Aspire) і запуск .NET за допомогою systemd розглядаються в [Розділі 26: Доставка й платформа](#chapter-26-delivery-and-platform).

## Чому Linux важливий для сучасного .NET

Три чинники привели .NET у Linux.

**Контейнери.** Образи Docker майже завжди збирають `FROM` базового образу Linux. Microsoft типово постачає `mcr.microsoft.com/dotnet/aspnet:10.0` як образ на основі Debian; також є варіанти Alpine й Ubuntu. Коли ви виконуєте `docker build` і `docker run`, застосунок запускається в невеликій системі Linux, навіть якщо ваш ноутбук працює на Windows. Kubernetes — стандартний у галузі оркестратор — розподіляє контейнери Linux.

**Вартість.** Хостинг у Linux дешевший. Немає ліцензування Windows Server за ядрами, образи менші, а запуск швидший. Компанія, що запускає тисячі реплік контейнерів, заощаджує реальні кошти, обираючи Linux. Це рішення ухвалюють вище, а до вас воно доходить як вимога «застосунок має працювати в Linux».

**Усередині хмари — Linux.** Azure App Service, AWS і Google Cloud мають величезні обчислювальні парки Linux. Керовані сервіси, runner-и CI (GitHub Actions `ubuntu-latest`, агенти Linux в Azure Pipelines) і безсерверні функції типово використовують Linux.

> **Рекомендація:** розробляйте й тестуйте в родині ОС, у якій розгортатимете застосунок. Через те що Linux **розрізняє великі й малі літери** у шляхах до файлів, а Windows — ні, виникають малопомітні, але реальні помилки. `Views/Home.cshtml` і `views/home.cshtml` — це той самий файл у Windows і два різні (відсутні) файли в Linux. Виявляйте такі проблеми до продакшену.

## Оболонка: ваш справжній інтерфейс

Коли на Linux кажуть «командний рядок», зазвичай мають на увазі **оболонку** — програму, яка читає текстові команди, запускає їх і показує результат. Найчастіше ви зустрінете **bash** (Bourne Again Shell, давню типову оболонку) і **zsh** (типову оболонку macOS, яка стає дедалі популярнішою і в Linux). Усе в цьому розділі вони виконують майже однаково; відмінності важливі лише для складних сценаріїв.

Основне завдання оболонки просте: прочитати рядок, розділити його на команду й аргументи, знайти програму, запустити її й дочекатися завершення. Коли ви вводите `ls -l /var`, оболонка знаходить виконуваний файл `ls` (шукаючи в каталогах зі environment variable `PATH`), передає йому аргументи `-l` і `/var` та запускає програму.

Деякі дії оболонка виконує *до* того, як програма побачить введені вами дані. Саме тут часто виникає плутанина:

- **Підстановка шаблонів:** перед запуском програми оболонка розгортає `*.dll` у список файлів із відповідними назвами. Сама програма ніколи не бачить `*`.
- **Підстановка змінних:** `$HOME` замінюється на `/home/you`.
- **Лапки:** одинарні лапки `'...'` зберігають буквальний вміст; подвійні лапки `"..."` допускають підстановку змінних. Шляхи з пробілами беріть у лапки.

```bash
# The shell expands the glob; 'ls' receives the actual filenames
ls -l *.dll

# Single quotes stop expansion — useful when you want a literal $
echo 'The cost is $5'      # prints: The cost is $5
echo "Home is $HOME"       # prints: Home is /home/you
```

## Ієрархія файлової системи

У Windows є літери дисків (`C:\`). У Linux є одне дерево, коренем якого є `/`, і до нього приєднано все — кожен диск і кожен пристрій. Структура каталогів відповідає домовленості (стандарту ієрархії файлової системи). Каталоги, важливі для .NET-розробника:

| Шлях | Що там міститься | Навіщо це знати |
|------|------------------|--------------|
| `/etc` | Загальносистемна конфігурація | Тут містяться файли systemd unit і конфігурація nginx |
| `/var` | Змінні дані: журнали, кеші | `/var/log` призначений для журналів; `/var/lib` — для стану |
| `/usr` | Встановлені програми й бібліотеки | `/usr/bin/dotnet`, спільні бібліотеки |
| `/home/<user>` | Домашні каталоги користувачів | Ваші `~`, конфігурація, ключі SSH |
| `/tmp` | Тимчасові файли, які видаляються під час перезавантаження | Тимчасове місце; у закритому контейнері часто *єдиний* каталог, доступний для запису |
| `/proc` | Віртуальна файлова система зі станом ядра й процесів | `/proc/<pid>/status` показує пам’ять процесу; це не справжні файли |
| `/opt` | Необов’язкове програмне забезпечення від сторонніх постачальників | Деякі постачальники розміщують тут застосунки |

Шляхи розділяються символом `/`, а не `\`. `~` — скорочення для домашнього каталогу. `.` означає поточний каталог, `..` — батьківський. Шлях, що починається з `/`, є **абсолютним**; решта шляхів є **відносними** до вашого поточного каталогу.

```bash
pwd                 # print working directory — where am I?
cd /var/log         # go to an absolute path
cd ..               # up one level
cd ~                # go home (cd with no args does the same)
cd -                # jump back to the previous directory
```

## Основні команди

```bash
ls -lah                 # list: long format, all files, human-readable sizes
cp source.txt dest.txt  # copy
cp -r src/ dst/         # copy a directory recursively
mv old.txt new.txt      # move or rename
rm file.txt             # remove a file
rm -rf node_modules/    # remove a directory tree — DANGEROUS, no undo
mkdir -p a/b/c          # create nested directories
```

> **Пастка:** `rm -rf` не має кошика. Команда `rm -rf /` або випадкова змінна на кшталт `rm -rf $DIR/`, коли `$DIR` порожня (і команда перетворюється на `rm -rf /`), може стерти всю систему. Завжди ретельно перевіряйте шлях.

**Пошук:**

```bash
find /app -name "*.log"              # find files by name pattern
find /app -type f -mtime +7          # files modified more than 7 days ago
find . -name "*.dll" -delete         # find and delete matches

grep "ERROR" app.log                 # lines containing ERROR
grep -r "ConnectionString" .         # recursive search through a tree
grep -i -n "timeout" app.log         # case-insensitive, with line numbers
```

**Читання файлів і журналів:**

```bash
cat appsettings.json     # dump a whole file to the screen
less app.log             # page through a big file (arrows, /search, q to quit)
head -n 20 app.log       # first 20 lines
tail -n 100 app.log      # last 100 lines
tail -f app.log          # follow — stream new lines live, great for logs
```

`tail -f` стане в пригоді, коли потрібно спостерігати, як застосунок у реальному часі записує журнали.

**Редагування потоків за допомогою sed і awk** — не потрібно опановувати їх повністю, достатньо вміти ними користуватися:

```bash
sed 's/localhost/prod-db/g' config.txt   # substitute all localhost -> prod-db
awk '{print $1}' access.log               # print the first whitespace field
awk -F: '{print $1}' /etc/passwd          # split on ':' , print field 1
```

`sed` шукає й замінює текст у потоках; `awk` виокремлює стовпці. Разом із `grep` вони дають змогу отримати потрібну інформацію з журналів, не виходячи з термінала.

**Робота з мережею:**

```bash
curl https://api.example.com/health           # fetch a URL, print the body
curl -i http://localhost:5000/health          # include response headers
curl -X POST -H "Content-Type: application/json" \
     -d '{"name":"test"}' http://localhost:5000/api/items

ssh appuser@10.0.0.5                           # open a remote shell
scp app.zip appuser@10.0.0.5:/tmp/             # copy a file to a remote host
```

## Канали, перенаправлення, коди завершення й об’єднання команд

Саме тут оболонка стає середовищем програмування. Кожна програма має три потоки: **stdin** (0), **stdout** (1) і **stderr** (2).

**Перенаправлення** надсилає ці потоки у файли:

```bash
dotnet MyApp.dll > out.log             # stdout to a file (overwrite)
dotnet MyApp.dll >> out.log            # stdout appended
dotnet MyApp.dll 2> err.log            # stderr to a file
dotnet MyApp.dll > all.log 2>&1        # both stdout and stderr to one file
dotnet MyApp.dll < input.txt           # feed a file as stdin
```

**Канали** (`|`) з’єднують stdout однієї програми зі stdin наступної. У цьому й полягає філософія Unix: невеликі інструменти об’єднуються в pipelines (конвеєри).

```bash
# Show the 5 lines with the most ERRORs across today's logs
grep "ERROR" app.log | sort | uniq -c | sort -rn | head -5

# Which dotnet processes are eating memory?
ps aux | grep dotnet | sort -k4 -rn | head
```

**Коди завершення** повідомляють, чи виконалися програми успішно. За домовленістю, `0` означає успіх, будь-яке ненульове значення — невдачу. Оболонка зберігає останній код завершення у `$?`. Саме його перевіряють pipelines CI, щоб визначити успіх або невдачу, і саме його повертає `dotnet test`.

```bash
dotnet build
echo $?          # 0 if the build succeeded, non-zero if it failed
```

**Об’єднання команд** використовує коди завершення для керування потоком виконання:

```bash
dotnet build && dotnet test          # run tests ONLY if build succeeded
dotnet test || echo "tests failed"   # run the echo ONLY if tests failed
dotnet restore ; dotnet build        # run both regardless (';' just sequences)
```

`&&` означає «і тоді, якщо попередня команда успішна»; `||` — «інакше, якщо вона завершилася невдало». Ви постійно використовуватимете їх у Dockerfile і CI-скриптах.

## Дозволи: чому застосунок у контейнері не може записати файл

Кожен файл і каталог мають **власника** (користувача), **групу** й набір бітів дозволів для трьох категорій: власник (`u`), група (`g`) і решта (`o`). Для кожної категорії є три біти: **читання (r)**, **запис (w)** і **виконання (x)**. Запустіть `ls -l` і прочитайте перший стовпець:

```bash
ls -l app.dll
# -rw-r--r-- 1 appuser appgroup 8192 Jul 21 10:00 app.dll
```

Розшифруймо `-rw-r--r--`:

- Перший символ `-` означає звичайний файл (`d` означав би каталог).
- `rw-` означає, що власник може читати й записувати, але не виконувати.
- `r--` означає, що група може лише читати.
- `r--` означає, що решта користувачів може лише читати.

Для **каталогу** `x` означає «можна зайти до каталогу або пройти крізь нього», а `w` — «можна створювати чи видаляти в ньому файли». Через це застосунок може не записати файл журналу, навіть якщо він є власником цього файлу: можливо, йому бракує `w` для *каталогу*.

Дозволи також записують вісімковими числами, де `r=4, w=2, x=1`. Отже, `rwxr-xr-x` = `755`, а `rw-r--r--` = `644`.

```bash
chmod 644 appsettings.json     # owner rw, everyone else r
chmod +x deploy.sh             # add execute so you can run the script
chmod 755 /app/data            # make a dir traversable + writable by owner

chown appuser:appgroup app.dll         # change owner and group
chown -R appuser /app/logs             # recursive, for a whole tree
```

Ось типова помилка в контейнері. Для безпеки Dockerfile переходить на користувача без root-доступу (інструкція `USER`; нижче, у розділі *Створення контейнера для застосунку .NET*, наведено весь файл):

```dockerfile
USER app        # runs as UID 1654, not root
```

Потім застосунок намагається записати в `/app/data`, але каталог раніше створили під час збірки від root із дозволом `755` — записувати до нього може лише `root`. Під час запуску процес із UID 1654 отримує **відмову в записі**, і .NET викидає `UnauthorizedAccessException`. Виправлення — під час збірки передати каталог користувачеві, який запускатиме процес:

```dockerfile
RUN mkdir -p /app/data && chown -R app:app /app/data
USER app
```

> **Пастка:** підключені томи переносять у контейнер дозволи й власника з *хоста*. Том, що належить хосту з UID 0, не буде доступний для запису в контейнері з UID 1654 — незалежно від інструкцій Dockerfile. Узгодьте UID, змініть власника тому або додайте крок ініціалізації від root, який виконає `chown` підключеного тому.

В офіційних образах .NET 8+ вже є попередньо створений користувач `app` (UID 1654). У розділі *Запуск без root-доступу* нижче пояснюється, чому варто його зберегти: не виправляйте помилку доступу переходом назад до root.

## Процеси й сигнали: коректне завершення роботи

Запущена програма — це **процес** із числовим **PID**. Переглянути процеси можна так:

```bash
ps aux                    # every process, with CPU/memory
ps aux | grep dotnet      # just the dotnet ones
top                       # live, updating process view (press q to quit)
htop                      # nicer top, if installed — colored, scrollable
```

Процеси спілкуються за допомогою **сигналів** — невеликих асинхронних сповіщень. Вам потрібно знати два:

- **SIGTERM (15):** «Будь ласка, заверши роботу». Процес може перехопити сигнал, завершити поточні запити, спорожнити буфери журналів, закрити з’єднання з БД і вийти. Це сигнал **коректного завершення**.
- **SIGKILL (9):** «Завершуйся негайно». Його неможливо перехопити чи проігнорувати; ядро завершує процес одразу, без очищення ресурсів. Існує ризик втрати даних.

```bash
kill 4321          # sends SIGTERM by default — polite
kill -9 4321       # sends SIGKILL — the hammer, last resort
kill -TERM 4321    # explicit SIGTERM
pkill dotnet       # kill by name
```

Це безпосередньо пов’язано з контейнерами. Коли Kubernetes або `docker stop` завершує застосунок, надсилається **SIGTERM**; після періоду очікування (для `docker stop` типово 10 секунд, задається через `-t`; у Kubernetes — `terminationGracePeriodSeconds`, типово 30) надсилається **SIGKILL**. Generic host ASP.NET Core слухає SIGTERM і запускає `IHostApplicationLifetime.ApplicationStopping`, викликає `IHostedService.StopAsync` і завершує активні запити. Якщо застосунок ігнорує SIGTERM або завершується надто довго, його вбивають сигналом SIGKILL під час запиту. У [Розділі 11: Коректне завершення роботи й `CancellationToken`](#graceful-shutdown-and-the-cancellationtoken) розглянуто бік застосунку: тайм-аут завершення та токен, за яким має стежити кожен worker.

> **Рекомендація:** переконайтеся, що .NET справді *отримує* SIGTERM. Використовуйте **exec-форму** `ENTRYPOINT` (`ENTRYPOINT ["dotnet", "MyApp.dll"]`), а не shell-форму (`ENTRYPOINT dotnet MyApp.dll`). Shell-форма запускає застосунок як дочірній процес `/bin/sh`, який стає PID 1 і не пересилає сигнали. Тому SIGTERM ніколи не доходить до .NET, і кожне завершення стає примусовим.

### Передній план, фоновий план і завдання

Зазвичай команда виконується на **передньому плані** й займає термінал. Додайте `&`, щоб виконати її **у фоновому режимі**:

```bash
dotnet MyApp.dll &      # runs in background, prints a job number and PID
jobs                    # list background jobs in this shell
fg %1                   # bring job 1 back to the foreground
# Ctrl+Z suspends the foreground job; bg %1 resumes it in the background
```

Для довготривалої роботи на сервері використовуйте systemd ([Розділ 26: systemd](#systemd-running-a-net-app-as-a-service)) або контейнер, а не `&`: фонові завдання завершаться, коли закриється оболонка.

## Environment variables й те, як їх читає .NET

Environment variables — це пари ключ-значення, які оболонка передає програмам. Це основний спосіб налаштувати застосунок у контейнері: перебудовувати образ із новою конфігурацією не потрібно.

```bash
export ASPNETCORE_ENVIRONMENT=Production   # set for this shell and children
echo $ASPNETCORE_ENVIRONMENT               # read it back
printenv                                   # list all environment variables
NAME=value dotnet MyApp.dll                # set just for this one command
```

Система конфігурації .NET автоматично читає environment variables як одне зі своїх джерел конфігурації ([Розділ 3: Система конфігурації](#the-configuration-system)). Важливі два домовлені префікси:

- Префікс **`ASPNETCORE_`** налаштовує хост ASP.NET Core: наприклад, `ASPNETCORE_ENVIRONMENT=Production`, `ASPNETCORE_URLS=http://+:8080`.
- Префікс **`DOTNET_`** налаштовує runtime (середовище виконання) й generic host: наприклад, `DOTNET_ENVIRONMENT`, `DOTNET_gcServer=1`.

Окрім префіксів, система конфігурації перетворює **подвійне підкреслення** (`__`) на роздільник вкладених секцій (`:`, який дозволено використовувати в назвах environment variables не на всіх платформах). Отже, налаштування JSON:

```json
{ "ConnectionStrings": { "Default": "Server=..." } }
```

```bash
export ConnectionStrings__Default="Server=prod;Database=app;..."
```

Так до контейнерів передають секрети й connection strings (рядки підключення), не записуючи їх в образ. У Dockerfile або маніфесті Kubernetes задайте `ConnectionStrings__Default` як environment variable, і .NET підхопить її.

```bash
docker run -e ASPNETCORE_ENVIRONMENT=Production \
           -e ConnectionStrings__Default="Server=db;..." \
           -p 8080:8080 myapp:latest
```

> **Рекомендація:** ніколи не зберігайте секрети в `appsettings.json` у системі version control (контролю версій). Для всього чутливого використовуйте environment variables або сховище секретів ([Розділ 12: Керування секретами](#secrets-management)). Домовленість із `__` дає змогу змінним середовища коректно перевизначати конфігурацію з файлів — саме такий порядок пріоритетів застосовує .NET.

## Коротко про менеджери пакетів

Щоб встановити програмне забезпечення, використовуйте менеджер пакетів дистрибутива, а не завантажуйте його із сайту. Є дві основні родини:

```bash
# Debian / Ubuntu (apt)
sudo apt-get update              # refresh the package index first
sudo apt-get install -y curl     # install curl, no prompts

# RHEL / Fedora / Amazon Linux (yum/dnf)
sudo yum install -y curl
```

`sudo` запускає команду від root (адміністратора). У Dockerfile ви побачите об’єднані команди `apt-get update && apt-get install`: `update` оновлює індекс, а `install` використовує його. Завжди об’єднуйте їх в один шар `RUN`, щоб не кешувати застарілий індекс.

## Текстові редактори: необхідний мінімум nano і vim

Рано чи пізно ви під’єднаєтеся до сервера через SSH без графічного інтерфейсу й муситимете відредагувати файл конфігурації. Два редактори є майже завжди.

**nano** — простий редактор. Команди показано внизу екрана; символ `^` означає Ctrl.

```bash
nano appsettings.json
# Edit normally. Ctrl+O then Enter to save. Ctrl+X to exit.
```

**vim** потужний, але має режими, що спантеличують новачків. Достатньо знати, як вийти:

```bash
vim config.txt
# Press i to enter INSERT mode and type normally.
# Press Esc to return to NORMAL mode.
# Type :wq then Enter to write and quit.
# Type :q! then Enter to quit WITHOUT saving (when you've made a mess).
```

> **Пастка:** якщо ви застрягли у vim і клавіатура лише видає звукові сигнали, натисніть `Esc`, введіть `:q!` і натисніть Enter. Це універсальний спосіб вийти. Вивчіть його заздалегідь — так не доведеться панікувати.

## WSL2: розробка у Windows для Linux

Щоб освоїти Linux, не потрібно відмовлятися від Windows. **WSL2** (Windows Subsystem for Linux, версія 2) запускає справжнє ядро Linux у легкій віртуальній машині, інтегрованій із Windows. Ви отримуєте повноцінну оболонку Ubuntu (або іншого дистрибутива), Docker Desktop на її основі й повну взаємодію з файлами Windows.

```powershell
wsl --install                 # install WSL2 with the default Ubuntu distro
wsl --list --verbose          # see installed distros and their version
wsl                           # drop into your Linux shell
```

Для розробки на .NET це майже ідеальний варіант: збирайте й запускайте застосунок у Linux-середовищі WSL2, щоб виявити чутливість до регістру й проблеми з дозволами *до* продакшену, і водночас користуйтеся Visual Studio або VS Code у Windows. Розширення WSL для VS Code редагує файли Linux безпосередньо.

> **Рекомендація:** зберігайте файли проєкту у файловій системі Linux WSL2 (`~/projects/...`), а не на диску Windows (`/mnt/c/...`). Доступ між файловими системами значно повільніший, а стеження за файлами (hot reload) через цю межу ненадійне.

## Що таке контейнер

Контейнер — це поєднання вже знайомих речей: процесів, дерева файлової системи й кількох функцій ядра. Найпоширеніша помилка — вважати контейнер легкою віртуальною машиною. Це не так.

**Віртуальна машина** віртуалізує *апаратне забезпечення*. Гіпервізор (VMware, Hyper-V, KVM) показує **повноцінній гостьовій ОС** фальшиві процесори, мережеві карти й диски, разом з її ядром. Якщо на хості запущено п’ять віртуальних машин, працюють п’ять окремих ядер, кожне споживає сотні мегабайт пам’яті ще до запуску застосунку й завантажується десятки секунд.

**Контейнер** віртуалізує *операційну систему*. Гостьового ядра немає. Усі контейнери на хості спільно використовують **одне ядро Linux хоста**. Ізоляцію, яку бачить контейнер (власний список процесів, мережеві інтерфейси й кореневу файлову систему), забезпечує набір функцій ядра, а не окрема машина.

### Дві функції ядра, завдяки яким це працює

**Простори імен (namespaces)** забезпечують *ізоляцію* — визначають, що може *бачити* процес. У Linux є кілька видів просторів імен, а контейнер — це, по суті, процес у новому наборі просторів:

- **Простір імен PID:** головний процес контейнера бачить себе як PID 1 і не бачить процесів хоста.
- **Мережевий простір імен:** контейнер отримує власний мережевий стек — інтерфейси, таблицю routing (маршрутизації) й порти. Два контейнери можуть одночасно прив’язатися до порту 80 без конфлікту.
- **Простір імен монтування:** контейнер має власне представлення дерева файлової системи з коренем в образі контейнера, а не в корені хоста.
- **Простір імен UTS:** власну назву хоста.
- **Простір імен користувача:** зіставляє ідентифікатори користувачів, щоб root *усередині* контейнера відповідав непривілейованому користувачу *зовні*.

**Групи керування (cgroups)** забезпечують *обмеження* — визначають, що процес може *використовувати*. Група керування обмежує частку процесора, пам’ять і пропускну здатність вводу-виводу для групи процесів. Коли ви повідомляєте Kubernetes, що pod може використовувати «500m процесора й 512Mi пам’яті», це обмеження зрештою забезпечують cgroups.

Простіше кажучи: **простори імен визначають, що ви бачите; cgroups — що можете споживати.** Контейнер — це звичайний процес Linux (або дерево процесів), ізольований просторами імен і обмежений cgroups. Тому контейнери запускаються за мілісекунди й майже нічого не коштують у простої: не потрібно завантажувати друге ядро.

> **Пастка:** оскільки контейнери спільно використовують ядро хоста, контейнер Linux не може працювати у Windows чи macOS безпосередньо. Docker Desktop непомітно запускає у фоновому режимі легку віртуальну машину Linux і запускає контейнери *в ній*. На сервері Linux такої віртуальної машини немає — контейнери працюють безпосередньо на ядрі хоста.

### Образи й контейнери

У розмовах ці слова часто використовують як синоніми, хоча вони означають різні речі:

- **Образ** — шаблон лише для читання: стек шарів файлової системи й метадані (команда для запуску, environment variables, відкриті порти). Він неактивний, як визначення класу чи інсталятор.
- **Контейнер** — запущений (або зупинений) *екземпляр* образу з тонким доступним для запису шаром зверху. Він активний, як об’єкт, створений на основі класу.

З одного образу можна запустити тисячу контейнерів, так само як один клас може створити тисячу об’єктів. Коли контейнер записує файл, він не змінює образ; запис за допомогою **копіювання під час запису** (copy-on-write) потрапляє до власного доступного для запису шару контейнера. Видаліть контейнер — і цей шар зникне. Саме тому контейнери називають *тимчасовими*, а постійні дані зберігають у томах, а не всередині контейнера.

## Docker: створення образів

Docker популяризував контейнери, надавши зручний інструмент збірки й формат розповсюдження. Образ декларативно описують у **Dockerfile**, а `docker build` виконує його й створює образ.

### Шари й кешування шарів

Кожна інструкція Dockerfile, що змінює файлову систему, створює новий **шар** — різницю поверх попереднього шару. Образи складаються з таких шарів і зберігаються за хешем вмісту. Саме ця будова визначає найважливішу характеристику продуктивності Docker: **кеш збірки**.

Під час збірки Docker для кожної інструкції перевіряє, чи вже створював ідентичний шар (та сама інструкція й той самий вхідний вміст). Якщо так, він використовує кеш і пропускає роботу. Щойно змінюється вхідний вміст однієї інструкції, цей шар і **всі наступні** недійсні й збираються повторно.

Це просте правило визначає порядок інструкцій у Dockerfile: **рідко змінювані речі розміщуйте ближче до початку, а ті, що часто змінюються, — ближче до кінця.** У застосунку .NET файли проєкту й відновлені пакети NuGet змінюються значно рідше за вихідний код. Тому спочатку копіюйте `.csproj` і відновлюйте пакети, а потім копіюйте решту вихідного коду. Тоді зміна файлу `.cs` не змусить повністю відновлювати пакети.

> **Рекомендація:** копіюйте маніфести залежностей і відновлюйте пакети *до* копіювання вихідного коду застосунку. Так дорогий шар `dotnet restore` залишається в кеші між багатьма збірками, у яких змінювався лише ваш код.

### Типові інструкції Dockerfile

- `FROM` — базовий образ для збірки. З нього починається кожен Dockerfile.
- `WORKDIR` — задає робочий каталог для наступних інструкцій (і створює його).
- `COPY` / `ADD` — копіюють файли з контексту збірки до образу. Віддавайте перевагу `COPY`: `ADD` має неочевидні додаткові можливості (завантаження з URL, автоматичне розпакування tar-архівів).
- `RUN` — виконує команду *під час збірки* і створює новий шар (наприклад, `dotnet restore`).
- `ENV` — задає environment variable, вбудований в образ.
- `ARG` — змінна часу збірки, доступна лише під час збірки.
- `EXPOSE` — документує порт, який слухає застосунок (лише метадані; порт насправді не публікується).
- `USER` — задає користувача для наступних інструкцій і контейнера під час запуску.
- `ENTRYPOINT` / `CMD` — визначають, що запускається разом із контейнером. `ENTRYPOINT` — фіксований виконуваний файл; `CMD` задає типові аргументи.

### .dockerignore

**Контекст збірки** — це набір файлів, які Docker передає рушію збірки до виконання Dockerfile. Якщо збирати з каталогу, у якому є `bin/`, `obj/`, `.git/` і `node_modules/`, усе це надсилається демону. Збірка сповільнюється, а секрети чи застарілі двійкові файли можуть потрапити в образ. Файл `.dockerignore` виключає їх так само, як `.gitignore`:

```gitignore
# .dockerignore
**/bin/
**/obj/
**/.vs/
**/.git/
**/node_modules/
**/*.user
Dockerfile
docker-compose*.yml
README.md
.env
```

> **Пастка:** без `.dockerignore` випадкова тека `bin/Debug`, скопійована широкою командою `COPY . .`, може перекрити щойно опублікований результат або збільшити контекст на сотні мегабайт. Завжди додавайте цей файл.

### Багатоетапні збірки

Ось у чому складність: щоб *зібрати* застосунок .NET, потрібен повний SDK (компілятори, NuGet, MSBuild) — сотні мегабайт. Щоб *запустити* його, потрібне лише значно менше runtime. **Багатоетапна збірка** дає змогу скомпілювати застосунок у великому образі SDK, а потім скопіювати лише опублікований результат у компактний образ runtime, повністю відкинувши SDK. У фінальному образі немає інструментів збірки.

## Створення контейнера для застосунку .NET

```dockerfile
# syntax=docker/dockerfile:1

# ---- Stage 1: build & publish ----
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

# Copy only the project files first so restore is cached
# when only source code changes.
COPY ["MyApi/MyApi.csproj", "MyApi/"]
COPY ["MyApi.Core/MyApi.Core.csproj", "MyApi.Core/"]
RUN dotnet restore "MyApi/MyApi.csproj"

# Now copy the rest of the source and publish.
COPY . .
WORKDIR /src/MyApi
RUN dotnet publish "MyApi.csproj" \
    -c Release \
    -o /app/publish \
    --no-restore \
    /p:UseAppHost=false

# ---- Stage 2: runtime ----
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app

# Copy only the published output from the build stage.
COPY --from=build /app/publish .

# Run as the built-in non-root user shipped in the base image.
USER $APP_UID

# Kestrel listens here; ASP.NET Core reads ASPNETCORE_HTTP_PORTS.
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080

ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Зверніть увагу на кілька деталей:

- **`AS build` / `AS final`** задають назви етапів. `COPY --from=build` дістає з попереднього етапу лише `/app/publish`. SDK не потрапляє до фінального образу.
- Прапорець **`--no-restore`** у publish запобігає зайвому повторному відновленню пакетів, адже ми вже зробили це в кешованому шарі.
- **`USER $APP_UID`** — сучасні базові образи Microsoft визначають користувача без root-доступу за допомогою environment variable `APP_UID` (UID 1654). Запуск від його імені — важливий захід безпеки (докладніше нижче).
- **Порт 8080, а не 80**: починаючи з .NET 8, типові образи Microsoft працюють без root-доступу, а такі користувачі не можуть прив’язуватися до привілейованих портів (нижче 1024). Саме тому типове значення портів в образах — 8080.

### Запуск без root-доступу

За замовчуванням процес контейнера працює від **root** — root усередині контейнера, що справді становить ризик, якщо не використовуються простори імен користувачів. Якщо зловмисник вийде з контейнера через уразливість ядра, на хості він отримає привілеї root. Запуск від непривілейованого користувача значно зменшує масштаб можливої шкоди; ціна — налаштувати власника каталогів і томів, до яких застосунок записує, як описано вище в розділі [Дозволи](#permissions-why-your-container-app-cant-write-that-file).

> **Рекомендація:** ніколи не запускайте продакшен-контейнери від root. Використовуйте `USER $APP_UID` з образами Microsoft або створіть окремого користувача. Для поглибленого захисту доповніть це файловою системою root лише для читання й вилученими можливостями Linux під час запуску.

### Образи Chiseled і distroless: зменшення поверхні атаки

Стандартний образ `aspnet:10.0` побудований на Debian і містить оболонку, менеджер пакетів і десятки системних інструментів. Застосунку майже нічого з цього не потрібно, але зловмисник, який проникне всередину, зможе цим скористатися. Образи **Chiseled** (варіант Microsoft підходу «distroless») містять лише найнеобхідніше: runtime .NET і його безпосередні залежності, **без оболонки, менеджера пакетів і з типовим користувачем без root-доступу.**

```dockerfile
# Runtime stage using an Ubuntu Chiseled image.
FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled AS final
WORKDIR /app
COPY --from=build /app/publish .
# Chiseled images already run as non-root (UID 1654) and default to port 8080.
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

Переваги суттєві: образи на десятки мегабайт менші, поверхня для CVE значно менша, а запуск без root-доступу налаштовано типово. Компроміс: **у контейнері не можна запустити оболонку через `docker exec`**, щоб оглянути його зсередини — там немає `/bin/sh`. Для діагностики приєднайте тимчасовий контейнер налагодження або користуйтеся журналами й метриками.

> **Рекомендація:** у продакшені віддавайте перевагу середовищам виконання chiseled/distroless. Менші образи швидше завантажуються, дешевше зберігаються й мають меншу поверхню атаки. Залишайте варіант образу з оболонкою, лише якщо він справді потрібен операційним процесам.

### Підсумок оптимізації розміру образу

- Використовуйте багатоетапні збірки, щоб інструменти збірки не потрапляли до фінального образу.
- Обирайте найменший придатний базовий образ (`-alpine`, `-chiseled`).
- Упорядковуйте інструкції з урахуванням кешу: відновлюйте залежності до копіювання вихідного коду.
- Додавайте докладний `.dockerignore`.
- Об’єднуйте пов’язані команди `RUN` і видаляйте непотрібне в тому самому шарі (файл, видалений у *наступному* шарі, усе одно займає місце в попередньому).

## Docker Compose для локальної розробки

Справжній застосунок рідко складається з одного процесу. Можливо, йому потрібні база даних Postgres і кеш Redis. Запускати кожен сервіс вручну з правильними портами, змінними середовища й порядком запуску — нудно й ризиковано. **Docker Compose** описує стек із кількох контейнерів в одному YAML-файлі й запускає його однією командою.

```yaml
# docker-compose.yml
services:
  api:
    build:
      context: .
      dockerfile: MyApi/Dockerfile
    ports:
      - "8080:8080"          # host:container
    environment:
      ASPNETCORE_ENVIRONMENT: Development
      ConnectionStrings__Postgres: "Host=db;Port=5432;Database=appdb;Username=app;Password=devsecret"
      ConnectionStrings__Redis: "cache:6379"
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devsecret
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    command: ["redis-server", "--save", "60", "1"]

volumes:
  pgdata:
```

Тут показано кілька важливих понять:

- **Виявлення сервісів за назвою.** Compose розміщує всі сервіси в спільній мережі, де кожен доступний за назвою сервісу. API підключається до Postgres за адресою хоста `db`, а до Redis — за адресою `cache`: IP-адреси й `localhost` не потрібні. Саме тому в connection string вказано `Host=db`.
- **`depends_on` з `condition: service_healthy`**: Postgres потрібен час після запуску контейнера, щоб почати приймати підключення. Health check (перевірка працездатності) (`healthcheck`) виконує `pg_isready`, поки база даних справді не буде готова, і API чекає на цей стан, а не просто на запуск контейнера.
- **Іменований том `pgdata`**: файли бази даних розміщені в томі під керуванням Docker, тому дані зберігаються після `docker compose down` і повторного створення контейнера. Без тому кожне перезавантаження стирало б базу даних.
- **Конфігурація через середовище.** `ConnectionStrings__Postgres` використовує домовленість із подвійним підкресленням із попереднього розділу *Environment variables й те, як їх читає .NET*: `IConfiguration` читає її як `ConnectionStrings:Postgres`.

Запустіть стек командою `docker compose up --build`, а зупиніть командою `docker compose down` (том збережеться). Додайте `-v`, щоб також видалити томи.

> **Пастка:** `depends_on` без умови працездатності чекає лише на те, щоб контейнер *запустився*, а не на готовність сервісу всередині. Застосунок може запуститися раніше, ніж база даних почне слухати порт. Використовуйте health check й однаково додайте retries (повторні спроби) до запуску застосунку, адже в продакшені (Kubernetes) `depends_on` взагалі не існує.

## Реєстри контейнерів

Ви створили образ локально. Щоб запустити його на сервері або в Kubernetes, надішліть його до **реєстру** — сховища версій образів, як NuGet для контейнерів. Назва образу має вигляд `registry/repository:tag`.

- **Docker Hub** — типовий публічний реєстр. Чудово підходить для базових образів із open source (відкритим кодом); зважайте на rate limiting (обмеження частоти) завантажень для анонімних користувачів і надавайте перевагу офіційним або перевіреним видавцям.
- **Azure Container Registry (ACR)** — керований реєстр Microsoft із тісною інтеграцією з Azure AD і AKS. Вхід: `az acr login --name myregistry`; назва образу: `myregistry.azurecr.io/myapi:1.4.0`.
- **Amazon ECR** — аналог AWS з інтеграцією IAM та EKS.
- **GitHub Container Registry (GHCR)** — `ghcr.io/owner/myapi:1.4.0`; зручний, якщо ваш CI вже працює на GitHub Actions.

Послідовність надсилання й отримання образу:

```bash
docker build -t myregistry.azurecr.io/myapi:1.4.0 .
docker push myregistry.azurecr.io/myapi:1.4.0
docker pull myregistry.azurecr.io/myapi:1.4.0
```

> **Рекомендація:** позначайте образи незмінною змістовною версією — наприклад, semver `1.4.0` або SHA коміту Git. Не розгортайте `latest` у продакшені: цей тег змінюється, тож неможливо знати, яка саме збірка працює, а відкат перетворюється на здогадки.

## Перегляд журналів

На сервері, де застосунок працює як сервіс systemd ([Розділ 26](#systemd-running-a-net-app-as-a-service)), systemd записує stdout/stderr до **журналу**:

```bash
journalctl -u myapp                 # all logs for the myapp unit
journalctl -u myapp -f              # follow live (like tail -f)
journalctl -u myapp --since "10 min ago"
journalctl -u myapp -p err          # only error-priority and worse
journalctl -u myapp -n 100          # last 100 lines
```

Для контейнерів runtime збирає stdout/stderr; прочитати ці дані можна так:

```bash
docker logs myapp                   # all logs from a container
docker logs -f --tail 100 myapp     # follow the last 100 lines
kubectl logs -f deploy/myapp        # in Kubernetes
```

> **Рекомендація:** у контейнерах записуйте журнали в **stdout/stderr**, а не у файл. Уся екосистема — Docker, Kubernetes, агрегатори хмарних журналів — очікує журнали в stdout. Типовий консольний журналювач .NET працює саме так, тож залиште його налаштування без змін і дозвольте платформі збирати та надсилати журнали.

## Мережеві інструменти

Коли застосунок «не відповідає», потрібно перевірити, які порти слухають і чи можна звернутися до них напряму.

```bash
ss -tlnp                 # TCP (t) listening (l) sockets, numeric (n), + PID (p)
ss -tlnp | grep 5000     # is anything listening on port 5000?
netstat -tlnp            # older equivalent, if ss isn't available
```

`ss` (статистика сокетів) — сучасна заміна `netstat`. Якщо ваш процес прив’язаний до очікуваного порту, це підтверджує, що застосунок запустився й правильно прив’язався. Поширена помилка: застосунок прив’язується до `localhost` (127.0.0.1) усередині контейнера й стає недоступним ззовні. Прив’яжіть його до `0.0.0.0` (усіх інтерфейсів) через `ASPNETCORE_URLS=http://+:8080`.

Потім перевірте endpoint (кінцеву точку) з того самого хоста, щоб виключити мережу й брандмауер:

```bash
curl -v http://localhost:8080/health     # -v shows the connection + headers
```

Якщо `curl` усередині машини працює, а зовнішній доступ — ні, проблема в мережі (зіставленні портів, брандмауері, групі безпеки), а не у застосунку.

## Три запитання

**1.** Кожне розгортання сервісу зупиняє старі контейнери рівно за період очікування (10 секунд під `docker stop`, 30 у Kubernetes), запити, що виконуються в цей момент, завершуються помилкою, а код виходу зупиненого контейнера — 137. Dockerfile закінчується на `ENTRYPOINT dotnet MyApi.dll`. Що відбувається?

<details>
<summary>Відповідь</summary>

- **Shell-форма робить PID 1 оболонку.** `ENTRYPOINT dotnet MyApi.dll` зберігається як `["/bin/sh", "-c", "dotnet MyApi.dll"]`, і в образах на основі Debian оболонка (dash) запускає `dotnet` як дочірній процес, а не замінює себе ним ([Процеси й сигнали](#processes-signals-graceful-shutdown)).
- **SIGTERM надходить до PID 1, а цей PID 1 його ігнорує.** Середовище виконання надсилає сигнал лише процесу PID 1 контейнера. Ядро не застосовує дію сигналу за замовчуванням до PID 1 простору імен, тож процес, який не встановив обробника (а оболонка не встановила), просто не реагує й не передає сигнал дочірньому процесу. .NET, який почав би коректне завершення, про сигнал так і не дізнається.
- **Тож період очікування завжди спливає.** Після нього надсилається SIGKILL, який неможливо проігнорувати, і все завершується одразу, посеред запиту. 137 — це 128 + 9: процес завершено сигналом 9, SIGKILL. `docker stop` для контейнера, де PID 1 був `sh -c` з дочірнім процесом, тривав 10,2 секунди й завершився з кодом 137.

Виправлення: використовуйте exec-форму `ENTRYPOINT ["dotnet", "MyApi.dll"]`, щоб `dotnet` був PID 1 і Generic Host отримував SIGTERM. Якщо спершу має виконатися скрипт, завершіть його на `exec dotnet MyApi.dll` або запускайте контейнер з `--init`, що ставить на місце PID 1 невеликий init-процес для пересилання сигналів. Потім перевірте, що власний тайм-аут завершення застосунку вкладається в період очікування оркестратора.
</details>

**2.** Контейнер ізольований від хоста — то чому важливо, що його процес працює від root?

<details>
<summary>Відповідь</summary>

- **Ізоляцію забезпечує ядро, а ядро спільне.** Контейнер — це звичайний процес у просторах імен ([Дві функції ядра, завдяки яким це працює](#the-two-kernel-features-that-make-it-work)). Якщо не налаштовано простори імен користувачів (а Docker типово цього не робить), UID 0 у контейнері — це UID 0 для ядра хоста.
- **Тоді кожна межа — за одну помилку від хоста.** Вразливість ядра, що дає процесу вийти зі своїх просторів імен, дає зловмисникові root на хості. Так само й помилка конфігурації: змонтований сокет Docker, том із шляхом хоста, контейнер, запущений з `--privileged`. Усередині контейнера root також дає зловмисникові змогу встановлювати інструменти, переписувати файли застосунку й читати кожен секрет на диску.
- **Змонтовані каталоги виносять власника назовні.** Файли, які процес root записує в змонтований каталог хоста, на хості належать root.

Виправлення: запускайте від непривілейованого користувача — користувача `app` (UID 1654), що є в образах .NET від Microsoft, або використовуйте образ chiseled, де він типовий. Передайте цьому користувачеві у власність кілька каталогів, у які він пише, і додайте кореневу файлову систему лише для читання та скинуті capabilities (можливості ядра) ([Запуск без root-доступу](#running-as-non-root)).
</details>

**3.** Dockerfile образу копіює код, збирає його й закінчується на `RUN rm -rf /src /root/.nuget`. Образ однаково на кілька сотень мегабайтів більший за опублікований застосунок. Чому `rm` не допоміг?

<details>
<summary>Відповідь</summary>

- **Шари незмінні, і кожен із них — diff.** `COPY` і збирання створили по шару з цими файлами. `rm` створює новий шар, який фіксує «ці шляхи видалено» (whiteout); попередні шари й кожен байт у них лишаються частиною образу, завантажуються й зберігаються разом із ним ([Шари й кешування шарів](#layers-and-layer-caching)).
- **Файли невидимі, а не зниклі.** У запущеному контейнері видалених шляхів немає, тому й здається, що очищення спрацювало. `docker history <image>` показує правду: по шару на інструкцію з розміром, і великі шари під маленьким `rm`. Тестовий образ, що записав файл на 50 MB в одному `RUN` і видалив його в наступному, показав шар на 50 MB, а за ним шар на 4,1 kB.
- **Базовий образ теж має значення.** Збирання на основі образу SDK постачає весь SDK, хоч що б ви видалили потім.

Виправлення: багатоетапна збірка ([Багатоетапні збірки](#multi-stage-builds)). Збирайте й публікуйте на етапі SDK, а потім копіюйте лише опублікований результат у новий етап runtime (або chiseled); нічого з етапу збирання не потрапляє до фінального образу. Якщо тимчасові файли створює один `RUN`, видаляйте їх у тому самому `RUN`.
</details>

## Перевірте на роботі

**Проаналізуйте код.** У кожному Dockerfile, який постачає ваша команда, перевірте:

- `ENTRYPOINT` і `CMD`: exec-форма (`["dotnet", "App.dll"]`) або скрипт, що завершується на `exec`;
- інструкцію `USER` або базовий образ chiseled; без жодного з них процес працює від root;
- багатоетапну збірку, де фінальний `FROM` — образ runtime, і `.dockerignore` поруч із Dockerfile;
- базові образи, закріплені за версією (`aspnet:10.0` або digest), а не `latest`, і відсутність секретів в `ENV` чи `ARG`.

Потім порівняйте період очікування оркестратора (`terminationGracePeriodSeconds`) з `HostOptions.ShutdownTimeout` застосунку: застосунок має завершитися в межах вікна оркестратора.

**Виміряйте.** Для продакшн-образу: його розмір (`docker image ls`), найбільші шари (`docker history <image>`) і користувача, від якого він працює (`docker inspect --format '{{.Config.User}}' <image>`; порожнє значення означає root). Потім запустіть контейнер, надішліть йому запит, виконайте `docker stop` і заміряйте час: зупинка, що триває весь тайм-аут, і код виходу 137 означають, що SIGTERM так і не дійшов до .NET.

## Запитання для співбесіди

**Чим контейнер відрізняється від віртуальної машини?**

<details>
<summary>Відповідь</summary>

Віртуальна машина віртуалізує обладнання й запускає повну гостьову операційну систему з власним ядром. Контейнер — це процес на ядрі хоста, ізольований просторами імен і обмежений cgroups; другого ядра, яке треба завантажити, немає, тому контейнери стартують за мілісекунди й майже нічого не коштують у простої. Зворотний бік — слабша межа: вразливість ядра спільна для всіх контейнерів на хості ([Що таке контейнер](#what-a-container-actually-is)).
</details>

**Що роблять простори імен і що роблять cgroups?**

<details>
<summary>Відповідь</summary>

Простори імен визначають, що процес бачить: власне дерево процесів, де він сам — PID 1, власний мережевий стек і порти, власний корінь файлової системи й назву хоста. Cgroups визначають, що він може споживати: CPU, пам’ять і введення-виведення. Обмеження пам’яті в Kubernetes — це обмеження cgroup, і процес, що його перевищує, завершує механізм ядра OOM killer ([Дві функції ядра, завдяки яким це працює](#the-two-kernel-features-that-make-it-work)).
</details>

**Чим образ відрізняється від контейнера і куди потрапляє файл, записаний усередині контейнера?**

<details>
<summary>Відповідь</summary>

Образ — це стек шарів лише для читання плюс метадані; контейнер — його запущений екземпляр із тонким шаром для запису згори. Запис потрапляє в цей шар через copy-on-write і зникає разом із контейнером, тож усе, що має зберегтися, повинно йти в том або зовнішнє сховище ([Образи й контейнери](#images-vs-containers)).
</details>

**Як упорядкувати Dockerfile для швидких збірок і чому порядок має значення?**

<details>
<summary>Відповідь</summary>

Кожна інструкція створює шар, і кеш повторно використовує шар, лише поки інструкція та її вхідні дані не змінилися; перша ж зміна анулює цей шар і всі наступні. Тому спершу скопіюйте файли проєктів і виконайте `dotnet restore`, а вже потім скопіюйте решту коду: тоді редагування файлу `.cs` перебудовує лише шари після відновлення пакетів ([Шари й кешування шарів](#layers-and-layer-caching)).
</details>

**Що дає багатоетапна збірка?**

<details>
<summary>Відповідь</summary>

Етап збирання на основі образу SDK компілює й публікує застосунок, а фінальний етап починається з набагато меншого образу runtime (або chiseled) і копіює лише опублікований результат. SDK, вихідний код і кеш NuGet не потрапляють до фінального образу, тож він швидше завантажується й дає зловмисникові менше інструментів ([Багатоетапні збірки](#multi-stage-builds)).
</details>

**SIGTERM чи SIGKILL: що відбувається із застосунком .NET у кожному випадку?**

<details>
<summary>Відповідь</summary>

SIGTERM можна обробити: Generic Host перехоплює його, сигналізує `ApplicationStopping`, зупиняє hosted services і дає завершитися запитам, що виконуються. SIGKILL перехопити неможливо: ядро негайно завершує процес, посеред запиту. Оркестратори надсилають SIGTERM, чекають період очікування, а потім надсилають SIGKILL, тож застосунок має справді отримати SIGTERM (exec-форма `ENTRYPOINT`) і завершитися в межах цього періоду ([Процеси й сигнали](#processes-signals-graceful-shutdown)).
</details>

**Застосунок у контейнері, що працює від непривілейованого користувача, кидає `UnauthorizedAccessException` під час запису в `/app/data`. Чому і яке виправлення правильне?**

<details>
<summary>Відповідь</summary>

Каталог створено під час збирання від root із режимом `755`, тож створювати в ньому файли може лише root, а процес працює як UID 1654. Виправлення — передати каталог у власність користувачеві runtime (`RUN mkdir -p /app/data && chown -R app:app /app/data` перед `USER app`), а для змонтованого тому — узгодити його власника; повернення до root міняє помилку дозволів на діру в безпеці ([Дозволи](#permissions-why-your-container-app-cant-write-that-file)).
</details>

**Застосунок відповідає на `curl` усередині контейнера, але недоступний ззовні. Що перевірити насамперед?**

<details>
<summary>Відповідь</summary>

На якій адресі він слухає. `ss -tlnp` усередині контейнера показує прив’язану адресу: застосунок, прив’язаний до `127.0.0.1`, приймає з’єднання лише зсередини власного мережевого простору імен. Прив’яжіть його до всіх інтерфейсів (`ASPNETCORE_URLS=http://+:8080` або `ASPNETCORE_HTTP_PORTS`, який образи .NET 8+ задають як 8080), а потім перевірте прокидання портів і брандмауер ([Мережеві інструменти](#networking-tools)).
</details>
