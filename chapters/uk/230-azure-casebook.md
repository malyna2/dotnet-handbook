# Розділ 30: Збірник випадків Azure — реальні інциденти, реальні виправлення

[У розділі 29](#chapter-29-azure-in-depth-for-net-developers) пояснено, як працює Azure. Цей розділ — про те, що відбувається, коли Azure зустрічається з продакшеном. Кожен випадок описує ситуацію, з якою команди .NET в Azure стикаються знову й знову. Це узагальнені приклади типових інцидентів, а не розбір events (події) в одній конкретній компанії. Кожен випадок має ті самі шість частин:

- **Ситуація**: що робила команда і що пішло не так.
- **Що ви бачите**: симптоми, які доходять до вас.
- **Що відбувається**: механізм, зазвичай нюанс із розділу 29.
- **Як це підтвердити**: команда, запит або експеримент, що перетворює припущення на діагноз.
- **Виправлення**: що змінити зараз і як виправити належним чином.
- **Як запобігти** та **Погляд на співбесіді**: звичка, що не дасть проблемі повторитися, і спосіб розповісти цю історію.

Прочитайте *Ситуацію* і *Що ви бачите* в одному випадку, зупиніться й запишіть власний діагноз, перш ніж читати далі. Ця звичка стане в пригоді і о третій ночі, і на співбесіді з проєктування систем. [Розділ 35](#chapter-35-production-incidents) розглядає так само сценарії, не прив’язані до конкретної хмарної платформи. Цей розділ присвячений Azure.

## Картка первинного аналізу Azure

Коли щось ламається, першою підозрою рідко має бути бізнес-логіка. Почніть із симптому:

| Симптом | Перша підозра | Перша перевірка |
|---|---|---|
| `403` від служби даних (Blob, Key Vault, Service Bus, Cosmos) | Немає ролі для рівня даних або її ще не поширено · неправильна ідентичність · мережеве правило | Код помилки (`AuthorizationPermissionMismatch` = RBAC); кому належить токен (`oid`); `az role assignment list --assignee <principal-id> --all` |
| `403` *після* ввімкнення приватної endpoint (кінцевої точки) | DNS повертає публічну IP-адресу | `nslookup <name>` **усередині** застосунку |
| Періодичні тайм-аути під навантаженням, процесор працює нормально | Вичерпання SNAT-портів · вичерпання connection pool (пулу з’єднань) · голодування thread pool (пулу потоків) ([розділ 4](#chapter-4-async-essentials)) | App Service *Diagnose and solve problems* → *SNAT Port Exhaustion*; збої залежностей в App Insights |
| Помилки 500 протягом хвилини після кожного deployment (розгортання) | Холодний запуск після перемикання слотів · налаштування, що перемістилися під час перемикання | Налаштування прогрівання; які параметри є параметрами слота |
| Повідомлення обробляються двічі | Завершився час блокування · збій між побічним ефектом і підтвердженням · немає ідемпотентності | `DeliveryCount` у повідомленні; `MessageLockLost` у журналах |
| Queue (черга) зростає, consumer (споживачі) «працюють нормально» | Циклічна обробка отруйних повідомлень · заповнюється queue недоставлених · consumers обмежує downstream-система | Метрики `ActiveMessages`, `DeadletteredMessages` |
| `429` від Cosmos, хоча виділено менше RU/s | Гарячий розділ | *Normalized RU Consumption* із розбивкою за `PartitionKeyRangeId` |
| `40613` / `40501` / `10928` від Azure SQL | Перемикання відмовостійкості (тимчасова помилка) · обмеження запитів · ліміт робочих потоків (надто висока паралельність) | Номер помилки; метрики ресурсів бази даних; кількість підключених клієнтів |
| Під час інциденту немає телеметрії | Досягнуто денний ліміт · семплювання · застосунок вимкнувся і не подає сигналів | Параметр ліміту Application Insights; тест доступності |

## Випадок 1 — «У нього Contributor на всю підписку, але все одно 403»

**Ситуація.** Команда переходить із connection strings (рядків підключення) з ключами облікового запису на managed identity (керовану ідентичність). У порталі вони призначають системній ідентичності App Service роль *Contributor* на рівні підписки, «щоб більше про це не думати». Deployment проходить успішно, але кожен виклик Blob Storage завершується помилкою.

**Що ви бачите.**

```
Azure.RequestFailedException: This request is not authorized to perform this operation using this permission.
Status: 403 (This request is not authorized to perform this operation using this permission.)
ErrorCode: AuthorizationPermissionMismatch
```

**Що відбувається.** Три окремі помилки дають однаковий 403; ця команда припустилася першої:

1. **Площина керування і площина даних.** Роль *Contributor* дає змогу керувати обліковим записом сховища (його `Actions`), але не містить `DataActions`. Щоб читати blob за токеном Entra, потрібна роль для даних, наприклад *Storage Blob Data Reader* або *Storage Blob Data Contributor*.
2. **Поширення ролі.** Призначення ролей може набувати чинності до 10 хвилин, а виданий раніше токен зберігає старий вміст до завершення строку дії.
3. **Не той суб’єкт.** Роль призначили реєстрації застосунку, а не managed identity, або ідентичності продакшен-слота, хоча виклик робить staging-слот (у якого окрема системна ідентичність).

Є і четвертий варіант, який стосується користувачів Cosmos DB: для RBAC рівня даних Cosmos DB використовує власні призначення ролей, тож жодна роль Azure RBAC у панелі IAM не надає доступу до елементів.

Зверніть увагу також на те, чого команда *насправді* хотіла досягти: Contributor на всю підписку — надмірно широкі права для застосунку. Якщо застосунок скомпрометують, зловмисник зможе видалити будь-який ресурс у підписці та отримати всі ключі облікових записів сховища в ній.

**Як це підтвердити.**

```bash
# Which principal is the app really using? (object ID of the managed identity)
az webapp identity show -g shop-rg -n shop-api --query principalId -o tsv

# What can that principal do, at every scope?
az role assignment list --assignee <principal-id> --all -o table
```

Якщо у списку є лише `Contributor`, відповідь знайдено. Якщо там є потрібна роль для даних, перевірте, *коли* її створено, та пошукайте призначення заборони.

**Виправлення.** Видаліть роль Contributor, призначену на всю підписку. Призначте ідентичності *Storage Blob Data Contributor* в межах єдиного потрібного їй контейнера. Розгортайте це призначення в тому самому модулі Bicep, що й обліковий запис сховища (розділ 29, *Інфраструктура як код*). Використовуйте **призначену користувачем** ідентичність, щоб призначення існувало до запуску застосунку й не доводилося чекати поширення під час deployment.

**Як запобігти.** Призначення ролей зберігаються в IaC і проходять перевірку коду; їхня область дії — ресурс або контейнер. Ніхто не додає їх кліками в порталі. Додайте Azure Policy (або хоча б періодичний запит), що виявляє призначення Owner і Contributor суб’єктам-службам на рівні підписки.

**Погляд на співбесіді.** «Поясніть різницю між доступом до площини керування і площини даних» — поширене запитання для досвідченого інженера. Наведіть цей випадок як приклад і завершіть принципом найменших привілеїв: *ми замінили Contributor на всю підписку роллю для даних в межах контейнера й визначили її в тому самому шаблоні, що й контейнер*.

## Випадок 2 — «На моєму комп’ютері працює, а в Azure — ні»: ланцюжок credentials обрав неправильну ідентичність

**Ситуація.** Фоновий процес без проблем працює локально та в тестовому середовищі. У продакшені він отримує від Key Vault помилки 401. Код між середовищами не змінювався. Інший варіант: той самий код починає збоїти після того, як хтось додає до застосунку другу ідентичність, призначену користувачем.

**Що ви бачите.**

```
Azure.Identity.AuthenticationFailedException: ClientSecretCredential authentication failed:
AADSTS7000222: The provided client secret keys for app '3f2a…' are expired.
```

або, у другому варіанті:

```
ManagedIdentityCredential authentication unavailable. ... Multiple user assigned identities exist,
please specify the clientId / resourceId of the identity in the token request
```

**Що відбувається.** `DefaultAzureCredential` проходить ланцюжок credentials (облікових даних), і перший доступний варіант перемагає. Першим іде `EnvironmentCredential`. Колись хтось додав `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` і `AZURE_CLIENT_SECRET` до параметрів продакшен-застосунку для швидкої перевірки. Відтоді застосунок працював від імені старого суб’єкта-служби, а не managed identity, доки не завершився строк дії секрету. У помилці згадується `ClientSecretCredential` — це підказка: managed identity ніколи не використовує клієнтський секрет.

У другому варіанті `ManagedIdentityCredential` не може вибрати між двома ідентичностями, призначеними користувачем, бо йому не вказали, яку саме використовувати.

**Як це підтвердити.** Увімкніть logging (журналювання) Azure SDK — ланцюжок повідомить про кожну спробу. З `AddAzureClients` events SDK уже надходять до `ILogger`. Для одного запуску встановіть для категорії `Azure.Identity` рівень `Information` або `Debug`:

```json
{ "Logging": { "LogLevel": { "Azure.Identity": "Debug" } } }
```

Потім перелічіть параметри застосунку, що починаються з `AZURE_`, і декодуйте твердження `oid` отриманого застосунком токена, щоб підтвердити, кому він належить.

**Виправлення.** Видаліть сторонні параметри `AZURE_*`. У продакшені явно створюйте `ManagedIdentityCredential`, передавши ідентифікатор клієнта ідентичності, призначеної користувачем (код наведено в розділі 29, *Ідентичність*). Або залиште `DefaultAzureCredential`, але задайте `AZURE_TOKEN_CREDENTIALS` значення `ManagedIdentityCredential` (або `prod`), а `AZURE_CLIENT_ID` — ідентифікатор клієнта цієї ідентичності. Використовуйте `DefaultAzureCredential` лише під час розробки.

**Як запобігти.** Параметри застосунку слід трактувати як код: генерувати їх з IaC і сповіщати про відхилення. Правило політики або рядок у pipeline (конвеєрі) deployment, який відхиляє `AZURE_CLIENT_SECRET` у параметрах продакшену, нічого не коштує.

**Погляд на співбесіді.** Цей випадок показує, що ви розумієте, *чому* зручні API мають застереження для продакшену, — це ознака досвідченого інженера. Назвіть ланцюжок, пріоритети та поясніть, як зробили поведінку передбачуваною.

## Випадок 3 — Періодичні тайм-аути під навантаженням, хоча всі панелі зелені

**Ситуація.** API замовлень в App Service (3 × P1v3) викликає платіжного та логістичного провайдерів через HTTPS. Під час рекламної кампанії кілька відсотків запитів завершуються тайм-аутом. Завантаження процесора — 35%, використання пам’яті не змінюється, провайдери кажуть, що в них усе працює, а збільшення кількості екземплярів до 6 *трохи допомагає*.

**Що ви бачите.**

```
System.Net.Http.HttpRequestException: A connection attempt failed because the connected party did not
properly respond after a period of time ... (payments.example.com:443)
 ---> System.Net.Sockets.SocketException (10060)
```

В Application Insights невдалі виклики залежностей згруповані за екземпляром і з’являються лише після перевищення певної частоти запитів.

**Що відбувається.** **Вичерпано SNAT-порти.** Вихідні з’єднання з App Service до інтернету проходять через source NAT; кожен екземпляр має 128 попередньо виділених SNAT-портів для кожної адреси й порту призначення. Під час перевірки коду виявляється такий фрагмент, що виконується на кожен запит:

```csharp
public async Task<PaymentResult> ChargeAsync(Charge charge, CancellationToken ct)
{
    using var http = new HttpClient { BaseAddress = new Uri(_options.BaseUrl) };   // new connection pool per call
    var response = await http.PostAsJsonAsync("/v1/charges", charge, ct);
    response.EnsureSuccessStatusCode();
    return (await response.Content.ReadFromJsonAsync<PaymentResult>(ct))!;
}
```

Кожен виклик відкриває нове TCP-з’єднання з тим самим вузлом, а балансувальник звільняє SNAT-порт лише через чотири хвилини після закриття з’єднання. Якщо відкривати понад одне нове з’єднання приблизно кожні дві секунди на екземпляр, попередньо виділені порти закінчуються ([у розділі 5 наведено розрахунок](#keep-alive-connection-pooling-and-socket-exhaustion)). Нові з’єднання чекають, доки Azure виділить порт або звільнить зайнятий; під час сплеску навантаження вони завершуються тайм-аутом. Збільшення кількості екземплярів «трохи допомагає», бо кожен отримує власні порти, — це також підказка.

**Як це підтвердити.** На порталі: App Service → *Diagnose and solve problems* → засіб **SNAT Port Exhaustion** показує кількість виділених і невдалих SNAT-з’єднань для кожного екземпляра. У коді пошукайте `new HttpClient(`, `new BlobServiceClient(`, `new CosmosClient(` і `new ServiceBusClient(` поза кодом запуску. (`new SqlConnection(` на кожен виклик — нормально: ADO.NET об’єднує фізичні з’єднання в пул.)

**Виправлення.**

1. **Повторно використовуйте з’єднання.** Використовуйте типізований клієнт з `IHttpClientFactory`, яка об’єднує handlers (обробники) в пул, а клієнти SDK реєструйте як singleton:

```csharp
builder.Services.AddHttpClient<PaymentClient>(c => c.BaseAddress = new Uri(builder.Configuration["Payments:BaseUrl"]!))
    .AddStandardResilienceHandler();   // Microsoft.Extensions.Http.Resilience: timeouts, retries, circuit breaker
```

2. **Перенесіть трафік Azure з SNAT.** Виклики служб Azure через приватні endpoints (або кінцеві точки служб) залишаються всередині VNet і не використовують SNAT-порти.
3. **Додайте шлюз NAT** до підмережі інтеграції VNet: 64 512 портів на кожну публічну IP-адресу та стабільна IP-адреса вихідного трафіку, яку платіжний провайдер може додати до списку дозволених.

**Як запобігти.** Додайте правило аналізатора або пункт контрольного списку перевірки коду проти `new HttpClient()` у шляхах обробки запитів. Навантажуйте систему реалістичним *вихідним* трафіком, а не лише вхідними запитами: проблема SNAT не проявиться в тестах, де провайдерів замінено заглушками.

**Погляд на співбесіді.** Це вдала історія, бо діагноз суперечить інтуїції: вичерпався не процесор і не пам’ять, а порти; це підтверджувало групування помилок за екземплярами.

## Випадок 4 — Хвилина помилок 500 після кожного deployment

**Ситуація.** Команда розгортає застосунок у staging-слот і перемикає його в production, як і рекомендовано. Після кожного перемикання production повертає помилки 500 і дуже повільні відповіді протягом 30–90 секунд. Одного разу після перемикання production протягом двадцяти хвилин записував замовлення в базу даних *staging*.

**Що ви бачите.** Сплеск помилок 5xx і затримки протягом хвилини після кожного перемикання. У випадку з базою даних замовлень немає у звітах production, але згодом їх знаходять у базі staging.

**Що відбувається.** Є дві окремі проблеми, і обидві спричинені порядком кроків перемикання (розділ 29, *Слоти deployment*):

1. **Немає справжнього прогрівання.** За замовчуванням під час перемикання кожен екземпляр прогрівається запитом до `/`, а «будь-яка HTTP-відповідь» вважається готовністю. `/` цього API миттєво повертає 404, тому перемикання вважає екземпляр готовим, хоча перший справжній запит іще чекає на JIT-компіляцію, побудову моделі EF Core, перші з’єднання з базою даних і заповнення кешів.
2. **Параметр не був закріплений за слотом.** Connection string був звичайним параметром застосунку в обох слотах, а не *параметром слота deployment*. Параметри, не закріплені за слотом, **переміщуються разом із кодом** під час перемикання, тож значення зі staging-слота потрапило в production.

**Як це підтвердити.** Зіставте сплески 5xx із часом перемикання (вони записуються в журналі активності). Для параметрів порівняйте конфігурації слотів і перевірте, які з них мають ознаку слота: `az webapp config appsettings list --slot staging` показує `"slotSetting": true|false` для кожного.

**Виправлення.**

- Позначте кожне значення, залежне від середовища (connection strings, endpoints, перемикачі функцій, що відрізняються між середовищами), як **параметр слота deployment**.
- Додайте endpoint прогрівання, який перевіряє справжні залежності застосунку, і спрямовуйте перемикання на неї:

```
WEBSITE_SWAP_WARMUP_PING_PATH     = /health/warmup
WEBSITE_SWAP_WARMUP_PING_STATUSES = 200
```

  Зі списком статусів невдале прогрівання (наприклад, відповідь 503 через недоступну базу даних) **зупиняє перемикання**, а не активує несправну збірку.
- Нехай endpoint `/health/warmup` виконує дорогу роботу під час першого запуску: відкриває з’єднання з базою даних, ініціалізує модель EF Core, заповнює критичні кеші.
- Для ризикованих випусків використовуйте **перемикання з попереднім переглядом**: staging-слот перезапускається з параметрами production, і ви тестуєте його до переміщення трафіку.

**Як запобігти.** Додайте до контрольного списку deployment запитання: *кожен новий параметр — закріплений за слотом чи ні?* Ще краще, формуйте параметри слотів з IaC, де закріплення є частиною визначення. Налаштуйте сповіщення про частку 5xx протягом десяти хвилин після перемикання, щоб виявити невдале перемикання за хвилини, а не з завтрашнього звіту.

**Погляд на співбесіді.** «Як забезпечити deployment App Service без простою?» Слоти, порядок перемикання, прогрівання, закріплені параметри та зворотна сумісність міграцій бази даних із версією, що обслуговує трафік ([розділ 13](#chapter-13-git-and-cicd), розширення/звуження схеми).

## Випадок 5 — Клієнтам двічі виставили рахунок: пакет пережив блокування повідомлень

**Ситуація.** Handler платежів читає команди `ChargeCard` з queue Service Bus. Щоб «зменшити кількість запитів», розробник змінив його так, щоб отримувати 50 повідомлень за раз і обробляти їх по одному. Кожне повідомлення викликає платіжного провайдера, що займає близько 2 секунд. Уже за день служба підтримки повідомляє про подвійні списання.

**Що ви бачите.** У журналах — `ServiceBusException` з `Reason = MessageLockLost` під час `CompleteMessageAsync`, а також повідомлення з `DeliveryCount` зі значенням 2 або 3 у журналах handler. Дубльовані списання мають однаковий `MessageId`.

**Що відбувається.** Блокування кожного отриманого в пакеті повідомлення починається **в момент отримання**. Типова тривалість блокування queue — 1 хвилина. Обробка 50 повідомлень по 2 секунди триває 100 секунд, тож приблизно після 30-го повідомлення решта обробляється *після завершення блокування*. Service Bus знову робить повідомлення видимим, і його отримує інший приймач (або той самий у наступному циклі). Списання виконується двічі, а початковий `Complete` завершується помилкою `MessageLockLost`. Попереднє отримання повідомлень спричиняє те саме: вони блокуються, поки чекають у пам’яті.

**Як це підтвердити.** Друга вправа *Знайдіть помилку* в цьому розділі відтворює проблему з емулятором Service Bus: час блокування скорочено до 5 секунд, а handler працює 1 секунду. У контрольному запуску 12 повідомлень спричинили 14 викликів handler: два збої `MessageLockLost`, два замовлення оброблено двічі. У продакшені зіставте `DeliveryCount > 1` у журналах handler з тривалістю блокування й розміром пакета.

**Виправлення.** Потрібні обидва рівні:

1. **Не допускайте, щоб обробка перевищувала тривалість блокування.** Використовуйте `ServiceBusProcessor`: він поновлює блокування повідомлення, поки виконується handler (`MaxAutoLockRenewalDuration`, типово 5 хвилин), і отримує стільки повідомлень, скільки має handlers. Для пропускної здатності збільшуйте `MaxConcurrentCalls`, а не використовуйте пакетну обробку. Якщо пакети необхідні, добуток `batch size × processing time` має значно поступатися тривалості блокування або поновлюйте блокування самостійно.
2. **Зробіть списання ідемпотентним**, оскільки завершення блокування — лише одна з кількох причин повторної доставки. Передавайте `PaymentId` провайдеру як idempotency key (ключ ідемпотентності) (більшість платіжних API підтримують його) і записуйте оброблені ідентифікатори в одній транзакції зі станом бізнес-операції ([розділ 11](#chapter-11-messaging-and-background-work), ідемпотентний consumer).

**Як запобігти.** Вважайте доставку «щонайменше один раз» вимогою проєктування, а не крайнім випадком. Тест із коротким часом блокування, як у вправі, виявить помилку пакетної обробки в CI.

**Погляд на співбесіді.** «Як гарантувати обробку рівно один раз?» Чесна відповідь: *не можна; забезпечте доставку щонайменше один раз і зробіть обробку ідемпотентною*. Цей випадок підтверджує, що ви розумієте, що це означає на практиці.

## Випадок 6 — 40 000 повідомлень у queue недоставлених, і ніхто про це не знав

**Ситуація.** Фінансовий відділ помічає, що рахунки за частину замовлень не надіслали. Handler рахунків здається справним: він працює, queue короткий, помилок за останню годину немає.

**Що ви бачите.** На порталі в queue `invoices` небагато активних повідомлень і **40 000 недоставлених повідомлень**, накопичених за три тижні. Для найстарішого значення `DeadLetterReason` — `MaxDeliveryCountExceeded`.

**Що відбувається.** Три тижні тому deployment змінив схему рахунку, і повідомлення про замовлення зі знижковим кодом перестали десеріалізуватися. Кожне таке повідомлення залишали необробленим 10 разів (типове `MaxDeliveryCount`), а потім переміщували до queue недоставлених — саме так має працювати Service Bus. Платформа виконала свою роботу, але операційний процес — ні: сповіщення про кількість недоставлених повідомлень не було, як і способу повторно їх надіслати.

Ще дві помилки погіршили ситуацію. Handler вважав *постійну* помилку (повідомлення, яке неможливо десеріалізувати) тимчасовою, тож кожне помилкове повідомлення оброблялося 10 разів до переміщення. Кожну невдалу спробу він записував як попередження, яке ніхто не читав.

**Як це підтвердити.** Метрика `DeadletteredMessages` для сутності покаже, коли почався ріст. Зіставте його з історією розгортань. Перегляньте кілька недоставлених повідомлень і перевірте `DeadLetterReason`, `DeadLetterErrorDescription` та властивості застосунку.

**Виправлення.**

1. Виправте помилку схеми, розгорніть зміни й **повторно надішліть** недоставлені повідомлення. Кожній команді, що використовує Service Bus, потрібен такий інструмент:

```csharp
public static async Task<int> ResubmitDeadLettersAsync(ServiceBusClient client, string queue, int max, CancellationToken ct)
{
    await using ServiceBusReceiver dlq = client.CreateReceiver(queue, new ServiceBusReceiverOptions { SubQueue = SubQueue.DeadLetter });
    await using ServiceBusSender sender = client.CreateSender(queue);

    int moved = 0;
    while (moved < max)
    {
        IReadOnlyList<ServiceBusReceivedMessage> batch =
            await dlq.ReceiveMessagesAsync(maxMessages: 20, maxWaitTime: TimeSpan.FromSeconds(5), ct);
        if (batch.Count == 0) break;

        foreach (ServiceBusReceivedMessage dead in batch)
        {
            // The copy constructor keeps body, MessageId, SessionId and application properties.
            var retry = new ServiceBusMessage(dead);
            retry.ApplicationProperties["resubmittedFromDlq"] = DateTimeOffset.UtcNow.ToString("O");

            await sender.SendMessageAsync(retry, ct);       // send first …
            await dlq.CompleteMessageAsync(dead, ct);       // … then remove: a crash in between duplicates, never loses
            moved++;
        }
    }
    return moved;
}
```

   Оскільки consumer ідемпотентний (випадок 5), повторна відправка вже обробленого повідомлення не зашкодить.

2. **Класифікуйте помилки в handler.** Помилки десеріалізації, перевірки та випадок «сутності більше не існує» — постійні: *негайно* переміщуйте такі повідомлення до queue недоставлених із причиною й описом, на який людина може відреагувати. Тайм-аути, 429 і 503 від залежностей — тимчасові: викиньте exception (виняток) і дозвольте повторно доставити повідомлення.

**Як запобігти.** Для кожної бізнес-черги налаштуйте сповіщення про `DeadletteredMessages > 0` і спрямуйте його відповідальній команді. Додайте queue недоставлених до інструкції з експлуатації з посиланням на інструмент повторного надсилання. Під час перегляду проєкту запитуйте: «Що робить цей consumer із повідомленням, яке він ніколи не зможе обробити?»

**Погляд на співбесіді.** Цей випадок демонструє відповідальність за межами коду: *платформа поводилася правильно, а нам бракувало операційного процесу навколо неї*. Інтерв’юери цінують інженерів, які завершують цей процес.

## Випадок 7 — Functions масштабувалася й поклала базу даних

**Ситуація.** Нічний імпорт надсилає 200 000 повідомлень у queue Service Bus. Функція на плані Flex Consumption обробляє їх, і кожне повідомлення виконує два записи SQL. Раніше імпорт тривав годину на віртуальній машині. Тепер за кілька хвилин падає весь магазин, зокрема клієнтський API, із помилками SQL.

**Що ви бачите.**

```
Microsoft.Data.SqlClient.SqlException (0x80131904): Resource ID : 1. The request limit for the database is 200 and has been reached.
```

Це помилка **10928**: досягнуто ліміту робочих потоків бази даних. Графік CPU Azure SQL показує 100%. Кількість екземплярів застосунку-функції за кілька хвилин зросла з одного до кількох десятків.

**Що відбувається.** Безсерверне масштабування працює саме як обіцяно. Queue був довгим, тому платформа додала екземпляри. Кожен екземпляр обробляв тригер Service Bus із типовою паралельністю (16 на ядро). Кілька десятків екземплярів × 16 або 32 одночасні запуски — понад тисяча SQL-сеансів до бази, розрахованої на звичайне навантаження магазину. База досягла ліміту робочих потоків і не могла відрізнити сеанси імпорту від сеансів оформлення замовлення.

**Як це підтвердити.** Побудуйте на одному графіку кількість екземплярів застосунку-функції та метрики робочих потоків і сеансів бази даних. Вони зростатимуть разом. Номер помилки 10928 вказує на конкретну проблему: не «база працює повільно», а «надто багато одночасних запитів».

**Виправлення.** Обмежте загальну паралельність відповідно до можливостей бази й зменште вартість кожної одиниці роботи:

- Обмежте паралельність на екземпляр у `host.json` (`maxConcurrentCalls`) і встановіть верхню межу **кількості екземплярів** застосунку-функції. Добуток цих значень визначає максимальну кількість одночасних операцій SQL, яку може створити імпорт. Виберіть її за лімітами бази, залишивши запас для магазину.
- Групуйте записи. Отримуйте повідомлення пакетами (тригер може зв’язати їх із `ServiceBusReceivedMessage[]`) і записуйте весь пакет за один мережевий обмін, використовуючи табличний параметр або `SqlBulkCopy`.
- Ізолюйте навантаження. Запускайте імпорт в окремій базі, еластичному пулі з лімітами на базу або в окреме часове вікно, щоб пакетне завдання не могло позбавити ресурсів оформлення замовлення.

**Як запобігти.** Для кожного consumer events запишіть його *максимальну* паралельність і звірте її з можливостями кожної downstream-системи: бази, API партнерів і лімітів запитів. Це *вирівнювання навантаження через queue*: queue приймає сплеск, а consumer забирають повідомлення зі швидкістю, яку може витримати downstream-система. Для цього швидкість вилучення треба обмежити.

**Погляд на співбесіді.** «Які ризики безсерверної архітектури?» Більшість кандидатів назве холодні запуски. Тут доречніша відповідь досвідченого інженера: *еластичні обчислення перед нееластичними залежностями* — і спосіб обмежити масштабування.

## Випадок 8 — Cosmos DB обмежує запити, використовуючи лише третину виділеної пропускної здатності

**Ситуація.** Мультитенантна SaaS-система зберігає всі документи в одному контейнері Cosmos DB із ключем розділу `/tenantId` і виділеними 30 000 RU/s. Підключається великий клієнт, на якого припадає близько 40% усього трафіку. Відтоді він отримує помилки 429 у робочі години, хоча метрики облікового запису показують лише близько 11 000 RU/s загалом.

**Що ви бачите.** `CosmosException` зі статусом 429 (TooManyRequests) доходить до застосунку: дев’яти автоматичних retries (повторних спроб) SDK не вистачило. Затримка зростає лише для *цього* клієнта.

**Що відбувається.** **Гаряче логічне розділення.** Усі документи великого клієнта мають однакове значення ключа розділу, тож вони розташовані в одному логічному розділі на одному фізичному розділі. Фізичний розділ обслуговує не більше 10 000 RU/s незалежно від загальної пропускної здатності контейнера. Пропускна здатність ділиться між фізичними розділами, тож цьому дістається лише частина з 30 000 RU/s, а трафіку клієнта потрібно більше. Інші фізичні розділи простоюють. Наступною проблемою буде ліміт 20 ГБ на логічний розділ.

**Як це підтвердити.** У *Insights* (або Metrics) облікового запису Cosmos DB перегляньте **Normalized RU Consumption** із розбивкою за `PartitionKeyRangeId`. Один діапазон завантажено на 100%, решта — слабо. Діагностика обмежених запитів показує той самий діапазон ключів розділу.

**Виправлення.** Розподіліть клієнта між розділами, зберігши запити в одному розділі для поширеного випадку:

- **Ієрархічні ключі розділів** (`/tenantId`, потім `/userId` або `/documentId`): запити з фільтром за `tenantId` звертатимуться лише до розділів клієнта, а його дані розподіляться між багатьма фізичними розділами й можуть перевищити 20 ГБ.
- Або **синтетичний ключ**, як-от `tenantId-bucket`, де bucket — це хеш ідентифікатора документа за модулем N. Записи розподіляться, але запити клієнта мають звертатися до N bucket-ів.

У будь-якому разі потрібна **міграція**: створіть новий контейнер із новим ключем, скопіюйте дані через change feed (процесор читає старий контейнер і записує в новий), перемкніть читання, а потім записи. Плануйте це як окремий проєкт.

**Як запобігти.** Проєктуйте ключі розділів з огляду на *найбільшого* клієнта, а не середнього. Налаштуйте сповіщення про нормалізоване споживання RU для кожного діапазону розділів, а не лише загалом. Тестуйте з реалістичною нерівномірністю даних: рівномірні синтетичні дані не виявляють гарячого розділу. [У розділі 18](#chapter-18-data-in-depth) докладніше розглянуто проєктування даних для мультитенантних систем.

**Погляд на співбесіді.** Запитання про розділення Cosmos DB часто трапляються на співбесідах з Azure. Сильна відповідь називає ліміти окремого розділу, пояснює, чому збільшення RU/s не допомогло, і чесно описує міграцію.

## Випадок 9 — Рахунок за Cosmos DB подвоївся після невеликої функції

**Ситуація.** Команда додає сторінку адміністратора «замовлення за статусом» і нічний експорт. У наступному рахунку вартість Cosmos DB подвоюється, а автомасштабування більшу частину дня працює на максимальному значенні.

**Що ви бачите.** Споживання RU зросло, хоча трафік користувачів не змінився. У журналі експорту (на щастя, команда записувала `RequestCharge`) є запит, що коштує тисячі RU на сторінку.

**Що відбувається.** Разом діють дві причини:

1. **Запити до всіх розділів у часто виконуваному потоці.** У `SELECT * FROM c WHERE c.status = 'Open' ORDER BY c.createdAt` немає фільтра за ключем розділу, тож запит надсилається кожному фізичному розділу. Сторінка адміністратора оновлює його кожні 30 секунд у кожній відкритій вкладці браузера.
2. **Типове індексування для контейнера з великою кількістю записів.** Індекс створюється для кожної властивості кожного замовлення, включно з великим масивом `lineItems`, який не використовує жоден запит. Тож кожен запис оновлює індекси кожного елемента.

**Як це підтвердити.** Записуйте `RequestCharge` за типом запиту (у прикладі `OrderStore` в розділі 29 показано як). Перегляньте метрики Cosmos DB: загальну кількість одиниць запиту за типом операції. Перевірте політику індексування контейнера.

**Виправлення.**

- Формуйте адміністративне подання з **проєкції**: невеликого контейнера або таблиці SQL, яку change feed підтримує в актуальному стані й розділяє за статусом і часовим bucket. Або з’ясуйте, чи потрібне це подання в реальному часі.
- Запускайте експорт з **аналітичної копії** даних (наприклад, дзеркала Cosmos DB у Microsoft Fabric) або з change feed, а не запитуйте транзакційний контейнер.
- **Виключіть** `/lineItems/*` та інші невикористовувані в запитах шляхи з індексування й додайте **складений індекс** для сортування за `status` і `createdAt`.

**Як запобігти.** Зробіть `RequestCharge` видимим: записуйте його під час розробки та додайте тест, що перевіряє верхню межу витрат RU для найчастіших запитів, так само, як лабораторна робота з розділу 19 перевіряє *роботу*, а не час. Під час перевірки нових запитів регулярно перевіряйте наявність фільтра за ключем розділу, як перевіряєте наявність індексу в SQL.

**Погляд на співбесіді.** Вартість — інженерна метрика. «Я знайшов три запити, на які припадало 80% витрат RU, і зменшив рахунок на [X]%» — сильний пункт резюме, якщо використовувати числа зі своєї системи.

## Випадок 10 — Приватний endpoint, який погіршив ситуацію

**Ситуація.** Перевірка безпеки вимагає прибрати обліковий запис сховища й Key Vault із публічного інтернету. Команда додає приватні endpoints для обох, вимикає публічний мережевий доступ і розгортає зміни. API в App Service одразу перестає працювати.

**Що ви бачите.**

```
Azure.RequestFailedException: This request is not authorized to perform this operation.
Status: 403 ... ErrorCode: AuthorizationFailure
```

Key Vault повертає 403 із повідомленням, що публічний мережевий доступ вимкнено, а запит надійшов не з довіреної служби й не через приватне з’єднання. Той самий код працює з віртуальної машини у VNet.

**Що відбувається.** Застосунок досі визначає *публічну* адресу. Потрібні три складники, але одного бракує:

1. **Інтеграція застосунку з VNet.** Без неї вихідні виклики застосунку взагалі не потрапляють у VNet.
2. **Приватні DNS-зони** (`privatelink.blob.core.windows.net`, `privatelink.vaultcore.azure.net`) з A-записами endpoints, **пов’язані з VNet**, до якої інтегровано застосунок.
3. **Розв’язання DNS через Azure DNS.** Якщо у VNet власні DNS-сервери (контролер домену або брандмауер), вони мають переспрямовувати запити `privatelink.*` на Azure DNS за адресою `168.63.129.16`.

Віртуальна машина працює, бо розташована у VNet, де налаштовано всі три складники. Зону так і не пов’язали з VNet інтеграції застосунку.

**Як це підтвердити.** З консолі Kudu (або SSH) *самого застосунку*:

```
nslookup shopdata.blob.core.windows.net
# broken:  ... Address: 20.60.x.x        (public IP)
# working: ... Aliases: shopdata.privatelink.blob.core.windows.net
#              Address: 10.1.2.5         (the private endpoint)
```

Публічна IP-адреса у відповіді підтверджує проблему DNS; зміни RBAC чи коду її не виправлять.

**Виправлення.** Пов’яжіть приватні DNS-зони з VNet інтеграції (або виправте переспрямування на власних DNS-серверах). Переконайтеся, що застосунок інтегровано з VNet і вихідний трафік маршрутизується через неї. Розгортайте endpoints, зони, зв’язки й групи DNS-зон разом в одному модулі IaC, щоб їх не створювали окремо.

**Як запобігти.** Створіть стандартний модуль «приватний ресурс PaaS», який завжди налаштовує endpoint, групу зони й зв’язок. Додайте після deployment перевірку, що визначає адресу кожної залежності *зсередини застосунку* й завершує pipeline помилкою, якщо адреса публічна.

**Погляд на співбесіді.** Запитання про мережі відрізняють розробників, які розгортали системи в середовищах із жорсткими обмеженнями, від тих, хто цього не робив. Фраза, що свідчить про досвід: *приватний endpoint настільки надійний, наскільки надійний DNS, який на неї вказує*.

## Випадок 11 — Великі завантаження не вдаються майже точно через чотири хвилини

**Ситуація.** Користувачі завантажують відео огляду об’єктів (1–4 ГБ) через API ASP.NET Core в App Service, що передає їх у Blob Storage. Невеликі файли працюють. Великі не вдається завантажити з повільним з’єднанням; усі збої стаються трохи раніше ніж через чотири хвилини.

**Що ви бачите.** Браузер повідомляє про мережеву помилку або 500. У журналах сервера видно, що завантаження тривало після того, як клієнт припинив чекати; іноді воно завершується, залишаючи blob-и, про які ніхто не знає.

**Що відбувається.** **Ліміт 230 секунд.** Front end App Service завершує будь-який запит без відповіді протягом 230 секунд (3 хвилини 50 секунд). Не має значення, що сервер іще зайнятий або що байти досі передаються. Крім того, кожне завантаження весь цей час утримує потік запиту, буфери пам’яті й вихідне з’єднання, тож десять одночасних великих завантажень шкодять усім іншим.

**Як це підтвердити.** Час збою — точна ознака: приблизно 230 секунд після початку запиту. В Application Insights тривалість невдалих запитів — близько 230 000 мс.

**Виправлення.** Приберіть API зі шляху передавання даних:

```
  browser ── 1. POST /uploads (metadata) ──────────────► API: validate, authorise, create a record
          ◄─ 2. { uploadUrl: <user delegation SAS> } ──  (create+write on ONE blob, 15 minutes)
          ── 3. PUT blocks directly ───────────────────► Blob Storage (browser SDK uploads in blocks, with retries)
                                                          │
                              4. BlobCreated event ◄──────┘  Event Grid → Service Bus queue → worker:
                                                              scan, transcode, mark the record complete
```

На кроці 2 використовується `UploadUrlIssuer` з розділу 29. Браузер завантажує блоками й може продовжити після збою; тривалість обмежує лише строк дії SAS, достатній для повільного з’єднання, але не довший за потреби. Запити до API тепер тривають мілісекунди. Спрямуйте `BlobCreated` через queue Service Bus, а не прямо до handler, щоб буферизувати сплески й отримати peek-lock та queue недоставлених.

**Як запобігти.** Правило проєктування: *запит не повинен виконувати роботу, розмір або тривалість якої контролює користувач*. Операції, що можуть тривати кілька секунд, мають працювати за схемою «прийняти, потім обробити асинхронно» ([Async Request-Reply](#async-request-reply-202-a-status-resource-and-retry-after) у розділі 11).

**Погляд на співбесіді.** Класичне додаткове запитання про проєктування систем («як обробляти великі завантаження?»). Назвіть ліміт, обмежену область дії SAS (один blob, лише створення й запис, короткий строк дії) і подієве завершення.

## Випадок 12 — Deployment зламав всі активні робочі процеси

**Ситуація.** Процес погодження повернення коштів працює на Durable Functions: оркестратор може чекати до трьох днів на схвалення менеджера. Команда додає на початку оркестратора дію перевірки шахрайства й розгортає зміни у вівторок. Відтоді кожне повернення, *розпочате до вівторка*, завершується помилкою, щойно менеджер його схвалює. Нові повернення працюють.

**Що ви бачите.** Екземпляри оркестрації в стані `Failed` з помилкою недетермінованості: історія оркестратора не відповідає діям, які планує поточний код. Зачеплено лише екземпляри, створені до deployment.

**Що відбувається.** **Повторне відтворення** (розділ 29, *Durable Functions*). Коли екземпляр прокидається через event схвалення, платформа запускає оркестратор від початку й порівнює кожну заплановану кодом дію із записаною історією. Стара історія каже: «перша дія: `NotifyApprover`». Перша дія нового коду — `CheckFraud`. Історії не збігаються, тож платформа не може безпечно продовжити й завершує екземпляр помилкою.

Цей механізм пояснює й іншу типову помилку Durable. Код, що використовує `DateTime.UtcNow` або `Guid.NewGuid()` в оркестраторі, отримує *інше* значення під час кожного повторного відтворення. Таймери спрацьовують не вчасно, а ідентифікатори змінюються.

**Як це підтвердити.** Збої залежать від того, чи створили екземпляр до deployment. У повідомленні про помилку зазначено невідповідність між історією та кодом.

**Виправлення для вже зламаних екземплярів.** Розгорніть виправлену версію, що відновлює стару структуру для старих екземплярів. Потім скористайтеся операціями керування *rewind* або *restart*, якщо вони підходять, або відтворіть запити з власних записів. Це ручна робота, тому запобігання проблемі важливе.

**Як запобігти.** Вважайте код оркестратора **версійованим контрактом** із кожним активним екземпляром:

- Для несумісних змін **розгортайте паралельно**: додайте новий оркестратор `ApproveRefundV2` і запускайте на ньому нові екземпляри, а старі нехай завершаться на незміненій V1; видаліть її після завершення всіх активних екземплярів. Або розгорніть нову версію в окремому task hub чи застосунку та дайте старій версії завершитися.
- Залишайте оркестратори невеликими й детермінованими: використовуйте `context.CurrentUtcDateTime`, `context.NewGuid()`, довготривалі таймери, а всі операції вводу-виводу виконуйте в діях. Дії можна вільно змінювати, якщо їхні вхідні та вихідні дані сумісні.
- Додайте тест, що повторно відтворює записану історію кожного оркестратора з новим кодом, і запускайте його перед кожним deployment.

**Погляд на співбесіді.** «Які компроміси Durable Functions?» Зріла відповідь: *код робочого процесу стає довготривалим контрактом з активними екземплярами*. Це стосується й інших рушіїв: Temporal, Logic Apps, саг у MassTransit.

## Випадок 13 — Ротація секрету зупинила продакшен

**Ситуація.** Політика безпеки вимагає змінювати ключ API партнера кожні 90 днів. Першу ротацію виконали вручну: створили новий ключ у партнера, оновили секрет у Key Vault, вимкнули старий ключ. API до доби отримував помилки 401 від партнера, причому різні екземпляри почали збоїти в різний час. Водночас нова служба, яка читає Key Vault *на кожен запит*, почала отримувати `429` у години пікового навантаження.

**Що ви бачите.** Одні екземпляри отримують від партнера 401, інші — ні. Нова служба отримує від Key Vault `RequestFailedException: Status: 429 (Too Many Requests)`.

**Що відбувається.** Key Vault використовують неправильно двома різними способами:

1. **Застарілі копії.** Кожен consumer кешує секрет окремо. Посилання Key Vault в App Service оновлюються кожні 24 години або відразу після перезапуску чи зміни конфігурації. Провайдер конфігурації перезавантажує дані з інтервалом `ReloadInterval`. `IOptions<T>` зберігає значення, прочитане під час запуску, до перезапуску процесу. Коли старий ключ вимкнули, багато екземплярів усе ще зберігали його — від кількох хвилин до доби.
2. **Key Vault не є кешем на кожен запит.** Запити до сховищ обмежуються; читання секрету на кожен запит перетворює піковий трафік на 429 і додає мережевий обмін до кожного виклику.

**Як це підтвердити.** Для 401 зафіксуйте, які екземпляри мають збої і коли кожен востаннє перезапускався або перечитував конфігурацію. Для 429 метрики Key Vault покажуть зростання *Service API Hit* разом із частотою запитів.

**Виправлення.**

- **Ротуйте з періодом перекриття.** Партнер дозволяє два активні ключі. Додайте новий ключ, оновіть Key Vault і дочекайтеся підтвердження, що всі consumer його отримали (примусово перезапустіть застосунок або змініть sentinel в App Configuration); лише потім вимкніть старий. Більшість провайдерів, які вимагають ротації, підтримують два ключі саме з цієї причини.
- **Завантажуйте секрети один раз і керуйте перезавантаженням.** Використовуйте провайдер конфігурації з `ReloadInterval` і `IOptionsMonitor<T>` у коді, що використовує ключ, щоб оновлення набувало чинності без перезапуску (розділ 29, *Key Vault*).
- У новій службі читайте секрет через конфігурацію під час запуску, а не на кожен запит.
- Якщо credentials потрібні для служби Azure, **приберіть їх зовсім**: managed identity не потрібно ротувати.

**Як запобігти.** Автоматизуйте ротацію events Key Vault про наближення завершення строку дії (Event Grid) і функцією, яка виконує послідовність із періодом перекриття. Запишіть її в інструкцію з експлуатації до першої ротації, а не під час неї.

**Погляд на співбесіді.** Запитання про керування секретами часто завершуються: «Як ротувати без простою?» Відповідь — період перекриття та consumer, що перечитують конфігурацію; ще краще — взагалі не мати секрету.

## Випадок 14 — «База даних наразі недоступна» раз на кілька днів

**Ситуація.** API на Azure SQL (General Purpose, безсерверний у тестовому середовищі) записує короткі сплески помилок: по кілька секунд кілька разів на тиждень у продакшені, а в тесті — під час першого запиту щоранку. Перша думка команди — звернутися до служби підтримки.

**Що ви бачите.**

```
Microsoft.Data.SqlClient.SqlException (0x80131904): Database 'Shop' on server 'shop-sql' is not currently available.
Please retry the connection later. ... Error Number:40613
```

Після ввімкнення retries EF Core один endpoint починає *щоразу* збоїти з такою помилкою:

```
InvalidOperationException: The configured execution strategy 'SqlServerRetryingExecutionStrategy' does not support
user-initiated transactions. Use the execution strategy returned by 'DbContext.Database.CreateExecutionStrategy()'
to execute all the operations in the transaction as a retriable unit.
```

**Що відбувається.** Помилкою 40613 платформа повідомляє, що *переміщує* базу: виконує перемикання під час встановлення виправлень, масштабування чи заміни обладнання. У продакшені це трапляється регулярно. У тестовій безсерверній базі автоматично призупиняється робота вночі, і перше ранкове з’єднання чекає, доки вона відновиться. Обидві ситуації тимчасові й очікувані. Служба підтримки відповіла б: «реалізуйте retries».

Друга помилка означає, що EF Core захищає вас. Стратегія retries не може відтворити лише половину транзакції, яку започаткували ви, тому відмовляється її виконувати.

**Як це підтвердити.** Перевірте номер помилки та його збіг із events обслуговування в *Resource health* Azure SQL або з events автоматичного призупинення в тесті.

**Виправлення.** Увімкніть `EnableRetryOnFailure` (розділ 29, *Azure SQL*) і обгорніть явні транзакції стратегією виконання, щоб повторювалася *вся одиниця роботи*:

```csharp
public async Task TransferStockAsync(int fromWarehouse, int toWarehouse, int productId, int quantity, CancellationToken ct)
{
    IExecutionStrategy strategy = _db.Database.CreateExecutionStrategy();

    await strategy.ExecuteAsync(async () =>
    {
        // Everything in here is retried as one unit, including the reads, which see fresh data on each attempt.
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        var from = await _db.Stock.SingleAsync(s => s.WarehouseId == fromWarehouse && s.ProductId == productId, ct);
        var to = await _db.Stock.SingleAsync(s => s.WarehouseId == toWarehouse && s.ProductId == productId, ct);
        from.Quantity -= quantity;
        to.Quantity += quantity;

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    });
}
```

Тонкий нюанс: якщо з’єднання обірветься *під час* `CommitAsync`, клієнт не знатиме, чи зафіксовано зміни. Retry може виконати переказ удвічі. Для таких операцій зробіть запис ідемпотентним (унікальний ідентифікатор операції) або використайте перевантаження `ExecuteInTransactionAsync` з функцією `verifySucceeded`, яка перевірить, чи відбулося підтвердження.

**Як запобігти.** Політики retries для кожної залежності мають бути в шаблоні сервісу, а не додаватися після першого інциденту. Автоматичне призупинення безсерверної бази в тестовому середовищі корисне: воно виявить відсутність retries до продакшену.

**Погляд на співбесіді.** «Як обробляти тимчасові збої?» Retries з наростанням затримки, ідемпотентність і важливий нюанс: *retry не знає, чи зафіксовано транзакцію, якщо підтвердження загубилося*. Саме це відрізняє відповідь досвідченого інженера.

## Випадок 15 — Під час інциденту нічого не видно

**Ситуація.** О 14:10 починають збоїти операції оформлення замовлень. Черговий інженер відкриває Application Insights: з 13:40 немає запитів, exceptions чи трасувань. Панель показує, наче сервіс простоює. Скарги клієнтів кажуть протилежне.

**Що ви бачите.** Телеметрія раптово обривається о 13:40, хоча метрики платформи (HTTP 5xx App Service, CPU) показують, що активність триває. Ресурс Application Insights попереджає, що денний ліміт досягнуто.

**Що відбувається.** Кілька місяців тому хтось установив **денний ліміт** для контролю витрат. Сьогодні шторм retries до залежності зі збоями примножив обсяг logging: кожен невдалий виклик з кожного екземпляра записував exception із повним вмістом даних на рівні `Information`. О 13:40 ліміт спрацював, і приймання даних **зупинилося** до кінця дня. Контроль витрат спрацював за задумом — у найгірший момент.

**Як це підтвердити.** Ліміт і час його скидання видно в параметрах використання Application Insights (або робочої області Log Analytics). Обсяг, який його вичерпав, видно в самій робочій області:

```kusto
// Which tables and apps produce the ingested volume? (_BilledSize is in bytes)
union withsource = TableName App*
| where TimeGenerated > ago(1d)
| summarize GB = round(sum(_BilledSize) / 1e9, 2) by TableName, AppRoleName
| order by GB desc
```

**Виправлення.** Тепер тимчасово підніміть ліміт і решту інциденту розслідуйте за метриками платформи (на які ліміт не впливає), потоком журналів і Kudu. Після цього:

- Контролюйте обсяг **у джерелі**: налаштуйте доречні рівні logging (для категорій фреймворку, як-от `Microsoft.EntityFrameworkCore`, — `Warning`), не записуйте тіла запитів чи відповідей, усувайте дублікати exceptions у циклах retries (записуйте остаточний збій, а не кожну спробу).
- Використовуйте **семплювання** (розділ 29, *Observability (спостережуваність)*), пам’ятаючи, що воно може приховувати рідкісні events.
- Якщо залишаєте денний ліміт, установіть його як аварійний запобіжник значно вище звичайного обсягу й налаштуйте сповіщення на нижчому порозі, щоб людина встигла втрутитися до зупинки телеметрії.

**Як запобігти.** **Тест доступності** й **сповіщення за метриками** не залежать від телеметрії застосунку, тому працюють, коли приймання даних зупинилося або застосунок надто несправний, щоб їх надсилати. Кожній критичній службі потрібен хоча б один сигнал, що не залежить від її власних журналів.

**Погляд на співбесіді.** Запитання про observability винагороджують інженерів, які розуміють *економіку* телеметрії: її вартість, що приховує семплювання та які сигнали переживають збій.

## Випадок 16 — Регіон вийшов з ладу: ретроспективний архітектурний огляд

**Ситуація.** Регіональний збій вимикає основний регіон магазину на чотири години. На архітектурній схемі було написано «кілька регіонів». Насправді вебрівень розгорнуто у двох регіонах, але база Azure SQL не мала георепліки, обліковий запис сховища використовував LRS, а Key Vault, App Configuration і простір імен Service Bus існували лише в основному регіоні. Екземпляри застосунку в резервному регіоні запустилися, але не мали доступу до жодної залежності.

**Що ви бачите.** Front Door повідомив, що резервний регіон справний, бо проба перевіряла лише, чи відповідає процес, і спрямувала туди трафік. Кожен запит завершувався помилкою на першій залежності.

**Що відбувається.** Доступність — властивість **усього шляху запиту**, а не лише рівня обчислень (розділ 29, *Регіони, зони доступності та SLA*). Для кожної залежності зі станом потрібна відповідь на запитання «де вона буде, якщо регіон зникне?». Проба працездатності має перевіряти критичні залежності — інакше перемикання скеровуватиме трафік у несправний регіон.

**Огляд залежностей:**

| Залежність | Що було | Що потрібно для заявленої мети | Прийнятний компроміс |
|---|---|---|---|
| Azure SQL | Один регіон | **Група перемикання відмовостійкості**, підключення застосунку через слухач | Асинхронна реплікація: примусове перемикання може втратити останні транзакції (RPO > 0) |
| Blob Storage | LRS | **GZRS** або **RA-GZRS** і відпрацьована процедура перемикання під керуванням клієнта | Вартість; після перемикання обліковий запис використовує LRS, доки георезервування не налаштують знову |
| Cosmos DB (каталог) | Один регіон | Додати другий регіон із керованим службою перемиканням відмовостійкості | RU/s оплачуються в кожному регіоні |
| Service Bus | Standard, один регіон | Premium із геореплікацією або відновленням після геокатастрофи чи архітектура, що витримує втрату активних повідомлень | Вартість Premium; заздалегідь вирішити, що станеться з повідомленнями в обробці |
| Key Vault, App Configuration | Лише основний | Репліка або окремий екземпляр у кожному регіоні з deployment із того самого IaC | Більше даних для синхронізації |
| Проба працездатності Front Door | `/` | Endpoint `/health/ready`, який перевіряє критичні залежності | Трафік проб; короткий збій залежності може перемкнути регіон, тому потрібне налаштування порогів |

**Важлива розмова.** Перш ніж купувати будь-що з цього, узгодьте з бізнесом **RTO** (допустиму тривалість простою) і **RPO** (допустиму втрату даних) для кожної можливості. «Оформлення замовлень не працює чотири години раз на кілька років» може бути прийнятним і значно дешевшим за активну роботу в кількох регіонах. Потім **відрепетируйте** перемикання. Перемикання, яке не тестували, — гіпотеза; цей інцидент і став перевіркою.

**Погляд на співбесіді.** «Як зробити цю систему мультирегіональною?» Найкращі відповіді починаються з RTO і RPO, розглядають стан, а не обчислення, та завершуються описом перевірки перемикання. Теорію наведено в [розділі 20](#chapter-20-distributed-systems), а таблиця показує практику.

## Короткі випадки

**Витік секрету CI.** Секрет клієнта суб’єкта-служби deployment, збережений у CI-системі, потрапив у журнал збірки, коли хтось увімкнув докладне logging скрипту. Він мав роль *Owner* на продакшен-підписці. *Виправлення:* негайно відкличте його, а потім замініть на **федерацію ідентичностей workload (робочого навантаження)** (розділ 29, *Ідентичність*): федеративні credentials довіряють лише середовищу `production` цього репозиторію, а роль обмежена групами ресурсів, які розгортає pipeline. *Як запобігти:* секрету більше немає, отже нічому витікати. Обмежуйте ідентичності deployment окремими середовищами й вимагайте погодження production-середовища ([розділ 27](#chapter-27-security-in-depth-and-the-supply-chain)).

**Events Event Grid не надходять.** Новий endpoint webhook, підписаний на `BlobCreated`, не отримує events. Для підписки показано помилковий стан підготовки. *Причина:* endpoint повернув `200` на event перевірки, не відобразивши `validationCode`. *Виправлення:* обробляйте `SubscriptionValidationEvent` (або використовуйте Function чи queue Service Bus, яким рукостискання не потрібне) і налаштуйте контейнер для недоставлених events, щоб events після вичерпання retries (30 спроб або 24 години за замовчуванням) зберігалися, а не губилися.

**Перемикання щоразу зупинялося під час прогрівання.** Staging-слот повертає 503 з endpoint прогрівання, а його журнали показують 403 від Key Vault. Production працює. *Причина:* налаштування managed identity **окреме для кожного слота**. У staging-слота власна системна ідентичність, роль надано лише ідентичності production-слота, а під час перемикання ідентичності не переміщуються. Тому staging не може звернутися до Key Vault, і прогрівання правильно зупиняє перемикання. *Виправлення:* призначте обом слотам одну **ідентичність, призначену користувачем**, і надайте їй роль один раз, щоб доступ не залежав від слота, у якому працює код.

**Тригер таймера спрацював двічі.** Функція з таймером після масштабування надіслала щоденний звіт двічі. *Причина:* не в таймері. Тригер таймера Functions використовує blob lease, щоб лише один екземпляр виконував розклад, але два *окремі* застосунки-функції (staging-застосунок розгорнули з тією самою конфігурацією) нічого не мали спільного, тож обидва запустили його. *Виправлення:* вимикайте таймери в непродакшен-середовищах через параметр (`AzureWebJobs.<FunctionName>.Disabled`) і зробіть звіт ідемпотентним для кожного дня.

## Вправи

### Знайдіть помилку

**1.** Два екземпляри служби складського обліку виконують цей код для резервування запасів. Вони зберігаються в одному JSON blob. Тести проходять, код працював кілька місяців. Аж раптом на складі товару більше, ніж система показує як проданий.

```csharp
public static async Task ReserveAsync(BlobClient blob, string sku, int quantity, CancellationToken ct)
{
    BlobDownloadResult current = await blob.DownloadContentAsync(ct);
    Inventory inventory = current.Content.ToObjectFromJson<Inventory>()!;

    if (inventory.Stock[sku] < quantity)
        throw new InvalidOperationException($"Not enough {sku} in stock.");

    inventory.Stock[sku] -= quantity;

    await blob.UploadAsync(BinaryData.FromObjectAsJson(inventory), overwrite: true, ct);
}
```

<details>
<summary>Відповідь</summary>

**Втрачене оновлення.** Екземпляр A читає `{ "sku-1": 10 }`. Екземпляр B читає те саме, резервує 3 й записує 7. Екземпляр A резервує 2 й записує 8, перезаписуючи результат B. Помилок немає: `overwrite: true` означає «записати незалежно від наявного значення». Тепер залишок дорівнює 8, а мав би бути 5.

Виправлення — **оптимістичний контроль паралельності через ETag**: записуйте лише якщо blob не змінився після читання; при `412 Precondition Failed` прочитайте його знову й повторіть зміну:

```csharp
for (var attempt = 1; ; attempt++)
{
    BlobDownloadResult current = await blob.DownloadContentAsync(ct);
    Inventory inventory = current.Content.ToObjectFromJson<Inventory>()!;
    if (inventory.Stock[sku] < quantity)
        throw new InvalidOperationException($"Not enough {sku} in stock.");
    inventory.Stock[sku] -= quantity;

    try
    {
        await blob.UploadAsync(BinaryData.FromObjectAsJson(inventory),
            new BlobUploadOptions { Conditions = new BlobRequestConditions { IfMatch = current.Details.ETag } }, ct);
        return;
    }
    catch (RequestFailedException e) when (e.Status == 412 && attempt < 5)
    {
        // someone else wrote first: loop, re-read, re-apply
    }
}
```

Це перевірено з Azurite у `verify/exercises/Ch51`: коли між читанням і записом примусово виконується запис іншого екземпляра, початковий код завершується зі значенням 8, а виправлений — 5, отримавши рівно одну помилку `412`. Важливіше проєктне запитання: чи варто взагалі зберігати спільний стан, який часто оновлюється, в одному blob? За реальної конкуренції retries накопичуватимуться. Краще масштабується рядок бази з умовним оновленням або розподіл стану (окремий blob на SKU).
</details>

**2.** Handler платежів спорожнює queue Service Bus. Типове блокування queue триває 1 хвилину, а кожен виклик для оплати — близько 2 секунд. Клієнти повідомляють про подвійні списання.

```csharp
public async Task DrainOnceAsync(CancellationToken ct)
{
    IReadOnlyList<ServiceBusReceivedMessage> batch =
        await receiver.ReceiveMessagesAsync(maxMessages: 50, maxWaitTime: TimeSpan.FromSeconds(5), ct);

    foreach (ServiceBusReceivedMessage message in batch)
    {
        await handler.HandleAsync(message, ct);          // calls a partner API, ~2 s
        await receiver.CompleteMessageAsync(message, ct);
    }
}
```

<details>
<summary>Відповідь</summary>

**Пакет переживає свої блокування.** Усі 50 повідомлень блокуються під час *отримання*. Послідовна обробка триває близько 100 секунд, тож приблизно від 30-го повідомлення кожне обробляється після завершення блокування. Service Bus уже зробив повідомлення видимим знову, тож воно доставляється й обробляється повторно (друге списання), а початковий виклик `CompleteMessageAsync` викидає `ServiceBusException` із `Reason == MessageLockLost`. Цей exception також залишає необробленими решту пакета.

Потрібні два рівні виправлення:

1. Використовуйте `ServiceBusProcessor`. Він поновлює блокування, доки працює handler (`MaxAutoLockRenewalDuration`, типово 5 хвилин), і отримує не більше повідомлень, ніж має паралельних handlers (`MaxConcurrentCalls`). Пропускну здатність дає паралельність, а не великі пакети.
2. Зробіть handler ідемпотентним (ідентифікатор платежу як idempotency key провайдера та запис оброблених повідомлень), бо завершення блокування — лише одна з причин повторної доставки.

Це перевірено з емулятором Service Bus у `verify/exercises/Ch51`: блокування скорочено до 5 секунд, handler працює 1 секунду. У контрольному запуску 12 повідомлень із цим кодом спричинили 14 викликів handler та 2 помилки `MessageLockLost`; з процесором — рівно 12 викликів.
</details>

### Як би ви вчинили

**1.** Після третьої помилки 403, пов’язаної з ідентичністю, цього місяця менеджер продукту просить «швидке виправлення»: «Може, просто дати застосунку Owner на підписці, щоб проблема зникла?» Керівник команди майже погоджується, бо випуск у п’ятницю.

<details>
<summary>Як міркує досвідчений інженер</summary>

Спершу з’ясуйте, що спричинило помилки 403. Якщо бракувало ролей для площини даних (випадок 1), Owner їх не виправила б — ця роль також не має дозволів на дані. Якщо це були затримки поширення нових ролей, Owner теж не допомогла б: затримка стосується кожного нового призначення. Тож «дати Owner» і небезпечно, і, ймовірно, неефективно; зазвичай другий аргумент переконує краще.

Запропонуйте виправлення *причини*, яке можна встигнути до п’ятниці: один раз створити ідентичність, призначену користувачем, і визначити для неї ролі доступу до даних у межах потрібного контейнера та сховища в тому самому модулі Bicep, що й ресурси. Це усуває брак ролі й затримки поширення. Така робота займе близько пів дня; зміни можна перевірити, як будь-який інший код.

Нарешті без зайвої драматизації поясніть конкретний ризик для неінженерів: з Owner одна вразливість застосунку (SSRF або витік токена) дала б зловмиснику змогу видалити всі ресурси й прочитати кожен ключ у підписці. Говоріть про *масштаб наслідків* — це зрозуміло продуктовій команді — і зафіксуйте рішення в ADR ([розділ 16](#chapter-16-working-like-a-middle-developer)), якщо вони все ж оберуть короткий шлях.
</details>

**2.** Ви проєктуєте нову службу «обробки документів»: PDF надходять через завантаження (кілька тисяч на день, сплесками після робочого часу), кожен обробляється від 20 секунд до 6 хвилин нативною бібліотекою, якій потрібен певний пакет Linux, а результати записуються в Azure SQL. Колега пропонує Functions на плані Consumption, «бо це безсерверно й дешево».

<details>
<summary>Як міркує досвідчений інженер</summary>

Зіставте обмеження з планами розміщення (розділ 29, *Обчислення*) по queue:

- **Тривалість.** Шість хвилин уміщуються в максимальні 10 хвилин застарілого плану Consumption, але запас малий. План також позначено як застарілий, а підтримка його версії Linux завершується у 2028 році. Цього достатньо, щоб не обирати його для нової служби.
- **Нативна залежність.** Певний пакет Linux вимагає **власного контейнера**, а Flex Consumption не підтримує контейнери (розгортає лише пакети коду). Реальні варіанти — **Container Apps** (завдання або застосунок із правилом масштабування Service Bus) чи Functions на Premium або з розміщенням у Container Apps, із власним образом.
- **Сплески після робочого часу.** Container Apps добре підходить для масштабування до нуля між сплесками. KEDA масштабується за довжиною queue.
- **Downstream Azure SQL.** Паралельність усіх компонентів, що масштабуються, треба обмежити (випадок 7). Задайте максимум реплік × паралельність кожної репліки з урахуванням лімітів бази.

Розумна пропозиція: пряме завантаження до Blob Storage через SAS (випадок 11) → `BlobCreated` → queue Service Bus → **завдання Container Apps** (або застосунок) із правилом масштабування Service Bus, `minReplicas: 0` та обмеженою максимальною кількістю реплік. Ідемпотентна обробка за назвою blob; результати записуються однією транзакцією. Потім назвіть, що виміряти перед остаточним вибором: розподіл часу обробки реальних документів і вартість очікуваного обсягу порівняно з невеликим постійно ввімкненим варіантом.

Коментар колезі під час перевірки: «Безсерверність» — властивість операційної моделі, а не продукт; тут залежність і downstream-база важливіші за ціну.
</details>

### Перевірте у своїй системі

Дайте відповіді на ці запитання про власну систему, а не з пам’яті:

- **Ідентичність.** Перелічіть усі призначення ролей для ідентичностей ваших застосунків: `az role assignment list --assignee <id> --all`. Скільки з них мають роль Contributor або Owner? Скільки призначені на рівні підписки або групи ресурсів, а не окремого ресурсу? Чи є `AZURE_CLIENT_SECRET` у параметрах будь-якого середовища?
- **Ключі.** Які облікові записи сховищ, простори імен Service Bus та облікові записи Cosmos DB досі дозволяють спільний ключ або локальну автентифікацію? Хто чи що ще використовує ці ключі?
- **З’єднання.** Пошукайте `new HttpClient(`, `new CosmosClient(`, `new ServiceBusClient(`, `new BlobServiceClient(` і `new DefaultAzureCredential(` поза кодом запуску.
- **Повідомлення.** Для кожної queue й підписки з’ясуйте тривалість блокування, `MaxDeliveryCount`, поточну кількість недоставлених повідомлень і наявність сповіщень. Чи ідемпотентний кожен consumer, і як ви це знаєте?
- **Deployment.** Які параметри застосунку закріплені за слотами? Що перевіряє маршрут прогрівання? Що перевіряють проби працездатності Front Door або Traffic Manager?
- **Дані.** Для кожного контейнера Cosmos DB визначте ключ розділу, найбільший логічний розділ і три запити з найбільшими витратами RU. Для Azure SQL перевірте, чи ввімкнено `EnableRetryOnFailure` і чи проходять явні транзакції через стратегію виконання.
- **Телеметрія.** Чи встановлено денний ліміт? Яка конфігурація семплювання? Чи є тест доступності для кожної публічної точки входу?
- **Відновлення.** Для кожної залежності зі станом з’ясуйте, де вона буде, якщо регіон зникне, і коли це востаннє перевіряли.

Кожне «не знаю» — кандидат на невелике вимірюване покращення й історію для портфоліо практичних результатів ([розділ 37](#chapter-37-the-story-bank-evidence-portfolio)). Історії про реального роботодавця залишайте приватними, а числа, якими ділитеся, знеособлюйте.

## Підсумок

Інциденти Azure, що забирають найбільше часу, рідко бувають екзотичними. Їх спричиняють кілька механізмів: дозволи **площини керування й площини даних** та затримка їх поширення; **ланцюжок credentials**, що вибирає неочікувану ідентичність; **SNAT-порти** й з’єднання, які не використовуються повторно; **послідовність перемикання слотів** і параметри, що переміщуються разом із нею; семантика **peek-lock**, завершення блокування й queue недоставлених, за якими ніхто не стежить; **еластичні обчислення перед нееластичними базами даних**; **гарячі розділи** в Cosmos DB; **приватні endpoints без DNS**; ліміт запиту **230 секунд**; **повторне відтворення** у Durable Functions; **ротація секретів** без періоду перекриття; **тимчасові помилки SQL**; **ліміти телеметрії** та **багаторегіональні схеми**, що резервують лише рівень обчислень.

У кожному випадку дотримуйтеся одного підходу: прочитайте симптом, назвіть механізм, підтвердьте його конкретною перевіркою, виправте причину, а не симптом, і додайте запобіжник, що утримає виправлення. Саме на цей підхід, а не на назву будь-якої служби, зважає інтерв’юер і покладається команда о третій ночі.
