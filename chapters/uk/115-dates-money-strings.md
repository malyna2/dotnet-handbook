# Розділ 15: Дати, гроші й рядки

У більшості підручників програмний код існує в уявному світі. На годиннику завжди полудень, усі розмовляють американською англійською, ціни округлені до долара, файли поміщаються в пам’ять, а електронні листи «просто надсилаються». У продакшені ці припущення розбиваються. Інциденти, що будять інженерів о третій ночі, рідко спричиняють невдалі хитромудрі алгоритми; частіше — часова позначка, збережена в місцевому часі сервера, `double`, який загубив копійку, `ToUpper()`, що зіпсував турецьке ім’я користувача, або завантаження на 2 ГБ, яке заповнило пам’ять вебсервера.

Цей розділ — практичний довідник із таких деталей. Жодна з них не є концептуально складною. Але в кожній легко припуститися малопомітної помилки, яка проявиться лише в реальних умовах: у клієнта з іншого часового поясу, для неочікуваної валюти чи культури, яку ви ніколи не тестували. Уміння все зробити правильно без підказки — важлива частина відповідальності розробника рівня middle.

Розділи об’єднує один механізм: **значення правильне лише разом із контекстом, який надає йому сенсу.** Для моменту часу потрібен UTC або зміщення; для часу на годиннику — часовий пояс; для суми — валюта й правило округлення; для порівняння рядків — оголошений тип порівняння. Якщо контекст не вказано явно, його підставляє машина: часовий пояс сервера, культура потоку або найближчий до десяткового значення двійковий дріб. Кожна описана нижче пастка — наслідок такої підміни. У розділі спочатку розглядаються дати й час, потім гроші й числа, далі культури й рядки; наприкінці — інтеграції, потрібні майже кожному застосунку (файли, електронна пошта, сповіщення, PDF), і пояснюється, чому важку роботу з ними треба виконувати поза обробкою запиту. Наприкінці програма *Перевірте на практиці* демонструє пастки роботи з грошима на вашій машині.

## Правильна робота з датою й часом

Поняття «дата й час» непомітно об’єднує кілька різних понять і тому є одним із найчастіших джерел помилок у бізнес-програмному забезпеченні.

### Чотири типи та їхнє значення

- **`DateTime`** — дата й час, а також прапорець `Kind` зі значенням `Utc`, `Local` або `Unspecified`. Саме `Kind` стає пасткою: його легко втратити або проігнорувати; типове значення — `Unspecified`, тобто «ніхто не знає, до якого часового поясу належить цей час».
- **`DateTimeOffset`** — дата, час і явне зміщення від UTC (наприклад, `-05:00`). Однозначно визначає один момент на глобальній часовій шкалі. **Для часових позначок віддавайте перевагу цьому типу.**
- **`DateOnly`** (додано в .NET 6) — календарна дата без часу й часового поясу. Ідеально підходить для днів народження, дат рахунків і свят, де «час» не має значення.
- **`TimeOnly`** (додано в .NET 6) — час доби без дати. Ідеально підходить для прикладу «магазин відчиняється о 09:00».

Якщо змоделювати день народження як `DateTime` опівночі, після першого необережного перетворення часового поясу дата зсунеться на попередній день. Якщо значення не має складника часу, не додавайте його.

> **`DateTime.Now` майже завжди є помилкою в коді сервера.** Ця властивість читає місцевий годинник і часовий пояс *сервера*. Сервери переносять між регіонами, запускають у контейнерах із UTC і мігрують у хмару. Бізнес-логіка, що залежить від `DateTime.Now`, дає різні результати залежно від того, де запущено процес. Натомість використовуйте `DateTimeOffset.UtcNow` (або `TimeProvider`, розглянутий нижче).

### Зберігайте й обчислюйте в UTC. Завжди.

Найцінніше правило цього розділу: **зберігайте моменти часу в UTC, виконуйте арифметику в UTC, а до місцевого часового поясу перетворюйте лише на самому краю — під час показу людині.**

```csharp
// Capture: an unambiguous instant.
DateTimeOffset createdAt = DateTimeOffset.UtcNow;

// Store: as UTC. In a database, use a type that preserves offset/UTC
// (PostgreSQL timestamptz, SQL Server datetimeoffset).

// Render: convert to the user's zone at the boundary, and format with the user's
// culture. Zone and culture are separate settings: a Kyiv user may read English.
TimeZoneInfo userZone = TimeZoneInfo.FindSystemTimeZoneById("Europe/Kyiv");
DateTimeOffset localForDisplay = TimeZoneInfo.ConvertTime(createdAt, userZone);
Console.WriteLine(localForDisplay.ToString("f", userCulture));
```

Причина — віднімання: інтервал має сенс лише між двома моментами на одній абсолютній часовій шкалі. Місцевий час не лежить на єдиній шкалі: через літній час місцева доба може тривати 23 або 25 годин.

### Літній час: проміжки й повторення

Двічі на рік час на годиннику поводиться незвично.

- **Весняний пропуск.** Коли годинник переводять уперед, певного діапазону місцевого часу *не існує*. У багатьох країнах Європи о 02:30 у ніч переведення годинника навесні не буває. Це можна перевірити через `TimeZoneInfo.IsInvalidTime`.
- **Осіннє повторення.** Коли годинник переводять назад, певний діапазон місцевого часу *повторюється двічі*. Осінні 02:30 — неоднозначний час, що відповідає двом різним моментам. `TimeZoneInfo.IsAmbiguousTime` виявляє це.

```csharp
var zone = TimeZoneInfo.FindSystemTimeZoneById("Europe/Berlin");
var springForward = new DateTime(2026, 3, 29, 2, 30, 0, DateTimeKind.Unspecified);

Console.WriteLine(zone.IsInvalidTime(springForward)); // True — 02:30 never happened

// TimeZoneInfo.ConvertTimeToUtc(springForward, zone) throws ArgumentException.
// zone.GetUtcOffset(springForward) does not: it returns the standard offset, +01:00,
// so code that builds a DateTimeOffset from it gets an instant nobody asked for.
```

> **Зверніть увагу.** **Що .NET робить під час пропуску й повторення часу.** Для часу у весняному пропуску `TimeZoneInfo.ConvertTimeToUtc` і `ConvertTime` викидають `ArgumentException`, а `GetUtcOffset` мовчки повертає стандартне зміщення. Для часу в осінньому повторенні винятку немає: перетворення мовчки вибирає момент за стандартним часом (у Берліні 25 жовтня 2026 року 02:30 перетворюється на 01:30 UTC — це друге входження цього часу), а `GetAmbiguousTimeOffsets` повертає обидва варіанти: +01:00 і +02:00. Арифметика `DateTime` також ігнорує ці особливості: від опівночі до опівночі 29 березня 2026 року в Берліні минає 23 години, але `AddDays(1)` завжди додає 24. Для всіх трьох випадків виправлення однакове: обчислюйте моменти часу (в UTC або з `DateTimeOffset`) і явно визначайте, що бізнес-логіка має робити з часом на годиннику, який припадає на пропуск або повторення. (Перевірено на .NET 10.0.12, Linux.)

> **Не плануйте повторювані завдання на наївний місцевий час «кожного вечора о 02:30».** У ніч переведення годинника таке завдання запуститься двічі або не запуститься зовсім. Плануйте за UTC або явно визначте поведінку для пропуску й повторення часу.

Щороку повторюються й інші пастки: **високосні роки** (не припускайте, що рік завжди має 365 днів; замість власноручних обчислень використовуйте `DateTime.IsLeapYear` і `DateTime.DaysInMonth`) і проблема «додати місяць до 31 січня»: `AddMonths(1)` обмежує результат 28 або 29 лютого, тому `date.AddMonths(1).AddMonths(-1)` не завжди дає початкову дату. Календарна арифметика не є асоціативною.

**Високосні секунди** існують в UTC, але арифметика `DateTime` їх не моделює. Для бізнес-програмного забезпечення ігноруйте їх і не покладайтеся на різницю з точністю до секунди через таку секунду.

### Ідентифікатори часових поясів IANA і Windows

Є дві конкуруючі системи ідентифікаторів часових поясів. Windows використовує назви на кшталт `"Pacific Standard Time"`; решта світу використовує **IANA** (також відому як база часових поясів Olson/tz) з ідентифікаторами на кшталт `"America/Los_Angeles"`. Через це код, написаний і перевірений у Windows, може поводитися інакше після розгортання в контейнері Linux.

Добра новина: починаючи з **.NET 6**, `TimeZoneInfo.FindSystemTimeZoneById` приймає обидва формати на обох платформах і автоматично конвертує їх за допомогою ICU. Перетворення можна виконати явно за допомогою `TimeZoneInfo.TryConvertIanaIdToWindowsId` і зворотного методу. Та все ж **стандартизуйте дані на ідентифікаторах IANA**: вони є спільною для платформ мовою, а база IANA — авторитетне джерело правил часових поясів у світі, яке часто оновлюється (історичні зміни й політичні перейменування відбуваються частіше, ніж очікують).

> **Нюанс.** *Правила* часового поясу надходять з операційної системи (з бази часових поясів у Linux або реєстру Windows), але зіставлення ідентифікаторів IANA й Windows бере дані з ICU. У режимі без урахування глобалізації (`InvariantGlobalization`, `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`, типовому для компактних образів контейнерів) на Linux виклик `FindSystemTimeZoneById("W. Europe Standard Time")` викидає `TimeZoneNotFoundException`, а `"Europe/Berlin"` і далі працює. Ще одна причина зберігати ідентифікатори IANA.

### NodaTime: коли вбудованих типів недостатньо

BCL дає змогу написати безглуздий код, який компілюється (додати `TimeSpan` до `DateTime`, що не знає часового поясу, або порівняти два значення `Unspecified`). **NodaTime**, створена Джоном Скітом, надає кожному поняттю окремий тип, тому компілятор не дозволяє змішувати їх:

- **`Instant`** — точка на глобальній часовій шкалі (як `DateTimeOffset.UtcNow`, але без додаткового зміщення).
- **`LocalDate` / `LocalTime` / `LocalDateTime`** — значення на місцевому годиннику без часового поясу. Їх неможливо випадково трактувати як моменти часу.
- **`ZonedDateTime`** — `LocalDateTime`, пов’язаний із `DateTimeZone` і перетворений на конкретний `Instant`.
- **`Duration`** (минулий час на часовій шкалі) і **`Period`** (календарні відрізки на кшталт «1 місяць») — це справді різні поняття, для яких не слід використовувати один тип.

```csharp
using NodaTime;

Instant now = SystemClock.Instance.GetCurrentInstant();
DateTimeZone kyiv = DateTimeZoneProviders.Tzdb["Europe/Kyiv"];
ZonedDateTime local = now.InZone(kyiv);

// A recurring meeting is a LocalTime + zone, resolved per-occurrence.
LocalDateTime wallClock = new LocalDateTime(2026, 3, 29, 2, 30);
// NodaTime forces you to choose a resolver for gaps/overlaps — it will
// not silently guess for you, which is the whole point.
ZonedDateTime resolved = kyiv.ResolveLocal(wallClock, Resolvers.LenientResolver);
```

Використовуйте NodaTime, коли час є суттєвою частиною предметної області (планування, календарі, фінанси — усе, що перетинає часові пояси): *типи* допоможуть запобігти помилкам.

### `TimeProvider`: тестування часу (.NET 8+)

Код, який безпосередньо викликає `DateTimeOffset.UtcNow`, неможливо перевірити на фіксований момент часу або опівніч. У .NET 8 стандартизували саморобну абстракцію `IClock` як **`TimeProvider`**.

```csharp
public class SubscriptionService
{
    private readonly TimeProvider _time;
    public SubscriptionService(TimeProvider time) => _time = time;

    public bool IsExpired(Subscription sub) =>
        _time.GetUtcNow() >= sub.ExpiresAtUtc;
}

// Production: register TimeProvider.System in DI.
// Tests: use FakeTimeProvider from Microsoft.Extensions.TimeProvider.Testing.
var fake = new FakeTimeProvider(
    new DateTimeOffset(2026, 7, 21, 12, 0, 0, TimeSpan.Zero));
var svc = new SubscriptionService(fake);
fake.Advance(TimeSpan.FromDays(1)); // deterministically move time forward
```

`TimeProvider` також абстрагує таймери й `Task.Delay`, тож можна тестувати тайм-аути й повторні спроби без реального очікування. **Упроваджуйте `TimeProvider` залежністю всюди, де інакше звернулися б до `DateTimeOffset.UtcNow`.**

### Розбір і форматування з урахуванням культури

`DateTime.Parse("03/04/2026")` — міна сповільненої дії: у США це четверте березня, а в більшості країн Європи — третє квітня, бо результат залежить від `CultureInfo.CurrentCulture`.

> **Для обміну даними між машинами (JSON, журнали, API, назви файлів) завжди використовуйте незмінний формат, незалежний від культури, — ISO 8601 (round-trip `"o"`) — і розбирайте дані через `CultureInfo.InvariantCulture` та `DateTimeStyles`. Форматування з урахуванням культури залиште для тексту, який показуєте людям.**

```csharp
string wire = DateTimeOffset.UtcNow.ToString("o", CultureInfo.InvariantCulture);
var parsed = DateTimeOffset.ParseExact(
    wire, "o", CultureInfo.InvariantCulture, DateTimeStyles.RoundtripKind);
```

## Гроші й числа

### Ніколи не використовуйте `double` (або `float`) для грошей

Двійковий тип із рухомою комою не може точно представити більшість десяткових дробів. `0.1 + 0.2` не дорівнює `0.3`. Якщо накопичувати такі значення тисячі разів під час обробки рахунків, суми в документах відрізнятимуться на копійки — а у фінансах навіть «різниця в копійки» означає невдалий аудит.

```csharp
Console.WriteLine(0.1 + 0.2 == 0.3);        // False (double)
Console.WriteLine(0.1m + 0.2m == 0.3m);     // True  (decimal)
```

`decimal` — 128-бітний десятковий тип: у межах діапазону він точно представляє десяткові дроби й зберігає їхній масштаб. **Використовуйте `decimal` для грошових сум і точних дробових величин.** `double` призначено для фізики й статистики, де відносна точність важливіша за точне десяткове подання.

### Округлення й несподіване округлення до парного

Округлення — це *бізнес-рішення*, а не технічна дрібниця. Типове правило `Math.Round` — **округлення до парного** (половини округлюють до найближчого парного числа): `Math.Round(2.5m)` дає `2`, а `Math.Round(3.5m)` — `4`. Це запобігає статистичному зміщенню під час округлення багатьох значень і дивує всіх, хто очікує звичного округлення половини вгору.

```csharp
Math.Round(2.5m);                               // 2  (to even — the default!)
Math.Round(2.5m, MidpointRounding.AwayFromZero); // 3  ("school" rounding)
Math.Round(2.345m, 2, MidpointRounding.AwayFromZero); // 2.35
```

> **Завжди явно вказуйте режим `MidpointRounding` і округлюйте лише на визначених межах** (наприклад, під час показу загальної суми або запису до бухгалтерського реєстру), а не кілька разів посеред обчислень. Округлюйте один раз, наприкінці: округлення проміжних результатів накопичує похибку.

> **Зверніть увагу.** **Форматування застосовує інше правило округлення.** `Math.Round(2.345m, 2)` дає `2.34` (до парного), а `2.345m.ToString("F2")` показує `2.35` (від половини від нуля). Рахунок, у якому збережено округлене значення, а надруковано неокруглене, розходиться з власним реєстром на копійку. Округлюйте один раз із явним режимом і форматуйте вже округлене значення. Ще дві копійки губляться в тих самих місцях: `double` округлюється від значення, яке ніколи не було тим десятковим числом, яке ви ввели (`1.005` зберігається як `1.00499999999999989342`, тому навіть `AwayFromZero` дає `1.00`), а розподіл 100.00 на 3 округлює кожну частку до 33.33 — загалом виходить 99.99, тож правило розподілу має визначити, кому дістанеться залишок.

### Зберігайте гроші в мінімальних одиницях і завжди разом із валютою

Сума без валюти не має сенсу: `100` у JPY (без десяткових розрядів), USD (два) і BHD (три) — зовсім різні величини. Є дві надійні стратегії зберігання:

1. **Мінімальні одиниці як ціле число** — збережіть 19.99 USD як ціле `1999` (центи) разом із кодом валюти. Так ви уникнете проблем із поданням дробових значень; саме так моделюють гроші платіжні провайдери (наприклад, Stripe).
2. **`decimal` і код валюти** — простіше читати, і цього досить для більшості бізнес-застосунків, якщо точність і масштаб стовпця бази даних достатні (наприклад, `DECIMAL(19,4)`).

У будь-якому разі **ніколи не зберігайте окреме число без контексту**. Інкапсулюйте гроші в об’єкті-значенні, щоб валюта залишалася разом із сумою, а незаконні операції (додавання USD до EUR) було неможливо виразити:

```csharp
public readonly record struct Money
{
    public long MinorUnits { get; }     // e.g. cents
    public string Currency { get; }     // ISO 4217, e.g. "USD"

    public Money(long minorUnits, string currency)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(currency);
        MinorUnits = minorUnits;
        Currency = currency.ToUpperInvariant();
    }

    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new InvalidOperationException(
                $"Cannot add {other.Currency} to {Currency}.");
        return new Money(MinorUnits + other.MinorUnits, Currency);
    }

    public static Money operator +(Money a, Money b) => a.Add(b);

    // Minor-unit digits vary by currency (JPY 0, USD 2, BHD 3), so scale by the currency's
    // exponent rather than assuming 2 decimals, and show the ISO code to avoid the wrong-symbol trap.
    public override string ToString()
    {
        var digits = Currency switch { "JPY" or "KRW" or "VND" => 0, "BHD" or "KWD" or "OMR" => 3, _ => 2 };
        var amount = MinorUnits / (decimal)Math.Pow(10, digits);
        return $"{amount.ToString("N" + digits, CultureInfo.CurrentCulture)} {Currency}";
    }
}
```

> **Конвертація валют — це не просто множення.** Курси залежать від часу (який курс і коли?), містять спред і мають правила округлення. Ніколи не закріплюйте курс у коді й не конвертуйте мовчки: записуйте використані курс і час, бо згодом хтось попросить звірити облік.

### Форматування чисел з урахуванням культури

Специфікатори формату `"C"` (валюта), `"N"` (число) й `"P"` (відсоток) залежать від `CultureInfo`: роздільники тисяч і дробової частини, символи валют відрізняються. У Німеччині це `1.234,56 €`, у США — `$1,234.56`. На межі відображення форматуйте для культури *користувача*, а для всього, що розбиратиме машина, використовуйте `InvariantCulture`.

## Глобалізація й локалізація (i18n / l10n)

**Інтернаціоналізація (i18n)** — це створення програмного забезпечення, *здатного* пристосовуватися до локалей; **локалізація (l10n)** — саме пристосування до певної локалі. .NET має добру підтримку обох процесів на основі `CultureInfo`.

### `CurrentCulture` і `CurrentUICulture`

- **`CultureInfo.CurrentCulture`** керує *форматуванням*: дат, чисел, валют і сортування.
- **`CultureInfo.CurrentUICulture`** визначає, *які перекладені ресурси* завантажити, тобто мову рядків інтерфейсу.

Їх навмисно розділено: німецькомовний експатріант у Німеччині може бажати англійський інтерфейс (`CurrentUICulture = en`) із німецьким форматуванням чисел і дат (`CurrentCulture = de-DE`). В ASP.NET Core проміжний компонент **Request Localization** задає обидва значення окремо для кожного запиту на основі заголовка `Accept-Language`, cookie або рядка запиту.

### Файли ресурсів і `IStringLocalizer`

Текст для перекладу зберігайте у файлах ресурсів **`.resx`**, а не в коді. Створіть основний `Messages.resx` і файли для окремих культур (`Messages.de.resx`, `Messages.uk.resx`). Середовище виконання застосовує **резервний пошук**: якщо не знайдено `de-CH`, воно шукає `de`, а потім нейтральний ресурс за замовчуванням. В ASP.NET Core передавайте `IStringLocalizer<T>` через впровадження залежностей:

```csharp
public class CheckoutController : Controller
{
    private readonly IStringLocalizer<CheckoutController> _t;
    public CheckoutController(IStringLocalizer<CheckoutController> t) => _t = t;

    public IActionResult Confirm() =>
        // Looks up "OrderPlaced" in the culture-appropriate .resx,
        // falling back to the key itself if no translation exists.
        Content(_t["OrderPlaced"]);
}
```

> **Ніколи не створюйте речення конкатенацією.** Рядок `"You have " + count + " items"` неможливо перекласти: порядок слів та й самі слова різняться залежно від мови. Використовуйте рядки ресурсів із параметрами: `_t["ItemCount", count]`.

### Множина й напрямок справа наліво

У мов дуже різні правила утворення множини. В англійській є дві форми (1 item / 2 items); в українській і російській — *три* (1 товар, 2 товари, 5 товарів); в арабській — шість. Просте `if (count == 1)` неправильне для більшості мов світу. Для якісної локалізації використовуйте рушій правил множини — **категорії множини** ICU/CLDR (`zero`, `one`, `two`, `few`, `many`, `other`), а не власні умови.

Мови з напрямком письма **справа наліво (RTL)** (арабська, іврит) віддзеркалюють увесь макет, а не лише текст. Здебільшого це питання інтерфейсу (CSS `dir="rtl"`, логічні замість фізичних відступів), але серверні розробники також стикаються з ним під час генерації PDF і листів: шаблони не мають жорстко задавати вирівнювання ліворуч чи праворуч.

### Порівняння й сортування рядків: непомітна катастрофа

Це одна з найменш оцінених проблем правильності в .NET, яка спричиняє справжні помилки безпеки. Є два принципово різні способи порівнювати рядки:

- **За порядковими значеннями (Ordinal)** — порівнює необроблені елементи коду UTF-16. Швидке, детерміноване й незалежне від культури. Правильний вибір для внутрішніх ідентифікаторів програми: ключів, токенів, шляхів до файлів, значень протоколу й ключів кешу.
- **З урахуванням культури (лінгвістичне)** — порівнює за правилами сортування певної культури. Символ `"ä"` може сортуватися біля `"a"` або після `"z"` залежно від локалі. Правильний вибір, якщо потрібно показати людині відсортований список.

> **Проблема турецької літери i.** У турецькій культурі (`tr-TR`) велика літера для `i` — це `İ` (з крапкою), а мала для `I` — `ı` (без крапки). Тож у турецькій культурі `"file".ToUpper()` дає `"FİLE"`, а `"file".ToUpper() == "FILE"` — **false**. Код, який таким чином порівнював, скажімо, розширення файлу чи заголовок HTTP, переставав працювати на турецьких машинах — і це використовували зловмисники.

Виправлення — вказувати тип порівняння явно й користуватися порядковим порівнянням для всього, що не є лінгвістичним:

```csharp
// WRONG for internal logic — culture-dependent; on tr-TR ".ZIP" lowers to ".zıp":
if (ext.ToLower() == ".zip") { }
if (header.Equals("Authorization", StringComparison.CurrentCultureIgnoreCase)) { }

// RIGHT — explicit, culture-independent:
if (ext.Equals(".zip", StringComparison.OrdinalIgnoreCase)) { }
if (header.Equals("Authorization", StringComparison.OrdinalIgnoreCase)) { }

// For case-insensitive normalization, use the invariant culture:
string normalized = ext.ToUpperInvariant();
```

**Практичне правило: якщо людина не читатиме порядок сортування, використовуйте `Ordinal` або `OrdinalIgnoreCase`.** Залиште порівняння `CurrentCulture` для сортування й пошуку в інтерфейсі. Аналізатори коду (CA1304, CA1305, CA1307, CA1310) виявляють виклики, що неявно залежать від культури; за замовчуванням вони вимкнені, тому ввімкніть їх.

> **Зверніть увагу.** **Які перевантаження самі вибирають культуру.** `==`, `Equals`, `Contains`, `Replace` і `IndexOf(char)` типово використовують порядкове порівняння. `string.Compare`, `CompareTo`, `StartsWith(string)`, `EndsWith(string)`, `IndexOf(string)`, `LastIndexOf(string)`, `ToUpper()` і `ToLower()` використовують *поточну культуру*, якщо не передати `StringComparison` чи культуру; це також стосується `OrderBy(s => s)` і `List<string>.Sort()`, які застосовують компаратор за замовчуванням. Починаючи з .NET 5, операції з урахуванням культури використовують ICU на всіх платформах, тож результати можуть несподівано відрізнятися від порядкових: приклад у документації — `"Hel\0lo".IndexOf("\0")`, що повертає `0`, бо ICU не надає нульовому символу ваги; із `StringComparison.Ordinal` результат — `3`. Завжди передавайте тип порівняння явно — тоді типове значення не матиме значення.

### Нормалізація Unicode

Той самий видимий символ може бути закодований кількома способами. `é` може бути одним кодовим пунктом (U+00E9, *складена* форма) або символом `e` і комбінованим наголосом (U+0065 U+0301, *розкладена* форма). Це *канонічно еквівалентні*, але **не рівні за порядковими значеннями** рядки: побайтове порівняння вважає їх різними, тому наївна перевірка входу або усунення дублікатів може трактувати «однакові» рядки як різні.

```csharp
string composed = "é";          // é
string decomposed = "é";       // e + combining acute
Console.WriteLine(composed == decomposed);              // False!
Console.WriteLine(composed.Normalize() == decomposed.Normalize()); // True
```

> **Нормалізуйте вхідні дані Unicode із зовнішніх джерел** (зазвичай до форми NFC) перед збереженням, порівнянням або використанням як ключа — особливо імена користувачів, адреси електронної пошти й ідентифікатори. У сучасних платформах порівняння рядків і зміна регістру в .NET спираються на **ICU**, який дотримується стандарту Unicode. Враховуйте, що дані ICU (а отже, порядок сортування й правила регістру) можуть змінюватися між версіями ОС і середовища виконання, тому не зберігайте порядок, відсортований *за культурою*, як незмінний.

## Поширені інтеграції, потрібні кожному застосунку

Ви підключатимете їх майже в кожній реальній системі. Тут розглянуто *безпечний підхід*, а не весь перелік API.

### Файли й об’єктне сховище: використовуйте потоки, не буферизуйте

Найчастіший інцидент під час роботи з файлами — **завантаження великого файлу цілком у пам’ять**. `IFormFile.CopyToAsync`, `ReadAllBytesAsync` або `new byte[file.Length]` для завантаження на кілька гігабайтів спричиняють різкий стрибок споживання пам’яті й можуть завершити процес через OOM за одночасних запитів.

> **Передавайте вміст файлу потоками на всьому шляху.** Читайте з потоку запиту й записуйте до потоку призначення, не створюючи повну копію вмісту в пам’яті. Тоді споживання пам’яті залишатиметься сталим незалежно від розміру файлу.

```csharp
// Streaming an upload straight to blob storage — memory stays flat.
public async Task SaveAsync(IFormFile file, BlobContainerClient container,
                            CancellationToken ct)
{
    BlobClient blob = container.GetBlobClient(file.FileName);
    await using Stream source = file.OpenReadStream();
    await blob.UploadAsync(source, overwrite: true, ct);
}
```

Інші важливі речі з практики: установлюйте **обмеження розміру** (`RequestSizeLimit` або `MaxRequestBodySize` у Kestrel), щоб завантаження не спричинили відмову в обслуговуванні; перевіряйте тип вмісту *й* сигнатуру файлу, а не лише розширення; ніколи не використовуйте надану клієнтом назву файлу як шлях до сховища (можливий вихід за межі каталогу); для дуже великих файлів застосовуйте **блокове завантаження** через SDK і розгляньте **підписані URL (SAS)**, щоб клієнти завантажували файли безпосередньо до сховища, оминаючи рівень вебзастосунку. Усі великі хмарні платформи — Azure Blob Storage, Amazon S3 і Google Cloud Storage — надають через SDK ті самі можливості потокового передавання й підписаних URL.

### Надсилання електронної пошти: SMTP чи транзакційні провайдери

Ви *можете* надсилати листи безпосередньо через SMTP (`System.Net.Mail.SmtpClient` — для нового коду він уже позначений застарілим; спільнота надає перевагу **MailKit**). Але для листів із застосунку майже завжди краще використовувати **транзакційного провайдера електронної пошти** (SendGrid, Amazon SES, Postmark, Mailgun). Він бере на себе найважливішу частину: **доставлення**.

Доставлення переважно залежить від трьох механізмів автентифікації на рівні DNS. Якщо налаштувати їх неправильно, лист потрапить у спам або його відхилять:

- **SPF** — визначає, яким серверам дозволено надсилати листи від імені вашого домену.
- **DKIM** — криптографічний підпис, який підтверджує, що лист не змінювали й надіслали саме ви.
- **DMARC** — політика, яка повідомляє одержувачам, що робити, якщо перевірка SPF/DKIM не пройшла.

> **Відокремте транзакційні листи** (чеки, скидання паролів) **від масових і маркетингових**, бажано на окремих піддоменах, щоб проблеми з репутацією маркетингової пошти ніколи не заблокували лист для скидання пароля. Також **створюйте шаблони листів** (за допомогою рушія шаблонів або шаблонів провайдера), а не об’єднуйте HTML у коді: це дає змогу змінювати вміст без розгортання коду й дозволяє редагувати його людям без інженерних знань.

### Сповіщення: push, SMS і вебхуки

- **Push-сповіщення й SMS** працюють за тим самим принципом «використовуйте провайдера»: Firebase Cloud Messaging / APNs для push, Twilio або подібний SMS-шлюз. Вважайте їх доставлення найкращим зусиллям і забезпечте ідемпотентність: мережа губить повідомлення, а дублікати є нормою.
- **Вебхуки** — це спосіб, у який сторонні системи повідомляють *вас* (платіж пройшов, обробку файлу завершено). Отримуючи вебхук, **обов’язково перевіряйте його справжність**. Стандартний механізм — **підпис HMAC**: відправник підписує необроблене тіло запиту спільним секретом і передає результат у заголовку; ви обчислюєте підпис повторно й порівнюєте його.

```csharp
// Verifying an inbound webhook signature. Two non-negotiables:
// (1) hash the RAW body bytes, before any deserialization;
// (2) compare in constant time to avoid timing attacks.
static bool IsValid(byte[] rawBody, string headerSig, byte[] secret)
{
    using var hmac = new HMACSHA256(secret);
    byte[] expected = hmac.ComputeHash(rawBody);
    byte[] provided = Convert.FromHexString(headerSig);
    return CryptographicOperations.FixedTimeEquals(expected, provided);
}
```

> **Обробники вебхуків мають бути ідемпотентними** (відправники повторюють спроби, тож можливі дублікати), **швидко відповідати** (підтвердити отримання кодом 200, а потім виконати справжню роботу у фоновій черзі) й **перевіряти підпис за точними необробленими байтами**: попередня повторна серіалізація JSON змінить байти й зламає перевірку.

### Генерація PDF і звітів

Звіти й PDF потрібні постійно. Зараз найпопулярніша бібліотека у світі .NET — **QuestPDF**: плавний API з описом через код і чудовий досвід розробки (для великих компаній перевірте умови ліцензування). Є й альтернативи: перетворювачі HTML у PDF (**Playwright** / безголовий Chromium, wkhtmltopdf), зріла комерційна бібліотека **iText** і **PuppeteerSharp**.

```csharp
// QuestPDF — declarative, and streams straight to the response.
Document.Create(doc =>
{
    doc.Page(page =>
    {
        page.Margin(40);
        page.Header().Text("Invoice #1042").FontSize(20).Bold();
        page.Content().Text(t =>
            t.Span($"Total: {new Money(1999, "USD")}"));
    });
}).GeneratePdf(responseStream);
```

> **Генерація PDF потребує багато процесорного часу й пам’яті** — особливо перетворення HTML у PDF, яке запускає рушій браузера. Для нетривалої роботи не виконуйте її безпосередньо в потоці обробки запиту. Один запит на великий звіт може перевантажити вебсервер.

### Об’єднайте підхід: переносьте важку роботу у фон

У цих прикладах повторюється один принцип: надсилання електронної пошти, зміна розміру чи обробка завантажень, створення PDF, надсилання push-сповіщень і виклики ненадійних сторонніх API — усе це **повільні операції, що можуть завершуватися невдало й потребують повторних спроб**. Якщо виконувати їх синхронно в HTTP-запиті, час відповіді користувачеві залежатиме від неконтрольованої вами системи, а тимчасова відмова провайдера перетвориться на помилку 500, яку побачить користувач.

Senior-розробник інтуїтивно **переносить такі операції у фонову обробку** ([Розділ 11](#chapter-11-messaging-and-background-work)): приймає запит, зберігає намір, додає завдання до черги (через hosted service, `Channel` або надійну чергу на кшталт Azure Service Bus / RabbitMQ, яку обробляє worker) і негайно повертає відповідь. Фоновий worker відповідає за повторні спроби, ідемпотентність і обробку черги недоставлених повідомлень.

```csharp
// The controller does the minimum and returns fast.
[HttpPost("orders/{id}/invoice")]
public async Task<IActionResult> Invoice(int id)
{
    Job job = await _jobs.EnqueueAsync(new GenerateInvoiceJob(id));  // durable: a job row and an outbox message
    Response.Headers.RetryAfter = "5";
    return AcceptedAtAction(nameof(GetJob), new { jobId = job.Id }, job);  // 202 + Location: where to check back
}
```

Виклик `Accepted()` без додаткових даних лише каже «перевірте пізніше», але не вказує, де саме. Заголовок `Location` містить ресурс стану завдання; клієнт опитує його, доки сервер не перенаправить до результату. У [Розділі 11, підрозділі «Асинхронний запит-відповідь»](#async-request-reply-202-a-status-resource-and-retry-after) розглянуто весь контракт: ресурс стану, `303 See Other`, помилки й ключ ідемпотентності, який робить повторений `POST` безпечним.

Так працює кожен стійкий реальний застосунок: **шлях обробки запиту залишається коротким і швидким; усе повільне, зовнішнє чи ненадійне переходить до фонового worker-а, який може безпечно повторити спробу.** Поєднайте це з попередніми правилами — усюди UTC, для грошей `decimal`, для внутрішньої логіки порядкове порівняння, потокове передавання вмісту файлів і перевірка вебхуків — і ви усунете більшість буденних помилок, які насправді призводять до збоїв продакшену.

## Перевірте на практиці

Спочатку розгляньмо гроші: спрогнозуйте результат кожного рядка, перш ніж запускати програму. Потрібен лише .NET 10 SDK.

`verify/path/MoneyAndRounding/Program.cs` · запускайте з `verify/path` командою `dotnet run --project MoneyAndRounding`:

```csharp
// Prove it: double cannot store most decimal fractions, decimal can; Math.Round sends a midpoint to
// the even neighbour unless told otherwise, and ToString("F2") does not round the way Math.Round does.
double d = 0.1 + 0.2;
decimal m = 0.1m + 0.2m;
Console.WriteLine($"0.1 + 0.2: double {d} (== 0.3: {d == 0.3}), decimal {m} (== 0.3: {m == 0.3m})");

double priceAsDouble = 1.005;
Console.WriteLine($"1.005 to cents, AwayFromZero: double {Math.Round(priceAsDouble, 2, MidpointRounding.AwayFromZero)}, " +
    $"decimal {Math.Round(1.005m, 2, MidpointRounding.AwayFromZero)}");
Console.WriteLine($"  the double 1.005 is really {priceAsDouble:F20}");

Console.WriteLine($"Math.Round(2.5m) = {Math.Round(2.5m)}, Math.Round(3.5m) = {Math.Round(3.5m)} (half to even: the default)");
Console.WriteLine($"Math.Round(2.5m, MidpointRounding.AwayFromZero) = {Math.Round(2.5m, MidpointRounding.AwayFromZero)}");
Console.WriteLine($"Math.Round(2.345m, 2) = {Math.Round(2.345m, 2)}, but 2.345m.ToString(\"F2\") = {2.345m.ToString("F2")}");

decimal share = Math.Round(100.00m / 3, 2);
Console.WriteLine($"100.00 split three ways: {share} each, {share * 3} in total; the missing cent needs a rule");
```

```text
0.1 + 0.2: double 0.30000000000000004 (== 0.3: False), decimal 0.3 (== 0.3: True)
1.005 to cents, AwayFromZero: double 1, decimal 1.01
  the double 1.005 is really 1.00499999999999989342
Math.Round(2.5m) = 2, Math.Round(3.5m) = 4 (half to even: the default)
Math.Round(2.5m, MidpointRounding.AwayFromZero) = 3
Math.Round(2.345m, 2) = 2.34, but 2.345m.ToString("F2") = 2.35

```

Результат отримано з `verify/path/reference-runs/money-and-rounding.txt` (.NET 10.0.12, Linux x64); він однаковий на всіх машинах, бо не залежить ні від годинника, ні від культури. Зверніть увагу:

- **Значення `double` ніколи не було 1.005.** Явне `AwayFromZero` не виправить значення, яке вже лежить нижче за середину. З тієї самої причини порівняння рівності не проходить: `0.1 + 0.2` і `0.3` — це два різних наближення у двійковій системі.
- **В одному рахунку застосовано два правила округлення.** `Math.Round` залишає 2.34 (до парного), а `"F2"` показує 2.35 (від половини від нуля). Округліть один раз явним `MidpointRounding` і форматуйте вже округлене значення, інакше документ розходитиметься з реєстром на копійку.
- **`decimal` точний лише для десяткових дробів.** Третина від 100.00 не має скінченного десяткового подання. Для розподілу потрібне правило — наприклад, віддати копійку залишку першій частці, — щоб сума частин дорівнювала загальній сумі.
