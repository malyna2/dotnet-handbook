# Розділ 19: лабораторна робота з повільними запитами — читання execution plans

[Розділ 18](#chapter-18-data-in-depth) пояснює, як читати план запиту, спираючись на основи SQL та індексів із [Розділу 7](#chapter-7-data-access). У цій лабораторній роботі ви прочитаєте дев’ять планів на наборі даних, достатньо великому, щоб різниця стала помітною: мільйон клієнтів, п’ять мільйонів замовлень і вісімнадцять мільйонів рядків замовлень, а також перекіс, властивий реальним даним: один клієнт створює 5% усіх замовлень, а один товар входить до 8% усіх рядків. Кожен повільний запит походить із коду EF Core, який пройшов би перевірку коду. Для кожного знайдіть механізм у плані, виправте його на відповідному рівні (LINQ, схема чи конфігурація) й доведіть результат повторним вимірюванням.

У результаті у вас буде найпереконливіший артефакт із продуктивності — таблиця показників до й після, де кожен рядок посилається на два плани й абзац із поясненням *чому*.

```
 run the rung ──► read the plan ──► name the mechanism ──► smallest fix ──► run it again
      ▲                                                                          │
      └──────── compare the work (statements, rows, buffers), not just time ◄────┘
```

> **Правило для портфоліо.** Нічого з виконаного тут не додавайте до репозиторію посібника. Виправлені кроки, плани до й після та таблицю результатів розмістіть **у власному публічному репозиторії для портфоліо**, де їх зможе переглянути людина, яка проводить співбесіду. Якщо переказуєте лабораторну як історію про систему справжнього роботодавця, ця версія має залишитися **приватною**.

Комплект лежить у [labs/37-execution-plans](https://github.com/malyna2/dotnet-handbook/tree/main/labs/37-execution-plans). До нього входять:

- стек Docker Compose із PostgreSQL 18, `pg_stat_statements` і `auto_explain`;
- детермінований набір тестових даних;
- застосунок .NET 10, який виконує кожен запит і зберігає фактично використаний сервером план;
- стартовий проєкт із дев’ятьма повільними реалізаціями;
- приймальні тести;
- додатковий трек для SQL Server 2025.

Числа в цьому розділі взято з `reference-runs/` комплекту. На початку кожного файла в цій папці вказано середовище вимірювання: 4 vCPU, 16 ГБ RAM, PostgreSQL 18.6, прогрітий кеш і середній обсяг даних.

## Мета й навичка досвідченого інженера

**Мета:** для повільного запиту знайти механізм у його плані, обрати найменше виправлення на відповідному рівні й довести результат числами, які інша людина зможе відтворити.

**Навичка досвідченого інженера — пояснити *чому* й оцінити вартість виправлення.** Більшість розробників уміє пришвидшити запит, додавши індекс і побачивши менший час виконання. Відповіді, які запам’ятовують на співбесідах, ідуть глибше:

- який вузол плану спричинив проблему;
- чому планувальник обрав цей вузол — кращого варіанта не було чи йому бракувало інформації;
- чого коштує виправлення: час побудови, місце на диску, додаткове навантаження на запис або помітні користувачам зміни;
- як переконатися, що покращення реальне, а не результат прогрітого кешу.

Цей ланцюжок — *вимірювання → механізм → мінімальне виправлення → доказ* — ви відпрацюєте тут дев’ять разів.

**Друга навичка: розуміти, що ORM визначає SQL.** Кілька кроків стосуються зовсім не бази даних. План лише показує докази, а виправлення — один рядок C#.

```bash
cd labs/37-execution-plans

dotnet run --project src/QueryLab.Cli -- all          # every rung: numbers and plans
dotnet run --project src/QueryLab.Cli -- 3 --no-plan  # one rung, numbers only
dotnet test --project tests/QueryLab.Tests            # the acceptance tests
```

Працюйте в `starter/QueryLab.Rungs/`. Кожен крок — окремий клас:

- **Вхідні дані й тип результату незмінні.** Їх визначає базовий клас у `src/QueryLab.Core/Contracts.cs`, тому змінюйте *спосіб* отримання відповіді, а не те, *що саме* вона повертає.
- **DDL додавайте до `Fixes`.** Крок може вказати там DDL, який застосунок запускає до виконання кроку.
- **Називайте створене `lab_*`.** Перед кожним кроком і після останнього застосунок видаляє всі індекси й об’єкти статистики `lab_*`. Кроки не залежать від виправлень одне одного, а після завершення база повертається до початкового заповненого стану.

Приймальні тести запускають власний PostgreSQL у контейнері, заповнюють його малим набором даних і перевіряють кожен крок за двома критеріями:

1. **Правильність.** Крок повертає точно ті самі рядки, що й еталонний запит SQL, написаний вручну.
2. **Обсяг роботи.** Він вкладається в обмеження на кількість операторів, рядків, буферів або вузол плану — не в мілісекундах. Тому результат тесту однаковий на ноутбуці й у CI.

Стартовий крок, який не проходить перевірку, повертає повідомлення з префіксом `ACCEPTANCE:`. Будь-яка інша помилка означає, що код зламано, а не просто повільно.

### Що друкує застосунок і в якому порядку це читати

Для кожного кроку CLI:

1. застосовує виправлення цього кроку;
2. один раз запускає крок, щоб прогріти кеш;
3. скидає статистику `pg_stat_statements`;
4. вимірює п’ять викликів;
5. друкує те, що надіслав EF Core, значення параметрів із типами та план.

Підсумок для кроку 4 виглядає так (повний рядок ширший):

```
fixes       : none
wall time   : median 488.2 ms over 5 calls (min 458.7, max 547.6)
per call    : 1 statement(s), 1 rows returned,
              shared buffers 6,741 hit + 42,702 read, 501.6 ms server execution
```

Читайте його в такому порядку:

1. **Спершу `per call`.** Кількість операторів, рядків і буферів вимірює обсяг *роботи*, тож на будь-якому комп’ютері має бути близькою до наших значень; мілісекунди — ні.
   - Буфер — це сторінка розміром 8 кБ.
   - `hit` означає, що сторінка вже була у спільних буферах PostgreSQL.
   - `read` означає, що її там не було. Вона могла бути в кеші сторінок операційної системи, тому `read` не завжди означає читання з диска.
2. **Потім — план зсередини назовні**, як у розділі [Читання EXPLAIN](#reading-explain): оцінена й фактична кількість рядків, `loops`, буфери кожного вузла.
3. **Порівняйте час із боку клієнта й сервера.**
   - Час із боку клієнта вимірюється в .NET навколо всього виклику.
   - Час сервера записує `pg_stat_statements`.
   - Різниця — це цикли обміну, мережа й перетворення рядків на об’єкти в EF Core. В одному з кроків саме ця різниця становить усю проблему.

У PostgreSQL 18 з’явилися три відмінності у виводі, яких ви не побачите у старих статтях:

- **Буфери типово.** `EXPLAIN ANALYZE` друкує кількість буферів, навіть якщо не вказати `BUFFERS`.
- **Два десяткові знаки для `rows=`.** Тепер `rows=` виводиться з двома десятковими знаками, бо це середнє на цикл. `rows=72421.50 loops=2` означає, що два паралельні процеси обробили в середньому по 72 421,5 рядка.
- **`Index Searches:`** новий рядок показує загальну кількість спусків індексом за всіма циклами. Значення дорівнює 1 для звичайного сканування, кількості зовнішніх рядків для внутрішнього боку вкладеного циклу й більше за 1, коли нове в PostgreSQL 18 сканування з пропуском переходить між значеннями провідного стовпця.

## Завдання

Назви кроків описують функцію, а не помилку; знайти помилку — ваше завдання. Кожен крок має критерій приймання й покажчик *спершу подивіться сюди*. Звіряйте міркування з розділом *Підказки й відповіді* лише після того, як виправлення пройшло перевірку.

### Рівень 1 — SQL визначає код (кроки 1–4)

| Крок | Сценарій | Успіх, якщо |
|---|---|---|
| 1 | Сторінка історії замовлень: останні 50 замовлень ключового клієнта 2 разом із рядками кожного. | не більше 2 операторів на виклик |
| 2 | Квартальний звіт доставки: відправлені замовлення ключового клієнта 2 за останні 90 днів разом із рядками й відправленнями. | сервер повертає не більше рядків, ніж є замовлень, рядків замовлень і відправлень |
| 3 | Вхід: знайти клієнта за введеною під час входу адресою електронної пошти, незалежно від регістру. | немає `Seq Scan` по `customers` |
| 4 | Партнерський webhook: партнер доставки надсилає номер замовлення, а handler (обробник) завантажує це замовлення. | немає `Seq Scan` по `orders` |

Спершу подивіться сюди:

- **Крок 1:** на кількість операторів, а не на план.
- **Крок 2:** на рядок `EF warning` і повернуті рядки.
- **Крок 3:** на рядок `Filter`.
- **Крок 4:** на SQL, який згенерував EF Core, символ за символом.

Готово, коли:

- приймальні тести для кроків 1–4 пройшли;
- у `RESULTS.md` вашого портфоліо є рядок для кожного кроку з часом до й після, кількістю операторів, рядків і буферів, а також одним реченням про механізм;
- плани до й після для кожного кроку збережено як текстові файли поруч.

### Рівень 3 — за межами застосунку

1. **Побачте N+1 з боку сервера.** Окремо запустіть стартовий крок 1 (`-- 1 --no-plan`). Потім самостійно опитайте `pg_stat_statements` щодо кількості викликів, рядків, сумарного часу й буферів на оператор. Що говорить співвідношення між записами? Чому один план не може показати цю проблему?
2. **Спіймайте крок 9 на місці.** Файл Compose завантажує `auto_explain` із порогом в одну секунду. Знайдіть виконання бестселера в `docker compose logs postgres` і лише за журналом доведіть, що сервер використав загальний план.
3. **Оцініть альтернативу.** Виправте крок 9 *без індексу*: запустіть стартовий код із `plan_cache_mode`, заданим через connection string (рядок підключення) (команда нижче). Потім запишіть, скільки коштує це рішення порівняно з індексом.
4. **Трек SQL Server.** Виконайте `docker compose --profile sqlserver up -d` і `./sqlserver.sh seed`, а потім скрипти від 1 до 4. Для кожного назвіть відповідний крок PostgreSQL і відмінності поведінки SQL Server.

### Застаріла статистика

У `break-it-stale-statistics.sql` клієнт 900,001 — звичайний покупець із трьома замовленнями — стає продавцем торговельного майданчика й пакетно завантажує 300 000 замовлень. Наприкінці скрипт скасовує транзакцію завантаження.

| | Оцінка планувальника для нового клієнта | План | Обсяг роботи |
|---|---|---|---|
| До `ANALYZE` | 23 рядки | Використовує звичайний індекс `customer_id`, отримує всі 300 003 рядки й сортує їх, щоб повернути 50 | 3 048 буферів, 80,5 мс |
| Після `ANALYZE` | 306 526 рядків | Іде індексом `created_at` у зворотному напрямку, доки не знайде 50 рядків | 12 буферів, 0,1 мс |

Перед запуском передбачте оцінку. Після запуску поясніть, звідки взялися 23. Скрипт друкує інформацію, яку мав планувальник.

### Карта видимості

`break-it-visibility-map.sql` будує покривний індекс кроку 5, а потім видаляє всі рядки товару 50 і скасовує видалення. Жоден рядок не змінився, але:

| Стан | Отримання з таблиці | Буфери | Час |
|---|---:|---:|---:|
| Карта видимості актуальна | 0 | 101 | 5,0 мс |
| Після скасованого `DELETE` | 18 015 | 17 091 | 60,4 мс |
| Після `VACUUM` | 0 | 98 | 7,6 мс |

Поясніть середній рядок. Що це означає для сканування лише індексу на таблиці, в яку записують увесь день?

> **Нюанс.** `ROLLBACK` — це не скасування наслідків. Рядки, які скасували, залишаються в таблиці й кожному індексі як мертві кортежі, доки `VACUUM` їх не видалить. Сторінки, що розділилися під час вставлення в індекс, залишаються розділеними й після цього. Саме тому обидва скрипти очищають дані. До додавання цього очищення пакетне завантаження, яке скасували, вимірювано збільшувало обсяг роботи для кроків 6 і 7, доки не запускався autovacuum. На спільній тестовій базі за експеримент платив би наступний користувач.

### Пагінація за ключем у різних формах

`sidebar-keyset-forms.sql` отримує сторінку кроку 7 чотирма способами. Усі повертають ті самі 50 рядків.

| Форма | Буфери | Час |
|---|---:|---:|
| `OFFSET 200000 LIMIT 50` | 2 791 | 68,2 мс |
| Пагінація за ключем, форма з OR: `created_at < x OR (created_at = x AND id < y)` | 2 791 | 23,0 мс |
| Пагінація за ключем, кортеж: `(created_at, id) < (x, y)` | 5 | 0,08 мс |
| Кортеж із індексом за `(created_at, id)` | 5 | 0,08 мс |

Форма з OR — правильна пагінація за ключем, але виконує стільки само роботи, скільки `OFFSET`. Знайдіть у плані рядок, який це пояснює. Потім скажіть, що дає четвертий план порівняно з третім, адже вони читають однакову кількість буферів.

### Помилкова оцінка, яка не має значення

`sidebar-correlated-columns.sql` підраховує замовлення за останній квартал для клієнтів із Берліна. Планувальник перемножує вибірковість `country = 'DE'` і `city = 'Berlin'`, наче ці умови незалежні, тому очікує **15 333** рядки замість фактичних **79 941** — приблизно вп’ятеро менше. `CREATE STATISTICS … (dependencies, mcv)` виправляє оцінку (до 80 967).

План не змінюється: те саме паралельне хеш-з’єднання, ті самі сканування, ті самі 15 369 буферів. Час виконання скорочується зі 127,6 мс до 95,9 мс, і легко приписати це статистиці. Але під час першого запуску з диска прочитали 72 сторінки, а під час другого вони вже були в кеші; сам план залишився тим самим. Краща статистика не пришвидшить план, який вона не змінила.

Два висновки:

- **Помилкова оцінка має значення, лише якщо змінює рішення.** Шукайте інший план, а не інше число.
- **Порівнюйте прогріті запуски з прогрітими й повторюйте вимірювання,** перш ніж приписувати зміні прискорення.

## Тема для співбесіди

Запитання «Сторінка стала повільною — що ви робите?» трапляється майже на кожній співбесіді для досвідченого .NET-інженера. [Розділ 9](#chapter-9-exceptions-logging-and-first-diagnosis) описує загальний підхід; ця лабораторна дає дев’ять конкретних прикладів і готову історію. Не приховуйте походження прикладу: сильний початок — «У практичній лабораторній роботі на наборі з п’яти мільйонів замовлень…», а видавати лабораторну за продакшен-досвід не слід (правила чесності наведені в [Розділі 37](#chapter-37-the-story-bank-evidence-portfolio)).

**«Розкажіть про запит, який ви пришвидшили»** — відповідь за STAR на основі кроку 9, бо тут найбільше матеріалу для додаткових запитань:

- **S:** Панель «останні продажі» на сторінці товару поверх таблиці з 18 мільйонами рядків працювала швидко під час тестування. У лабораторній для бестселера вона займала близько секунди, але лише після того, як сервіс деякий час працював. [Для реальної історії: endpoint (кінцева точка), розмір таблиці, як проблему помітили.]
- **T:** з’ясувати, чому це відбувалося лише після прогрівання, і виправити проблему, не сповільнюючи інші товари.
- **A:**
  - Знайшов повільне виконання в журналі `auto_explain`. Умова індексу плану містила `$1` — це був загальний план.
  - Відстежив причину: автоматична підготовка Npgsql перетворила запит на підготовлений оператор на сервері. Після п’яти спеціальних планів PostgreSQL перейшов до загального, розрахованого на середній товар (оцінка — 463 рядки), тоді як бестселер має 1,44 млн.
  - Оцінив два виправлення:
    - примусове створення спеціального плану: 7 буферів, але планування кожного виконання кожного оператора на цих підключеннях;
    - індекс `(product_id, id)`, з яким один план підходить для всіх товарів: 7 буферів, 11 секунд побудови, 542 МБ на диску.
  - Обрав індекс.
- **R:** у лабораторній — із 151 331 буфера й приблизно секунди до 7 буферів і 1,5 мс для бестселера, без змін для інших товарів. Приймальний тест перевіряє це. [Для реальної історії: p95 до й після за даними вашого APM.]

Три ймовірні додаткові запитання:

1. **«Чому лише після прогрівання?»** Спрацьовує правило кешу планів PostgreSQL. Для підготовленого оператора створюються п’ять спеціальних планів; після цього сервер використовує загальний, якщо оцінена вартість не набагато вища за середню вартість спеціальних планів. Під час прогрівання запити для популярних товарів зробили спеціальні плани дорогими, тож переміг загальний план.
2. **«Чому просто не задати `force_custom_plan`?»** Разову витрату (індекс) це замінює постійною: планування кожного виконання кожного оператора на цих підключеннях. Також це приховує наступну проблему нерівномірності, а не усуває цю. Це добрий тимчасовий захід або налаштування для певної ролі в workload (робочому навантаженні), про яке відомо, що воно має перекоси.
3. **«Скільки коштує індекс для запису?»** Кожне вставлення до `order_lines` обслуговуватиме ще один індекс. Виміряйте пропускну здатність вставлення до й після. Старий індекс `product_id` тепер зайвий (це провідний стовпець нового індексу), тож видаліть його, коли `pg_stat_user_indexes` підтвердить, що більше ніщо ним не користується. Тоді кількість індексів, які оновлює кожне вставлення, повернеться до попередньої, хоча індекс, який залишився, буде більшим.

Плани правильні. Перший оператор читає 81 буфер, а оператор для рядків кожного замовлення — 4 буфери й працює 0,04 мс. Сервер виконував 2,0 мс роботи на виклик, а медіанний час завантаження сторінки становив 78,0 мс. Майже весь час пішов на 51 цикл обміну й 51 перетворення результатів на об’єкти в EF Core.

Виправлення — одна проєкція з вкладеною колекцією:

```csharp
.Select(o => new OrderHistoryRow(o.Id, o.CreatedAt, o.Status, o.Total,
    o.Lines.OrderBy(l => l.Id)
           .Select(l => new OrderLineRow(l.ProductId, l.Quantity, l.UnitPrice))
           .ToList()))
```

EF Core перетворює її на `LEFT JOIN` із підзапитом, який спершу вибирає 50 замовлень. У результаті один оператор, ті самі 291 буфер і 9,1 мс. `AsSplitQuery()` також проходить перевірку: два оператори. Обсяг роботи бази даних зовсім не змінився — змінилася кількість циклів обміну. Саме тому N+1 непомітний в окремому плані: витрати виникають через цикли обміну, як пояснює [Розділ 7](#the-n1-problem-seeing-it-and-killing-it), а виявити проблему можна за кількістю операторів.

<summary>Крок 2 — квартальний звіт доставки</summary>

CLI друкує попередження самого EF Core: `MultipleCollectionIncludeWarning`. Два `Include` колекцій в одному запиті стають двома `LEFT JOIN`, і кожен рядок замовлення повторюється для кожного його відправлення:

```
Nested Loop Left Join  (actual ... rows=72421.50 loops=2)
  ->  Nested Loop Left Join  (actual ... rows=2895.00 loops=2)
        ->  Parallel Index Scan ... on orders o  (actual ... rows=725.00 loops=2)
        ->  Index Scan using ix_shipments_order_id ...  (actual ... rows=3.99 loops=1450)
  ->  Index Scan using ix_order_lines_order_id ...  (actual ... rows=25.02 loops=5790)
```

Подивіться на `loops`:

- 1 450 замовлень приблизно по 4 відправлення дають 5 790 рядків із замовленням і відправленням;
- далі кожен такий рядок з’єднується приблизно з 25 рядками замовлення;
- результат — 144 843 рядки, хоча звіту потрібно лише 43 529 (сума кількості замовлень, рядків і відправлень).

Сортування над з’єднанням вилилося на диск: `Sort Method: external merge  Disk: 16704kB`. Сервер витрачав 425,4 мс на виклик.

`AsSplitQuery()` надсилає окремий оператор для кожної колекції:

- 3 оператори, 43 529 рядків, 86,3 мс на сервері;
- 308,4 мс із боку клієнта. Залишилося передавання 43 529 рядків і створення з них об’єктів; проєкція лише потрібних файлу стовпців зменшила б і це.

Ціна розділеного запиту — consistency (узгодженість). Три оператори використовують окремі знімки, тож замовлення може отримати нове відправлення між запитами. Якщо звіт має бути внутрішньо узгодженим, обгорніть операції у транзакцію рівня snapshot або serializable. Для вивантаження менеджера облікового запису це рідко потрібно.
</details>

<details>
<summary>Крок 3 — вхід за адресою електронної пошти</summary>

```
Seq Scan on customers c  (actual ... rows=1.00 loops=1)
  Filter: (lower(email) = 'diego.larsen54321@corp.example'::text)
  Rows Removed by Filter: 999999
  Buffers: shared hit=13659
```

`c.Email.ToLower() == email.ToLower()` стає `lower(c.email) = lower(@email)`. B-tree за `email` зберігає `email`, а не `lower(email)`, тому він не може відповісти на це запитання, і сервер читає всі 13 659 сторінок таблиці, щоб знайти один рядок. Уся таблиця в кеші (`hit`), але виклик однаково займає 327,0 мс.

Створіть індекс за виразом:

```sql
CREATE UNIQUE INDEX lab_customers_email_lower ON customers (lower(email));
ANALYZE customers;
```

Результат — 4 буфери й 1,9 мс. Індекс навмисно `UNIQUE`: «один обліковий запис на адресу незалежно від регістру» — це бізнес-правило, яке тепер забезпечує база даних. `ANALYZE` збирає статистику нового виразу, яку планувальнику інакше довелося б вгадувати. Побудова тривала 3,3 с, розмір — 49 МБ.

Альтернативи — `citext` або зіставлення без урахування регістру — описано в розділі [Коли план неправильний](#when-the-plan-is-wrong).
</details>

<details>
<summary>Крок 4 — партнерський webhook</summary>

```sql
WHERE o.id::numeric = @payload_OrderNumber      -- @payload_OrderNumber = 424242 (numeric)
```

```
Seq Scan on orders o  (actual ... rows=1.00 loops=1)
  Filter: ((id)::numeric = '424242'::numeric)
  Rows Removed by Filter: 4999999
```

DTO партнера задає номер замовлення типом `decimal`. Вираз `o.Id == payload.OrderNumber` компілюється, бо C# непомітно розширює `long` до `decimal`, а EF Core точно відображає це розширення, додаючи приведення типу до *стовпця*. Первинний індекс за `bigint` не може виконати порівняння з `numeric`, тому пошук за ключем перетворюється на читання всіх 49 443 сторінок таблиці `orders`.

Під час кожного виклику, навіть після прогрівання, більшість цих сторінок — `read`, а не `hit`. Для таблиці розміром понад чверть `shared_buffers` PostgreSQL використовує мале кільцеве сховище буферів під час послідовного сканування, тому великий послідовний прохід не витісняє все інше з кешу. Розмір `orders` — 386 МБ за 512 МБ спільних буферів; таблиця `customers` у кроці 3 має 107 МБ і залишилася в кеші.

Перетворюйте тип і перевіряйте значення на боці .NET:

```csharp
if (payload.OrderNumber != decimal.Truncate(payload.OrderNumber)
    || payload.OrderNumber < 1 || payload.OrderNumber > long.MaxValue)
    return null;
var orderId = (long)payload.OrderNumber;
```

Результат — `Index Scan using orders_pkey`, 4 буфери й 1,6 мс замість медіани 488,2 мс. Індекс не знадобився: вже наявний індекс знову можна використовувати. Версія цієї помилки для SQL Server — скрипт 1 у треку SQL Server.
</details>

<summary>Крок 5 — показники продажів товару</summary>

  Heap Blocks: exact=16993
  ->  Bitmap Index Scan on ix_order_lines_product_id  (actual ... rows=18015.00 loops=1)

Індекс знаходить 18 015 рядків товару за 18 буферів. Але `quantity` і `unit_price` лежать у таблиці, а рядки розкидані по ній — 16 993 різні сторінки для 18 015 рядків. Відповідь коштує 17 011 буферів.

Результат — `Index Only Scan`, `Heap Fetches: 0`, 98 буферів і 5,8 мс. Стовпці `INCLUDE` зберігаються лише на листках дерева. За ними не можна шукати чи сортувати, але вони й не збільшують верхні рівні дерева.

Тепер оцініть вартість. Побудова зайняла 12,9 с, розмір — **697 МБ**; індекс `product_id`, який він замінює, має 120 МБ. Цей індекс малий завдяки дедуплікації B-tree, доступній у PostgreSQL починаючи з версії 13: повторний ключ зберігається один раз зі списком вказівників на рядки, тож 18 мільйонів записів для 50 000 товарів добре стискаються. Індекс із стовпцями `INCLUDE` дедуплікувати не можна. Оцінюйте це рішення з огляду на конкретні числа.

Розділ *Зламайте це* показує іншу вартість: сканування лише індексу добре працює лише тоді, коли актуальна карта видимості.

<summary>Крок 6 — замовлення клієнта за цей рік</summary>

```
Index Scan Backward using ix_orders_created_at_customer_id on orders o  (actual ... rows=3.00 loops=1)
  Index Cond: ((created_at >= '2025-09-01 ...') AND (customer_id = '33'::bigint))
  Buffers: shared hit=6386
```

Обидва стовпці є в `Index Cond`, тож здається, що індекс використано добре. Насправді це не так. Спершу індекс упорядковано за `created_at`. Діапазон можна звузити лише провідним стовпцем, тож сканування проходить усі замовлення за останній рік і перевіряє `customer_id` для кожного: 6 386 із 19 228 сторінок індексу — третину — щоб знайти 3 рядки.

`Index Searches: 1` показує, що сканування з пропуском у PostgreSQL 18 теж не допомогло. Воно ефективне, коли провідний стовпець має мало різних значень, а в `created_at` їх мільйони.

Поставте стовпець рівності першим, а стовпець діапазону — другим:

```sql
CREATE INDEX lab_orders_customer_id_created_at ON orders (customer_id, created_at);
```

Результат — 6 буферів і 1,5 мс. Правило: **спершу стовпці рівності, потім стовпець діапазону або сортування**. Цей самий індекс також повертає замовлення клієнта вже відсортованими за датою. Його побудова коштувала 2,2 с і 150 МБ; перевірте, чи старий індекс усе ще потрібен для іншого запиту, перш ніж залишити обидва.
</details>

<summary>Крок 7 — список замовлень для адміністратора, сторінка 4 001</summary>

```
Limit  (actual ... rows=50.00 loops=1)
  ->  Incremental Sort  (actual ... rows=200050.00 loops=1)
        ->  Index Scan Backward using ix_orders_created_at_customer_id ...  (actual ... rows=200051.00 loops=1)
```

`OFFSET 200000` змушує сервер створити 200 050 рядків і відкинути всі, крім останніх 50. Витрати лінійно зростають із номером сторінки; сторінка 4 001 коштує 2 791 буфер.

Запит уже містить останній рядок попередньої сторінки, тому почніть після нього. Це пагінація за ключем. У PostgreSQL її слід записати як порівняння кортежів, яке провайдер Npgsql перетворює з `ValueTuple`:

```csharp
.Where(o => EF.Functions.LessThan(
    ValueTuple.Create(o.CreatedAt, o.Id),
    ValueTuple.Create(after.CreatedAt, after.Id)))
.OrderByDescending(o => o.CreatedAt).ThenByDescending(o => o.Id)
.Take(page.PageSize)
```

```
Index Scan Backward using ix_orders_created_at_customer_id on orders o  (actual ... rows=51.00 loops=1)
  Index Cond: (created_at <= '2026-07-19 03:50:41.811925+00'::timestamp with time zone)
  Filter: (ROW(created_at, id) < ROW('2026-07-19 03:50:41.811925+00'::timestamp with time zone, '4800001'::bigint))
  Rows Removed by Filter: 1
```

Результат — 5 буферів і 1,7 мс. Планувальник отримав межу індексу `created_at <=` із порівняння кортежів. Форма з OR із розділу *Зламайте це* повертає ті самі рядки, але PostgreSQL сприймає її лише як `Filter`, тому сканування й далі проходить і відкидає 200 000 рядків перед сторінкою (`Rows Removed by Filter: 200000`).

З індексом за `(created_at, id)` усе порівняння стає `Index Cond`, а `Incremental Sort` зникає, бо індекс уже повертає рядки в порядку `ORDER BY`. Тут він читає стільки само буферів; виграш — сортування, яке більше не виконується.

Ці витрати стосуються продукту, а не бази даних:

- більше немає переходу «до сторінки 4 001» — доступні лише наступна й попередня;
- сортування потребує унікального критерію для розв’язання рівності (`id`);
- курсор потрібно передавати разом із запитом.

[Розділ 18](#chapter-18-data-in-depth) так само пояснює цю думку для необмежених списків.
</details>

<summary>Крок 8 — пошук клієнта</summary>

```sql
WHERE c.email ILIKE @p ESCAPE ''      -- @p = '%tomasz.kowalski%'
```

```
Parallel Seq Scan on customers c  (actual ... rows=83.00 loops=3)
  Filter: (email ~~* '%tomasz.kowalski%'::text)
  Rows Removed by Filter: 333250
```

B-tree обслуговує шаблон `'prefix%'`, але не той, що починається зі знака підстановки. Три процеси прочитали по третині таблиці (`loops=3`, кожен відкинув 333 250 рядків): 13 735 буферів.

Такий запит обслуговує триграмний індекс:

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX lab_customers_email_trgm ON customers USING gin (email gin_trgm_ops);
```

`pg_trgm` індексує кожну трисимвольну частину тексту, а триграми самого шаблону звужують коло кандидатів ще до читання рядків. Результат — `Bitmap Index Scan on lab_customers_email_trgm`, 439 буферів і 9,0 мс. Побудова зайняла 4,6 с, розмір — 52 МБ. Індекси GIN повільніше оновлювати, ніж B-tree, а пошуковий термін коротший за три символи не має триграми для звуження пошуку, тому задайте мінімальну довжину запиту.

> **Нюанс.** Подивіться на `ESCAPE ''` у SQL стартового коду. Провайдер Npgsql EF Core (тут версія 10.0.3) додає його, якщо викликати `EF.Functions.ILike(match, pattern)` без символу екранування — тобто символу екранування *немає взагалі*. Тоді `_`, введене в поле пошуку, відповідає будь-якому символу (а підкреслення часто трапляється в адресах електронної пошти), і користувач не може вказати його буквально. Рішення передає зворотну скісну риску як символ екранування й екранує введений текст:
>
> ```csharp
> var pattern = "%" + EscapeLike(term) + "%";
> .Where(c => EF.Functions.ILike(c.Email, pattern, @"\"))
>
> static string EscapeLike(string s) =>
>     s.Replace(@"\", @"\\").Replace("%", @"\%").Replace("_", @"\_");
> ```

<details>
<summary>Крок 9 — останні продажі товару</summary>

Застосунок повторює оператор так, як його справді виконував сервер: як підготовлений оператор після такого самого прогрівання. `pg_prepared_statements` показує **3 загальні й 5 спеціальних планів** на цей момент:

```
Limit  (actual ... rows=20.00 loops=1)
  Buffers: shared read=151331
  ->  Sort  (actual ... rows=20.00 loops=1)
        Sort Key: id DESC
        Sort Method: top-N heapsort  Memory: 27kB
        ->  Index Scan using ix_order_lines_product_id on order_lines o  (cost=0.44..518.89 rows=463 width=26) (actual ... rows=1441651.00 loops=1)
              Index Cond: (product_id = $1)
```

`$1` в `Index Cond` означає загальний план: його побудовано без знання конкретного значення. Ось як сервер до нього дійшов:

1. **Автоматична підготовка.** Сервіс задає `Max Auto Prepare=20`; типове значення 0 вимикає функцію. Після п’яти виконань оператора (`Auto Prepare Min Usages`) Npgsql готує його на сервері.
2. **Кеш планів.** PostgreSQL створює для підготовленого оператора п’ять спеціальних планів, потім порівнює очікувану вартість загального плану із середньою вартістю попередніх. Популярні товари під час прогрівання зробили спеціальні плани дорогими, тож переміг загальний план.
3. **Загальна оцінка.** Загальний план розраховано для *середнього* товару: 463 рядки, тож він отримує їх усі й сортує. Для більшості товарів це правильно. Бестселер має 1 441 651 рядок. Сканування торкається 151 331 сторінки — майже всієї таблиці з 150 272 сторінок. Вони не залишаються в кеші, тому кожен виклик читає їх знову: 1 014,2 мс на сервері.

Рішення усуває цей вибір:

```sql
CREATE INDEX lab_order_lines_product_id_id ON order_lines (product_id, id);
```

З цим індексом один план підходить для кожного товару: він проходить записи товару у зворотному порядку й зупиняється після 20 рядків. `Index Scan Backward using lab_order_lines_product_id_id`, 7 буферів, 1,5 мс. Повторне виконання показує 0 загальних і 8 спеціальних планів: спеціальні тепер настільки дешеві, що загальний не перемагає. Ціна — 11,0 с побудови й 542 МБ на диску проти 120 МБ для старого індексу. `(product_id, id)` унікальний для кожного рядка, тож дедуплікувати нічого.

Альтернативи й їхню вартість наведено у відповідях до рівня 3.

<summary>Рівень 3 — погляд із боку сервера, auto_explain і компроміс кроку 9</summary>

**1. N+1 у `pg_stat_statements`** після п’яти викликів стартового кроку 1:

```
 calls | rows | total_ms | buffers | query
-------+------+----------+---------+-------------------------------------------
   250 | 5910 |     9.11 |    1050 | SELECT o.product_id, o.quantity, o.unit_price FROM order_lines ...
     5 |  250 |     1.67 |     405 | SELECT o.id, o.created_at, o.currency, o.customer_id, ...
```

Ознака — два оператори, у яких кількість викликів відрізняється рівно на розмір сторінки (250 ÷ 5 = 50). Кожен оператор швидкий, жоден окремий план не виглядає неправильним. Загалом сервер витрачає менш як 11 мс на всі п’ять сторінок; у контрольному запуску одна сторінка медіанно займала 78,0 мс із боку клієнта. Ця різниця — цикли обміну. У продакшені сортуйте `pg_stat_statements` і за `calls`, і за `total_exec_time`. У розділі [Як знаходити запити, на які варто звернути увагу](#finding-the-queries-worth-looking-at) пояснено, чому запит із найбільшими сумарними витратами рідко є найповільнішим.

**2. `auto_explain`** записував у журнал кожне виконання тривалістю понад секунду. У контрольному запуску таких виконань шість: повільні виміряні виклики й повторні виклики застосунку. Кожне має такий вигляд:

```
LOG:  duration: 1085.995 ms  plan:
  Query Text: SELECT o.id, o.order_id, o.quantity, o.unit_price FROM order_lines AS o
              WHERE o.product_id = $1 ORDER BY o.id DESC LIMIT $2
  Query Parameters: $1 = '1', $2 = '20'
  Limit  (cost=539.39..539.51 rows=46 width=26)
    ->  Sort  (cost=539.39..540.55 rows=463 width=26)
          ->  Index Scan using ix_order_lines_product_id on order_lines o  (... rows=463 ...)
                Index Cond: (product_id = $1)
```

Дві ознаки доводять, що це загальний план: `$1` в `Index Cond`, хоча в журналі також записане значення `'1'`, і оцінка 463 рядки для товару з 1,44 млн. У лабораторній `auto_explain.log_analyze` не ввімкнено. Документація попереджає: інструмент вимірює *кожен* оператор, а не лише повільні, а `auto_explain.log_timing = off` зменшує витрати.

**3. `force_custom_plan` через connection string.** Стартовий крок 9 виконується без змін і без нового індексу:

| | Виправлення: індекс `(product_id, id)` | Виправлення: `plan_cache_mode = force_custom_plan` |
|---|---|---|
| Бестселер | 7 буферів, 1,5 мс | 7 буферів, 1,9 мс |
| Плани | 0 загальних, 8 спеціальних | 0 загальних, 8 спеціальних |
| План | проходить новий індекс у зворотному напрямку | проходить *первинний ключ* у зворотному напрямку й фільтрує за `product_id` (відкинуто 225 рядків) |
| Вартість | 11,0 с побудови, 542 МБ, ще один індекс для підтримки під час кожного вставлення | планування кожного виконання (тут 0,114 мс) кожного оператора на цих підключеннях |
| Від чого залежить | ні від чого | від правильності спеціального плану планувальника для кожного значення |

Спеціальне планування працює тут, бо бестселер рівномірно розподілений у таблиці, тож зворотний прохід первинним ключем знаходить 20 його рядків за 245 записів. Планувальник ухвалює рішення для кожного значення окремо, тому все залежить від точності статистики.

Інші варіанти:

- задавати `plan_cache_mode` для ролі чи бази даних, а не в connection string;
- вимкнути автоматичну підготовку, втративши всюди її економію на плануванні, щоб виправити один оператор;
- використовувати `EXPLAIN (GENERIC_PLAN)`, доступний починаючи з PostgreSQL 16, щоб переглянути загальний план без прогрівання під час перевірки коду.

Для відомого перекосу й запиту під вашим контролем надійне виправлення — індекс. `force_custom_plan` — тимчасовий засіб, який можна розгорнути за кілька хвилин без міграції.

<details>
<summary>«Зламайте це» — відповіді</summary>

**Застаріла статистика.** Клієнт 900,001 відсутній у списку найчастіших значень. Для такого значення планувальник рівномірно розподіляє між рештою різних значень частку рядків, не охоплену списком: (1 − 0.0975) ÷ (210,578 − 11) × 5,000,396 ≈ 21.4 рядка. Він також масштабує кількість рядків відповідно до поточного розміру таблиці, який зріс через завантаження на 6%, тому оцінка стає 23.

Коли очікується 23 рядки, «отримати їх усі через `customer_id` і відсортувати» здається недорогим. Коли очікується 306 526, це явно не так, і зворотний прохід індексом за датою майже відразу знаходить 50 збігів. Два висновки:

- **явно запускайте `ANALYZE` після пакетного завантаження.** Поріг autovacuum становить частку таблиці (за замовчуванням 20% рядків для vacuum і 10% для analyze), а 300 000 рядків — це лише 6% цієї таблиці;
- **звертайте увагу на плани з `LIMIT`.** Особливо підозрілий план, який здається дешевим лише через `LIMIT`, коли оцінка помилкова — див. [Коли план неправильний](#when-the-plan-is-wrong).

**Карта видимості.** Навіть скануванню лише індексу потрібно знати, чи видимий кожен рядок для поточної транзакції. Карта видимості зберігає по одному біту на сторінку таблиці зі значенням «кожен рядок цієї сторінки видимий усім». Будь-яка зміна сторінки скидає біт, навіть якщо зміну згодом скасували. Відновлює його лише `VACUUM`. Після скидання бітів усі 18 015 записів індексу потребували звернення до таблиці (`Heap Fetches: 18015`), і покривний індекс уже нічим не був кращим за звичайний.

Для таблиці, до якої весь час записують, ефективність сканування лише індексу залежить від частоти запуску autovacuum. У продакшені перевіряйте `Heap Fetches` у планах і за потреби налаштовуйте `autovacuum_vacuum_scale_factor` для окремої таблиці.

**Пагінація за ключем, форма з OR.** У її плані є `Filter:`, тоді як у формі з порівнянням кортежів — `Index Cond:`, і вказано `Rows Removed by Filter: 200000`. PostgreSQL не перетворює це OR на межу індексу. Сканування починається з найновішого замовлення й відкидає рядки, доки умова не стане істинною.

Четверта форма переміщує все порівняння рядків до `Index Cond`, а також прибирає `Incremental Sort`. Буферів стільки само (5), бо старий індекс і так майже ідеально підходив до цієї сторінки.

SQL Server обробляє форму з OR (скрипт 4 треку SQL Server). Це справжня відмінність між рушіями, і ще один доказ того, що «на іншій базі було швидко» — не свідчення.
</details>
