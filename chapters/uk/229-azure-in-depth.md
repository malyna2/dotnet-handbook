# Розділ 29: Azure докладно для розробників .NET

[Розділ 28](#chapter-28-cloud-fundamentals-aws-azure) дав вам загальну картину: що таке App Service, Functions, Cosmos DB і Service Bus та як вони співвідносяться зі службами AWS. Цієї карти вистачить для розмови. Але не для першого тижня відповідальності за систему в продакшені на Azure, коли запитання звучать так: *чому застосунок отримує 403 від Blob Storage, якщо його ідентичність має роль Contributor на рівні підписки? Чому перемикання слотів спричинило хвилину відповідей 500? Чому Cosmos DB обмежує пропускну здатність до 3 000 RU/s, якщо ми виділили 20 000?*

У цьому розділі — сама територія. Для кожної служби, з якою розробник .NET працює щотижня, пояснюється **механізм** (що насправді відбувається під час виклику), показано **код .NET**, перелічено **обмеження, що створюють проблеми**, а наприкінці наведено **таблицю рішень**. Цільовий рівень — сильний розробник середнього рівня, здатний створювати, випускати й налагоджувати систему Azure без постійної підтримки команди платформи та пояснювати свій вибір на співбесіді. Далі в [розділі 30](#chapter-30-the-azure-casebook-real-incidents-real-fixes) усе це застосовується до реальних інцидентів.

У кожному розділі повторюється одна ідея: у продакшені ваш код виконується всередині механізмів платформи, які він ніколи не викликає, — фронтенда з тайм-аутом, NAT із лімітом портів, endpoint (кінцевої точки) токенів, зони DNS, планувальника, який масштабує, зупиняє й переміщує його. Більшість інцидентів у хмарі виникає через один із них, що працює саме так, як описано в документації. Практичне завдання наприкінці розділу дає змогу перевірити це на практиці: два підтверджені дефекти з практикуму, два архітектурні рішення й pipeline (конвеєр) deployment (розгортання), у якому відкат — це перемикання слотів.

```
                        how a typical .NET system on Azure is layered
  ┌─────────────────────────────────────────────────────────────────────────────┐
  │ EDGE        Front Door / Application Gateway (WAF)  ·  API Management       │
  ├─────────────────────────────────────────────────────────────────────────────┤
  │ COMPUTE     App Service  ·  Functions  ·  Container Apps  ·  AKS            │
  ├───────────────────────────────┬─────────────────────────────────────────────┤
  │ DATA        Azure SQL         │ MESSAGING   Service Bus  (commands)         │
  │             Cosmos DB         │             Event Hubs   (streams)          │
  │             Blob Storage      │             Event Grid   (notifications)    │
  │             Managed Redis     │                                             │
  ├───────────────────────────────┴─────────────────────────────────────────────┤
  │ CROSS-CUTTING   Entra ID + Managed Identity + RBAC   ·   Key Vault          │
  │                 App Configuration  ·  Azure Monitor / Application Insights  │
  │                 VNet + Private Endpoints + Private DNS   ·   Bicep / azd    │
  └─────────────────────────────────────────────────────────────────────────────┘
        the cross-cutting row is where most production incidents actually live
```

Уважно прочитайте рядок наскрізних компонентів. Спершу більшість розробників вивчає служби середніх рівнів. На практиці збої, які годинами налагоджують, виникають у нижньому рядку: ідентичності, мережі, конфігурації й відсутності телеметрії.

## Площина керування: як організовано Azure

Кожен ресурс Azure розташований у чотирирівневій ієрархії в межах одного клієнта Microsoft Entra:

```
  Microsoft Entra tenant  (the identity boundary: users, groups, apps, managed identities)
   └── Management groups  (optional, nestable: policy + RBAC for many subscriptions at once)
        └── Subscription   (the billing and quota boundary; one trust relationship with a tenant)
             └── Resource group   (a lifecycle boundary: things that are deployed and deleted together)
                  └── Resources   (a storage account, a web app, a Service Bus namespace …)

  RBAC role assignments and Azure Policy assignments made at any level are INHERITED downward.
```

У реальній роботі знов і знов трапляються три наслідки:

- **Група ресурсів — межа життєвого циклу, а не мережі чи регіону.** Розміщуйте в одній групі ресурси, що створюються й видаляються разом (застосунок, його план, Application Insights і Key Vault), щоб знищення середовища зводилося до `az group delete`. Ресурси однієї групи можуть розташовуватися в різних регіонах; розташування самої групи вказує лише на місце зберігання її метаданих.
- **Одиниця тарифікації й квот — підписка.** Багато обмежень встановлено для підписки в кожному регіоні (наприклад, квоти vCPU). Команди часто використовують по одній підписці на середовище (dev, test, prod), що забезпечує чітку ізоляцію й окремий рахунок для кожного.
- **Дозволи успадковуються вниз.** Той, хто має роль *Contributor* на рівні підписки, має її для кожної групи ресурсів і кожного ресурсу в ній. Саме тому старший інженер заперечить проти запиту «просто надайте мені Contributor для підписки».

### ARM: один API для всіх інструментів

Портал, Azure CLI, PowerShell, Bicep, Terraform і SDK керування зрештою надсилають HTTPS-запити до одного endpoint — **Azure Resource Manager** (`management.azure.com`). ARM автентифікує вас через Entra ID, перевіряє RBAC і політики та пересилає запит постачальнику ресурсу (`Microsoft.Storage`, `Microsoft.Web` тощо). Тому все, на що можна натиснути в порталі, можна також запускати сценарієм, а засоби IaC можуть виявляти відхилення.

Звідси випливає найкорисніше розрізнення в Azure й причина багатьох інцидентів із запитанням «чому отримую 403?»:

| | **Площина керування** | **Площина даних** |
|---|---|---|
| Призначення | Керує *ресурсом*: створює обліковий запис сховища, змінює його SKU, перелічує ключі, додає queue (чергу) | Використовує *ресурс*: читає blob, надсилає повідомлення, читає секрет, запитує контейнер |
| Endpoint | `management.azure.com` (ARM) | Власний endpoint служби: `<account>.blob.core.windows.net`, `<ns>.servicebus.windows.net`, `<vault>.vault.azure.net` |
| Ролі RBAC | *Owner*, *Contributor*, *Reader* і спеціалізовані ролі керування службами | Ролі з `DataActions`: *Storage Blob Data Contributor*, *Azure Service Bus Data Receiver*, *Key Vault Secrets User* тощо |

Роль *Contributor* для облікового запису сховища дозволяє його видалити, але не дає прочитати жодного blob за токеном Entra, бо Contributor не має дій із даними. До даних усе ж можна дістатися *опосередковано*: Contributor може отримати ключі облікового запису, а ключ відкриває доступ до всього. Це одна з причин вимкнути доступ за спільним ключем (див. розділ *Ідентичність*).

### Керування: RBAC, політики, блокування й теги

Ці чотири інструменти часто плутають, бо кожен із них може заборонити дію. Але відповідають вони на різні запитання:

| Інструмент | На яке запитання відповідає | Приклад |
|---|---|---|
| **RBAC** | *Хто* може виконати *яку дію* в *якій області*? | Managed identity (керована ідентичність) застосунку може читати секрети лише в цьому сховищі. |
| **Azure Policy** | *Які* конфігурації дозволені незалежно від того, хто їх створює? | Для облікових записів сховища потрібно вимкнути публічний мережевий доступ; ресурси можна створювати лише в Західній і Північній Європі; кожна група ресурсів має мати тег `costCenter`. |
| **Блокування ресурсу** | Чи потрібно захистити ресурс від видалення або змін, навіть власником? | `CanNotDelete` для виробничого сервера SQL. |
| **Теги** | Що це за ресурс, хто ним володіє і хто за нього платить? | `env=prod`, `owner=payments-team`, `costCenter=4711`. |

Політики мають *ефекти*: `Deny` блокує запит, `Audit` лише повідомляє про порушення, `Modify` змінює ресурс (наприклад, додає пропущений тег), а `DeployIfNotExists` розгортає додатковий ресурс (наприклад, параметри діагностики). Розробник зазвичай зустрічає політику як невдалий deployment з помилкою `RequestDisallowedByPolicy`. Помилка називає призначену політику — саме з цієї назви й варто почати розслідування.

> **Нюанс.** Блокування захищають **ресурс**, а не **дані** в ньому. У документації Microsoft прямо сказано: блокування лише читання чи заборони видалення облікового запису сховища не перешкоджає видаленню або зміні blob, queues чи таблиць. Блокування лише читання також має несподіваний побічний ефект: воно блокує *List Keys* — запит `POST` у площині керування, — тому інструменти з автентифікацією за ключем облікового запису припиняють працювати.

### Регіони, зони доступності й SLA

**Регіон** — це набір центрів обробки даних в одному географічному регіоні. У більшості регіонів є три **зони доступності**: фізично відокремлені центри обробки даних із незалежними системами живлення, охолодження й мережі. Багато регіонів також мають пару в іншому регіоні тієї самої географічної області. Ця пара має значення для георезервованого сховища й послідовності випуску Microsoft оновлень платформи.

Щодо зон служби належать до трьох типів. **Зонально-надлишкові** ресурси Azure самостійно розподіляє між зонами (зонально-надлишкове сховище, плани App Service, Azure SQL із резервуванням зон). **Зональні** ресурси прив'язані до обраної вами зони (віртуальна машина, диск). **Ресурси без зони** не мають гарантій щодо зон. Архітектура переживе збій зони лише тоді, коли кожен компонент на шляху запиту є зонально-надлишковим або ви самі продублювали його в різних зонах.

**Складені SLA перемножуються, і це часто дивує.** Якщо запит спочатку проходить через App Service (99,95%), а потім Azure SQL (99,99%), і потрібні *обидві* служби, доступність шляху не перевищить:

```
0.9995 × 0.9999 = 0.9994   → 99.94%  (about 26 minutes of downtime in a 30-day month, against 22 for App Service alone)
```

Кожен компонент, доданий *послідовно*, знижує цей показник. Компоненти *паралельно* (два регіони за Front Door, де кожного достатньо окремо) його підвищують: два незалежні шляхи з доступністю 99,94% дають на папері `1 − (0.0006 × 0.0006) ≈ 99.99996%`. Це число справджується лише за успішного перемикання й справді незалежних шляхів. Саме тому в [розділі 20](#chapter-20-distributed-systems) надійність розглядається як те, що потрібно тестувати, а не просто обчислювати. Самі відсотки SLA змінюються — перевіряйте актуальну сторінку SLA кожної служби.

### Моделі ціноутворення: рівень для іспиту й перевірки коду

| Модель | Що це | Коли підходить |
|---|---|---|
| Оплата за використання | За секунду, годину чи операцію, без зобов'язань | Розробка/тестування, пікове або невідоме навантаження |
| Резервування | Зобов'язання на 1 або 3 роки для певного типу ресурсів (віртуальні машини, vCore SQL, RU/s Cosmos тощо) в обмін на значну знижку | Стабільна базова потужність продакшену |
| План заощадження для обчислень | Зобов'язання на погодинні витрати обчислень, що діють для різних розмірів віртуальних машин і регіонів | Стабільні витрати за змінних конфігурацій |
| Spot | Резервна потужність із великою знижкою, яку можуть раптово відібрати | Переривана пакетна обробка; ніколи — для обслуговування запитів |
| Azure Hybrid Benefit | Повторне використання наявних ліцензій Windows Server або SQL Server | Міграція з локальної інфраструктури без зміни архітектури |

**Бюджети сповіщають, але не зупиняють витрати.** Бюджет у Cost Management надсилає листа або запускає групу дій, коли фактичні чи прогнозовані витрати перевищують поріг. Він нічого не вимикає, якщо не під'єднати до нього автоматизацію. У [розділі 31](#chapter-31-compliance-data-privacy-cloud-cost-finops) докладно розглянуто FinOps. У розділі *Витрати* наприкінці цього розділу перелічено конкретні рішення розробників, що впливають на рахунок.

## Ідентичність: Entra ID, managed identity і RBAC на практиці

[Розділ 28](#chapter-28-cloud-fundamentals-aws-azure) показав основний шаблон: managed identity і `DefaultAzureCredential`, без секретів у коді. Тут пояснюється, що відбувається за цим одним рядком, адже в разі помилки її причини зрозумілі лише тоді, коли ви знаєте механізм.

### Об'єкти: реєстрація застосунку, суб'єкт-служба, managed identity

- **Реєстрація застосунку** — *глобальне визначення* програми в домашньому клієнті: її client ID, URI перенаправлення, запитані дозволи API, відкриті ролі застосунку й credentials (облікові дані) (секрети, сертифікати, федеративні облікові дані).
- **Суб'єкт-служба** (у порталі показується як *корпоративний застосунок*) — *екземпляр* програми в конкретному клієнті. Призначення ролей і згода прив'язуються до суб'єкта-служби, а не до реєстрації.
- **Managed identity** — суб'єкт-служба, credentials якого Azure створює, зберігає й оновлює самостійно. Код їх ніколи не бачить. Є два типи:

| | Призначена системі | Призначена користувачу |
|---|---|---|
| Життєвий цикл | Створюється разом із ресурсом, видаляється разом із ним | Окремий ресурс, який створюєте й видаляєте ви |
| Спільне використання | Лише для одного ресурсу | Для будь-якої кількості ресурсів |
| Призначення ролей | Лише після створення ресурсу | Можливе **до deployment застосунку**, у тому самому запуску IaC |
| Типове використання | Прості застосунки з одним ресурсом | Багато екземплярів чи слотів з однаковим доступом; blue/green; уникнення затримки поширення під час deployment |

Для всього, що часто розгортається, кращим типовим вибором є призначена користувачу ідентичність. За системної ідентичності кожен новостворений ресурс отримує нового суб'єкта, а призначеним ролям може знадобитися кілька хвилин, щоб набути чинності (див. нижче). Тому перші хвилини роботи нового середовища завершуються помилками 403. Ідентичність, призначена користувачу, уже існує, як і її ролі.

### Як насправді надходить токен

На хості Azure ваш код не спілкується з Entra ID напряму. Платформа надає **локальний endpoint токенів**. На віртуальних машинах це служба метаданих екземпляра за немаршрутизованою адресою `169.254.169.254`. В App Service і Functions це локальний endpoint, адресу й секретний заголовок якого платформа передає як environment variables (змінні середовища) `IDENTITY_ENDPOINT` і `IDENTITY_HEADER`. SDK Azure викликає цей endpoint через `ManagedIdentityCredential`, запитує токен для **ресурсу** (аудиторії, наприклад `https://storage.azure.com/`) і кешує його до наближення строку завершення дії.

Токен — це JWT. Під час налагодження перевірте такі твердження:

| Твердження | Значення | Типовий несподіваний випадок |
|---|---|---|
| `aud` | Для якого API призначено токен | Токен для `https://management.azure.com/` не працює для `vault.azure.net`. |
| `oid` | Ідентифікатор об'єкта суб'єкта (для managed identity — суб'єкта-служби) | Ролі потрібно призначати цьому ID, а не ID об'єкта реєстрації застосунку. |
| `roles` | Ролі застосунку, призначені програмі (потік credentials клієнта) | Порожнє значення означає, що роль призначили не тому суб'єкту або немає згоди адміністратора. |
| `scp` | Делеговані області доступу (лише для входу *користувача*) | Є в токенах користувача, відсутнє в токенах лише для застосунку. API має перевіряти правильне значення. |

Декодуйте токен локально за допомогою надійного інструмента чи кількох рядків коду, а не вставляйте робочі токени на вебсайт.

### `DefaultAzureCredential`: як насправді працює ланцюжок

`DefaultAzureCredential` перевіряє перелік credentials у заданому порядку й використовує перші, що повернули токен. У поточній версії `Azure.Identity` (1.21; типи credentials постачаються в `Azure.Core`) порядок такий:

```
  EnvironmentCredential          AZURE_CLIENT_ID / AZURE_TENANT_ID / AZURE_CLIENT_SECRET (or certificate)
  WorkloadIdentityCredential     AKS workload identity (federated token file)
  ManagedIdentityCredential      the platform's token endpoint (App Service, Functions, VMs, Container Apps …)
  VisualStudioCredential         developer tools, only useful on your machine
  VisualStudioCodeCredential
  AzureCliCredential             `az login`
  AzurePowerShellCredential
  AzureDeveloperCliCredential    `azd auth login`
  (BrokerCredential, when the Azure.Identity.Broker package is referenced)
  InteractiveBrowserCredential   excluded unless you opt in
```

У документації SDK сказано, що в продакшені краще використовувати інший тип. Причин три:

1. **Неправильна ідентичність без повідомлення.** Якщо після старого експерименту в налаштуваннях застосунку залишилися `AZURE_CLIENT_ID` і `AZURE_CLIENT_SECRET`, перемагає `EnvironmentCredential`, тож застосунок працює від імені забутого суб'єкта-служби, а не managed identity.
2. **Повільна помилка.** Якщо на хості не налаштовано managed identity, ланцюжок переходить до credentials розробника й послідовно чекає, поки кожен варіант завершиться помилкою. Це спричиняє повільний перший запит і незрозуміле об'єднане повідомлення про помилки.
3. **Для ідентичностей користувачів потрібен ID.** Якщо є кілька таких ідентичностей або одна, але немає системної, потрібно вказати, *яку саме* використовувати: `ManagedIdentityClientId` у параметрах або environment variable `AZURE_CLIENT_ID`.

Вирішення: у продакшені задавайте ідентичність явно, а в розробці зберігайте зручність. Новіші версії `Azure.Identity` підтримують environment variable `AZURE_TOKEN_CREDENTIALS`: значення `prod` залишає лише credentials розгорнутих служб (середовище, ідентичність workload (робочого навантаження), managed identity), `dev` — лише інструменти розробника, а назва окремого облікового запису, наприклад `ManagedIdentityCredential`, — лише його. Коли вказано `ManagedIdentityCredential`, він також пропускає початковий пробний запит і натомість повторює спробу з експоненційною затримкою.

```csharp
using Azure.Core;
using Azure.Identity;
using Microsoft.Extensions.Azure;

var builder = WebApplication.CreateBuilder(args);

// One credential for the whole app. In Azure: exactly the user-assigned managed identity we
// deployed. On a laptop: whoever ran `az login` / signed in to Visual Studio.
TokenCredential credential = builder.Environment.IsDevelopment()
    ? new DefaultAzureCredential()
    : new ManagedIdentityCredential(
        ManagedIdentityId.FromUserAssignedClientId(builder.Configuration["Identity:ClientId"]!));

// Azure SDK clients are thread-safe and meant to be singletons. AddAzureClients registers them
// once, wires their logging into ILogger, and shares the credential.
builder.Services.AddAzureClients(clients =>
{
    clients.AddBlobServiceClient(new Uri(builder.Configuration["Storage:BlobEndpoint"]!));
    clients.AddServiceBusClientWithNamespace(builder.Configuration["ServiceBus:Namespace"]!);
    clients.AddSecretClient(new Uri(builder.Configuration["KeyVault:Uri"]!));
    clients.UseCredential(credential);
});
```

> **Пастка.** Створювати `new DefaultAzureCredential()` або `new BlobServiceClient(...)` для кожного запиту. Кожен екземпляр credentials має власний кеш токенів, тож на кожен запит припадатиме новий запит токена. Під навантаженням це призводить до rate limiting (обмеження частоти) запитів endpoint ідентичності й затримки кожного виклику. Credentials й клієнти мають бути одиничними екземплярами.

### RBAC докладно

**Призначення ролі** має три частини: *хто* (суб'єкт безпеки: користувач, група, суб'єкт-служба чи managed identity), *що* (визначення ролі: перелік `Actions`, `NotActions`, `DataActions` і `NotDataActions`) і *де* (область: група керування, підписка, група ресурсів або окремий ресурс; у деяких служб — підресурс, як-от один контейнер blob). Доступ — це об'єднання всіх призначень, що діють у цій області або на вищому рівні. В Azure є також *призначення заборон*, але створити їх напряму не можна: вони з'являються через функції на кшталт стеків deployment й керованих застосунків.

Мінімальні привілеї для типового API на практиці виглядають так:

| Що потрібно застосунку | Призначте роль | Область |
|---|---|---|
| читати й записувати blob в одному контейнері | Storage Blob Data Contributor | цей контейнер (`…/blobServices/default/containers/uploads`) |
| отримувати повідомлення з одного queue | Azure Service Bus Data Receiver | цей queue |
| надсилати повідомлення в одну тему | Azure Service Bus Data Sender | ця тема |
| читати секрети | Key Vault Secrets User | це сховище (або окремий секрет) |
| отримувати образи | AcrPull | цей реєстр |

**Зміни призначення ролей застосовуються із затримкою.** У посібнику Microsoft з усунення несправностей зазначено, що набуття чинності може тривати до 10 хвилин. Уже видані токени також зберігають вміст до завершення строку дії. Тож «я щойно призначив роль, а бачу 403» часто є очікуваною поведінкою, а не помилковою конфігурацією. Зачекайте або перезапустіть застосунок, щоб отримати новий токен, перш ніж змінювати налаштування.

**Запам'ятайте exception (виняток) — Cosmos DB.** RBAC площини даних для API NoSQL використовує *власні* визначення й призначення ролей Cosmos DB (їх створюють командою `az cosmosdb sql role assignment create`), а не призначення ролей Azure RBAC. Призначення ролі *Contributor* на вкладці IAM порталу не дає ідентичності доступу до елементів.

### Вимкніть ключі, коли ідентичність уже працює

Більшість служб даних приймає токени Entra або спільний секрет (ключ облікового запису сховища, ключ SAS для Service Bus чи Event Hubs, первинний ключ Cosmos DB). Спільний секрет повністю обходить RBAC: його власник може робити будь-що, а дії не пов'язано з конкретною людиною. Коли застосунки вже використовують managed identity, **вимкніть локальну автентифікацію**: `allowSharedKeyAccess: false` для облікових записів сховища й `disableLocalAuth: true` для Service Bus, Event Hubs і Cosmos DB. Політика Azure з ефектом `Deny` не дозволить знову її ввімкнути. У [розділі 12](#chapter-12-security-essentials) пояснюється, чому секрет, якого у вас немає, — єдиний секрет, який ви не можете розкрити.

### Захист власного API

Ваш API теж є ресурсом, для виклику якого потрібні токени. За допомогою `Microsoft.Identity.Web` перевірка токенів Entra займає один рядок:

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.Identity.Web;

builder.Services.AddAuthentication()
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));   // TenantId, ClientId (the API's app registration), Audience

builder.Services.AddAuthorization(options =>
{
    // Service-to-service callers get an *app role* (the "roles" claim), granted by an admin.
    options.AddPolicy("OrdersWriter", p => p.RequireRole("Orders.Write"));
});

app.MapPost("/orders", [Authorize(Policy = "OrdersWriter")] (CreateOrder cmd) => Results.Accepted());
```

Ось потоки автентифікації, які варто знати за назвою:

| Потік | Хто викликає | Що містить токен |
|---|---|---|
| **Credentials клієнта** | Служба від власного імені: демон, функція або інший API з managed identity | `roles` (ролі застосунку), без користувача |
| **Код авторизації + PKCE** | Користувач через вебклієнт або SPA | `scp` (делеговані області доступу) + користувач |
| **Від імені користувача (OBO)** | Ваш API викликає іншу службу *як користувач, що увійшов* | Новий токен для нижчого API з тією самою ідентичністю користувача |

Managed identity також може використовувати потік credentials клієнта для *вашого* API: викликач запитує токен з аудиторією `api://<your-api-client-id>/.default`, а адміністратор призначає роль застосунку вашого API managed identity викликача.

### Федерація ідентичності workload: жодних секретів у CI

Останній довгостроковий секрет у більшості команд — credentials, які CI використовує для deployment. **Федерація ідентичності workload** усуває їх. Додайте до реєстрації застосунку або ідентичності, призначеної користувачу, *федеративні credentials* з правилом: «довіряти токенам від `token.actions.githubusercontent.com` для репозиторію `org/repo` у середовищі `production`». Завдання GitHub Actions запитує токен OIDC у GitHub, обмінює його через Entra ID і отримує токен Azure. Ніде не зберігається секрет. Це робить дія `azure/login`, якщо передати їй `client-id`, `tenant-id` і `subscription-id` та надати робочому процесу `id-token: write`. У [розділі 13](#chapter-13-git-and-cicd) описано pipeline, а в [розділі 27](#chapter-27-security-in-depth-and-the-supply-chain) — чому викрадення credentials CI є однією з найнебезпечніших атак на ланцюг постачання.

## Обчислення: що обрати й як запускати

Спершу визначте потребу, потім вивчіть подробиці відповідного варіанта:

| У вас… | Обирайте | Тому що… |
|---|---|---|
| Стандартний вебзастосунок ASP.NET Core або API, стабільний трафік, команда без навичок Kubernetes | **App Service** | Найменше операційної роботи; слоти, автоматичне масштабування, автентифікація й TLS уже вбудовані |
| Робота на events (повідомлення черги, завантаження blob, таймер), пікове або рідкісне навантаження | **Azure Functions** (Flex Consumption) | Масштабування на кожен event аж до нуля; прив'язки усувають шаблонний код |
| Кілька контейнеризованих служб, масштабування за events й до нуля, без бажання керувати Kubernetes | **Container Apps** | У їхній основі Kubernetes і KEDA, але без операцій із кластером |
| Команда платформи, багато служб, власна мережа чи оператори, сильні навички Kubernetes | **AKS** | Повний контроль Kubernetes і повна відповідальність за Kubernetes |
| Залежність від рівня ОС, застаріла служба Windows, ліцензія прив'язана до машини | **Virtual Machines** | IaaS: максимальний контроль і максимальна робота з виправленнями |

### App Service

**План — це машина.** *План App Service* — це набір екземплярів віртуальних машин одного розміру (SKU: B1, S1, P1v3 тощо). Кожен застосунок плану працює *на кожному* його екземплярі. Звідси два наслідки. По-перше, надмірно завантажений застосунок виснажує ресурси сусідів. По-друге, ви платите за план, коли застосунки завантажені й коли простоюють. *Вертикальне масштабування* змінює SKU (збільшує машину). *Horizontal scaling (горизонтальне масштабування)* змінює кількість екземплярів вручну або за правилами метрик, як-от використання CPU чи довжина queue HTTP.

**Конфігурація стає змінними середовища.** Параметри застосунку передаються як environment variables, які читає конфігурація ASP.NET Core. Для вкладених ключів використовуйте подвійне підкреслення: параметр `Payments__Stripe__Timeout` перевизначає `Payments:Stripe:Timeout`. Connection strings (рядки підключення) передаються з префіксом типу, наприклад `SQLAZURECONNSTR_` або `CUSTOMCONNSTR_`. Постачальник конфігурації environment variables розпізнає ці префікси й зіставляє їх із `ConnectionStrings:<name>`, тож `GetConnectionString("Default")` далі працює.

**Посилання Key Vault** дають змогу не зберігати секрети в параметрах застосунку. Замість секрету у значення параметра записують посилання:

```
@Microsoft.KeyVault(SecretUri=https://<vault>.vault.azure.net/secrets/<name>)
```

Платформа отримує секрет за допомогою managed identity застосунку, якому потрібна роль *Key Vault Secrets User* для сховища, а ваш код бачить звичайну environment variable. Якщо не вказати версію в URI, платформа підхоплюватиме оновлені значення, хоча й не миттєво.

**Слоти deployment** — це активні застосунки з власними іменами хостів, що спільно використовують екземпляри плану. Важливо розуміти послідовність їх перемикання, адже збої виникають саме через порядок кроків. За документацією Microsoft перемикання з вихідного слота (staging) до цільового (production) відбувається так:

```
  1. Apply the TARGET's slot-specific settings to every SOURCE instance  → the source restarts
  2. Wait for every source instance to finish restarting (any failure → swap aborted, rolled back)
  3. Local cache initialisation, if enabled (another restart)
  4. Warm up: request the application root on every source instance (or the path set in
     WEBSITE_SWAP_WARMUP_PING_PATH, accepting only WEBSITE_SWAP_WARMUP_PING_STATUSES)
  5. Switch the routing rules                     ← the only instant step; production now serves the new build
  6. Apply the settings to the old production code, now in the source slot, and restart it
```

Що це означає на практиці:

- **Позначайте налаштування середовища як *параметри слота deployment*** (закріплені). Решта переміщується разом із кодом. Якщо connection string не закріплено, він разом із тестовою збіркою потрапить у продакшен.
- **Для прогрівання використовуйте endpoint, що перевіряє роботу застосунку,** наприклад health check (перевірку працездатності), яка відкриває підключення до бази даних і заповнює кеш. Стандартний запит до `/` лише засвідчує, що процес запустився.
- **На останньому кроці старі екземпляри продакшену перезапускаються.** Незавершена довготривала робота переривається. У документації це сказано прямо; це стосується й застосунків Functions, тож фонові завдання мають підтримувати повторний запуск (див. [розділ 11](#chapter-11-messaging-and-background-work)).
- **Перемикання з попереднім переглядом** зупиняється після першого кроку: можна перевірити вихідний слот із параметрами продакшену, перш ніж завершити перемикання.

**Health check.** Налаштуйте її endpoint, і після 10 помилкових перевірок поспіль (за замовчуванням) App Service вилучить екземпляр із балансувальника навантаження, а якщо він залишиться несправним — замінить його. Щоб захистити інші екземпляри, за раз вилучається не більш ніж половина. Перевірка має охоплювати критичні для застосунку залежності й бути легкою: кожен екземпляр перевіряється щохвилини.

**Налаштування, які мають бути в кожному контрольному списку для продакшену:**

| Параметр | Навіщо |
|---|---|
| **Always On** (рівень Basic і вище) | Без нього застосунок вивантажується після 20 хвилин без запитів, а перший наступний запит оплачує все налаштування запуску. |
| Вимкнений **ARR affinity** для API без стану | Інакше cookie закріплює кожного клієнта за одним екземпляром, заважаючи horizontal scaling й перевантажуючи окремі екземпляри. |
| Лише HTTPS, мінімум TLS 1.2 | Очевидно, але про це й далі забувають. |
| Endpoint health check | Дивіться вище. |
| **Надлишковість зон** для плану (у підтримуваних рівнях, щонайменше 2 екземпляри) | Допомагає пережити збій зони: екземпляри розподіляються між зонами. |

**Два обмеження, що спричиняють реальні інциденти:**

- **230 секунд.** Фронтенд-балансувальник Azure закриває HTTP-запит, якщо за 230 секунд не отримано відповіді. Ваш код продовжує працювати, але клієнт отримує помилку. Те саме обмеження діє для функцій із HTTP-тригером незалежно від їхнього власного тайм-ауту. Для довгої роботи прийміть запит, поверніть `202 Accepted` із URL стану й обробляйте його у фоні (queue й handler (обробник) або Durable Functions).
- **Порти SNAT.** Вихідні підключення до публічних endpoints проходять через NAT джерела. За посібником Microsoft з усунення несправностей кожен екземпляр отримує *заздалегідь виділені* 128 портів. Застосунок, який створює нове вихідне підключення для кожного запиту (`new HttpClient()` на виклик, нове підключення SQL без пулу, новий клієнт SDK на запит), вичерпує їх. Симптоми — періодичні тайм-аути й `SocketException`, що з'являються лише під навантаженням, без сповіщення про CPU чи пам'ять. Виправлення: повторно використовуйте підключення (`IHttpClientFactory`, клієнти SDK як singleton), використовуйте приватні endpoints для служб Azure (трафік у межах VNet не використовує SNAT) або додайте NAT gateway (64 512 портів на публічну IP-адресу). У [розділі 30](#chapter-30-the-azure-casebook-real-incidents-real-fixes) розглянуто саме цей інцидент.

### Azure Functions

**Використовуйте модель ізольованого worker-процесу.** Функції виконуються в окремому від хоста Functions процесі .NET і в будь-якій цільовій версії .NET, з повноцінним dependency injection (впровадженням залежностей) і проміжним ПЗ. Підтримка старої моделі в одному процесі **завершується 10 листопада 2026 року**, тому міграцію кожного застосунку з нею вже треба планувати.

```csharp
using Microsoft.Azure.Functions.Worker.Builder;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var builder = FunctionsApplication.CreateBuilder(args);

builder.Services.AddHttpClient<PartnerApiClient>();   // pooled connections: see SNAT above
builder.Services.AddSingleton<IOrderRepository, SqlOrderRepository>();

builder.Build().Run();
```

```csharp
public sealed class OrderPlacedFunction(IOrderRepository orders, ILogger<OrderPlacedFunction> log)
{
    [Function(nameof(OrderPlacedFunction))]
    public async Task Run(
        [ServiceBusTrigger("orders", Connection = "ServiceBus")] ServiceBusReceivedMessage message,
        CancellationToken ct)
    {
        var order = message.Body.ToObjectFromJson<OrderPlaced>()!;

        // The trigger completes the message if this returns, and abandons it if this throws.
        // After MaxDeliveryCount abandons the message is dead-lettered. So: be idempotent.
        if (await orders.ExistsAsync(order.OrderId, ct))
        {
            log.LogInformation("Order {OrderId} already processed; skipping duplicate", order.OrderId);
            return;
        }
        await orders.InsertAsync(order, ct);
    }
}
```

Параметр `Connection = "ServiceBus"` — це *назва* префікса конфігурації, а не connection string. Якщо задати `ServiceBus__fullyQualifiedNamespace` як `<ns>.servicebus.windows.net` (і `ServiceBus__clientId` для ідентичності, призначеної користувачу), тригер автентифікується за managed identity без секрету.

**Плани хостингу.** Оберіть план до написання коду, бо він визначає тайм-аути, мережу й холодний старт:

| План | Масштабування | Тайм-аут за замовчуванням / максимум | Мережа | Примітки |
|---|---|---|---|---|
| **Flex Consumption** | За events, для кожної функції, аж до нуля; за бажанням — постійно готові екземпляри | 30 хв / необмежений | Інтеграція з VNet | Рекомендований безсерверний план для нових застосунків. Linux. |
| Consumption (застарілий) | За events, до нуля | 5 хв / 10 хв | Немає | Позначений застарілим. **Linux Consumption буде виведено з експлуатації 30 вересня 2028 року.** |
| Premium (Elastic Premium) | Попередньо прогріті екземпляри; до нуля не масштабується | 30 хв / необмежений | Інтеграція з VNet | Передбачувана затримка. Оплачується мінімальна кількість екземплярів. |
| Dedicated (план App Service) | Автоматичне масштабування плану | 30 хв / необмежений | Як у App Service | Використовуйте вільну потужність наявного плану. |
| Container Apps | KEDA | 30 хв / необмежений | Середовище Container Apps | Functions як контейнер поруч з іншими контейнерними застосунками. |

Незалежно від плану, **функція з HTTP-тригером має 230 секунд** на відповідь (той самий балансувальник, що в App Service). Навіть «необмежені» тайм-аути мають пільговий період: при скороченні масштабу Flex Consumption чи Premium поточне виконання має 60 хвилин на завершення, а під час оновлення платформи — 10 хвилин.

**Масштабування множить паралельність.** Тригер Service Bus обробляє до `maxConcurrentCalls` повідомлень одночасно *на кожен екземпляр*. Типове значення — 16; за документацією, фактична межа множиться на кількість ядер екземпляра (32 для двоядерного). Поки queue зростає, платформа додає екземпляри. За 40 двоядерних екземплярів це 1 280 одночасних виконань, кожне з яких відкриває підключення до тієї самої бази даних. Тригер масштабується; ваша база — ні. Якщо нижчий рівень має обмежену потужність, обмежте добуток цих чисел: задайте `maxConcurrentCalls` у `host.json` і максимальну кількість екземплярів (у Flex Consumption це налаштовується). Потім виміряйте. У розділі 30 розглянуто інцидент із такою проблемою.

```json
{
  "version": "2.0",
  "extensions": {
    "serviceBus": {
      "maxConcurrentCalls": 8,
      "maxAutoLockRenewalDuration": "00:05:00"
    }
  }
}
```

**Durable Functions** дають змогу описати робочий процес (викликати A, потім розгалузити виконання на B×100, чекати схвалення людини з тайм-аутом у 3 дні, потім викликати C) звичайним на вигляд асинхронним кодом `async`. Механізм — **logging (журналювання) events і повторне відтворення**. Щоразу, коли оркестратор відновлює роботу, платформа *повторно виконує функцію оркестратора з початку* й передає їй записані результати вже завершених кроків. Тому код оркестратора має бути **детермінованим**:

```csharp
[Function(nameof(ApproveRefund))]
public static async Task<string> ApproveRefund([OrchestrationTrigger] TaskOrchestrationContext context)
{
    var request = context.GetInput<RefundRequest>()!;

    // ✗ DateTime.UtcNow, Guid.NewGuid(), Random, HttpClient, Task.Delay, reading config or the DB:
    //   they return something different on replay and break the orchestration.
    // ✓ Use the context's replay-safe versions, and put all I/O in activities.
    DateTime deadline = context.CurrentUtcDateTime.AddDays(3);
    Guid refundId = context.NewGuid();

    await context.CallActivityAsync(nameof(NotifyApprover), new ApprovalRequest(refundId, request));

    using var timeoutCts = new CancellationTokenSource();
    Task<bool> approval = context.WaitForExternalEvent<bool>("ApprovalDecision");
    Task timeout = context.CreateTimer(deadline, timeoutCts.Token);

    if (await Task.WhenAny(approval, timeout) == approval)
    {
        timeoutCts.Cancel();
        return approval.Result
            ? await context.CallActivityAsync<string>(nameof(IssueRefund), refundId)
            : "rejected";
    }
    return "expired";
}
```

Варто знати назви таких шаблонів: *ланцюжок функцій*, *розгалуження/об'єднання*, *асинхронний HTTP API* (платформа надає endpoints `202` і URL стану), *монітор* (цикл опитування зі стійкими таймерами) й *взаємодія з людиною* (приклад вище).

### Container Apps

Container Apps запускає контейнери в керованому кластері Kubernetes, якого ви не бачите, із **KEDA** для масштабування й додатковим **Dapr** для міжслужбових викликів, pub/sub і стану.

- **Середовище** — спільна межа: одна VNet, один робочий простір Log Analytics і внутрішній DNS для всіх застосунків у ньому. Застосунки одного середовища звертаються один до одного за назвою.
- **Ревізія** — незмінний знімок шаблону застосунку (образ і конфігурація). У режимі *однієї ревізії* нова замінює стару після успішного health check. У режимі *кількох ревізій* можна розподілити трафік за вагами (канарковий deployment 90/10) або позначкою (URL `green` для тестування до надходження реального трафіку).
- **Правила масштабування** — засоби KEDA: паралельність HTTP, CPU або пам'ять, довжина queue Service Bus, відставання Event Hubs, cron та багато іншого. `minReplicas: 0` забезпечує масштабування до нуля (і холодний старт). `minReplicas: 1` постійно тримає теплу репліку.
- **Завдання** — контейнери, що виконуються до завершення: вручну, за розкладом cron або за events (одне виконання на пакет повідомлень черги).
- **Вхідний трафік** — *зовнішній* (публічний) або *внутрішній* (лише у VNet середовища). Отримуйте образи з Azure Container Registry за допомогою managed identity з роллю *AcrPull*, а не credentials адміністратора.

Це природне середовище для системи .NET із кількох служб, до якої веде [розділ 14](#chapter-14-containers-and-linux). Переходьте на AKS, якщо потрібна можливість, якої немає в Container Apps: власні оператори, контроль service mesh, налаштування рівня вузлів або команда платформи, якій потрібен повний API Kubernetes.

## Облікові записи сховища й Blob Storage

**Обліковий запис сховища** — це простір імен (`<name>` має бути унікальним у всьому світі, містити 3–24 малих літер і цифр), який відкриває кілька служб на окремих endpoints: Blob (`.blob.core.windows.net`), Queue, Table, Files і Data Lake (`.dfs.`). Якщо немає особливої причини, використовуйте облікові записи загального призначення v2.

### Надлишковість: кількість копій і місце їх зберігання

| Варіант | Копії | Захист від | Примітки |
|---|---|---|---|
| **LRS** | 3 в одному центрі обробки даних | Відмови диска чи стійки | Найдешевший варіант. Збій усього центру зробить дані недоступними. |
| **ZRS** | 3 у трьох зонах доступності | Збою зони | Розумний типовий вибір для продакшену в регіонах із зонами. |
| **GRS** | LRS і ще 3 копії (LRS) у парному регіоні | Збою регіону після аварійного перемикання | Реплікація на вторинну копію **асинхронна**. |
| **GZRS** | ZRS і LRS у парному регіоні | Збоїв зони й регіону | Найвищий рівень захисту. |
| **RA-GRS / RA-GZRS** | Як вище, але вторинна копія доступна для читання за `<name>-secondary.blob.core.windows.net` | Читання під час збою регіону **без перемикання** | Код має вміти читати з вторинної копії. |

Геореплікація асинхронна, тому регіональна катастрофа може знищити нещодавні записи. У документації Microsoft цей інтервал називають цільовим часом відновлення точки даних; гарантувати його (15 хвилин або менше для блочних blob) може лише додаткова функція *geo priority replication*. Без неї RPO не гарантовано. Перемикання на вторинну копію ініціюєте *ви*, і це має наслідки: після незапланованого перемикання копію в початковому регіоні видаляють, а новий основний обліковий запис має лише локальну надлишковість, доки ви знову не налаштуєте георезервування. Відпрацюйте це заздалегідь.

### Рівні доступу: вартість і затримка

| Рівень | Для чого | Мінімальний строк зберігання (інакше плата за дострокове видалення) | Затримка читання |
|---|---|---|---|
| Hot | Часто запитувані дані | немає | мс |
| Cool | Рідко запитувані дані | 30 днів | мс |
| Cold | Дуже рідко запитувані, але доступні онлайн дані | 90 днів | мс |
| Archive | Зберігання на роки, рідкісне читання | 180 днів | **години**: спершу blob треба *відновити* |

Відновлення архівного blob зі стандартним пріоритетом може тривати до 15 годин. Високий пріоритет може завершити його менш ніж за годину для blob розміром до 10 GB, але коштує дорожче. Використовуйте **політики керування життєвим циклом** (наприклад, «перемістити blob у `logs/` до Cool через 30 днів і видалити через 365») замість сценарію очищення. Плата за дострокове видалення також стягується під час *перезапису* blob, тож щоденний перезапис у Cool щоразу коштує як 30 днів зберігання.

### Надання доступу: спершу Entra, потім SAS делегування користувача

| Спосіб | Для чого використовувати | Відкликання |
|---|---|---|
| **Entra ID (RBAC)** | Власні служби через managed identity | Видалити призначення ролі |
| **SAS делегування користувача** | Надати *клієнту* (браузеру чи партнеру) обмежений у часі доступ до певних blob | Відкликати ключі делегування користувача; SAS чинний щонайбільше 7 днів |
| SAS служби з **збереженою політикою доступу** | Застарілі інтеграції, яким потрібен довший доступ | Видалити чи змінити політику |
| Ключ облікового запису / SAS облікового запису | Для нових інтеграцій — нічого | Оновити ключ, що порушить роботу всіх, хто ним користувався |

Типовий шаблон функції «завантажити великий файл»: API **не** передає файл через себе (згадайте ліміт у 230 секунд і потрібну для цього пам'ять). Він видає клієнту короткостроковий, вузько обмежений SAS, і той завантажує файл прямо до Blob Storage:

```csharp
using Azure.Storage.Blobs;
using Azure.Storage.Blobs.Models;
using Azure.Storage.Sas;

public sealed class UploadUrlIssuer(BlobServiceClient blobService)   // authenticated with managed identity
{
    public async Task<Uri> IssueAsync(string tenantId, string fileName, CancellationToken ct)
    {
        // A user delegation key is signed by Entra ID, not by the account key. The identity needs
        // a role with the generateUserDelegationKey action (Storage Blob Delegator, or a Data role).
        DateTimeOffset now = DateTimeOffset.UtcNow;
        UserDelegationKey key = await blobService.GetUserDelegationKeyAsync(
            startsOn: now.AddMinutes(-5), expiresOn: now.AddHours(1), ct);

        BlobClient blob = blobService
            .GetBlobContainerClient("uploads")
            .GetBlobClient($"{tenantId}/{Guid.NewGuid():N}/{fileName}");

        var sas = new BlobSasBuilder
        {
            BlobContainerName = blob.BlobContainerName,
            BlobName = blob.Name,
            Resource = "b",                                // this one blob
            StartsOn = now.AddMinutes(-5),                 // allow for clock skew
            ExpiresOn = now.AddMinutes(15),
        };
        sas.SetPermissions(BlobSasPermissions.Create | BlobSasPermissions.Write);   // no read, no list, no delete

        return new BlobUriBuilder(blob.Uri)
        {
            Sas = sas.ToSasQueryParameters(key, blobService.AccountName),
        }.ToUri();
    }
}
```

Підписка Event Grid на `Microsoft.Storage.BlobCreated` повідомить серверну частину про завершення завантаження. Опитування не потрібне, а байтів сервер торкнеться лише під час обробки.

### Паралельний доступ: ETag і оренди

Два екземпляри служби, які читають, змінюють і записують той самий blob, втратять оновлення, якщо не скористатися одним із двох механізмів паралельного доступу Blob Storage:

- **Оптимістичний: ETag.** Після кожного запису повертається новий `ETag`. Передайте прочитаний ETag як `IfMatch` під час запису. Якщо хтось записав дані раніше, служба поверне `412 Precondition Failed`, тоді їх можна прочитати ще раз і повторити операцію. Це дешево й коректно за низької конкуренції.
- **Песимістичний: оренда.** Отримайте оренду на 15–60 секунд або безстрокову й утримуйте її під час роботи. Записи без ID оренди завершуються помилкою. Оренди також часто використовують для вибору лідера («лише екземпляр з орендою `leader.lock` запускає планувальник»).

У першій вправі *Знайдіть помилку* в розділі 30 перевіряється відсутній ETag; тест виконується проти Azurite.

### Queue Storage чи Service Bus?

| | Queue Storage | Queue Service Bus |
|---|---|---|
| Розмір повідомлення | 64 KB | 256 KB (Standard); до 100 MB (Premium) |
| Порядок | Не гарантується | FIFO у межах сеансу |
| Dead-letter queue (черга недоставлених повідомлень) | Вбудованої немає (перевіряйте `DequeueCount` самостійно) | Автоматична після MaxDeliveryCount; для кожної сутності є DLQ |
| Виявлення дублікатів, транзакції, відкладені повідомлення, теми | Ні | Так |
| Вартість і масштаб | Дуже дешево; дуже великі queue | Більше можливостей; оплата за операцію або одиницю messaging |

Обирайте Queue Storage для простих високонавантажених завдань «просто виконай це згодом». Щойно бізнес-процес залежить від повідомлення, беріть Service Bus.

## Cosmos DB для NoSQL

Cosmos DB — не «NoSQL-база, куди можна помістити будь-що». Це секціоноване сховище ключ-значення й документів, де кожна операція має вартість. Воно винагороджує рішення, що враховують його модель, і карає ігнорування обмеженнями пропускної здатності й рахунками.

### Модель: секції й одиниці запитів

```
  account ─► database ─► container (partition key path, e.g. /tenantId)
                              │
          logical partitions: all items with the same partition key value
          (/tenantId = "acme", /tenantId = "globex", …), up to 20 GB each
                              │   many logical partitions are hashed onto each
          physical partitions: up to 10,000 RU/s and 50 GB each; Cosmos splits them as you grow
```

- **Одиниці запитів (RU)** — це валюта. Кожна операція коштує RU: точкове читання невеликого елемента — близько 1 RU, а записи, запити й більші елементи коштують дорожче. Можна резервувати RU/s або використовувати безсерверну модель з оплатою за RU. Відповідь SDK містить витрати в `RequestCharge`, тож записуйте їх у журнали під час розробки й перевіряйте під час перегляду коду.
- **Пропускна здатність окремої логічної секції не може перевищити 10 000 RU/s**, оскільки вона розміщується рівно в одній фізичній секції. Резервування 50 000 RU/s не допоможе, якщо весь трафік іде на одне значення ключа секції. Це **гаряча секція**; вона обмежує пропускну здатність до частки оплаченого вами рівня.
- **Логічна секція обмежена 20 GB** (ієрархічні ключі секцій скасовують це обмеження).

### Вибір ключа секції: рішення, яке складно змінити

Хороший ключ секції має **високу кардинальність** (багато різних значень), **рівномірно розподіляє сховище й запити** та **входить до фільтра найчастіших запитів**, щоб вони працювали в одній секції. Змінити ключ секції контейнера не можна: дані потрібно перенести в новий контейнер.

| Навантаження | Варіант | Оцінка |
|---|---|---|
| Багатоклієнтська SaaS, запити завжди в межах одного клієнта | `/tenantId` | Добре, *якщо* один клієнт не створює 30% трафіку. У такому разі використовуйте ієрархічний ключ `/tenantId` + `/userId`. |
| Замовлення читають за ID, список формують для кожного клієнта | `/customerId` | Добре: список замовлень працює в одній секції, а точковому читанню потрібні `id` і `customerId`. |
| Телеметрія IoT: мільйони пристроїв, запити за пристроєм і часовим діапазоном | `/deviceId` (ієрархічно: `/deviceId`, `/yyyyMM`) | Добре; другий рівень утримує кожну секцію в межах 20 GB. |
| Будь-що | `/status`, `/country`, `/type` | **Погано.** Низька кардинальність створює кілька величезних гарячих секцій. |
| Журнал events | `/createdDate` (день) | **Погано.** Усі записи за сьогодні потрапляють в одну секцію. |

Запит без ключа секції — це **міжсекційний запит**: він надсилає запити до кожної фізичної секції, витрачає RU в кожній і дорожчає зі зростанням контейнера. Він прийнятний для рідкісного екрана адміністратора й катастрофічний у найгарячішому шляху.

```csharp
using Microsoft.Azure.Cosmos;

public sealed class OrderStore(Container orders, ILogger<OrderStore> log)   // Container from a singleton CosmosClient
{
    public async Task<Order?> GetAsync(string customerId, string orderId, CancellationToken ct)
    {
        try
        {
            // Point read: id + partition key. The cheapest operation Cosmos DB has.
            ItemResponse<Order> read = await orders.ReadItemAsync<Order>(orderId, new PartitionKey(customerId), cancellationToken: ct);
            log.LogDebug("Point read cost {RU} RU", read.RequestCharge);
            return read.Resource;
        }
        catch (CosmosException e) when (e.StatusCode == System.Net.HttpStatusCode.NotFound)
        {
            return null;
        }
    }

    public async Task<List<Order>> ListOpenAsync(string customerId, CancellationToken ct)
    {
        var query = new QueryDefinition("SELECT * FROM c WHERE c.customerId = @c AND c.status = 'Open'")
            .WithParameter("@c", customerId);

        // Scoping the query to one partition key keeps it single-partition.
        using FeedIterator<Order> it = orders.GetItemQueryIterator<Order>(
            query, requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey(customerId) });

        var result = new List<Order>();
        double charge = 0;
        while (it.HasMoreResults)
        {
            FeedResponse<Order> page = await it.ReadNextAsync(ct);
            charge += page.RequestCharge;
            result.AddRange(page);
        }
        log.LogDebug("Open-orders query cost {RU} RU for {Count} items", charge, result.Count);
        return result;
    }
}
```

### Рівні consistency

Cosmos DB пропонує п'ять рівнів, від найсуворішого до найслабшого: **суворий**, **обмежене відставання**, **сеансовий** (типовий), **узгоджений префікс** і **зрештою узгоджений**. Слабші рівні знижують вартість читань у RU, затримку й доступність між регіонами.

Важливо зрозуміти **сеансовий** рівень, оскільки він типовий. Він гарантує читання власних записів *у межах сеансу*, а сеанс визначається **токеном сеансу**, який SDK відстежує для кожного екземпляра `CosmosClient`. Два екземпляри API за балансувальником навантаження мають різні клієнти. Тож користувач, який записав через екземпляр A, а читає через B, може не побачити свій запис, якщо B читає з репліки, що ще не оновилася. Вирішення: читати з того самого екземпляра, передавати токен сеансу далі (повернути клієнту й надіслати з наступним запитом як `ItemRequestOptions.SessionToken`) або погодитися на певну застарілість даних в інтерфейсі.

### Індексування, стрічка змін і TTL

- **Політика індексування.** За замовчуванням індексується кожна властивість кожного елемента. Це дає змогу виконувати будь-які запити, але збільшує вартість кожного запису, навіть якщо властивості ніхто не запитує. У контейнерах із великими документами й частими записами виключайте шляхи (`"excludedPaths": [{ "path": "/payload/*" }]`). Додайте **складені індекси** для `ORDER BY` за двома чи більшою кількістю властивостей, інакше запит завершиться помилкою.
- **Стрічка змін.** Постійний упорядкований за ключем секції запис змін, який споживається *handler стрічки змін*. Він зберігає позицію в *контейнері оренд* і розподіляє секції між екземплярами. Це природний спосіб створювати проєкції, індекси пошуку й ретранслятори outbox ([розділ 11](#chapter-11-messaging-and-background-work)). Типовий режим *останньої версії* **не** записує видалень, тож consumer (споживач) не дізнається, що елемент зник. Або позначайте запис як видалений і пізніше прибирайте за TTL, або використовуйте режим *усіх версій і видалень*.
- **TTL.** Задайте час життя контейнера за замовчуванням і перевизначайте його для окремих елементів властивістю `ttl`. Прострочені елементи видаляються у фоновому режимі за рахунок невикористаних RU — завдання видалення писати не треба.

### Правила SDK, що запобігають більшості інцидентів

- **Один `CosmosClient` на обліковий запис протягом життя процесу.** Він зберігає підключення, карту секцій і токени сеансів. Клієнт на кожен запит — еквівалент проблеми SNAT для Cosmos, і він ще й викидає токени сеансів.
- **Залишайте типовий режим прямого підключення**, якщо брандмауер не змушує використовувати режим шлюзу.
- **Сприймайте `429` як сигнал, а не шум.** SDK повторює обмежені запити автоматично: типово 9 спроб, до 30 секунд очікування загалом. `CosmosException` зі статусом 429, що дійшла до вашого коду, означає, що retries (повторні спроби) вичерпано. Відповідь містить `RetryAfter`. Перш ніж купувати більше RU/s, перевірте, чи немає гарячої секції.
- **Використовуйте `_etag` для оптимістичного паралельного доступу** (`ItemRequestOptions.IfMatchEtag`), так само як для blob.

## Azure SQL Database

Для команди .NET Azure SQL — це SQL Server, де виправленнями, резервними копіями й високою доступністю займається інша сторона. Різниця полягає у способі придбання, збоях і підключенні.

### Придбання

| Варіант | Можливості | Рекомендація |
|---|---|---|
| Deployment | Окрема база даних · еластичний пул · керований екземпляр | Пул розподіляє обчислювальні ресурси між багатьма малими базами з нерівномірним навантаженням (окрема база на клієнта). Керований екземпляр майже повністю сумісний із SQL Server (SQL Agent, запити між базами) й підходить для перенесення без зміни архітектури. |
| Модель оплати | DTU (пакетна) · vCore | vCore: обчислення й сховище обираються окремо; доступні резервування й Azure Hybrid Benefit. |
| Рівень служби | General Purpose · Business Critical · Hyperscale | Business Critical надає локальний SSD і безкоштовну доступну для читання вторинну репліку. Hyperscale підтримує дуже великі сховища й швидко додає репліки. |
| Обчислення | Виділені · **безсерверні** | Безсерверний варіант автоматично масштабує vCore і може **автоматично призупинятися** під час простою, що зручно для розробки/тестування. Перше підключення відновлює базу й завершується тимчасовою помилкою, доки відновлення не завершено. |

### Перемикання неминучі — повторюйте спроби

Керована база переходить між вузлами для виправлень, масштабування й усунення збоїв обладнання. Кожне перемикання спричиняє кілька секунд тимчасових помилок: `40613` («база даних … наразі недоступна»), `40197`, `40501` («служба тимчасово зайнята»), `49918` та інші. Рекомендація Microsoft однозначна: кожен хмарний застосунок має повторювати спроби після тимчасових помилок підключення; для безсерверних баз це особливо важливо. В EF Core увімкніть стратегію виконання SQL Server:

```csharp
builder.Services.AddDbContext<ShopDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("Shop"),
        sql => sql.EnableRetryOnFailure(
            maxRetryCount: 5,
            maxRetryDelay: TimeSpan.FromSeconds(10),
            errorNumbersToAdd: null)));
```

> **Нюанс.** Зі стратегією retries транзакція, яку ви почали самі (`BeginTransaction`), спричиняє помилку, бо EF Core не може відтворити лише частину транзакції. Отримайте стратегію через `CreateExecutionStrategy()` і запустіть усю одиницю роботи в `ExecuteAsync`, щоб повтор охоплював *усе*, разом із читаннями (код наведено в розділі 30, кейс 14). У [розділі 7](#chapter-7-data-access) докладно розглянуто транзакції EF Core.

### Підключайтеся за ідентичністю, а не паролем

`Microsoft.Data.SqlClient` сам отримує токен Entra:

```
Server=tcp:shop-sql.database.windows.net,1433;Database=Shop;
Authentication=Active Directory Managed Identity;User Id=<client-id-of-user-assigned-identity>;
Encrypt=True;
```

`Active Directory Default` використовує ланцюжок на кшталт `DefaultAzureCredential`, тож той самий connection string працюватиме й на ноутбуці після `az login`. База даних має знати про ідентичність, тому адміністратор Entra одноразово виконує для кожної бази:

```sql
CREATE USER [shop-api-identity] FROM EXTERNAL PROVIDER;   -- the managed identity's name
ALTER ROLE db_datareader ADD MEMBER [shop-api-identity];
ALTER ROLE db_datawriter ADD MEMBER [shop-api-identity];
```

Потім увімкніть на сервері *лише автентифікацію Microsoft Entra* — і входи SQL більше не працюватимуть.

**Політика підключення.** За замовчуванням клієнтів в Azure *перенаправляють* для прямого підключення до вузла бази даних. Це зменшує затримку порівняно з передаванням кожного пакета через шлюз. Тому вихідний брандмауер має дозволяти порти **11000–11999** до адрес Azure SQL у регіоні (тег служби `Sql`), а не лише 1433. Ситуація «з ноутбука підключається, а з віртуальної машини — тайм-аут» часто пояснюється саме цим.

### Висока доступність і аварійне відновлення

- **Надлишковість зон** розподіляє репліки між зонами доступності одного регіону.
- **Активна геореплікація** підтримує доступні для читання вторинні копії в інших регіонах.
- **Групи аварійного перемикання** надають дві endpoints *слухачів*, які змінюються разом з основною: `<group>.database.windows.net` для читання й запису та `<group>.secondary.database.windows.net` лише для читання. **Завжди підключайтеся через слухача**, щоб аварійне перемикання регіону не вимагало зміни конфігурації. Геореплікація асинхронна, тож примусове перемикання може втратити недавні транзакції — врахуйте це у своєму RPO.

Навички налаштування SQL з [розділу 19](#chapter-19-the-slow-query-lab-reading-execution-plans) (частина про SQL Server) безпосередньо застосовуються і тут. В Azure SQL типово ввімкнено Query Store, а також є *автоматичне налаштування*, яке може створювати й вилучати індекси та примусово використовувати останній відомий добрий план. Перевіряйте його дії, але не підмінюйте ним власне розуміння.

## Messaging: Service Bus, Event Hubs і Event Grid

[Розділ 11](#chapter-11-messaging-and-background-work) навчає шаблонів: outbox, ідемпотентний consumer, saga. Тут ідеться про три брокери Azure, які є трьома різними інструментами, а не трьома брендами одного засобу:

| | **Service Bus** | **Event Hubs** | **Event Grid** |
|---|---|---|---|
| Модель | Брокер із queues й темами | Секціонований журнал лише для додавання | Routing (маршрутизація) events із доставкою push |
| Повідомлення — це… | Команда чи бізнес-подія, що потребує обробки | Один із мільйонів записів телеметрії чи потоку кліків | Сповіщення про event («створено blob») |
| Споживання | Конкуруючі consumer, peek-lock і підтвердження кожного повідомлення | Кожна група consumers читає журнал зі своєї позиції й зберігає контрольні точки | Доставка до вашого endpoint (webhook, функція, черга) з retries |
| Порядок | FIFO у межах сеансу | У межах секції | Не гарантовано |
| Після читання | Видаляється після підтвердження | Зберігається до завершення строку; можливе повторне відтворення | Зникає після доставки |
| Обирайте для | «Списати кошти з цієї картки — фактично рівно один раз» | «Приймати 100 тис. events за секунду й надати читання трьом командам» | «Реагувати на створення blob чи зміну ресурсу» |

### Service Bus

**Рівні.** *Basic* підтримує лише queue. *Standard* додає теми, сеанси, транзакції й виявлення дублікатів на спільній інфраструктурі. *Premium* працює на виділених одиницях messaging з приватними endpoints й передбачуваною затримкою. Розмір повідомлення: 256 KB у Basic і Standard; у Premium — 1 MB за замовчуванням і до 100 MB із підтримкою великих повідомлень.

**Peek-lock — типовий режим і саме той, який слід використовувати.** Одержувач отримує повідомлення й **блокування** на нього; доки блокування чинне, інші одержувачі його не побачать. Потім одержувач **підтверджує результат**:

```
            receive (peek-lock)
  queue ──────────────────────────► handler ──┬── Complete  → deleted
    ▲                                         ├── Abandon   → back in the queue now, DeliveryCount + 1
    │                                         ├── Dead-letter → moved to <queue>/$deadletterqueue
    │                                         └── Defer     → set aside, retrievable by sequence number
    │   lock expires (1 min by default,
    └── max 5 min) before settlement → back in the queue, DeliveryCount + 1
                                        DeliveryCount > MaxDeliveryCount (default 10) → dead-lettered
```

Важливі факти, про які також запитують на співбесідах:

- **Типова тривалість блокування — 1 хвилина, максимум — 5.** Робота довша за це має *поновлювати* блокування. `ServiceBusProcessor` автоматично поновлює його до `MaxAutoLockRenewalDuration` (типово 5 хвилин). Якщо строк спливе, `CompleteMessageAsync` викине `MessageLockLost`, повідомлення доставлять повторно *після виконання побічних ефектів*. У другій вправі *Знайдіть помилку* з розділу 30 це показано й перевірено в емуляторі Service Bus.
- **Доставка завжди щонайменше один раз.** Блокування спливає, процес аварійно завершується між побічним ефектом і `Complete`, мережа втрачає підтвердження. Кожен consumer має бути **ідемпотентним**: захоплювати ID повідомлення за унікальним ключем в одній транзакції з ефектом ([розділ 11: ідемпотентні consumer](#idempotent-consumers)), ніколи не перевіряти спершу, а записувати згодом.
- **Dead-letter queue не очищається сам.** Вони залишаються там, доки хтось їх не прочитає. Налаштуйте сповіщення про кількість таких повідомлень (метрика `DeadletteredMessages`) та інструмент для їх перегляду, виправлення й повторного надсилання. Ніхто не стежить за DLQ — це механізм непомітної втрати даних.
- **Сеанси впорядковують обробку за ключем.** Задайте `SessionId = customerId`; queue передаватиме повідомлення кожного сеансу одному одержувачу за раз у правильному порядку, а різні сеанси оброблятимуться паралельно. Стан сеансу (до розміру одного повідомлення) дає змогу зберігати невеликий автомат станів для кожного сеансу.
- **Виявлення дублікатів** відкидає повідомлення з `MessageId`, уже побаченим протягом певного вікна (20 секунд – 7 днів; типове значення в службі — 10 хвилин, а `CreateQueueOptions` у .NET задає 1 хвилину, якщо не налаштувати `DuplicateDetectionHistoryTimeWindow`). Це захищає від *відправника*, що повторює спробу після тайм-ауту. Повторна доставка — це те саме повідомлення, надіслане ще раз, тому цей механізм не замінює ідемпотентного consumer.
- **Відкладені повідомлення** (`ScheduledEnqueueTime`) і **транзакції** (атомарно підтвердити й надіслати *в межах одного простору імен*) доповнюють можливості. Транзакція не може охопити вашу базу даних — для цього й існує outbox.

**Клієнт .NET.** `ServiceBusClient` керує підключенням AMQP, тож створюйте один екземпляр на простір імен на весь час життя процесу. Відправники, одержувачі й handlers недорогі та використовують спільне підключення. Типові параметри handler консервативні — запам'ятайте їх:

| `ServiceBusProcessorOptions` | Типове значення | Примітка |
|---|---|---|
| `MaxConcurrentCalls` | **1** | Одне повідомлення за раз. Збільшуйте обдумано, зважаючи на потужність нижчого рівня. |
| `AutoCompleteMessages` | `true` | Підтверджує повідомлення після повернення handler. Якщо handler викине exception і не підтвердить його, повідомлення буде скасовано незалежно від цього параметра. |
| `MaxAutoLockRenewalDuration` | 5 хвилин | Для довших handlers збільште значення. |
| `PrefetchCount` | 0 | Попередньо отримані повідомлення *блокуються, поки чекають у пам'яті*. Велике значення разом із повільною обробкою призводить до спливання блокувань і повторної доставки. |
| `ReceiveMode` | `PeekLock` | `ReceiveAndDelete` забезпечує доставку щонайбільше один раз: у разі аварійного завершення повідомлення втрачається. |

```csharp
ServiceBusProcessor processor = client.CreateProcessor("payments", new ServiceBusProcessorOptions
{
    MaxConcurrentCalls = 8,                                 // sized to what the payment provider tolerates
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(10),
});

processor.ProcessMessageAsync += async args =>
{
    var command = args.Message.Body.ToObjectFromJson<ChargeCard>()!;
    try
    {
        await payments.ChargeOnceAsync(command, args.CancellationToken);   // idempotent on command.PaymentId
    }
    catch (CardDeclinedException e)
    {
        // A business failure: retrying cannot help, so dead-letter it with a reason a human can read.
        await args.DeadLetterMessageAsync(args.Message, "CardDeclined", e.Message, args.CancellationToken);
    }
    // Any other exception: the processor abandons the message → it is retried, up to MaxDeliveryCount.
};
processor.ProcessErrorAsync += args =>
{
    logger.LogError(args.Exception, "Service Bus error in {Source} on {Entity}", args.ErrorSource, args.EntityPath);
    return Task.CompletedTask;
};
await processor.StartProcessingAsync();
```

Викидайте exception за *тимчасових* збоїв, щоб повторити обробку; *постійні* помилки одразу переміщуйте до dead-letter queue із зрозумілою причиною. Інакше повідомлення, яке ніколи не вдасться обробити, вичерпає всі 10 спроб доставки, кожна з яких може повторити побічний ефект.

### Event Hubs

Event Hubs — **секціонований журнал**, та сама модель, що й Kafka (він навіть підтримує протокол Kafka).

- У центрі events є **секції**: до 32 у Basic і Standard. Events з однаковим **ключем секції** потрапляють в одну секцію; порядок гарантовано лише в її межах. Зазвичай кількість секцій у Standard згодом змінити не можна, тож розрахуйте її на піковий рівень паралельності.
- **Група consumers** — незалежне представлення журналу з окремою позицією для кожної секції. Basic дозволяє одну групу, Standard — 20. Для кожної програми-споживача створюйте власну.
- **Строк зберігання**: 1 день у Basic, до 7 у Standard і до 90 у Premium та Dedicated. Consumer можуть повторно прочитати все, що ще зберігається, наприклад після виправлення помилки.
- **Контрольні точки.** `EventProcessorClient` розподіляє секції між екземплярами й зберігає позицію кожної в контейнері Blob. Ви визначаєте частоту контрольних точок: після кожної events — найбезпечніше, але найповільніше; після N events або T секунд — швидше, проте після перезапуску events від останньої контрольної точки будуть прочитані знову. Отже, consumer Event Hubs теж мають бути ідемпотентними.
- **Capture** записує потік у Blob Storage або Data Lake як файли Avro, створюючи архів без коду consumer.

### Event Grid

Event Grid **передає events push-механізмом** підписникам. **Системні теми** публікують events Azure (`Microsoft.Storage.BlobCreated`, зміни груп ресурсів, наближення строку дії секрету Key Vault тощо). **Власні теми** й **домени** несуть ваші events. Підписки фільтрують їх за типом, префіксом чи суфіксом теми й полями даних; доставка можлива за схемою CloudEvents 1.0.

- **Retries.** Якщо доставити event не вдалося, Event Grid повторює спробу з експоненційним збільшенням інтервалу. За замовчуванням він припиняє після **30 спроб або 24 годин** (1 440 хвилин), залежно від того, що настане раніше; обидва обмеження налаштовуються. Укажіть цільовий **dead-letter queue** (контейнер blob), інакше events, для яких вичерпано спроби, буде відкинуто.
- **Перевірка webhook.** Перш ніж надсилати events до HTTP-кінцевої точки, Event Grid перевіряє, що ви володієте нею. Він надсилає `SubscriptionValidationEvent`, а endpoint має синхронно повернути `validationCode` (або хтось має відкрити `validationUrl` із events запитом `GET`). Якщо повернути `200` без коду, справжні events надходити не будуть. Підписка на функцію Azure або queue Service Bus дає змогу цього уникнути й зазвичай є кращим рішенням: queue поглинає пікові навантаження й забезпечує семантику peek-lock.
- **Доставка щонайменше один раз і без упорядкування.** Усуньте дублікати за ID events `id`.

## Конфігурація й секрети: Key Vault та App Configuration

| Тип значення | Де зберігається |
|---|---|
| Типові значення, однакові всюди | `appsettings.json` у репозиторії |
| Значення середовища, не секрети (URL, перемикачі функцій, тайм-аути) | Параметри App Service / Container Apps або **App Configuration** з міткою для середовища |
| Секрети, яких не можна позбутися (ключ стороннього API, сертифікат підпису) | **Key Vault**, на який посилається застосунок; ніколи не копіюйте в параметри |
| Credentials служб Azure | **Ніде.** Їх замінює managed identity. |

### Key Vault

- У сховищі є **секрети** (рядки), **ключі** (ключі RSA/EC, які можна використовувати, але не експортувати, наприклад для підпису чи конвертного шифрування) і **сертифікати** (з автоматичним оновленням від підтримуваних центрів сертифікації).
- Використовуйте **модель дозволів Azure RBAC** (ролі на кшталт *Key Vault Secrets User*), а не старіші політики доступу сховища. RBAC можна обмежити одним секретом, а призначення аудіюються, як інші ролі.
- **Програмне видалення** завжди ввімкнено: вилучене сховище й об'єкти можна відновити за 7–90 днів (типово 90; строк обирається під час створення сховища). **Захист від остаточного очищення** не дає нікому, навіть власнику, очистити його до завершення цього строку. Нюанс у тому, що програмно видалене сховище чи секрет і далі займає своє ім'я: IaC не зможе створити їх знову з тією самою назвою, доки старий об'єкт не очистять остаточно або не відновлять.
- **Key Vault обмежує частоту запитів** для кожного сховища й повертає `429` при перевищенні лімітів. Він призначений для завантаження секретів під час запуску й ротації, а не для читання на кожен запит. Одноразово завантажуйте секрети через систему конфігурації й періодично оновлюйте їх:

```csharp
// Package: Azure.Extensions.AspNetCore.Configuration.Secrets
using Azure.Extensions.AspNetCore.Configuration.Secrets;

builder.Configuration.AddAzureKeyVault(
    new Uri(builder.Configuration["KeyVault:Uri"]!),
    credential,
    new AzureKeyVaultConfigurationOptions
    {
        ReloadInterval = TimeSpan.FromMinutes(30),   // picks up rotated secrets without a restart
    });

// A secret named "Stripe--ApiKey" becomes the configuration key "Stripe:ApiKey",
// so it binds to options classes like any other setting.
builder.Services.Configure<StripeOptions>(builder.Configuration.GetSection("Stripe"));
```

Після ротації секрету застосунок має вміти *використовувати* нове значення. `IOptionsMonitor<T>` бачить оновлену конфігурацію, а `IOptions<T>` зберігає значення на час запуску. Якщо credentials не можна перемкнути атомарно, використовуйте **схему двох ключів**: постачальник приймає ключі A і B одночасно; оновіть B, поки клієнти використовують A, перемкніть клієнтів на B, а тоді оновіть A.

### App Configuration і перемикачі функцій

App Configuration — це централізоване сховище пар ключ-значення з **мітками** (наприклад, для кожного середовища), **посиланнями Key Vault** і **перемикачами функцій**, які підтримує `Microsoft.FeatureManagement` (зокрема поступовий відсотковий випуск і націлювання). Найцікавіша можливість — динамічне оновлення за **ключем-маркером**: застосунок стежить за одним ключем, і після його зміни перезавантажує всю конфігурацію. Так пакет пов'язаних змін набуває чинності одночасно. Зверніть увагу: постачальник конфігурації й проміжне ПЗ оновлення надходять із двох окремих пакетів:

```csharp
// Packages: Microsoft.Extensions.Configuration.AzureAppConfiguration (the provider)
//           Microsoft.Azure.AppConfiguration.AspNetCore (UseAzureAppConfiguration, the refresh middleware)
builder.Configuration.AddAzureAppConfiguration(options =>
{
    options.Connect(new Uri(builder.Configuration["AppConfig:Endpoint"]!), credential)
        .Select(KeyFilter.Any, LabelFilter.Null)
        .Select(KeyFilter.Any, builder.Environment.EnvironmentName)       // environment label overrides
        .ConfigureKeyVault(kv => kv.SetCredential(credential))            // resolves Key Vault references
        .ConfigureRefresh(refresh => refresh
            .Register("App:Sentinel", refreshAll: true)                   // bump this key to reload everything
            .SetRefreshInterval(TimeSpan.FromSeconds(30)))
        .UseFeatureFlags();
});
builder.Services.AddAzureAppConfiguration();

var app = builder.Build();
app.UseAzureAppConfiguration();   // triggers the refresh check on incoming requests
```

## API Management

API Management (APIM) — це шлюз перед вашими API. В одному місці він дає змогу налаштовувати автентифікацію, rate limiting, перетворення, кешування й портал розробника. До його складників належать:

- **API** та їхні **операції**, імпортовані зі специфікації OpenAPI.
- **Продукти** об'єднують API, а **підписки** на продукт видають ключі підписки. Ці ключі ідентифікують *викликача*, але не забезпечують надійної автентифікації, тож поєднуйте їх із `validate-jwt` (або `validate-azure-ad-token`).
- **Політики** — це pipelines XML із чотирма етапами: `inbound`, `backend`, `outbound` і `on-error`, які можна визначати на рівні всього шлюзу, продукту, API чи операції.

```xml
<policies>
  <inbound>
    <base />
    <validate-azure-ad-token tenant-id="{{tenant-id}}">
      <audiences><audience>api://orders-api</audience></audiences>
    </validate-azure-ad-token>
    <rate-limit-by-key calls="100" renewal-period="60"
                       counter-key="@(context.Request.Headers.GetValueOrDefault("Authorization",""))" />
    <set-backend-service backend-id="orders-api-backend" />
  </inbound>
  <backend><base /></backend>
  <outbound><base /></outbound>
  <on-error><base /></on-error>
</policies>
```

На іспитах і архітектурних оглядах згадують два розрізнення. **Rate limiting й квота:** rate limiting захищає нижчий рівень від піків (виклики за короткий період), а квота встановлює контракт використання (виклики чи пропускна здатність за тиждень або місяць). **Ревізії й версії:** ревізія — це несумісних змін не вносить; її можна перевірити й зробити поточною. Версія — це несумісна зміна, яку викликачи обирають самі (`/v2/`, заголовком або рядком запиту). Є рівні від *Consumption* (безсерверний, оплата за виклик) і *Developer* (без SLA, лише для не виробничого використання) до Basic, Standard і Premium та їхніх версій v2. Мережеві можливості й багаторегіональний deployment залежать від рівня (для кількох регіонів потрібен Premium), тому перед проєктуванням перевірте порівняння рівнів.

## Мережа для розробників застосунків

Проєктувати топології hub-and-spoke не потрібно. Але треба знати достатньо, щоб служба була доступною лише потрібним викликачам і щоб можна було налагодити недоступність. Усе зводиться до п'яти понять:

- **VNet** — приватна мережа в регіоні, поділена на **підмережі**; **групи мережевої безпеки (NSG)** визначають дозволи й заборони на рівні підмереж і мережевих карт.
- **Приватний endpoint** надає PaaS-ресурсу (обліковому запису сховища, сховищу секретів, серверу SQL, простору імен Service Bus) **приватну IP-адресу у вашій VNet**. Якщо вимкнути публічний доступ до мережі ресурсу, це буде єдиний шлях усередину. Вона керує **вхідним** доступом *до* служби.
- **Endpoint служби** — старіший і простіший варіант: трафік із підмережі йде до служби магістральною мережею Azure, а брандмауер служби може дозволити цю підмережу. Публічна IP-адреса служби залишається, а правило задається для підмережі, не ресурсу.
- **Інтеграція App Service / Functions із VNet** контролює **вихідний** трафік: застосунок може звертатися до приватних endpoints і інших ресурсів *у* VNet. Це не робить сам застосунок приватним. Для цього додайте приватний endpoint *до застосунку* або поставте перед ним Front Door чи Application Gateway і обмежте до нього доступ.
- **Приватний DNS** спрямовує ім'я на приватну IP-адресу, і саме на цьому етапі найчастіше виникають збої.

```
  app (VNet-integrated) asks DNS for  shopdata.blob.core.windows.net
        │
        ▼
  public DNS: CNAME → shopdata.privatelink.blob.core.windows.net
        │
        ├── Private DNS zone "privatelink.blob.core.windows.net" LINKED to the app's VNet?
        │        yes → A record → 10.1.2.5  (the private endpoint)                         ✓
        │        no  → resolves to the PUBLIC IP → the storage firewall says 403 (public access off) ✗
        │
        └── the app uses custom DNS servers (on-premises, a firewall)? Then THOSE servers must forward
            privatelink.* to Azure DNS (168.63.129.16), or the lookup never reaches the private zone.
```

Перше, що треба зробити, якщо «приватний endpoint не працює», — виконати DNS-запит *із runtime (середовища виконання) застосунку* (консоль Kudu або SSH в App Service, `az containerapp exec` у Container Apps): `nslookup shopdata.blob.core.windows.net`. Публічна IP-адреса у відповіді означає, що проблема в DNS, а не брандмауері, RBAC чи коді. Назви зон утворюються за шаблоном: `privatelink.blob.core.windows.net`, `privatelink.vaultcore.azure.net`, `privatelink.database.windows.net`, `privatelink.servicebus.windows.net`, `privatelink.documents.azure.com`.

**Трафік перед застосунком:**

| Служба | Рівень | Область | Застосування |
|---|---|---|---|
| **Front Door** | L7 (HTTP) | Глобальна | Вебзастосунки й API у кількох регіонах: вхід через anycast, WAF, кешування CDN, перемикання між регіонами |
| **Application Gateway** | L7 | Регіональний | WAF і routing за шляхом у межах регіону, зокрема до приватних серверних компонентів |
| **Load Balancer** | L4 (TCP/UDP) | Регіональна | Трафік без HTTP, віртуальні машини |
| **Traffic Manager** | DNS | Глобальна | Перемикання за DNS або геомаршрутизація для будь-чого, із затримками кешування DNS |

**Вихідний трафік:** NAT gateway у підмережі інтеграції надає застосунку статичну зовнішню IP-адресу (партнери можуть додати її до списку дозволених) і 64 512 портів SNAT на публічну IP-адресу. Це інфраструктурна частина рішення проблеми SNAT, описаної в розділі App Service.

## Observability: Application Insights і KQL

[Розділ 9](#chapter-9-exceptions-logging-and-first-diagnosis) пояснює три складники observability (спостережуваності) й OpenTelemetry. В Azure вони зберігаються в **Azure Monitor**: *метрики* (числові часові ряди, недорогі, зберігаються 93 дні й дають швидкі сповіщення) і *журнали* (записи в **робочому просторі Log Analytics**, які запитують мовою **KQL**). **Application Insights** надає робочому простору представлення продуктивності застосунку: запити, залежності, exceptions й tracing (трасування), пов'язані за ID операції в одну наскрізну транзакцію.

Для .NET рекомендовано використовувати **Azure Monitor OpenTelemetry Distro**:

```csharp
using Azure.Monitor.OpenTelemetry.AspNetCore;

builder.Services.AddOpenTelemetry().UseAzureMonitor(options =>
{
    // The connection string comes from APPLICATIONINSIGHTS_CONNECTION_STRING.
    options.Credential = credential;        // Entra-authenticated ingestion, if the resource requires it
    options.TracesPerSecond = 5.0;          // the distro's default: rate-limited sampling at 5 traces/s
});
```

**Вибірка визначає рахунок і видимість.** Поточні версії Distro типово використовують обмежену частотою вибірку приблизно 5 трас за секунду. Її можна змінити через `TracesPerSecond` або перейти на відсоткове вибирання з `SamplingRatio`. Відкинутий tracing зникає, тож рідкісного збою може взагалі не бути в даних. Зважайте на це, перш ніж вирішити, що «цього ніколи не траплялося».

**Запити KQL, які знадобляться першого тижня** (назви таблиць Application Insights; у дужках — відповідники для робочого простору):

```kusto
// Failed requests by operation over the last hour  (AppRequests)
requests
| where timestamp > ago(1h) and success == false
| summarize failures = count() by name, resultCode
| order by failures desc

// p50/p95/p99 latency per endpoint, in 5-minute buckets
requests
| where timestamp > ago(6h)
| summarize percentiles(duration, 50, 95, 99) by name, bin(timestamp, 5m)
| render timechart

// Which dependency is slow or failing?  (AppDependencies)
dependencies
| where timestamp > ago(1h)
| summarize calls = count(), failed = countif(success == false), p95 = percentile(duration, 95) by type, target
| order by p95 desc

// Everything that happened in one request, across services  (join on operation_Id)
union requests, dependencies, exceptions, traces
| where operation_Id == "<operation id from an error report>"
| project timestamp, itemType, name, resultCode, duration, message, cloud_RoleName
| order by timestamp asc
```

**Сповіщення.** Для швидких і недорогих сигналів використовуйте *сповіщення про метрики* (частота HTTP 5xx, довжина queue, кількість недоставлених повідомлень, CPU). Для запитів із певною логікою потрібні *сповіщення пошуку в журналах* (певний тип exception, частота помилок за клієнтом). Обидва види надсилаються через **групи дій** (електронна пошта, SMS, webhook, Logic App). Додайте **перевірку доступності**, яка перевіряє працездатність із кількох регіонів: вона виявляє збій, якого не помітить ваша телеметрія, бо зупинений застосунок нічого не надсилає.

> **Пастка.** Встановлювати **денне обмеження** для скорочення витрат Application Insights. Коли воно спрацює, приймання телеметрії *припиниться до кінця дня*. Найімовірніше, перевищення бюджету відбудеться в день інциденту, і ви осліпнете посеред нього. Обмежуйте обсяг вибіркою, рівнем logging (не записуйте `Information` для кожного запиту EF Core) і відмовою від logging тіла запитів. Денний ліміт залиште як запасний захід, задавши рівень значно вище за звичайний обсяг.

## Інфраструктура як код у Azure

[Розділ 28](#chapter-28-cloud-fundamentals-aws-azure) порівнює Bicep, Terraform і Pulumi. Який би інструмент ви не обрали, для Azure важливо **розгортати ідентичність і призначення її ролей разом із ресурсом**, щоб доступ переглядали в тому самому pull request (запиті на злиття), що й ресурс, якому його надають:

```bicep
param location string = resourceGroup().location
param appName string

resource identity 'Microsoft.ManagedIdentity/userAssignedIdentities@2023-01-31' = {
  name: '${appName}-id'
  location: location
}

resource storage 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: toLower(replace('${appName}data', '-', ''))
  location: location
  sku: { name: 'Standard_ZRS' }
  kind: 'StorageV2'
  properties: {
    allowSharedKeyAccess: false          // identity only: keys and account SAS stop working
    allowBlobPublicAccess: false
    minimumTlsVersion: 'TLS1_2'
  }
}

// Storage Blob Data Contributor: a built-in role definition ID, the same in every tenant.
var blobDataContributor = subscriptionResourceId('Microsoft.Authorization/roleDefinitions', 'ba92f5b4-2d11-453d-a403-e96b0029c9fe')

resource blobAccess 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  scope: storage
  name: guid(storage.id, identity.id, blobDataContributor)   // deterministic: re-deploying is idempotent
  properties: {
    roleDefinitionId: blobDataContributor
    principalId: identity.properties.principalId
    principalType: 'ServicePrincipal'   // avoids a race with Entra replication right after the identity is created
  }
}

output identityClientId string = identity.properties.clientId
output blobEndpoint string = storage.properties.primaryEndpoints.blob
```

Запускайте `az deployment group what-if` у pull request, щоб рецензенти бачили, що саме буде змінено, зокрема видалення й заміну ресурсів, приховані звичайною різницею в шаблоні. Для циклу внутрішньої розробки **Azure Developer CLI** (`azd up`) створює інфраструктуру й розгортає код за одним шаблоном. У CI розгортайте через федерацію ідентичності workload з розділу *Ідентичність*, щоб не зберігати секрет.

## Витрати: частка розробника в рахунку

FinOps стосується кожного ([розділ 31](#chapter-31-compliance-data-privacy-cloud-cost-finops)), але деякі витрати визначаються кодом, і помітити це може лише розробник:

| Рішення в коді або конфігурації | Механізм витрат |
|---|---|
| Ключ секції Cosmos DB, політика індексування, міжсекційні запити | RU/s, які доводиться резервувати, щоб уникнути 429 |
| Рівень logging й розмір корисного навантаження | Приймання даних у Log Analytics оплачується за GB |
| Опитування замість events (таймер перевіряє blob, цикл заглядає в чергу) | Транзакції за кожну операцію та обчислення, що ніколи не засинають |
| Premium SKU з продакшену в кожному середовищі розробки й pull requests | Проста потужність рахується цілодобово |
| Вихідний трафік між регіонами чи в інтернет (часті виклики іншого регіону, передавання великих файлів без CDN) | Оплата пропускної здатності |
| Blob залишаються на рівні Hot без зміни класу | Безкінечне зберігання за найдорожчим тарифом |
| Залишки: диски видалених віртуальних машин, публічні IP, старі знімки, покинуті групи ресурсів | Чисте марнування; його виявляють теги й періодичний перегляд |

Встановіть **бюджет зі сповіщенням** для кожної підписки, додайте **теги** з власником до кожного ресурсу й зробіть тимчасові середовища зручними для видалення. Найдешевший ресурс — той, якого більше не існує.

## Самоперевірка: запитання в стилі іспиту

Спробуйте відповісти на кожне запитання, перш ніж відкрити відповідь. Вони поєднують основи AZ-900 із механізмами для розробників — так само, як робить хороший інтерв'юер.

**1.** Managed identity App Service призначено роль *Contributor* для облікового запису сховища, але `BlobClient.DownloadContentAsync` повертає 403 `AuthorizationPermissionMismatch`. Чому?

<details>
<summary>Відповідь</summary>

Contributor — це роль **площини керування**, у якій немає `DataActions`. Для читання blob за токеном Entra потрібна роль площини даних, наприклад *Storage Blob Data Reader* або *Storage Blob Data Contributor*, на рівні облікового запису чи контейнера. Якщо роль щойно призначили, також зачекайте до 10 хвилин, доки вона набуде чинності.
</details>

**2.** Запит проходить через Front Door (99.99%), App Service (99.95%) і Azure SQL (99.99%); потрібні всі три. Яке максимальне складене SLA можна заявити і що його підвищить?

<details>
<summary>Відповідь</summary>

Перемножте: 0.9999 × 0.9995 × 0.9999 ≈ **99.93%**. Додавання послідовних компонентів знижує доступність. Deployment пари App Service і SQL у другому регіоні за Front Door підвищить її, якщо кожного регіону достатньо окремо, аварійне перемикання справді працює, а для даних є механізм реплікації (наприклад, групи аварійного перемикання).
</details>

**3.** Потрібне фонове завдання, яке працює 45 хвилин раз на ніч. Які плани Functions можуть виконати його одним запуском, а які — ні?

<details>
<summary>Відповідь</summary>

План **Consumption** не може: його максимальний тайм-аут — 10 хвилин. **Flex Consumption**, **Premium** і **Dedicated** можуть: типовий тайм-аут у них 30 хвилин, тому задайте `functionTimeout`; його можна зробити необмеженим. Краще розділити роботу на повторно запускані частини (розгалуження Durable Functions або завдання Container Apps), щоб масштабування чи оновлення платформи не втратило 44 хвилини виконання.
</details>

**4.** Яка функція Service Bus гарантуватиме впорядковану обробку всіх events одного клієнта, поки events інших клієнтів обробляються паралельно?

<details>
<summary>Відповідь</summary>

**Сеанси:** задайте `SessionId` як ID клієнта в queue чи підписці, де сеанси мають бути ввімкнені. Кожен сеанс блокується за одним одержувачем і передається йому у порядку FIFO, а різні сеанси паралельно надходять різним одержувачам.
</details>

**5.** Виявлення дублікатів увімкнено з десятихвилинним вікном. Чи безпечно це для списання коштів із кредитної картки без перевірки ідемпотентності?

<details>
<summary>Відповідь</summary>

**Ні.** Виявлення дублікатів відкидає повторно *надіслане* повідомлення з тим самим `MessageId` у межах вікна. Воно нічого не робить із *повторною доставкою* одного повідомлення consumer: після завершення блокування, аварійного завершення до `Complete` чи скасування. Consumer мають бути ідемпотентними.
</details>

**6.** Ключ секції контейнера — `/status`, що має три значення. Для контейнера зарезервовано 30,000 RU/s, але він обмежує пропускну здатність за навантаження приблизно 10,000 RU/s. Поясніть.

<details>
<summary>Відповідь</summary>

Одна логічна секція (одне значення `status`) розміщується в одній фізичній секції, яка обслуговує не більш ніж 10,000 RU/s. Якщо більшість трафіку припадає на одне чи два значення стану, навантаження не розподілиться, скільки б ви не зарезервували: це гаряча секція. Потрібен ключ із високою кардинальністю, який входить до основних запитів, — отже, дані доведеться перенести в новий контейнер.
</details>

**7.** У чому різниця між Azure Policy і RBAC? Наведіть приклад кожного.

<details>
<summary>Відповідь</summary>

RBAC контролює **хто** може виконувати дії («ідентичність CI може розгортати ресурси в цій групі»). Policy контролює, **який стан** дозволений для ресурсів незалежно від їхнього автора («публічний мережевий доступ до сховищ має бути вимкненим», «дозволені лише Західна й Північна Європа»). Користувача з повними правами RBAC однаково може зупинити політика `Deny`.
</details>

**8.** Ви ввімкнули приватний endpoint Key Vault і вимкнули публічний доступ. Тепер застосунок отримує 403 «публічний мережевий доступ вимкнено». Що й як перевірити насамперед?

<details>
<summary>Відповідь</summary>

**DNS.** У застосунку (Kudu/SSH) виконайте `nslookup <vault>.vault.azure.net`. Якщо відповідь містить публічну IP-адресу, приватної зони DNS `privatelink.vaultcore.azure.net` немає, її не пов'язано з VNet застосунку або власні DNS-сервери не пересилають запити до Azure DNS. Також перевірте наявність у застосунку інтеграції з VNet: без неї його вихідні запити не потрапляють до VNet.
</details>

**9.** Назвіть три онлайнові рівні доступу до blob, один офлайновий і нюанс переміщення даних у Cool наступного дня після запису.

<details>
<summary>Відповідь</summary>

Hot, Cool і Cold — онлайнові. Archive — офлайновий, його потрібно відновити (до 15 годин зі стандартним пріоритетом). Є вимога мінімального строку зберігання (30 днів для Cool, 90 для Cold, 180 для Archive): дострокове видалення, перезапис або повторна зміна рівня спричиняє плату. Зміна рівня окупається, лише якщо дані справді залишаються незмінними.
</details>

**10.** Чому створювати `new DefaultAzureCredential()` у дії контролера — це помилка, хоча код працює?

<details>
<summary>Відповідь</summary>

У кожного екземпляра власний кеш токенів, тож кожен запит отримує новий токен: це додає затримку й може призвести до rate limiting endpoint ідентичності. На неправильно налаштованому хості кожен запит ще й проходить увесь ланцюжок credentials. Створюйте credentials й клієнти SDK один раз як singleton.
</details>

**11.** Endpoint webhook, підписаний на Event Grid, відповідає `200 OK` на все, але підписка лишається в стані помилки налаштування й events не надходять. Чому?

<details>
<summary>Відповідь</summary>

Endpoint не завершив **рукостискання перевірки**. Event Grid надсилає `SubscriptionValidationEvent`, а endpoint має повернути в тілі відповіді його `validationCode` (або хтось має викликати `validationUrl`). Відповідь `200` без коду не підтверджує володіння endpoint.
</details>

**12.** Який варіант тарифікації підійде стабільній виробничій базі даних, що працюватиме наступні три роки, а який — перериваному нічному пакетному завданню візуалізації?

<details>
<summary>Відповідь</summary>

Для бази — **резервування на 3 роки**: найбільша знижка за фіксовану базову потужність. Для завдання — потужність **Spot**: значна знижка в обмін на можливе переривання, яке витримає перезапускане пакетне завдання.
</details>

**13.** Команда видаляє й повторно створює Key Vault `kv-shop-dev` під час кожного тестового запуску, але другий запуск завершується помилкою «ім'я сховища вже використовується». Чому?

<details>
<summary>Відповідь</summary>

**Програмне видалення:** видалене сховище резервує ім'я протягом строку зберігання (7–90 днів). Після видалення остаточно очистьте його (лише якщо захист від очищення вимкнений, що припустимо для dev) або задавайте унікальну назву для кожного запуску.
</details>

**14.** Розробник стверджує, що керованій Azure SQL не потрібна логіка retries. Що відповісте?

<details>
<summary>Відповідь</summary>

«Керована» означає, що *Azure* виконує перемикання, встановлює виправлення й масштабує базу, а кожна така операція на кілька секунд створює тимчасові помилки (40613, 40197, 40501 тощо). Microsoft рекомендує кожному хмарному застосунку повторювати тимчасові помилки підключення; для безсерверних баз це ще важливіше через відновлення після автопаузи. Увімкніть `EnableRetryOnFailure`, а явні транзакції обгорніть у стратегію виконання».
</details>

**15.** Яка служба messaging підходить для кожного випадку: (a) 200 000 показників пристроїв за секунду, які незалежно читають три команди; (b) «зарезервувати товар для замовлення 42»; (c) «запускати функцію щоразу, коли файл потрапляє в контейнер `invoices`»?

<details>
<summary>Відповідь</summary>

(a) **Event Hubs**: секціонований журнал із групою consumers для кожної команди й повторним читанням у межах строку зберігання. (b) **Service Bus**: команда для одного з кількох конкуруючих consumers, із peek-lock, dead-letter queue і, можливо, сеансами. (c) **Event Grid** (системний event `BlobCreated`), напряму доставлений функції або через queue Service Bus для буферизації й retries.
</details>

## Підсумок

Azure організовано ієрархічно: клієнт, групи керування, підписки, групи ресурсів і ресурси. Усім керують через один API — ARM. RBAC визначає *хто*, Policy — *що*, а блокування захищають ресурси, але не дані. Важливо пам'ятати розрізнення **площини керування й площини даних**: керувати ресурсом і використовувати його — різні дозволи.

Основою є ідентичність. Managed identities замінюють секрети. `DefaultAzureCredential` зручний для розробки, а в продакшені треба вказувати credentials явно. Призначення ролей поширюються із затримкою, а ролі площини даних Cosmos DB відрізняються від ролей інших служб. Коли ідентичність запрацює, вимкніть ключі.

Для вебнавантажень типовим вибором обчислень є App Service: вивчіть послідовність перемикання слотів, ліміт 230 секунд і порти SNAT. Functions призначені для events: використовуйте ізольований процес у Flex Consumption, пам'ятайте, що масштабування збільшує паралельність, і робіть оркестратори Durable детермінованими. Container Apps запускає контейнерні системи без потреби керувати кластером. Для даних Blob Storage потребує правильного вибору надлишковості, рівнів зберігання, SAS делегування користувача й ETag. Cosmos DB — рішення про секціонування з ціною за кожну операцію. Azure SQL — це SQL Server із перемиканнями, тож потрібні retries. Service Bus, Event Hubs і Event Grid — три різні інструменти: команди, потоки й сповіщення. Усі вони доставляють повідомлення щонайменше один раз.

Навколо цього — Key Vault і App Configuration (завантажуйте один раз, оновлюйте свідомо), приватні endpoints (їхні збої майже завжди спричиняє DNS), Application Insights (вибірка й KQL), інфраструктура як код із призначенням доступу в тому самому pull request, що й ресурс, і витрати, помітити які може лише розробник. У [розділі 30](#chapter-30-the-azure-casebook-real-incidents-real-fixes) усе це застосовується в продакшені й ламається.

Потім запустіть тести, які відтворюють кожен дефект у помилковому коді та його відсутність у виправленому, проти Azurite й емулятора Service Bus ([`verify/exercises/Ch51`](https://github.com/malyna2/dotnet-handbook/tree/main/verify/exercises/Ch51); потрібні SDK .NET 10 і Docker, обидва емулятори мають ліцензійні угоди):

```bash
ACCEPT_EULA=Y verify/exercises/Ch51/verify.sh
```

**2. Дві вправи *Що б ви зробили* з розділу 30 (45 хвилин).** Перш ніж читати відповідь, підготуйте рішення на одну сторінку для другого випадку — служби обробки документів: обчислювальна платформа, шлях в обхід ліміту 230 секунд, масштабування й обмеження, ідентичність і обставина, яка змусила б вас змінити рішення. Перший випадок — «просто надайте застосунку Owner» — допомагає сформулювати відповідь під тиском дедлайну.

**3. Pipeline deployment з недорогим відкатом (2 год 30 хв).** Він спирається на [повний робочий процес GitHub Actions для .NET](#a-complete-github-actions-workflow-for-net) із розділу 13 (або [Azure Pipelines на практиці](#azure-pipelines-in-practice) із розділу 26) і стратегії deployment та перемикачі функцій із [розділу 26](#chapter-26-delivery-and-platform). Візьміть один із цих pipelines і розширте для однієї служби:

- зберіть і перевірте один раз, опублікуйте один незмінний артефакт і просувайте його між середовищами без повторної збірки;
- увійдіть в Azure за допомогою федерації ідентичності workload, щоб pipeline не зберігав секрет;
- розгорніть на тестовий слот, прогрійте його health check, який звертається до бази даних, перемкніть слот і виконайте відкат повторним перемиканням;
- винесіть міграції в контрольований крок, застосовуючи розширення, а потім скорочення, щоб попередня збірка працювала з новою схемою;
- сховайте одну зміну за перемикачем функції й випустіть її без deployment.

Завдання виконано, коли ви можете показати відкат за лічені хвилини й відсутність збережених секретів. У кроках 4 і 8 капстоуна з [розділу 44](#chapter-44-capstone-one-project-growing-up) використовується той самий шлях.

Pipeline, записку з рішенням і нотатки зберігайте у **власному публічному репозиторії портфоліо**, а не тут; відомості про систему реального роботодавця залишайте приватними.

## Три запитання

**1.** API в App Service викликає публічний API партнера. Під навантаженням виникають періодичні тайм-аути підключень, а CPU завантажений на 30%. Масштабування з 2 до 4 екземплярів усуває тайм-аути на кілька тижнів. Чому масштабування «допомагає», чому проблема повертається й що є справжнім виправленням?

<details>
<summary>Відповідь</summary>

- **Механізм.** Кожне нове вихідне підключення до публічної адреси використовує порт SNAT. Екземпляр має 128 попередньо виділених портів на призначення, і звільнений порт повертається в пул лише за чотири хвилини. Межа стосується кількості нових підключень за чотири хвилини, для кожного екземпляра й адресата, тож CPU й пам'ять у нормі. Новий `HttpClient`, підключення SQL без пулу або клієнт SDK на кожен запит створюють нове підключення на запит.
- **Чому допомагає horizontal scaling.** Кожен екземпляр має власний пул портів: удвічі більше екземплярів — удвічі більший бюджет. Трафік зростає разом із цим бюджетом, і тайм-аути повертаються, але рахунок уже більший.
- **Виправлення в правильному порядку.** Повторно використовуйте підключення (`IHttpClientFactory` або один довготривалий клієнт, singleton-клієнти SDK), щоб у звичайному режимі вистачало кількох портів. Використовуйте приватні endpoints для служб Azure: їхній трафік залишається в межах VNet і оминає SNAT. Додайте NAT gateway (64 512 портів на публічну IP) лише тоді, коли кількість справді нових підключень однаково перевищує бюджет. Перевірте результат у *Діагностика й усунення проблем → Вичерпання портів SNAT*.
</details>

**2.** Застосунок Functions із тригером Service Bus спорожнює великий queue імпорту, а спільна база Azure SQL, яку використовує checkout, починає повертати помилку 10928. Поясніть механізм і скажіть, що зміните.

<details>
<summary>Відповідь</summary>

- **Паралельність = кількість екземплярів × паралельність на екземпляр.** Тригер обробляє до `maxConcurrentCalls` повідомлень на екземпляр (типово 16, фактично — на кожне ядро), а платформа масштабується за глибиною queue. Десятки екземплярів перетворюються на понад тисячу одночасних виконань, кожне з підключенням і сеансом.
- **У бази даних є верхня межа.** 10928 означає досягнення ліміту робочих потоків: імпорт зайняв усі, і checkout завершується помилкою в тій самій базі.
- **Виправлення.** Обмежте `maxConcurrentCalls` у `host.json` і максимальну кількість екземплярів; оберіть їх добуток за лімітом бази з резервом для checkout. Об'єднуйте записи в пакети (одне мережеве звернення на пакет). Ізолюйте навантаження: окрема база, еластичний пул із лімітами на базу чи часовий проміжок.
- **Принцип.** Queue вирівнює навантаження лише тоді, коли consumer спорожнюють її з обмеженою швидкістю. Необмежені consumer перетворюють її на лінію затримки перед тим самим перевантаженням.
</details>

**3.** Команда вважає, що завжди може виконати відкат, повторно розгорнувши попередню збірку. Назвіть три зміни, через які це стане неможливим, і що допомагає здешевити відкат.

<details>
<summary>Відповідь</summary>

- **Зміна схеми, з якою стара збірка несумісна:** видалений або перейменований стовпець, новий стовпець `NOT NULL`. Спочатку розширюйте схему, потім скорочуйте: додайте nullable-стовпець, заповніть його, перемкніть код, а стару структуру видаліть у наступному випуску ([розділ 18](#chapter-18-data-in-depth)).
- **Зміна контракту, від якої вже залежать інші:** перейменоване поле відповіді чи властивість повідомлення. Відкат видавця не відкликає повідомлення з queues, а consumer могли розгорнутися з новою формою. Робіть зміни додавальними (розширення–скорочення для API, [розділ 22](#chapter-22-api-evolution-real-time-and-serialization)) і навчіть читачів бути толерантними.
- **Змінені параметри й дані:** параметр, який не закріпили за слотом, перемістився разом зі збіркою в продакшен (розділ 30, кейс 4), або міграція перезаписала рядки. Закріплюйте параметри середовища за слотом; міграції даних робіть ідемпотентними, а заздалегідь визначте, чи можна їх скасувати, чи потрібно виправляти проблему вперед.

Відкат здешевлюють незмінний артефакт, відокремлення випуску від deployment перемикачем (тоді багато відкатів — це перемикання прапорця), схема, сумісна з попередньою збіркою протягом одного випуску, і відпрацьований заздалегідь сценарій відкату.
</details>

## Вирішіть

Orders (App Service) викликає Pricing (Container Apps). Обидві служби належать вашій команді й містяться в одній VNet. Наразі Pricing перевіряє спільний ключ API, який обидві служби читають із Key Vault. Перевірка безпеки вимагає «перейти до zero trust (нульової довіри)» цього кварталу. Що робити?

- **A.** Залишити ключ, щомісяця оновлювати його й обмежити вхідний трафік Pricing мережею VNet.
- **B.** Managed identity і Entra ID: Orders запитує токен для URI ідентифікатора застосунку Pricing через власний managed identity; Pricing перевіряє токен і авторизує за роллю застосунку, призначеною ідентичності Orders.
- **C.** Перенести обидві служби в AKS із service mesh, використати mTLS і політики авторизації mesh.

<details>
<summary>Відповідь</summary>

**Ціна кожного варіанта.**
- **A** — найдешевша зміна, яка зберігає модель «замок і рів»: будь-що в VNet, що має ключ, *є* Orders; викрадений ключ працює до наступної ротації, а кожна ротація ризикує зупинити продакшен (розділ 30, кейс 13). Перевірці безпеки ви відповідаєте графіком, а не архітектурою.
- **B** потребує реєстрації Pricing із роллю застосунку, призначення ролі ідентичності Orders (адміністратора з правом надання), перевірки токена в Pricing і часу на поширення під час першого deployment (ідентичність, призначена користувачу й створена заздалегідь, усуває затримку). Це прибирає секрет, видає короткостроковий токен для кожного викликача й дозволяє Pricing окремо авторизувати кожного.
- **C** потребує кластера й mesh, які доведеться обслуговувати, — повної відповідальності за Kubernetes — для розв'язання проблеми автентифікації двох служб. mTLS автентифікує службу, а не користувача, тож для контексту користувача все одно знадобиться авторизація за токеном.

**Що визначає вибір тут:** наявна платформа й розмір системи. Для двох служб в App Service і Container Apps уже є ідентичності, підтверджені платформою; її власний механізм буде найдешевшим правильним варіантом.

**Вибір: B.** Потім вимкніть ключ API, щоб система не могла перейти на нього як на резервний варіант.

**Що могло б змінити вибір.** Десятки служб у Kubernetes із командою платформи: mesh для mTLS між workloads, а токени як у B — для авторизації. Викликач поза Azure: федерація ідентичності workload з власним постачальником ідентичності, так само без спільного секрету.
</details>

## Перевірте на роботі

**Огляньте.** Застосуйте картку сортування з розділу 30 до однієї власної служби. Від якої ідентичності працює застосунок у кожному середовищі — декодуйте `oid` токена чи перелічіть призначення ролей цієї ідентичності — і чи залишилися в його параметрах ключі або connection strings із секретами? Чи розпізнає застосунок приватні IP-адреси всіх приватних endpoints? Які параметри закріплені за слотами? Для кожного consumer queue перемножте паралельність на екземпляр і їх максимальну кількість, а потім порівняйте з лімітом бази даних нижчого рівня.

**Виміряйте.** Час від запиту «виконай відкат» до повернення попередньої версії для користувачів — за останнього реального відкату. Якщо відкатів не було, заплануйте репетицію: невипробуваний відкат — це лише надія. У App Service також відкрийте *Діагностика й усунення проблем → Вичерпання портів SNAT* для застосунку з найбільшим навантаженням.
