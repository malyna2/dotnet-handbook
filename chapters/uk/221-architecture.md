# Розділ 21: архітектура

Можна писати правильний код і водночас створити систему, яку нестерпно змінювати. Правильність відповідає на запитання, чи повертає окрема функція правильну відповідь; архітектура — чи займе нова функція пів дня або два тижні через шість місяців. Архітектура — це заздалегідь визначена вартість змін: кожна межа здешевлює зміни з одного боку й ускладнює їх через межу. Цей розділ допоможе розміщувати межі там, де частини бізнесу змінюються незалежно, обирати між модульним монолітом і мікросервісами з чітким описом вартості кожного варіанта, захищати рішення під час архітектурного перегляду й документувати його, щоб наступна команда розуміла причину.

[Розділ 10](#chapter-10-design-basics) охоплював основи на рівні коду: SOLID, поширені шаблони, Repository і Unit of Work, багаторівневу архітектуру та Clean Architecture. Тут вони стають рішеннями на рівні системи. Розділ починається з двох чинників, між якими доводиться шукати компроміс: зв’язності й цілісності; далі розглядає межі домену (агрегати DDD і обмежені контексти, шаблон Specification для правил запитів), розмежування моделі запису й читання (CQRS і зберігання events (подій)), архітектурні стилі з іншими межами (вертикальні зрізи, модульний моноліт, мікросервіси) і, насамкінець, край системи, де клієнти взаємодіють із сервісами (шлюзи й BFF). Коли межа стає мережевою, до справи береться [Розділ 20](#chapter-20-distributed-systems); розвиток контрактів, які її перетинають, розглянуто в [Розділі 22](#chapter-22-api-evolution-real-time-and-serialization).

«Правильної» архітектури не існує — є лише архітектури, що відповідають певним чинникам: розміру команди, темпу deployment (розгортання), складності домену й рівню невизначеності. У кожному розділі запитуйте себе про єдине важливе: *яку проблему це розв’язує і чи справді ця проблема є у мене?*

## Чому важлива архітектура: зв’язність і цілісність

Зрештою кожне обговорення архітектури зводиться до двох понять: **зв’язність** і **цілісність**. Опануйте їх — і все інше стане коментарями.

**Цілісність** показує, наскільки елементи модуля належать одне одному. Клас `OrderProcessor`, який перевіряє замовлення, стягує оплату й надсилає електронні листи, має *низьку* цілісність: у ньому зібрано три не пов’язані між собою відповідальності. Розділіть їх, щоб кожна одиниця добре виконувала одну задачу, і цілісність зросте.

**Зв’язність** показує, наскільки модуль залежить від внутрішньої будови іншого. Якщо зміна структури таблиці бази змушує редагувати контролери HTTP, ці компоненти тісно зв’язані. Тісна зв’язність — тиха вбивця програмного забезпечення: мала зміна спричиняє каскад правок, а міркувати про одну частину без усієї системи в голові стає неможливо.

> **Золоте правило: висока цілісність, низька зв’язність.** Пов’язані речі тримайте разом, а не пов’язані мають змінюватися незалежно. Майже кожен архітектурний шаблон у цьому розділі — конкретний спосіб досягнути цієї мети.

Аналогія — добре впорядкована кухня. Ножі лежать разом (цілісність), а перестановка полиці зі спеціями не потребує переміщення холодильника (низька зв’язність). У погано впорядкованій кухні виделки лежать у трьох шухлядах, і заради солі треба спорожнити комору. Програмне забезпечення руйнується так само — по одній необережній залежності.

Зв’язність не буває лише «є» чи «немає»; є різновиди — від найгірших до найменш шкідливих:

- **Зв’язність за вмістом** — модуль проникає у приватні дані іншого. Цього слід повністю уникати.
- **Загальна зв’язність** — модулі використовують спільний змінний глобальний стан. Це крихко.
- **Керувальна зв’язність** — модуль передає прапорець, що визначає потік керування іншого (`DoThing(isPreview: true)`).
- **Зв’язність даних** — модулі спілкуються лише через прості параметри. Це мета.

Наслідки невдалого вибору накопичуються. ПЗ, яке легко змінювати, виграє в довгостроковій перспективі не завдяки елегантності, а тому, що бізнес змінює думку, і виживає система, яка здатна підлаштуватися.

## Розробка, орієнтована на домен

Domain-Driven Design (DDD) — радше філософія, ніж архітектура: поставте **домен** — реальну бізнес-проблему — у центр проєктування, а код нехай розмовляє мовою бізнесу. DDD охоплює *стратегічне* проєктування (межі на загальному рівні) і *тактичне* (будівельні блоки всередині межі).

### Єдина мова

Усе починається з **єдиної мови** — спільного точного словника, яким однаково послуговуються фахівці домену й розробники, в розмові *та* в коді. Якщо бізнес каже: «Поліс вважається *простроченим*, коли страховий внесок прострочено на 30 днів», у коді має бути поняття `Lapsed`, а не магічне `status == 3`. Єдина мова усуває дорогу трансляцію між значенням бізнес-правила й поведінкою програми.

### Тактичні будівельні блоки

**Сутності** мають ідентичність, яка зберігається з часом. `Customer` залишається тим самим клієнтом, навіть коли змінює ім’я й адресу. Рівність визначає ID, а не атрибути.

```csharp
public sealed class Customer   // Entity: identity matters
{
    public CustomerId Id { get; }
    public string Name { get; private set; }
    public void Rename(string newName) { /* invariants enforced here */ }
}
```

**Об’єкти-значення** не мають ідентичності — їх повністю визначають незмінні значення. Це можуть бути гроші, діапазон дат або адреса. Два екземпляри `Money(10, "USD")` взаємозамінні. Для цього природно підходять типи записів C# (`record`).

```csharp
public sealed record Money(decimal Amount, string Currency)
{
    public Money Add(Money other)
    {
        if (other.Currency != Currency) throw new InvalidOperationException("Currency mismatch");
        return this with { Amount = Amount + other.Amount };
    }
}
```

> **Рекомендація:** активно використовуйте об’єкти-значення. Заміна звичайних `decimal` і `string` на `Money` й `EmailAddress` переносить перевірку до системи типів: буквально неможливо створити неправильне значення, а самодокументованість домену зростає.

**Агрегати й корені агрегатів.** Агрегат — це група об’єктів, яку під час зміни даних розглядають як єдине ціле. **Корінь агрегату** — єдина сутність, через яку мають відбуватися всі зовнішні звернення; вона забезпечує виконання інваріантів усієї групи. Корінь `Order` містить об’єкти `OrderLine`. Ззовні ніколи не змінюють `OrderLine` безпосередньо — викликають `order.AddLine(...)`, а `Order` гарантує правила на кшталт «сума не перевищує кредитний ліміт».

```csharp
public sealed class Order   // Aggregate Root
{
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();
    public Money Total => _lines.Aggregate(Money.Zero, (sum, l) => sum.Add(l.Subtotal));

    public void AddLine(ProductId product, int qty, Money unitPrice)
    {
        if (qty <= 0) throw new DomainException("Quantity must be positive.");
        _lines.Add(new OrderLine(product, qty, unitPrice));   // invariant guarded by the root
    }
}
```

> **Межа агрегату одночасно є межею транзакції й consistency (узгодженості).** Одна транзакція має змінювати один агрегат. Агрегати мають бути малими: великі агрегати створюють конкуренцію за блокування й завантажують до пам’яті цілі графи об’єктів. Координуйте взаємодію двох агрегатів через *consistency із часом* і доменні events, а не однією величезною транзакцією; між сервісами така координація стає сагою ([Розділ 20](#chapter-20-distributed-systems)).

**Доменні events** фіксують значущі events домену: `OrderPlaced`, `PaymentFailed`. Їх створює агрегат, а handlers (обробники) в інших частинах системи реагують на них. Це відокремлює «що сталося» від «що робити далі».

```csharp
public sealed record OrderPlaced(OrderId OrderId, CustomerId CustomerId, DateTime OccurredAt);
```

**Репозиторії** надають кореням агрегатів схоже на колекцію представлення сховища — по одному репозиторію на агрегат, ніколи не на таблицю. `IOrderRepository`, а не `IOrderLineRepository`. Інтерфейс належить домену, реалізація — інфраструктурі (Clean Architecture із [Розділу 10](#chapter-10-design-basics)).

### Стратегічне проєктування: обмежені контексти

Ось думка, що відрізняє досвідчене володіння DDD від початкового. У різних частинах бізнесу слово «клієнт» означає різні поняття. Для відділу продажів Customer — це потенційний клієнт зі стадією продажу. Для доставки — адреса й уподобання щодо доставлення. Для виставлення рахунків — спосіб оплати й кредитний ліміт. Спроба помістити їх усіх в універсальний клас `Customer` створює роздуту й суперечливу модель, яку ніхто не може безпечно змінювати.

**Обмежений контекст** — явна межа, у межах якої послідовно застосовується певна модель і єдина мова. У контексті Sales слово «клієнт» має значення продажу, і крапка. У різних контекстах може бути власний `Customer`, а з’єднуються вони через чітко визначені контракти (ці зв’язки, як-от спільне ядро, відносини замовник/постачальник і антикорупційний шар, описує *карта контекстів*).

```
   Sales Context           Shipping Context          Billing Context
+----------------+       +------------------+      +------------------+
|  Customer      |       |  Customer        |      |  Customer        |
|  (lead, stage) | <---> |  (address, pref) |<---> |  (credit, cards) |
|  Opportunity   |       |  Shipment        |      |  Invoice         |
+----------------+       +------------------+      +------------------+
      each context owns its own model & language
```

> **Обмежені контексти — найцінніша ідея DDD і, що не дивно, природні межі для майбутнього поділу на мікросервіси.** Правильно визначте їх — і все подальше стане простішим. **Антикорупційний шар** — проміжок перекладу на межі контекстів, що не дає моделі іншої команди проникнути до вашої й забруднити її.

## Шаблон Specification

Репозиторії ([Repository і Unit of Work представлені в Розділі 10](#chapter-10-design-basics)) порушують запитання, щойно в домені з’являються правила про те, *які* об’єкти відповідають умовам: де має жити це правило? Шаблон Specification упаковує запит або бізнес-правило в повторно використовуваний комбінований об’єкт. Він усуває проблему дублювання й розпорошення логіки запитів (`IsActive && SignedUpBefore(x)`).

```csharp
public interface ISpecification<T>
{
    Expression<Func<T, bool>> ToExpression();
}

public sealed class ActiveCustomerSpec : ISpecification<Customer>
{
    public Expression<Func<Customer, bool>> ToExpression() => c => c.IsActive;
}

public sealed class PremiumCustomerSpec : ISpecification<Customer>
{
    public Expression<Func<Customer, bool>> ToExpression() => c => c.TotalSpent > 10_000m;
}

// Because they return expressions, EF Core can translate them to SQL.
var spec = new ActiveCustomerSpec();
var activeCustomers = await dbContext.Customers
    .Where(spec.ToExpression())
    .ToListAsync();

public record Customer(bool IsActive, decimal TotalSpent);
```

Оскільки спецификации повертають `Expression<Func<T, bool>>`, EF Core перетворює їх на SQL, і правило виконується в базі даних, а не в пам’яті. Реальні реалізації (популярна бібліотека **Ardalis.Specification**) дають змогу поєднувати специфікації через `And`/`Or`, а також інкапсулювати `Include`, сортування й пагінацію. Specification природно поєднується з Repository: `GetAsync(ISpecification<T> spec)` надає один гнучкий метод запиту замість десятків іменованих.

## CQRS і зберігання events

### CQRS

**Command Query Responsibility Segregation** ґрунтується на простому спостереженні: потреби зміни даних і читання даних різні. Записи відповідають за інваріанти, перевірку й consistency. Читання — за швидкість і форму: часто їм потрібні денормалізовані дані, вже підготовлені для екрана. CQRS пропонує використовувати для цього окремі моделі.

У найпростішому вигляді CQRS — це лише домовленість у коді: команди (повертають void чи ID і спричиняють побічні ефекти) та запити (повертають дані й не спричиняють побічних ефектів) проходять через різні handlers. Бібліотеки на кшталт MediatR роблять такий підхід зручним.

```csharp
public sealed record PlaceOrderCommand(CustomerId CustomerId, IReadOnlyList<CartLine> Lines)
    : IRequest<OrderId>;

public sealed record GetOrderSummaryQuery(OrderId Id) : IRequest<OrderSummaryDto>;
```

MediatR — це диспетчер у межах одного процесу з pipeline (конвеєром) ([у Розділі 10 його подано як шаблон Mediator](#chapter-10-design-basics)): він відокремлює контролер від handler та надає єдине місце для наскрізної поведінки (перевірки, logging (журналювання), транзакції). Сам собою MediatR **не** забезпечує CQRS. Команди й запити через MediatR можуть і далі використовувати ту саму модель сутностей і `DbContext`; поки ви не створите сховище читання, ви не отримаєте його, масштабування чи гарантії consistency.

> **Примітка щодо ліцензування.** У квітні 2025 року MediatR оголосив про комерційну ліцензію для нових основних версій (наявні версії лишаються з open source (відкритим кодом)); у розділі Mediator [Розділу 10: Основи проєктування](#chapter-10-design-basics) наведено докладну примітку й альтернативи. Перевірте умови, перш ніж зробити MediatR типовою залежністю.

Зауважте, чого не вимагає спрощена версія: окремих баз даних, зберігання events чи consistency із часом. Це розширені варіанти для систем, у яких потреби читання й запису справді розійшлися.

У найповнішому варіанті CQRS використовує *фізично окремі сховища*: записи проходять через багату доменну модель агрегатів у нормалізовану транзакційну базу даних; процес проєкції оновлює денормалізоване сховище читання (наприклад, документну базу чи набір плоских таблиць), оптимізоване для запитів. Модель читання узгоджується з моделлю запису із часом і часто отримує дані з того самого outbox чи потоку CDC, що й інші consumer (споживачі) ([Розділ 18](#nosql-and-polyglot-persistence) розглядає її серед інших сховищ).

```
  Command --> Write Model (aggregates) --> Write DB
                     |
                 publishes events
                     v
             Projection Handler --> Read DB --> Query --> DTO
```

> **Компроміс:** повний CQRS з окремими сховищами забезпечує незалежне масштабування читань, спеціально сформовані моделі запитів і позбавляє необхідності перекручувати одну модель ORM заради складної форми редагування й панелі моніторингу. Ціна значна: потрібно синхронізувати дві моделі даних, інтерфейс має враховувати consistency із часом, а експлуатація стає складнішою. **Почніть із легкого розділення команд і запитів. Переходьте до окремого сховища читання, лише коли справді розійшлися потреби масштабування чи моделювання читань і записів.** Не застосовуйте важкий CQRS типово — це один із найбільш надмірно вживаних шаблонів.

### Зберігання events

Зберігання events — окрема ідея, яку часто поєднують із CQRS. Замість збереження *поточного стану* сутності з перезаписуванням після кожної зміни зберігайте *повну послідовність events*, що привела до цього стану. Поточний стан обчислюється згорнутим проходом (повторним відтворенням) events.

Уявіть банківський рахунок. Традиційна система зберігає `Balance = 120`. Система зі зберіганням events зберігає історію:

```
Event Stream for Account #A-1001
--------------------------------------------------
1. AccountOpened        { owner: "Ivy",  at: 09:00 }
2. MoneyDeposited       { amount: 100,   at: 09:05 }
3. MoneyDeposited       { amount: 50,    at: 10:12 }
4. MoneyWithdrawn       { amount: 30,    at: 11:40 }
--------------------------------------------------
Current balance = 0 + 100 + 50 - 30 = 120   (replayed)
```

```csharp
public Account Rehydrate(IEnumerable<object> events)
{
    var account = new Account();
    foreach (var e in events) account.Apply(e);   // fold events into state
    return account;
}
```

Events — джерело істини, а поточний стан похідний. Це забезпечує повний audit log (журнал аудиту), подорож у часі («який баланс був минулого вівторка?») і дає змогу будувати нові проєкції читання постфактум повторним відтворенням історії.

> **Зберігання events — потужний підхід, який потрібен рідко.** Витрати високі: еволюція схеми старих events, створення знімків заради продуктивності, зміна підходу всієї команди та неможливість «просто виправити рядок». Використовуйте його там, де audit log *і є продуктом* — фінанси, відповідність нормативним вимогам, реєстри запасів, — а не тому, що підхід звучить складно. І пам’ятайте: **CQRS не потребує зберігання events, як і зберігання events не потребує CQRS**, хоча вони природно поєднуються.

## Архітектура вертикальних зрізів

Багаторівнева й чиста архітектури ([Розділ 10](#chapter-10-design-basics)) упорядковують код *горизонтально* за технічною відповідальністю: контролери тут, сервіси там, репозиторії десь іще. Щоб додати одну функцію, потрібно торкнутися файлів кожного рівня, а не пов’язані функції ділять між собою роздуті класи служб (низька цілісність, пам’ятаєте?).

**Архітектура вертикальних зрізів** змінює напрям. Код упорядковують за *функціями*. Кожен зріз містить усе потрібне — endpoint (кінцеву точку), запит і відповідь, handler, перевірку й доступ до даних, — часто в одній папці чи навіть файлі.

```
Features/
  Orders/
    PlaceOrder/
      PlaceOrderCommand.cs
      PlaceOrderHandler.cs
      PlaceOrderValidator.cs
      PlaceOrderEndpoint.cs
    GetOrderSummary/
      GetOrderSummaryQuery.cs
      GetOrderSummaryHandler.cs
```

Філософія така: **максимізуйте цілісність функції й мінімізуйте зв’язність між функціями**. Кожен зріз обирає власний підхід: простий запит може напряму звертатися до бази, а складна команда — використовувати повні доменні агрегати. Вам більше не потрібно примушувати всі функції проходити однакові абстракції.

> **Компроміс:** вертикальні зрізи спрощують додавання, видалення й ізольований розгляд функцій — усі зміни однієї функції охоплюють одну папку. Ризик — дублювання й розбіжність між зрізами, а також менша кількість обов’язкових структур. Вони чудово поєднуються з CQRS/MediatR. Багато сучасних команд .NET поєднують їх із Clean Architecture: зрізи на рівні застосунку, а нижче — спільне ядро домену.

## Моноліт, мікросервіси й модульний моноліт

### Спектр архітектур

**Моноліт** — це єдина одиниця deployment. Усі модулі виконуються в одному процесі, використовують одну базу даних і випускаються разом. **Архітектура мікросервісів** розділяє систему на малі сервіси, які можна розгортати незалежно; кожен володіє власними даними й спілкується з мережею. **Модульний моноліт** посідає проміжне місце: одна одиниця deployment, але всередині — суворо розділені модулі з примусовими межами й, бажано, окремими схемами.

```
 Monolith            Modular Monolith           Microservices
+----------+       +---------------------+     +------+ +------+ +------+
|          |       | [Mod A][Mod B][Mod C]|     | Svc A| | Svc B| | Svc C|
|  one big |       |  strict boundaries   |     |  +DB | |  +DB | |  +DB |
|  blob    |       |  one deployable      |     +------+ +------+ +------+
+----------+       +---------------------+       network calls between
  one DB               one DB (schemas)
```

### Компроміси

Мікросервіси часто продають як *єдину* сучасну архітектуру. Обравши їх із хибних причин, ви заміните виклики методів у процесі (швидкі, транзакційні, легко налагодити) мережевими викликами (повільними, ненадійними, узгодженими із часом і складними для tracing (трасування)). Вам дістануться проблеми distributed systems (розподілених систем) ([Розділ 20](#chapter-20-distributed-systems)): часткові збої, розділення мережі, розподілені транзакції, версіювання контрактів ([Розділ 22](#chapter-22-api-evolution-real-time-and-serialization)) і операційне навантаження, що вимагає зрілого DevOps.

Що насправді дають мікросервіси:

- **Незалежне deployment** — команди випускають зміни без узгодження великого випуску.
- **Незалежне масштабування** — масштабуйте лише сервіс із найбільшим навантаженням.
- **Різнорідність технологій** — обирайте інструмент для кожного сервісу.
- **Ізоляція збоїв** — погіршення роботи одного сервісу не обов’язково зупиняє всю систему (якщо це передбачено архітектурою).
- **Автономність команд** — невеликі команди володіють сервісами від початку до кінця.

Більшість цих переваг стосується *організації й масштабування*, а не якості коду. Саме це і є вирішальним чинником.

### Коли розділяти й закон Конвея

> **Закон Конвея:** «Організації проєктують системи, що віддзеркалюють структуру комунікації в них». Ваша архітектура зрештою буде схожа на організаційну схему, плануєте ви це чи ні. Мікросервіси працюють, коли є кілька автономних команд, яким потрібне незалежне deployment. Якщо у вас одна команда із шести людей, мікросервіси переважно дадуть розподілений моноліт: та сама зв’язність, відсутність автономності й додаткова мережева затримка.

> **Рекомендація — починайте з модульного моноліту.** Він дає чіткі межі (обмежені контексти як модулі), один простий deployment, виклики в межах процесу й справжні транзакції. Якщо згодом модулю буде потрібне незалежне масштабування чи окрема команда, чиста межа спростить його виокремлення в мікросервіс. Не починайте новий проєкт із мікросервісів, якщо ще не знаєте точних меж і не маєте потрібної структури команди й операційного досвіду. **Модульний моноліт — прагматичний типовий вибір досвідченого інженера.**

Наслідок такий: невдалу межу в моноліті дешево виправити (перемістити клас), а невдалу межу між мікросервісами — болісно (узгоджена міграція кількох сервісів). Визначте межі правильно *до* розподілення.

## Шлюз API й Backend for Frontend

Коли сервісів кілька, клієнти не мають викликати кожен із них окремо: так розкривається внутрішня топологія, а на клієнт лягає оркестрація, автентифікація й повтори. **Шлюз API** — єдина точка входу, яка маршрутизує запити до серверних сервісів і керує наскрізними аспектами: автентифікацією, rate limiting (обмеженням частоти), завершенням TLS, агрегацією запитів і кешуванням. У .NET поширений будівельний блок — YARP (Yet Another Reverse Proxy); [Розділ 26](#chapter-26-delivery-and-platform) розглядає шлюзи серед іншої інфраструктури на периферії (балансувальників, зворотних проксі, CDN). Архітектурне питання — скільки потрібних точок входу й хто за них відповідає.

```
                 +------------------+       +-- Orders Service
   Clients  -->  |   API Gateway    | --->  +-- Catalog Service
                 | auth, routing,   |       +-- Pricing Service
                 | rate-limit, agg  |       +-- ...
                 +------------------+
```

**Backend for Frontend (BFF)** іде далі: замість одного універсального шлюзу ви створюєте *окремий* серверний застосунок для кожного типу клієнта. Мобільний застосунок має інші потреби, ніж вебзастосунок: менше полів, інша агрегація, інше кешування. Універсальний API змушує йти на незручні компроміси. Натомість кожен інтерфейс отримує власний спеціалізований BFF, який об’єднує саме ті дані, що потрібні йому.

```
  Mobile App  --> Mobile BFF  -->
  Web SPA     --> Web BFF     -->  [ downstream services ]
  Partner API --> Partner BFF -->
```

> **Компроміс:** BFF усувають надмірне й недостатнє отримання даних і дають командам інтерфейсів змогу швидко працювати без очікування спільного API. Ціна — більше сервісів, які треба підтримувати, і можливе дублювання логіки між BFF. У сучасних SPA BFF також природно підходить для обробки токенів OAuth (токени зберігаються на сервері). Використовуйте BFF, коли клієнти справді відрізняються; якщо ні, достатньо одного шлюзу.

## Усе разом

Якщо винесете із цього розділу одну думку, нехай це буде: **архітектура — мистецтво відкладати зміни й обмежувати їхній вплив**. Кожен описаний шаблон проводить межу так, щоб зміна з одного боку не змушувала змінювати другий. Зв’язність і цілісність — закони фізики; Clean Architecture, обмежені контексти DDD, CQRS, вертикальні зрізи й модульні моноліти — інженерні інструменти; а розподілені шаблони з [Розділу 20](#chapter-20-distributed-systems) (саги, outbox, ідемпотентність, consistency із часом) потрібні, коли межа стає мережевою.

Досвідчений інженер виявляє стриманість. Обирайте найпростішу структуру, яка відповідає наявним потребам, і додавайте церемонії лише тоді, коли цього вимагає справжній чинник. Модульний моноліт із чіткими межами домену служитиме більшості систем набагато довше, ніж очікують інженери, а складніші варіанти залишатимуться доступними, коли й лише коли вони справді знадобляться.

## Практика

**1. ADR для одного рішення (1 год).** Візьміть рішення вашої команди або наведене нижче у вправі *Прийміть рішення* й запишіть його за структурою [записів архітектурних рішень із Розділу 16](#architecture-decision-records-adrs): контекст, варіанти з їхньою вартістю, рішення, наслідки й умови перегляду. Обмежтеся однією сторінкою: ADR читає людина, яка поспішає.

**2. Проєктування системи за 90 хвилин (1 год 30 хв).** Оберіть незнайоме завдання, наприклад «доставляти партнерам webhooks із retries (повторними спробами) для кількох сотень тисяч events на день». Дотримуйтеся [підходу Розділу 23](#chapter-23-system-design) і запишіть кожен крок: вимоги (функціональні й інші), оцінки (запитів за секунду, обсяг сховища за рік), API, модель даних, компоненти, перші дві вузькі ланки, а також відхилений варіант і причину для кожного важливого рішення. Потім позначте кожне місце, де застосовуються гарантії [Розділу 20](#chapter-20-distributed-systems) (outbox, ідемпотентність, порядок).

**3. Підсумковий проєкт як довготривале завдання.** Кроки 6 і 7 [Розділу 44](#chapter-44-capstone-one-project-growing-up) ([Рефакторинг до Clean Architecture та DDD](#step-6-refactor-toward-clean-architecture-and-ddd) і [Поділ на мікросервіси](#step-7-split-into-microservices)) застосовують матеріал цього розділу на практиці; оформіть ADR для кожного поділу.

**Збережіть підтвердження роботи** у власному публічному репозиторії портфоліо, а не в цьому: ADR і опис проєктування. Рішення щодо систем справжнього роботодавця залишаються приватними; опублікуйте версію про підсумковий проєкт або вигадану систему.

Згодом вам можуть знадобитися: [Розділ 26: застосунок The 12-Factor](#the-12-factor-app) і [.NET Aspire](#net-aspire), а також [Розділ 22: стратегії версіювання API REST](#versioning-strategies-for-rest-apis).

## Три запитання

**1.** Команда розділила моноліт на п’ять сервісів, але тепер для кожного випуску все одно потрібно розгортати всі п’ять разом, а збій одного зупиняє інші. Що пішло не так і як відрізнити справжню межу сервісу від несправжньої?

<details>
<summary>Відповідь</summary>

- **Зв’язність перемістилася, а не зникла.** Зазвичай сервіси використовують спільну базу даних (зміна схеми порушує роботу кожного), викликають один одного синхронними ланцюжками (один повільний сервіс затримує решту) або використовують спільну бібліотеку доменних типів, яку потрібно оновлювати всім одночасно. Це розподілений моноліт.
- **Справжня межа має три ознаки.** Сервіс володіє своїми даними, і ніхто інший не читає його таблиці. Він обслуговує власні запити на основі свого стану, отримуючи дані інших сервісів уже отриманими events, а не викликами в межах запиту. І він змінюється за власним графіком, що зазвичай означає відповідальність однієї команди.
- **Як виправити.** Об’єднайте сервіси, що завжди змінюються разом, або зробіть їх модулем модульного моноліту; розмістіть спільні таблиці за межами одного власника; замініть синхронні ланцюжки events й локальними копіями даних (outbox і ідемпотентні consumer з [Розділу 11](#chapter-11-messaging-and-background-work) і [Розділу 20](#chapter-20-distributed-systems)).
</details>

**2.** Команда стверджує, що використовує CQRS, бо кожен запит проходить через MediatR. Що дає MediatR, чого він не дає і що змінив би справжній CQRS?

<details>
<summary>Відповідь</summary>

- **Що дає MediatR.** Диспетчеризацію об’єкта запиту до одного handler в межах процесу, завдяки якій контролери не залежать від сервісів безпосередньо, і поведінку pipeline для перевірки, logging чи транзакції кожного запиту.
- **Чого він не дає.** Окремих моделей: команди й запити можуть і далі використовувати ту саму модель сутностей і `DbContext`. Він не додає сховище читання, масштабування чи гарантії consistency, зате створює рівень посередництва під час кожного виклику. Нові основні версії мають комерційну ліцензію.
- **Що змінює CQRS.** Запити читають модель, сформовану для інтерфейсу (проєкцію, подання або окреме сховище), а команди проходять через доменну модель, яка забезпечує інваріанти. Окреме сховище робить читання узгодженими із часом, що має враховувати інтерфейс і бізнес-правила. Це виправдано, коли форми чи обсяги читань і записів дуже відрізняються; для CRUD це зайві формальності.
</details>

**3.** Публічне API повертає `customerName`. Тепер бізнес хоче `givenName` і `familyName`. Як випустити зміни без v2, які кроки що порушують і як визначити, що старе поле можна видалити?

<details>
<summary>Відповідь</summary>

- **Розширення.** Додайте `givenName` і `familyName` у відповіді поруч із `customerName` і приймайте обидва формати в запитах. Читачі, які ігнорують невідомі поля, мають безпечно пережити додаткові поля; перевірте поведінку відомих клієнтів.
- **Міграція.** Позначте `customerName` застарілим у документі OpenAPI й журналі змін, сповістіть consumers і записуйте, хто досі читає чи надсилає його. Якщо consumers багато, використовуйте журнали або tracing, а не теги метрик.
- **Звуження.** Видаліть `customerName`, коли телеметрія показуватиме, що погоджений період його не використовують, і мине оголошена дата.
- **Коли потрібна нова версія.** Якщо змінюється значення (ім’я більше не є одним рядком у будь-якій частині домену) або старе поле неможливо отримати з нових, чесніше випустити нову версію й оприлюднити дату завершення підтримки старої, ніж залишити поле, яке бреше.
</details>

## Прийміть рішення

Дванадцять розробників працюють над одним монолітом ASP.NET Core з однією базою даних. Deployment займає пів дня, конфлікти merge (злиття) часті, а минулого місяця помилка у виставленні рахунків заблокувала випуск каталогу. Є три пропозиції:

1. Розділити його на шість мікросервісів за наявними папками.
2. Перетворити на модульний моноліт: модулі з власними схемами й вузькими API, межі яких перевіряють архітектурні тести; deployment залишається одним.
3. Залишити структуру, але виправити pipeline постачання: пришвидшити тести, перейти на розробку через trunk і використовувати feature flags.

<details>
<summary>Як це оцінює досвідчений інженер</summary>

**Вартість кожного варіанта.**

- *Шість сервісів:* місяці роботи й постійні операційні витрати (pipelines, моніторинг, чергування, контракти й версіювання між сервісами, механізми consistency з [Розділу 20](#chapter-20-distributed-systems)). Невідомо, чи відповідають папки бізнес-межам, тому поділ може створити розподілений моноліт. Лише цей варіант дає змогу незалежно розгортати й масштабувати частини.
- *Модульний моноліт:* кілька тижнів на визначення й забезпечення меж, а також значне розплутування взаємного читання таблиць модулями. Він усуває конфлікти merge й обмежує вплив помилки, залишаючи один deployment й транзакції між модулями; майбутній поділ буде дешевим, бо модуль із власною схемою й API вже майже є сервісом.
- *Виправити pipeline:* від кількох днів до кількох тижнів. Це безпосередньо розв’язує проблему повільного deployment й заблокованих випусків (feature flag дав б змогу випустити каталог із вимкненим виставленням рахунків), не змінюючи зв’язність.

**Що визначає вибір:** проблеми пов’язані з постачанням і зв’язністю, а не масштабом. Ніщо не свідчить, що одну частину потрібно масштабувати або розгортати незалежно.

**Рішення.** Спершу виправити pipeline, бо результат буде за кілька тижнів, і паралельно перейти до модульного моноліту, по одному модулю за раз, почавши з найавтономнішого. Зафіксувати обидва рішення в ADR.

**Що змінило б рішення.** Частина з істотно іншими вимогами до масштабування чи доступності, окрема команда зі своїм графіком випусків або межа відповідності нормативам виправдали б виокремлення саме цього модуля в сервіс; модульна межа здешевлює це.
</details>

## Перевірте на роботі

**Перевірте.** Чи посилається проєкт домену на EF Core, ASP.NET Core або HTTP-клієнт? Які модулі чи сервіси читають чужі таблиці? Які торішні рішення існують лише в чиїйсь пам’яті? Оберіть одне й оформіть ADR. Для API: чи є письмовий список змін, що вважаються несумісними, і чи виявляє їх щось у pipeline (різниця OpenAPI, контрактні тести) до випуску?

**Виміряйте.** Для кожної версії API чи застарілого поля: скільки consumers викликали його за останні 30 днів? Для шляху запиту, що проходить через сервіси: скільки синхронних викликів він робить і як наскрізна затримка співвідноситься із сумою затримок окремих частин?

## Запитання для співбесіди

**Поясніть SOLID по одному реченню на принцип.**
- **S**RP — клас має одну причину для зміни (розділіть клас, який одночасно форматує *і* зберігає звіт).
- **O**CP — відкритість для розширення, закритість для змін (додавайте новий тип оплати новим класом, а не редагуванням `switch`).
- **L**SP — підтипи мають замінювати базові типи, не порушуючи поведінки викликачів (пастка `Square : Rectangle`).
- **I**SP — багато малих інтерфейсів кращі за один роздутий (не змушуйте реалізації додавати пусті методи, які їм не потрібні).
- **D**IP — залежте від абстракцій, а не конкретних реалізацій (впроваджуйте `IEmailSender`, а не `SmtpClient`).

**DI та IoC — це те саме?**
IoC (інверсія керування) — загальний принцип: потоком і створенням об’єктів керує фреймворк, а не ваш код. Dependency injection (впровадження залежностей) — один конкретний спосіб його застосувати: клас отримує залежності ззовні, а не створює їх через `new`. DI забезпечує тестованість і заміну реалізацій.

**Чи варто використовувати шаблон репозиторію з EF Core?**
Питання дискусійне. Аргумент *проти*: `DbContext` уже є Unit of Work, а `DbSet` — репозиторієм, тож обгортка створює абстракцію з витоками. Аргумент *за*: репозиторій може зібрати логіку запитів, не допустити залежності домену від сховища й спростити тестування. Відповідь досвідченого інженера: не додавайте універсальний репозиторій автоматично; створюйте репозиторій для конкретного завдання, коли він справді корисний, інакше використовуйте EF безпосередньо.

**Тривожна відповідь:** «EF завжди потрібно обгортати універсальним репозиторієм — це найкраща практика». `DbContext` уже є Unit of Work і репозиторієм; автоматична обгортка створює абстракцію з витоками.

**Що таке CQRS і коли його застосовують?**
Command Query Responsibility Segregation розділяє модель запису (команди, що змінюють стан) і модель читання (запити), часто з різними структурами й навіть різними сховищами. Застосовуйте його, коли форми чи обсяги читань і записів суттєво відрізняються або потрібні оптимізовані проєкції читання. Він додає складність — не використовуйте його для простого CRUD.

**Що таке агрегат у DDD?**
Кластер доменних об’єктів, який є єдиною межею consistency й має один **корінь агрегату** як точку входу. Інваріанти діють у межах агрегату, який завантажують і зберігають як одне ціле. Практичне правило: тримайте агрегати малими, посилайтеся на інші агрегати за ID, а consistency між ними забезпечуйте асинхронно.

**Мікросервіси чи моноліт — у чому компроміс?**
Моноліт простіше розробляти, розгортати й налагоджувати; одна кодова база, виклики в процесі й прості транзакції, але масштабується та розвивається як єдине ціле. Мікросервіси дають незалежне deployment, масштабування, технології й автономність команд, але ціною мережевої затримки, розподілених транзакцій, операційної складності й складнішого налагодження. Більшості команд слід починати з добре структурованого моноліту.

**Тривожна відповідь:** «Мікросервіси сучасні, а моноліти — застарілі». Поділ без чіткої потреби утворює розподілений моноліт.

**Визначте й пов’яжіть зв’язність і цілісність.**
Цілісність — наскільки модуль зосереджений на одній відповідальності (висока — добре). Зв’язність — наскільки модулі залежать один від одного (низька — добре). Прагніть високої цілісності й низької зв’язності: модулі добре виконують одну справу й взаємодіють через вузькі стабільні інтерфейси.

**Коли НЕ варто використовувати мікросервіси?**
Для малих команд, продуктів на ранній стадії, нечітких меж домену або браку операційної зрілості (CI/CD, observability (спостережуваності), чергування). Передчасні мікросервіси перетворюються на розподілений моноліт: усі проблеми мережі без переваг автономності. Розділяйте лише тоді, коли є чітка межа й потреба масштабування або автономності команди.
