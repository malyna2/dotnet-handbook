# Розділ 22: еволюція API, обмін даними в реальному часі й серіалізація

Будь-яка нетривіальна система зрештою перестає бути одним процесом, що зберігає об’єкти в пам’яті. Щойно дані перетинають межу — сокет, брокер повідомлень, файл на диску, кеш або відповідь HTTP — об’єкти в пам’яті потрібно сплющити в послідовність байтів, а на іншому боці відновити. Це сплющення називається *серіалізацією*, а відновлення — *десеріалізацією*. Звучить механічно й майже не варте уваги досвідченого інженера. Це не так. Від ваших рішень залежить швидкість сервісу, вартість мережі й сховища, можливість незалежного розгортання команд і те, чи пройде зміна схеми непомітно у вівторок, чи спричинить інцидент о другій ночі.

Цей розділ допоможе ухвалювати такі рішення свідомо. Він складається з трьох частин. Спершу — **формати кодування**, з якими ви зустрінетеся в .NET: JSON, XML, Protocol Buffers, MessagePack, Avro — і тип ідентифікатора поля в кожному з них, адже саме ця властивість визначає правила розвитку формату. Далі — складніша задача, яку самі формати не розв’язують: **еволюція контракту без порушення роботи систем, що вже від нього залежать** — правила сумісності, клієнт, поблажливий до нових полів, версіювання й виведення з експлуатації HTTP API та версіювання подій, що живуть роками. Наприкінці — **транспорти, крім JSON у схемі запит/відповідь**: gRPC для внутрішніх викликів, WebSockets, Server-Sent Events і SignalR для надсилання даних клієнтам.

Розділ спирається на [Розділ 5: HTTP і веб-API](#chapter-5-http-and-web-apis), де розглянуто `System.Text.Json`, REST, коди статусу й OpenAPI, та на [Розділ 11: обмін повідомленнями й фонова робота](#chapter-11-messaging-and-background-work), у якому йдеться про повідомлення зі схемами, що розвиваються тут.

## Чому важливий формат серіалізації

Обираючи формат, ви насправді шукаєте компроміс між чотирма властивостями, і рідко можна отримати їх усі водночас.

- **Сумісність.** Чи можуть прочитати дані сервіс Python, браузер і мейнфрейм? Тут перемагають текстові формати: JSON може розібрати будь-що. Пропрієтарний двійковий формат, зрозумілий лише збірці C#, стає проблемою, щойно з’являється друга мова.
- **Розмір у мережі.** Назва поля `"customerAccountBalance"`, що повторюється в мільйоні записів, означає мільйон копій цього рядка. Двійкові формати, які посилаються на поля цілими тегами, а не назвами, значно компактніші.
- **Швидкість кодування й декодування.** Щоб прочитати текст, потрібно переглядати символи, обробляти екранування й виділяти пам’ять під рядки. Двійковий формат безпосередньо читає цілі числа фіксованої ширини й довжини. На гарячому шляху, що обслуговує десятки тисяч запитів за секунду, ця різниця означає реальні витрати CPU і грошей.
- **Схема й еволюція.** Чи має формат вбудоване поняття «ось структура даних» і чи дає правила безпечної зміни цієї структури? Саме тут формати різняться найбільше; для систем із тривалим життєвим циклом ця властивість найважливіша.

Корисно уявляти так: формат — це *кодування*, а схема — *контракт*. Кодування (наприклад, JSON на Protobuf) змінити набагато простіше, ніж контракт, від якого залежать десятки споживачів. Більшість проблем розподілених систем виникає через порушення контрактів, а не через хибний вибір кодування.

> **Рекомендація:** обирайте формат для *межі*, а не для всієї системи. Публічному REST API для браузерів потрібен JSON. Внутрішній сервісний контур із великим трафіком — Protobuf поверх gRPC. Потоку подій, який багато команд споживають роками, потрібен формат зі схемою в реєстрі, як-от Avro чи Protobuf. Одна система може й зазвичай має використовувати різні формати на різних межах.

## Текстові й двійкові формати: головний поділ

**Текстові формати** (JSON, XML, CSV) кодують дані читабельними для людини символами. Їхня головна перевага — дані можна прочитати, отримати через `curl`, вставити у звіт про помилку й опрацювати будь-якою мовою без визначення схеми. Недоліки — розмір (назви полів і роздільники повторюються, числа зберігаються рядками цифр) і швидкість (посимвольний розбір, обробка екранування, виділення пам’яті під рядки).

**Двійкові формати** (Protobuf, MessagePack, Avro й вбудовані двійкові формати) компактно кодують дані за допомогою префіксів довжини, цілих тегів і власного подання чисел. Вони менші й швидші, але непрозорі: зазвичай потрібна схема (або принаймні декодер), щоб розібрати байти.

Практичне правило: **текст — на периферії, де працюють люди й різнорідні клієнти; двійковий формат — усередині, де системи активно обмінюються даними між собою.**

## JSON у сучасному .NET: `System.Text.Json`

[Розділ 5](#chapter-5-http-and-web-apis) охоплює основи: що таке `System.Text.Json` (STJ), чим він відрізняється від Newtonsoft.Json, які параметри задавати, власні конвертери й типові налаштування вебзастосунків ASP.NET Core. Тут розглянуто те, що важливо на довготривалій межі: попередню компіляцію серіалізатора, типові значення, які підводять під час переходу, і поліморфні дані, для яких дискримінатор є такою самою частиною контракту, як будь-яке поле.

### Генератори джерельного коду: JSON без рефлексії

За замовчуванням STJ у середовищі виконання використовує рефлексію, щоб визначити, як читати й записувати типи. Рефлексія гнучка, але має недоліки: одноразове навантаження під час першого виклику, витрати на кожну серіалізацію й, що особливо важливо, несумісність із **обрізанням** і **Native AOT**. Обрізувач не може визначити, які типи ви переглянете через рефлексію, і може їх видалити.

Проблему розв’язує **генератор джерельного коду**. Оголосіть partial `JsonSerializerContext`, позначте його типами, які серіалізуєте, — і компілятор згенерує код серіалізації під час збірки. Жодної рефлексії під час виконання, швидший запуск, менше виділення пам’яті, повна сумісність із AOT та обрізанням.

```csharp
[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]
[JsonSerializable(typeof(Order))]
internal partial class AppJsonContext : JsonSerializerContext { }

// Usage — note the generated metadata is passed in, so no reflection is needed:
string json = JsonSerializer.Serialize(order, AppJsonContext.Default.Order);
Order? round = JsonSerializer.Deserialize(json, AppJsonContext.Default.Order);
```

> **Рекомендація:** для сервісу на гарячому шляху й *усього*, що працює з Native AOT або суворим обрізанням, використовуйте генератор джерельного коду `System.Text.Json`. Це майже безкоштовний виграш у продуктивності й надійності. В ASP.NET Core контекст можна зареєструвати через `services.ConfigureHttpJsonOptions(o => o.SerializerOptions.TypeInfoResolverChain.Insert(0, AppJsonContext.Default))`.

Кілька фактів про STJ, які варто пам’ятати під час переходу з Newtonsoft:

- За замовчуванням STJ **розрізняє регістр** назв властивостей (задайте `PropertyNameCaseInsensitive = true`, щоб відтворити поведінку Newtonsoft, але це трохи сповільнює роботу).
- Типово він **не серіалізує поля й непублічні члени**.
- Для серіалізації й десеріалізації переліків як рядків потрібен `JsonStringEnumConverter`; типово вони представлені числами.
- Кешуйте й повторно використовуйте екземпляр `JsonSerializerOptions`. Створення нового екземпляра для кожного виклику вимикає внутрішнє кешування й різко знижує пропускну здатність.

### Поліморфізм: дискримінатор є частиною контракту

Якщо дані можуть мати кілька форм, наприклад `PaymentMethod` є карткою або банківським переказом, STJ серіалізує їх поліморфно, лише якщо це задано на базовому типі: `[JsonPolymorphic]` і по одному `[JsonDerivedType(typeof(CardPayment), "card")]` для кожного підтипу. Серіалізатор записує властивість-дискримінатор типу (типово `$type`), а під час читання вибирає підтип. Звідси випливають два наслідки, пов’язані з рештою цього розділу. Значення дискримінатора — оголошений вами список дозволених варіантів; це не те саме, що `TypeNameHandling` у Newtonsoft, який вбудовує до даних назви типів .NET і дозволяє даним обирати, що створити — це давно відома поверхня атаки десеріалізації. А кожне значення дискримінатора є частиною контракту, як елемент переліку: старі читачі не знають нового підтипу, тож до нього застосовуються правила переліку нижче, а перейменування — несумісна зміна.

## XML: досі існує, і часом це правильно

XML з’явився раніше за JSON як мова обміну між системами й не зник. Ви зустрінете його в вебслужбах SOAP, застарілих корпоративних інтеграціях, державних і медичних стандартах та форматах документів (`.docx`, `.xlsx` — це архіви з XML). Для нього в .NET призначені `System.Xml.Serialization.XmlSerializer` і `System.Runtime.Serialization.DataContractSerializer`.

Справжні переваги XML над JSON — **простори імен** (усувають конфлікти назв елементів під час об’єднання словників), **атрибути й елементи** (розрізнення, якого немає в JSON) та **схеми XSD із розвиненими інструментами** перевірки й генерації коду. Недоліки — багатослівність (закривальні теги подвоюють накладні витрати структури) й повільніший розбір.

```csharp
using System.Xml.Serialization;

var serializer = new XmlSerializer(typeof(Order));
using var writer = new StringWriter();
serializer.Serialize(writer, order);
string xml = writer.ToString();
```

Для нових внутрішніх API використовуйте JSON чи двійковий формат. XML доречний, коли його вимагає стандарт або наявний партнер — це поширена й поважна причина.

## Protocol Buffers: двійковий формат із визначенням схеми

Protocol Buffers («protobuf») від Google — двійковий формат, із яким більшість розробників .NET знайомиться через **gRPC** (розглянутий нижче в цьому розділі), де він є типовим форматом даних. Його визначальна властивість — **схема передує коду**: ви створюєте файл `.proto` з описом повідомлень, а генератор коду створює класи C#. Схема — не необов’язкова документація, а джерело істини, з яким компілюються і виробник, і споживач.

```proto
syntax = "proto3";
option csharp_namespace = "Shop.Contracts";

message Order {
  int32 id = 1;
  string customer = 2;
  double total = 3;
  int64 placed_at_unix = 4;
}
```

Числа після кожного поля (`= 1`, `= 2`) — це **номери полів** (теги), центральний елемент еволюції protobuf. У мережі protobuf не записує назви полів, а для кожного поля записує невеликий байтовий «тег» із номером поля й типом, а потім значення. `customer = 2` приблизно перетвориться на «поле 2, дані з обмеженою довжиною, 4 байти, A-c-m-e».

Це має два важливі наслідки:

1. **Назва поля не впливає на байти.** Можна перейменувати `customer` на `customerName` у `.proto`, і старі та нові бінарні файли далі без проблем взаємодіятимуть, бо вони погодили *номер* 2, а не назву.
2. **Номер поля — постійний і критично важливий ідентифікатор.** Змініть `customer` із `2` на `5` — кожен наявний споживач шукатиме поле 2, не знайде його й мовчки отримає порожнє значення. Повторно використайте номер 2 для *іншого* поля з іншим типом — отримаєте сміття або помилку декодування.

> **Найважливіше правило protobuf:** *ніколи не змінюйте й не використовуйте повторно номер поля після його випуску в продакшен*. Номери полів — назавжди. Видаливши поле, виконайте `reserve` для його номера (а бажано й назви), щоб ніхто випадково не використав його повторно:
> ```proto
> message Order {
>   reserved 4;
>   reserved "placed_at_unix";
>   int32 id = 1;
>   string customer = 2;
>   double total = 3;
> }
> ```

У proto3 всі поля фактично необов’язкові й мають **типові значення** (0, порожній рядок, false). Не можна відрізнити «поля немає» від «полю присвоєно нуль», якщо не вказати `optional` (це додає відстеження наявності) або не використати обгортку. Така поведінка типових значень і забезпечує еволюцію: новий споживач старих даних отримує типове значення відсутнього поля, а старий споживач нових даних ігнорує невідомі теги.

У .NET додайте пакет `Grpc.Tools` і помістіть `.proto` до проєкту — MSBuild згенерує класи. Згенерований код швидкий, мало виділяє пам’яті й використовує інтерфейс `IMessage` бібліотеки `Google.Protobuf`.

> **Варто знати:** довготривалий поділ на proto2 і proto3 замінюють **Protobuf Editions** (Edition 2023 — перший випуск, що з’явився в другій половині 2023 року). Замість вибору синтаксису із зафіксованою семантикою редакція дає змогу налаштовувати окремі аспекти прапорцями функцій, не змінюючи формат даних. Це напрям розвитку, у якому обидва синтаксиси зближуються, тому сучасному читачеві варто знати цей термін, навіть якщо в більшості наявних файлів `.proto` ще вказано `syntax = "proto3"`.

## MessagePack: двійковий JSON без файла схеми

MessagePack найкраще описати як «модель даних JSON, двійкове кодування». Він має таку саму структуру — словники, масиви, рядки, числа, логічні значення, null, — але компактно кодує її префіксами довжини й тегами типів, а не текстом. На відміну від protobuf, він не потребує окремого файла схеми; у .NET чудова бібліотека **MessagePack-CSharp** безпосередньо серіалізує позначені атрибутами типи C#, як звичайний серіалізатор, а не генератор коду.

```csharp
using MessagePack;

[MessagePackObject]
public class Order
{
    [Key(0)] public int Id { get; set; }
    [Key(1)] public string Customer { get; set; } = "";
    [Key(2)] public decimal Total { get; set; }
    [Key(3)] public DateTimeOffset PlacedAt { get; set; }
}

byte[] bytes = MessagePackSerializer.Serialize(order);
Order back = MessagePackSerializer.Deserialize<Order>(bytes);
```

Цілі числа `[Key(0)]` виконують ту саму роль, що номери полів protobuf: це компактні ідентифікатори в мережі, і **правило «ніколи не використовувати ключ повторно» діє так само**. MessagePack-CSharp також підтримує текстові ключі (`[Key("customer")]`): вони самодокументованіші, але більші — компроміс, подібний до JSON, у межах того самого формату.

MessagePack-CSharp відомий високою швидкістю: він використовує генерацію джерельного коду чи IL і є одним із найшвидших серіалізаторів для .NET. Добре підходить для кешування (компактні дані Redis), внутрішніх RPC (це типовий формат SignalR для двійкових даних і фреймворку MagicOnion) і ситуацій, коли потрібна компактність двійкових даних без окремих файлів `.proto`. Компроміс порівняно з protobuf: схема зберігається в атрибутах C#, а не в незалежному від мови IDL, тому міжмовні контракти трохи менш формалізовані.

> **Ще швидший варіант для обміну між .NET:** **MemoryPack** (від neuecc, автора MessagePack-CSharp) — двійковий серіалізатор «без кодування», що використовує сучасний C# і лише генерацію вихідного коду без IL-генерації під час виконання. Тому він **сумісний із Native AOT** і для багатьох даних у кілька разів швидший за MessagePack. Це найгостріший інструмент, коли обидві сторони працюють на .NET і міжмовний обмін не потрібен; за задумом формат специфічний для .NET.

## Apache Avro: створений для еволюції

Avro походить зі світу Hadoop і є канонічним вибором на платформах даних Kafka. Його відмінна ідея: **схема передається разом із даними, а для читання потрібні схема виробника й схема читача**.

Під час серіалізації Avro записує необроблені значення майже без витрат на кожне поле — без тегів полів, — бо точний порядок і типи визначає схема. Щоб *прочитати* ці байти, потрібні **схема виробника** (з чим записано дані) і **схема читача** (чого очікує код). Правила узгодження Avro зводять їх разом: поля, наявні у виробника, але відсутні в читача, пропускаються; поля читача, відсутні у виробника, заповнюються з **типових значень**; перейменовані поля зіставляються через **псевдоніми**.

Це справді інша й потужна модель. Оскільки читання — це узгодження двох схем, а не фіксоване декодування, Avro може автоматично підтримувати ширший спектр змін, але лише за наявності *обох* схем. У файлі Avro вбудовує схему виробника до заголовка. У потоці, наприклад Kafka, зберігати повну схему в кожному повідомленні було б марнотратно, тому повідомлення містить малий **ID схеми**, який вказує на схему в **реєстрі схем** (про нього йтиметься далі).

Схеми Avro самі є JSON:

```json
{
  "type": "record",
  "name": "Order",
  "namespace": "shop.contracts",
  "fields": [
    { "name": "id", "type": "int" },
    { "name": "customer", "type": "string" },
    { "name": "total", "type": "double" },
    { "name": "note", "type": ["null", "string"], "default": null }
  ]
}
```

Поле `note` з об’єднаним типом `null` і `string` та `default: null` — класичний приклад безпечного додавання: старі читачі його ігнорують, а нові отримують `null`, якщо поля немає.

## Відчуття щодо продуктивності: розмір і швидкість

Не надавайте надмірної ваги окремим мікротестам — більше впливають структура даних, розмір об’єктів і шаблони доступу, — але загальний *порядок* стабільний, його варто засвоїти:

- **Розмір:** Protobuf і Avro зазвичай найкомпактніші (цілі теги або їх відсутність, щільне кодування). Невдовзі за ними йде MessagePack. JSON набагато більший: часто у 2–5 разів за двійкове подання тих самих даних, а з довгими назвами полів — ще більший. XML — найбільший.
- **Швидкість:** MessagePack-CSharp і protobuf найшвидше кодують і декодують дані в .NET, особливо з генерацією вихідного коду. STJ із генератором дивовижно швидкий для текстового формату й значно випереджає Newtonsoft. `XmlSerializer` — найповільніший серед поширених варіантів.
- **Читабельність і інструменти:** тут беззаперечно перемагають JSON і XML; для двійкових форматів потрібен декодер.

> **Рекомендація:** перш ніж оптимізувати, виміряйте *свої* дані за допомогою BenchmarkDotNet ([Розділ 17](#benchmarking-with-benchmarkdotnet)). Як типовий варіант: JSON із генерацією вихідного коду для публічних і периферійних API, Protobuf для gRPC і внутрішніх міжмовних сервісів, MessagePack для внутрішніх RPC між .NET і кешування, Avro для конвеєрів Kafka з реєстром схем.

Формат визначає кодування; далі розділ присвячений контракту.

## Головна тема: схеми й розвиток контрактів

Ось ситуація, через яку все це складно. Ви розгортаєте версію 1 виробника й версію 1 споживача. Вони сумісні. Потім потрібно змінити дані. Але **не можна атомарно оновити всіх виробників і споживачів одночасно** — у цьому й сенс розподіленої системи. Під час поступового розгортання, а часто й довго після нього, старі та нові версії працюють паралельно. Старі виробники надсилають дані новим споживачам, а нові виробники — старим. Ваше завдання — змінити схему так, щоб *працювала кожна комбінація*.

### Напрями сумісності

Сумісність називають з погляду того, який бік новіший:

- **Зворотна сумісність:** новий код читає дані, записані старим кодом. (Спершу можна оновити *споживачів*.) Не робіть обов’язковими поля, яких старі виробники не надсилали: додавайте поля з типовими значеннями й не видаляйте обов’язкові поля.
- **Пряма сумісність:** старий код читає дані, записані новим. (Спершу можна оновити *виробників*.) Старі читачі мають витримувати невідомі поля, тож ключовий механізм — *ігнорування невідомих полів*; не додавайте нових *обов’язкових* полів, які старі читачі вимагатимуть.
- **Повна сумісність:** працюють обидва напрями. Саме це потрібно для незалежного розгортання в будь-якому порядку; так налаштовують багато реєстрів схем.

Уявляйте матрицю: «яка схема записала» × «яка читає». Зворотна сумісність охоплює читання новим старих даних, пряма — читання старим нових, повна — обидва варіанти.

### Безпечні й несумісні зміни

Правила для protobuf, Avro й коректно реалізованого JSON напрочуд схожі.

**Зазвичай безпечні зміни:**

- **Додати необов’язкове поле з типовим значенням.** Старі читачі його ігнорують, а нові використовують типове значення, якщо його немає. Це робоча основа еволюції схеми.
- **Видалити необов’язкове поле** (поки жоден споживач його *не вимагає*) і зарезервувати його ідентифікатор, щоб ніхто не використав його знову.
- **Перейменувати поле** *за ідентифікації номером або ключем* (protobuf, MessagePack): назва косметична. В Avro скористайтеся **псевдонімами**. У JSON перейменування несумісне, якщо стару назву не залишити.

**Несумісні зміни — не робіть їх у чинному контракті:**

- **Повторно використати чи перенумерувати номер поля або ключ.** Це катастрофічна тиха помилка. Зарезервуйте видалені номери.
- **Змінити тип поля** (ціле число на рядок або звузити int64 до int32). Байти починають означати інше.
- **Додати *обов’язкове* поле.** Старі виробники його не надсилатимуть — ви порушите зворотну сумісність.
- **Видалити поле, потрібне споживачу,** або змінити його семантику, залишивши назву (це тонша й підступніша проблема: перевірку схеми пройдено, а поведінка неправильна).

Якщо пам’ятати, що формати вважають ідентичністю поля *назву* (JSON, Avro) або *номер/ключ* (Protobuf, MessagePack), правила можна звести до таблиці. Усе нижче з цього випливає.

| Зміна | JSON (STJ) | Protobuf | MessagePack (цілі ключі) | Avro |
|---|---|---|---|---|
| Додати необов’язкове поле з типовим значенням | ✅ | ✅ | ✅ (додати в кінець) | ✅ (задати типове значення) |
| Видалити поле | ⚠️ якщо не використовується | ⚠️ зарезервувати номер | ⚠️ зарезервувати ключ | ⚠️ якщо не використовується |
| Перейменувати поле | ⚠️ залишити стару назву | ✅ (ідентичність — номер) | ✅ (ідентичність — ключ) | ⚠️ псевдонім |
| Змінити тип поля | ❌ | ❌ | ❌ | ❌ |
| Повторно використати тег/назву видаленого поля | ❌ | ❌ тиха помилка | ❌ тиха помилка | ❌ |
| Зробити необов’язкове поле обов’язковим | ❌ | ❌* | ❌ | ❌ |

\* Proto3 навіть не дає виразити `required` у форматі даних — помилка з’явиться пізніше в рівні перевірки, тобто її легше пропустити, а не безпечніше.

### Переліки: додавання, яке всі вважають безпечним

Додавання елемента переліку здається нешкідливою зміною, але саме вона часто порушує роботу суворих читачів. Виробник із новішою схемою надсилає значення, якого споживач іще не знає. Споживач із вичерпним `switch` без типового варіанта може аварійно завершитися; згенерований із документа OpenAPI SDK може представити перелік закритим переліком C# і, залежно від генератора, викинути помилку під час десеріалізації невідомого елемента.

Захист потрібен з обох боків. **На боці виробника:** передавайте в мережі рядкові значення замість цілих чисел і документуйте, що споживач має приймати невідомі елементи. **На боці споживача:** десеріалізуйте поле як `string` і зіставляйте його самостійно, явно передбачивши невідомий варіант:

```csharp
public OrderStatus MapStatus(string wireValue) => wireValue switch
{
    "pending"   => OrderStatus.Pending,
    "shipped"   => OrderStatus.Shipped,
    "delivered" => OrderStatus.Delivered,
    _           => OrderStatus.Unknown   // tolerate values added later
};
```

Protobuf передбачає це: у proto3 невідоме значення переліку зберігається як базове ціле число, а не відхиляється, тож проходить крізь споживача, який іще його не розуміє. Завжди передбачайте в переліках значення `Unknown` або `Unspecified` під номером нуль.

### Невідомі поля й поблажливий читач

Пряма сумісність залежить від поведінки читача з невідомими йому даними. Закон Постеля («будь консервативним у надсиланні й поблажливим у прийманні») зазвичай цитують на боці сервера, але найбільший ефект дає поведінка споживача. **Поблажливий читач** десеріалізує лише поля, які справді використовує, ігнорує решту, не відхиляє додаткових даних, не покладається на порядок полів і не аварійно завершується через невідомий елемент переліку. Такий споживач переживає багато змін виробника без зміни коду. Протилежний варіант — суворий читач, який перевіряє весь документ за точною схемою й відхиляє все несподіване, — перетворює кожне адитивне оновлення виробника на координований несумісний випуск.

Типова поведінка форматів:

- **Protobuf** зберігає невідомі поля: посередник, який десеріалізує й повторно серіалізує повідомлення, не втрачає незрозумілі йому поля. Це чудовий вибір для середнього рівня.
- **`System.Text.Json`** ігнорує невідомі властивості під час десеріалізації; виняток буде лише за наявності `JsonSerializerOptions.UnmappedMemberHandling = JsonUnmappedMemberHandling.Disallow`. Типова поведінка — перевага. Не намагайтеся «посилити» її заради суворості: тоді кожне додаткове поле виробника стає для вас незначною зміною замість потреби в новому розгортанні.

Ігнорування не дорівнює збереженню, і тут ховається менш помітна небезпека. Клієнт, що десеріалізує дані у сувору модель і згодом серіалізує їх повторно (наприклад, виконує `PUT` із читанням, зміною й записом), мовчки *видаляє* всі незмодельовані поля й стирає дані, про існування яких не знав. Якщо потрібно повторно передавати дані, захоплюйте невідомі поля за допомогою `[JsonExtensionData]`:

```csharp
public class Order
{
    public int Id { get; set; }
    public string Customer { get; set; } = "";

    [JsonExtensionData]
    public Dictionary<string, JsonElement>? Extra { get; set; }
}
```

Усе, чого немає в схемі, потрапляє до `Extra` і записується під час серіалізації — JSON-варіант поблажливого читача.

> **Рекомендація.** Еволюцію здешевлює поблажливість з обох боків: виробник лише додає поля, а споживач читає лише потрібне. Поруште будь-яку частину домовленості — виробник перейменує поле чи споживач повторно серіалізує сувору модель — і кожна зміна вимагатиме узгодженого розгортання. Для контрактів, які ви повністю не контролюєте, надавайте перевагу поблажливим читачам.

## Версіювання API й зворотна сумісність

Наведені правила стосуються будь-якого контракту. В HTTP API є й інші елементи контракту, яких не видно у файлі схеми: коди стану, правила перевірки, форма помилок, типові значення, а також модель розгортання, у якій ви рідко знаєте всіх клієнтів. Команди вдаються до версіювання, але справжня мета — зворотна сумісність. Якщо забезпечити друге, першого знадобиться набагато менше, тож почніть із сумісності.

### Що справді є несумісною зміною

Зміна несумісна, якщо *коректно написаний і вже розгорнутий* клієнт після неї перестає працювати. Наведені вище правила для полів залишаються чинними; таблиця додає ті частини контракту HTTP, які не належать до схеми даних. Несподіванка в асиметрії: та сама правка в одному напрямі нешкідлива, в іншому — критична.

| Зміна | Оцінка | Причина |
|---|---|---|
| Додати **необов’язкове** поле запиту | Безпечно | Старі клієнти його не надсилають; сервер уже має типове значення |
| Додати **обов’язкове** поле запиту | **Несумісно** | Кожен запит у процесі стає недійсним |
| Додати поле до відповіді | Зазвичай безпечно | Поблажливі читачі ігнорують його; суворі чи згенеровані клієнти можуть не прийняти |
| Видалити чи перейменувати поле відповіді | **Несумісно** | Клієнти звертаються до полів за назвою |
| **Посилити** перевірку (`maxLength` від 200 до 100, додати регулярний вираз) | **Несумісно** | Запити, що вчора були допустимі, тепер отримують `400` |
| Послабити перевірку | Безпечно | Розширює набір допустимих значень |
| Змінити тип чи формат поля (`int` на `string`, епоха на ISO-8601) | **Несумісно** | Десеріалізація не вдається або тихо перетворює значення |
| Почати повертати `null` для поля, яке завжди було заповнене | **Несумісно** | Клієнт звертається до нього, не перевіряючи на null |
| Додати **нове значення переліку** | **Несумісно для суворих читачів** | Згенерований клієнт із закритим переліком викидає помилку для невідомого елемента (див. *Переліки* вище) |
| Додати нову кінцеву точку або необов’язковий параметр запиту | Безпечно | Ніхто не викликає невідомої йому функції |
| Змінити код успіху (`200` на `202`) | **Несумісно** | Клієнти перевіряють код; крім того, `201` і `200` по-різному визначають місце отримання ресурсу |
| Змінити форму помилки (рядок на `ProblemDetails`) | **Несумісно** | Обробка помилок — теж контракт, і його забувають версіювати найчастіше |
| Змінити типову кількість елементів на сторінці чи порядок сортування | **Практично несумісно** | Цього немає у схемі, але цикли пагінації й тести від цього залежать |
| Змінити *значення* поля, лишивши назву й тип | **Найгірший варіант** | `amount` у доларах стає `amount` у центах |

На двох рядках варто наголосити. **Посилення перевірки** легко проходить повз перевірку коду, бо схоже на виправлення помилки: хтось помічає, що `Description` приймає 10 000 символів, і обмежує поле до 500. Кожен клієнт, який спокійно надсилав 800 символів, тепер отримує `400`. Контракт змінено без змін жодного типу, а перевірка різниці OpenAPI не помітить цього, якщо порівнювати лише структуру, а не обмеження. **Тиха зміна семантики** — єдиний пункт без жодної помилки як ознаки: нічого не викидає винятку, сповіщення не спрацьовує, а фінансова звірка знаходить проблему через три тижні. Якщо значення поля змінилося, дайте йому нову назву. Завжди.

### Розширення й звуження: як уникнути нової версії

Для більшості змін, які, здається, вимагають `v2`, цього не потрібно. **Розширення й звуження** (також паралельна зміна) — це той самий маневр, що й [міграції схеми без простою з Розділу 18](#migrations-at-scale-zero-downtime), але для контракту передавання даних, а не таблиці:

```
expand    add the new field/endpoint alongside the old one; write both, read either
migrate   move consumers to the new one, individually, at their own pace
contract  once telemetry shows nobody reads the old one, delete it
```

Канонічний приклад — перейменувати `name` на `fullName` у відповіді. Нова версія потребує паралельної поверхні v2, дубльованої таблиці маршрутів, другого набору тестів і строку міграції для кожного споживача. Розширення й звуження потребує одного випуску, що надсилає *обидва* поля, періоду спостереження за тим, яке з них справді читають, і другого випуску, що видаляє `name`. Жодної версії, строку чи наради для узгодження.

Так само можна обробити більшість несумісних змін із таблиці вище. Потрібно посилити перевірку? Протягом одного випуску записуйте порушення, але не відхиляйте їх; побачте, хто не проходить, і лише потім увімкніть перевірку. Змінюються одиниці вимірювання? Додайте поле з новою назвою й оголосіть старе застарілим. Одну кінцеву точку потрібно розділити на дві? Випустіть обидві, змусьте стару кінцеву точку викликати нові, а потім приберіть її, коли звернення припиняться.

Вводьте нову версію лише для змін, які справді неможливо виконати через розширення й звуження: змінена модель ресурсів, інша схема автентифікації, зміна етапів процесу. Кожна версія означає ще один шлях коду для підтримки, матрицю тестів і майбутню розмову про припинення підтримки. **Найдешевша версія — та, яка вам не знадобилася.**

### Стратегії версіювання API REST

Коли зміни неможливо виконати через розширення й звуження, версія має бути десь у запиті. Є чотири місця, де її можна вказати:

| Варіант | Приклад | Переваги | Недоліки |
|---|---|---|---|
| **Шлях URL** | `/v2/products` | Видно в журналах, браузерах і `curl`; безкоштовно входить до ключа кешу CDN; звичайна маршрутизація; проксі може спрямувати дві версії в різні розгортання | Порушує ідеал «один URI на ресурс»: той самий товар має два URL; версія потрапляє до кожного посилання |
| **Рядок запиту** | `/products?api-version=2.0` | Непомітний; якщо його немає, природно застосувати типову версію | Його легко загубити: проксі й кеші можуть нормалізувати чи ігнорувати; засмічує кожен URL; незручно використовувати в гіпермедійних посиланнях |
| **Власний заголовок** | `X-Api-Version: 2.0` | URL чисті й стабільні для всіх версій | Не видно в адресному рядку й більшості журналів доступу; кеші ігнорують його, якщо не встановити `Vary`; підтримка складніша, коли просять «надішліть curl, який не працює» |
| **Тип медіаданих** | `Accept: application/vnd.acme.product.v2+json` | Найчистіша модель: версія належить *представленню*, а не ресурсу; підтримує деталізацію для кожного ресурсу | Майже ніхто так не робить; слабка підтримка інструментів; плутає звичайних споживачів; ще один шлях узгодження вмісту, де можна помилитися |

Чесний рейтинг такий: **шлях URL** для публічних API, бо налагоджуваність і поведінка кешу важливіші за чистоту, а проксі може спрямовувати v1 і v2 до різних розгортань. **Тип медіаданих** — якщо у вас досвідчені споживачі й справді потрібне версіювання кожного ресурсу; врахуйте, що доведеться постійно пояснювати його. Заголовок і рядок запиту — прийнятні проміжні варіанти. Набагато важливіше за вибір — застосовувати один варіант послідовно.

> **Нюанс — кешування.** У будь-якому варіанті, де версію вказано *поза* URL, задайте заголовок відповіді `Vary`. Інакше спільний кеш може віддати тіло v1 запиту v2. Саме тому версіювання в URL перемагає в суперечках, де з погляду естетики мало б програти.

### Налаштування через Asp.Versioning

```csharp
builder.Services.AddApiVersioning(o =>
{
    o.DefaultApiVersion = new ApiVersion(1, 0);
    o.AssumeDefaultVersionWhenUnspecified = true;
    o.ReportApiVersions = true;                  // api-supported-versions / api-deprecated-versions
    o.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),                  // /v2/products
        new HeaderApiVersionReader("X-Api-Version"),
        new QueryStringApiVersionReader("api-version"));
})
.AddApiExplorer(o =>                             // Asp.Versioning.Mvc.ApiExplorer
{
    o.GroupNameFormat = "'v'VVV";                // v1, v1.1, v2 — becomes the OpenAPI group name
    o.SubstituteApiVersionInUrl = true;          // resolves {version:apiVersion} in the docs
});
```

`ApiVersionReader.Combine` приймає *будь-яке* із заданих джерел — це практичне типове рішення під час міграції: споживача можна перевести із заголовка на URL без одночасного перемикання всіх. `ReportApiVersions` змушує кожну відповідь повідомляти про наявні версії, тож клієнт може виявити нову, не читаючи журнал змін.

У мінімальних API версії належать **набору версій**, спільному для групи:

```csharp
var versions = app.NewApiVersionSet()
    .HasApiVersion(new ApiVersion(1, 0))
    .HasApiVersion(new ApiVersion(2, 0))
    .Build();

var products = app.MapGroup("/api/v{version:apiVersion}/products")
                  .WithApiVersionSet(versions);

products.MapGet("/{id:int}", GetProductV1).MapToApiVersion(new ApiVersion(1, 0));
products.MapGet("/{id:int}", GetProductV2).MapToApiVersion(new ApiVersion(2, 0));
```

Два обробники одного шаблону маршруту не конфліктують: версію визначає зіставлення. У контролерах використовують атрибути: `[ApiVersion("2.0")]` на класі, `[MapToApiVersion("1.0")]` на дії, що залишилася, і шаблон `[Route("api/v{version:apiVersion}/[controller]")]`.

Окремі документи OpenAPI на версію надходять від дослідника API, який позначає кожну кінцеву точку назвою групи з `GroupNameFormat`:

```csharp
builder.Services.AddOpenApi("v1");
builder.Services.AddOpenApi("v2");   // one document per version
// ...
app.MapOpenApi();                    // /openapi/v1.json, /openapi/v2.json
```

Кожен документ містить кінцеві точки з відповідною назвою групи. У результаті згенеровані SDK клієнтів прив’язані до версії: споживач створює SDK за `v2.json`, коли *він* готовий, а не коли ви його випускаєте.

### Виведення версії з експлуатації

Випустити v2 — легка половина. Саме видалення v1 затримує команди іноді на роки, і причина майже ніколи не технічна.

Оголошуйте про припинення підтримки безпосередньо у відповідях, а не лише в блозі. RFC 8594 визначає заголовок `Sunset` — дату, коли ресурс припинить працювати; його зазвичай поєднують із заголовком `Deprecation` і посиланням `Link` на інструкцію з міграції. Їх треба записати *до* початку відповіді, тому використовуйте `OnStarting`, а не задавайте їх після `await next`:

```csharp
app.Use((ctx, next) =>
{
    ctx.Response.OnStarting(() =>
    {
        if (ctx.GetRequestedApiVersion()?.MajorVersion == 1)
        {
            ctx.Response.Headers["Deprecation"] = "true";
            ctx.Response.Headers["Sunset"] = "Wed, 31 Dec 2026 23:59:59 GMT";
            ctx.Response.Headers["Link"] =
                "<https://docs.acme.com/api/v2-migration>; rel=\"deprecation\"";
        }
        return Task.CompletedTask;
    });
    return next(ctx);
});
```

`ReportApiVersions = true` автоматично доповнює це заголовками `api-supported-versions: 1.0, 2.0` і `api-deprecated-versions: 1.0` у кожній відповіді. Позначити версію застарілою можна одним атрибутом — `[ApiVersion("1.0", Deprecated = true)]` або `.HasDeprecatedApiVersion(...)` у наборі версій. Відповідально написаний клієнт зможе сповістити вас до настання дати припинення підтримки.

**Чого не вистачає більшості команд.** Ніщо з наведеного не відповідає, чи *безпечно* видаляти v1, а це і є справжня перешкода. На запитання «чи залишився хтось на v1?» дасть відповідь загальний лічильник. Насправді потрібно знати: «*хто* досі на v1, як часто й для чого?» — а заднім числом цього не дізнатися. Від дня випуску v2 додавайте до телеметрії запитів визначену версію API **й** ідентичність споживача: ID клієнта з токена, ключ API чи обов’язковий `User-Agent`. Тоді виведення версії з експлуатації стане звітом, а не суперечкою: три споживачі, двоє внутрішніх, один робить сорок викликів на день — їм можна написати замість вгадувати. Без телеметрії за версіями й споживачами чесна відповідь на «чи можна видалити v1?» назавжди звучатиме «ми не знаємо», а її завжди перекриє «залишмо, про всяк випадок». Інструментування розглянуто в [Розділі 25: спостережуваність і тестування у масштабі](#chapter-25-observability-and-testing-at-scale).

> **Пастка — кардинальність.** Ідентичність споживача — саме той тип необмеженого значення, що псує сервер метрик (попередження про кардинальність у [розділі метрик Розділу 25](#metrics) стосується цього безпосередньо). Для кількох відомих партнерів тег метрики прийнятний. Для великої чи відкритої аудиторії записуйте версію й споживача в *журнал або проміжок трасування*, а не як теги метрик; запити про завершення підтримки виконуйте за трасами. Саме там мають бути дані з високою кардинальністю, а не в часових рядах.

## Версіювання подій і повідомлень

Асинхронні повідомлення складніші за REST: споживачів часто не видно й неможливо з ними домовитися, повідомлення можуть зберігатися роками (особливо за зберігання подій), а синхронного запиту для узгодження версії немає. Зазвичай поєднують кілька шаблонів.

**Версія в оболонці.** Загорніть кожне повідомлення в невелику оболонку з метаданими — назвою типу й версією схеми — навколо непрозорих даних. Споживачі маршрутизують обробку за ними:

```csharp
public record EventEnvelope(
    string Type,        // "OrderPlaced"
    int SchemaVersion,  // 2
    DateTimeOffset OccurredAt,
    JsonElement Payload);
```

**Реєстр схем.** В екосистемі Kafka **Confluent Schema Registry** централізовано зберігає всі версії схем. У кожному повідомленні лежить лише компактний ID схеми (кілька байтів), а не повна схема; споживач завантажує й кешує її за ID. Але справжня сила реєстру — **керування схемами**: налаштуйте режим сумісності (`BACKWARD`, `FORWARD`, `FULL` або їхні транзитивні варіанти) для кожної теми, і коли виробник намагається зареєструвати нову схему, **реєстр відхиляє її під час розгортання, якщо вона порушує задану сумісність**. Це вирішальна зміна: замість виявлення несумісної зміни в продакшені, коли споживач завершується помилкою, ви дізнаєтеся про неї, коли CI спробує зареєструвати схему. Перевірка контракту відсувається на ранні етапи, а команди виробника й споживача стають незалежними: один раз погодили політику сумісності й далі самостійно розвивають системи в її межах.

```csharp
// Producer side (Confluent.Kafka + Confluent.SchemaRegistry.Serdes)
using var registry = new CachedSchemaRegistryClient(
    new SchemaRegistryConfig { Url = "http://schema-registry:8081" });

using var producer = new ProducerBuilder<string, Order>(producerConfig)
    .SetValueSerializer(new AvroSerializer<Order>(registry))
    .Build();
// Registering an incompatible schema fails here, not in the consumer at 2 a.m.
```

**Зв’язок виробника й споживача.** Саме контракт повідомлення пов’язує команди — тому реєстри схем і правила сумісності важливі. Без їх забезпечення цей зв’язок *неявний і недокументований*: команда A змінює поле, команда B отримує збій і лише під час інциденту дізнається про залежність. Реєстр робить зв’язок *явним і обов’язковим*: правила стають інтерфейсом, а інструменти не дозволяють жодній стороні їх порушувати.

### Підвищення версії в Event Sourcing

Event Sourcing підвищує ставки: події — ваше **джерело істини**, вони зберігаються назавжди й відтворюються для відновлення стану. Через роки ви й далі читатимете події `OrderPlacedV1`, створені кодом, якого вже немає. Недбало переписати історію не можна, але й захаращувати агрегат умовами для старих форматів не хочеться.

Стандартний підхід — **підвищення версії (upcasting)**: під час читання перетворюйте старі версії подій на поточну форму *до* передавання доменній логіці, щоб вона бачила лише найновішу версію.

```csharp
public interface IUpcaster
{
    bool CanUpcast(string type, int version);
    (string Type, int Version, JsonElement Payload) Upcast(
        string type, int version, JsonElement payload);
}

// V1 had no Currency field; V2 adds it, defaulting legacy orders to USD.
public sealed class OrderPlacedV1ToV2 : IUpcaster
{
    public bool CanUpcast(string type, int version)
        => type == "OrderPlaced" && version == 1;

    public (string, int, JsonElement) Upcast(string type, int version, JsonElement payload)
    {
        var dict = payload.Deserialize<Dictionary<string, JsonElement>>()!;
        dict["currency"] = JsonSerializer.SerializeToElement("USD");
        return ("OrderPlaced", 2, JsonSerializer.SerializeToElement(dict));
    }
}
```

Поєднуйте upcaster-и в ланцюжок (V1 → V2 → V3), щоб кожен крок залишався малим і незалежно тестованим, а активні обробники працювали лише з найновішою версією. Старі події на диску незмінні; перетворення виконується під час читання.

## Конкретний приклад: безпечна еволюція події замовлення

Розвиньмо подію protobuf `OrderPlaced` через три реалістичні зміни й подивімося, як дотримуватися правил.

**Версія 1** — оригінал:

```proto
message OrderPlaced {
  int32 order_id = 1;
  string customer = 2;
  double total = 3;
}
```

**Версія 2** — потрібна валюта, а `total` замінюємо на `Money`, що пов’язує суму з валютою. *Не* змінюйте тип поля 3 і не використовуйте його повторно. Правильний варіант — **адитивна зміна**:

```proto
message OrderPlaced {
  int32 order_id = 1;
  string customer = 2;
  double total = 3;              // kept for old consumers; still populated
  string currency = 4;           // new, optional, defaults to "" -> treat as USD
  Money money = 5;               // new richer representation
}

message Money { double amount = 1; string currency_code = 2; }
```

Старі споживачі й далі читають `total` (поле 3) і не помічають полів 4 і 5. Нові віддають перевагу `money` (поле 5), тобто новішому поданню суми; якщо `money` немає (виробник ще старий), вони переходять до `total` і `currency`. Поля `currency` й `money` безпечні, бо незадані поля декодуються як типові значення, а старі читачі ігнорують невідомі теги. Отже, сумісність одночасно зворотна *й* пряма — повна; виробники й споживачі можуть розгортатися в будь-якому порядку.

**Версія 3** — тепер `total` і `currency` зайві, а всі виробники перейшли на `money`. Переконайтеся, що жоден чинний споживач не читає поля 3 або 4 (це операційна перевірка, а не лише перевірка коду: пошук тексту не знайде єдиний сервіс, який ще відстає), потім видаліть їх і **назавжди зарезервуйте номери**:

```proto
message OrderPlaced {
  reserved 3, 4;
  reserved "total", "currency";
  int32 order_id = 1;
  string customer = 2;
  Money money = 5;
}
```

Поле 5 так і залишилося 5. Ми не змінювали номери, не використовували їх повторно й не міняли типи. Кожен крок можна було розгорнути незалежно. Ось як на практиці розвивають схему безпечно: послідовність адитивних змін, свідомий період виведення старого з використання й постійне резервування номерів — жодних масових перейменувань одним випуском.

> **Контрактне тестування** — перевірка за допомогою інструментів на кшталт **Pact**, чи справді певний споживач і виробник погоджуються щодо контракту, — додатковий рівень захисту до всього, що розглянуто в цьому розділі. Правила сумісності схем доводять, що схеми *можна* безпечно розвивати; контрактні тести доводять, що дві конкретні служби *зараз* справді узгоджені. Контрактне тестування зі споживачами докладно розглянуто в [Розділі 25](#contract-testing-killing-the-integration-test-explosion).

Досі йшлося про те, *що* передавати мережею й як це змінюється. Далі — про те, *як* передавати дані, якщо JSON у схемі запит/відповідь не підходить: внутрішні виклики з великим трафіком і передавання даних сервером клієнтам.

## gRPC

**gRPC** — двійковий RPC-фреймворк на основі HTTP/2 і Protocol Buffers із контрактом, що задається до написання коду. Ви визначаєте сервіс у файлі `.proto`; інструменти генерують строго типізований код клієнта й сервера. Він значно компактніший і швидший за JSON поверх HTTP/1.1 та підтримує **потокове передавання** в обох напрямах.

```proto
service PriceService {
  rpc GetPrice (PriceRequest) returns (PriceReply);           // Unary
  rpc StreamPrices (PriceRequest) returns (stream PriceReply); // Server streaming
}
```

Поняття «контракт до коду» стає конкретним, якщо побачити обидві сторони. За цим `.proto` під час збірки створюється базовий клас; ваша реалізація — лише ще одна кінцева точка вже знайомого конвеєра:

```csharp
public class PriceGrpcService : PriceService.PriceServiceBase   // Generated base class.
{
    public override Task<PriceReply> GetPrice(PriceRequest req, ServerCallContext ctx) =>
        Task.FromResult(new PriceReply { Symbol = req.Symbol, Price = 42.17 });

    public override async Task StreamPrices(PriceRequest req,
        IServerStreamWriter<PriceReply> stream, ServerCallContext ctx)
    {
        while (!ctx.CancellationToken.IsCancellationRequested)
        {
            await stream.WriteAsync(new PriceReply { Symbol = req.Symbol, Price = Next() });
            await Task.Delay(1000, ctx.CancellationToken);
        }
    }
}
// app.MapGrpcService<PriceGrpcService>();
```

Клієнт має дзеркальний вигляд: без URL і серіалізації — лише виклики методів, а серверний потік доступний через `await foreach`:

```csharp
using var channel = GrpcChannel.ForAddress("https://prices.internal");
var client = new PriceService.PriceServiceClient(channel);

var reply = await client.GetPriceAsync(new PriceRequest { Symbol = "MSFT" }); // Unary

using var call = client.StreamPrices(new PriceRequest { Symbol = "MSFT" });
await foreach (var price in call.ResponseStream.ReadAllAsync(ct))             // Server streaming
    Render(price);
```

HTTP/2 — не внутрішня деталь реалізації: саме він це уможливлює. Багато паралельних **мультиплексованих потоків** в одному з’єднанні забезпечують роботу тривалих потокових викликів ([у Розділі 5](#http11-vs-http2-vs-http3-a-history-of-fixing-head-of-line-blocking) докладно розглянуто HTTP/2). З ним пов’язані й дві операційні пастки gRPC. По-перше, потрібен **наскрізний HTTP/2**: проксі, що знижує версію до HTTP/1.1, порушує роботу gRPC. По-друге, канал — це довготривале з’єднання, тож балансувальник L4 (рівня з’єднань, [Розділ 26](#load-balancers-l4-vs-l7)) прив’язує *всі* виклики клієнта до одного сервера. Щоб розподіляти *виклики*, а не *з’єднання*, потрібне балансування L7 із підтримкою gRPC (Envoy, YARP, Linkerd).

Замість аналогів HTTP використовують дві ідіоми. **Крайні строки** — це тайм-аути gRPC: `client.GetPriceAsync(req, deadline: DateTime.UtcNow.AddSeconds(3))`. На відміну від `HttpClient.Timeout`, вони *передаються далі*: залишок бюджету супроводжує виклик, а на сервері доступний у `ServerCallContext.CancellationToken` (тому його враховано в прикладі потоку; дисципліна з [розповсюдженням `CancellationToken` із Розділу 5](#cancellationtoken-propagation) тут так само застосовується). Помилки передаються як `RpcException` із `StatusCode` (`NotFound`, `Unavailable`, `DeadlineExceeded` тощо), а не кодами статусу HTTP.

Використовуйте gRPC для **внутрішнього обміну між сервісами**, коли контролюєте обидві сторони й потрібні продуктивність і строгий контракт, або для потокових даних. Він не підходить для браузерів (є gRPC-Web і перетворення JSON, але вони зменшують переваги) та публічних API, де важливі читабельний JSON і широка підтримка інструментів. Практичне правило: **gRPC усередині центру обробки даних, REST — на периферії**. Правила еволюції схеми protobuf (як додати поля, не порушивши вже розгорнутих клієнтів) наведено в розділі [Protocol Buffers](#protocol-buffers-schema-first-binary) і прикладі події замовлення вище.

## Обмін даними в реальному часі: WebSockets, SSE чи довге опитування

Звичайний HTTP ініціює клієнт: сервер не може сам надіслати дані. Для чатів, панелей у реальному часі й сповіщень потрібен канал від сервера до клієнта. Є три способи, від найпростішого до найпотужнішого:

- **Довге опитування (long-polling)** — клієнт надсилає запит, а сервер *утримує його відкритим*, поки з’являться дані (або сплине тайм-аут), а потім відповідає; клієнт одразу повторює запит. Імітує push через звичайний HTTP і працює всюди, але неефективне через постійні запити й накладні витрати заголовків.
- **Server-Sent Events (SSE)** — одна довготривала відповідь HTTP, якою сервер із часом надсилає події (`text/event-stream`). Потік **односпрямований** (лише сервер → клієнт), лише текстовий, зате простий, автоматично перепідключається й проходить звичайну інфраструктуру HTTP.
- **WebSockets** — справді **повнодуплексне двостороннє** з’єднання. Клієнт надсилає HTTP-запит із `Upgrade: websocket`; сервер відповідає `101 Switching Protocols`; далі обидві сторони довільно обмінюються повідомленнями через постійне TCP-з’єднання. Це правильний інструмент, коли клієнт теж часто надсилає дані (багатокористувацька гра, спільне редагування, чат).

У .NET ці механізми рідко пишуть вручну. **SignalR**, розглянутий у наступному розділі, — високорівнева бібліотека реального часу, яка обгортає всі три: віддає перевагу WebSockets і *автоматично перемикається* на SSE або довге опитування, якщо з’єднання не вдалося оновити (наприклад, корпоративний проксі блокує WebSockets).

> **Рекомендація:** використовуйте SSE, коли потрібен лише потік сервер → клієнт (сповіщення, поступ виконання, актуальні ціни): він легший і простіший. Обирайте WebSockets/SignalR, коли клієнт часто відповідає. Уникайте ручного довгого опитування, якщо лише не мусите підтримувати стару інфраструктуру.

## SignalR

**SignalR** забезпечує двосторонній зв’язок у реальному часі: сервер може надсилати дані клієнтам, а не лише відповідати на запити. Він абстрагує WebSockets і переходить на Server-Sent Events чи довге опитування (транспорти порівняно в попередньому розділі), тож ви працюєте з простим API *хабів*.

```csharp
public class NotificationsHub : Hub
{
    public override async Task OnConnectedAsync()
    {
        // A "group" is just a named set of connection ids, tracked server-side.
        await Groups.AddToGroupAsync(Context.ConnectionId, "traders");
        await base.OnConnectedAsync();
    }

    public async Task SendToGroup(string group, string message) =>   // Client → server.
        await Clients.Group(group).SendAsync("notify", message);     // Server → client(s).
}
// app.MapHub<NotificationsHub>("/hubs/notifications");
```

Друга частина розмови — клієнт: він підключається один раз і *реєструє обробники за назвою події*. Наведений вище `"notify"` — не магічне значення, а назва, на яку підписався клієнт:

```ts
const conn = new signalR.HubConnectionBuilder()
    .withUrl("/hubs/notifications").withAutomaticReconnect().build();
conn.on("notify", msg => showToast(msg));          // Handles SendAsync("notify", ...).
await conn.start();
await conn.invoke("SendToGroup", "traders", "hi"); // Calls the hub method.
```

Отже, модель симетрична: методи хаба викликає клієнт → сервер, а `Clients.*.SendAsync` запускає на клієнті обробник за назвою. ([Розділ 34](#real-time-with-signalr) налаштовує його з повноцінним клієнтом TypeScript.) Ще одна частина картини: більшість реальних повідомлень походить не з хаба — завершується фонова задача, відправляється замовлення. У таких випадках упровадьте `IHubContext<NotificationsHub>` у будь-який компонент і використовуйте той самий API `Clients`:

```csharp
public class OrderShippedHandler(IHubContext<NotificationsHub> hub)
{
    public Task Handle(OrderShipped e) =>
        hub.Clients.Group("traders").SendAsync("notify", $"Order {e.Id} shipped");
}
```

SignalR підходить для панелей, чатів, спільної роботи наживо, сповіщень і поступу завдань. Обмеження під час масштабування: з’єднання **зберігають стан і закріплені** за одним сервером. Якщо запущено три екземпляри, сервер 2 не може сповістити користувача, чий WebSocket під’єднаний до сервера 1. **Backplane** (pub/sub у Redis) розв’язує це, повторно публікуючи кожне повідомлення на кожен сервер, а ті пересилають його власним з’єднанням; або Azure SignalR Service повністю знімає з серверів обробку з’єднань.

```
   client A ──ws── server 1 ──┐
   client B ──ws── server 2 ──┼── Redis backplane (pub/sub)
   client C ──ws── server 3 ──┘
   server 2 publishes → all servers receive → each pushes to its own sockets
```

> **Нюанс.** Якщо явно не обмежити транспорти лише WebSockets, резервні транспорти використовують кілька HTTP-запитів для кожного з’єднання, тому балансувальнику потрібні **липкі сеанси**.

### Як обрати між REST, gRPC і SignalR

| Потреба | Рекомендація |
|---|---|
| Публічне API, різнорідні клієнти, дані, які легко налагоджувати | REST + JSON |
| Внутрішні виклики сервісів, строгий контракт, продуктивність, потоки | gRPC |
| Надсилання даних браузерам (панелі, чати, сповіщення) | SignalR |
| Лише потік від сервера до клієнта, мінімум складових | SSE (див. *Обмін даними в реальному часі* вище) |

## Підсумок

Серіалізація — місце зустрічі моделі даних із зовнішнім світом, а формат обирають як компроміс між сумісністю, розміром, швидкістю й еволюцією. На периферії, де працюють люди й різноманітні клієнти, використовуйте текст (JSON через `System.Text.Json`, бажано зі згенерованим кодом); для обміну між машинами всередині системи — двійкові дані (Protobuf для gRPC і міжмовного обміну, MessagePack для швидкого обміну між .NET, Avro для конвеєрів Kafka). Але формат — лише кодування: довгострокова складність полягає в еволюції *контракту* без порушення роботи систем, які від нього залежать. Опануйте напрями сумісності, ніколи не змінюйте ідентичність полів, додавайте необов’язкові поля з типовими значеннями, ігноруйте незнайомі дані й надавайте перевагу розширенню й звуженню перед випуском нової версії. Якщо версія неминуча, оберіть один варіант, оголошуйте застарілість у відповідях і додавайте до телеметрії версію та споживача, щоб згодом вивести її з експлуатації. Для подій використовуйте реєстр схем і upcaster-и, щоб забезпечити й поглинати зміни. Обирайте транспорт для межі: REST на периферії, gRPC усередині, SSE чи SignalR, коли сервер має сам надсилати дані. Тоді ваші контракти зможуть розвиватися роками без сповіщення о другій ночі.
