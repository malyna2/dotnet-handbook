# Розділ 17: Внутрішня будова runtime й продуктивність

Кожен запит, який обробляє сервіс .NET, використовує два спільні ресурси runtime (середовища виконання): невеликий thread pool (пул потоків) і купу з поколіннями. Обидва оптимізовано для коротких операцій. Потік, зайнятий очікуванням, або об’єкт, який зберігався трохи довше, затримує кожен інший запит. Після цього розділу ви зможете передбачати поведінку сервісу, коли його потоки блокуються або купа постійно змінюється; підтверджувати причину лічильниками, tracing (трасуванням) і дампом; обирати між налаштуванням runtime й зміною коду та пояснювати команді вартість кожного рішення.

Розділ спирається на Частину 1: стек, купу й покоління garbage collector (збирача сміття) з [Розділу 3](#chapter-3-how-net-runs-your-code), state machine (машину станів), thread pool і синхронне очікування асинхронного коду з [Розділу 4](#chapter-4-async-essentials), типи-значення, boxing і замикання з [Розділу 1](#chapter-1-c-essentials). Спочатку розглянемо дисципліну (спочатку вимірюйте, а потім виконуйте бенчмаркінг і профілювання), бо всі наступні методи налаштування доречні лише тоді, коли на них указує вимірювання. Потім розберемо механізми, які показують ці вимірювання: garbage collector, виділення пам’яті й інструменти для його зменшення, thread pool і модель пам’яті під навантаженням, `ValueTask`, паралелізм і канали. Наприкінці — частини runtime, що впливають на запуск і deployment (розгортання): reflection і генератори коду під час компіляції, JIT, ReadyToRun і Native AOT, завантаження збірок. Продуктивність доступу до даних (EF Core, кешування) розглянуто в [Розділі 18](#chapter-18-data-in-depth).

## Золоте правило: вимірюйте, не вгадуйте

Людська інтуїція щодо продуктивності відома своєю ненадійністю — майже комічною. Процесор, на якому працює ваш код, — неймовірно складна машина: позачергове виконання, кілька рівнів кешу, передбачення переходів, JIT-компілятор, який переписує IL під час роботи, і garbage collector, який зупиняє потоки в моменти, неможливі для передбачення за вихідним кодом. Обмірковувати все це подумки — як передбачати погоду, дивлячись на одну хмару.

> **Найважливіше речення в цьому розділі:** спочатку вимірюйте, потім оптимізуйте. Якщо оптимізувати до вимірювання, це не інженерія — це азартна гра, де ставкою є ваш час.

Фразу Дональда Кнута «передчасна оптимізація — корінь усіх бід» цитують так часто, що вона втратила гостроту. Часто забувають продовження, де сказано, що оптимізації *варто* відкладати в «критичних 3%». Сенс не в тому, що оптимізація погана, а в тому, що оптимізувати не те гірше, ніж нічого не робити: це забирає час, ускладнює код, породжує помилки й ускладнює читання, поки справжнє bottleneck (вузьке місце) залишається недоторканим.

Уявіть приймальне відділення лікарні. Пацієнт приходить із видимим синцем на руці, але лікар не починає лікувати саме його. Спершу вимірює життєві показники, виявляє загрозу життю й лікує *її*. Із кодом так само: повільне місце майже ніколи не там, де ви очікуєте. За відомим «правилом 90/10» близько 90% часу виконання припадає приблизно на 10% коду. Ваше завдання — знайти ці 10%, перш ніж щось змінювати.

> **Рекомендація:** перш ніж оптимізувати, визначте бюджет продуктивності й вихідне значення. «Ця endpoint (кінцева точка) має відповідати швидше ніж за 200 мс на 95-му перцентилі за 500 одночасних користувачів» — вимірювана мета. «Зробити швидше» — ні.

Послідовність дисциплінованої оптимізації:

1. **Визначте мету.** Затримка? Пропускна здатність? Обсяг пам’яті? Час запуску? Ці цілі можуть конфліктувати.
2. **Виміряйте поточний стан.** Отримайте вихідне число справжнім інструментом.
3. **Знайдіть bottleneck.** Профілювальник покаже, на що насправді витрачаються час і пам’ять.
4. **Сформулюйте гіпотезу й змініть одну річ.** Лише одну.
5. **Виміряйте ще раз.** Чи справді стало краще? Наскільки? Чи варте поліпшення доданої складності?
6. **Повторіть або зупиніться.** Досягли бюджету — зупиніться. Не поліруйте зайве.

Наступні два розділи підготують вас до кроків 2, 3 і 5: бенчмаркінгу підозрілого фрагмента коду й профілювання запущеної системи, щоб визначити, що саме треба підозрювати. Решта розділу пояснює механізми кроку 4, щоб, коли профілювальник вкаже на певне місце, ви знали, за який важіль узятися.

## Бенчмаркінг за допомогою BenchmarkDotNet

Для вимірювання продуктивності невеликої ізольованої ділянки коду — методу, алгоритму чи серіалізації — стандартом де-факто в .NET є **BenchmarkDotNet**. Вручну написати правильний мікробенчмарк оманливо складно. Потрібно враховувати прогрів JIT, запобігати видаленню непотрібного коду, запускати достатньо ітерацій для статистично значущих результатів і відокремлювати код від шуму garbage collector. BenchmarkDotNet робить усе це за вас.

Ось повний приклад запуску, який порівнює три способи об’єднання рядків у циклі:

```csharp
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;
using System.Text;

[MemoryDiagnoser] // Reports allocations and GC collections
public class StringConcatBenchmarks
{
    [Params(100, 1000)] // Runs every benchmark for each value
    public int N;

    private string[] _parts = null!;

    [GlobalSetup]
    public void Setup() =>
        _parts = Enumerable.Range(0, N).Select(i => i.ToString()).ToArray();

    [Benchmark(Baseline = true)]
    public string NaiveConcat()
    {
        var result = string.Empty;
        foreach (var part in _parts)
            result += part; // Allocates a new string every iteration
        return result;
    }

    [Benchmark]
    public string StringBuilderConcat()
    {
        var sb = new StringBuilder();
        foreach (var part in _parts)
            sb.Append(part);
        return sb.ToString();
    }

    [Benchmark]
    public string StringJoin() => string.Join("", _parts);
}

public class Program
{
    public static void Main() => BenchmarkRunner.Run<StringConcatBenchmarks>();
}
```

Зверніть увагу на кілька особливостей цього коду, адже важливо розуміти механізми:

- **`[MemoryDiagnoser]`** — атрибут, який застосовують майже в кожному бенчмарку. Він додає стовпці з кількістю байтів, виділених за операцію, і кількістю збирань сміття Gen0/Gen1/Gen2. Виділення пам’яті часто є прихованими витратами, а цей атрибут робить їх видимими.
- **Кожен метод бенчмарку повертає значення.** Результат заважає JIT вирішити, що робота не потрібна, і повністю її видалити (усунути непотрібний код). Якби бенчмарк оптимізувався до порожньої операції, ви вимірювали б швидкість повернення нуля.
- **`[Params]`** перебирає кілька розмірів вхідних даних, щоб ви побачили, як кожен підхід *масштабується*, а не лише його продуктивність для одного розміру.
- **Налаштування відокремлено.** `[GlobalSetup]` виконується один раз і не вимірюється; час обчислюють лише для тіла `[Benchmark]`.

### Як читати результати

BenchmarkDotNet виводить таблицю, що приблизно має такий вигляд (числа наведено для прикладу):

```
| Method              | N    |         Mean |   Ratio |   Allocated |
|-------------------- |----- |-------------:|--------:|------------:|
| NaiveConcat         | 100  |     3.512 us |    1.00 |    50.42 KB |
| StringBuilderConcat | 100  |     0.681 us |    0.19 |     1.66 KB |
| StringJoin          | 100  |     0.402 us |    0.11 |     0.45 KB |
| NaiveConcat         | 1000 |   198.400 us |    1.00 |  4980.10 KB |
| StringBuilderConcat | 1000 |     6.240 us |    0.03 |    16.30 KB |
| StringJoin          | 1000 |     4.100 us |    0.02 |     4.30 KB |
```

Навчіться читати цю таблицю, як лікар читає діаграму:

- **Mean** — середній час на операцію. `us` — мікросекунди, `ns` — наносекунди, `ms` — мілісекунди; перевірте одиниці, вони різняться в різних таблицях.
- **Ratio** порівнює кожен рядок із бенчмарком `Baseline = true`. `0.03` означає, що StringBuilder витратив 3% часу наївного варіанта — тобто більш ніж у 30 разів швидший.
- **Allocated** — пам’ять на операцію. Зауважте: наївне об’єднання за N=1000 виділяє майже 5 МБ, щоб створити один рядок, бо кожен `+=` створює новий рядок з усім накопиченим вмістом. За зовні невинним кодом ховається квадратична (O(n²)) схема виділення пам’яті.
- BenchmarkDotNet також показує стовпці **похибки** й **стандартного відхилення** (вище їх не наведено). Якщо похибка велика відносно середнього значення, бенчмарк зашумлений: закрийте фонові програми й запустіть його знову.

> **Пастка:** ніколи не запускайте бенчмарки в режимі Debug чи під налагоджувачем. BenchmarkDotNet відмовиться й попередить вас, але загальне правило стосується всіх вимірювань: **завжди вимірюйте збірки Release.** У збірках Debug вимкнено оптимізації JIT, тому числа не мають сенсу.

> **Пастка:** мікробенчмарки вимірюють код ізольовано, з прогрітими кешами й без конкуренції. Метод, який виграє мікробенчмарк, може програти в продакшені, де кеш процесора холодний, а ресурси ділять інші потоки. Мікробенчмарки відповідають на запитання «який алгоритм швидший?», а не «чому сервіс повільний?». Для другого запитання потрібне профілювання.

## Профілювання: пошук bottleneck в запущеній системі

Бенчмаркінг вимірює код, який ви вже підозрюєте. **Профілювання** підказує, що саме підозрювати. Коли реальний сервіс працює повільно, під’єднайте профілювальник і подивіться, куди насправді йдуть час і пам’ять. .NET постачається з чудовим набором безкоштовних кросплатформних діагностичних інструментів командного рядка (їх установлюють через `dotnet tool install -g`), а також потужнішими графічними засобами.

Ось набір інструментів і, що важливо, *для чого призначений кожен*:

| Інструмент | Що робить | Коли застосовувати… |
|------|-------------|---------------------|
| **dotnet-counters** | Поточні метрики з майже нульовими накладними витратами: процесор, швидкість виділення пам’яті, паузи GC, queue (черга) thread pool, exceptions (винятки) за секунду, частота запитів ASP.NET. | Потрібен швидкий звіт про «життєві показники» процесу. Перший засіб реагування. |
| **dotnet-trace** | Протягом певного періоду збирає вибірки стеків усіх потоків і записує events (події) runtime; створює tracing для аналізу офлайн. | Треба з’ясувати, які *методи* споживають процесор, не встановлюючи графічних засобів на сервер. |
| **dotnet-dump** | Створює й аналізує дамп пам’яті процесу за допомогою команд SOS (`dumpheap`, `gcroot`). | Система зависла, виникло deadlock (взаємне блокування) або потрібно перевірити керовану купу й корені об’єктів. |
| **dotnet-gcdump** | Знімає легкий знімок активної купи GC для аналізу пам’яті. | Ви підозрюєте **витік пам’яті** й хочете побачити, екземпляри яких типів накопичуються. |
| **PerfView** | Потужний безкоштовний профілювальник на основі Windows ETW для процесора, виділення пам’яті й GC. Високий поріг входження, глибоке розуміння. | Потрібен серйозний аналіз виділення пам’яті й GC у Windows. |
| **Профілювальник Visual Studio** | Інтегровані засоби аналізу процесора, виділення пам’яті й БД зі зручним інтерфейсом. | Ви вже у VS і хочете покрокового наочного аналізу. |
| **JetBrains dotTrace / dotMemory** | Найкращі комерційні профілювальники процесора (dotTrace) і пам’яті (dotMemory) із чудовою візуалізацією. | Потрібен найзручніший інтерфейс для аналізу часової шкали й дерева викликів або знімків пам’яті зі шляхами утримання. |

Типова робота в полі: спершу запустіть **dotnet-counters**, щоб підтвердити симптом (процесор постійно завантажений? виділення пам’яті надзвичайно інтенсивне? довгі паузи GC?). Результат підкаже, до якого глибшого інструмента перейти. Високе завантаження процесора → **dotnet-trace** або dotTrace, щоб знайти гарячий метод. Зростання пам’яті → **dotnet-gcdump** або dotMemory, щоб виявити тип, екземпляри якого накопичуються. Зависання → **dotnet-dump**, щоб перевірити стеки потоків.

```bash
# Watch live vital signs of a running process (PID 12345)
dotnet-counters monitor -p 12345 --counters System.Runtime,Microsoft.AspNetCore.Hosting

# Collect a 20-second trace; it writes <process>_<timestamp>.nettrace for PerfView,
# Visual Studio, or speedscope after `dotnet-trace convert --format Speedscope`
dotnet-trace collect -p 12345 --duration 00:00:20

# Snapshot the heap to hunt a leak; open in dotMemory or PerfView
dotnet-gcdump collect -p 12345
```

> **Нюанс.** Типовий сеанс `dotnet-trace` приблизно 100 разів на секунду збирає вибірки стеків *усіх* потоків, зокрема тих, що чекають (у dotnet-trace 10 профіль називається `dotnet-sampled-thread-time`). Завдяки цьому він добре виявляє зависання або виснаження thread pool: заблоковані потоки накопичуються на тому самому кадрі стека. Але під час розслідування завантаження процесора це вводить в оману: потік у `Monitor.Wait` дає стільки ж вибірок, як потік, що крутиться в гарячому циклі. Для процесора в Linux у dotnet-trace 10 додано `dotnet-trace collect-linux --profile cpu-sampling`; команда збирає вибірки через ядро `perf_events`, тож показує лише запущені потоки (потрібні права адміністратора). У Windows те саме дають стеки процесора PerfView.

> **Рекомендація:** профілюйте середовище, якомога подібніше до продакшену: та сама версія runtime, збірка Release, репрезентативний обсяг даних. Профілювання локальної бази розробки з десятьма рядками ніколи не виявить запит, що помирає на десяти мільйонах.

## Поглиблений розгляд garbage collector

[У Розділі 3](#chapter-3-how-net-runs-your-code) розглянуто модель: трасувальний garbage collector з поколіннями й ущільненням; gen0, gen1 і gen2; що запускає збирання; фіналізацію й причину, чому `GC.Collect()` майже завжди неправильний вибір. Тут розглянуто, як ця модель працює під навантаженням сервера: де зберігаються великі об’єкти, як два режими GC розподіляють роботу між ядрами й як повне збирання відбувається без зупинки застосунку.

### Купа великих об’єктів (LOH)

Об’єкти розміром **85 000 байтів або більше** виділяються не в Gen 0, а в окремій **купі великих об’єктів (LOH)**. Поріг існує тому, що ущільнення великих об’єктів (фізичне копіювання, скажімо, масиву на 10 МБ) дороге. Через це історично LOH типово **не ущільнювали**; вона використовувала список вільних блоків, як традиційний `malloc`, і тому могла *фрагментуватися*: загальної кількості вільних байтів вистачає, але немає одного суміжного блока, достатнього для наступного великого масиву.

Важливо, що **LOH збирається лише під час збирання Gen 2**. Тож часто виділювані великі буфери спричиняють дорогі повні збирання. Типовий винуватець — постійне виділення великих масивів або буферів `MemoryStream`.

```csharp
// Anti-pattern: churning the LOH
for (int i = 0; i < 1000; i++)
{
    var buffer = new byte[100_000]; // >85KB → LOH, triggers Gen 2 pressure
    Process(buffer);
}

// Better: pool and reuse large buffers
var pool = System.Buffers.ArrayPool<byte>.Shared;
for (int i = 0; i < 1000; i++)
{
    byte[] buffer = pool.Rent(100_000);
    try { Process(buffer.AsSpan(0, 100_000)); }
    finally { pool.Return(buffer); }
}
```

За потреби можна примусово ущільнити LOH (`GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;` перед `GC.Collect()`), але це важкий інструмент для виняткових випадків, а не звичайна практика.

### GC робочих станцій і серверів

.NET постачається з двома «різновидами» GC; правильний вибір може істотно змінити пропускну здатність і затримку.

- **GC робочих станцій** оптимізовано для чутливості клієнтських застосунків. Він використовує одну купу GC і (в режимі без паралельного збирання) збирає сміття в потоці, який це спричинив. Невеликі накладні витрати на пам’ять; добре підходить для настільних програм і середовищ із невеликою кількістю ядер.
- **Серверний GC** створює **по одній купі й окремому потоку GC на кожне логічне ядро процесора** (до певної межі). Збирання відбуваються паралельно на цих потоках, істотно збільшуючи пропускну здатність багатоядерних серверів. Ціна — більше споживання пам’яті (кілька куп, кожна зі своїм бюджетом Gen 0); він розрахований на те, що процес може домінувати на машині.

```xml
<!-- In the .csproj -->
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
  <ConcurrentGarbageCollection>true</ConcurrentGarbageCollection>
</PropertyGroup>
```

> **Рекомендація:** ASP.NET Core типово використовує серверний GC, і зазвичай це правильний вибір для сервісів, орієнтованих на пропускну здатність. Раніше попереднє виділення окремої купи на кожне ядро серверним GC марнувало пам’ять у **контейнерах із жорсткими обмеженнями або малою кількістю ядер**, тож звичайним обхідним рішенням було перемикання таких workloads (робочих навантажень) на GC робочих станцій. **DATAS** (Dynamic Adaptation To Application Sizes) — необов’язкова функція в .NET 8, увімкнена типово із серверним GC від .NET 9, — здебільшого розв’язує проблему: кількість і розмір куп GC динамічно узгоджуються з фактичним навантаженням замість попереднього виділення купи на кожне ядро. У .NET 9 і новіших версіях спершу виміряйте результати, перш ніж перемикати невеликі контейнери на GC робочих станцій: DATAS — передбачене виправлення, а цей прийом здебільшого залишився в історії.

### Фоновий (паралельний) GC

Проблема збирання Gen 2 у тому, що сканування всієї купи може тривати довго; якщо на цей час призупинити всі потоки застосунку («зупинити світ»), виникнуть стрибки затримки. **Фоновий GC** розв’язує це для Gen 2: більша частина збирання Gen 2 відбувається *паралельно* у фоновому потоці, поки потоки застосунку продовжують роботу. Потоки застосунку зупиняються лише на короткий час (щоб створити узгоджений знімок і завершити збирання). Збирання Gen 0 і Gen 1 залишаються блокувальними, але проходять достатньо швидко. Фоновий GC увімкнено типово; саме він дає змогу сучасному .NET мати короткі паузи навіть на великих купах.

## Пам’ять і виділення: непомітний вбивця продуктивності

У керованому .NET пам’ять вручну не звільняють — цим займається garbage collector. Це полегшує розробку й водночас спричиняє найпоширеніші неочевидні проблеми продуктивності. У цьому розділі механіку GC перетворено на запитання, яке ставить профілювальник: які виділення пам’яті цей hot path (гарячий шлях) може припинити?

### Чому виділення коштують

Виділити невеликий об’єкт у керованій купі дешево: зазвичай це лише пересування вказівника. Витрати з’являються *пізніше*, коли GC має його прибрати; під час збирання потоки застосунку можуть призупинятися (про покоління йдеться в [Розділі 3](#chapter-3-how-net-runs-your-code), про LOH, серверний GC і DATAS — у попередньому підрозділі).

Отже, справжня вартість виділень — це **навантаження на GC**: що більше сміття ви створюєте, то частіше запускається GC, то більше процесорного часу він забирає й то більше стрибків затримки (пауз) відчувають користувачі. Hot path, що виділяє тимчасовий об’єкт на кожну ітерацію, може спричинити тисячі збирань Gen 0 за секунду. Окреме виділення було дешевим; сукупна вартість збирання — ні.

> **Модель для розуміння:** кожне виділення — невелика позика в GC, яку доведеться повернути з відсотками в непередбачуваний момент. Трохи позичати нормально. Мільйони позик за секунду означають, що збирач постійно працює — забирає такти процесора й часом заморожує потоки.

Тож мета для hot paths — не «ніколи нічого не виділяти», а **не виділяти зайвого й багаторазово**. Один із важелів — сам тип: невеликий `struct`, розміщений вбудовано, не потребує виділення купи; boxing щоразу потребує ([Розділ 1](#chapter-1-c-essentials) розглядає обидва випадки). Ось інші засоби, доступні в .NET.

### Span<T>, Memory<T> і stackalloc: зрізи без копіювання

`Span<T>` — це `ref struct`, що представляє **неперервну область пам’яті**, тобто зріз, незалежно від того, чи пам’ять належить керованому масиву, буферу `stackalloc` або нативній пам’яті. Оскільки це лише *представлення* (посилання й довжина), створення зрізу нічого не виділяє й не копіює: зріз — нове вікно над *тією самою* пам’яттю.

```csharp
int[] array = { 10, 20, 30, 40, 50 };
Span<int> span = array;
Span<int> middle = span.Slice(1, 3);   // view over {20, 30, 40}, no allocation
middle[0] = 99;                        // array[1] is now 99 — same memory
```

Розгляньмо розбір рядка, поля якого розділено комами. Наївний підхід із `Split` виділяє масив і окремий рядок для кожного поля:

```csharp
// Allocates: a string[] and one string per part
string[] parts = line.Split(',');
int id = int.Parse(parts[0]);
```

Підхід зі span розбирає дані безпосередньо й не виділяє пам’яті в купі:

```csharp
public static int ParseFirstField(ReadOnlySpan<char> line)
{
    int comma = line.IndexOf(',');
    ReadOnlySpan<char> firstField = comma >= 0 ? line[..comma] : line;
    return int.Parse(firstField); // int.Parse has a span overload — no substring allocated
}
```

`firstField` — лише посилання й довжина в послідовності символів початкового рядка. Багато API BCL (`int.Parse`, `Utf8Formatter`, `Encoding`, `string.Create`) приймають span, щоб працювати зі зрізами без виділення пам’яті під підрядки.

**`stackalloc`** виділяє буфер безпосередньо в стеку; присвоєний `Span<T>`, він стає швидким буфером для тимчасових даних, якого GC не бачить:

```csharp
Span<byte> buffer = stackalloc byte[128];   // stack allocation, zero heap pressure
Utf8Formatter.TryFormat(12345, buffer, out int written, default);
// use buffer[..written] with no allocation
```

Оскільки `Span<T>` — це `ref struct` (правило пояснено в [Розділі 1](#chapter-1-c-essentials)), він живе лише в стеку: його не можна використовувати як поле класу, упаковувати, зберігати в масиві чи переносити через `await` або `yield`. Якщо потрібні такі можливості — наприклад, буфер треба зберегти під час асинхронного виклику, — використовуйте **`Memory<T>`**, його різновид, який можна зберігати в купі, і отримуйте з нього `Span<T>` (`memory.Span`) саме в момент доступу до даних.

> **Пастка.** `Span<T>` не можна переносити через `await` або `yield`, захоплювати в лямбді чи зберігати в купі. Це перевіряє компілятор. Якщо ви намагаєтеся обійти цю перевірку, скористайтеся `Memory<T>`: правило захищає посилання `Span<T>` на стекову пам’ять.

> **Рекомендація.** Застосовуйте `Span<T>` для розбору, серіалізації й роботи з буферами, щоб прибрати проміжні виділення. Розмір `stackalloc` має бути невеликим і обмеженим: стек має межу (зазвичай близько 1 МБ), а його переповнення завершує процес без exception, який можна перехопити.

### Пул об’єктів: повторне використання замість повторного виділення

Коли буфери чи об’єкти справді потрібні багаторазово, найшвидше виділення — те, якого ви уникнули. **Пулінг** бере об’єкт зі спільного резерву, використовує його й повертає назад, замість створювати й відкидати.

`ArrayPool<T>` — основний засіб для тимчасових масивів і буферів:

```csharp
public static void ProcessLargeBuffer(Stream stream, int size)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(size);
    try
    {
        // Note: Rent may return a LARGER array than requested.
        int read = stream.Read(buffer, 0, size);
        // ... work with buffer[0..read] ...
    }
    finally
    {
        // Always return, even on exception. clearArray: true if it held secrets.
        ArrayPool<byte>.Shared.Return(buffer);
    }
}
```

Правильне використання пулу визначають два правила. Перше: **`Rent` може повернути масив, більший за запитаний** — завжди окремо відстежуйте логічну довжину й не припускайте, що `buffer.Length == size`. Друге: **завжди викликайте `Return` у `finally`**. Якщо забути повернути масив, пошкодження не станеться, але пул непомітно втратить сенс і почне виділяти нові масиви.

Для пулінгу складніших об’єктів (парсерів, builder-ів, DTO) використовуйте `Microsoft.Extensions.ObjectPool`:

```csharp
var pool = new DefaultObjectPoolProvider().Create<StringBuilder>(
    new StringBuilderPooledObjectPolicy());

StringBuilder sb = pool.Get();
try
{
    sb.Append("reusable");
    // ... use sb ...
}
finally
{
    pool.Return(sb); // Policy resets it for the next caller
}
```

> **Рекомендація:** застосовуйте пул лише тоді, коли профілювання показало, що виділення справді коштують дорого. Пулінг додає складності й ризик використання об’єкта після повернення до пулу. Він виправданий для великих або надзвичайно часто потрібних буферів, а не для поодинокого малого об’єкта.

### StringBuilder і механізми рядків

Рядки .NET незмінні, тож кожна «зміна» створює новий рядок. Як показав попередній бенчмарк, об’єднання в циклі за допомогою `+=` має квадратичну складність і за часом, і за кількістю виділень. `StringBuilder` підтримує внутрішній буфер зі змінним розміром і створює кінцевий рядок лише один раз, перетворюючи квадратичний шторм виділень O(n²) на лінійний.

Нюанс, відомий senior-розробникам: для **невеликої фіксованої кількості об’єднань** `StringBuilder` *повільніший* через власні початкові витрати. Вираз `"Hello, " + name + "!"` компілюється в один ефективний виклик `string.Concat`: не «оптимізуйте» його за допомогою StringBuilder. Використовуйте StringBuilder, коли кількість додавань велика або невідома заздалегідь (цикли). Також віддавайте перевагу **інтерполяції рядків** (`$"..."`) заради читабельності: сучасний C# ефективно її перетворює, а handlers (обробники) інтерпольованих рядків навіть уникають проміжних виділень у таких API, як logging (журналювання).

### Замикання й LINQ у hot paths

LINQ виразний; у переважній більшості коду його вартість незначна, а виграш у читабельності того вартий. Але в справді hot path він приховує виділення пам’яті: кожен запит виділяє стани перелічувачів, а лямбда, яка **захоплює** змінну, виділяє об’єкт замикання для зберігання захопленого стану.

```csharp
// In a tight loop, each captured 'threshold' can allocate a closure,
// and the LINQ chain allocates enumerators per call.
int threshold = GetThreshold();
var count = items.Where(x => x.Value > threshold).Count();

// A plain loop in a hot path: zero allocations, no delegate calls.
int count = 0;
foreach (var x in items)
    if (x.Value > threshold) count++;
```

> **Рекомендація:** типово пишіть на LINQ — код читабельніший, а витрати рідко мають значення. Замінюйте його явними циклами *лише* там, де профілювальник виявив hot path. Це правило «спочатку виміряйте» у мініатюрі: не вилучайте LINQ превентивно з усієї кодової бази лише тому, що прочитали, ніби він повільний. 90% вашого коду це не обходить.

## Thread pool під навантаженням

[У Розділі 4](#chapter-4-async-essentials) пояснено, чому заблокований потік із пулу шкідливий: продовження, яке мало б його розблокувати, теж потребує потоку з пулу, а пул додає потоки навмисно повільно. Під навантаженням найважливіша *швидкість* додавання, тож ось графік. До мінімального значення, типово по одному потоку на ядро, пул створює потоки в міру надходження роботи. Понад мінімум їх додають три механізми, кожен повільніший за попередній:

- **Компенсація блокування.** Починаючи з .NET 6, потік пулу, заблокований у `Task.Wait` (який також застосовують `.Result` і `.GetAwaiter().GetResult()`), повідомляє про це пул. У .NET 10 пул одночасно додає ще до одного потоку на ядро, а далі — по одному: пауза 25 мс перед кожним; після кожної наступної групи з одного потоку на ядро пауза збільшується ще на 25 мс, але не перевищує 250 мс (`PortableThreadPool.Blocking.cs` у dotnet/runtime).
- **Детектор виснаження пулу.** Кожні 500 мс керівний потік додає один потік, якщо queue роботи не зрушував 500 мс, але лише коли використання процесора нижче 80%. Якщо воно вище, пул чекає цільову кількість потоків × 1 с. Це все, що отримають `Thread.Sleep`, `SemaphoreSlim.Wait` і блокувальний `lock`, бо вони не повідомляють про блокування.
- **Алгоритм hill climbing.** Він змінює кількість потоків, зберігає напрямок, що збільшує кількість завершеної роботи за секунду, і ніколи не додає потік, коли використання процесора перевищує 95%. Він розрахований на роботу процесора й не допомагає тим, хто заблокований.

```
work queued ─▶ below the minimum? ──yes──▶ new thread now
                    │ no
                    ▼
     blocked in Task.Wait? ──yes──▶ compensation: +1/core at once, then 25…250 ms per thread
                    │ no (Sleep, SemaphoreSlim.Wait, lock)
                    ▼
     starvation detector: +1 per 500 ms, only while CPU < 80%
```

> **Зверніть увагу.** **Чому здається, що `ThreadPool.SetMinThreads` допомагає.**
>
> - **Нижче за мінімум графіка немає.** Для роботи в queue пул негайно створює потік, без жодної з описаних затримок. Тому мінімум, вищий за пікову кількість заблокованих викликів, прибирає виснаження зі спостережуваних графіків.
> - **Блокування нікуди не зникло.** Кожен заблокований виклик і далі утримує потік і його стек. Hill climbing більше не може зменшити кількість потоків нижче за новий мінімум, а попередній збій повернеться в день, коли паралельних запитів стане більше за вибране число. У коді ніщо не пояснюватиме, чому його вибрали.
>
> Вважайте підвищений мінімум тимчасовим обхідним заходом, визначеним вимірюванням, із коментарем, де названо блокувальний виклик. Виправлення — припинити блокування (`await`, `SemaphoreSlim.WaitAsync`).

### Модель пам’яті: коротке пояснення

[У Розділі 4](#chapter-4-async-essentials) розглянуто переупорядкування й бар’єри; самі правила короткі. Без синхронізації JIT і процесор можуть переупорядкувати доступи до пам’яті; JIT також може об’єднати два сусідні читання того самого поля в одне. Через це цикл `while (!_stop)` в оптимізованому коді може крутитися без кінця. `Volatile.Read` має семантику acquire, а `Volatile.Write` — release. Взяття `lock` є acquire, його звільнення — release; кожен метод `Interlocked` встановлює повний бар’єр. Присвоєння посилання на повністю створений об’єкт — операція release, тож потік, який побачив посилання, побачить і поля цього об’єкта (див. [`Memory-model.md`](https://github.com/dotnet/runtime/blob/main/docs/design/specs/Memory-model.md) у dotnet/runtime). А `ConcurrentDictionary` робить атомарним кожен окремий *виклик*, але не послідовність «перевірити й виконати дію» з кількох викликів.

## Task і ValueTask

Кожен метод `async`, який справді призупиняється, створює state machine ([у Розділі 4](#chapter-4-async-essentials) показано результат компілятора), а результат передається через `Task`. Зазвичай ці витрати — шум. `Task` є класом, тож кожен екземпляр — окреме виділення в купі. Для методу, який викликається мільйони разів на секунду й *зазвичай завершується синхронно* (влучання в кеш), це зайві витрати. `ValueTask<T>` — структура, яка містить *або* вже доступний результат, *або* `Task` для повільного шляху; синхронний шлях не виділяє пам’яті.

```csharp
public ValueTask<User> GetUserAsync(int id)
{
    if (_cache.TryGetValue(id, out User? cached))
        return new ValueTask<User>(cached);          // fast path, no allocation

    return new ValueTask<User>(LoadFromDbAsync(id));  // slow path wraps a Task
}
```

Структуру для очікування легше використати неправильно:

> **Пастка.**
> - **Не очікуйте `ValueTask` більше одного разу.** Після першого використання ресурс, який лежить в його основі, може повернутися до пулу.
> - **Не читайте `.Result`, поки операція не завершилася**, і не використовуйте її паралельно.
> - **Не зберігайте `ValueTask` у полі чи колекції.** Якщо потрібно його зберегти, викличте `.AsTask()`.

**Типово використовуйте `Task`.** Застосовуйте `ValueTask` лише на hot paths, де профілювання підтвердило важливість виділення пам’яті й операція зазвичай завершується синхронно. Пам’ятайте про відносні масштаби: `ValueTask` заощаджує одне невелике виділення на виклик, а один `.Result` на hot path може виснажити весь пул (наступний розділ). Більшість оптимізації асинхронного коду — це просто відмова від блокування.

## TPL: паралелізм для процесорних завдань

Асинхронність із [Розділу 4](#chapter-4-async-essentials) забезпечує *конкурентність* під час вводу-виводу: дає змогу одночасно очікувати. **Паралелізм** — інше: одночасне виконання процесорної роботи на кількох ядрах.

### Task.Run: перенесення процесорної роботи

`Task.Run` ставить делегат у queue thread pool. Використовуйте його, щоб перенести процесорну роботу з потоку, який має залишатися чутливим до вводу користувача, наприклад із потоку інтерфейсу:

```csharp
// In a UI event handler: keep the UI thread free during heavy computation
int result = await Task.Run(() => ComputeExpensiveThing(data));
```

> **Пастка.** Не огортайте асинхронний ввід-вивід у `Task.Run` на сервері. `await Task.Run(() => httpClient.GetAsync(url))` не прискорює роботу: запит і так виконується в потоці з пулу, а після початку операції вводу-виводу потік не потрібен. Ви без причини платите за перехід між queues й перемикання потоків.

### Parallel.For і ForEach

Для розпаралеленої процесорної обробки даних `Parallel` розподіляє цикл між ядрами:

```csharp
Parallel.ForEach(images, image =>
{
    image.Thumbnail = GenerateThumbnail(image); // CPU-bound, independent
});
```

`Parallel.ForEachAsync` (.NET 6) виконує *асинхронну* роботу для елементів колекції з вбудованим обмеженням паралелізму — часто це чистіший варіант, ніж шаблон із `SemaphoreSlim`:

```csharp
await Parallel.ForEachAsync(
    urls,
    new ParallelOptions { MaxDegreeOfParallelism = 8 },
    async (url, ct) => await ProcessAsync(url, ct));
```

### Коли паралелізм допомагає, а коли шкодить

- **Допомагає**, коли робота обмежена процесором, елементи незалежні, а кожен потребує достатньо обчислень, щоб виправдати координаційні витрати.
- **Шкодить**, коли робота обмежена вводом-виводом (використовуйте async), елементи надто малі (домінує планування), або вони спільно змінюють стан (конкуренція все одно послідовно виконує роботу).

> **Рекомендація.** Паралелізм — для процесора, асинхронність — для вводу-виводу. `Task.Run` навколо вводу-виводу чи `Parallel.ForEach` навколо мережевих викликів — ознака коду, який іще не доріс до рівня senior.

## System.Threading.Channels: pipelines виробників і consumers

Коли виробники створюють роботу, а consumer (споживачі) її обробляють, і їх потрібно роз’єднати, обмеживши швидкість створення роботи відповідно до споживання, використовуйте `System.Threading.Channels`. `Channel<T>` — асинхронно-сумісний потокобезпечний queue:

```csharp
var channel = Channel.CreateBounded<WorkItem>(new BoundedChannelOptions(capacity: 100)
{
    FullMode = BoundedChannelFullMode.Wait // producers wait when full: back-pressure
});

// Producer
async Task ProduceAsync(CancellationToken ct)
{
    foreach (var item in GetWork())
        await channel.Writer.WriteAsync(item, ct); // awaits if channel is full
    channel.Writer.Complete();                      // signal: no more items
}

// Consumer(s)
async Task ConsumeAsync(CancellationToken ct)
{
    await foreach (WorkItem item in channel.Reader.ReadAllAsync(ct))
        await HandleAsync(item);
}

// Wire up several consumers reading the same channel:
var producer = ProduceAsync(cts.Token);
var consumers = Enumerable.Range(0, 4).Select(_ => ConsumeAsync(cts.Token));
await Task.WhenAll(consumers.Prepend(producer));
```

Ключове тут — **обмежений** канал із `FullMode = Wait`: коли буфер заповнюється, `WriteAsync` призупиняє виробника, доки не з’явиться вільне місце. Це і є **зворотний тиск**: система сама регулює роботу, замість ставити в queue необмежену кількість завдань у пам’яті. `Complete()` дає `ReadAllAsync` завершитися, коли робота закінчиться.

## Коротко про Rx.NET

**Reactive Extensions (Rx.NET)** надає `IObservable<T>` — потік events, який сам надсилає дані підписникам, із операторами на кшталт LINQ для поєднання events у часі (`Throttle`, `Buffer`, `Merge`, `CombineLatest`); пошук із затримкою введення в полі — один рядок коду. Для запит-відповідь і звичайного асинхронного вводу-виводу дотримуйтеся `Task`. Rx виправданий лише тоді, коли ви моделюєте *потоки events у часі*.

## Атрибути й reflection

Остання група механізмів впливає на швидкість запуску процесу й те, що може містити deployment. Усе залежить від одного запитання: типи виявляються під час виконання чи відомі компілятору під час збірки? Почнімо з метаданих.

**Атрибути** додають декларативні метадані до коду — класів, методів, властивостей і параметрів. Самі собою вони нічого не роблять: це пасивні дані, скомпільовані у збірку й очікують, доки їх прочитає **reflection** або інструмент.

```csharp
[AttributeUsage(AttributeTargets.Property)]
public sealed class DisplayNameAttribute : Attribute
{
    public string Name { get; }
    public DisplayNameAttribute(string name) => Name = name;
}

public class Product
{
    [DisplayName("Product Title")]
    public string Title { get; set; } = "";
}
```

**Reflection** — це API для перевірки типів і метаданих під час виконання, а також для динамічного виклику членів.

```csharp
var prop = typeof(Product).GetProperty(nameof(Product.Title))!;
var attr = prop.GetCustomAttribute<DisplayNameAttribute>();
Console.WriteLine(attr?.Name);   // "Product Title"

// Dynamic invocation
var product = Activator.CreateInstance<Product>();
prop.SetValue(product, "Widget");
Console.WriteLine(prop.GetValue(product));   // "Widget"
```

Reflection використовують серіалізатори, контейнери dependency injection (впровадження залежностей), ORM і валідатори. Але він **повільний** порівняно з прямими викликами (обходить оптимізації JIT і виконує пошук під час роботи), а також заважає аналізу trimming/AOT, бо linker не бачить статично використання reflection.

> **Рекомендація:** використовуйте reflection для роботи під час конфігурації (наприклад, одноразового налаштування контейнера під час запуску), а не в hot paths. Якщо потрібно повторювати reflection, кешуйте об’єкти `PropertyInfo`/`MethodInfo` або компілюйте делегати з дерев виразів. А ще краще — розгляньте генератори коду під час компіляції.

## Генератори коду під час компіляції: загальне поняття

**Генератор коду під час компіляції** — це плагін компілятора, який працює *під час компіляції*, аналізує ваш код (через синтаксичну й семантичну моделі Roslyn) і *створює додатковий вихідний код C#*, що компілюється разом із вашим. Це сучасний спосіб розв’язувати проблеми, для яких раніше використовували reflection під час виконання або Reflection.Emit.

Модель така: замість знаходити метадані й створювати поведінку *під час виконання* (повільно й непридатно для AOT), генератор виконує пошук *під час компіляції* й записує звичайний код, який можна було б написати вручну. Результат швидший, сумісний із trimming і придатний до налагодження.

```csharp
// You write a partial declaration with an attribute:
[JsonSerializable(typeof(Person))]
public partial class MyJsonContext : JsonSerializerContext { }

// System.Text.Json's source generator emits the other 'partial' half at compile time:
// fully typed, reflection-free serialization code for Person.
```

Зазвичай генератори не пишуть, а використовують. `System.Text.Json`, `LoggerMessage`, регулярні вирази (`[GeneratedRegex]`) і багато бібліотек мають генератори, які замінюють reflection згенерованим кодом. Розуміння цього пояснює, *чому* сучасний .NET може серіалізувати JSON і знаходити збіги регулярних виразів без reflection під час виконання й із повною сумісністю з Native AOT.

## Від IL до машинного коду: CLR і JIT

Компілятор Roslyn не створює машинний код із C#. Він створює **проміжну мову (IL)** — стековий байткод, незалежний від процесора, — а також метадані, упаковані у збірку (`.dll` або `.exe`). Переклад у машинний код відбувається під час виконання за допомогою **CLR** (Common Language Runtime); сучасна кросплатформна реалізація називається **CoreCLR**.

### JIT-компіляція

Компілятор **Just-In-Time (JIT)** перетворює IL на машинний код **для кожного методу під час його першого виклику**. Коли програма вперше викликає метод, JIT компілює його, змінює адресу виклику так, щоб вона вказувала на скомпільований код, а наступні виклики відразу переходять до машинного коду. Такий підхід «компілювати на вимогу» не змушує платити за компіляцію шляхів коду, які ви не виконуєте, а JIT може оптимізувати код для *фактичного* процесора (наприклад, використовувати AVX2, якщо він є).

Недолік — **вартість запуску**: перше виконання кожного методу включає час компіляції. Це важливо для короткотривалих CLI-інструментів і безсерверних функцій із холодним запуском. У .NET є кілька засобів зменшити ці витрати.

### Багаторівнева компіляція

Сучасний .NET застосовує **багаторівневу компіляцію**, щоб отримати переваги обох підходів: швидкий запуск *і* високу стабільну пропускну здатність.

- **Рівень 0** («швидкий JIT»): під час першого виклику JIT швидко компілює метод із мінімальними оптимізаціями. Код створюється швидко, тому застосунок швидко запускається, але сам код не такий швидкий.
- **Рівень 1** («оптимізувальний JIT»): runtime підраховує виклики кожного методу. Коли кількість перетинає **поріг викликів** (тобто метод справді «гарячий»), JIT у фоновому режимі перекомпілює його з повним набором оптимізацій і замінює попередню версію.

Рідко викликані методи залишаються дешевими для компіляції (Рівень 0), без витрат часу на оптимізацію; гарячі цикли повністю оптимізуються. **On-Stack Replacement (OSR)** розв’язує складний випадок методу з довготривалим циклом, що досі виконується в момент, коли стає гарячим: оптимізований код можна підставити *під час виконання циклу*, не чекаючи на наступний виклик методу.

```xml
<!-- Tiered compilation is ON by default. You can tune or disable it: -->
<PropertyGroup>
  <TieredCompilation>true</TieredCompilation>
  <!-- Tier-0 + Quick JIT for loops can hurt microbenchmarks;
       TieredPGO enables Profile-Guided Optimization -->
  <TieredPGO>true</TieredPGO>
</PropertyGroup>
```

**Динамічна PGO (оптимізація з профілюванням)**, типово ввімкнена з .NET 8, іде далі: код Рівня 0 *інструментується*, щоб записати поведінку під час виконання (які типи фактично проходять через віртуальний виклик, які гілки вибирають), а Рівень 1 використовує цей профіль для кращих рішень — наприклад, **усуває віртуальність** виклику, який майже завжди отримував той самий тип, або змінює порядок гілок. Це оптимізація з огляду на те, як програма *справді* працює, чого статичний компілятор не може досягти.

### ReadyToRun (R2R)

**ReadyToRun** — це форма попередньої компіляції, яка вбудовує *скомпільований машинний код* поруч з IL у збірці. Під час виконання CLR може безпосередньо використати цей машинний код замість компілювати все JIT із нуля, значно прискорюючи запуск. Компроміс — більший розмір збірки (у ній є і IL, і машинний код), а також слабша оптимізація порівняно з Рівнем 1 (код компілюють без знання точного процесора й профілю виконання). Якщо метод стає гарячим, код R2R усе одно проходить повторну JIT-компіляцію до Рівня 1. Так ви поєднуєте швидкий запуск із R2R і максимальною пропускною здатністю після оптимізації. Часто застосунки ASP.NET Core публікують із `<PublishReadyToRun>true</PublishReadyToRun>`, щоб пришвидшити холодний запуск.

### Native AOT

**Native AOT (Ahead-Of-Time)** іде до кінця: під час збірки компілює весь застосунок у **один автономний виконуваний файл машинного коду**, без JIT і без IL під час виконання. JIT у CLR повністю відсутній; постачається машинний код і мінімальне runtime (разом зі збирачем сміття).

Переваги:
- **Миттєвий запуск** — не потрібно прогрівати JIT. Ідеально для безсерверних функцій, CLI-інструментів і мікросервісів.
- **Невелике автономне deployment** — не потрібно попередньо встановлювати платформу.
- **Менше використання пам’яті** й передбачувана продуктивність.

Витрати й обмеження:
- **Немає генерації коду під час виконання.** Не працюватимуть засоби, що залежать від `System.Reflection.Emit`, генерації IL під час виконання або динамічного завантаження збірок.
- **Обмежений reflection.** AOT агресивно видаляє непотрібний код і не може побачити шляхи, доступні лише через reflection. Функції на основі reflection, як-от серіалізація, потребують окремої обробки (генераторів коду під час компіляції; у [Розділі 5](#chapter-5-http-and-web-apis) розглянуто `System.Text.Json`).
- Обов’язкова **компіляція всієї програми** з **trimming**, що може зламати код, який використовує типи, видалені тримером.

```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
</PropertyGroup>
<!-- dotnet publish -r linux-x64 -c Release -->
```

> **Рекомендація.** Native AOT найкраще підходить, якщо важливі холодний запуск і розмір: безсерверні функції, CLI-інструменти, контейнери, що масштабуються з нуля. Для великого моноліту, який запускається раз і працює тижнями, обмеження зазвичай не виправдані. Обирайте інструмент за важливою для вас метрикою.

### Trimming

**Trimming** (також linking) видаляє зі зібраного застосунку невикористаний IL, зменшуючи розмір deployment. Тример виконує статичний аналіз, знаходить доступний код і відкидає решту. Небезпека — **reflection**: якщо під час виконання шукати тип чи метод за назвою, тример не бачить цю залежність статично й може видалити її. У продакшені це спричинить `MissingMethodException`. Тому trimming, Native AOT і бібліотеки, що активно використовують reflection, конфліктують; саме тому екосистема переходить до **генераторів коду під час компіляції**, які створюють безпечний для trimming код. Бібліотеки позначають сумісність із trimming такими атрибутами, як `[RequiresUnreferencedCode]` і `[DynamicallyAccessedMembers]`, щоб тример міг попередити вас.

## Збірки, завантаження й strong name

**Збірка** — це одиниця deployment й версіонування в .NET: файл `.dll` або `.exe` з IL, метаданими (маніфестом, що описує типи, версію й залежності) та, за потреби, ресурсами. Саме на межі збірки визначається ідентичність типу: повна ідентичність складається з назви з простором імен *і* збірки, у якій тип міститься.

### AssemblyLoadContext

У сучасному .NET збірки завантажуються в **`AssemblyLoadContext` (ALC)**. Уявіть ALC як ізольований контейнер для набору завантажених збірок. **Типовий ALC** завантажує застосунок і його залежності. Але можна створити *додаткові* контексти завантаження — це основа **систем плагінів** і сценаріїв **гарячого перезавантаження / заміни**: ви завантажуєте плагін (і його приватні версії залежностей) у власний ALC, використовуєте його, а потім **вивантажуєте** весь контекст, щоб повернути пам’ять. У старій моделі .NET Core на основі фіксованих AppDomain так зробити було неможливо (у .NET 5+ AppDomain більше немає).

```csharp
public sealed class PluginLoadContext : AssemblyLoadContext
{
    private readonly AssemblyDependencyResolver _resolver;

    public PluginLoadContext(string pluginPath)
        : base(isCollectible: true)      // collectible → can be unloaded
        => _resolver = new AssemblyDependencyResolver(pluginPath);

    protected override Assembly? Load(AssemblyName name)
    {
        string? path = _resolver.ResolveAssemblyToPath(name);
        return path is null ? null : LoadFromAssemblyPath(path);
    }
}
```

Дві збірки з *однаковою назвою*, завантажені у *два різні ALC*, runtime вважає **різними типами**. У системах плагінів це може непомітно спричинити `InvalidCastException` («неможливо перетворити Foo на Foo»). Ідентичність типу включає контекст завантаження.

### Strong name

**Strong name** — криптографічний ідентифікатор збірки: її підписують приватним ключем, а ідентичність складається з назви, версії, культури й **токена відкритого ключа**. Раніше це було потрібно для Global Assembly Cache (GAC) і запобігання збігам назв. У сучасному кросплатформному .NET GAC більше немає, а strong name менш важливий. Він актуальний переважно для авторів бібліотек, яким потрібна стабільна публічна ідентичність або на які мають посилатися інші збірки з strong name. Це *не* функція безпеки (відкритий ключ вбудовано й можна перевірити, але він не запобігає підробці, як Authenticode). Не покладайтеся на strong name для безпеки; використовуйте його для стабільності ідентичності широко вживаних бібліотек.

## Типові антишаблони продуктивності .NET

Зведений довідник із поширених джерел проблем, більшість із яких ми вже розглянули:

- **Оптимізація без вимірювання.** Метаантишаблон. Неможливо виправити те, чого ви не виміряли.
- **Об’єднання рядків через `+=` у циклах.** Квадратична кількість виділень. Використовуйте `StringBuilder` або `string.Join`.
- **Запит N+1.** Один запит стає сотнями через ліниве завантаження зв’язаних даних. Використовуйте `Include` або проєкцію ([Розділ 7](#chapter-7-data-access); поглиблений розгляд продуктивності EF Core — у [Розділі 18](#chapter-18-data-in-depth)).
- **Синхронне очікування асинхронного результату (`.Result`/`.Wait()`).** Блокує потоки й під навантаженням виснажує пул.
- **`List.Contains` у циклі.** O(n²): нормально для сотні рядків у розробці, катастрофічно для 100 000. Один раз до циклу створіть `HashSet` або `Dictionary`; у [Розділі 2](#chapter-2-data-structures-and-algorithms-essentials) розглянуто колекції та їхню вартість.
- **Завантаження всіх сутностей і необмежених результатів.** Проєктуйте дані в DTO; завжди додавайте пагінацію.
- **Перехоплення exceptions для керування потоком.** Створення exception дороге (потрібно зняти стек). Не використовуйте `try/catch`, якщо підійде `TryParse` або перевірка на null. Exceptions призначено для виняткових випадків.
- **Прихований boxing.** Типи-значення непомітно потрапляють у купу через перетворення на `object`/інтерфейс і нетипізовані колекції.
- **LINQ і замикання в справді гарячих циклах.** В інших місцях усе гаразд; у 10% коду, визначених профілювальником, це реальні витрати.
- **Надмірне logging на hot paths.** Форматування рядків і ввід-вивід для кожного запиту накопичуються. Використовуйте структуроване logging з перевіркою рівня й handlers інтерпольованих рядків.
- **Незвільнені або витеклі `IDisposable`.** Незакритий `HttpClient` для кожного запиту вичерпує сокети; незакриті з’єднання з БД — пул. Використовуйте `IHttpClientFactory` і `using`.

## Усе разом

Інженерія продуктивності — не набір хитрощів, які треба розсипати по коду, а дисципліна, що ґрунтується на *доказах*. Перевага senior-інженера не в тому, що він знає більше оптимізацій за розробника middle, а в стриманості — він не застосовує їх, доки цього не вимагають вимірювання, — і в умінні швидко й правильно виміряти, коли потреба виникла.

Запам’ятайте послідовність: **визначити мету, виміряти вихідний стан, профілюванням знайти справжнє bottleneck, змінити одну річ, виміряти знову й зупинитися після досягнення бюджету.** Пам’ятайте механізми (виділення створюють навантаження на GC; великий буфер для кожного запиту означає роботу Gen 2 для кожного запиту; заблокований потік затримує всіх; вибір правильної колекції змінює криву витрат; EF може перетворити один рядок на тисячу запитів), щоб знати, за який важіль узятися, коли профілювальник указав на гарячі 10% коду.

І передусім пам’ятайте золоте правило з початку розділу, яке щоразу захочеться порушити: **спочатку вимірюйте. Не вгадуйте.** Код, який *ви були певні* що повільний, майже ніколи таким не є. Нехай ваші зусилля визначають докази, а не інтуїція.

## Практика

**1. Спостерігайте, як пул додає потоки (30 хв).** Повторіть експеримент [`Starvation`](https://github.com/malyna2/dotnet-handbook/tree/main/verify/path/Starvation) із *Перевірте на практиці* у [Розділі 4](#chapter-4-async-essentials) у режимі блокування, відкривши лічильники:

```bash
dotnet tool install -g dotnet-counters
cd verify/path
dotnet build -c Release Starvation       # build first: the run itself lasts about 12 s
dotnet run -c Release --project Starvation -- block
# in a second terminal, as soon as the run starts:
dotnet-counters monitor -n Starvation --counters 'EventCounters\System.Runtime'
```

Під час кожного оновлення читайте `ThreadPool Thread Count` і записуйте приріст. Спершу він різкий, а потім зростає дедалі меншими кроками; порівняйте криву з графіком компенсації блокування в підрозділі [Thread pool під навантаженням](#the-thread-pool-under-load). `ThreadPool Queue Length` залишається високим, доки потоки не наздоженуть роботу, а `CPU Usage (%)` майже не змінюється. (Без префікса `EventCounters\` .NET 10 показує `dotnet.thread_pool.thread.count` як зміну за секунду, а не як кількість; пояснення є в [методології з прикладом у Розділі 9](#diagnosing-a-performance-problem-a-worked-methodology).) У [довідковому запуску](https://github.com/malyna2/dotnet-handbook/tree/main/verify/path/reference-runs) на 4 vCPU пул досяг 68 потоків і завершив роботу за 11,6 с; запуск `-- await` досяг максимуму у 3 потоки й завершився за 1,1 с.

Якщо програма завершується до підключення інструмента, запустіть її через інструмент. Документація застерігає від `dotnet run` у цьому режимі, бо моніторитиметься перший процес .NET, який під’єднається:

```bash
dotnet-counters monitor --counters 'EventCounters\System.Runtime' -- dotnet exec Starvation/bin/Release/net10.0/Starvation.dll block
```

**2. Знайдіть заблоковані потоки в дампі (20 хв).** Під час наступного запуску з блокуванням:

```bash
dotnet tool install -g dotnet-dump
dotnet-dump collect -n Starvation
dotnet-dump analyze <the dump file it names>
# then, at the analyzer's prompt:
#   threadpool         the pool's threads and its state
#   threadpoolqueue    the work items waiting for a thread
#   parallelstacks     every thread's stack, merged
```

Більшість потоків пулу матимуть спільний об’єднаний стек, що закінчується на `Task.Wait`: у дампі саме так виглядає синхронне очікування асинхронного результату; `threadpoolqueue` покаже роботу, виконання якої затримують ці потоки.

**3. Запишіть tracing (10 хв).** Під час третього запуску виконайте `dotnet-trace collect -n Starvation`, а через кілька секунд зупиніть його. Типове семплювання записує стеки всіх потоків — і тих, що чекають, і тих, що працюють, — тому заблоковані потоки буде видно, навіть якщо процесор простоює. Відкрийте `.nettrace` у PerfView або Visual Studio чи конвертуйте його через `dotnet-trace convert --format Speedscope`.

**4. Вправи з Розділу 4 (20 хв).** У розділі *Вправи* [Розділу 4](#chapter-4-async-essentials) у завданні *Знайдіть помилку* назвіть механізм пулу, що стоїть за кожним дефектом, і порівняйте з перевіреним запуском у [`verify/exercises/Ch08`](https://github.com/malyna2/dotnet-handbook/tree/main/verify/exercises/Ch08): 20 запитів тривали 6 с, а виправлення — 0,8 с; пул зріс до 49 потоків, а після виправлення — до 5. У завданні *Що б ви зробили* потрібно обґрунтувати механізм `ConfigureAwait` під час перевірки коду.

**Докази зберігайте** у власному публічному репозиторії-портфоліо, а не в цьому: лічильники як CSV (`dotnet-counters collect --counters 'EventCounters\System.Runtime' --format csv`), уривок `parallelstacks` і абзац, що пояснює криву кількості потоків графіком їх додавання.

Якщо знадобиться згодом: [Сценарій 7 Розділу 35](#scenario-7-the-slow-leak-memory-keeps-growing-until-the-pod-is-oom-killed) (пошук витоку за знімком купи), [бенчмаркінг за допомогою BenchmarkDotNet](#benchmarking-with-benchmarkdotnet) і [специфікація моделі пам’яті](https://github.com/dotnet/runtime/blob/main/docs/design/specs/Memory-model.md) runtime.

## Три запитання

**1.** Два сервіси блокують потік пулу на кожен запит: один через `.Result`, інший — через `SemaphoreSlim.Wait()`. Чому за однакового сплеску запитів другий відновлюється повільніше й набагато повільніше, коли процесор зайнятий? І чому після збільшення `ThreadPool.SetMinThreads` обидва графіки виглядають здоровими?

<details>
<summary>Відповідь</summary>

- **`.Result` повідомляє про блокування, а `SemaphoreSlim.Wait()` — ні.** `.Result` блокує потік у `Task.Wait`, який повідомляє пул. Пул компенсує блокування: спершу додає один потік на ядро, потім по одному, з паузами від 25 до 250 мс. В експерименті на 4 ядрах пул зріс до 68 потоків за 11,6 с.
- **Для неповідомленого блокування є лише детектор виснаження.** Поки використання процесора нижче 80%, він додає щонайбільше один потік за 500 мс. Вище 80% очікування становить цільову кількість потоків × 1 с, тож зайнятий сервіс отримує новий потік раз на хвилину або ще рідше.
- **Нижче за мінімум графіка немає.** Пул створює потоки в міру надходження роботи, тому мінімум, вищий за пікову кількість блокувань, приховує обидві проблеми. Але блокування не припинилося: кожен виклик і далі утримує потік, hill climbing не може знизити кількість нижче за мінімум, а збій повернеться за більшого навантаження.

Виправлення: припиніть блокування (`await`, `SemaphoreSlim.WaitAsync`). Залишайте підвищений мінімум лише як тимчасовий захід, обґрунтований вимірюванням, і додайте коментар, що пояснює, для чого його встановлено.
</details>

**2.** Сервіс перед завантаженням файлу виділяє буфер на 100 КБ для кожного запиту. Кожні кілька секунд стрибає p99 затримки, а лічильники показують збільшення збирань gen2 разом із LOH. Чому буфер, що живе лише один запит, спричиняє повне збирання і що та в якій послідовності змінити?

<details>
<summary>Відповідь</summary>

- **Межа — 85 000 байтів.** Масив такого розміру виділяється в купі великих об’єктів, яку збирають лише разом із gen2. Буфер швидко стає непотрібним, але його звільнення потребує повного збирання, тому часті великі виділення спричиняють часті повні збирання. Фоновий GC виконує більшу частину gen2 паралельно із застосунком, але його паузи й споживання процесора позначаються на запитах у роботі.
- **Спершу змініть код.** Передавайте файл потоком, щоб узагалі не було буфера, або беріть його з `ArrayPool<byte>.Shared` і повертайте в `finally` (масив може бути більшим, тож окремо відстежуйте довжину). Порівняйте `dotnet.gc.heap.total_allocated`, кількість gen2 за хвилину й `dotnet.gc.pause.time` до та після зміни.
- **Потім змінюйте конфігурацію, якщо на це й далі вказують лічильники.** В ASP.NET Core уже типово ввімкнено серверний GC; починаючи з .NET 9, DATAS пристосовує його купи. Ніколи не викликайте `GC.Collect()`: так ви скинете налаштування GC й навмисно призупините виконання.
</details>

**3.** У циклі worker-а читають поле `bool _stop`, яке встановлює інший потік. У Debug і всіх тестах усе працює; у Release під навантаженням один екземпляр не зупиняється. Що допускає модель пам’яті та яке найменше правильне виправлення?

<details>
<summary>Відповідь</summary>

- **Читання може бути об’єднане або усунене.** Модель пам’яті .NET дозволяє JIT об’єднати сусідні читання того самого невольтильного місця. Якщо тіло циклу не змушує повторно читати значення (немає блокування, `Interlocked` чи виклику, код якого неможливо проаналізувати), оптимізований код може прочитати `_stop` один раз і далі перевіряти власну копію. У Debug такої оптимізації немає, тому код і «працює».
- **Найменше виправлення:** застосуйте `Volatile.Read(ref _stop)` у циклі або оголосіть поле `volatile`: читання acquire, яке не можна об’єднати. З боку потоку, що записує, відповідно використайте `Volatile.Write`.
- **Краще виправлення:** використовуйте `CancellationToken`. Він уже забезпечує видимість змін і сумісний з усіма асинхронними API, які викликає цикл.
</details>

## Ухваліть рішення

Сервіс ASP.NET Core на 8 ядрах викликає SDK постачальника, у якого є лише синхронний API: кожен виклик блокує потік на 200 мс — 2 с під час очікування сокета. У піковий момент одночасно виконуються близько 150 викликів, і сповільнюються всі endpoints, навіть ті, що не звертаються до постачальника. Є три варіанти:

1. Збільшити `ThreadPool.SetMinThreads`, щоб вистачило на пікову кількість викликів.
2. Ізолювати SDK за допомогою **ізолятора** (bulkhead): обмеженого `Channel<T>`, який спорожнює фіксована кількість окремих потоків (`TaskCreationOptions.LongRunning`). Запити очікують на результат і швидко отримують `503`, коли канал заповнений.
3. Замінити SDK на HTTP API постачальника й викликати його через `HttpClient` із `await`.

<details>
<summary>Як senior-інженер оцінює варіанти</summary>

**Ціна кожного варіанта.**

- *Збільшити мінімум:* один рядок і deployment. До нового мінімуму пул перестає повільно додавати потоки. Але кожен виклик і далі блокує потік пулу, hill climbing не може знизити кількість нижче за мінімум, а після перевищення пікової кількості блокувань старий збій повернеться. У коді ніщо не пояснюватиме причину.
- *Ізолятор:* приблизно день роботи. Блокування відбувається на потоках, які ніколи не виконують продовження інших операцій, тому затримки постачальника більше не впливають на решту сервісу; перевантаження перетворюється на швидку й видиму відмову замість виснаження пулу. Плата — queue викликів постачальника в піковий момент і потреба призначити відповідального за пропускну здатність (кількість потоків × виклики за секунду).
- *Переписати інтеграцію:* тижні роботи й повторна реалізація всього, що робив за вас SDK (автентифікація, retries (повторні спроби), формат обміну). Зате блокування повністю зникає.

**Що визначає рішення тут:** інші endpoints використовують той самий пул. Шкода є побічною; вона не є власною затримкою постачальника. Ізоляція усуває побічну шкоду за будь-якої поведінки постачальника.

**Рішення:** зараз запровадити ізолятор; підвищений мінімум використати як захід на той самий день, розрахований за виміряним піком, і прибрати, щойно ізолятор буде готовий. Переписування додати до плану, якщо HTTP API постачальника задокументований і стабільний.

**Що могло б змінити рішення.** Якщо низьконавантажений endpoint — єдиний consumer, самого підвищеного мінімуму може бути досить. Якщо постачальник випустить асинхронний SDK, використайте його й відмовтеся від ізолятора. Якщо виклик не може чекати в queue (наприклад, підтвердження оплати в присутності клієнта), розрахуйте кількість окремих потоків на пік і відхиляйте запити заздалегідь.
</details>

## Перевірте на роботі

**Перевірте код.** Пошукайте в сервісі `Thread.Sleep`, `.Wait()`, `.Result`, `.GetAwaiter().GetResult()`, `SemaphoreSlim.Wait(` і блоки `lock` навколо вводу-виводу; `new byte[` і `MemoryStream` на шляхах запитів; `GC.Collect` і `SetMinThreads`. Добрий результат: усі блокування є лише в коді запуску, великі буфери передаються потоком або беруться з пулу, а біля підвищеного мінімуму є коментар із назвою блокувального виклику. Поганий: блокування на шляху запиту чи повідомлення або мінімум, який ніхто не може пояснити.

**Виміряйте.** За пікового навантаження сервісу протягом п’яти хвилин виконуйте `dotnet-counters monitor -n <process> --counters 'EventCounters\System.Runtime'` або перегляньте ті самі метрики в APM: довжину queue thread pool (майже нуль), кількість потоків (пласка, а не така, що зростає), час пауз GC за хвилину, кількість gen 2 за хвилину й розмір LOH. В APM на .NET 9+ це `dotnet.thread_pool.queue.length`, `dotnet.thread_pool.thread.count`, `dotnet.gc.pause.time`, `dotnet.gc.collections` для `gen2` і `dotnet.gc.last_collection.heap.size` для `loh`; переконайтеся, що перші дві метрики відображено як значення, а не швидкість зміни.

## Запитання для співбесіди

**Як працює GC і що таке покоління?**
Це трасувальний збирач із поколіннями, що використовує позначення й очищення. Об’єкти починаються в **gen 0**; ті, що пережили збирання, переходять у **gen 1**, потім у **gen 2** (довгоживучі). Збирання поділено на покоління, бо більшість об’єктів швидко стають непотрібними: часте збирання gen 0 і рідке gen 2 дешеве й ефективне. Після збирання купу ущільнюють, щоб зменшити фрагментацію.

**Тривожний сигнал:** «Якщо пам’яті забагато — викличте `GC.Collect()`». Примусове збирання суперечить поколіннєвому дизайну й приховує корені, що утримують об’єкти.

**Що таке купа великих об’єктів?**
Об’єкти розміром від 85 000 байтів потрапляють у LOH, яку збирають разом із gen 2. За замовчуванням її не ущільнюють (ущільнювати великі блоки дорого), тому вона може фрагментуватися. Часте виділення великих масивів і буферів — поширена причина надлишкового використання пам’яті; використовуйте пул або повторно використовуйте їх.

**Серверний GC і GC робочих станцій?**
GC робочих станцій оптимізовано для малої затримки в клієнтських програмах: куп менше, збирання виконується в потоці застосунку. Серверний GC для більшої пропускної здатності використовує керовану купу й потік GC на ядро, споживаючи більше пам’яті. Він типовий для ASP.NET Core на багатоядерних серверах. Обирайте його для сервісів, орієнтованих на пропускну здатність; GC робочих станцій — для настільних програм із обмеженнями пам’яті чи вимогами до затримки.

**Керована й некерована пам’ять?**
Керована пам’ять — купа об’єктів .NET, за якою стежить GC. Некерована — усе, про що GC не знає: нативні дескриптори, ресурси ОС, `Marshal.AllocHGlobal`, буфери взаємодії. Некеровані ресурси треба явно звільняти через `IDisposable`/фіналізатори, бо GC їх не поверне.

**Фіналізатори й `IDisposable`: коли що використовувати?**
`IDisposable.Dispose()` забезпечує детерміноване очищення, яке викликаєте ви (через `using`). Фіналізатор (`~T()`) — резервний механізм, який запускає GC для некерованих ресурсів, якщо хтось забув про `Dispose`. Фіналізатори шкідливі: відкладають звільнення (об’єкт переживає ще одне збирання) і виконуються в одному потоці фіналізатора. Віддавайте перевагу `SafeHandle`/`IDisposable`; додавайте фіналізатор, лише якщо безпосередньо володієте некерованим ресурсом, а в `Dispose` вимикайте його через `GC.SuppressFinalize`.

**Що спричиняє витік керованої пам’яті, якщо GC збирає все?**
Небажані посилання, які не дають об’єктам стати недосяжними: статичні колекції, що безмежно ростуть; handlers events, від яких ніколи не відписалися (видавець утримує підписника); захоплені замикання; довгоживучі кеші без видалення записів; об’єкти `IDisposable`, які так і не звільнили. GC не може зібрати те, що досі досяжне.

**Тривожний сигнал:** «У .NET є GC, тож витоків пам’яті не буває». Небажані, але досяжні об’єкти (статичні списки, підписки на events) чудово витікають.

**Як знайти витік у продакшені?**
Спершу стежте за трендом: `dotnet-counters` або APM показує зростання керованої купи без стабілізації. Потім у різний час створіть два знімки купи (`dotnet-gcdump`) і порівняйте, щоб побачити, екземпляри яких типів збільшуються; перевірте шлях утримання (хто зберігає посилання). Тип, що накопичується, і корінь GC зазвичай указують на помилку.

**Яка справжня вартість boxing на hot path?**
Кожен boxing виділяє місце в купі й копіює значення, збільшуючи роботу gen 0. У тісному циклі це перетворюється на мільйони дрібних виділень і постійні збирання, які видно як високу швидкість виділення й час GC у лічильниках. Уникайте цього за допомогою узагальнених типів, `Span` і відмови від нетипізованих колекцій на кшталт `ArrayList`.
