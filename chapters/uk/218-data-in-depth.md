# Розділ 18: Поглиблене вивчення даних

[Розділ 7](#chapter-7-data-access) навчив вас правильно працювати з EF Core і SQL в одному сервісі: відстеженням змін, завантаженням і проєкціями, індексами, рівнями ізоляції, кешуванням і міграціями. У цьому розділі — наступний етап: як прискорити одну базу даних, коли очевидні способи вже застосовано, а потім — що робити, якщо однієї бази більше не вистачає. Ви навчитеся читати план PostgreSQL і виправляти механізм, через який він повільний; проєктувати кеш Redis, збій якого сповільнює сервіс, а не виводить його з ладу; та обирати між репліками, шардингом і ізоляцією клієнтів, розуміючи вартість кожного підходу.

Розділи йдуть від одного запиту до всієї системи. Спочатку — поглиблений розгляд одного вузла: додаткові засоби продуктивності EF Core (пагінація, скомпільовані запити, масове завантаження), модель зберігання, індекси й плани PostgreSQL та практичне використання Redis. Потім масштабування від найменшого втручання до найбільшого: масштабування вгору, репліки для читання, пули підключень під навантаженням, секціонування й шардинг, міграції без простою, захоплення змін даних, поліглотне зберігання і, нарешті, багатоклієнтність, де сходяться обидва напрями. В обох випадках головне запитання те саме: *де зберігаються дані й хто може до них звертатися?* Практичну роботу з читання планів наведено в лабораторній роботі [Розділу 19](#chapter-19-the-slow-query-lab-reading-execution-plans).

## Entity Framework Core: об’єктно-реляційний засіб зіставлення — поглиблений розгляд

У бізнес-сервісах Entity Framework Core найчастіше стає джерелом проблем продуктивності: один невинний рядок C# може створити катастрофічний шаблон SQL. У [Розділі 7](#chapter-7-data-access) розглянуто засоби, які усувають більшість таких проблем: `AsNoTracking`, проєкцію в DTO, усунення N+1 за допомогою `Include` чи проєкції, розділені запити й `ExecuteUpdate`/`ExecuteDelete`. Коли їх уже застосовано, допоможуть ще три прийоми.

> **Рекомендація.** Перш ніж щось змінювати, запишіть і перегляньте фактичний SQL EF (`LogTo` або профілювальник). Більшість проблем продуктивності EF невидимі в C# і очевидні, щойно побачите SQL.

### Пагінація: ніколи не завантажуйте необмежений набір результатів

`ToListAsync()` для таблиці, що зростає до мільйонів рядків, зрештою виведе сервіс із ладу. Завжди обмежуйте запити:

```csharp
var page = await db.Products
    .OrderBy(p => p.Id)
    .Skip((pageNumber - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync();
```

`Skip` перетворюється на `OFFSET`, але база й далі читає та відкидає кожен пропущений рядок. Тому сторінка 10 000 коштує стільки ж, скільки читання десяти тисяч сторінок. Для великих зміщень застосовуйте **пагінацію за ключем**: запам’ятовуйте останній ключ, показаний клієнту, і запитуйте `WHERE Id > @lastId ORDER BY Id LIMIT @pageSize`. Індекс відповість безпосередньо незалежно від номера сторінки.

### Скомпільовані запити

Щоразу, коли EF виконує LINQ-запит, потрібно перетворити дерево виразів на SQL (розібрати й проаналізувати його, закешувати за формою). Для гарячого запиту, виконуваного мільйони разів, ці витрати накопичуються. `EF.CompileQuery` (або `CompileAsyncQuery`) виконує перетворення один раз і повертає делегат для повторного використання:

```csharp
private static readonly Func<AppDb, int, Task<User?>> _getUser =
    EF.CompileAsyncQuery((AppDb db, int id) =>
        db.Users.FirstOrDefault(u => u.Id == id));

public Task<User?> GetUserAsync(int id) => _getUser(_db, id);
```

Це дрібна оптимізація: застосовуйте її лише тоді, коли профілювання показало, що bottleneck (вузьке місце) стала компіляція запиту, а не типово.

### Масове додавання й обмеження SaveChanges

`ExecuteUpdate` і `ExecuteDelete` дають змогу змінювати багато рядків, які не потрібно завантажувати. Для вставок такого засобу немає, і саме тут команди найчастіше виявляють межу `SaveChanges`.

`SaveChanges` не такий наївний, як здається. Він упорядковує очікувані зміни за залежностями, а потім **об’єднує** команди в якомога меншу кількість циклів туди й назад: провайдер SQL Server типово пакує до 42 команд в одну групу (`MaxBatchSize` можна налаштувати), а Npgsql теж об’єднує команди. Тож 1000 вставок не означають 1000 циклів. Але все одно виконуються 1000 параметризованих команд `INSERT` з 1000 наборами параметрів і роботою механізму відстеження для кожної сутності.

Саме ця робота механізму відстеження дивує людей:

```csharp
// Quadratic: DetectChanges runs on every Add, scanning everything added so far.
foreach (var p in products)
    ctx.Products.Add(p);           // 50k entities -> DetectChanges 50k times

// Linear: one DetectChanges pass at the end.
ctx.Products.AddRange(products);
```

`Add` викликає `DetectChanges`, який обходить усі відстежувані сутності й шукає зміни. Тож додавання *n* сутностей по одній створює квадратичну складність O(n²) у механізмі відстеження. Саме це пояснює класичне запитання: «Чому імпорт 50 000 рядків триває чотири хвилини, коли база даних простоює?» `AddRange` зводить роботу до одного проходу. Для імпортів можна ще й повністю вимкнути виявлення змін (`ctx.ChangeTracker.AutoDetectChangesEnabled = false`), якщо потім його знову ввімкнути.

Навіть після оптимізації `SaveChanges` відстає від максимальної швидкості приймання даних базою, бо bottleneck є протокол: кожен рядок надсилається як параметризована команда. В обох провідних рушіях є шлях масового завантаження, який узагалі оминає протокол команд: SQL Server має `SqlBulkCopy`, PostgreSQL — двійковий протокол `COPY`, доступний через Npgsql:

```csharp
await using var conn = new NpgsqlConnection(connectionString);
await conn.OpenAsync(ct);

await using var writer = await conn.BeginBinaryImportAsync(
    "COPY products (sku, name, price) FROM STDIN (FORMAT BINARY)", ct);

foreach (var p in products)
{
    await writer.StartRowAsync(ct);
    await writer.WriteAsync(p.Sku, NpgsqlDbType.Text, ct);
    await writer.WriteAsync(p.Name, NpgsqlDbType.Text, ct);
    await writer.WriteAsync(p.Price, NpgsqlDbType.Numeric, ct);
}

await writer.CompleteAsync(ct);   // nothing is written unless you call this
```

Різниця велика. Завантаження кількох сотень тисяч рядків через `SaveChanges` триває хвилини, а через `COPY` — секунди: рядки передаються серверу безперервно за одну операцію, без розбору кожної команди, прив’язування параметрів і відстеження.

> **Нюанс:** саме `CompleteAsync()` завершує двійковий імпорт. Якщо звільнити writer, не викликавши цей метод, увесь імпорт відкочується — і код цього непомітно не виявить, бо exception (виняток) не буде. Якщо забути його викликати, щоночі імпорт «успішно» завершуватиметься, а таблиця залишатиметься порожньою.

Вибір переважно залежить від масштабу й того, що ще потрібно виконати:

| Рядків за операцію | Засіб | Чому |
|---|---|---|
| До ~100 | `SaveChanges` | Команди вже об’єднано; витрати механізму відстеження незначні. Доменною event (подія) й перехоплювачами можна користуватися звичайно. |
| ~100–10 000 | `AddRange` + `SaveChanges`, виявлення змін вимкнене | Досі одна транзакція й ваша модель сутностей, додаткової залежності немає. |
| 10 000+ | `SqlBulkCopy` / `COPY` або бібліотека масових операцій | Bottleneck стає протокол команд; прибирає його лише масове завантаження. |
| «Змінити рядки, які не потрібно читати» | `ExecuteUpdate` / `ExecuteDelete` | Один декларативний запит; нічого не матеріалізується. |

Бібліотеки **EFCore.BulkExtensions** і **linq2db.EntityFrameworkCore** надають обгортки над масовими API провайдерів із інтерфейсом, схожим на EF (`BulkInsertAsync`, `BulkMergeAsync`), і додають підтримку upsert, якої немає в базових API. Залежність виправдана, якщо потрібна поведінка на кшталт `MERGE`; для простого додавання рядків вона зайва.

> **Пастка:** масові операції обходять усе, що EF додає поверх бази: немає відстеження, перехоплювачів, events `SaveChanges`, надсилання доменних events і перевірки даних. Саме тому вони швидкі й саме тому доречні в імпортах і завданнях обслуговування, а не всередині доменної логіки.

## Практичний PostgreSQL: індекси й плани запитів

SQL у [Розділі 7](#chapter-7-data-access) не залежить від рушія. PostgreSQL став типовою реляційною базою даних для нових сервісів .NET; він відрізняється від SQL Server у питаннях індексації й діагностики повільних запитів. Добра новина: Postgres зрозуміло повідомить, що саме він зробив, якщо знати, як запитати.

### Модель зберігання, яка пояснює все інше

Три факти про зберігання рядків у Postgres пояснюють більшість його поведінки.

**Кластеризованого індексу немає.** Рядки таблиць містяться в невпорядкованій **купі**, а кожен індекс, зокрема первинний ключ, — окрема структура, записи якої вказують на фізичне розташування рядка (`ctid`). Отже, пошук за первинним ключем завжди має два кроки: знайти запис в індексі, а потім отримати рядок із купи. Уявлення SQL Server «кластеризований індекс *і є* таблицею» тут не працює; звичку обирати ключ кластеризації також не можна перенести.

**Кожне оновлення записує нову версію рядка.** Postgres реалізує MVCC, ніколи не змінюючи рядок на місці: `UPDATE` записує цілу нову версію й позначає стару як мертву; `DELETE` лише позначає рядок як мертвий. Пізніше **autovacuum** вилучає мертві версії. Через це таблиця, яку часто оновлюють, росте навіть за сталої кількості рядків (**роздування**); також через це довготривала транзакція дорога для *всієї* бази — доки вона відкрита, неможливо очистити версії, новіші за найстарішу відкриту транзакцію.

Тут є важлива оптимізація: якщо оновлення **не зачіпає жодного стовпця з індексом** і на сторінці є вільне місце, Postgres виконує **HOT update**: нова версія потрапляє на ту саму сторінку, і жоден індекс змінювати не треба. Для таблиці з вісьмома індексами HOT-оновлення трапляються рідко; із трьома — частіше. Індекси коштують вам під час *кожного* запису, а не лише у звичний спосіб.

**Сам індекс не може довести, що вам видно рядок.** Інформація про видимість зберігається в купі, тож запит, відповідь на який знайшлася цілком в індексі, усе одно має перевірити видимість рядка для вашого знімка. У Postgres є **карта видимості**, яка позначає сторінки, де всі рядки видимі всім, і дає змогу пропустити купу. Це робить можливою **перевірку лише за індексом** (index-only scan); ось чому в плані є `Heap Fetches: N` і чому відразу після масового оновлення таблиця тимчасово втрачає такі перевірки, доки autovacuum не оновить карту.

### Вибір типу індексу

B-tree — типовий варіант і здебільшого правильний, але в Postgres є справді корисний набір індексів:

| Тип | Для чого підходить | Зауваження |
|---|---|---|
| **B-tree** | Рівність, діапазони, сортування, `LIKE 'prefix%'` | Типовий тип. Також обслуговує `ORDER BY` і `MIN`/`MAX`. |
| **GIN** | Включення в `jsonb`, масиви, повнотекстовий пошук | Багато ключів на рядок. Оновлюється повільно; можна налаштувати `fastupdate`. |
| **GiST** | Геометрія, діапазони, найближчий сусід, обмеження-винятки | Розширюваний тип; на ньому побудовано PostGIS. |
| **BRIN** | Величезні таблиці, де фізичний порядок відповідає стовпцю (часові ряди) | Дуже малий — кілобайти для таблиці на гігабайти, — але працює лише за природно впорядкованих даних. |
| **Hash** | Рівність для великих значень | Рідко вартий зусиль: B-tree майже так само добре обробляє рівність і має більше можливостей. |

Практичні правила для B-tree:

- **Багатостовпцеві індекси дотримуються правила лівого префікса.** Індекс `(customer_id, created_at)` обслуговує `WHERE customer_id = ?` і `WHERE customer_id = ? ORDER BY created_at`, але не окреме `WHERE created_at > ?`. Спершу вказуйте стовпці рівності, далі — діапазону або сортування; пояснення наведено в [підрозділі «Індекси: кластеризовані, некластеризовані, покривні»](#indexes-clustered-non-clustered-covering).
- **Індекс може надати дані вже відсортованими.** Якщо порядок індексу відповідає `ORDER BY`, вузла `Sort` у плані не буде — рядки надійдуть відсортованими. Напрямок і `NULLS FIRST/LAST` також мають збігатися.
- **`INCLUDE` робить індекс покривним**, тож запит можна виконати, не звертаючись до купи.
- **Часткові індекси** індексують лише рядки, які ви справді запитуєте, тому вони значно менші й дешевші в обслуговуванні.
- **Індекси виразів** призначені для індексації обчислених значень. Вони потрібні, бо *будь-яка* функція, застосована до стовпця, не дає скористатися звичайним індексом цього стовпця.

```sql
-- Only open orders are ever listed, and always newest first.
CREATE INDEX idx_orders_open_recent
    ON orders (created_at DESC)
    WHERE status = 'open';

-- "Email must be unique among users who are not soft-deleted."
CREATE UNIQUE INDEX uq_users_email_active
    ON users (lower(email))
    WHERE deleted_at IS NULL;
```

Другий приклад варто запам’ятати: **частковий унікальний індекс** виражає умовне обмеження унікальності, якого не можна задати звичайним обмеженням, і саме на рівні бази гарантує унікальність, потрібну для безпечної перевірки в застосунку (див. перевірку даних у [Розділі 5](#chapter-5-http-and-web-apis): без цього індексу послідовність «перевірити, потім вставити» містить race condition, а не встановлює правило).

EF Core може описати все це, тож не обов’язково додавати SQL вручну до міграцій:

```csharp
modelBuilder.Entity<Order>()
    .HasIndex(o => o.CreatedAt)
    .IsDescending()
    .HasFilter("status = 'open'")
    .IncludeProperties(o => o.Total);
```

### Читання EXPLAIN

`EXPLAIN` показує план, який *обрав* планувальник, разом з оцінками. `EXPLAIN (ANALYZE, BUFFERS)` справді виконує запит і додає фактичні результати й обсяг вводу-виводу. Для діагностики завжди використовуйте другий варіант: самі оцінки приховують найцікавіше.

> **Нюанс:** `EXPLAIN ANALYZE` виконує команду, зокрема `UPDATE` і `DELETE`. Обгорніть її в транзакцію: `BEGIN; EXPLAIN (ANALYZE) ...; ROLLBACK;`.

Читайте дерево плану **зсередини назовні**: спершу виконується найбільш відступлений вузол, а потім передає результат батьківському. Майже всю діагностичну цінність дають три речі:

1. **Оцінені `rows=` порівняно з фактичними `rows=`.** Велика розбіжність означає, що планувальник працює з поганими даними; кожне його рішення вище в дереві може бути хибним.
2. **`actual time=` і `loops=`.** Час указано *для кожного циклу*. Вузол із `actual time=0.3..0.4 rows=1 loops=50000` виконувався не 0,4 мс, а двадцять секунд.
3. **`Buffers: shared hit=` порівняно з `read=`.** `hit` означає, що сторінка була в кеші; `read` — що її довелося читати з операційної системи. Запит із хорошим планом, але десятками тисяч операцій читання, виконує надто багато вводу-виводу.

Ось типовий план із реального життя — endpoint (кінцева точка) списку сповільнилася в міру зростання таблиці:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total
FROM orders
WHERE status = 'open'
ORDER BY created_at DESC
LIMIT 20;
```

```
Execution Time: 812.503 ms
```

Тут є все потрібне. `Rows Removed by Filter: 1903416` означає, що база прочитала два мільйони рядків, щоб залишити дев’яносто шість тисяч. `Sort` показує, що їх усі відсортували, щоб повернути двадцять. `read=23891` означає, що більшість даних надійшла з диска. Оцінка відповідає фактичній кількості, тож планувальник не помилився — він просто не мав кращого варіанта. Частковий індекс, наведений вище, змінює план:

```
Limit  (cost=0.42..2.31 rows=20 width=24)
       (actual time=0.028..0.061 rows=20 loops=1)
  Buffers: shared hit=24
  ->  Index Scan using idx_orders_open_recent on orders
        (cost=0.42..9124.55 rows=96584 width=24)
        (actual time=0.026..0.057 rows=20 loops=1)
Execution Time: 0.089 ms
```

Немає `Filter`, бо в індексі є лише відкриті замовлення. Немає `Sort`, бо індекс уже відсортований за `created_at DESC`. Було 24 влучання в буфер замість 25 000 читань, а час зменшився з 812 до 0,09 мс. `LIMIT` зупиняє сканування, щойно знайдено двадцять рядків, тому фактична вартість — лише частина оціненої повної вартості вузла.

Словник для читання будь-якого плану:

| Вузол | Значення |
|---|---|
| `Seq Scan` | Читає всю таблицю. Правильно для малих таблиць і фільтрів, що залишають більшість рядків; проблема за вибіркового фільтра. |
| `Index Scan` | Проходить індекс і отримує з купи кожен відповідний рядок. |
| `Index Only Scan` | Отримав відповідь лише з індексу. Перевірте `Heap Fetches`: велике число означає застарілу карту видимості. |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | Збирає адреси відповідних рядків, сортує їх і читає купу у фізичному порядку. Використовується, якщо відповідностей надто багато для ефективного випадкового доступу. `Recheck Cond` з `lossy=true` означає, що пошук повернувся до точності сторінок. |
| `Nested Loop` | Для кожного зовнішнього рядка шукає внутрішній. Чудово за малої зовнішньої таблиці; квадратично, якщо вона велика. |
| `Hash Join` | Створює хеш однієї сторони й шукає збіги для іншої. Звичайний вибір для великих невідсортованих з’єднань. |
| `Merge Join` | Обидві сторони відсортовано й проходять паралельно. Дешево, коли індекси вже забезпечують потрібний порядок. |
| `Sort` | Перевірте `Sort Method`: `quicksort`/`top-N heapsort` із `Memory:` — добре; `external merge` із `Disk:` означає, що сортування вийшло на диск і `work_mem` замалий. |
| `Memoize` | Кешує пошуки внутрішньої таблиці в `Nested Loop` (PostgreSQL 14+). Часто рятує план із повторними пошуками. |
| `Gather` / `Workers Launched` | Паралельне виконання. Корисне для великих сканувань, але додає зайві витрати для малих. |

### Коли план неправильний

Якщо оцінена й фактична кількість рядків сильно розходяться, планувальник отримав неправильні дані, і виправлення треба шукати до запиту:

- **Застаріла статистика.** `ANALYZE orders;` оновлює її. Autovacuum робить це після досягнення порогу, тому таблицю після масового завантаження можуть планувати за статистикою порожньої таблиці. Це вагома причина явно запускати `ANALYZE` після імпорту.
- **Корельовані стовпці.** Планувальник вважає умови незалежними, тому `WHERE country = 'DE' AND city = 'Berlin'` перемножує дві вибірковості й оцінює надто мало рядків. `CREATE STATISTICS ... (dependencies)` навчає його враховувати залежність.
- **Функція навколо стовпця.** Для `WHERE lower(email) = ...` не можна скористатися індексом `email`. Додайте індекс виразу або зробіть стовпець нечутливим до регістру через `citext` чи недетерміновану колацію ICU.
- **Типове значення `random_page_cost` — 4.0**, яке моделює обертовий диск. Для сховища на SSD реалістичне значення близько 1.1; неправильне значення послідовно схиляє планувальник до повного сканування.
- **`LIMIT` із хибною оцінкою.** Планувальник вважає, що зможе зупинитися рано, і вибирає план, який проходить індекс, доки не знайде достатньо відповідностей. Якщо умова трапляється рідше, ніж оцінено, такий прохід охоплює всю таблицю. Класичний випадок: «для більшості клієнтів миттєво, для одного — тридцять секунд».

> **Пастка:** `.Where(u => u.Email.ToLower() == email)` у LINQ стає `lower(email) = $1` у SQL і непомітно вимикає індекс `email`. У EF Core для PostgreSQL це найпоширеніший випадковий спосіб знешкодити індекс. Індексуйте вираз або виправте колацію стовпця.

### Як знайти запити, які варто переглянути

Не можна виконати `EXPLAIN` для запиту, який ви не знайшли. Два розширення допоможуть:

- **`pg_stat_statements`** агрегує всі нормалізовані команди, кількість викликів і загальний час виконання. Сортуйте за `total_exec_time`, а не за `mean_exec_time`: найбільше коштує зазвичай швидкий запит, що виконується постійно, а не повільний, який запускають раз на годину.
- **`auto_explain`** записує план кожної команди, що перевищує заданий час. Це дає змогу захопити план запиту, який стає повільним лише в продакшені з продакшен-даними.

Також варто переглянути `pg_stat_user_indexes`: індекс із `idx_scan = 0` після репрезентативного періоду створює самі витрати — збільшує кількість операцій запису й заважає HOT-оновленню. Видаліть його.

### Бік .NET

Отримати SQL із EF Core — лише перший крок; `LogTo` виведе його, а в розробці `EnableSensitiveDataLogging` покаже значення параметрів, щоб можна було точно відтворити запит. Виконуйте `EXPLAIN` з **тими самими значеннями параметрів**, бо вибірковість саме й визначає рішення планувальника.

Варто знати дві особливості Npgsql:

- **Автоматична підготовка.** Після кількох виконань Npgsql перетворює команду на підготовлену на сервері (`Max Auto Prepare`). Це економить час розбору й планування, але після п’яти виконань Postgres може перейти до **узагальненого плану**, створеного без значень параметрів. Для стовпця з перекошеним розподілом це поганий компроміс. Обхідний варіант — `plan_cache_mode = force_custom_plan`.
- **Connection pools (пули з’єднань) змінюють правила.** PgBouncer у режимі пулінгу транзакцій розподіляє підключення між транзакціями, що ламає стан рівня сеансу. Підготовлені команди традиційно ставали першими жертвами: команда, підготовлена на одному з’єднанні сервера, не існувала на наступному. Починаючи з PgBouncer 1.21, він відстежує підготовлені на рівні протоколу команди (саме такі використовує Npgsql) і повторно готує їх на з’єднанні, до якого потрапила транзакція; у 1.24 це ввімкнули типово (`max_prepared_statements = 200`). Команди рівня SQL `PREPARE`/`EXECUTE` досі ламаються; так само driver-level підготовка не працює зі старим PgBouncer або за значення 0. Пулінг розглянуто в підрозділі [Керування підключеннями під навантаженням](#connection-management-under-load). Тут важливо, що виграш від кешування плану на боці драйвера може повністю зникнути залежно від проміжного компонента.

Насамкінець — три налаштування зіставлення, які усувають цілі класи проблем: зберігайте часові позначки як `timestamptz`, а не `timestamp` (див. [Розділ 15](#chapter-15-dates-money-and-strings), де пояснено, чому «місцевий час» не можна зберігати як поняття); для даних, за якими виконуватимете запити, використовуйте `jsonb`, а не `json`, і створіть індекс GIN; замість розкидати `ToLower()` по LINQ, використовуйте `citext` або нечутливу до регістру колацію.

> **Рекомендація:** індексуйте реальні запити, а не стовпці, які здаються важливими. Перед додаванням і після нього зберігайте `EXPLAIN (ANALYZE, BUFFERS)` у pull request і видаляйте індекси, до яких лічильник сканувань жодного разу не звертався.

## Кешування — поглиблений розгляд

[У Розділі 7](#chapter-7-data-access) розглянуто основи: `IMemoryCache` і `IDistributedCache`, підхід cache-aside, інвалідацію, шторми запитів до кешу й HybridCache. Додаткове судження senior полягає в тому, *коли* взагалі варто кешувати: дані, які **читають набагато частіше, ніж змінюють**, і **які можуть бути трохи застарілими** (довідкові дані, обчислені підсумки, згенеровані фрагменти). Дані, що швидко змінюються, є критичними для конкретного користувача або мають бути узгодженими, кешувати не варто. Для кожного кешу потрібні строк придатності, обмеження розміру й спосіб оновлення застарілих даних. У решті цього підрозділу йдеться про надійну роботу спільного рівня кешування Redis.

### Практичний Redis: проєктування ключів, типи даних і витіснення

`IDistributedCache` показує Redis як словник масивів байтів. Цього досить для початку, але така абстракція приховує більшість переваг Redis. Знання кількох нюансів окупиться.

**Проєктування ключів — це проєктування схеми.** У Redis немає таблиць, тож структура ключа — єдина структура, яку ви маєте. Звична форма — ієрархічна назва з двокрапками: від загального до конкретного, з окремим сегментом версії:

```
shop:v3:product:1234
shop:v3:product:1234:reviews
shop:v3:tenant:acme:cart:9f2c
```

Саме сегмент версії часто пропускають, а потім шкодують. Коли форма кешованого об’єкта змінюється після deployment (розгортання), старі записи десеріалізуються в новий тип як безлад або спричиняють помилку. Збільште `v3` до `v4`, і вся попередня версія стане недоступною за ключем та природно зникне після завершення строку дії. Це перейменування замість масового видалення, яке не спричиняє шторм запитів до бази під час deployment.

**Завжди задавайте TTL і додавайте випадковість.** Кеш без строку дії — витік пам’яті з гарними манерами. А якщо deployment чи пакетне завдання одночасно створить десять тисяч ключів з однаковим TTL, усі вони закінчаться одночасно, спричинивши спільне промахування — шторм за розкладом. Невеликий випадковий розкид у кілька відсотків розсинхронізує строки.

**Використовуйте типи даних.** Якщо зберігати серіалізований об’єкт у звичайному рядку, після кожної зміни поля доведеться переписувати все значення, а кожне читання передаватиме його повністю:

| Тип | Для чого використовувати |
|---|---|
| String | Серіалізований об’єкт, лічильник (операція `INCR` атомарна), прапорець |
| Hash | Об’єкт, поля якого читають чи змінюють окремо: `HSET user:1 last_seen ...` змінює одне поле |
| Sorted set | Таблиці лідерів, обмежувачі частоти й індекси за часом; запити за діапазоном оцінки |
| Set | Перевірка належності й індекси за тегами: «які ключі належать товару 1234» |
| List | Прості queue (черга); `BLPOP` блокує виконання до отримання елемента |
| Stream | Журнал лише для додавання з групами consumers (споживачі) — справжній засіб для messaging (обмін повідомленнями) (див. [Розділ 11](#chapter-11-messaging-and-background-work)) |

**Інвалідація за тегом** показує користь множин. Пошук ключів за шаблоном для видалення недоступний: `KEYS pattern` проходить усе простір ключів і, оскільки Redis виконує команди в одному потоці, блокує *всіх інших клієнтів*. Альтернатива — `SCAN` із курсором, який не блокує; його варто застосовувати в обслуговувальних сценаріях. Натомість підтримуйте індекс самостійно: коли кешуєте похідне значення, що залежить від товару 1234, додайте його ключ до множини `tag:product:1234`. Після запису прочитайте множину, видаліть ключі, а потім і множину. HybridCache безпосередньо реалізує цю ідею за допомогою тегів у `GetOrCreateAsync` і `RemoveByTagAsync`.

**Час на обмін даними — головні витрати.** Операція Redis займає мікросекунди на сервері й потребує мережевого циклу туди й назад, тому десять послідовних `GET` коштують десяти циклів, а один пакет — одного. StackExchange.Redis автоматично створює pipeline (конвеєр), якщо запустити кілька завдань, перш ніж очікувати на їх завершення:

```csharp
var db = _mux.GetDatabase();
var batch = ids.Select(id => db.StringGetAsync($"shop:v3:product:{id}")).ToArray();
var values = await Task.WhenAll(batch);   // one round trip, not ids.Length
```

**Політику витіснення потрібно обрати.** Коли Redis досягає `maxmemory`, типова політика `noeviction` починає *відхиляти записи*: кеш перестає приймати нові значення, і запис до нього спричиняє помилку застосунку. Для звичайного кешу потрібні `allkeys-lru` (або `allkeys-lfu`), які видаляють найменш корисні ключі. Неправильний вибір перетворює заповнений кеш на збій, а не просто уповільнення. Це найпоширеніша помилка конфігурації Redis у продакшені.

> **Нюанс:** Redis виконує команди в одному потоці. Саме це робить його операції атомарними й затримку передбачуваною, але через це одна дорога команда — повний перегляд `KEYS`, великий `LRANGE`, необмежений сценарій Lua або видалення значення на кілька мегабайт — затримує кожного клієнта на весь час виконання. Повільні запити Redis уповільнюють не одного клієнта, а всіх.

Ще дві практичні нотатки. `ConnectionMultiplexer` — дорогий, потокобезпечний об’єкт, розрахований на спільне використання: зареєструйте рівно один екземпляр як **singleton** і ніколи не огортайте його в `using` (це типова помилка й причина загадкових штормів з’єднань; строки життя розглянуто в [Розділі 3](#chapter-3-how-net-runs-your-code)). А в **кластері Redis** ключі розподіляються за хеш-слотами, тож операція з кількома ключами працює лише тоді, коли всі ключі опинилися на тому самому вузлі. Візьміть спільну частину ключа у фігурні дужки — `cart:{acme}:9f2c`; Redis хешуватиме лише її й триматиме ключі клієнта разом.

> **Пастка:** не використовуйте блокування Redis для гарантування правильності. Одновузлове блокування `SET key value NX PX` годиться, щоб придушити дубльовану роботу (один екземпляр оновлює кеш, решта чекають), але не гарантує взаємного виключення під час перемикання вузлів; розподілений варіант Redlock спирається на припущення про час, які активно оскаржують. Якщо дублювання роботи двох worker-ів зіпсує дані, гарантуйте правильність у базі за допомогою обмеження унікальності чи блокування рядка, а не в кеші.

Насамкінець вимірюйте показник, який повідомляє, чи працює кеш: **частку влучань**. Якщо вона нижча приблизно за 80%, зазвичай кешують не ті дані або строки дії коротші за час повторного використання. Тепер кожен промах коштує мережевого циклу *плюс* початкового запиту, через що погано налаштований кеш повільніший за повну відсутність кешу.

### Стан сеансу й stateless-рівень застосунку

Щойно ви запускаєте кілька екземплярів застосунку за балансувальником навантаження, **стан у пам’яті стає проблемою**. Якщо екземпляр A зберігає сеанс користувача у власній оперативній пам’яті, а наступний запит потрапляє на екземпляр B, сеанс зникає. Тому спільний стан виносять за межі процесу — найчастіше до Redis:

```
        ┌── App Instance 1 ──┐
Client ─┤   App Instance 2   ├──▶ [ Redis ] ← single source of shared truth
        └── App Instance 3 ──┘       (cache + session store)
```

Налаштуйте сеанси ASP.NET Core на використання розподіленого кешу, і будь-який екземпляр зможе обслуговувати будь-якого користувача. Так рівень застосунку стає **stateless** — саме ця властивість спрощує horizontal scaling (горизонтальне масштабування): сервери застосунку без стану, винесений назовні стан і асинхронний messaging — короткий опис архітектури майже кожної сучасної масштабованої системи. Якщо кешоване значення залежить від даних, якими володіє інший сервіс, інвалідація стає event: consumer повідомлення `ProductUpdated` видаляє відповідний ключ ([Розділ 11](#chapter-11-messaging-and-background-work)).

> **Зв’язок із підсумковим проєктом.** На кроці 5 ShopCore (кешування, автентифікація та observability (спостережуваність)) у [Розділі 44](#chapter-44-capstone-one-project-growing-up) додає Redis як розподілений кеш для частих читань каталогу товарів і виконує інвалідацію під час запису.

## Вертикальне й horizontal scaling

Більшу частину життя системі достатньо однієї добре налаштованої бази даних. Ви додаєте індекси, кешуєте часто використовувані запити, купуєте потужніший сервер — і графіки залишаються зеленими. Аж до дня, коли це змінюється. Журнал попереднього запису не встигає скидатися на диск, нічний звіт блокує таблицю, потрібну клієнтам, підключення накопичуються швидше, ніж пул може їх видати, а трафік найбільшого клієнта починає витісняти запити решти. Масштабування даних — це мистецтво відсувати цей день якомога далі й знати, що робити, коли він зрештою настане.

Є лише два напрями масштабування, і вибір визначає всі подальші рішення.

**Вертикальне масштабування** (масштабування *вгору*) означає надати одній машині більше ресурсів: більше ядер CPU, RAM, швидші диски NVMe. Це надзвичайно просто. Застосунок не змінюється, транзакції залишаються ACID, а з’єднання таблиць і далі працюють. Але межа існує: найбільший хмарний екземпляр бази даних має скінченні ресурси, а ціна зростає експоненційно. Перехід від середньої машини до великої недорогий; подвоїти найбільшу машину — неможливо за будь-які гроші.

**Horizontal scaling** (масштабування *назовні*) означає додати машини й розподілити між ними навантаження. Теоретично межі майже немає, але ціна — складність: дані тепер лежать у кількох місцях, а зручні гарантії одного вузла — глобальна транзакція, дешеве з’єднання, унікальний індекс — поступово зникають.

> **Рекомендація:** спершу масштабуйте *вгору*, доки це справді не стане болісним, і лише тоді масштабуйте *назовні*. Один екземпляр Postgres на сучасному обладнанні може обслуговувати величезні навантаження. Horizontal scaling — це двері в один бік, які назавжди підвищують операційну складність; проходьте крізь них свідомо, а не за звичкою.

Далі розглянуто методи horizontal scaling — приблизно від найменш до найбільш інвазивних.

## Масштабування читань за допомогою реплікації

Найдешевший спосіб horizontal scaling спирається на факт, справедливий майже для кожної бізнес-системи: **читань набагато більше, ніж записів**. Каталог товарів записують один раз, а читають мільйон разів. Якщо обслуговувати читання з копій бази даних, головному вузлу залишиться приймати лише записи.

Це і є **реплікація**. *Первинний вузол* (або *лідер*) приймає всі записи й надсилає свої зміни — у Postgres це журнал попереднього запису — одній чи кільком *реплікам* (або *послідовникам*). Кожна репліка застосовує ті самі зміни й може обслуговувати запити на читання. Додайте репліки — обслуговуватимете більше читань.

### Затримка реплікації — ключове питання

Репліки не оновлюються миттєво. Між фіксацією запису на первинному вузлі й появою зміни на репліці минає певний час — зазвичай мілісекунди, під навантаженням іноді секунди. Ця **затримка реплікації** — найважливіше, що потрібно знати про репліки для читання, бо вона порушує припущення, на яке ваш код мовчки покладався завжди: *читання власних записів*.

Уявіть, що користувач змінив ім’я у своєму профілі. Запис іде на первинний вузол. Сторінка перезавантажується, надсилає запит на читання, а той спрямовується на репліку, яка ще не встигла оновитися. Користувач бачить *старе* ім’я й вирішує, що збереження не спрацювало. Він надсилає запит знову — і у вас уже є звернення до підтримки.

> **Пастка:** репліки для читання дають **consistency (узгодженість) із часом**, а не сильну consistency одного вузла. У будь-якому сценарії, де користувач читає дані відразу після запису — надсилання форми, майстер налаштування, перевірка «чи збереглося?» — потрібно або спрямувати читання на первинний вузол, або погодитися на застарілі дані.

Поширені способи пом’якшення проблеми:

- **Після запису спрямовуйте читання на первинний вузол.** Після запису в межах запиту спрямовуйте наступні читання тієї самої логічної операції на первинний вузол.
- **Тимчасове закріплення за первинним вузлом.** Протягом кількох секунд після запису користувачем надсилайте туди всі його запити на читання.
- **Дозвольте застарілість, якщо вона не шкодить.** Для панелей моніторингу, результатів пошуку й звітів затримка у 200 мс зазвичай не має значення.

### Routing читань і записів в EF Core

EF Core не має вбудованої підтримки первинних вузлів і реплік, але шаблон простий: під час створення контексту визначте, чи він підключатиметься до первинного вузла або репліки, і видавайте потрібний екземпляр через фабрику.

```csharp
public sealed class CatalogContext(DbContextOptions<CatalogContext> options)
    : DbContext(options)
{
    public DbSet<Product> Products => Set<Product>();
}

public sealed class CatalogContextFactory(IConfiguration config)
{
    public CatalogContext CreateWrite() => new(Build("Primary", readOnly: false));
    public CatalogContext CreateRead()  => new(Build("Replica", readOnly: true));

    private DbContextOptions<CatalogContext> Build(string name, bool readOnly)
    {
        var builder = new DbContextOptionsBuilder<CatalogContext>()
            .UseNpgsql(config.GetConnectionString(name));
        // A replica context should never accidentally issue writes.
        if (readOnly)
            builder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
        return builder.Options;
    }
}
```

> **Пастка:** спокуслива альтернатива — один контекст із прапорцем `_readOnly`, який перемикають перед запитом і перевіряють в `OnConfiguring`, — непомітно дає збій. Конфігурацію контексту створюють один раз, а потім кешують (для екземпляра під час першого використання, а також між екземплярами, коли контекст пулізується або отримується з DI). Тому прапорець, змінений пізніше, мовчки ігнорується, а запит «до репліки» виконується на первинному вузлі. Обирайте підключення під час *створення* контексту, а не після нього.

Головне правило: **будь-який `SaveChanges` має виконуватися на первинному вузлі**, а запити лише на читання, для яких допустима затримка, — на репліці. `NoTracking` у контекстах реплік корисний подвійно: він швидший і структурно запобігає спробі збереження через контекст репліки.

## Керування підключеннями під навантаженням

Непомітна перешкода масштабуванню не пов’язана з обсягом даних: це **підключення**. Кожне підключення Postgres — окремий серверний процес, що споживає кілька мегабайт RAM, а сервер найкраще працює з *невеликою* кількістю активних підключень — часто лише кількома десятками. Але парк серверів застосунку, кожен зі своїм пулом підключень, легко може потребувати тисячі.

Виручають два рівні пулізації:

- **Пулізація на рівні застосунку.** ADO.NET / Npgsql пулізує підключення в межах процесу й повторно використовує їх для запитів замість того, щоб щоразу відкривати нове (відкриття підключення Postgres дороге: потрібні TCP-рукостискання й створення процесу). Це ввімкнено типово; пастка — *неправильно налаштувати максимальний розмір пулу*, через що сплеск повільних запитів вичерпує його, а запити стають у queue.
- **Зовнішній пулізатор, як-от PgBouncer.** Він стоїть між парком застосунків і Postgres та мультиплексує тисячі клієнтських підключень через невеликий пул справжніх підключень до бази. У режимі **пулізації транзакцій** справжнє підключення утримується лише протягом транзакції, тому сотні переважно неактивних клієнтів спільно використовують кілька серверних процесів. Безсерверним архітектурам і архітектурам з автоматичним масштабуванням, де кількість екземплярів непередбачувано зростає, пулізатор фактично *необхідний*, щоб не перевантажити базу даних.

> **Пастка:** режим пулізації транзакцій у PgBouncer порушує роботу всього, що спирається на стан сеансу між кількома операторами: `SET` на рівні сеансу, `PREPARE` на рівні SQL, `LISTEN/NOTIFY`, консультативні блокування, що утримуються між операторами. Підготовлені оператори на рівні протоколу, які використовує Npgsql, підтримуються лише починаючи з PgBouncer 1.21 за умови, що `max_prepared_statements` більше за 0 (типове значення починаючи з 1.24). Перш ніж розгортати рішення, з’ясуйте режим пулізації та його обмеження.

## Секціонування й шардинг

Реплікація масштабує *читання*, але нічого не змінює для *записів*: кожен запис усе одно надходить на єдиний первинний вузол, а весь набір даних має вміщатися на одній машині. Коли обсяг записів або даних перевищує можливості одного вузла, потрібно розділити самі дані. Це **секціонування**, а якщо секції розташовано на різних серверах бази даних — **шардинг**.

Ідея така: замість однієї таблиці з мільярдом рядків зберігати багато таблиць (шардів), кожна з яких містить частину рядків і розміщена на окремому сервері. Ви обираєте **ключ шарду** — стовпець, значення якого визначає шард для рядка, — і стратегію зіставлення ключів із шардами.

### Шардинг за діапазоном, хешем і ключем

- **Шардинг за діапазоном** розділяє дані за діапазонами ключа: клієнти A–F на шарді 1, G–M на шарді 2 тощо. Запити за діапазоном («усі замовлення за січень») залишаються в межах одного шарду, що ефективно. Небезпека — **гарячі точки**: якщо прізвища половини клієнтів починаються на S, відповідний шард перевантажений. Діапазони за часом особливо проблемні: шард поточного дня отримує *всі* записи, а вчорашній простоює.
- **Хеш-шардинг** передає ключ хеш-функції й вибирає шард за результатом. Це рівномірно розподіляє навантаження й усуває гарячі точки, але руйнує локальність: запит за діапазоном тепер має звертатися до *кожного* шарду.
- **Шардинг за каталогом/ключем** зберігає явну таблицю пошуку, яка зіставляє ключі (або діапазони ключів) із шардами. Такий підхід максимально гнучкий і полегшує ребалансування, але каталог стає критичною залежністю, яку треба підтримувати доступною та узгодженою.

### Вибір ключа шарду — найважливіше рішення

Ключ шарду — найважливіший вибір у всій архітектурі, бо він визначає, які запити будуть дешевими, а які — болісно повільними. Хороший ключ шарду має три властивості:

1. **Висока кардинальність** — достатньо різних значень, щоб розподілити дані між усіма шардами.
2. **Рівномірний розподіл** — жодне значення не домінує (не обирайте `Country`, якщо 80% користувачів живуть в одній країні).
3. **Відповідність шаблонам доступу** — найчастіші запити мають виконуватися в межах *одного* шарду.

Саме третя властивість — ключова. У багатоклієнтському SaaS `TenantId` часто є ідеальним ключем шарду: майже кожен запит і так обмежений одним клієнтом, тому природно потрапляє в один шард. Невдалий ключ перетворює найпоширеніший запит на **розсилання й збирання** результатів з усіх шардів.

> **Рекомендація:** обирайте ключ шарду за *шаблонами читання*, а не за моделлю даних. Питання не в тому, «як структуровані дані?», а в тому, «за чим відфільтровується 95% мого трафіку?»

### Проблеми запитів, з’єднань і транзакцій між шардами

Після поділу даних три речі, які раніше діставалися безкоштовно, стають дорогими або неможливими:

**Запити між шардами (розсилання й збирання).** Запит, не обмежений ключем шарду, потрібно надіслати *кожному* шарду, а результати об’єднати в застосунку. `ORDER BY ... LIMIT 10` на 20 шардах означає отримати по 10 найкращих рядків із кожного, а потім повторно відсортувати 200 рядків, щоб знайти справжню десятку. Агрегації, пагінація та `COUNT(*)` також стають складними.

**Розподілені з’єднання.** З’єднання двох таблиць дешеве лише тоді, коли потрібні рядки обох таблиць розміщені на *тому самому* шарді. Тому системи з шардингом намагаються **розміщувати поруч** пов’язані дані — наприклад, клієнта й усі його замовлення за ключем `CustomerId`, — щоб з’єднання виконувалися локально. З’єднання через межу шарду вимагає або передавати дані мережею, або повністю денормалізувати модель.

**Розподілені транзакції.** Одна ACID-транзакція між двома шардами потребує протоколу на кшталт двофазної фіксації (2PC). Він повільний, блокує ресурси на кількох вузлах і повністю зупиняється, якщо координатор завершує роботу посеред фіксації. На практиці більшість великих систем **відмовляється** від розподілених транзакцій і приймає consistency із часом: кожен шард фіксує зміни локально, а consistency між шардами відновлюється асинхронно за допомогою шаблонів на кшталт **Saga** (послідовність локальних транзакцій із компенсувальними діями в разі помилки; див. [Розділ 20](#chapter-20-distributed-systems)).

> **Пастка:** команда може розпочати шардинг, щоб розв’язати проблему швидкодії, а згодом виявити, що замінила проблему *пропускної здатності* проблемою *коректності й складності*. Єдина база даних із транзакціями та з’єднаннями — розкіш, якої не цінуєш, доки її не втратиш.

### Повторний розподіл шардів

Початковий розподіл шардів виявиться невдалим, бо дані зростатимуть нерівномірно. **Повторний розподіл шардів** — перенесення даних між шардами для їх ребалансування — одна з найскладніших операцій в інженерії даних, адже її потрібно виконувати *поки система працює*.

Полегшує це **узгоджене хешування** разом із великою кількістю малих **віртуальних шардів**. Замість прямого зіставлення ключів із 4 фізичними серверами зіставте їх (наприклад) із 256 віртуальними шардами, а вже ті — з фізичними серверами. Щоб додати потужності, перенесіть частину віртуальних шардів на новий сервер: переміститься лише частина даних, а зміна зіставлення буде оновленням метаданих, а не повним перерозподілом. Значний запас логічних шардів порівняно з поточними потребами («надмірний шардинг») — недорога страховка: пізніше можна розподілити їх між більшою кількістю обладнання, не перехешовуючи ключі.

## Міграції у масштабі (без простою)

У невеликій системі можна запустити міграцію, зупинити роботу на тридцять секунд і продовжити. У великому масштабі це неприйнятно; ще гірше, деякі міграції блокують великі таблиці на кілька хвилин і затримують кожен запит. Мета — **зміна схеми без простою**, а основний метод — шаблон **розширення/звуження** (також відомий як паралельна зміна).

Суть у тому, що **не можна одночасно розгорнути зміну схеми й код, якому вона потрібна**: під час поступового deployment стара й нова версії коду працюють водночас із тією самою базою. Тому кожну несумісну зміну потрібно розбити на кроки, сумісні назад:

1. **Розширення.** Додайте нову структуру, не видаляючи стару. Додайте стовпець, що допускає `NULL`, нову таблицю чи новий індекс (у Postgres його створюють через `CONCURRENTLY`, щоб не блокувати записи). Старий код його ігнорує, новий може почати використовувати. Цей крок безпечний, бо нічого не порушує.
2. **Міграція й подвійний запис.** Розгорніть код, який записує *і в стару, і в нову структуру*, а наявні рядки заповнюйте пакетами. Тепер дані узгоджені в обох формах.
3. **Звуження.** Коли весь код читає й записує нову структуру, а старого коду більше не залишилося, видаліть старий стовпець або таблицю в наступному випуску.

Наприклад, перейменування стовпця `Name` на `FullName` — це однорядкова зміна, яка за наївного виконання порушить роботу кожного запущеного екземпляра старої версії. Розширення/звуження перетворює її на послідовність: додати `FullName` (розширення) → розгорнути код, що записує в обидва стовпці, і заповнити наявні рядки (міграція) → розгорнути код, який використовує лише `FullName` → видалити `Name` (звуження). Кожен крок можна розгорнути окремо й скасувати.

> **Пастка:** операції `ALTER TABLE`, які переписують таблицю або беруть блокування `ACCESS EXCLUSIVE`, на цей час блокують усі читання й записи. Під навантаженням на великій таблиці це означає збій. Завжди перевіряйте, чи операція не блокує таблицю; створюйте індекси через `CONCURRENTLY`; додавайте стовпці *без змінного значення за замовчуванням* (у сучасному Postgres додавання стовпця зі сталим значенням за замовчуванням дешеве, але заповнення даних — ні).

[Розділ 7](#chapter-7-data-access) визначає, *де* виконувати міграції (під час запуску чи окремим кроком pipeline). **Feature flags (прапорці функцій)** ([Розділ 26](#feature-flags)) природно поєднуються з розширенням/звуженням: вони відокремлюють *deployment* коду, який використовує нову структуру, від її *випуску*. Це саме те, що потрібно, поки схема переходить до нового стану.

## Захоплення змін даних (CDC)

З шардингом чи без нього, великі системи рідко зберігають усі дані в одному місці. Каталог лежить у Postgres, пошук — в Elasticsearch, рушію рекомендацій потрібен потік events, а аналітиці — повний набір даних у сховищі. Наївний підхід — змусити застосунок записувати в усі ці системи — перетворюється на проблему розподілених транзакцій: що станеться, якщо запис у Postgres успішний, а в Elasticsearch — ні?

**Захоплення змін даних** розв’язує цю проблему, використовуючи власний журнал змін бази як джерело істини. Кожну зафіксовану зміну (вставлення, оновлення чи видалення) захоплюють і передають нижчим consumers. Оскільки журнал попереднього запису читається *після фіксації*, consumer бачить рівно ті зміни, які надійно збережено, — суперечності подвійного запису не виникають.

**Debezium** — фактичний стандарт платформи CDC з open source (відкритий код). Вона підключається до потоку реплікації бази (логічна реплікація Postgres, журнал binlog MySQL тощо) і публікує кожну зміну як event в **Kafka**. Далі один consumer оновлює пошуковий індекс, інший — кеш, ще один — аналітику. Усі вони відокремлені від застосунку й отримують дані з одного впорядкованого потоку.

### Транзакційний outbox і CDC

Поширена мета — *«коли я зберігаю замовлення, надійно опублікувати event OrderCreated»*. Для цього є два шаблони.

**Транзакційний outbox** (механіку розглянуто в [Розділі 11](#chapter-11-messaging-and-background-work)) записує бізнес-зміну й рядок events до таблиці `outbox` **у межах тієї самої локальної транзакції**. Оскільки обидві зміни належать одній ACID-транзакції, вони фіксуються або скасовуються разом — проблеми подвійного запису немає. Окремий процес-посередник згодом читає outbox і публікує events.

Посередник може опитувати таблицю outbox або — елегантніше — **CDC може читати таблицю outbox** і передавати її рядки до Kafka, забезпечуючи публікацію з малою затримкою без опитування. Поєднання «outbox + Debezium» — поширений і надійний шаблон.

Як пов’язані outbox і CDC? Outbox — це *events, які ваш застосунок навмисно записує за розробленим вами контрактом*; CDC — це *інфраструктура, що захоплює сирі зміни рядків*. Використовуйте **outbox**, коли потрібні чіткі доменні events зі стабільним контрактом. Використовуйте **сирий CDC**, коли потрібно реплікувати зміни таблиць або реагувати на них без змін у застосунку, наприклад передавати дані до аналітичного сховища. Вони чудово поєднуються: CDC часто слугує *транспортом* для рядків outbox.

> **Рекомендація:** ніколи не виконуйте подвійний запис до бази даних і message broker (брокер повідомлень) у коді застосунку, сподіваючись, що обидві операції пройдуть успішно. Використовуйте шаблон outbox, щоб event та зміна стану належали одній транзакції, а потім передавайте events через CDC або процес-посередник.

## NoSQL і поліглотне зберігання даних

Жодна база даних не підходить для всього, а деякі форми даних краще відповідають іншим моделям, ніж таблиці:

- **MongoDB (сховище документів):** зберігає документи, подібні до JSON. Підходить для ієрархічних даних, які читаються як єдине ціле (товар із вкладеними варіантами, характеристиками й відгуками). Гнучка схема годиться для даних, що змінюються, або різнорідних записів. Слабше працює з транзакціями між документами та складними з’єднаннями.
- **Redis (ключ-значення / оперативна пам’ять):** швидкий, бо працює в RAM. Ідеально підходить для кешування, стану сеансів, лічильників rate limiting (обмеження частоти), таблиць лідерів і pub/sub. Це не основне джерело даних; вважайте його вміст тимчасовим.
- **Elasticsearch (пошукова система):** створений для повнотекстового пошуку, ранжування за релевантністю й аналітики великих обсягів. Використовуйте його разом із головною базою, а не замість неї: саме вона залишається джерелом істини.

**Поліглотне зберігання даних** означає вибір потрібного сховища для кожного завдання: Postgres для транзакційної цілісності, Elasticsearch для повнотекстового пошуку, Redis для тимчасових даних сеансів, колоночне сховище для аналітики, графова база для запитів про зв’язки. CDC пов’язує ці сховища й синхронізує їх із єдиного джерела істини.

Та сама ідея в межах одного сервісу називається **сховищем читання CQRS** ([шаблон розглянуто в Розділі 21](#chapter-21-architecture)): записи йдуть до нормалізованої транзакційної моделі, а читання обслуговуються сховищами, сформованими саме під шаблони запитів (із попередніми з’єднаннями, денормалізованими даними чи індексами для окремої сторінки). Вони оновлюються асинхронно, часто з того самого потоку events або CDC. Ви приймаєте consistency із часом в обмін на швидкі моделі читання, які не конкурують із записами. А під ними працюють рівні кешу (у процесі, Redis, HTTP і CDN на периферії); CDC також може точно інвалідувати кеш, передаючи конкретні рядки, що змінилися.

> **Практичне правило.** Обирайте сховище за шаблоном доступу, а не за хайпом. Більшість систем поліглотні: реляційна база як джерело істини, Redis для кешування, Elasticsearch для пошуку. NoSQL — це спеціалізація, а не заміна.

## Багатоклієнтська архітектура

**Багатоклієнтський** застосунок обслуговує багатьох незалежних клієнтів (тенантів) на спільній інфраструктурі. Центральний інженерний компроміс — **ізоляція та ефективність**: сувора ізоляція (усе окремо) безпечна, але дорога; спільне розміщення (усе в одному місці) дешеве, але ризиковане. Є три основні моделі цього спектра.

### Три моделі ізоляції

**1. Спільна схема (стовпець-дискримінатор).** Усі клієнти використовують ті самі таблиці; кожен рядок клієнта має стовпець `TenantId`, і кожен запит фільтрує за ним. Це **найдешевша й наймасштабованіша** модель: одна база, одна схема, один пул підключень. Так працює більшість великих SaaS-продуктів. Ціна — ізоляцію *повністю забезпечує ваш код*: забудьте один `WHERE TenantId = ...` — і дані одного клієнта витечуть до іншого. Сусіди, які створюють значне навантаження, також безпосередньо ділять ресурси.

**2. Схема на клієнта.** Одна база, але кожен клієнт має власну схему (простір імен) і власну копію таблиць. Ізоляція краща — запит обмежений схемою, — а клієнтів можна частково резервувати й переносити незалежно. Але кількість схем створює операційне навантаження: міграції мають запускатися в сотнях схем, а тисячі схем перевантажують каталог бази даних.

**3. База даних на клієнта.** Кожен клієнт має окрему фізичну базу даних (або навіть сервер). Це **максимальна ізоляція**: помилка буквально не може перетнути межу бази, сусіди з великим навантаженням ізольовані, а преміум-клієнта можна розмістити на виділеному обладнанні чи у потрібному регіоні зберігання даних. Ціна — операційна складність: потрібно створювати, переносити, резервувати й моніторити сотні баз, а незадіяних ресурсів значно більше (кожна база має власні накладні витрати, навіть якщо клієнт крихітний).

| Модель | Ізоляція | Вартість/щільність | Операційне навантаження | Типове застосування |
|---|---|---|---|---|
| Спільна схема | Найслабша (залежить від коду) | Найдешевша, найщільніша | Найнижче | Високонавантажений SaaS, багато малих клієнтів |
| Схема на клієнта | Середня | Середня | Середнє | Середній сегмент, помірна кількість клієнтів |
| База на клієнта | Найсильніша | Найдорожча | Найвище | Корпоративні, регульовані клієнти, вимоги до розміщення даних |

> **Рекомендація:** багато зрілих SaaS-платформ використовують *гібридний підхід*: спільну схему для довгого хвоста дрібних клієнтів і окремі бази для великих корпоративних клієнтів, які платять за ізоляцію та вимагають зберігання даних у певному регіоні. Модель задається окремо для кожного клієнта, а не є глобальним рішенням.

### Визначення клієнта

Перш ніж виконати запит, система має відповісти: *для якого клієнта цей запит?* **Визначення клієнта** відбувається на ранньому етапі pipeline (у middleware) і зазвичай використовує одне з джерел:

- **Хост або піддомен** — `acme.myapp.com` → клієнт `acme`. Зрозуміло й зручно для кешування.
- **HTTP-заголовок** — власний заголовок `X-Tenant-Id`, поширений для API.
- **Claim у токені автентифікації** — JWT містить claim `tenant_id`. Це найбезпечніший спосіб, бо ідентичність клієнта криптографічно прив’язана до автентифікованого користувача й не може бути підроблена зміною URL.

Визначений клієнт зберігається в сервісі, обмеженому запитом (`ITenantContext`), який використовують усі наступні компоненти, зокрема `DbContext`.

> **Пастка:** визначити клієнта із заголовка чи параметра маршруту, яким керує *клієнт*, не звіривши його з дозволеними для автентифікованого користувача клієнтами, — класична вразливість підвищення привілеїв. Користувач, автентифікований для клієнта A, не повинен мати змоги задати `X-Tenant-Id: B` і читати дані клієнта B. Завжди перевіряйте запитуваного клієнта за claims токена.

### Забезпечення ізоляції глобальними фільтрами запитів EF Core

У моделі зі спільною схемою найгірший сценарій — забутий фільтр. Додавати `WHERE TenantId = @t` до кожного з сотень запитів — лише питання часу, перш ніж хтось про нього забуде. **Глобальні фільтри запитів** EF Core роблять ізоляцію *типовою поведінкою*, а не тим, про що потрібно пам’ятати: визначте фільтр один раз для сутності, і EF автоматично додаватиме його до **кожного** запиту цієї сутності.

```csharp
public class AppDbContext : DbContext
{
    private readonly ITenantContext _tenant;

    public AppDbContext(DbContextOptions options, ITenantContext tenant)
        : base(options)
    {
        _tenant = tenant;
    }

    public DbSet<Invoice> Invoices => Set<Invoice>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // Every query against Invoice is silently scoped to the current tenant.
        modelBuilder.Entity<Invoice>()
            .HasQueryFilter(i => i.TenantId == _tenant.TenantId);
    }

    // Also stamp TenantId on insert so nobody has to remember.
    public override int SaveChanges()
    {
        foreach (var entry in ChangeTracker.Entries<Invoice>())
            if (entry.State == EntityState.Added)
                entry.Entity.TenantId = _tenant.TenantId;
        return base.SaveChanges();
    }
}
```

Тепер `context.Invoices.ToList()` повертає лише рахунки поточного клієнта — фільтр вбудовано в SQL. Це **багаторівневий захист за замовчуванням**, а не повна гарантія. Пам’ятайте про способи його обійти:

- **`IgnoreQueryFilters()`** прибирає фільтр для запиту. Це потрібно для легітимних адміністративних задач і звітів, але це заряджена зброя: один необережний виклик — і ізоляцію втрачено.
- **Необроблений SQL** (`FromSqlRaw`) і **збережені процедури** повністю оминають фільтр; обмеження потрібно задавати вручну.
- **Завантаження навігацій і `Find()`** враховують фільтри, але будьте уважні зі зовнішніми ключами між клієнтами.
- Фільтр читає `_tenant.TenantId` **під час побудови запиту**, тому клієнта потрібно правильно визначити до виконання будь-якого запиту.

> **Пастка:** глобальний фільтр запиту захищає *читання*. Він **не** забороняє *вставити* рядок із неправильним `TenantId` або *оновити* рядок, завантажений через `IgnoreQueryFilters`. Автоматично задавайте `TenantId` під час вставлення (як вище) і вважайте кожен виклик `IgnoreQueryFilters` операцією, важливою для безпеки й вартою позначки під час перевірки коду. Для найсильнішого захисту додайте бар’єр на рівні бази: політики **безпеки на рівні рядків** Postgres забезпечують обмеження за клієнтом, навіть якщо застосунок про нього забув.

### Міграції для кожного клієнта, сусіди з великим навантаженням і вартість

**Міграції** ускладнюються зі зростанням ізоляції. Спільна схема: одна міграція — і готово. Схема чи база на клієнта: *ту саму* міграцію потрібно запускати для кожної схеми або бази. Для цього потрібна оркестрація (цикл за клієнтами з retries (повторні спроби) й відстеженням поступу), а часткове deployment створює ризик (частина клієнтів уже оновлена, частина — ні, тож код має підтримувати обидві форми, дотримуючись правил розширення/звуження з розділу [Міграції у масштабі](#migrations-at-scale-zero-downtime)). Для тисяч клієнтів це займає чимало часу.

**Сусіди з великим навантаженням** — зворотний бік щільного розміщення. За спільної схеми клієнт, який запускає великий звіт або неконтрольований запит, споживає CPU, I/O та підключення, потрібні іншим, і затримка зростає для всіх. Способи пом’якшення — від м’яких (rate limiting для клієнта, тайм-аути запитів, окремі пули підключень для важких операцій) до суворих (перенести проблемного клієнта до окремої бази — сама модель ізоляції є найнадійнішим захистом від галасливих сусідів). Саме тому великі клієнти часто отримують власну базу: вони платять за те, щоб *не ділити* ресурси.

**Масштабування й вартість для кожного клієнта** пов’язують масштабування з багатоклієнтською архітектурою. Шардинг і багатоклієнтськість перетинаються: коли багатоклієнтську систему шардять за `TenantId`, кожен шард фактично містить групу клієнтів, а перенесення клієнта з великим навантаженням до окремого шарду *і є повторним розподілом шардів*. Економіка становить основу SaaS-бізнес-моделі: щільне розміщення (багато клієнтів на ресурс) збільшує валову маржу, а ізоляція дає змогу обслуговувати корпоративних і регульованих клієнтів. Завдання досвідченого інженера — знайти для кожного клієнта правильний баланс: щільно розміщувати дрібних, ізолювати великих і тих, хто потребує захисту, та створити інструменти для переходу між моделями зі зростанням клієнта.

## Три запитання

**1.** Два запити зменшують кількість товару на складі через EF Core: завантажують сутність, виконують `Stock -= 1`, `SaveChanges`. За Read Committed обидва запити успішні, але одне зменшення губиться. Чому Read Committed цьому не запобігає, як натомість поводиться Repeatable Read у PostgreSQL і SQL Server та яке рішення ви випустили б у продакшен?

<details>
<summary>Відповідь</summary>

- **Read Committed гарантує зафіксовані дані, а не найновіші.** Обидва читання цілком правомірно побачили залишок 10. Запис обчислюється за значенням, яке тим часом змінилося: це гонка читання-модифікації-запису, від якої не захищає жодна гарантія читання.
- **Repeatable Read перетворює це на помилку.** У PostgreSQL знімок даних спричиняє помилку другого оновлення з SQLSTATE 40001. У SQL Server обидві транзакції зберігають спільні блокування, обидві запитують ексклюзивні — і монітор взаємоблокувань скасовує одну з них (1205). У будь-якому разі клієнт має повторити всю транзакцію, починаючи з читання.
- **Обирайте один із трьох варіантів залежно від конкуренції:**
  - атомарне умовне оновлення (`ExecuteUpdate` з `WHERE Stock >= 1` і перевіркою кількості змінених рядків): немає читання, гонки чи retry, але воно обходить відстежувач змін і перехоплювачі;
  - оптимістичний токен конкурентності (`[Timestamp]` у SQL Server, `xmin` у PostgreSQL) з обмеженою кількістю retries за `DbUpdateConcurrencyException`, коли доменній логіці потрібна сутність;
  - `SELECT … FOR UPDATE` у короткій транзакції, коли конкуренція висока й retries призводили б до постійних збоїв.
</details>

**2.** Запит місяцями виконувався за 5 мс, а тепер для одного клієнта займає секунду; нічого не розгортали. Назвіть три механізми, які змінюють план без змін коду, поясніть, як розпізнати їх у плані, та вкажіть довгострокове виправлення для кожного.

<details>
<summary>Відповідь</summary>

- **Застаріла статистика.** На етапі сканування оцінена й фактична кількість рядків відрізняється на порядки; команда `ANALYZE` (або оновлення статистики) виправляє оцінку. Довгострокове рішення: аналізувати дані явно після пакетного завантаження й налаштувати пороги autovacuum для таблиць, що зростають стрибками.
- **План побудовано для іншого значення.** У PostgreSQL `$1` в умові індексу й оцінка, розрахована для середнього значення, означають загальний план. У SQL Server значення параметрів, за якими скомпільовано план, відрізняються від фактичних під час виконання: це підглядання за параметрами. Довгострокове рішення — індекс, за якого один план підходить для будь-якого значення. Тимчасові заходи: `plan_cache_mode = force_custom_plan`, `OPTION (RECOMPILE)`, примусово заданий план у Query Store.
- **Очищена карта видимості або роздування таблиці.** В `Index Only Scan` кількість `Heap Fetches` зросла після значного обсягу записів або скасованої пакетної операції. Довгострокове рішення: забезпечити своєчасний запуск vacuum для цієї таблиці (`autovacuum_vacuum_scale_factor` для кожної таблиці) і не покладатися на сканування лише індексу для таблиць із частими записами.

Спільна звичка для всіх трьох випадків: перш ніж змінювати індекс, порівняйте план із його попередньою версією — вузол за вузлом.
</details>

**3.** Сторінки товарів кешуються в Redis із TTL 10 хвилин, а після deployment одночасно прогріваються всі 10 000 ключів. Кожні 10 хвилин після deployment навантаження на базу різко зростає, а зміну ціни видно із затримкою до 10 хвилин. Поясніть обидві проблеми й виправте їх, не вимикаючи кеш.

<details>
<summary>Відповідь</summary>

- **Сплеск — це масове одночасне промахування за розкладом.** Ключі, записані разом із однаковим TTL, одночасно закінчуються, і кожне промахування одночасно завантажує дані з бази. Додавайте до TTL кілька відсотків випадковості й об’єднуйте одночасні промахування за кожним ключем: HybridCache робить це в межах одного процесу, а коротке блокування `SET NX PX` пригнічує повторне завантаження між екземплярами (це блокування заради ефективності, а не правильності).
- **Застаріла ціна виникає через інвалідацію лише за TTL.** Видаляйте ключ у коді, який змінює ціну, *після* фіксації транзакції, щоб читач не закешував старий рядок, поки транзакція відкрита. Залиште TTL як страховку на випадок пропущеного запису або запускайте видалення через CDC.
- **Що залишиться.** Читач, який завантажив стару ціну безпосередньо перед фіксацією, усе ще може записати її до кешу вже після видалення ключа. Цей проміжок обмежений TTL; якщо це неприпустимо (наприклад, для ціни під час оформлення замовлення), читайте з бази, а не з кешу.
</details>

## Прийміть рішення

Багатоклієнтський SaaS працює на одному первинному вузлі PostgreSQL зі спільною схемою (`TenantId` у кожній таблиці). У піковий час CPU первинного вузла завантажений на 80%. Близько 70% навантаження становлять читання для панелей моніторингу, а один клієнт створює 30% усіх записів. Є три пропозиції:

1. Додати репліки для читання й спрямувати на них запити панелей.
2. Виконати шардинг за `TenantId`.
3. Перенести великого клієнта до окремої бази, залишивши решту у спільній.

<details>
<summary>Як це оцінює досвідчений інженер</summary>

**Спершу перевірте передумову.** Причиною 80% навантаження на CPU можуть бути кілька операторів. Перш ніж купувати інфраструктуру, відсортуйте `pg_stat_statements` за загальним часом і перегляньте плани найповільніших запитів: порада з розділу [Вертикальне й horizontal scaling](#vertical-vs-horizontal-scaling) — масштабуватися вгору, доки це справді не стане болісним.

**Ціна кожної пропозиції.**

- *Репліки:* кілька днів, без змін моделі даних. Вони поглинають більшу частину навантаження — читання панелей. Ціна — затримка: кожне читання відразу після запису має йти на первинний вузол, тому routing (маршрутизація) стає правилом у коді. У записів і далі один вузол.
- *Шардинг:* кілька місяців і двері в один бік. Він масштабує обсяг записів і даних, але запити між шардами перетворюються на розсилання й збирання, транзакції між шардами — на саги, а повторний розподіл шардів — на окремий проєкт.
- *Окрема база для великого клієнта:* кілька тижнів. Вона усуває сусіда з великим навантаженням, і зростання цього клієнта стає його власною проблемою. Ціна — ще один варіант обслуговування: міграції мають запускатися для двох цілей, а код мусить маршрутизувати запити за клієнтом.

**Що визначає вибір:** джерело навантаження. Переважають читання, тому репліки усувають більшу частину проблеми. Великий клієнт створює проблему сусіда з великим навантаженням, але це ще не проблема масштабування.

**Рішення.** Оптимізуйте найповільніші запити, додайте репліки для панелей і після запису тимчасово спрямовуйте читання на первинний вузол. Якщо частка записів великого клієнта продовжить зростати, заплануйте його перенесення. До шардингу переходьте лише тоді, коли записи або обсяг даних перевищать можливості одного первинного вузла після всіх цих кроків.

**Що змінило б рішення.** Переважання записів, набір даних, який більше не вміщується на одному вузлі, або вимога щодо розміщення даних великого клієнта — тоді йому потрібна окрема база незалежно від навантаження.
</details>

## Перевірте на роботі

**Перевірте.** Виберіть шлях запису, який змінює баланс, складські запаси або статус. Що запобігає втраченому оновленню: атомарний оператор, токен конкурентності, блокування чи нічого? Чи повторює код спробу після взаємоблокувань (1205 у SQL Server, 40P01 у PostgreSQL) і помилок серіалізації (40001)? Чи починається retry з самого початку транзакції? Для кешу: чи мають TTL випадковий розкид, чи версійовано ключі, яке значення `maxmemory-policy` і яка частка влучань? Для міграцій: вони запускаються під час старту чи окремим кроком pipeline, і чи показує історія останню несумісну зміну як розширення, а потім звуження?

**Виміряйте.** П’ять операторів із найбільшим сумарним часом за даними `pg_stat_statements` або Query Store; для кожного — оцінену й фактичну кількість рядків на найдорожчому вузлі. Якщо використовуються репліки, виміряйте затримку реплікації в піковий час.
