# Розділ 13: Git і CI/CD

Люди, які пишуть програмне забезпечення, і ті, хто його запускає, користуються спільним механізмом: системою version control (контроль версій), яка дає багатьом людям змогу безпечно змінювати ту саму кодову базу, та pipelines (конвеєри), які однаково збирають і тестують кожну зміну на кожній машині. Після цього розділу ви зможете підтримувати гілку актуальною, чистою та зручною для перевірки, не втрачаючи чужої роботи; відновлювати коміти, які здаються втраченими; налаштовувати SDK, його інструменти, аналізатори й форматувач так, щоб ваш ноутбук і збірка CI застосовували однакові правила; а також читати й писати pipeline GitHub Actions для сервісу .NET.

Обидві половини розділу спираються на один механізм. **Коміт — це незмінний знімок, ідентифікатор якого є хешем його вмісту, включно з ідентифікаторами батьківських комітів; гілка — лише рухома назва одного коміту.** З цього випливає все інше: відмінності між merge і rebase, reflog, те, чого `.gitignore` не може скасувати, і причина, чому довгі гілки створюють проблеми. А **CLI `dotnet` — це керівний інструмент**: ті самі команди, інструменти й аналізатори, що працюють у компіляторі, запускаються на кожній машині, тож pipeline — це ваш локальний процес збірки, записаний і запущений після кожного надсилання змін.

Розділ переходить від моделі Git до pipeline: спочатку Git, потім значення CI і CD, CLI `dotnet` і MSBuild, які викликає кожен pipeline, повний робочий процес GitHub Actions, версіонування, секрети й перевірки аналізу, а наприкінці — повсякденні інструменти. Azure Pipelines, публікація NuGet, стратегії deployment (розгортання), feature flags (прапорці функцій) і платформна інженерія розглядаються в [Розділі 26: Доставка й платформа](#chapter-26-delivery-and-platform).

## Git без непорозумінь

У Git багато команд, але модель, що лежить в їх основі, проста. Зрозумівши її, ви зможете передбачити роботу кожної команди.

### Модель об’єктів

Git — це сховище з адресацією за вмістом: кожен *об’єкт* ідентифікується хешем свого вмісту (типово SHA-1; в опублікованому плані наступної основної версії Git для нових репозиторіїв типовим стане SHA-256). У повсякденній роботі важливі три з чотирьох типів об’єктів.

**Blob** — це необроблені байти файлу без його назви й дозволів. Однаковий вміст зберігається один раз; змініть один байт — і отримаєте інший blob з іншим хешем.

**Tree** — це каталог: список записів, кожен із яких пов’язує назву й режим із хешем blob (файлу) або іншого tree (підкаталогу).

**Коміт** посилається на одне tree — повний знімок проєкту — і містить метадані: автора, того, хто створив коміт, часові позначки, повідомлення та хеші батьківських комітів (зазвичай один, два або більше для merge (злиття), жодного для першого коміту).

Головне: **коміт — це не diff, а повний знімок.** Git обчислює відмінності на вимогу, порівнюючи два знімки. Кожен коміт посилається на батьківський, тому коміти утворюють орієнтований ациклічний граф (DAG). Оскільки хеш батьківського коміту входить у вміст коміту, ідентифікатор коміту охоплює всю попередню історію. Змініть будь-що раніше в історії — і зміняться ідентифікатори всіх наступних комітів.

> **Ключова модель для розуміння:** гілка — не контейнер комітів. Це легкий рухомий *вказівник* на один коміт — буквально 40-символьний хеш у невеликому файлі під `.git/refs/heads/`. `HEAD` указує на гілку, яку ви зараз маєте вибраною. Тому створення гілки в Git відбувається миттєво: потрібно записати лише один файл.

Усе це можна побачити безпосередньо:

```bash
# Show the type of any object
git cat-file -t HEAD          # commit
# Show the contents of the commit object
git cat-file -p HEAD          # tree hash, parent hash, author, message
# Follow the tree hash from above
git cat-file -p <tree-hash>   # lists blobs and subtrees with their hashes
```

Оскільки гілки — це вказівники, «страшні» операції пересувають вказівники. Reset пересуває вказівник гілки. Rebase створює нові коміти й пересуває вказівник. Merge створює коміт і пересуває вказівник. Негайно нічого з уже закоміченого не знищується (див. нижче розділ про reflog).

### .gitignore

Перш ніж створити перший коміт, вирішіть, що *ніколи* не має потрапити до сховища об’єктів. У .NET це зазвичай результати збірки, стан IDE та все, що містить секрети.

```gitignore
# Build artifacts
bin/
obj/
[Dd]ebug/
[Rr]elease/
*.user

# Test and coverage output
TestResults/
coverage/
*.trx

# Local secrets and environment
appsettings.Development.local.json
.env
*.pfx

# IDE
.vs/
.idea/
```

> **Пастка:** `.gitignore` не дає додавати лише *не відстежувані* файли. Якщо ви вже закомітили `bin/` або файл із секретами, додавання їх до `.gitignore` нічого не змінить — Git і далі їх відстежуватиме. Щоб припинити відстеження, виконайте `git rm --cached <path>`, а потім створіть коміт із цим вилученням. Якщо секрет уже потрапив до коміту, він назавжди залишається в історії, доки ви її не перепишете; майже завжди швидше й безпечніше замінити секрет, ніж чистити історію.

### Стратегії роботи з гілками: GitFlow і розробка на основі trunk

**GitFlow** використовує довготривалі гілки з визначеними ролями: `main` містить випущений код, `develop` є гілкою інтеграції, а короткотривалі гілки `feature/*`, `release/*` і `hotfix/*` зливаються до них. Такий підхід пасує до окремих версійних випусків, наприклад застосунку, який клієнти встановлюють самостійно. Його слабке місце — відкладена інтеграція: `develop` і гілки функцій віддаляються одна від одної, а велике merge спричиняє болісні конфлікти — саме цього безперервна інтеграція покликана уникати.

**Розробка на основі trunk** передбачає, що всі розробники багато разів на день комітять зміни в одну гілку (`main`), а для неповної роботи використовують дуже короткотривалі гілки (на години, а не тижні), які швидко зливаються назад. Незавершену роботу приховують за feature flags ([Розділ 26: Feature flags](#feature-flags)), а не за довготривалими гілками. Команди, що безперервно розгортають зміни, обирають цей підхід, бо малі й часті merge обходяться дешево й мають низький ризик.

> **Рекомендація:** для сервісу, який ви розгортаєте безперервно, віддавайте перевагу розробці на основі trunk із короткотривалими гілками й feature flags. Стиль GitFlow залиште для програмного забезпечення, якому справді потрібно паралельно підтримувати кілька версій. Що довше живе гілка, то дорожче обійдеться її майбутнє merge.

### Merge і rebase

`git merge feature` у `main` створює новий *коміт merge* з двома батьківськими комітами й об’єднує обидві історії. Історія зберігається точно в тому вигляді, у якому її було створено, але граф стає менш наочним.

Коли ви перебуваєте у `feature` і виконуєте `git rebase main`, Git відкладає кожен коміт вашої гілки, пересуває вказівник гілки на вершину `main`, а потім *відтворює коміти поверх неї* один за одним. У результаті отримуємо лінійну історію, наче ви почали роботу від поточного стану `main`. Зверніть увагу: rebase створює *нові* коміти з новими хешами — початкові коміти залишаються поза історією.

```bash
# Merge approach: integrate main's updates into your feature branch
git switch feature
git merge main            # creates a merge commit if histories diverged

# Rebase approach: replay your work on top of the latest main
git switch feature
git rebase main           # linear history, new commit hashes
```

Коли застосовувати кожен підхід:

- **Rebase — щоб підтримувати власну гілку незавершеної функції актуальною** щодо `main` і впорядкувати нечисту локальну історію перед тим, як ділитися нею. Лінійну історію легше читати й аналізувати за допомогою bisect.
- **Merge — щоб інтегрувати завершену функцію у спільну гілку**, особливо з `--no-ff`, щоб коміт merge зафіксував об’єднання функції як цілого.

> **Золоте правило rebase:** не виконуйте rebase для комітів, які інші вже отримали. Оскільки rebase переписує історію (створює нові хеші), історія тих, хто почав роботу від старих комітів, розійдеться з вашою, а наступний `git pull` перетвориться на безлад із дубльованих комітів. Переписуйте власну історію вільно, але вважайте спільну історію незмінною.

> **Зверніть увагу.** **Чому після rebase гілку не можна звичайним способом надіслати до віддаленого репозиторію.** `git push` оновлює віддалену гілку, лише коли віддалений коміт є предком вашого (fast-forward). Після rebase ваші коміти стали новими об’єктами, тож старої вершини віддаленої гілки більше немає у вашій історії, і надсилання відхиляється. Це відхилення захищає від втрати даних: `--force` відкине все, що є у віддаленій гілці, але немає у вас, зокрема коміт колеги. У власній гілці pull request скористайтеся `git push --force-with-lease`: він перезапише гілку, лише якщо віддалений вказівник досі там, де його показував останній fetch. Фонове отримання змін (деякі IDE запускають його самі) непомітно оновлює цю очікувану позицію, тому додайте також `--force-if-includes`. У гілці, на основі якої працюють інші, взагалі не застосовуйте force — натомість виконайте merge.

### Інтерактивний rebase

Інтерактивний rebase допомагає впорядкувати історію перед тим, як ви нею поділитеся: змінити порядок комітів, об’єднати їх (squash), відредагувати або вилучити.

```bash
git rebase -i HEAD~4
```

У редакторі з’явиться список останніх чотирьох комітів із командою перед кожним:

```
pick a1b2c3d Add order validation
squash e4f5g6h Fix typo in validation
reword h7i8j9k Add repository method
drop  k0l1m2n Debug logging I forgot to remove
```

- `pick` залишає коміт без змін.
- `squash` (або `s`) додає коміт до попереднього, даючи змогу об’єднати повідомлення.
- `fixup` працює як squash, але повністю відкидає повідомлення доданого коміту.
- `reword` залишає коміт, але дає змогу змінити його повідомлення.
- `drop` вилучає коміт.

Так гілку з купою комітів «wip», «fix» і «actually fix» можна перетворити на кілька чистих комітів, які легко перевіряти. Зробіть це *до* відкриття pull request і ніколи не переписуйте спільні коміти після початку перевірки.

### Cherry-pick

`git cherry-pick <hash>` застосовує зміни з одного коміту до поточної гілки, створюючи новий коміт із тим самим diff, але новим батьківським комітом і хешем. Типовий випадок — термінове виправлення: помилку виправлено в `main`, і те саме виправлення потрібно внести до гілки `release/1.4`, не переносячи решту змін.

```bash
git switch release/1.4
git cherry-pick 9f8e7d6      # apply just that one fix here
```

> **Пастка:** cherry-pick тієї самої зміни в кілька гілок дублює логічну зміну під різними хешами. Коли ці гілки згодом зливаються, Git може розпізнати дубль, а може й ні; іноді це спричиняє несподівані конфлікти. Використовуйте cherry-pick свідомо для окремих виправлень, а не як звичний спосіб інтеграції.

### Розв’язання конфліктів

Конфлікт виникає, коли під час merge або rebase Git не може автоматично узгодити дві зміни тієї самої ділянки файлу. Git позначає файл маркерами конфлікту:

```csharp
<<<<<<< HEAD
    var timeout = TimeSpan.FromSeconds(30);
=======
    var timeout = TimeSpan.FromSeconds(60);
>>>>>>> feature/longer-timeout
```

Усе між `<<<<<<<` і `=======` — версія вашої поточної гілки; усе між `=======` і `>>>>>>>` — версія, яку вносять. Відредагуйте файл, залишивши правильний кінцевий стан, вилучіть маркери, а потім додайте файл до staging.

```bash
# After editing the file to its correct final form:
git add src/HttpClientFactory.cs
git status                 # confirm no remaining "Unmerged paths"
git merge --continue       # or git rebase --continue
# Escape hatch if things went wrong:
git merge --abort          # returns to the pre-merge state
```

> **Рекомендація:** робіть pull request невеликими. Імовірність конфліктів і складність їх розв’язання зростають разом із розміром і віком гілки. Pull request на 40 рядків, злитий сьогодні, навряд чи спричинить конфлікт; pull request на 4000 рядків, злитий наступного місяця, майже напевно його спричинить. Для складних випадків увімкніть інструмент merge (`git mergetool`) або скористайтеся тристороннім переглядом merge у своїй IDE.

### Reflog — ваша страховка

Git майже ніколи не втрачає *закомічену* роботу. Щоразу, коли змінюється `HEAD` — після commit, checkout, reset, rebase чи merge, — Git записує попередню позицію в **reflog**.

```bash
git reflog
# a1b2c3d HEAD@{0}: rebase finished
# f4e5d6c HEAD@{1}: checkout: moving to feature
# 9a8b7c6 HEAD@{2}: commit: Add order validation  <-- the state before I broke everything
```

Припустімо, ви виконали `git reset --hard` і втратили коміти або rebase пішов не за планом. Знайдіть у reflog хеш потрібного стану й відновіть його:

```bash
git reset --hard 9a8b7c6      # move the branch back to that commit
# or, to inspect without moving your branch:
git switch -c recovery 9a8b7c6
```

Записи reflog локальні й мають строк дії (типово 90 днів або 30 днів для комітів, на які вже не посилається жодна гілка), чого цілком достатньо для моменту «я знищив свою роботу». Обмеження стосується слова *закомічену*: `git reset --hard` остаточно відкидає незакомічені зміни, бо вони так і не стали об’єктами. Перед експериментом створіть коміт (або stash), і тоді кожну команду Git можна буде скасувати.

### Графічні інтерфейси Git

Командний рядок незамінний, але хороший графічний інтерфейс значно спрощує перегляд історії, додавання змін до staging і розв’язання конфліктів. **Fork** і **GitKraken** показують граф гілок і полегшують інтерактивний rebase; **lazygit** — швидкий термінальний інтерфейс для тих, хто працює в оболонці. Користуйтеся тим, що допомагає *розуміти* історію, а не уникати вивчення Git.

## Що насправді означає CI/CD

Абревіатура об’єднує три різні практики. Точне розуміння відрізняє тих, хто розуміє pipeline, від тих, хто просто повторює модне слово.

**Безперервна інтеграція (CI)** — це практика часто зливати роботу кожного розробника у спільну основну гілку — щонайменше щодня — і перевіряти кожне merge автоматичною збіркою та тестами. Мета — виявляти проблеми інтеграції за кілька хвилин після їх появи, поки зміна невелика й свіжа в пам’яті автора. CI за своєю суттю є *людською* практикою (часто інтегрувати зміни), яку підтримує автоматизація (збірка й тести після кожного надсилання).

**Безперервна доставка (CD)** розширює CI: кожна зміна, що проходить pipeline, автоматично готується й перевіряється як така, що *готова до deployment* у продакшен. Збірка створює артефакт, готовий до випуску, і може автоматично розгорнути його у staging, але остаточне deployment у продакшен залишається свідомим рішенням людини в один клік.

**Безперервне deployment** прибирає навіть цю останню кнопку. Кожна зміна, що проходить усі автоматизовані перевірки, автоматично потрапляє в продакшен без участі людини. Для цього потрібна дуже висока довіра до набору тестів і безпечні методи deployment (прапорці функцій, канаркові випуски, швидкий відкат).

> **Важлива для співбесіди й практики відмінність:** безперервна *доставка* залишає людську перевірку перед продакшеном; безперервне *deployment* — ні. Обидва підходи спираються на однаково ретельний автоматизований pipeline.

## Автоматизація збірки за допомогою CLI dotnet

Кожен pipeline у цьому розділі покладається на CLI `dotnet` — той самий інструмент, яким ви користуєтеся локально. Спочатку опануйте його: consistency (узгодженість) локальної збірки й CI усуває цілий клас проблем «у мене на машині працює».

```bash
dotnet restore                       # download NuGet dependencies
dotnet build -c Release --no-restore # compile; skip a redundant restore
dotnet test  -c Release --no-build   # run tests against the built output
dotnet publish -c Release -o ./out   # produce a self-contained, deployable app
dotnet pack  -c Release -o ./nupkgs  # produce a NuGet package (.nupkg)
```

Прапорці `--no-restore` і `--no-build` важливі в CI: кожен етап задано явно, тож CLI не запускає непомітно попередні кроки повторно й не марнує час. `dotnet publish` збирає застосунок, його залежності й конфігурацію runtime (середовище виконання) в папку, готову до копіювання на сервер або в контейнер. `dotnet pack` створює бібліотеки для розповсюдження через NuGet.

### MSBuild, Directory.Build.props і централізоване керування пакетами

Під CLI працює **MSBuild** — рушій, який читає файли `.csproj` (це файли MSBuild у форматі XML) і виконує збірку. Зазвичай ви не запускаєте його безпосередньо, але розуміння, що `dotnet build` *і є* MSBuild, пояснює, де зберігається конфігурація збірки.

Вказувати ті самі властивості в кожному `.csproj` нудно й ненадійно. Проблему розв’язує **`Directory.Build.props`**: розмістіть такий файл у корені репозиторію, і MSBuild автоматично імпортує його в кожен проєкт нижче в дереві каталогів.

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>
```

Тепер кожен проєкт успадковує nullable reference types і найновішу версію мови, а також — що важливо для охайного CI — налаштування «попередження вважаються помилками». Тож неохайне попередження зупинить збірку, а не залишиться непоміченим.

**Централізоване керування пакетами (CPM)** так само централізує версії NuGet. Замість закріплювати версії в кожному проєкті, оголосіть їх один раз у `Directory.Packages.props`:

```xml
<Project>
  <PropertyGroup>
    <ManagePackageVersionsCentrally>true</ManagePackageVersionsCentrally>
  </PropertyGroup>
  <ItemGroup>
    <PackageVersion Include="Serilog.AspNetCore" Version="8.0.1" />
    <PackageVersion Include="FluentValidation" Version="11.9.0" />
  </ItemGroup>
</Project>
```

Тоді в окремих проєктах посилання на пакети вказують *без версії*:

```xml
<PackageReference Include="Serilog.AspNetCore" />
```

> **Рекомендація:** якомога раніше запровадьте `Directory.Build.props` і централізоване керування пакетами. Це запобігає розбіжностям версій, коли різні проєкти одного рішення підтягують несумісні версії тієї самої бібліотеки — одній із найприкріших проблем налагодження у великих кодових базах.

### Інструменти .NET: глобальні, локальні й одноразові

CLI `dotnet` — це керівний інструмент. Вбудовані команди постачаються із SDK: `build`, `test`, `publish`, `format`, `user-secrets`, `watch`. Решта — це **інструменти .NET**, пакети NuGet із консольною програмою; ви самі обираєте, де вони житимуть:

- **Глобальні** (`dotnet tool install -g dotnet-ef`): встановлюються для користувача в `~/.dotnet/tools` (`%USERPROFILE%\.dotnet\tools` у Windows), який уже входить до `PATH`. Зручно, але на кожній машині може бути своя встановлена кимось версія.
- **Локальні**: `dotnet new tool-manifest` створює `.config/dotnet-tools.json`; `dotnet tool install dotnet-ef` (без `-g`) закріплює версію в ньому; після свіжого клонування або на агенті CI виконайте `dotnet tool restore`. Додайте маніфест до коміту: CLI запускатиме саме перелічені в ньому інструменти.
- **Одноразові** (SDK .NET 10): `dnx dotnet-counters monitor -p 1234` (або `dotnet tool exec`) запускає інструмент без встановлення й бере версію з найближчого маніфесту, якщо він є.

Команду інструмента, що починається з `dotnet-`, також можна викликати як `dotnet <rest>`. Тому `dotnet ef` здається вбудованою командою, хоча це не так.

> **Зверніть увагу.** **Звідки беруться `dotnet-counters`, `dotnet-trace` і `dotnet-dump` та чому вони не бачать ваш контейнер.** Це інструменти .NET із NuGet, а не частина SDK чи runtime. Кожен із них взаємодіє із запущеним процесом через *діагностичний порт* runtime: іменований канал `dotnet-diagnostic-{pid}` у Windows і сокет домену Unix `dotnet-diagnostic-{pid}-…-socket` у `$TMPDIR` (або `/tmp`) у Linux і macOS. Інструмент на хості не може знайти процес у контейнері, бо цей сокет розташовано в `/tmp` контейнера, а PID належить його простору імен. Запустіть інструмент усередині контейнера (у документації є однофайлові збірки для образів без SDK) або спільно використовуйте `/tmp` із sidecar-контейнером. `DOTNET_EnableDiagnostics=0` закриває порт, а разом із ним — доступ усіх цих інструментів.

## Платформи CI/CD

Ці ідеї реалізовано на кількох платформах. Вони різняться моделлю розміщення й синтаксисом, але самі поняття залишаються тими самими.

**GitHub Actions** — автоматизація, що реагує на events (події) й зберігається у вашому репозиторії GitHub. Робочі процеси — це YAML-файли в `.github/workflows/`. Екосистема повторно використовуваних *actions* із Marketplace дає змогу швидко збирати pipelines. Це типовий вибір для проєктів на GitHub. Докладно розглянемо його нижче.

**Azure DevOps Pipelines** — зрілий продукт Microsoft, глибоко інтегрований з екосистемою .NET, цілями deployment Azure та корпоративними функціями, як-от середовища, затвердження й групи змінних на основі Azure Key Vault. Pipelines описують у `azure-pipelines.yml` за допомогою `stages`, `jobs` і `steps` або налаштовують у класичному візуальному редакторі. Ця платформа поширена в корпоративних командах .NET.

**GitLab CI/CD** вбудований у GitLab і налаштовується у файлі `.gitlab-ci.yml`. Він використовує `stages` і `jobs` із моделлю runner та відомий цілісним досвідом роботи в одному застосунку: від коду й CI до реєстру та deployment.

**Jenkins** — ветеран серед серверів автоматизації з open source (відкритий код). Він надзвичайно гнучкий завдяки екосистемі плагінів і pipelines `Jenkinsfile`, розміщується на власних серверах і досі широко використовується в організаціях із наявною інфраструктурою. Компроміс — операційні витрати: сервер і його агенти потрібно самостійно запускати, оновлювати й захищати.

Тригери, завдання, кроки, артефакти, кешування, секрети й середовища є на всіх чотирьох платформах. Вивчіть їх один раз — і зможете читати конфігурацію будь-якої з цих платформ.

## Повний робочий процес GitHub Actions для .NET

Створімо справжній pipeline, який відновлює залежності, збирає, тестує й публікує застосунок .NET, створює контейнер і розгортає його. Потім розберемо його по частинах.

```yaml
name: build-test-deploy

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

env:
  DOTNET_VERSION: '10.0.x'
  DOTNET_SKIP_FIRST_TIME_EXPERIENCE: true
  DOTNET_NOLOGO: true

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        configuration: [ Debug, Release ]
    steps:
      - name: Check out code
        uses: actions/checkout@v4

      - name: Set up .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Cache NuGet packages
        uses: actions/cache@v4
        with:
          path: ~/.nuget/packages
          key: nuget-${{ runner.os }}-${{ hashFiles('**/packages.lock.json', '**/*.csproj') }}
          restore-keys: |
            nuget-${{ runner.os }}-

      - name: Restore
        run: dotnet restore

      - name: Build
        run: dotnet build --configuration ${{ matrix.configuration }} --no-restore

      - name: Test
        run: >
          dotnet test --configuration ${{ matrix.configuration }} --no-build
          --logger trx --results-directory ./TestResults
          --collect:"XPlat Code Coverage"

      - name: Upload test results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results-${{ matrix.configuration }}
          path: ./TestResults

  publish-and-containerize:
    needs: build-and-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4

      - name: Set up .NET
        uses: actions/setup-dotnet@v4
        with:
          dotnet-version: ${{ env.DOTNET_VERSION }}

      - name: Publish
        run: >
          dotnet publish src/OrderApi/OrderApi.csproj
          --configuration Release --output ./publish

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

  deploy-production:
    needs: publish-and-containerize
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://api.example.com
    steps:
      - name: Deploy to production
        run: |
          echo "Deploying image ghcr.io/${{ github.repository }}:${{ github.sha }}"
          # e.g. az webapp deploy, kubectl set image, helm upgrade, etc.
        env:
          DEPLOY_TOKEN: ${{ secrets.PRODUCTION_DEPLOY_TOKEN }}
```

Розберімо його будову.

**Тригери (`on`).** Робочий процес запускається після надсилання змін до `main` і створення pull request із цільовою гілкою `main`. Перевірки PR дають змогу отримати успішний статус до merge; після надсилання змін до `main` робочий процес доходить аж до deployment. Обмеження тригерів не дає марнувати хвилини на несуттєві events.

**Завдання та залежності (`needs`).** Три завдання виконуються послідовно, бо кожне має `needs` попереднього. Завдання без зв’язку `needs` виконуються паралельно на окремих runner-ах. Умова `if: github.ref == 'refs/heads/main'` пропускає завдання публікації для pull request: PR перевіряються, але збірка й публікація відбуваються лише з `main`.

**Матриця (`strategy.matrix`).** Завдання збірки й тестування виконується двічі паралельно — один раз для кожної `configuration`. Матриці можна розширити кількома вимірами (ОС, версія .NET, рушій бази даних); завдяки їм можна недорого перевіряти комбінації. Кожна комірка матриці — окремий runner.

**Кешування (`actions/cache`).** Завантажувати пакети NuGet з інтернету під час кожного запуску повільно. Дія кешування зберігає `~/.nuget/packages` із ключем, обчисленим на основі хешів файлів проєкту й блокувальних файлів. Якщо ці файли не змінювалися, ключ збігається, і пакети відновлюються з кешу за кілька секунд. Резервний `restore-keys` дає змогу використати кеш із частковим збігом, навіть якщо точного ключа немає.

**Секрети.** `${{ secrets.PRODUCTION_DEPLOY_TOKEN }}` читає зашифроване значення, збережене в налаштуваннях репозиторію або середовища. Секрети ніколи не виводяться в журнали (GitHub маскує їх) і ніколи не містяться в YAML. `GITHUB_TOKEN` — спеціальний секрет, який автоматично створюється для поточного запуску й обмежений його межами.

**Середовища.** Блок `environment: production` прив’язує завдання deployment до іменованого середовища, для якого можна встановити правила захисту: обов’язкове затвердження рецензентом, таймер очікування й секрети, доступні лише цьому середовищу. Так реалізується людська перевірка перед безперервною *доставкою*: налаштуйте для `production` обов’язкове ручне затвердження, і завдання призупиниться, поки хтось не натисне кнопку підтвердження.

**Дозволи.** Блок `permissions` дотримується принципу найменших привілеїв: завдання створення контейнера отримує `packages: write`, бо публікує образ, і більше нічого.

## Семантичне версіонування й GitVersion

Номер версії — це контракт. **Семантичне версіонування (SemVer)** формалізує його як `MAJOR.MINOR.PATCH`:

- **MAJOR** збільшується після несумісної зміни — наявні consumer (споживач) мають змінити свій код.
- **MINOR** збільшується після додавання функцій зі збереженням зворотної сумісності.
- **PATCH** збільшується після виправлень помилок зі збереженням зворотної сумісності.

До попередніх версій додають суфікс, наприклад `2.4.0-beta.1`; така версія впорядковується *перед* фінальною `2.4.0`. Дотримання SemVer дає consumers змогу безпечно задавати діапазони залежностей: `[2.0,3.0)` означає «будь-яка версія 2.x, але не оновлювати автоматично до несумісної межі 3.0».

Визначати й записувати номер версії вручну нудно й легко помилитися. **GitVersion** обчислює версію автоматично на основі історії Git — тегів, назв гілок і кількості комітів, — тож той самий коміт завжди дає ту саму версію, а номер збільшується послідовно.

```bash
dotnet tool install --global GitVersion.Tool
dotnet-gitversion /showvariable SemVer   # e.g. 2.4.0-feature-orders.5
```

У CI це значення зберігають і передають у `dotnet pack -p:Version=$VERSION`, щоб артефакти отримували версію детерміновано з системи version control, а не залежали від того, чи хтось не забув збільшити номер.

## Секрети в pipelines

Головне правило: **секрети не потрапляють до системи version control.** Ні в `appsettings.json`, ні в закоміченому `.env`, ні «тимчасово» у файлі конфігурації. Щойно секрет потрапив до історії Git, його скомпрометовано, бо історія поширюється до всіх, хто клонує репозиторій.

Де зберігаються секрети:

- **Локально й у продакшені** — у user-secrets і керованому сховищі, доступ до якого надає managed identity (керована ідентичність), як пояснено в [Розділі 12: Керування секретами](#secrets-management).
- **У CI** — у зашифрованому сховищі секретів платформи: секретах GitHub Actions, групах змінних Azure DevOps (в ідеалі — на основі Azure Key Vault), змінних GitLab CI/CD. Під час виконання їх передають як environment variables (змінні середовища) й маскують у журналах, як `secrets.PRODUCTION_DEPLOY_TOKEN` у наведеному вище робочому процесі.

> **Рекомендація:** додайте до pipeline автоматичне сканування секретів (GitHub secret scanning, Gitleaks або `git-secrets` як pre-commit hook), щоб випадково закомічений ключ API виявився до merge. Якщо витік стався, *негайно замініть секрет* — вилучити його з історії недостатньо, бо копії та форки можуть його зберегти.

## Перевірки статичного аналізу в CI

Pipeline, який запускає лише тести, перевіряє правильність, але не якість коду. Перевірки статичного аналізу об’єктивно підтримують якість, щоб стандарти не погіршувалися через брак часу. Є три рівні: аналізатори всередині компілятора, форматувач і перевірка якості на сервері.

### Аналізатори й `.editorconfig`

Усередині IDE та компілятора за правила відповідають:

- **Аналізатори Roslyn** працюють у компіляторі. Вони постачаються із SDK (правила `CAxxxx`), доступні в пакетах NuGet, а також їх можна створювати власноруч. Вони показують проблеми як попередження збірки, тож без додаткових зусиль інтегруються з CI.
- **`.editorconfig`** — єдине джерело правил стилю. Файл міститься в репозиторії, його розуміють VS, Rider і `dotnet format`; у ньому можна налаштувати правила іменування, використання `var` і серйозність аналізаторів для кожної теки.
- **ReSharper** (плагін для VS) додає поглиблені перевірки, масові рефакторинги й профілі очищення коду.
- **StyleCop.Analyzers** забезпечує послідовне форматування коду й документацію.
- **SonarLint / SonarQube** виявляє помилки, потенційно небезпечні місця й проблеми стилю коду; серверний компонент відстежує тенденції якості й перевірки «нового коду» в команді.

> **Порада:** якомога раніше додайте `.editorconfig` до репозиторію й переведіть кілька важливих правил аналізаторів у стан `error` (наприклад, `dotnet_diagnostic.CA2007.severity` для коду бібліотеки). Попередження ігнорують; помилки, що блокують збірку, виправляють.

> **Зверніть увагу.** **Що саме перевіряє збірка.** Аналізатори працюють усередині компілятора, тому діагностика є попередженням збірки всюди, де її запускають: і в IDE, і в CI. Але типово (`AnalysisMode` зі значенням `Default`) як попередження ввімкнено лише невеликий набір правил `CA`; `<AnalysisMode>Recommended</AnalysisMode>` або `All` вмикає більше правил. Правила стилю (`IDExxxx`) взагалі не запускаються в `dotnet build`, доки не встановлено `<EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>`. А `AnalysisLevel` типово має значення `latest`: нова версія SDK може ввімкнути нові попередження, які `TreatWarningsAsErrors` перетворить на помилки збірки без жодної зміни коду. Зафіксуйте `AnalysisLevel` (наприклад, `10.0`) і змінюйте його свідомо.

### Форматування в CI

Суперечки про стиль марнують час перевірки коду. `dotnet format` читає `.editorconfig` і переформатовує код за його правилами. Додайте `dotnet format --verify-no-changes` до CI: збірка завершиться помилкою, якщо хтось забув відформатувати код. Тоді форматуванням займається машина, а не рецензент.

### SonarQube і перевірки покриття

**SonarQube** (або SonarCloud) виконує поглиблений статичний аналіз: шукає помилки, проблеми стилю коду, потенційно небезпечні місця, дублювання й надмірну складність, а також застосовує **перевірку якості** — набір умов успіху або невдачі, наприклад «немає нових критичних проблем» і «покриття нового коду ≥ 80%». Якщо перевірку не пройдено, pipeline завершується невдало й блокує merge. Оскільки оцінюється саме *новий* код, якість застарілої кодової бази можна поступово поліпшувати, не намагаючись одразу погасити всі наявні проблеми.

**Пороги покриття** гарантують, що тести справді виконують код. Зберіть дані про покриття під час `dotnet test` (за допомогою Coverlet або колектора `XPlat Code Coverage` із наведеного вище робочого процесу), а потім завершіть збірку помилкою, якщо покриття нижче за поріг:

```bash
dotnet test --collect:"XPlat Code Coverage" \
  -- DataCollectionRunSettings.DataCollectors.DataCollector.Configuration.Threshold=80
```

Типовий етап перевірки якості в pipeline запускає сканер Sonar навколо кроків збірки й тестування, передає результати та очікує рішення перевірки:

```yaml
      - name: SonarQube scan
        run: |
          dotnet sonarscanner begin /k:"order-api" \
            /d:sonar.host.url="${{ secrets.SONAR_HOST }}" \
            /d:sonar.token="${{ secrets.SONAR_TOKEN }}" \
            /d:sonar.cs.opencover.reportsPaths="**/coverage.opencover.xml"
          dotnet build -c Release
          dotnet test -c Release --collect:"XPlat Code Coverage"
          dotnet sonarscanner end /d:sonar.token="${{ secrets.SONAR_TOKEN }}"
```

> **Рекомендація:** застосовуйте перевірки якості до *нового* коду, а не вимагайте, щоб величезна застаріла кодова база раптом досягла 90% покриття. Поступове посилення вимоги — «не погіршувати» — реальне й постійно поліпшує кодову базу; нереалістичну абсолютну вимогу просто вимкнуть, щойно вона заблокує термінове виправлення.

> **Зв’язок із підсумковим проєктом:** практичне застосування цього розділу — Кроки 4 (CI/CD із GitHub Actions) і 8 (deployment за допомогою Infrastructure as Code) проєкту ShopCore. Ви створите робочий процес, який перевіряє кожен PR і публікує образи з тегами, а потім розгорне ці образи в середовищі, створеному за допомогою Terraform. Див. [Розділ 44](#chapter-44-capstone-one-project-growing-up).

## Повсякденний набір інструментів

Нижче наведено інструменти, якими сучасна команда .NET користується під час роботи зі збіркою. Знайте, яку проблему розв’язує кожен, щоб обирати свідомо, а не за звичкою.

### IDE: Visual Studio, Rider і VS Code

**Visual Studio** (Windows) — це потужне середовище. Його налагоджувач найкращий у своєму класі, особливо для складних сценаріїв: налагодження змішаного режиму, дампів пам’яті, IntelliTrace і засобів діагностики процесора та виділення пам’яті. Якщо ви працюєте з WPF/WinForms, складними конфігураціями MSBuild або вам потрібні найпоглибленіші засоби налагодження, з ним важко зрівнятися. Недолік — він ресурсоємний і доступний лише у Windows.

**JetBrains Rider** — кросплатформене середовище й для багатьох оптимальний інструмент на щодень. Воно поєднує рушій аналізу ReSharper зі швидкою моделлю рішень, чудовими засобами рефакторингу й підтримкою EF Core, Docker, баз даних і запуску модульних тестів в одному продукті. На великих рішеннях Rider часто працює жвавіше за VS і однаково працює в macOS, Linux і Windows.

**VS Code + C# Dev Kit** — легкий і розширюваний варіант. На основі мовного сервера Roslyn C# Dev Kit надає оглядач рішень, інтеграцію з тестами й IntelliSense, якого вже цілком досить для повсякденної роботи. Він особливо зручний для мікросервісів, багатомовних репозиторіїв (.NET API поруч із фронтендом React) і віддаленої розробки в контейнерах через Dev Containers і SSH.

> **Порада:** добирайте інструмент до завдання, а не до особистої відданості бренду. Багато senior-розробників тримають VS Code відкритим для швидких змін і скриптів, а для серйозного рефакторингу чи налагодження запускають Rider або Visual Studio.

### Тестування API

Засоби перевірки HTTP-кінцевих точок:

- **Файли `.http`** зберігаються в репозиторії й запускаються безпосередньо у VS, Rider і VS Code. Оскільки вони версіонуються разом із кодом, це ще й виконувана документація. Використовуйте їх для запитів, якими команда ділиться і які зберігає в репозиторії.
- **Postman** — функціонально насичений стандарт із середовищами, сценаріями, колекціями й mock-серверами, хоча він дедалі активніше просуває хмарні облікові записи.
- **Insomnia** — легша й простіша альтернатива з гарною підтримкою GraphQL.
- **Bruno** зберігає колекції як звичайні файли у вашому Git-репозиторії — це значна перевага для версіонування й уникнення залежності від одного постачальника.

> **Порада:** для всього, на що покладається команда, файли `.http` або Bruno в репозиторії кращі за приватний робочий простір Postman, якого більше ніхто не бачить.

### Створення діаграм

Діаграми як код кращі за інструменти з перетягуванням, бо їх можна порівнювати й версіонувати. **Mermaid** відображається безпосередньо в Markdown GitHub/GitLab, тому діаграми послідовностей і потоків зберігаються поруч із кодом. **PlantUML** має більше можливостей для докладних UML-діаграм. **Модель C4** (Context, Container, Component, Code) дає спільну лексику для опису архітектури на різних рівнях деталізації; її відображають такі інструменти, як Structurizr або C4-PlantUML.

> **Порада:** діаграма послідовностей Mermaid у README заощадить десять хвилин пояснень біля дошки кожному новому учасникові команди.

### Інструменти для локальної розробки

Надійні локальні середовища не дають виникнути проблемі «у мене на машині працює». **Testcontainers** запускає в Docker справжні залежності (Postgres, Redis, Kafka) для інтеграційних тестів, а потім зупиняє їх; більше не потрібні спільні тестові бази даних, конфігурація яких постійно змінюється ([Розділ 8: Testcontainers для .NET](#testcontainers-for-net) пояснює, як це робити). **Azurite** локально емулює Azure Storage (Blob, Queue, Table), а **LocalStack** — широкий набір сервісів AWS. Це дає змогу розробляти й тестувати інтеграції з хмарою без мережі та в CI.

## Усе разом

Упевнена робота з Git і CI складається з невеликих, добре зрозумілих рішень. Ви тримаєте гілки короткотривалими й постійно інтегруєте зміни, бо гілка — лише вказівник, а відкладена інтеграція накопичує проблеми. Перед перевіркою коду впорядковуєте історію інтерактивним rebase і вважаєте спільну історію незмінною, знаючи, що reflog допоможе виправити помилки. Збірку описуєте командами `dotnet`, які однаково працюють на ноутбуці й у CI; закріплюєте інструменти в маніфесті, централізуєте конфігурацію за допомогою `Directory.Build.props` і централізованого керування пакетами, а артефакти версіонуєте передбачувано через SemVer і GitVersion. Pipeline відновлює залежності з кешу, тестує різні конфігурації в матриці, перевіряє аналізатори, форматування, покриття й статичний аналіз, зберігає всі секрети на платформі та створює один незмінний артефакт.

Жодна з цих практик не є екзотичною. Їхня сила накопичується: разом вони перетворюють випуск програмного забезпечення з events, що нервує, на звичний, нудний і зворотний процес. Про безпечне потрапляння артефакту в продакшен (стратегії deployment, feature flags, Azure Pipelines і вимірювання доставки) читайте в [Розділі 26: Доставка й платформа](#chapter-26-delivery-and-platform).

## Перевірте на роботі

**Перевірте.** Чотири команди у власному репозиторії:

- `git log --graph --oneline -40 main`: один рядок невеликих злиттів означає, що на практиці застосовується розробка на основі trunk; довгі паралельні лінії — це гілки, що жили тижнями.
- `git ls-files | grep -E '(^|/)(bin|obj)/|\.user$|\.env$'`: усе, що виведено, — це результати збірки, особисті файли IDE або секрети, які відстежує репозиторій.
- Знайдіть `.config/dotnet-tools.json`. CI має запускати `dotnet tool restore`, а не `dotnet tool install -g` із найновішою на той день версією.
- Перевірте, чи запускає CI `dotnet format --verify-no-changes` і чи збирає проєкт із налаштуванням «попередження — це помилки». Якщо ні, аналізатори лише радять.

**Зробіть.** У тимчасовій копії репозиторію виконайте `git reset --hard HEAD~3`, а потім відновіть три коміти з `git reflog` — перш ніж доведеться робити це насправді.

**Виміряйте.** Для останніх десяти злитих pull request запишіть кількість змінених рядків і години від першого коміту до merge. Кілька днів або кілька сотень рядків — це масштаб, за якого перевірки перетворюються на «LGTM», а конфлікти починають коштувати дорожче за саму зміну.
